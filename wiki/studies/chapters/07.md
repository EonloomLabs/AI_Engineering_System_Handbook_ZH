## 1. 把模型服务视作有状态协议，而不是一个字符串函数

简单接口可以是`answer = model(prompt)`，但真实Agent需要区分文本消息、函数调用、函数结果、推理或压缩状态以及响应终态。某些接口可以由服务保存历史，某些要求客户端回传项目；隐私配置、模型能力与产品接口共同决定可用方式。适配层应保留结构化对象，不应只提取文本后把其余项目全部丢弃。[[N01]](../sources.html#N01 "本地来源与核查范围")[[N06]](../sources.html#N06 "本地来源与核查范围")[[N17]](../sources.html#N17 "本地来源与核查范围")

例如一个响应可能同时有说明文本和两个工具调用。如果代码只判断“有文本就结束”，工具永远不会执行；若把整个响应转成字符串塞回历史，调用ID、角色和服务需要的状态就失去了原始类型。公开接口要求保留的不透明状态，应原样保存或按文档引用，不能自造摘要代替。

工具调用是模型提出的动作候选。它的名称、参数和ID进入验证器；验证器返回可执行的内部命令；执行器完成实际动作；结果再以匹配的调用ID反馈。名称存在、参数语法正确、权限允许、状态新鲜、执行成功，是五个独立判断。

## 2. 流不是以完整字符或JSON对象为单位抵达

先认识这里的对象与符号

[SSE、chunk、delta：不同的分片层](../../concepts.html#concept-sse)
:   SSE是服务端发送事件的文本协议；网络chunk是这次收到的一段字节；delta是某个输出项的增量内容。三者边界不保证重合。一个完整事件也未必意味着完整工具参数。参数可能先收到{"path":"a，后收到.py"}；必须组装并等协议规定的完成条件，不能见到片段就执行。

网络字节流可以把一个中文字符、一个JSON转义序列或SSE边界拆开。正确解析顺序应是：字节增量UTF-8解码，按SSE行规则组装事件，遇到空行形成完整事件，拼接data字段，然后解析该事件JSON，再分派事件类型。[[N19]](../sources.html#N19 "本地来源与核查范围")

先认识这里的对象与符号

[LF、CRLF与EventSource](../../concepts.html#concept-linebreak)
:   LF是换行字符，CRLF是回车再换行的组合。SSE规定事件行与空行的解释；EventSource是浏览器接收SSE的接口。只解析一种分隔符的教学代码不等于完整协议实现。实际网络片段可能恰好把CR和LF分开送达，解析器应按已实现的协议规则组装，不能直接把每个网络片段当一条事件。

本书实现支持分块字节、CRLF换行和多data行，并对未结束的最后一事件报截断。测试把中文内容逐字节送入，验证不会因多字节切分损坏文本。不要对每个网络chunk直接`json.loads`；chunk只是传输边界，不是协议边界。

同理，`arguments.delta`只是参数的增量，可能尚不闭合。模型先输出`{"path":"src/`时，不应提前读取一个目录；看到字符串中途的危险片段，也不能简单通过字符串替换“修复”参数。等待约定的输出项完成，再做完整解析与授权。

## 3. 输出项完成与整个响应完成

本书教学适配器采用保守策略：收集完成的调用项，并在收到响应成功终态后才允许执行；响应失败或截断，禁止执行尚未提交的候选。这是参考实现选择，不意味着所有商业客户端都必须等待相同节点。某些系统可在完整工具项到达后调度，但仍需要处理后续中断和幂等性。[[N05]](../sources.html#N05 "本地来源与核查范围")[[N19]](../sources.html#N19 "本地来源与核查范围")

`Calls`对象把同一调用ID的增量与完成事件关联。若同一ID被重复用于不同内容，返回冲突；如果收到响应失败，已收集但未执行的调用不会被默默执行。协议层还应区分未知事件（可能向前兼容忽略）与关键缺失（必须失败），不能对所有异常都返回空文本后宣称成功。

生产接入还需要事件大小上限、解析超时、连接闲置超时、取消传播和重连语义。重连不是从头盲目执行所有工具，尤其当上一轮已经产生外部副作用时。

### “输出停止”与“任务成功”要画在不同状态线上

**本例条件：**独立工具任务：模型先要求写入文件，再需要测试验证。下面列出几种停止事件，它们不是同一条时间线上的连续步骤。

响应结束
:   本次模型输出不再继续到来。

工具完成
:   获准动作已产生可核验结果。

任务完成
:   用户要求的验收条件已成立。

“输出停止”与“任务成功”要画在不同状态线上

| 观察到的事件 | 你能够确认 | 你不能据此确认 |
| --- | --- | --- |
| 出现EOS | 本次序列选择了终止标记 | 文件一定已正确修改 |
| 达到max\_output\_tokens | 生成预算用完 | JSON完整、答案正确 |
| 工具参数生成完 | 可以尝试解析/校验 | 工具已经执行 |
| 测试通过并绑定当前版本 | 本组检查对当前工件有效 | 没覆盖的需求也自动满足 |

各行是独立对象或条件的对照，不暗示上一行的结果自动进入下一行。

#### 怎样把图中的变化读明白

把“模型结束、工具结束、任务完成”设成不同字段，才能避免结束标记触发假成功。

长度限制可能把JSON截在半个字段，应该记录不完整而不是把收到的文本强行当合法调用。

工具调用响应结束后，外层Agent仍可能要执行、回填、再次调用模型。内外两种循环的停止条件不同。

**不要混淆：**取消请求不证明远端副作用已取消；取消后仍应核对在途操作状态。

## 4. Schema验证能保证到哪里

先认识这里的对象与符号

[Schema与Structured Outputs](../../concepts.html#concept-schema)
:   Schema是一份字段和类型等结构规则；结构化输出机制让模型更容易返回符合规则的数据。字段合法仍不等于目标文件存在、已授权或业务正确。独立例：要求path为字符串；{"path":3}类型不合规则，{"path":"missing.py"}虽结构合规则仍可能找不到文件。

JSON Schema可以约束字段类型、枚举、必填项和额外字段，但不能判断某个订单是否属于当前用户，也不能证明`path`指向的是用户授权的仓库。结构化输出是协议可靠性的基础，不是业务可信性的终点。[[N18]](../sources.html#N18 "本地来源与核查范围")

应把参数转换成类型明确的内部对象，再验证语义。读取文件工具至少要限定根目录、允许的文件类型、最大字节数、符号链接策略和编码失败行为。更新工具还要比较期望版本，以免把模型基于旧代码生成的修改写到新代码上。

异常结果应该具有可行动的含义。`not_found`可以指导换定位方式；`permission_denied`表示不能通过换拼写绕过；`stale_version`要求重新读取；`timeout_unknown`说明外部动作是否发生尚不确定。把它们都包成“工具失败，请重试”，会诱导错误恢复策略。

### Schema通过后，还有业务合法性与授权两层检查

**本例条件：**独立工具delete\_file要求path为字符串、recursive为布尔值。输入{"path":"secrets/key","recursive":false}符合类型，但并未因此获准删除。

语法合法
:   JSON能被解析。

结构合法
:   字段与类型满足Schema。

语义合法
:   目标存在、适用且在授权范围。

Schema通过后，还有业务合法性与授权两层检查

| 关卡 | 检查对象 | 此例结果 |
| --- | --- | --- |
| 解析 | 是否完整JSON | 通过 |
| Schema | path:str；recursive:bool | 通过 |
| 资源与权限 | secrets/key是否获准 | 不通过 |
| 执行 | 只在全部前置条件通过后 | 未执行删除 |

各行是独立对象或条件的对照，不暗示上一行的结果自动进入下一行。

#### 怎样把图中的变化读明白

严格结构输出主要约束模型生成的形状，不知道你的运行目录、用户身份或对象是否已过期。

拒绝、截断与响应不完整也应单独处理；不要在没有完整工具项时硬取arguments。

让程序承担已知的确定性校验，模型负责在合法操作范围内决策，二者职责更清楚。

**不要混淆：**给Schema增加“请不要删敏感文件”的description只是行为提示，不是运行时权限校验。

## 5. 工具描述与返回内容如何影响模型

工具名称和描述是模型选择动作的线索。应说明适用场景、关键参数和返回语义，不要把内部服务细节全部暴露给模型。对一组容易混淆的读写工具，强调副作用差异；对搜索工具，返回命中位置、片段、版本和是否截断，比无结构的几万行文本更容易继续使用。[[N25]](../sources.html#N25 "本地来源与核查范围")

但“返回更少”不是绝对优化。只返回命中行可能丢失决定分支的前置条件；只返回摘要可能丢失证据。较好的接口支持先定位、再读取连续范围，并明确结果是否完整。模型能逐步扩展证据，比工具擅自把关键信息永久丢掉更稳健。

先认识这里的对象与符号

[Skill、JIT与触发描述](../../concepts.html#concept-skills)
:   在能力加载场景，Skill是一组可复用指导与资源；JIT表示需要时再加载，不是必然指编译器即时编译。触发描述帮助模型判断适用性，不自动授予工具权限。应先判断任务需不需要某技能，再读详细内容；已加载技能不等于它的要求已实际执行。

当前工具Schema也占用上下文。工具很多时可以先提供发现入口，再加载相关定义；只有宿主支持该机制时才这样做。技能文件里写“自动JIT”不代表执行器已经实现按需工具发现。

## 6. 可选在线适配器的边界

[`live_readonly.py`](../code/live_readonly.html)使用官方Responses接口，要求明确`--allow-paid-api`、用户指定模型和环境变量中的密钥。只暴露只读文件工具，没有Shell、写入或部署工具；不自动重试网络请求，避免不明确的重复成本。响应输出项按结构保留再回传。

配套结果不包含这个在线入口的实测，因此服务兼容性、模型能力、实际计费与真实任务效果均标为未实测。读者应仅使用人工准备、无秘密的样本目录；文件内容会发送给模型服务。根目录检查不是面向恶意并发文件系统的生产沙箱，不应直接开放整个主目录或企业仓库。

先认识这里的对象与符号

[call\_id、item\_id、request\_id](../../concepts.html#concept-identifiers)
:   这些是不同层对象的标识：工具调用、输出项、请求或响应。用来把增量和结果配回正确对象，不是模型输入的Token ID，也不天然是业务幂等键。两次read\_file可分别有c1与c2；结果返回顺序颠倒时仍按调用标识配对，而不是按工具名称猜。

### 工具参数语法结束后，还需要等待调用结束信号吗

**输入与条件。**流中先出现参数片段 `{"n":1}`，后面还可能有同一输出项的后续delta或结束事件。

| 步骤与对象 | 内部动作 | 中间结果 / 新状态 |
| --- | --- | --- |
| 1临时可解析 | 目前字符串恰好是合法JSON | 只说明这个前缀能解析。 |
| 2协议完成 | 等待所用接口定义的调用参数或输出项完成 | 确认没有后续修正或追加。 |
| 3结构/业务检查 | n必须为正整数且在上限内 | 完整语法不代表参数可用。 |
| 4调用一次 | 以稳定call\_id登记执行状态 | 避免重连事件重复触发。 |
| 5断线恢复 | 不知道完整结束事件是否到达 | 按协议查询或重建，不任意猜完成。 |

**把过程连起来。**可解析前缀、完整参数、调用完成和整个响应完成不是必然同一时刻。

**边界与反例。**不同API的事件名与完成边界不同，教学代码只实现已声明子集。

## 7. 验收与失败定位

必须通过四个反例：UTF-8在字符中间切分，参数JSON在字符串中间切分，调用项完成但响应失败，收到文本后网络断开。前三者能测试协议状态机，第四项检验“人类可见回答”是否被错误当成任务完成。

若模型反复调用不存在的工具，先比较本轮实际工具Schema和模型返回名称，而不是直接增加Prompt警告。如果工具存在但被权限拦截，应检查身份、宿主配置和调用作用域。模型不应该负责猜测执行器隐藏的配置错误。
