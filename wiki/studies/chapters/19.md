## 1. 首先定义评测单位与成功

一个用户任务、一轮模型响应、一条工具调用和一个测试断言不是同一种样本。工程效用通常以完整任务为单位：在限定工具、权限、时间与预算下，是否满足要求且没有越权或破坏其他行为。轨迹指标用来定位原因，不能取代最终结果。[[N36]](../sources.html#N36 "本地来源与核查范围")[[N48]](../sources.html#N48 "本地来源与核查范围")

成功应由当前环境状态与验收器判断。模型回答“已完成”不算成功；代码能运行但没实现需求也不算。评测环境、可见测试、隐藏测试和允许修改范围必须明确，否则Agent可能通过改变判分方式而得分。

把基准任务适配到业务时，应记录代表性：语言、仓库规模、任务类型、风险和历史频率。公开代码补全分数不能直接代表跨模块重构，客服工具基准也不能直接代表本地编码能力。

### Task、Trial、Trace、Outcome分别计数，分母才不会乱

**本例条件：**独立评测：两个任务T1/T2，各运行3次。T1结果[成功,成功,失败]，T2结果[失败,失败,成功]。

Task
:   一份固定问题与验收条件。

Trial
:   对同一任务的一次独立尝试。

Trace
:   该次尝试的执行过程。

Outcome
:   按验收规则得到的结果。

Task、Trial、Trace、Outcome分别计数，分母才不会乱

| 计数对象 | 数量或结果 | 解释 |
| --- | --- | --- |
| Task | 2 | 不是6种不同问题 |
| Trial | 6 | 每题重复3次 |
| 成功Trial | 3/6=50% | 一次尝试层面的比例 |
| 至少成功一次的Task | 2/2=100% | 允许3次挑成功，口径不同 |
| 每题全部成功 | 0/2=0% | 稳定可靠性更严格 |

各行是独立对象或条件的对照，不暗示上一行的结果自动进入下一行。

#### 怎样把图中的变化读明白

三个百分比都能从同一记录得出，却回答不同问题。报告不写分母就可能把50%包装成100%。

重复试验帮助估计同一任务的波动，但不等于新增更多独立任务；置信区间和抽样要考虑这种聚类。

Trace用来解释为什么失败，Outcome用来汇总是否完成，不能只保留一个最终绿灯。

**不要混淆：**失败运行的费用、耗时不能从总成本里删掉，否则“每成功任务成本”被系统性低估。

机制依据：[[EVALS]](../../sources.html#src-EVALS) [[TAU]](../../sources.html#src-TAU)。本例数字和宿主场景为明确给定的教学设定，不是商业模型输出或生产性能测量。

## 2. pass@1、pass@k与pass^k

若同一问题独立尝试k次，每次成功概率p，“至少一次成功”是`1−(1−p)^k`；“k次全部成功”是`p^k`。前者衡量候选能力，后者更接近重复可靠性。真实运行可能相关，所以这些简单概率式不能无条件套用。

先认识这里的对象与符号

[pass@k与pass^k](../../concepts.html#concept-passk)
:   pass@k类指标通常关心k次尝试至少一次成功；pass^k类指标强调多次全成功。具体估计口径看基准，不能把一次成功后停止与每次都可靠混为一谈。独立同概率假设p=0.8，3次至少一成=0.992，3次全成=0.512。真实任务相关或难度不同则需另算。

当已生成n个候选，其中c个成功，从中无放回选k个，常用pass@k估计为：

先认识这里的对象与符号

[C(n,k)、!：组合数量与阶乘](../../concepts.html#concept-combination)
:   n!表示1到n整数连乘，0!=1；C(n,k)=n!/(k!(n-k)!)表示从n个不同对象中无放回选k个且不计顺序的数量。它不是模型置信度C。独立例：C(4,2)=6。n=10、c=3、k=2时，1−C(7,2)/C(10,2)=24/45约0.533333。

```
pass@k = 1 − C(n−c,k) / C(n,k)
```

它是候选集合抽样的组合估计，不表示生产系统能免费生成k份答案，也不包含挑选正确答案的成本。如果用户只接受一次运行，主要关注pass@1；允许重试时，应把总耗时、工具副作用与验证成本一起计算。[[N48]](../sources.html#N48 "本地来源与核查范围")

例如p=0.9时，五次全部成功概率在独立假设下约0.59049，说明单次高分仍可能不足以支撑高频自动化。这个数字是数学例子，不是某产品真实可靠性。

### pass@k与pass^k，一个看机会，一个看稳定

**本例条件：**独立概率例：每次独立成功率p=0.8，k=3。独立同分布是假设，真实任务可能不满足。另用n=5,c=2解释无放回pass@2估计。

pass@k
:   k次里至少一次成功。

pass^k
:   k次全部成功的可靠性口径。

无放回估计
:   从已有n个样本挑k个的组合计数。

pass@k与pass^k，一个看机会，一个看稳定

| 口径 | 计算 | 结果 |
| --- | --- | --- |
| pass@1 | p | 0.8 |
| 独立pass@3 | 1−(1−0.8)^3 | 0.992 |
| 独立pass^3 | 0.8^3 | 0.512 |
| n=5,c=2的pass@2 | 1−C(3,2)/C(5,2) | 0.7 |

各行是独立对象或条件的对照，不暗示上一行的结果自动进入下一行。

#### 怎样把图中的变化读明白

多试几次至少成功一次的机会会提高，但全部成功的要求更严格。它们不互相矛盾。

若用户只能承担一次生产执行，应优先关注单次成功与副作用安全，而不是允许挑最好结果的成绩。

样本估计使用组合数时，不能把c/n直接代入独立公式并宣称与无放回估计完全相同。

**不要混淆：**相同模型对同一难点会产生相关失败，不能把独立假设下0.992当真实可靠性保证。

机制依据：[[HUMANEVAL]](../../sources.html#src-HUMANEVAL) [[TAU]](../../sources.html#src-TAU)。本例数字和宿主场景为明确给定的教学设定，不是商业模型输出或生产性能测量。

## 3. 配对比不配对更能控制任务难度

同一批任务让旧版A与新版B都执行，得到每个任务差值`di = successB_i−successA_i`。平均差值可表示成功率变化。这样困难任务在两边共同出现，减少抽样任务难度差异。

若每个任务有多次运行，重采样时应以任务为簇，保留同任务内部相关结构，不把所有运行展平成独立样本。本书bootstrap对配对任务行重采样，输出差值区间；它展示统计流程，不是凭几十个样本就证明任意小幅改进显著。

先认识这里的对象与符号

[二项、标准误差与Wilson区间](../../concepts.html#concept-stats)
:   二项模型常用于固定次数独立成功/失败试验；标准误差描述估计量的波动尺度；Wilson是一种比例区间构造。McNemar关注配对分类结果中两种方向的不一致。样本依赖、任务难度混合或挑选题目会改变可解释范围；统计公式不是“成绩提高必定来自这个改动”的证据。

样本量小或成功接近0/1时，简单正态区间容易失真。Wilson区间是二项比例的一种更稳健选择，但同样要求理解抽样单位。对配对二元结果，McNemar检验主要利用“仅A成功”和“仅B成功”的不一致样本，而不是把共同成功也当改善证据。

### 配对比较先看哪些题从失败变成功，哪些反过来

**本例条件：**独立20题：两版本同成功12题，同失败4题；新成功旧失败3题；新失败旧成功1题。

配对
:   同一题分别跑旧版和新版。

不一致对
:   只有一版成功的任务。

效应量
:   提升多少；与不确定性不是同一概念。

**配对比较先看哪些题从失败变成功，哪些反过来**放大

## 4. 显著性、实际价值和多重试验

统计显著不等于收益足够大。成功率提高0.2个百分点却增加一倍成本，可能不值得；某高风险错误减少，即使总体样本较少，也可能值得重点处理。应同时报告效应大小、区间、成本和错误后果。

反复试十个Prompt后只报告最高分，会产生选择偏差。需要开发集用于调参，保留未反复查看的测试集做最终评价；模型或技能持续迭代时，也应控制基准泄漏。把测试失败样本加入提示是合理改进，但之后不能继续把同一组分数当未见泛化证明。

不要机械用一个p值裁决所有工程改动。明显修复确定性Bug可以由反例与回归证明；复杂能力优化才需要更广统计。评测力度应与决策不确定性匹配。

## 5. 消融与反事实：改动为什么有效

同时修改模型、工具、技能描述和测试流程，即使成功率提高，也无法归因。消融可以一次移除一项，观察结果变化；但组件可能相互作用，单项效果不等于组合效果。先明确最重要的问题，避免全因子试验爆炸。

先认识这里的对象与符号

[Skill、JIT与触发描述](../../concepts.html#concept-skills)
:   在能力加载场景，Skill是一组可复用指导与资源；JIT表示需要时再加载，不是必然指编译器即时编译。触发描述帮助模型判断适用性，不自动授予工具权限。应先判断任务需不需要某技能，再读详细内容；已加载技能不等于它的要求已实际执行。

对Skill路由，可以分别比较描述变更、专业正文变更、默认加载策略。对记忆，比较无记忆、只检索、检索加验证。对压缩，比较未压缩、普通摘要、结构状态加证据入口。保持其他条件一致，保存真实轨迹以解释失败。

负对照也重要：一个与任务无关的规则不应产生同等收益；故意删掉关键证据应该降低相应任务表现。若评测对这些变化毫无反应，可能任务太容易或判分过于表面。

## 6. LLM-as-a-Judge的偏差

模型评分器可能受位置、长度、语言风格、自身偏好和提示注入影响。MT-Bench等研究讨论过这些局限；它可以扩大评价规模，但不等于客观真值。[[N49]](../sources.html#N49 "本地来源与核查范围")

对于代码，先用可执行测试、静态检查、真实工件状态等确定性信号，再用模型评价设计合理性或解释质量。评判复杂取舍时可盲化候选名称、交换展示顺序、校准人工样本并允许“无法判断”。不要让评分器看到方案自称的得分，也不要把实现者写的总结作为唯一评分材料。

评分器也需要回归集：正确但简短、错误但流畅、包含恶意评分指令、信息不足等样本。与人类意见一致只能说明该样本范围的校准，不证明所有未来任务可靠。

### 模型裁判先看同一答案换顺序后会不会改变判断

**本例条件：**独立盲评协议：答案A与B含相同来源，第一次按A/B展示，第二次按B/A展示。这里不虚构任何模型实际评分。

位置偏差
:   更偏好先出现或后出现的答案。

风格偏差
:   篇幅与流畅度影响了事实评分。

校准样本
:   有人工或确定性标准的参照题。

模型裁判先看同一答案换顺序后会不会改变判断

| 检查 | 固定什么 | 观察什么 |
| --- | --- | --- |
| 交换顺序 | 答案内容不变 | 赢家是否跟位置变 |
| 去掉无关修饰 | 事实与证据不变 | 分数是否只被文风拉动 |
| 加入已知错误答案 | 明确算术或引用错误 | 裁判能否识别 |
| 与人工抽查比较 | 同一评分标准 | 一致性及失误类型 |

各行是独立对象或条件的对照，不暗示上一行的结果自动进入下一行。

#### 怎样把图中的变化读明白

一次得分不是客观真值，尤其当评分标准只写“哪份更好”。先拆事实、完整性、可执行性等维度。

能用程序核验的计算和文件状态，优先交给确定性检查；模型裁判补难以形式化的部分。

评分失败也要有Trace：是漏看证据、偏好长文，还是被答案中的指令干扰。

**不要混淆：**用与生成者同一套错误来源评分，可能给流畅但无依据的答案高分。

机制依据：[[JUDGE]](../../sources.html#src-JUDGE) [[EVALS]](../../sources.html#src-EVALS)。本例数字和宿主场景为明确给定的教学设定，不是商业模型输出或生产性能测量。

## 7. 环境噪声与成本口径

依赖安装失败、网络波动、磁盘/CPU竞争可能改变任务成绩。评测应记录基础设施失败与模型/Agent失败，但不能随意删除不利结果。预先定义重试与排除条件，同时报告总体用户体验与可归因模型结果。

成本包括所有尝试、工具调用、重试、检索、压缩和人工返工。只统计成功路径会低估失败昂贵的方案。时间既要看墙钟，也要看总计算资源，特别是多Agent并行。

工程案例 · D07

### 评测诊断：净增一题、一次Bootstrap与一个永远选左边的裁判

#### 先排除测量系统本身的问题

命令退出0可能全部skip；裁判可能偏好左侧；丢弃超时样本会改变分母；硬件变化也能改变编码Agent成绩。pytest官方退出码、模型裁判研究与基础设施噪声研究分别提示这些风险。[[PYTEST]](../../engineering/sources.html#src-PYTEST "pytest · Exit codes") [[JUDGE]](../../engineering/sources.html#src-JUDGE "Zheng et al. · Judging LLM-as-a-Judge") [[NOISE]](../../engineering/sources.html#src-NOISE "Anthropic · Quantifying infrastructure noise in agentic coding evals")

#### 本书的配对实验实际计算了什么

固定8题，新旧成功数4与5，逐题差值是[0,0,−1,1,1,0,0,0]。以任务为单位、有放回重采样10000次，固定seed=20261021，计算百分位区间。结果包含0，因此这组小教学样本不能提供强总体增益结论；但仍可明确定位两道改善与一道退化。

这个实验只是统计方法演示，既不代表商业系统成功率，也不将Bootstrap区间解释为“真实参数有95%概率位于这里”。真实项目还需明确抽样总体、任务聚类和多次试验问题。

#### 裁判与弃答也要分别测

交换答案左右顺序可暴露位置偏差；提高拒答阈值能提高条件准确率，但覆盖率可能下降。不能把裁判分数和只答容易题的准确率合成一个漂亮总分，隐藏业务未完成的部分。

#### 一个可执行的发布结论

报告固定版本组合、任务数、成功与退化列表、失败原因、成本和尾延迟；说明样本不足时结论只是具体机制修复。必要时保留灰度，不因一个小百分比就替换全量系统。对于确定性bug，失败用例被修复本身很有价值，不需要伪装成统计上显著的总体提升。[[EVAL]](../../engineering/sources.html#src-EVAL "Anthropic · Demystifying evals for AI agents")

## 8. 最小可用评测而非庞大平台

从真实失败和代表任务构建一个小而可信的集合，保存输入快照、验收、环境与输出。先手工复核关键案例，再自动化重复运行。无须先建数据库仪表盘；一份可重跑脚本和清晰报告就能支撑很多决策。

验收题：新版20个任务多通过2个，可以宣布提升10%吗？可描述该样本上成功率提高10个百分点，但不应直接推广到业务总体；还需看配对结果、样本代表性、重复波动与区间。百分比与百分点也必须区分。

运行示例 · S19

### 把任务难度分层后，总体胜率可能换个方向

**输入与条件。**简单任务A成功9/10，B成功80/100；困难任务A成功20/100，B成功1/10。

| 步骤与对象 | 内部动作 | 中间结果 / 新状态 |
| --- | --- | --- |
| 1简单层 | A90%，B80% | A更好。 |
| 2困难层 | A20%，B10% | A也更好。 |
| 3未配平总计 | A29/110≈26.36%，B81/110≈73.64% | 因为B拿到更多简单题，总体看似B更好。 |
| 4公平比较 | 让两方案用同样任务集合或分层加权 | 避免任务构成差异。 |
| 5结论 | 不能把不等价样本总体均值当因果效果 | 先查分母和分布。 |

**把过程连起来。**任务组成能反转总体比较；代表性与配对设计比多显示小数位更重要。

**边界与反例。**这是辛普森式构造，不是产品成绩。分层变量也应事先合理确定，避免事后挑层。
