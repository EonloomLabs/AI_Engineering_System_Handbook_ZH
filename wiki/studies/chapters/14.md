## 1. 文本匹配、语法匹配与语义绑定

全文搜索回答“这个字符串出现在哪里”；AST回答“这个位置是什么语法结构”；名称绑定/类型分析回答“这个标识符实际引用哪个定义”。三者不等价。例如两个文件都有`open`，它们可能分别是内置函数、方法或导入别名，全文搜索无法消歧。

Tree-sitter查询可以按节点结构和字段定位语法片段；它还暴露错误或缺失节点，适合编辑中不完整代码。LSP定义客户端与语言服务之间的请求，包括定义、类型定义、引用与诊断；具体语言服务器是否支持、精度如何，需要查询能力和实现。[[N96]](../sources.html#N96 "本地来源与核查范围")[[N34]](../sources.html#N34 "本地来源与核查范围")

AST并不自动提供完整调用图。动态属性、反射、依赖注入、生成代码和运行时插件使静态关系可能不完整。本书Python AST实验仅返回函数/类的名称和行范围，不声称完成跨文件名称解析。

### grep、AST、LSP、运行日志分别回答不同层的问题

**本例条件：**独立代码例：两个模块都定义parse；某处调用obj.parse()。只找到字符串parse，不能确定运行时调用哪一个实现。

AST
:   解析后的语法结构树。

LSP
:   编辑器与语言服务沟通定义、引用等能力的协议。

动态派发
:   实际接收者类型可能在运行时才确定。

grep、AST、LSP、运行日志分别回答不同层的问题

| 工具层 | 能得到的证据 | 还不能确定 |
| --- | --- | --- |
| grep | 所有出现parse的位置 | 哪些是注释，哪些是调用 |
| AST | 这是一处成员调用表达式 | obj实际是哪种类型 |
| 语言服务 | 在当前项目配置下推断定义与引用 | 反射、运行时注入的所有路径 |
| 测试/栈轨迹 | 此次执行进入模块B.parse | 其他输入是否也走同一路径 |

各行是独立对象或条件的对照，不暗示上一行的结果自动进入下一行。

#### 怎样把图中的变化读明白

每一层都不是上一层的万能替代。grep适合快速缩小范围，AST排除文本噪声，语言服务补静态语义，运行证据核对实际路径。

运行一次确定了一条路径，不等于证明所有输入都只走这条路径。诊断报告应注明样例输入与环境。

某层失败后要识别原因：解析失败可能是语法版本，跳转错误可能是项目配置，不必直接归因于模型。

**不要混淆：**LSP返回的字符位置也有编码约定，UTF-16偏移不能不加转换地当成Python字符下标。

机制依据：[[TREESITTER]](../../sources.html#src-TREESITTER) [[LSP]](../../sources.html#src-LSP) [[HARNESS]](../../sources.html#src-HARNESS)。本例数字和宿主场景为明确给定的教学设定，不是商业模型输出或生产性能测量。

## 测试证据失效

先测试工作树r7，再格式化产生r8；判断应重跑哪些检查，并记录差异。

**关键边界：**同一commit不等于同一工作树，必须绑定内容版本。

**顺着源码或工程依据继续追：**源码、诊断、补丁和测试必须指向同一对象。 不只检查顺利路径，也核对取消、版本变化与结果未知时的行为。

源码与证据版本链证据绑定对象失效条件补丁r7旧文本文件已被改成r8测试工作树哈希+命令测试后再修改诊断环境+运行输入配置与数据变化

| 证据 | 绑定对象 | 失效条件 |
| --- | --- | --- |
| 补丁 | r7旧文本 | 文件已被改成r8 |
| 测试 | 工作树哈希+命令 | 测试后再修改 |
| 诊断 | 环境+运行输入 | 配置与数据变化 |

源码与证据版本链。数值与状态属于本节明确设定的教学例；不是生产性能或商业模型实测。

**证据与理解边界：**读取、补丁和测试需要绑定工作树版本；最终文件再次变化后，旧测试不能自动覆盖新结果。

## 2. 一次“技能没有加载”的证据路径

先读取实际任务记录，确定失败发生在发现、选择、读取、注入还是执行。然后定位加载入口和条件分支；再读决定分支的配置类型和调用方；最后找针对这些条件的测试。这个路径围绕一个可证伪假设展开，而不是先遍历整个根目录。

例如候选根因是cwd错误。必须找到启动时cwd如何产生、规则发现函数如何使用cwd、测试是否覆盖嵌套目录。只看到一个函数名`load_skills`，还不能证明它被调用，更不能证明返回内容进入模型输入。运行轨迹和源码链共同建立证据。

当代码路径不明确，文本搜索可以低成本先找错误消息、配置键和日志事件；语义检索则帮助从“为什么不生效”映射到可能的模块。正确方法通常是组合，而不是宣布某一种检索全面取代其余工具。

### Skill有效应用是一条证据链，不是一个“loaded”日志

**本例条件：**独立技能目录包含“目录规则审查”Skill，目标检查exclude边界。先追踪元数据，再追踪正文和实际测试。

发现
:   宿主找到了名称与描述。

加载
:   相关说明实际进入上下文。

应用
:   执行中出现该方法要求的操作或验证。

Skill有效应用是一条证据链，不是一个“loaded”日志

| 阶段 | 可检查对象 | 仍不能声称什么 |
| --- | --- | --- |
| 磁盘存在 | SKILL.md路径 | 宿主已经发现 |
| 元数据已发现 | name/description列表 | 正文已经读取 |
| 正文已加载 | 请求中含边界规则 | 模型已经遵循 |
| 测试已生成 | myvendor/a.py应保留的反例 | 测试真实运行 |
| 验证通过 | 当前版本执行记录 | 未覆盖的场景也正确 |

各行是独立对象或条件的对照，不暗示上一行的结果自动进入下一行。

#### 怎样把图中的变化读明白

逐层定位可以避免“技能文件写得很专业，却完全没有进入模型”的无效优化。

反过来，加载了长篇说明但没有任何对应动作，也不算有效应用；要看任务行为与结果。

Skill的专业性应通过具体失败案例验证，而不是以篇幅或术语数量衡量。

**不要混淆：**模型回复“已使用某技能”只能当声明，不能替代加载轨迹与执行证据。

机制依据：[[SKILLS]](../../sources.html#src-SKILLS) [[COPILOTSKILL]](../../sources.html#src-COPILOTSKILL)。本例数字和宿主场景为明确给定的教学设定，不是商业模型输出或生产性能测量。

## 3. 文件和符号索引如何切块

按固定字符数切代码，可能截断函数签名、异常处理和闭包。按AST符号切块更符合结构，但大函数仍可能过长，小函数又可能脱离类型与调用上下文。一个合理索引可保存主符号文本、父作用域、导入摘要、路径与版本，再按需扩展关联信息。

符号名称不能单独做全局主键：重载、同名类、不同文件、不同版本都会冲突。可用仓库+版本+路径+限定符号名作为定位，再附稳定范围。行号是快照坐标，修改后可能移动；展示行号时应同时标明版本。

代码注释和文档也是证据，但与执行逻辑冲突时要调查，而不是自动选择更易读的一方。测试断言可以表达预期，源码表达当前行为，两者不一致可能正是待修复缺陷。不能把“当前代码这么写”当成用户期望也必须如此。

## 4. 依赖图如何用于变更影响分析

图节点可以是模块、函数、类型、配置或测试；边可以表示调用、导入、继承、数据依赖或覆盖关系。不同边的可信度不同：编译器解析的直接引用通常比文本猜测强；运行trace只覆盖实际执行路径，不证明其他路径不存在。

修改函数后，先看直接调用者、参数与返回契约，再看边界使用和错误处理；测试选择可以沿依赖扩展。但静态图缺边、动态路径、共享数据与构建配置都可能导致遗漏。对高风险改动，可在聚焦测试后增加更宽回归，而不是把图当作绝对证明。

这也解释了为什么代码库RAG不仅需要“找最像的一段代码”。实现任务需要定义、调用、配置和测试的组合证据。RepoCoder研究了迭代检索与生成的联动，但仓库补全基准的成功不能直接推成任意Bug修复能力。[[N74]](../sources.html#N74 "本地来源与核查范围")

## 5. Git历史能解释什么

提交历史有助于找到行为何时引入、当时理由、相关测试和回滚风险。它是当前代码理解的辅助，不是替代。某个旧决策可能针对已消失的约束；把旧PR结论直接写成永久规则会造成记忆过期。

对回归问题，可用二分定位引入变化的范围，但环境与依赖必须可复现；否则测试红绿可能来自基础设施噪声。记录失败样本和命令比只记一个commit更有用。提交说明也可能不完整，需要结合diff与可运行证据。

### 同一路径，commit、工作树、编辑器可以有三份内容

**本例条件：**独立文件filter.py：仓库r7返回False，磁盘未提交改成True，编辑器未保存又加条件。索引基于r7构建。

commit
:   版本库中的固定快照。

工作树
:   当前磁盘文件。

buffer
:   编辑器尚未保存的内容。

同一路径，commit、工作树、编辑器可以有三份内容

| 读者/系统 | 实际版本 | 潜在误判 |
| --- | --- | --- |
| 语义索引 | r7: return False | 解释已经过期 |
| CLI测试 | 工作树: return True | 测试对象与索引不同 |
| IDE诊断 | buffer: 条件返回 | 还不是磁盘测试对象 |
| 可信补丁前置 | 读取当前内容并核对hash | 不把r7旧行号直接应用 |

各行是独立对象或条件的对照，不暗示上一行的结果自动进入下一行。

#### 怎样把图中的变化读明白

这里不是时间越新越好这么简单，而是先确定“我们要修改和验证的工件到底是哪一个”。

每份证据携带版本；应用补丁前再次核对当前内容，避免基于旧索引覆盖用户的新修改。

索引更新可以增量化，但删除、重命名和配置变化也会使关联失效，不能只监听新增文件。

**不要混淆：**只记录分支名main不足以定位工件，因为分支会移动；需要提交或内容指纹和必要的工作树差异。

机制依据：[[LSP]](../../sources.html#src-LSP) [[HARNESS]](../../sources.html#src-HARNESS)。本例数字和宿主场景为明确给定的教学设定，不是商业模型输出或生产性能测量。

## 6. “没搜到”为什么不是不存在

搜索可能受忽略规则、文件类型、隐藏目录、索引延迟、语言服务器未完成分析或查询表达式限制。负结论应带搜索范围和方法。例如“在当前src目录中未找到此符号的文本引用”，不能升级成“整个系统不会调用它”。

扩大搜索应由缺口触发：先增加可能模块或配置目录，再查动态注册和生成代码。无限扩展到所有依赖也会降低效率。停止标准是当前证据足以支持决策，或者剩余不确定性已明确且需要外部资料，而非必须遍历所有文件。

## 7. 检索到证据后还要控制写入

精确定位后，补丁应针对读取版本生成并验证。文件可能在检索与写入之间改变，LSP buffer可能和磁盘不同，测试可能读取构建产物而非当前源码。这些版本错位是AI开发中的高频工程风险。

先认识这里的对象与符号

[IDE、CLI、UI与DOM](../../concepts.html#concept-interface-environment)
:   IDE是集成开发环境，CLI是命令行界面，UI是用户界面，DOM是网页文档的结构对象树。不同入口自动附带的代码、选区和页面信息可能不同。模型在IDE里看到选中函数，不代表同一任务在CLI里也已收到该函数；先检查本轮输入对象。

在IDE场景，应明确以未保存编辑器buffer还是磁盘文件为准；在CLI场景，应检查工作树已有用户修改并避免覆盖。不能因为AI承担开发，就降低普通软件工程中的变更隔离要求。

### 增量分析一个函数改名，哪些证据应更新

**输入与条件。**把a.py中的parse改名为parse\_config，b.py静态导入它，c.py通过字符串注册名字。

| 步骤与对象 | 内部动作 | 中间结果 / 新状态 |
| --- | --- | --- |
| 1语法变化 | a.py定义节点更新 | 增量解析只需重建受影响语法范围。 |
| 2静态引用 | b.py的绑定与调用需更新 | 检查语言服务索引是否重建。 |
| 3动态引用 | c.py字符串未被静态重命名覆盖 | 用注册表与运行测试补验证。 |
| 4版本标记 | 旧搜索结果仍显示parse | 作为过期定位线索，不直接采信。 |
| 5最终验证 | 导入、注册查找与调用测试 | 覆盖不同证据类型的遗漏。 |

**把过程连起来。**增量语法树更新不等于全项目语义和运行行为自动一致。

**边界与反例。**各语言服务器重命名覆盖不同；不保证所有动态引用可被静态工具找全。

依据与适用范围：[[DERIVE]](../../example-sources.html#ex-src-DERIVE)。示例输入和场景由本书明确设定。

### 原子替换防半写，CAS防覆盖，它们不是一回事

**本例条件：**独立文件例：A读取r7并生成补丁；B先把文件改到r8；A仍尝试写入自己的结果。

原子替换
:   读者看到完整旧文件或完整新文件，而非半份。

CAS
:   只有版本等于预期值才执行更新。

TOCTOU
:   检查与使用之间状态变化的竞态。

原子替换防半写，CAS防覆盖，它们不是一回事

| 时间 | A动作 | 文件状态 |
| --- | --- | --- |
| t0 | 读r7，记录expected=r7 | r7 |
| t1 | 仍在生成补丁 | B写入r8 |
| t2错误路径 | 无条件原子replace | 完整覆盖了r8；仍丢更新 |
| t2正确条件提交 | 在协调边界内比较r7与当前r8 | 不一致，拒绝覆盖并重新取证 |

各行是独立对象或条件的对照，不暗示上一行的结果自动进入下一行。

#### 怎样把图中的变化读明白

一次写得“完整”仍然可能是错误内容。原子性只解决可见半写，不能证明你基于最新版本工作。

先检查hash，再隔一段无锁写入，仍可能在中间被其他进程修改。比较与更新必须由同一协调机制保护。

数据库事务只能包住参与它的资源；普通文件、远程API与数据库之间还要设计恢复和补偿。

**不要混淆：**不要把rename/replace、CAS、事务、fsync四个名词互相替代：它们分别涉及可见性、条件更新、一致性与持久性。

机制依据：[[SQLITE]](../../sources.html#src-SQLITE) [[HARNESS]](../../sources.html#src-HARNESS) [[SQLITE-ATOMIC]](../../mechanisms/sources.html#source-SQLITE-ATOMIC)。本例数字和宿主场景为明确给定的教学设定，不是商业模型输出或生产性能测量。

## 8. 验收题

AST找到了一个函数调用，能否证明目标函数必然执行？不能，控制流可能不进入该分支，名称绑定也可能指向其他对象。需要控制流、类型/绑定信息和运行条件。

一次修复的证据包应至少能指出：哪个行为不满足什么要求、根因在哪个具体分支、哪些调用受影响、补丁如何改变行为、当前版本哪些验证通过。内容可简短，但链条不能靠笼统“已全面检查”替代。
