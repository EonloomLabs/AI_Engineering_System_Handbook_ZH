## 1. 企业知识问答：不是一个公开向量库

场景：员工询问内部接口迁移方案，资料分布在文档、PR与会议纪要中。首先绑定员工身份与项目权限，确定问题涉及的产品版本。查询先在授权集合中召回，返回片段、来源、版本和上下文范围；生成答案时区分当前方案与历史决定。

一个最小数据模型包含`document_id, revision, tenant, acl, effective_time, source_uri, chunk_range`。Embedding版本单独记录，便于重建。派生摘要也保留来源依赖，原文撤回或权限变化后可以找到需要失效的摘要与答案缓存。

验收包含：有答案、无答案、旧版冲突、跨文档组合、权限相近用户、权限撤回。关键指标不只是答案流畅度，而是证据支持率、当前版本正确率、授权泄漏、拒答覆盖与延迟。检索到机密内容再要求模型“不说出来”不是合格权限设计。

上线先做只读问答，保留人工反馈与错误样本；没有必要第一天就让系统自动修改文档。写入能力应另设授权与审核流程。第13、15、20章分别提供检索、生命周期与安全基础。[[N24]](../sources.html#N24 "本地来源与核查范围")[[N35]](../sources.html#N35 "本地来源与核查范围")[[N83]](../sources.html#N83 "本地来源与核查范围")

### 企业问答的正确答案，要同时过范围、时间和证据三关

**本例条件：**独立员工问答：问“我今年能报销多少”。公司有地区、岗位、年度不同规则；当前用户属于地区A、岗位P、年度2026。

身份范围
:   哪些资料可访问、哪些规则适用。

时效
:   规则对何时生效。

可支持结论
:   引用中有足够条件与数值。

企业问答的正确答案，要同时过范围、时间和证据三关

| 候选规则 | 匹配结果 | 处理 |
| --- | --- | --- |
| A/P/2025：100 | 地区岗位对，年度旧 | 仅供历史，不直接作答 |
| B/P/2026：200 | 年度对，地区不符 | 排除 |
| A/P/2026：150 | 三条件都符 | 继续核对例外与审批限制 |
| 回答 | 在对应条件下上限150 | 附具体来源与适用范围 |

各行是独立对象或条件的对照，不暗示上一行的结果自动进入下一行。

#### 怎样把图中的变化读明白

这个系统不是“文档越多越会答”。没有身份和适用范围，最相关的数字也可能对当前用户是错的。

允许访问某规则不等于该规则一定适用当前人；授权过滤与业务范围判断是两道检查。

不能验证必要条件时应说明缺口或询问，而不是拼接多份候选中的数值。

**不要混淆：**图中额度纯属教学数字；事实、政策和权限都必须来自真实系统，而非模型补齐。

机制依据：[[CTXRETRIEVAL]](../../sources.html#src-CTXRETRIEVAL) [[OWASP]](../../sources.html#src-OWASP)。本例数字和宿主场景为明确给定的教学设定，不是商业模型输出或生产性能测量。

## 2. 仓库诊断助手：先定位再决定是否实施

场景：开发者报告某功能回归。系统读取当前分支、工作树状态与用户描述，定位日志、入口和相关测试。输出可以先是“证据支持的候选根因+最小复现”，而不是立即修改大量文件。

数据路径是任务→精确搜索→AST/LSP扩展→源码/测试→假设验证。若需要历史理由，再查Git；若需要外部接口，再查对应版本官方文档。检索应逐步扩展，避免全库默认载入。当前源码优先于旧记忆，但旧记忆可以指出高价值入口。

允许实施时，补丁绑定读取版本，限制变更范围，运行原失败测试及必要回归，检查最终diff。高风险改动增加独立审查；普通小修复不必默认多Agent。验证结论必须绑定最终工件，而非聊天中的某一中间版本。

评测按真实任务分层：简单Bug、跨模块功能、并发/存储、构建配置、文档。比较同一模型下有无Skill、有无记忆、不同检索策略，确定收益来自专业知识还是工具改善。不要用静态路由成功代替代码结果。[[N79]](../sources.html#N79 "本地来源与核查范围")[[N47]](../sources.html#N47 "本地来源与核查范围")

### 最小仓库修复器，也应留下能复核的四份对象

**本例条件：**独立exclude修复任务，工作树从r7变到r8。只追踪必要对象，不引入固定多Agent审批链。

任务契约
:   目标、限制、验收。

证据集
:   实际源码与失败记录。

候选补丁
:   还需应用与验证的修改。

交付记录
:   最终版本和对应测试结果。

最小仓库修复器，也应留下能复核的四份对象

| 对象 | 本例内容 | 下一对象怎样依赖它 |
| --- | --- | --- |
| 契约 | vendor/排除，但myvendor/保留 | 决定要测哪些输入 |
| 证据 | r7实现 + 最小失败例 | 支持根因判断 |
| 补丁 | 只改路径前缀判断 | 应用后形成r8 |
| 验证 | r8上的正例、反例、回归 | 支持最终交付 |
| 报告 | 改动范围+命令+结果+限制 | 读者可复核，不只一句成功 |

各行是独立对象或条件的对照，不暗示上一行的结果自动进入下一行。

#### 怎样把图中的变化读明白

如果把中间分析文件删掉，至少还应保留能重建关键判断的证据引用和最终diff。

小任务可以单Agent直接做，但“少流程”不等于省略当前版本验证。

长任务增加检查点时，保存的是这四份对象的状态与位置，不是无限延长聊天历史。

**不要混淆：**报告写得很细但缺最终文件版本，仍无法证明测试结果属于实际交付物。

## 3. 研究助理：从资料堆积到可追溯结论

场景：研究团队要判断某项Agent技术是否值得采用。系统先定义决策问题与比较基线，再收集原论文、官方文档和复现实验；每个结论保留出处、版本、实验条件和是否为作者推断。

先认识这里的对象与符号

[OAuth、scope与授权](../../concepts.html#concept-oauth)
:   在授权场景，OAuth使应用能按授权取得访问凭据；scope声明一类访问范围，资源服务仍应检查具体权限。在记忆或任务场景，scope又可只表示适用范围，不能混成登录凭据。获准“读取日历”不等于获准删除所有事件；连接成功也不证明操作被批准。

证据对象可包含`claim, source, scope, date, method, limitation, status`。这不是强制数据库表，而是避免把“某研究集上有效”写成“普遍最佳实践”的最小语义。多篇文章重复引用同一实验，不应被当成多个独立证据。

研究停止标准是当前决策所需关键不确定性已经有足够证据，或剩余缺口明确需要本地实验。无限阅读同类文章不会自动提高确定性。输出应能回答采用、暂缓、局部试验以及什么新证据会改变决定。

评价不是文章数量，而是来源准确性、结论支持、反证覆盖、可执行实验和实际决策价值。检索不到时说明搜索范围与缺口，不编造文献。图检索或多Agent只在跨资料规模与独立探索确有需要时引入。[[N26]](../sources.html#N26 "本地来源与核查范围")[[N46]](../sources.html#N46 "本地来源与核查范围")

## 4. 运营自动化：先只读，再分级增加副作用

场景：系统检查构建失败并建议重试。只读阶段获取状态、日志和近期变更；建议阶段给出可核验原因；执行阶段才允许对特定任务重试或创建工单。每一步权限与完成条件不同，不应因系统会分析就自动拥有生产写权限。

一次执行绑定用户/服务身份、目标对象、前置状态与操作ID。服务超时后保留unknown，通过查询任务状态对账，避免重复创建。重试只用于明确可重试错误；权限错误不绕过，配置错误不无限重试。

上线采用影子模式或人工确认的逐步放权策略，先观察建议质量与误触发，再允许低风险动作。影子模式没有真实副作用，不能证明实际执行恢复可靠，因此仍要单独做沙箱故障注入与对账测试。

### 业务规则要有可执行的例外，而不只是一句口号

**本例条件：**独立业务：退款通常不能超过已付款，但已退款金额也必须扣除。订单付款100、已退40，本次申请70。金额单位为教学点数。

业务不变量
:   所有允许操作都应满足的约束。

当前状态
:   规则在这一笔操作前的真实数据。

验收例
:   具体输入与预期结果。

业务规则要有可执行的例外，而不只是一句口号

| 规则层 | 计算或证据 | 结论 |
| --- | --- | --- |
| 模糊说明 | 退款不超过付款 | 70≤100，看似允许 |
| 完整约束 | 本次≤已付−已退 | 可退100−40=60 |
| 本次70 | 70>60 | 应拒绝或调整 |
| 并发条件 | 另一退款也可能改变已退 | 提交时需按当前状态原子校验 |

各行是独立对象或条件的对照，不暗示上一行的结果自动进入下一行。

#### 怎样把图中的变化读明白

懂业务不是把文档读得多，而是能把“约束、例外、状态、验证”连成明确判断。

业务知识应放在可维护规则与测试中；Agent检索到规则后仍要读取当前订单状态。

为了展示并发风险可以先用两次请求的时间线，不能把这条规则仅写成模型提示而没有执行端保护。

**不要混淆：**付款100不变不代表可退额不变；忽略已退和在途操作会把静态知识误当动态事实。

机制依据：[[HARNESS]](../../sources.html#src-HARNESS) [[REVIEW]](../../sources.html#src-REVIEW)。本例数字和宿主场景为明确给定的教学设定，不是商业模型输出或生产性能测量。

## 5. 共用组件与不该共用的逻辑

身份、追踪、预算、工具协议和基础检索可复用；业务验收、风险阈值和专业技能通常要按应用定义。把所有业务都塞进一个全能Agent，可能让权限与上下文不断膨胀；把每个步骤都拆成服务，又可能过度工程化。

先建立一个清晰单进程或小服务边界，只有并发、隔离、扩展或团队责任需要时才拆分。共享模块应有真实重复使用场景，而不只是“未来可能”。

## 6. 生产上线的最小证据包

包含代表任务集、错误分类、权限测试、恢复测试、成本/延迟、数据删除策略、回滚条件和未验证范围。高风险系统需要更严格审计；个人只读助手可以简化，但不能省掉密钥和数据边界。

验收题：三种业务都用同一LLM，能否共用同一成功率指标？不能。知识问答看证据与权限，代码任务看工件与回归，运营自动化看外部状态与副作用。模型相同不代表业务质量相同。

### 同一份研究结论转为自动化动作，需要补哪一层

**输入与条件。**研究报告建议“升级服务超时至5秒”；真实自动化要修改项目P生产配置。

| 步骤与对象 | 内部动作 | 中间结果 / 新状态 |
| --- | --- | --- |
| 1研究结论 | 有证据支持建议 | 仍不是用户授权的写操作。 |
| 2动作规格 | 明确项目、环境、字段、旧值和新值 | 避免把测试配置当生产。 |
| 3风险与权限 | 确认允许执行及适当批准 | 不能由报告自授权限。 |
| 4执行与验证 | 按版本条件写入、读回并运行必要检查 | 建议正确不保证执行正确。 |
| 5失败恢复 | 超时、未知结果、回滚条件 | 在动作前设计，而不是故障后猜。 |

**把过程连起来。**从建议到行动跨过了权限和副作用边界，需要新增工程保证。

**边界与反例。**为受控自动化设计示例，不构成真实生产变更授权。

工程机制与失败边界

## 非阻断问题直接修复

给审查发现分成架构错误与局部命名问题；后者直接带入实现与验证，前者再改变方案。

**关键边界：**不把每个问题都升级为重新设计，衡量返工与缺陷是否真的减少。

**顺着源码或工程依据继续追：**用可恢复状态、功能验收与最小检查点连接工作。 不只检查顺利路径，也核对取消、版本变化与结果未知时的行为。

验收证据绑定最终产物对象已验证修改后源文件r7r8测试结果针对r7通过不覆盖r8交付声明仅能描述r7需重跑受影响检查

| 对象 | 已验证 | 修改后 |
| --- | --- | --- |
| 源文件 | r7 | r8 |
| 测试结果 | 针对r7通过 | 不覆盖r8 |
| 交付声明 | 仅能描述r7 | 需重跑受影响检查 |

验收证据绑定最终产物。数值与状态属于本节明确设定的教学例；不是生产性能或商业模型实测。

完整机制与连续例子见 [长期任务如何避免每次重新开始或虚假完成？](../../chapters/22.html#agent-practice-quality)；本节仍保留原有推导与实验，两处说明使用不同层次而不互相替代。

**证据与理解边界：**长任务角色和重置策略并非越多越好；模型升级后应做删减机制的对照，而不是固定套用最长流程。
