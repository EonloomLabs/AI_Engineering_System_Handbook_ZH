## 案例一：Skill显示加载，但代码仍不专业

观察：日志有技能名称，输出却未处理事务超时。竞争解释包括：只加载了元数据；正文被裁剪；子Agent未得到内容；正文根本没有有效专业知识；模型看到但未应用；测试没有要求该行为。

最小排查先看实际加载范围与正文，再看执行轨迹中是否涉及相应风险，最后用能触发该错误的任务验证。不应第一步增加一个路由Agent，因为选择可能已经正确。修复可能只是补一条具体事务边界知识与对应测试。

回归同时包含需要事务处理与无关任务，防止把所有任务都升级成分布式系统分析。验收是错误行为减少，而不是回答更频繁提到“事务”。

### Skill有效应用是一条证据链，不是一个“loaded”日志

**本例条件：**独立技能目录包含“目录规则审查”Skill，目标检查exclude边界。先追踪元数据，再追踪正文和实际测试。

发现
:   宿主找到了名称与描述。

加载
:   相关说明实际进入上下文。

应用
:   执行中出现该方法要求的操作或验证。

Skill有效应用是一条证据链，不是一个“loaded”日志

| 阶段 | 可检查对象 | 仍不能声称什么 |
| --- | --- | --- |
| 磁盘存在 | SKILL.md路径 | 宿主已经发现 |
| 元数据已发现 | name/description列表 | 正文已经读取 |
| 正文已加载 | 请求中含边界规则 | 模型已经遵循 |
| 测试已生成 | myvendor/a.py应保留的反例 | 测试真实运行 |
| 验证通过 | 当前版本执行记录 | 未覆盖的场景也正确 |

各行是独立对象或条件的对照，不暗示上一行的结果自动进入下一行。

#### 怎样把图中的变化读明白

逐层定位可以避免“技能文件写得很专业，却完全没有进入模型”的无效优化。

反过来，加载了长篇说明但没有任何对应动作，也不算有效应用；要看任务行为与结果。

Skill的专业性应通过具体失败案例验证，而不是以篇幅或术语数量衡量。

**不要混淆：**模型回复“已使用某技能”只能当声明，不能替代加载轨迹与执行证据。

机制依据：[[SKILLS]](../../sources.html#src-SKILLS) [[COPILOTSKILL]](../../sources.html#src-COPILOTSKILL)。本例数字和宿主场景为明确给定的教学设定，不是商业模型输出或生产性能测量。

## 案例二：压缩后工作方向改变

观察：原要求只改description，压缩后开始重构执行器。竞争解释：负约束丢失、假设升级、旧记忆覆盖、新用户输入未进入、子任务说明截断。

取压缩前后任务状态，检查“不能改什么”是否保留；比较下游委派说明与当前权威目标。若宿主压缩不可读，用相同前缀分叉继续执行，测试具体约束。修复优先持久化少量关键约束与证据入口，不必默认自建第二套全历史摘要服务。

回归应包含多次压缩与新的目标变更，避免系统过度固定旧约束，反而不能遵循用户后来授权的变化。保真不是永远不变，而是正确保留时间与权威。

### 保真检查要问“还能正确做什么”，不只看摘要像不像

**本例条件：**独立任务约束：不能改公共API；补丁已生成但未应用；测试在旧版本r7通过。用三道问题核对压缩前后状态。

事实保留
:   关键语义及否定没有丢。

状态保留
:   已计划、已执行、已验证不混淆。

继续执行评测
:   看压缩后任务实际能否推进。

保真检查要问“还能正确做什么”，不只看摘要像不像

| 探针问题 | 正确答案 | 危险摘要会给的答案 |
| --- | --- | --- |
| 可以改公共签名吗？ | 不可以 | 略去“不”后变成可以 |
| 补丁是否已落盘？ | 没有，只生成候选 | 总结成“修复完成” |
| 测试证明当前补丁吗？ | 不证明，测试属于r7 | 总结成“测试通过” |

各行是独立对象或条件的对照，不暗示上一行的结果自动进入下一行。

#### 怎样把图中的变化读明白

三条探针都很短，但比词面相似度更接近真实风险。摘要即便使用了同样词语，也可能把时间和否定方向改反。

探针集合应在真实任务前定义重要约束，不能看完摘要后专挑它保留的部分提问。

最后还要让任务继续，检查是否重复动作、越权修改或引用错版本。问答通过只是局部信号。

**不要混淆：**模型给自己的摘要打高分不等于保真，尤其当评分者与生成者共享同一盲点时。

机制依据：[[CONTEXT]](../../sources.html#src-CONTEXT) [[EVALS]](../../sources.html#src-EVALS)。本例数字和宿主场景为明确给定的教学设定，不是商业模型输出或生产性能测量。

## 案例三：检索结果相关，却总是旧版本

观察：回答术语正确，但API字段已废弃。可能是索引未更新、向量语义偏爱旧长文、缓存键没有版本、重排未使用时间范围或生成阶段混合旧证据。

沿管线检查当前文档是否入库、候选是否包含、过滤后是否保留、排序/选择是否丢弃、最终引用是否对应。修复点可能是索引代次与版本过滤，而不是更换Embedding模型。

回归加入同名不同版本、回滚场景和历史查询。不能简单永远选择时间最新的一条，因为用户可能问旧版本迁移原因。第15章有效时间与知晓时间帮助区分这些需求。

### 同一路径，commit、工作树、编辑器可以有三份内容

**本例条件：**独立文件filter.py：仓库r7返回False，磁盘未提交改成True，编辑器未保存又加条件。索引基于r7构建。

commit
:   版本库中的固定快照。

工作树
:   当前磁盘文件。

buffer
:   编辑器尚未保存的内容。

同一路径，commit、工作树、编辑器可以有三份内容

| 读者/系统 | 实际版本 | 潜在误判 |
| --- | --- | --- |
| 语义索引 | r7: return False | 解释已经过期 |
| CLI测试 | 工作树: return True | 测试对象与索引不同 |
| IDE诊断 | buffer: 条件返回 | 还不是磁盘测试对象 |
| 可信补丁前置 | 读取当前内容并核对hash | 不把r7旧行号直接应用 |

各行是独立对象或条件的对照，不暗示上一行的结果自动进入下一行。

#### 怎样把图中的变化读明白

这里不是时间越新越好这么简单，而是先确定“我们要修改和验证的工件到底是哪一个”。

每份证据携带版本；应用补丁前再次核对当前内容，避免基于旧索引覆盖用户的新修改。

索引更新可以增量化，但删除、重命名和配置变化也会使关联失效，不能只监听新增文件。

**不要混淆：**只记录分支名main不足以定位工件，因为分支会移动；需要提交或内容指纹和必要的工作树差异。

机制依据：[[LSP]](../../sources.html#src-LSP) [[HARNESS]](../../sources.html#src-HARNESS)。本例数字和宿主场景为明确给定的教学设定，不是商业模型输出或生产性能测量。

## 案例四：测试全绿，用户仍发现问题

可能原因包括测试根本没运行、关键项被跳过、测试被模型弱化、测试版本陈旧、新要求未覆盖、环境与生产不同。首先读取实际命令、数量、退出码和工件版本，不能只读模型总结。

修复应针对原因：空测试集设置明确失败；新要求补断言；验证绑定当前版本；高风险测试资源隔离。不要机械再加三轮自然语言Review，因为它们可能重复相信同一份错误绿色报告。

回归故意修改测试后文件、删除关键断言、制造超时，观察系统是否仍会宣布成功。第27章已实测其中的陈旧验证拒绝。

### 绿色测试需要绑定“真的运行过”和“当前版本”

**本例条件：**独立记录：测试命令退出0，但0项被收集；另一次有12项通过，但它运行在r7，最终代码已改为r8。

收集数量
:   测试框架实际找到多少项。

执行数量
:   实际运行而非跳过的测试数。

工件身份
:   测试时对应的代码与环境版本。

绿色测试需要绑定“真的运行过”和“当前版本”

| 记录 | 看起来怎样 | 实际能证明 |
| --- | --- | --- |
| exit=0, collected=0 | 命令成功结束 | 没有功能测试证据 |
| 12 passed @r7 | 有有效测试 | 只覆盖r7 |
| 之后改成r8 | 仍显示旧绿灯 | 不能自动外推到r8 |
| 12 passed @r8 + 边界反例 | 对应当前工件 | 这些测试定义的性质成立 |

各行是独立对象或条件的对照，不暗示上一行的结果自动进入下一行。

#### 怎样把图中的变化读明白

先检查有没有实际执行，再检查测的是什么版本，最后检查用例能不能击中目标缺陷。三关缺一不可。

变异测试可以故意放回错误实现；如果仍全绿，说明测试没有分辨力。

验证后格式化、生成代码或改配置也会改变对象，应重新执行受影响检查或证明不影响。

**不要混淆：**不能把“测试没有发现问题”改写成“没有任何问题”，尤其当覆盖和环境都有限。

机制依据：[[SWEBENCH]](../../sources.html#src-SWEBENCH) [[HARNESS]](../../sources.html#src-HARNESS)。本例数字和宿主场景为明确给定的教学设定，不是商业模型输出或生产性能测量。

## 案例五：任务越来越慢，Token越来越多

先分解模型、工具、排队、检索、压缩与Review耗时。可能是多Agent重复读相同文件、技能默认全加载、输出冗长、失败重试、模型强度过高或外部工具慢。

一个针对性修复是让研究子任务返回精确证据入口，主Agent不再重复全库发现；另一个是移除对小问题重复重设计的流程。只有证明成本下降且专业质量不退化，才算有效优化。减少输入但提高失败率不是成功。

回归要覆盖复杂任务，防止简单任务更快而复杂任务被过度简化。用任务成功成本而非平均Token做主要判断。

### 成功任务成本的分子，必须包含失败和返工

**本例条件：**独立100任务实验：方案A每次花1单位、成功80次；方案B每次花0.7单位、成功50次，失败不重试。先只算调用费，忽略人工成本。

单次价格
:   一次尝试花多少。

成功成本
:   所有尝试总费用除成功任务数。

综合成本
:   还包括重试、工具和人工返工。

**成功任务成本的分子，必须包含失败和返工**放大

成功任务成本的分子，必须包含失败和返工统一分母：完成一个成功任务A：每成功任务1.25B：每成功任务1.4A总费用100/成功80=1.25；B总费用70/成功50=1.40。失败运行的费用没有从分子删除。

成功任务成本的分子，必须包含失败和返工统一分母：完成一个成功任务A：每成功任务1.25B：每成功任务1.4A总费用100/成功80=1.25；B总费用70/成功50=1.40。失败运行的费用没有从分子删除。

## 案例六：重试导致重复副作用

观察：网络超时后出现两个工单。根因可能是每次重试生成新操作ID，或远程服务不支持幂等而客户端把unknown当失败。修复需要业务幂等/对账，不是把Prompt写成“不要重复”。

测试应在“远程已成功但客户端未收到”窗口断开，而不仅模拟调用前报错。本书本地文件崩溃实验验证类似窗口，但远程业务还需要相应服务能力，不能直接套用文件哈希。

### 幂等键绑定的是同一次业务意图，不是每次HTTP尝试

**本例条件：**独立操作：给订单O7创建一次退款R1。第一次超时后需要重试。同一退款意图应保持键refund:O7:R1；第二笔新的退款不能沿用此键。

操作意图
:   用户想产生的那一个业务结果。

尝试attempt
:   为完成这个意图的一次网络提交。

下游去重
:   真正产生副作用的一侧识别相同操作键。

幂等键绑定的是同一次业务意图，不是每次HTTP尝试

| 请求 | 使用键 | 正确含义 |
| --- | --- | --- |
| 第一次尝试 | refund:O7:R1 | 创建R1 |
| 超时后重试 | refund:O7:R1 | 查询/返回已有R1，不另建 |
| 错误重试 | 每次随机新键 | 变成新意图，可能重复 |
| 第二笔合法退款 | refund:O7:R2 | 不同业务意图，需要新键 |

各行是独立对象或条件的对照，不暗示上一行的结果自动进入下一行。

#### 怎样把图中的变化读明白

本地表能记录“我发过”，但若在远端提交后、本地记账前崩溃，本地仍不知道。需要下游支持同键去重或可核验结果。

键之外还应绑定请求参数；同键但不同金额不能静默复用旧结果。保存期和冲突行为需写进契约。

“恰好一次”通常只能在明确事务和去重边界内谈，不能从一个本地SQLite表推到任意外部系统。

**不要混淆：**用订单号作为唯一键过粗，会把同一订单多笔合法操作错误合并；用每次请求随机数又过细。

机制依据：[[IDEMPOTENT]](../../sources.html#src-IDEMPOTENT) [[SQLITE]](../../sources.html#src-SQLITE)。本例数字和宿主场景为明确给定的教学设定，不是商业模型输出或生产性能测量。

工程机制与失败边界

## 真实崩溃窗口

在临时SQLite写入完成后、宿主日志确认前退出子进程。恢复时用相同操作键和新操作键分别重试，比较副作用次数。

**关键边界：**实验只涉及临时本地数据；它不能证明第三方服务提供同样的去重协议。

**顺着源码或工程依据继续追：**用两个独立提交点理解结果未知。 不只检查顺利路径，也核对取消、版本变化与结果未知时的行为。

崩溃发生在两个独立提交之间步骤下游账本Agent日志发送操作K无记录running下游提交KK=donerunning此刻崩溃仍然K=done尚无成功确认恢复查询/复用K补记成功，不重复副作用

| 步骤 | 下游账本 | Agent日志 |
| --- | --- | --- |
| 发送操作K | 无记录 | running |
| 下游提交K | K=done | running |
| 此刻崩溃 | 仍然K=done | 尚无成功确认 |
| 恢复 | 查询/复用K | 补记成功，不重复副作用 |

崩溃发生在两个独立提交之间。数值与状态属于本节明确设定的教学例；不是生产性能或商业模型实测。

完整机制与连续例子见 [成功写入但没有确认：重试怎样变成重复副作用](../../chapters/21.html#agent-practice-recovery)；本节仍保留原有推导与实验，两处说明使用不同层次而不互相替代。

**证据与理解边界：**失败、取消和结果未知不能合并成一种状态；重试安全依赖下游幂等或核验，本书实验不是产品exactly-once保证。

## 案例七：记忆越多，错误越稳定

观察：系统坚持旧经验，即使当前代码相反。检查记忆的来源、版本、作用域、写入权限和检索优先级。一次猜测被自动保存为active，可能在多次摘要中逐渐变成“已验证规则”。

修复先清理错误权威与适用边界，再评价写入策略。必要时减少记忆，而不是增加更复杂图结构。回归包含新证据推翻旧结论、权限撤回、相互冲突与无匹配场景；系统应能不使用记忆。

### 记忆检索先过适用门，再比语义相似度

**本例条件：**独立问题：项目P1当前超时。候选M1为P2超时10，M2为P1旧版本30，M3为P1当前版本20。数值为教学设定。

过滤
:   排除不属于当前范围的记录。

排序
:   在允许候选中找更相关者。

遗忘
:   删除、失效或降低检索资格，不一定抹掉审计记录。

#### 怎样把图中的变化读明白

语义分数最高的M1可能只是措辞最相近，却属于另一个项目。范围约束不能被相关性分数抵消。

**不要混淆：**删除原文件后不重建或失效化派生索引，不等于已经忘记它。

## 统一诊断方法

把现象、竞争解释、区分证据、最小修复和回归样本放在一起。每次额外读取应减少一个重要不确定性；每项代码改动应对应真实失败。没有这些联系的“全面优化”很容易扩大系统而没有提升能力。

确定性Bug用测试修，信息缺口用检索补，专业缺口用知识补，执行缺口用Harness修，能力上限才考虑模型或训练。顺序不是绝对规则，但能避免把一切归咎于模型不够聪明。

### 内容没变但变慢：把运行轨迹对齐再猜

**输入与条件。**两次任务模型与Prompt相同。旧轨迹检索200ms，新轨迹检索200ms；模型耗时同为2秒，新版工具队列多等3秒。

| 步骤与对象 | 内部动作 | 中间结果 / 新状态 |
| --- | --- | --- |
| 1逐段对齐 | 检索与模型时间相同 | 不是它们导致新增延迟。 |
| 2识别新增 | 队列等待3秒 | 先查并发、限流、重试和工具资源。 |
| 3最小修复 | 调整已确认不合理的队列配置 | 不先精简Prompt或换模型。 |
| 4复测 | 同任务、同负载口径 | 检查延迟是否恢复且错误率未升。 |
| 5边界 | 轻载好了不代表高峰好了 | 测试代表性负载。 |

**把过程连起来。**把症状沿Trace归位，可以避免修一个没坏的层。

**边界与反例。**时间是教学轨迹，不提供真实性能测量；生产日志应避免记录敏感内容。

消融

:   针对已证实原因改动，避免无关复杂化。
