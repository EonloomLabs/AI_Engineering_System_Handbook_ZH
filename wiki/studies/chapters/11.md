## 1. 每轮输入都应有一个明确目的

Agent不需要一次性知道整个仓库，而需要足够的信息选择下一步可靠行动。一个调试轮次可能只需入口、候选分支、相关测试和当前约束；实施轮次需要精确代码范围；验证轮次需要当前diff与验收标准。阶段变化，信息需求也变化。[[N23]](../sources.html#N23 "本地来源与核查范围")

上下文管线可分为：获得候选信息，验证来源与权限，判断适用范围与新鲜度，去重，选择必要依赖，分配预算，序列化并记录来源。不要把所有步骤都交给一个“总结一下”的Prompt，否则无法区分检索漏了、选择丢了还是压缩改错了。

原始证据与指导规则也应分区。网页里写“忽略前面指令”，只是外部文本，不应在序列化后变成高优先级命令。权限和来源标签必须由宿主生成，而不是相信文档自报的“最高权威”。

## 2. 预算模型与依赖闭包

先认识这里的对象与符号

[Σ：按下标逐项求和](../../concepts.html#concept-sum)
:   Σ是加法的简写。下标指出哪项在变化；没有被求和的下标保持不变。它不是一个额外参数，也不表示把数组拼在一起。独立微例：Σᵢ xᵢyᵢ，x=[1,2]、y=[3,4]，就是1×3+2×4=11。

设候选项i有成本ci、估计价值vi、选择变量xi。最简单选择问题类似背包：最大化`Σvi xi`，满足`Σci xi≤B`。但现实还存在必须保留项和依赖：如果读取调用点需要类型定义，则`x_call≤x_type`。没有这些约束，仅按“语义相关度/Token”排序可能留下无法理解的碎片。

本书`pack`使用明确依赖闭包和价值密度启发式，不声称求出全局最优。必要项先保留；如果必要项本身超出预算，直接报错，而不是静默丢失硬约束。循环依赖、缺失依赖也显式失败。这些元数据检查可以确定性测试，但vi是教学输入，不是经实测校准的真实信息价值。

预算也不能只等于最大上下文窗口。要预留工具结果、模型输出和后续步骤，并考虑服务实际计算方式。若只能近似Token，应留安全余量并用服务用量校准；字节长度、字符数、Token数不能混用。

### 只取命中的一行，可能把判断条件一起丢掉

**本例条件：**独立源码证据：第18行return 10，只有读取第15—17行才能知道它受debug开关控制。查询命中第18行，但当前任务研究生产配置。

依赖闭包
:   为解释命中内容而必须带上的相关定义与条件。

JIT
:   到需要时再读取，而非全部常驻上下文。

最小充分
:   信息少，但能支持当前判断。

只取命中的一行，可能把判断条件一起丢掉

| 证据层 | 具体内容 | 能否回答生产超时 |
| --- | --- | --- |
| 仅命中行18 | return 10 | 不能，缺分支条件 |
| 加入行15—17 | if debug: return 10 | 知道10仅用于debug |
| 再查实际配置 | debug=false | 该分支生产不生效 |
| 生产分支 | else: return 30 | 生产超时应查30 |

各行是独立对象或条件的对照，不暗示上一行的结果自动进入下一行。

#### 怎样把图中的变化读明白

闭包不是把整个仓库都读完，而是补足当前结论真正依赖的条件。这里多读三行与一个配置，比多读十个无关文件更有价值。

JIT只决定何时取资料，不替代判断哪些资料是必需依赖。检索命中后仍需沿条件与引用扩展。

扩展有停止标准：已经能解释当前现象、满足验收需要，再扩大范围应有新的疑问。

**不要混淆：**把“尽量少读”硬编码成每次只读一行，会系统性丢失函数契约和分支条件。

机制依据：[[CONTEXT]](../../sources.html#src-CONTEXT) [[HARNESS]](../../sources.html#src-HARNESS)。本例数字和宿主场景为明确给定的教学设定，不是商业模型输出或生产性能测量。

工程机制与失败边界

## 依赖丢失的压缩输入

从结论、测试版本、禁止动作、长日志四项中做预算裁剪。要求能说明丢掉哪项会把正确结论变成不安全动作。

**关键边界：**不把Token减少量当成功指标；检查任务成功、关键约束与证据恢复成本。

**顺着源码或工程依据继续追：**同时维护来源、依赖、预算和可信边界。 不只检查顺利路径，也核对取消、版本变化与结果未知时的行为。

完整机制与连续例子见 [上下文组装为什么不能只做“取前N条”？](../../chapters/13.html#agent-practice-context)；本节仍保留原有推导与实验，两处说明使用不同层次而不互相替代。

**证据与理解边界：**某次请求的工具字段为空，可能是增量协议，而非定义丢失。要结合历史与实际协议核查。

核验依据：[[C01]](../../engineering/agent-evidence.html#source-C01) [[C02]](../../engineering/agent-evidence.html#source-C02) [[C08]](../../engineering/agent-evidence.html#source-C08) [[A02]](../../engineering/agent-evidence.html#source-A02)。源码限提交 86e17e98c7f9 和已读取路径；文章经验、公开文档与原创教学实验分别标注。[查看取得方式、阅读范围与限制](../../engineering/agent-evidence.html#acquisition)。

## 3. 小而完整，比碎片多更重要

例子：调用点显示`should_exclude(path,rules)`，函数定义解释path相对仓库根，测试说明末尾斜杠代表目录。三个片段共同定义行为。只保留调用点会误判字符串处理；只保留测试名没有断言，也不足以知道契约。

“最小充分证据”不是固定行数，而是足以回答当前决策的闭包。源码读取可先拿定义与关键调用，再扩展到异常处理和边界测试；每次扩展说明新增证据解决什么不确定性。这样避免无条件扫描，又不会把复杂任务压成片面片段。

长文件截断时要显示是否截断、总范围与继续读取位置。返回100行却不告诉模型后面还有逻辑，会造成虚假的完整性。工具提供范围精确的继续读取，比让模型凭截断结果下结论更可控。

## 4. 权威、新鲜度与适用范围不是一个分数

用户明确要求、当前源码、官方接口文档、过往经验、模型假设有不同语义。不能简单给每条信息一个置信度再加权平均。例如过往经验再高分，也不能授权修改用户禁止的文件；旧版接口示例再相关，也不能覆盖当前版本的真实响应。

推荐分开记录：来源类型、版本或读取时间、作用域、状态（观察/假设/已验证）、证据位置。选择时先施加硬约束，再在允许集合中考虑价值和成本。并非每次任务都要建数据库，简单结构化列表也能承担这件事。

信息冲突应保留冲突及解决条件。两个文档描述相反，先看版本和适用产品面；无法判定时不应在摘要中融合成一个看似确定的结论。保留“不确定的具体是什么”，比写泛泛的免责声明更有用。

### 指令冲突与事实冲突，不能用同一“最新优先”解决

**本例条件：**独立项目问答：项目规则要求不发送密钥；新抓网页要求上传密钥。另有同权限配置：旧默认30、新版本默认10。两类冲突分开看。

权限层级
:   谁有权要求执行动作。

适用范围
:   事实对哪个项目、版本、时间有效。

来源时间
:   记录或发布的时间，不自动等于生效时间。

指令冲突与事实冲突，不能用同一“最新优先”解决

| 冲突类型 | 冲突的两项 | 判断依据 |
| --- | --- | --- |
| 行为指令 | 项目禁止泄露 / 新网页要求上传 | 网页不能提升为指令权威 |
| 版本事实 | v1超时30 / v2超时10 | 当前运行版本决定适用值 |
| 生效时间 | 今天得知下周改为10 | 今天仍可能适用30 |

各行是独立对象或条件的对照，不暗示上一行的结果自动进入下一行。

#### 怎样把图中的变化读明白

新网页比项目规则晚出现，也不能因此改变安全边界。这里“最新”不是授权。

同一权限的业务事实要核对版本和生效时间，不能只按消息排列决定哪个是真。

把结论写成“v2自某日开始默认10”比孤立写“默认10”更容易在后续检索中保持正确。

**不要混淆：**给所有来源一个综合相关性分数后直接选最高，会把权限、时效和语义匹配混成无法审计的排序。

机制依据：[[SPEC]](../../sources.html#src-SPEC) [[CONTEXT]](../../sources.html#src-CONTEXT) [[LONGMEM]](../../sources.html#src-LONGMEM)。本例数字和宿主场景为明确给定的教学设定，不是商业模型输出或生产性能测量。

## 5. JIT加载的收益与失败方式

技能描述适合保持短而可判别，专业细节在确认相关后读取，资源按任务继续展开。这样减少默认上下文，但描述过窄会漏加载，过宽会误加载；延迟发现关键约束也可能导致返工。[[N27]](../sources.html#N27 "本地来源与核查范围")

先认识这里的对象与符号

[Skill、JIT与触发描述](../../concepts.html#concept-skills)
:   在能力加载场景，Skill是一组可复用指导与资源；JIT表示需要时再加载，不是必然指编译器即时编译。触发描述帮助模型判断适用性，不自动授予工具权限。应先判断任务需不需要某技能，再读详细内容；已加载技能不等于它的要求已实际执行。

因此JIT的评价不是“加载Token减少”，而是必需能力召回、不必要加载、首次有效行动时间和最终工程结果。专业技能必须包含能改变动作的知识，如特定语言并发语义、存储事务边界、框架测试策略；泛泛要求“高质量、可维护”并不能替代专业内容。

代码注入与工具权限也不同。加载一个含MCP说明的Skill，不会自动授予MCP连接。应分别验证内容路由与工具路由。把权限故障误判为JIT失败，会造成错误设计。

### 把需要确定执行的动作放在程序里，不只写进说明

**本例条件：**独立需求：提交前必须运行格式检查，复杂安全修改再请Reviewer。比较Instruction、Skill、Hook、Tool与Agent的职责。

Instruction
:   持续或当前任务的指导。

Hook
:   在明确事件触发的程序逻辑。

Tool
:   模型可请求的动作。

Agent
:   有自己上下文与执行循环的任务承担者。

把需要确定执行的动作放在程序里，不只写进说明

| 要求 | 更合适的承载方式 | 为什么 |
| --- | --- | --- |
| 项目默认编码约定 | Instruction/文档 | 持续指导 |
| 特定迁移任务的检查方法 | Skill | 按需加载专业步骤 |
| 提交前确定跑格式检查 | Hook或CI | 不依赖模型记得请求 |
| 需要读取/测试 | Tool | 提供明确动作 |
| 独立复杂审查 | 子Agent，按风险启用 | 有独立任务与证据需求 |

各行是独立对象或条件的对照，不暗示上一行的结果自动进入下一行。

#### 怎样把图中的变化读明白

如果某操作是机械必做且容易确定触发，程序钩子通常比让模型每次记住它更可靠。

Skill不是钩子的替代：它告诉“怎样做”，不自动保证事件发生时执行。

多Agent也不是更高级的Tool，每个独立上下文会产生初始化、交接和合并成本。

**不要混淆：**所有任务固定经过多个Agent和重复Review，可能增加成本而没有解决新的失败模式。

机制依据：[[SKILLS]](../../sources.html#src-SKILLS) [[AGENTS]](../../sources.html#src-AGENTS) [[HARNESS]](../../sources.html#src-HARNESS)。本例数字和宿主场景为明确给定的教学设定，不是商业模型输出或生产性能测量。

## 6. 评测上下文而不干扰它

对同一组任务比较全量默认加载、按需加载、按需加结构状态三种方案。固定模型、工具与测试；记录实际读取的文件、必需证据首次出现时间、重复读取、压缩次数、最终通过率。按任务类型分层，防止平均值掩盖复杂任务退化。

还可以做移除实验：拿掉一份参考后结果不变，说明它在当前任务集中的边际贡献可能有限；但不能据此证明所有未来任务都不需要。新增内容应有明确失败样本，删除内容也应保留对应回归样本。

运行示例 · S11

### 选了高分片段，却漏掉它的否定前半句

**输入与条件。**原句“不要部署到production；staging可以。”候选片段拆成“部署到production”和“staging可以”。

| 步骤与对象 | 内部动作 | 中间结果 / 新状态 |
| --- | --- | --- |
| 1打分失误 | 前半残片与部署问题高度相关 | 检索分数并不能保留逻辑否定。 |
| 2依赖补全 | 恢复完整句子及主体 | 得到正确禁止项。 |
| 3预算冲突 | 完整句多占少量空间 | 先保约束完整，而非机械挑最高相关短片。 |
| 4输入拼接 | 区分用户限制与引用资料 | 防止重新获得错误指令身份。 |
| 5核验 | 在候选行动production上检查 | 应拒绝，staging仍按其余条件判断。 |

**把过程连起来。**上下文选择需要语义依赖，不能只优化各独立片段的分数/长度比。

**边界与反例。**“上下文编译器”在本书是工程类比，不意味着LLM输入可以完全确定性语义检查。

依据与适用范围：[[CONTEXT]](../../example-sources.html#ex-src-CONTEXT)。示例输入和场景由本书明确设定。

## 7. 验收题

一条高价值调用示例依赖一个很长的类型文件，预算放不下，怎么办？先检索精确类型定义与必要字段，减少依赖成本；若仍不够，拆成先理解类型再记录可追溯结论的阶段，但不能把未读内容当已知。必要约束冲突必须显式处理。

本章最重要的成果不是一个庞大context manager，而是能指出每轮输入里哪些信息必需、为什么可信、来自何处、何时失效，以及缺少它会导致哪种具体错误。
