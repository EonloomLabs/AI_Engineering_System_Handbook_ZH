## 1. 多Agent能带来什么真实收益

相对独立的信息搜索可并行，不同任务可拥有不同上下文与工具，部分审查可隔离实现者的假设。Anthropic研究系统提供了主Agent协调、子Agent并行探索的工程案例；Agentless则提示某些软件任务中结构化简单流程也有竞争力。二者回答的任务与设置不同，不存在一条“多Agent总是更好”的结论。[[N26]](../sources.html#N26 "本地来源与核查范围")[[N47]](../sources.html#N47 "本地来源与核查范围")

多Agent增加的成本包括任务说明、重复检索、上下文交接、合并、冲突解决和额外模型调用。若所有人修改同一段核心逻辑，分工可能只把原本连续的思考切碎。若任务本身很小，协调成本甚至超过实现成本。

## 2. 用关键路径而不是Agent数量估计加速

设工作中可并行比例p，理想N个执行者的加速上界近似`1/[(1−p)+p/N]`；再加入协调、通信、重复和合并开销，真实速度更低。这是Amdahl式推导的应用，不是模型实验结果。

先认识这里的对象与符号

[DAG、依赖与关键路径](../../concepts.html#concept-dag)
:   DAG是有方向且没有环的任务依赖图。箭头A→B表示B依赖A完成；关键路径是在给定任务时长与依赖下决定最早完成时间的最长依赖链。独立例：A需2秒，B/C依赖A分别需3/5秒且可并行，则A后两者完成至少7秒，不是把2+3+5=10当墙钟时间。

以两个独立模块各自修改、最后集成为例，理想耗时是二者最大值加集成时间，而不是两者相加。但如果第二模块需要第一模块确定接口，存在依赖边，不能真正并行。任务DAG应表达产出依赖，而不是按“分析/实现/审查”机械切成固定三层。

共享限流也会破坏理想并行。四个Agent同时请求同一外部API，可能互相限流；总Token预算固定时，扩大并发也会挤压每个任务可用证据。评估应统计完整任务墙钟时间与总资源，而不是只看某个子任务很快。

## 3. 委派契约需要哪些信息

委派说明至少应有目标、范围、当前事实、必要约束、可用工具、预期返回形式与完成条件。信息要充分但不复制整段主会话。重要假设应明确是待验证，不要作为事实灌输给所有子Agent。

返回结果应区分结论、证据位置、已执行动作、未解决问题。主Agent只接收漂亮摘要而没有原始来源，就无法判断冲突或复核。需要精确代码时，应读取子Agent标明的当前版本，而不是让它在摘要里手工重写一段可能错的源码。

不同宿主的上下文继承方式不同，有独立上下文也有fork；工具与权限也由产品配置决定。设计时先核实宿主机制，不应在技能里写一个抽象“继承全部权限”就当作已经实现。[[N21]](../sources.html#N21 "本地来源与核查范围")[[N22]](../sources.html#N22 "本地来源与核查范围")

### 交接包至少要让接手者知道证据和未完成动作

**本例条件：**独立主Agent委派：子Agent验证exclude补丁，不允许写文件。主Agent已改filter.py到r8，测试尚未运行。

任务目标
:   子Agent这次要交付什么。

证据快照
:   它应阅读的具体版本。

未完成项
:   不能被总结成完成的工作。

交接包至少要让接手者知道证据和未完成动作

| 交接字段 | 本例内容 | 缺失后的风险 |
| --- | --- | --- |
| 目标 | 验证exclude边界，不重新设计 | 工作方向扩大 |
| 证据 | filter.py@r8 + diff + 失败样例 | 回到r7误判 |
| 权限 | 只读与运行测试 | 误改文件 |
| 状态 | 补丁已应用，测试未跑 | 把未验证当通过 |
| 回传要求 | 测试命令、版本、结果、失败项 | 主Agent无法复核 |

各行是独立对象或条件的对照，不暗示上一行的结果自动进入下一行。

#### 怎样把图中的变化读明白

子Agent不是天然拥有父Agent全部记忆。交接包要让它从明确状态开始，而不是仅给“检查一下”。

可以保留短的摘要，再按引用读取原始证据；不必复制整个父级历史，但不能丢掉约束和版本。

回传既要有结论，也要有可验证产物。仅有“没问题”无法支持最终交付。

**不要混淆：**为省Token删掉未完成项，可能让两个Agent都以为对方已执行关键测试。

## 4. 文件并发与集成边界

对独立写任务，分支或worktree可降低直接覆盖，但不能消除语义冲突。两个补丁分别通过测试，合并后可能改变共享接口、依赖版本或配置行为。合并后的当前工件必须重新验证，不应沿用各分支的绿色结果。

先认识这里的对象与符号

[CAS、版本检查与TOCTOU](../../concepts.html#concept-cas)
:   CAS是比较预期版本/值仍匹配后再更新的受控操作。TOCTOU是检查与使用之间发生变化的竞态：分开的“先看版本再写”不自动等价原子CAS。读到版本7生成补丁，提交时已是8，应拒绝直接覆盖并重新处理；比较与写入间也要防并发插入。

对同一文件的修改，先定义责任范围或串行化关键部分。内容哈希/CAS可防覆盖，但失败后仍需人工或Agent理解冲突，不能自动选择最后写者。某些任务适合子Agent只研究，主Agent集中实施，减少并发写冲突。

如果子Agent能修改测试，主Agent需要识别测试是否被弱化。验证资源应有明确所有权，高风险验收可放在工作区外或受限执行环境。把“测试全绿”当成果时，先确认测试本身仍验证原要求。

### 不同文件无文本冲突，也可能产生语义冲突

**本例条件：**独立协作例：Agent A把函数返回值从int改为对象；Agent B在另一个文件新增调用，仍按int比较。两个分支Git可干净合并。

文本冲突
:   修改同一文本区域产生冲突。

语义冲突
:   接口与调用者假设不一致。

集成验证
:   针对合并后的组合状态运行检查。

不同文件无文本冲突，也可能产生语义冲突

| 分支 | 局部修改 | 局部结果 |
| --- | --- | --- |
| A分支 | parse()返回{"value":3} | 自身测试通过 |
| B分支 | if parse()>2: ... | 基于旧接口测试通过 |
| 合并后 | 新parse + 新调用者 | 运行时对象与整数比较失败 |
| 正确验收 | 在合并工件r9上运行契约测试 | 绑定最终组合版本 |

各行是独立对象或条件的对照，不暗示上一行的结果自动进入下一行。

#### 怎样把图中的变化读明白

Git保证的是文本合并能力，不验证业务接口。两个“都通过”属于不同工件，不能相加为合并后通过。

共享接口改动宜先明确契约或分配所有权，让依赖方知道何时更新。

提交前检查最终diff、接口契约和受影响集成测试，比仅给每个Agent单独评分更接近交付质量。

**不要混淆：**用多工作树隔离写入能防覆盖，却不能免掉最终语义集成。

## 5. 独立Review不等于独立错误

同一模型、同一提示和同一上下文可能共享错误前提。实现者的解释先展示给审查者，会让其被结论锚定。独立审查可先看原需求、当前diff和测试，再看实现理由；但这也增加阅读成本，需用于值得的任务。

多数投票只在错误具有足够独立性、投票目标可识别时才有预期收益。若所有Agent都相信过期API文档，投票不会恢复事实。更有效的方法可能是增加独立证据，例如读取当前接口或运行测试，而不是再加入第五个相同审查者。

小问题可在当前Review中直接修复并验证，不必退回重新分析、重新设计、再次Review的完整循环。涉及目标改变、破坏性架构决策时才需要回到设计。风险驱动而非仪式驱动。

### 两个Reviewer同意，可能只是共享了同一个盲点

**本例条件：**独立补丁审查：作者与两个Reviewer都只看到正常输入vendor/a.py，没有看到myvendor/a.py反例。

相关错误
:   多个评审因同样资料或假设而犯同类错。

独立证据
:   不同测试或观察，不只是不同措辞。

A2A
:   通信与任务交互协议，不替代审查质量。

两个Reviewer同意，可能只是共享了同一个盲点

| 评审者 | 看到的测试 | 结论能力 |
| --- | --- | --- |
| 作者 | 只有正常路径 | 无法排除包含匹配Bug |
| Reviewer 1 | 复用同一测试 | 同意不能新增边界证据 |
| Reviewer 2 | 仍复用同一测试 | 票数增加，覆盖没增加 |
| 增加反例 | myvendor/a.py必须保留 | 能真正区分错误实现 |

各行是独立对象或条件的对照，不暗示上一行的结果自动进入下一行。

#### 怎样把图中的变化读明白

独立会话与独立错误是不同概念。相同模型、相同输入、相同测试容易共享漏点。

可把审查任务分成契约核对、反例生成和运行证据复查，让新增工作确实带来不同证据。

A2A能帮助系统发现对方、交换任务状态；它不自动提供全局事务、权限或“多票就是真”的保证。

**不要混淆：**把多数投票包装成可靠性认证，会掩盖相关失败，尤其在高风险但低频边界上。

## 6. 取消、失败与部分完成

一个子任务失败不一定使所有任务无效。主Agent应知道哪些产物可复用、哪些依赖失败结果。取消后可能仍有在途工具动作，需要等待可确认的终态或记录unknown。不要通过删除子任务日志假装一切未发生。

对超时任务，先读取已持久化证据，避免重做；对无进展循环，调整任务边界或缩小问题。重启新Agent并复制全部历史，有时只把同一失败再次运行。恢复策略应针对错误类型，而不是统一“再试一次”。

## 7. 何时不拆分

目标清晰、修改小、证据集中、验证便宜的任务，单Agent往往足够。跨语言/独立模块/广泛研究且结果容易独立核验的任务，更可能受益于并行。这个判断应由实际依赖和风险支撑，不要求为每个任务创建复杂度分数。

验收题：四个研究Agent产出四份不同结论，应该总结平均意见吗？不应。先比较来源、时间、作用域和证据质量；有些分歧只是条件不同，有些是真矛盾。整合是证据裁决，不是语言折中。

运行示例 · S17

### 相关错误下，三位Agent不应按独立概率相乘

**输入与条件。**假设三位审查者面对相同错误资料，总会一起判断错误。每次任务共同出错概率20%。

| 步骤与对象 | 内部动作 | 中间结果 / 新状态 |
| --- | --- | --- |
| 1边际错误 | 每位都是20% | 单独观察看起来一样。 |
| 2错误相关 | 三位一起错的概率仍20% | 不是0.2³=0.8%。 |
| 3多数票 | 共同错误仍获全票通过 | 投票没有改善这一类失败。 |
| 4独立证据 | 增加运行测试或新版本读取 | 可能打破共同前提，但要实测。 |
| 5工程成本 | 三倍调用却无新增信息 | 应考虑减少重复审查而不是加第四位。 |

**把过程连起来。**概率乘法需要独立条件；多Agent通常共享模型、上下文和环境，不能默认独立。

**边界与反例。**完全相关是极端构造，用于反例；真实相关度介于多种情况之间，需要实际数据估计。
