## 1. 比较对象必须先明确

先认识这里的对象与符号

[IDE、CLI、UI与DOM](../../concepts.html#concept-interface-environment)
:   IDE是集成开发环境，CLI是命令行界面，UI是用户界面，DOM是网页文档的结构对象树。不同入口自动附带的代码、选区和页面信息可能不同。模型在IDE里看到选中函数，不代表同一任务在CLI里也已收到该函数；先检查本轮输入对象。

Claude Code CLI、IDE中的聊天、Copilot CLI、GitHub托管编码Agent，并非同一个运行环境。某项工具、Skill、记忆或MCP功能在一个产品面可用，不能自动推到另一个。比较模型能力时，还要控制实际模型、可用工具、网络、仓库索引、权限和执行环境，否则观察到的是整套系统差异。

官方文档公开了Claude Code的循环、上下文构成、自动清理与压缩、子Agent和记忆机制；Copilot CLI自定义Agent文档公开了profile与工具配置。两者并未提供所有内部Prompt和服务实现。对未公开部分，应写“未公开/未测”，而不是根据一次输出猜出固定算法。[[N20]](../sources.html#N20 "本地来源与核查范围")[[N21]](../sources.html#N21 "本地来源与核查范围")[[N22]](../sources.html#N22 "本地来源与核查范围")

## 2. 上下文不是只有聊天记录

Claude Code公开说明其上下文包含会话、工具结果、项目指令、记忆和按需加载内容，并存在清理旧工具输出与会话压缩机制。技能可先加载描述、使用时再读取内容。工具定义的发现方式也可能随产品实现变化，不能把一个旧版本的工具Token成本当作恒定值。[[N20]](../sources.html#N20 "本地来源与核查范围")

工程上要区分“文件已存在于项目”“工具已经读过”“目前仍在模型上下文”“被保存在外部记忆”四种状态。一个大文件先被读过，经过压缩后可能只剩摘要；后续需要精确代码时，应重新读取原始位置，而不是要求模型凭摘要恢复源码。

对多目录仓库，还应检查规则加载作用域。自动记忆与人工维护的项目指令具有不同生命周期，不能因为名字都含memory就视为同一权威。当前源码和用户明确要求应能纠正过期经验，而不是被历史摘要永久压住。

### 有状态与无状态接口，区别在于谁保存前一轮对象

**本例条件：**独立两轮协议示意：第一轮输出工具调用c1，结果为“30”。左边由客户端完整重放，右边通过服务端响应ID关联。具体字段随API而变。

客户端历史
:   宿主显式保留并提交的消息序列。

服务端状态
:   由响应ID等引用的已存对象。

请求级配置
:   工具、规则等是否继承要查具体接口约定。

有状态与无状态接口，区别在于谁保存前一轮对象

| 本轮需要的信息 | 客户端重放路线 | 服务端关联路线 |
| --- | --- | --- |
| 任务与调用 | 显式提交原任务+c1 | 引用之前响应r1 |
| 工具结果 | 提交c1结果=30 | 提交c1结果=30 |
| 本轮规则/工具 | 按需再次提交 | 不能只凭r1推定所有配置自动继承 |
| 长期记忆 | 需单独保存/检索 | 会话关联本身不提供事实更新与遗忘 |

各行是独立对象或条件的对照，不暗示上一行的结果自动进入下一行。

#### 怎样把图中的变化读明白

两条路线都要让模型知道结果对应c1。不同的是旧记录通过实际内容还是引用传递。

一个字符串session\_id只是一把查状态的钥匙；服务是否存了什么、保留多久、哪些配置本轮有效，要由契约决定。

迁移到别的模型时，普通文本证据可能可重组，不透明压缩块则不能假定可跨提供方解释。

**不要混淆：**链路连续不等于状态无限、完整或永不失效。故障时检查实际请求与服务状态，而不是仅确认ID没变。

机制依据：[[TOOLS]](../../sources.html#src-TOOLS) [[COMPACT]](../../sources.html#src-COMPACT) [[RESPONSE-STATE]](../../mechanisms/sources.html#source-RESPONSE-STATE)。本例数字和宿主场景为明确给定的教学设定，不是商业模型输出或生产性能测量。

## 3. 子Agent不应被笼统描述为“完整继承”或“完全空白”

Claude Code文档描述独立子上下文，也存在fork当前会话的方式；委派模式不同，初始上下文不同。主Agent最终得到什么返回内容、工具调用是否留在子上下文、技能是否预加载，都需要按具体配置核实。[[N21]](../sources.html#N21 "本地来源与核查范围")

Copilot CLI的自定义profile包含描述、提示、可选工具列表和MCP配置；文档说明未限定工具时可以访问可用工具集合。但“可用工具”仍受宿主配置、连接和权限影响，不代表系统里任何MCP服务都自动登录可用。[[N22]](../sources.html#N22 "本地来源与核查范围")

从工程角度可拆成三层：工具发现决定看见哪些名称，Agent配置决定允许请求哪些工具，执行权限决定一次具体调用能否成功。模型选中工具是第四层。只修其中一层不能保证最终调用发生。

### 子Agent继承什么，要逐字段检查而不是说“全继承”

**本例条件：**独立主子Agent实验：主任务有规则R、证据E、工具集合T和凭据P。是否传给子任务由真实产品配置决定，下图是待核对的清单，不伪造默认行为。

继承
:   新上下文实际获得的内容与能力。

独立上下文
:   有自己消息历史，不等于没有任何配置。

授权
:   执行器给予的权限，不是任务文本。

子Agent继承什么，要逐字段检查而不是说“全继承”

| 字段 | 应查证的问题 | 证据位置 |
| --- | --- | --- |
| 规则R | 是否自动载入项目说明 | 子请求或可见配置 |
| 证据E | 主Agent读过的代码是否转交 | 子上下文材料清单 |
| 工具T | 允许哪些工具 | 子Agent工具配置 |
| 凭据P | 是否有下游访问身份 | 执行结果/鉴权日志 |
| 完成回传 | 返回结论还是工件与证据 | 交接内容 |

各行是独立对象或条件的对照，不暗示上一行的结果自动进入下一行。

#### 怎样把图中的变化读明白

主Agent说“去修同一个问题”只给了目标，可能没给根因证据；子Agent因此重新搜索，不一定是能力变差。

工具权限可以比父级更窄。不能靠在子任务文字里写“沿用全部权限”来扩大实际能力。

用可复查探针确认每一列，结论标明产品入口与版本；不要把一次行为推广到所有版本。

**不要混淆：**为了省Token只回传“已完成”，会丢掉文件版本、失败项和测试证据，主Agent无法验证成果。

机制依据：[[SUBAGENTS]](../../sources.html#src-SUBAGENTS) [[CLAUDE]](../../sources.html#src-CLAUDE)。本例数字和宿主场景为明确给定的教学设定，不是商业模型输出或生产性能测量。

工程机制与失败边界

## 继承矩阵

按规则、历史、模型、工具、权限、身份和环境分别列父子关系，明确每项继承、重新配置或禁止的条件。

**关键边界：**避免“默认继承全部”这种不可执行说明；验证的是实际运行配置。

**顺着源码或工程依据继续追：**逐项核对文件、层级、快照与运行时能力。 不只检查顺利路径，也核对取消、版本变化与结果未知时的行为。

完整机制与连续例子见 [规则文件加载与子Agent继承，为什么不能只说“自动继承”？](../../chapters/12.html#agent-practice-rules)；本节仍保留原有推导与实验，两处说明使用不同层次而不互相替代。

**证据与理解边界：**共享规则文件名不等于跨产品自动生效；Claude Code的AGENTS.md需按文档引入，子Agent也不是复制所有父上下文。

核验依据：[[C10]](../../engineering/agent-evidence.html#source-C10) [[C11]](../../engineering/agent-evidence.html#source-C11) [[C12]](../../engineering/agent-evidence.html#source-C12) [[D02]](../../engineering/agent-evidence.html#source-D02) [[D03]](../../engineering/agent-evidence.html#source-D03)。源码限提交 86e17e98c7f9 和已读取路径；文章经验、公开文档与原创教学实验分别标注。[查看取得方式、阅读范围与限制](../../engineering/agent-evidence.html#acquisition)。

## 4. 一套低成本、可复查的宿主行为探针

本书没有在用户本机运行Codex、Claude或Copilot。下面是读者可自行执行的实验设计，不能当成已测结果：建立无秘密的样例仓库，根目录和子目录分别放一条无害、可辨认的规则；用同一简单任务在不同cwd启动；记录版本、加载提示与输出。然后显式调用一个只读自定义Agent，比较它能看到的工具和规则。

先认识这里的对象与符号

[JSON：结构化文本，不是执行动作](../../concepts.html#concept-json)
:   JSON是一种用对象、数组、字符串、数字等表达数据的文本格式。花括号对象把字段名映射到值，方括号数组保留项目顺序。解析JSON只得到数据，不会自动执行其中的工具名称。独立例：{"path":"a.py","limit":3}有两个字段；"3"是字符串而3是数值，Schema可以要求其中一种。

探针不应让模型仅回答“我已经加载了技能”。应设置必须使用该规则才能满足的可验证结果，例如生成一个规定键名的JSON，但同时避免把该键名直接泄露到用户任务中。即使结果符合，也只能作为间接证据；若宿主支持加载日志或上下文显示，应结合更直接证据。

压缩探针可以在长任务早期设置明确约束，中间加入正常工作记录，触发受支持的压缩，再让Agent继续一个依赖该约束的任务。还要保留未压缩对照、不同位置与重复试验。单次回忆成功不等于任何长任务都安全。

### IDE、CLI与云端任务的工作区不是天然同一份

**本例条件：**独立产品比较方法：同一仓库commit=r7，但IDE里文件未保存，CLI看到磁盘，云端可能只有已推送commit。这里只列潜在差异，实际以使用版本和配置核对。

编辑器缓冲区
:   尚未落盘的文字。

工作树
:   本地文件系统的当前状态。

远端快照
:   运行环境取得的指定提交或工件。

IDE、CLI与云端任务的工作区不是天然同一份

| 入口 | 可能看到的版本 | 验证动作 |
| --- | --- | --- |
| IDE | r7 + 未保存修改u1 | 核对选区、缓冲区与附件 |
| CLI | r7 + 已落盘修改w1 | 读取工作树内容与diff |
| 云端 | 已推送r7或指定快照 | 核对checkout版本和依赖 |

各行是独立对象或条件的对照，不暗示上一行的结果自动进入下一行。

#### 怎样把图中的变化读明白

“模型一样、问题一样”不代表输入一样。入口差异可能在模型调用之前就决定了它看见的代码版本。

先固定commit、工作树diff、环境与权限，再比较结果，否则把环境差异归因于模型是错误实验。

云端测试通过后，还要确认结果对应最终下载或合并的工件，而不是另一个尚未同步版本。

**不要混淆：**聊天里粘贴了新代码，不等于测试进程执行的文件已变成新代码；模型视图与执行环境要分别核对。

机制依据：[[COPILOT]](../../sources.html#src-COPILOT) [[HARNESS]](../../sources.html#src-HARNESS)。本例数字和宿主场景为明确给定的教学设定，不是商业模型输出或生产性能测量。

## 5. 权限与检查点的误区

先认识这里的对象与符号

[checkpoint：必须看保存的对象](../../concepts.html#concept-checkpoint)
:   模型检查点保存权重或训练状态；激活检查点保存少量中间节点以便反向时重算；Agent任务检查点保存执行进展。三者同名，但恢复对象完全不同。看到checkpoint先问“恢复参数、重算激活，还是继续任务”。Agent保存摘要不会更新模型权重。

一些工具提供文件编辑回退或会话恢复，但不应推断它能撤销外部邮件、远程部署或数据库写入。文件checkpoint、会话历史、执行日志与远程世界是不同状态空间。第08章的unknown状态在真实产品里同样需要考虑。

配置“只读审查”也要检查工具能力。如果审查Agent能执行任意Shell，实际权限可能超过文字描述。应由执行器限制，而不是只写一句“不修改文件”。另一方面，不必对每次正常读文件都要求人工批准；用边界清晰的沙箱可以减少审批疲劳。

## 6. 面向rd-skills这类扩展层的最佳取舍

扩展层应该增加宿主欠缺的专业知识与准确路由，而不是重复实现宿主已有的会话、工具、持久化和权限系统。先确认具体失败发生在skill描述、加载边界、专业内容、返回证据还是宿主自身。若正确技能已可见但内容泛泛，继续优化router不会解决专业质量问题。

一个高价值改动的例子：某技能在明确不相关任务误加载，添加适用边界及反例，并在误加载与必须加载任务上共同验证。一个低价值改动的例子：因为担心任何任务遗漏，默认加载所有专业资料，再额外建立多个路由Agent审查。后者同时增加上下文、延迟与冲突，必须有非常明确的实测收益才能成立。

## 7. 比较结论应该如何书写

严谨结论应写成：“在某版本CLI、某仓库、某权限与工具配置下，任务集X观察到Y；未测试托管版或其他模型。”不能写成“Claude总是这样、Copilot永远那样”。产品行为会变，可信工程知识要能区分稳定原理和版本事实。

本章验收：能够为一次技能未生效列出至少三个相互竞争的解释，并设计最少额外调用来区分它们。优先获取可观察配置和运行证据，避免通过模型自述或不断增加规则来猜原因。

### 黑箱产品实验：只改一项指令来源

**输入与条件。**准备同一仓库同一任务，A运行在仓库指令缺失时，B只新增只读规则文件，其余工具权限与模型配置不变。

| 步骤与对象 | 内部动作 | 中间结果 / 新状态 |
| --- | --- | --- |
| 1记录输入条件 | 版本、表面、规则位置和发现日志 | 保证能解释差异。 |
| 2执行A/B | 观察是否读取规则以及是否提出写动作 | 不只看最终答复是否客气。 |
| 3加入执行边界 | 工具权限始终只读 | 避免为了测试而实际产生越权副作用。 |
| 4解释结果 | B提出写动作减少 | 只能说明这组条件下行为变化，不揭示闭源内部Prompt全文。 |
| 5重复 | 相同任务多次与相邻任务对比 | 区分偶然采样和稳定影响。 |

**把过程连起来。**公开文档与黑箱行为实验可以互补，但不能由一次行为推断全部内部实现。

**边界与反例。**这是实验设计而非已执行的商业产品测试，没有虚构胜率。

工程机制与失败边界

## 产品行为与代码事实对照

对照同一任务的实际请求、工具日志和最终产物；开源可追函数，闭源只陈述公开文档及可观察事实。

**关键边界：**不要推测隐藏Prompt或把某个历史工程文章当成所有当前会话的固定算法。

**顺着源码或工程依据继续追：**把实现事实、经验报告、产品文档和教学设计分开。 不只检查顺利路径，也核对取消、版本变化与结果未知时的行为。
