## 批准后参数改写

对最终动作计算稳定身份摘要，分别改变字段顺序和目标环境。字段顺序变化不应改变逻辑身份，目标环境变化应使原批准失效。

**关键边界：**不要只批准函数名；审核日志同时记录实际执行与向模型呈现的结果。

**顺着源码或工程依据继续追：**尤其警惕“拒收结果”被误读为“动作未发生”。 不只检查顺利路径，也核对取消、版本变化与结果未知时的行为。

后置拒收不回滚已完成动作路径外部写入次数模型看到的状态执行前拒绝0blocked / 未执行执行后拒收1blocked / 结果被拒收补偿操作取决于下游协议不是自动发生

| 路径 | 外部写入次数 | 模型看到的状态 |
| --- | --- | --- |
| 执行前拒绝 | 0 | blocked / 未执行 |
| 执行后拒收 | 1 | blocked / 结果被拒收 |
| 补偿操作 | 取决于下游协议 | 不是自动发生 |

后置拒收不回滚已完成动作。数值与状态属于本节明确设定的教学例；不是生产性能或商业模型实测。

完整机制与连续例子见 [前置检查、后置检查为什么不能互相替代？](../chapters/10.html#agent-practice-hooks)；本节仍保留原有推导与实验，两处说明使用不同层次而不互相替代。

**证据与理解边界：**后置检查发生时动作可能已完成。Codex与Claude Code的后置block语义不同；结果脱敏还须检查原日志。

## B.4｜模型调用M2：明确下一步缺哪段证据

M2根据定位结果发出两个读取动作：

```
[
 {"kind":"tool_call","call_id":"c2","name":"read_file",
  "arguments":{"path":"pipeline/filter.py","start_line":1,"end_line":70}},
 {"kind":"tool_call","call_id":"c3","name":"read_file",
  "arguments":{"path":"tests/test_filter.py","start_line":1,"end_line":60}}
]
```

它们是只读、互不依赖的操作，可以并行，但每个结果仍须保留自己的ID。c3先返回不代表它属于c2。宿主不应按“第一个回来就是第一个调用”匹配。

假设读到以下教学代码：

```
from fnmatch import fnmatchcase

def excluded(path, patterns):
    return any(fnmatchcase(path, pattern) for pattern in patterns)

def select_files(root, files, patterns):
    return [p for p in files if not excluded(str(p), patterns)]
```

这里还不能立刻断言root未使用就是唯一错误。需要确认files传入的是绝对路径还是相对路径，patterns语义是什么，路径分隔符规则如何。一个未使用参数是线索，不是根因证明。

### c2和c3可以并行，但结果不能按到达顺序串号

沿用M2的两个只读调用和r42，不假定它们谁先完成。

c2和c3可以并行，但结果不能按到达顺序串号

| 调用ID | 应当读取的文件 | 结果归属规则 |
| --- | --- | --- |
| c2 | pipeline/filter.py，1—70行 | 返回c2只能填到实现证据槽 |
| c3 | tests/test\_filter.py，1—60行 | 返回c3只能填到测试证据槽 |
| 即使c3先到 | 不得当成第一个发出的c2 | 按call\_id关联，而非按数组位置关联 |

并行改变的是等待方式，不会取消每个动作的身份。源文件与测试文件混淆后，模型可能基于不存在的实现作判断。

两次只读相对独立，所以可以并行；后续补丁写入则仍要绑定版本，不能因为读取并行就把所有后续写入也并行。

## B.5｜模型调用M3：从候选解释到可反证检查

把需要验证的假设写成可检查关系：

```
H1：匹配函数本身不支持此模式。
H2：调用方把绝对路径传入了相对模式匹配。
H3：测试期望与已确定的产品语义不一致。
```

在本教学轨迹中，运行独立的两个断言：相对路径`generated/a.py`应匹配`generated/*`；同一文件绝对路径`/work/demo/generated/a.py`不匹配该相对模式。再确认用户指定的产品语义确实是根目录相对路径。这样H2获得支持，H1与H3被相应证据削弱。

M3输出运行测试调用c4，而不是“我已经验证过”：

```
{"kind":"tool_call","call_id":"c4","name":"run_tests",
 "arguments":{"target":"tests/test_filter.py","revision":"r42"}}
```

结果应包含命令、返回码、实际运行测试数和失败断言。这里的教学轨迹假定原始失败已被观察；不能把本页的示例文本当成真实仓库测试报告。可执行的机制实验见拓展阅读，确定性协议测试见计算与运行链路实验。两组示例分别说明输入条件和结果范围。

## B.6｜模型调用M4：补丁表达的是变更，不是结果

候选修复应在正确边界把路径转为根目录相对形式，并明确根外路径如何处理。`relative_to`可能失败；不能为了让它不报错就把异常静默吞掉，也不能无需求地重新设计所有路径语义。

```
{"kind":"tool_call","call_id":"c19","name":"apply_patch",
 "arguments":{
  "path":"pipeline/filter.py",
  "expected_revision":"r42",
  "patch_ref":"patch/p1",
  "purpose":"仅在匹配前构造根目录相对路径"
 }}
```

执行器检查版本和补丁前提，再修改文件。这里出现了三个不同状态：模型提出p1、执行器开始c19、文件实际变为r43。它们不能压成一个“已修复”。

如果其他用户先把文件改成r42b，expected\_revision不匹配，应该拒绝或重新读取协调。直接按旧片段覆盖，会破坏用户修改。版本检查与写入之间还有并发窗口，需要与存储机制结合；仅在Python中“先读哈希再写”并不自动消除竞争。

## B.7｜最重要的故障窗口：文件改了，但成功结果丢失

假设c19已完成文件替换，运行器却在记录成功前崩溃。模型和任务状态只知道超时，外部文件已经是r43。

```
时间t1：记录 c19 pending
时间t2：执行 c19，文件 r42 → r43
时间t3：进程中断，成功响应未送达
时间t4：恢复时看到 c19 尚未确认
```

把c19标为failed并直接重试，可能再次修改文件；把它标为succeeded则可能在另一种故障窗口下撒谎。正确状态是[unknown](../glossary.html#g149 "无法确认外部动作是否已经完成的状态。 例：超时可能发生在成功执行之后。")：需要核验。

恢复器调用inspect\_operation或读取目标版本/补丁效果。如果外部系统支持幂等键，可以用c19或独立业务键查询；本地文件系统则检查目标内容和预期变更是否已应用。只有证据表明未发生，才允许按适当条件重试。

这里不能承诺“有一张本地表就实现分布式[exactly-once](../glossary.html#g183 "要求业务效果恰好一次的语义目标。 例：至少一次传输加幂等可帮助实现，不是任意系统自动保证。")”。如果状态表和外部副作用不在一个原子事务里，仍有窗口。工程目标是明确结果、避免危险重复，并为无法判定的情况提供受控恢复。

### c19响应丢失时，三个地方的状态并不相同

沿用p1、c19、r42→r43这一次修改；没有把“超时”解释为“没有修改”。

c19响应丢失时，三个地方的状态并不相同

| 时刻/对象 | 实际变化 | 可得出的结论 |
| --- | --- | --- |
| t1：任务账本 | c19=pending | 动作已登记 |
| t2：磁盘 | p1已应用；r42→r43 | 外部副作用已经发生 |
| t3：进程/网络 | 成功回执丢失 | 不能据此否认磁盘变化 |
| t4：恢复宿主 | 将c19标记unknown并核验 | 匹配r43则转入测试，不再重复补丁 |

失败回执和缺少回执不是同一件事。这里最重要的对象是磁盘事实，不是摘要对这件事的措辞。

恢复后先核验p1是否生效，既不能直接重做，也不能盲目猜成功；核验本身失败时仍需保留unknown。

## B.8｜长会话要压缩：压缩前有哪些信息不能丢

到这里历史可能已有多次搜索、整文件读取和失败尝试。对后续任务最重要的是目标、约束、已确认根因、当前文件版本、未确认操作、测试状态和证据位置。

错误摘要：

> 已修复exclude问题，准备交付。

它同时犯了三件事：把执行未知写成完成；把原始测试结果误用到新版本；丢掉“不提交、不部署”。即使文字很短很流畅，也不适合作为恢复状态。

更合理的教学摘要：

```
{
 "task":"t7",
 "goal":"exclude按根目录相对路径匹配",
 "constraints":["保留包含规则","不提交、不部署"],
 "confirmed_cause":{"claim":"绝对路径进入相对模式匹配",
   "evidence":["e/read-c2@r42","e/test-c4@r42"]},
 "patch":{"id":"p1","call_id":"c19","status":"unknown"},
 "workspace":{"last_confirmed":"r42","observed_candidate":"r43"},
 "next":"先核验c19，再对确认后的当前版本运行测试",
 "verification":{"current_patch_tested":false}
}
```

摘要不是原始证据的替代品。`e/read-c2@r42`必须能找回来源；如果源码已变，要知道旧证据只能支持历史判断，不能直接代表当前事实。

### 压缩时保留哪几个字段，才能继续核验c19

承接同一个c19未确认窗口。新摘要不是新的执行证明；原始动作记录仍是恢复依据。

压缩时保留哪几个字段，才能继续核验c19

| 字段 | 必须保留的值/关系 | 丢失后的风险 |
| --- | --- | --- |
| 动作身份 | task=t7，call=c19，patch=p1 | 无法关联到底哪次修改 |
| 执行前提 | expected\_revision=r42 | 把旧补丁应用到新文件 |
| 当前知识 | 回执缺失，执行结果unknown | 误写failed诱发重复修改 |
| 核验入口 | 目标pipeline/filter.py与p1记录 | 只能凭摘要猜测是否完成 |

这里的关键不是让摘要更长，而是保留决定下一步动作的事实与未决状态。背景闲聊可以省，unknown不能改成失败。

原始日志或外部状态核验完成后，才有依据把任务状态推进为已应用或未应用；摘要不能自己创造这个结论。

## B.9｜压缩不是原地删历史，而是一次状态切换

先取得待压缩历史的快照版本H17，再生成候选摘要C18。校验关键约束、工具调用配对、unknown状态和证据引用。重建稳定系统指令、必要工具定义与新摘要，再条件性替换当前上下文。

若生成摘要时用户插入新指令，当前历史已变成H18，就不能盲目用基于H17的摘要覆盖新消息。可以把新消息追加到新上下文，或重新协调快照；具体策略由运行器决定。本质是并发状态更新问题，不是“让模型总结得更认真”就能解决。

压缩后模型请求M5应包含：原始授权范围、上述恢复状态、核验工具以及最新观察。旧的所有大段源码不必常驻，但模型需要时可以按证据ID重新读取。缓存命中可能变化；这影响成本，不应成为保留错误上下文的理由。

## B.10｜模型调用M5：先核验，不重复写

M5看到c19 unknown，选择：

```
{"kind":"tool_call","call_id":"c20","name":"inspect_operation",
 "arguments":{"operation_id":"c19","target":"pipeline/filter.py","patch_ref":"patch/p1"}}
```

教学返回：

```
{"call_id":"c20","status":"succeeded",
 "finding":{"operation_applied":true,"workspace_revision":"r43",
 "expected_change_present":true}}
```

宿主现在可以把c19更新为已核验完成，仍不能把整个任务标成完成。新代码是否满足功能和回归要求，是下一阶段验证问题。

如果返回只说“文件存在”，不足以证明补丁已应用；如果内容与p1部分一致，要识别部分修改、外部并发或核验不足，不能强行归到成功。结果Schema需要表达不确定性，而不是只有true/false逼模型选一个。

## B.11｜模型调用M6：测试必须绑定r43

M6调用测试c21，结果应表明实际在r43上运行了哪些测试。若通过，再检查改动范围和用户约束，形成最终交付。若测试期间源码再次变化，结果不能自动证明新版本正确，需要重新核对受影响范围。

最终回答的结构可以是：根因、修改范围、验证证据、剩余限制。不得声称已经提交或部署，因为用户明确禁止且本例没有执行。一个合格的结束条件是：所需修复已确认、相关验证完成、无待核验重要副作用、未越权。

这里不存在必须追加一整轮独立Review的固定要求。若变更风险低且证据充分，可结束；若跨模块语义或并发风险尚未确认，就继续有针对性的验证。Review的价值来自消除特定风险，不来自流程名字。

## B.12｜面试官继续追问：每轮都把全部历史重新传一遍吗

不一定。接口可能由客户端传完整逻辑历史，也可能引用服务端保存的响应或会话；服务仍需构建本轮可用上下文。逻辑历史连续、网络只发增量、计算缓存命中，是三个独立维度。

使用不透明压缩状态时，客户端可能无法逐字段检查模型内部保留内容，所以更要在外部持久状态中保留任务约束、操作结果和证据引用。不能把全部工程可靠性押在一个无法检查的摘要块上。

另一个追问是：子Agent是否自动继承这些工具和状态？不能假设。应根据产品和配置确认，交接时显式提供任务所需的最小证据与权限。主Agent有[MCP](../glossary.html#g150 "宿主与外部工具或资源服务器交互的一套协议。 例：不是Agent间全部通信的总称。")，不代表每个子Agent都能访问；子Agent返回“完成”也不代表最终工作区已经整合并通过测试。

读完本例应能回答：一项事实最早在哪个阶段被知道、谁有权改变它、谁负责记录它、压缩后如何恢复，以及哪个证据足以关闭任务。能回答这些，才是理解Agent运行，而不只是会背“思考—行动—观察”。
