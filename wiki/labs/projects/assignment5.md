# 作业05｜全栈：用一个可推翻的假设改进同一任务

**作业范围**

这是本教材的原创累积实验。默认离线路径仅操作生成的临时数据；真实模型、外部账号及GPU路径须自行配置，未运行项明确保留为NOT\_RUN。

Agent、模型和服务都可以改，不等于应该同时改。最后一次综合实验的核心是解释因果：什么工作被省掉了，什么开销被转移了，为什么任务仍然正确。

<a id="question"></a>

## 先定义一条主张

好的主张有对象、条件和结果。例如：“在本机公开夹具、固定任务与脚本后端下，移除无用diagnostics降低累计请求字节；是否降低真实模型计费与端到端延迟尚待验证。”这比“上下文优化提高了系统性能”更窄，却可复查。

真实项目可以提出更强主张，但必须增加匹配证据。不能将GPU内核加速、模型回答偏好和任务成功率揉成一个“提升百分比”。

<a id="section-3b0dd1413e62"></a>

### 两个手算检查

一项任务40毫秒模型计算后，并行执行20毫秒读取与60毫秒检索，再30毫秒汇总。按依赖最早完成为40+max(20,60)+30＝130毫秒，而总工作量为150毫秒。把20毫秒读取加速到10毫秒，关键路径仍为130；它可能省资源，却没有减少该任务的最短墙钟时间。

若60%的总时间所在部分加速2倍，理想总加速为`1/(0.4+0.6/2)=1.42857`。这假设比例和其他开销不变；新通信、额外验证、排队与缓存失效会降低实际收益。不要把2倍局部加速直接写成2倍任务加速。

<a id="matrix"></a>

## 实验矩阵

| 实验 | Agent策略 | 模型／引擎 | 目的 |
| --- | --- | --- | --- |
| 基线 | 固定 | 固定 | 确定正确率、资源及失败类型 |
| 单改Agent | 只改一个因素 | 与基线一致 | 分离控制流或上下文效果 |
| 单改服务 | 与基线一致 | 只改一个服务因素 | 分离缓存、调度或精度效果 |
| 组合 | 已验证策略 | 已验证配置 | 检查交互，不能假设收益可相加 |
| 反例与压力 | 冻结候选 | 冻结候选 | 长上下文、并发、失败恢复与分布外任务 |

更换模型可能改变工具选择、轨迹长度和验证次数，所以不能只把新的单次调用延迟代入旧轨迹，便宣布新系统更快。模型路由同样需要让候选策略真实运行到任务结束。

## 交付目录

```
project/
  hypothesis.json       # 改动前保存的预测与否证条件
  environment.json      # 硬件、模型、引擎、工具、依赖版本
  task-manifest.json    # 任务及初始状态、切分、排除规则
  baseline/             # 全部运行，不只成功样本
  candidate/
  grader/               # 固定判分逻辑及版本
  analysis.md           # 配对结果、质量约束、资源账、限制
  reproduce.md          # 可执行命令与外部依赖
  rollback.md           # 配置、权重、索引、记忆如何恢复
```

<a id="review-assignment-5-handoff"></a>

### 最终报告只需要一条可被反例推翻的主张

选一个具体瓶颈，固定基线与验收，先预测结果，再做一个主要干预和消融。把失败改动、预算耗尽、无法复现的差异一并保留；结论强度不能超过实测范围。

| 最小交接字段 | 含义 |
| --- | --- |
| task\_set\_revision | 任务集合与拆分，不只任务数量 |
| artifact\_before / artifact\_after | 待处理与交付工件的版本 |
| system\_revision | 代码、模型、模板、工具/检索设置 |
| run\_mode | script\_fixture / local\_numeric / live\_model |
| budget / seed / environment | 可控条件；不支持或未测写明 |
| outcome / evidence | 成功、失败、未知、未运行与对应原始记录 |

这些字段用于对照，不要求为小练习搭建数据库或复杂平台。一份JSON和已有日志足够；没有改变的输入用同一版本，新增资料不要悄悄覆盖旧结果。

依据与范围：[[CS2680-A3]](../../sources.md#review-CS2680-A3)；[[CS2680-A4]](../../sources.md#review-CS2680-A4)；[[LOCAL]](../../sources.md#review-LOCAL)。算例条件在本节给定；教学结果不代表商业模型或生产性能。

<a id="project"></a>

## 最终项目的两条路线

**产品路线：**从你日常确实重复的工作出发，例如资料问答或仓库诊断，证明目标用户能完成任务，错误可恢复、权限清楚、成本可承担。**研究路线：**提出一个现有基线不能解释的问题，给出可辨别机制的对照和消融，说明结果在哪类工作负载成立。研究路线不能用演示替代实验，产品路线也不能用高分替代可用性。

写报告前先让另一人复现一条成功与一条失败。书中的参考答案只覆盖机制，不替你编造项目观察；用AI辅助代码或文字时，记录你核验了哪些输出、哪些结论来自亲自运行。

<a id="rubric"></a>

## 自学评分量表

| 维度 | 应提供的证据 |
| --- | --- |
| 问题与价值 | 真实任务、用户和不可接受后果，非技术名词堆叠 |
| 机制理解 | 输入、状态、关键计算或调用链及其边界 |
| 实验有效性 | 强基线、配对数据、质量约束和失败费用 |
| 复现与诚信 | 原始记录、环境、命令、NOT\_RUN项与限制 |
| 取舍 | 收益以外的复杂度、维护、安全和回滚代价 |

该量表服务于本教材自学，不是Harvard正式评分政策。CS2680截至2026-10-23的A5仅有公开总体目标，尚未发布完整任务细则；本作业是原创延伸，不能称为官方A5的翻译。
