## Q065｜grep、AST、LSP、调用图各知道什么？为什么不能互相替代？

这题先认识什么正则找文本，AST找语法结构，LSP找语言语义关系。动态加载、宏和生成代码会影响静态分析的完整性。

[F30 · 代码不是普通文档](../foundations/30.html)

### 核心回答

grep寻找文本模式；[AST](../glossary.html#g168 "抽象语法树，表示程序的语法结构。 例：能区分函数定义与普通字符串，但不包含全部运行事实。")描述语法结构；[LSP](../glossary.html#g169 "编辑器与语言服务交互的协议，支持定义、引用和诊断等。 例：服务能力取决于语言实现与项目配置。")通过语言服务提供定义、引用、类型诊断等能力；调用图描述可能或已观察的调用关系。文本出现不等于符号引用，语法正确不等于类型正确，静态可达不等于运行实际发生。[[TREESITTER]](../sources.html#src-TREESITTER "来源说明")[[LSP]](../sources.html#src-LSP "来源说明")

### 顺着一个函数名检索

搜索`filter_items`，可能命中函数定义、注释、字符串和测试数据。grep快且通用，但不知道哪些是同一符号。AST能识别函数声明和调用表达式，排除一部分注释/字符串干扰；但仅凭语法树，未必能解析导入别名、泛型或运行时分派。

语言服务结合项目配置、依赖与类型信息，把某个使用位置解析到具体定义。两个不同模块同名函数不应混在一起。若构建配置错、依赖没装、语言服务器索引未完成，结果也可能缺失或过期。

静态调用图能帮助扩展影响范围，但反射、依赖注入、动态导入、函数指针和多态会使它不完整或保守过宽。运行[trace](../glossary.html#g197 "一次任务的执行轨迹与其中有开始结束的操作跨度。 例：并行跨度的耗时不能直接全加成墙钟时间。")只展示这一次输入经过的路径，也不能证明其他路径不存在。可靠定位通常组合文本、结构、类型和运行证据。

### grep、AST、LSP、运行日志分别回答不同层的问题

**本例条件：**独立代码例：两个模块都定义parse；某处调用obj.parse()。只找到字符串parse，不能确定运行时调用哪一个实现。

AST
:   解析后的语法结构树。

LSP
:   编辑器与语言服务沟通定义、引用等能力的协议。

动态派发
:   实际接收者类型可能在运行时才确定。

grep、AST、LSP、运行日志分别回答不同层的问题

| 工具层 | 能得到的证据 | 还不能确定 |
| --- | --- | --- |
| grep | 所有出现parse的位置 | 哪些是注释，哪些是调用 |
| AST | 这是一处成员调用表达式 | obj实际是哪种类型 |
| 语言服务 | 在当前项目配置下推断定义与引用 | 反射、运行时注入的所有路径 |
| 测试/栈轨迹 | 此次执行进入模块B.parse | 其他输入是否也走同一路径 |

各行是独立对象或条件的对照，不暗示上一行的结果自动进入下一行。

#### 怎样把图中的变化读明白

每一层都不是上一层的万能替代。grep适合快速缩小范围，AST排除文本噪声，语言服务补静态语义，运行证据核对实际路径。

运行一次确定了一条路径，不等于证明所有输入都只走这条路径。诊断报告应注明样例输入与环境。

某层失败后要识别原因：解析失败可能是语法版本，跳转错误可能是项目配置，不必直接归因于模型。

**不要混淆：**LSP返回的字符位置也有编码约定，UTF-16偏移不能不加转换地当成Python字符下标。

机制依据：[[TREESITTER]](../sources.html#src-TREESITTER) [[LSP]](../sources.html#src-LSP) [[HARNESS]](../sources.html#src-HARNESS)。本例数字和宿主场景为明确给定的教学设定，不是商业模型输出或生产性能测量。

运行示例 · Q065

### 同名foo出现三次，grep和LSP给出的集合为何不同

**输入与条件。**文件a定义foo，文件b导入a.foo并调用，文件c在一个函数内定义了另一个局部foo；注释也提到foo。

| 步骤与对象 | 内部动作 | 中间结果 / 新状态 |
| --- | --- | --- |
| 1文本搜索 | 搜索字符串foo | 得到定义、调用、局部同名与注释。 |
| 2语法过滤 | AST识别Call节点 | 可去掉注释，但同名调用仍可能属于不同绑定。 |
| 3符号解析 | LSP查a.foo的引用 | 应关联b的调用，不把c的局部foo混入。 |
| 4运行证据 | 若调用由字符串动态生成 | 静态引用可能漏，需检查注册与实际日志。 |
| 5修改范围 | 根据绑定和测试确定调用方 | 不能机械替换所有foo文本。 |

**把过程连起来。**文本相等、语法角色相等和符号身份相等是逐步增强但不同的关系。

**边界与反例。**LSP准确性依语言服务与工程配置；动态语言、反射、生成代码不保证静态穷尽。

依据与适用范围：[[DERIVE]](../example-sources.html#ex-src-DERIVE)。示例输入和场景由本书明确设定。

### 追问：Tree-sitter解析成功就表示代码能编译吗？

不。它关注语法结构并可容忍不完整编辑状态；类型错误、链接错误、依赖缺失和运行异常需要其他工具。把AST当完整语义数据库会错过工程配置层。

### 追问：为什么查references比全仓grep更有价值？

当语言服务正确配置时，它按符号身份返回引用，减少同名误命中，并可跨别名和模块追踪。但不支持的动态模式可能仍漏；应根据语言和项目情况选择，不能把零引用当绝对无人使用。

### 追问：什么时候直接grep最好？

已知错误码、配置键、日志文本、文件名或精确函数名时，低成本文本搜索往往是最有效入口。先用便宜工具缩范围，再使用语义与类型工具深入。不是技术越高级越应优先执行。

工程深挖 · E33 · 接续Q065

### 代码位置的单位错一个，编辑就可能改错字符：UTF-8、UTF-16与版本号

预备知识：[F03](../foundations/03.html) · [F23](../foundations/23.html) · [F30](../foundations/30.html)。阅读顺序：先确认运行契约，再看反例与修复，最后检验边界。

#### “character=3”先问单位是什么

LSP3.17的Position.character按初始化协商的PositionEncodingKind解释；UTF-16是默认且服务器必须支持的编码，UTF-8和UTF-32的计数含义不同。这一规则来自Microsoft规范的position.md，不是根据JavaScript字符串习惯猜出来的。[[LSP]](../engineering/sources.html#src-LSP "Microsoft · Language Server Protocol 3.17")

固定字符串`a😀b`，b之前有2个Unicode码点、3个UTF-16 code unit、5个UTF-8字节。Python的普通字符串len、JavaScript常用的字符串长度、协议传输Content-Length和LSP位置因此可能给出不同数字。不要把中文英文测试通过当成Unicode位置处理正确。

#### 从一个位置到一次安全编辑

先用协商编码解释起止位置，再按对应的文档快照转换到内部索引；范围采用协议约定的边界，不能把结束位置误当包含最后字符。随后核对文档版本，最后生成编辑。相同line/character在用户继续输入后可能指向完全不同内容。

本书实际计算上述三个长度，另将版本与内容指纹检查作为执行层约束。它没有启动真实语言服务器，因此不宣称通过某IDE兼容性认证。

#### 版本冲突不能靠“附近搜索同名文本”盲目修复

如果收到的编辑基于版本7，而当前buffer已经版本8，直接应用可能覆盖用户新内容。自动重定位需要明确上下文和冲突策略；无法唯一判断时应重新获取范围或拒绝。模型给出的行号只是提议，不能绕过宿主的版本保护。

#### 追问：文件落盘内容与编辑器buffer谁更权威？

要看动作对象。LSP常处理内存文档；shell测试通常读取磁盘。两个视图没同步时，模型可能分析buffer而测试旧文件。证据中应写“来源是内存版本还是工作树文件”，必要时显式保存或让验证读同一快照。

#### 追问：为什么不用所有地方统一成字节偏移？

内部可以统一，但边界仍需精确转换；协议、编辑器和模型报告未必使用字节。统一存储单位不代表可以忽略输入单位。包含组合字符、emoji、CRLF和非BMP字符的测试能暴露隐藏假设。

#### 本地观察与复核入口

以下为随包程序实际运行记录。数值算子、临时文件／数据库实验与教学逻辑模拟各自的范围，在实验页逐项注明；不能据此声称已测试商业模型或生产环境。

## 代码证据为什么需要工作树版本，而不只是commit？

### commit相同，文件也可能不同

用户有未提交修改，Agent也会在任务中连续写文件。两次测试都写着commit abc，实际测试对象可能分别是工作树r7和r9。应记录受影响文件内容哈希、运行命令、环境与测试集合，而不只记录分支名。

源码与证据版本链证据绑定对象失效条件补丁r7旧文本文件已被改成r8测试工作树哈希+命令测试后再修改诊断环境+运行输入配置与数据变化

| 证据 | 绑定对象 | 失效条件 |
| --- | --- | --- |
| 补丁 | r7旧文本 | 文件已被改成r8 |
| 测试 | 工作树哈希+命令 | 测试后再修改 |
| 诊断 | 环境+运行输入 | 配置与数据变化 |

源码与证据版本链。数值与状态属于本节明确设定的教学例；不是生产性能或商业模型实测。

### 从文本搜索到可验证修改

先用路径、报错、精确符号缩小范围；需要时再借AST或LSP查定义与引用；最后用运行证据验证假设。语法树能表达结构，但不自动知道动态加载、运行配置或生成文件。LSP位置还依赖协议协商的编码单位，不能把UTF-16位置无条件当UTF-8字节偏移。

### 补丁的三个前置条件

教学补丁P针对r7的第12行。真正应用前要核对目标仍是r7、预期旧文本仍存在、路径仍在允许范围内。若文件变成r8，不能依赖旧行号硬覆盖。补丁工具自动寻找相似上下文也不证明语义正确，应用后仍要看diff与测试。

### 为什么测试通过之后再修改会失效

测试结果对象应绑定 `source_hash + command + environment + test_selection`。通过后再格式化或生成代码，至少需要重新验证受影响部分。退出码0也要检查是否全部跳过、没有收集到测试、命令被错误包装或环境变量改变了测试范围。

Anthropic的长任务工程强调可恢复进度与可验证功能，而非只写“完成”；大型并行编码案例同样依赖测试与协调。案例说明一种工程方法的价值，不是任何任务都该采用大规模并行。[[A06]](../engineering/agent-evidence.html#source-A06)[[A15]](../engineering/agent-evidence.html#source-A15)

### 交付应该回答四个问题

改了什么、为什么改、哪些证据支持、哪些仍未验证。把“静态检查通过”和“实际运行验证通过”分别表述；无法执行某项检查时记录原因与风险，而不是把未运行写成通过。

### 阅读、修改、测试必须指向同一对象

固定教学例：read看到r7，patch生成r8，测试运行r8；若格式化又产生r9，不能在交付中继续把r8测试标成r9已通过。这个原则不要求任何小修改都全仓重测，而是要求验证覆盖面与最后变动匹配。

长任务工程文章强调可恢复产物和实际测试，但没有提供适用于所有语言的测试选择器。AST、LSP、依赖图如何帮助缩小范围仍需语言工具自己的定义与当前工作树证据；不将一般Harness文章作为具体LSP协议结论的出处。[[A06]](../engineering/agent-evidence.html#source-A06)[[D07]](../engineering/agent-evidence.html#source-D07)

## Q066｜代码索引怎样处理Git版本、工作树和未保存文件？

这题先认识什么仓库快照、工作区未提交文件与运行依赖共同决定实际程序；仅引用commit不足以代表当前执行版本。

[F24 · 状态、事件与检查点](../foundations/24.html)[F30 · 代码不是普通文档](../foundations/30.html)[F34 · 工程质量的基础](../foundations/34.html)

### 核心回答

一个仓库可能同时有提交快照、磁盘工作树、编辑器未保存缓冲和后台索引。[Agent](../glossary.html#g136 "根据任务与观察调用模型和工具、持续推进的执行系统。 例：不只是一次写得很长的Prompt。")必须知道当前证据来自哪一层，编辑与测试针对哪一层。路径相同不等于内容相同。

### 四份“同一个文件”的冲突

main上的`filter.py`版本r10，用户本地已改为r11但未提交；编辑器又有未保存r12；索引仍是r10。Agent从索引读到r10，生成补丁后写磁盘覆盖r11；用户保存编辑器r12又覆盖Agent补丁。即使每一步本身没有报错，最终结果也错。

先认识这里的对象与符号

[IDE、CLI、UI与DOM](../concepts.html#concept-interface-environment)
:   IDE是集成开发环境，CLI是命令行界面，UI是用户界面，DOM是网页文档的结构对象树。不同入口自动附带的代码、选区和页面信息可能不同。模型在IDE里看到选中函数，不代表同一任务在CLI里也已收到该函数；先检查本轮输入对象。

安全的读取接口应尽可能返回内容来源与版本标识。编辑时核对预期旧内容或版本；测试实际运行磁盘或构建环境中的哪份代码也要明确。对IDE集成，可设计工作区overlay优先读取未保存内容，但不能假设所有工具都自动共享该overlay。

增量索引要处理文件修改、删除、重命名和生成文件变化。只按mtime可能漏掉特殊时间戳或缓存问题；只按路径也会误识别重命名。具体实现可以结合版本和内容标识，但不必为每次简单搜索建立复杂全仓签名。

先认识这里的对象与符号

[HEAD、工作树、ETag与内容指纹](../concepts.html#concept-version-tools)
:   Git的HEAD标识当前检出的提交或分支位置；工作树还可能有未提交修改。ETag是HTTP资源表示的校验标识，其保证取决于服务。内容指纹按字节计算；几种版本身份不能互换。索引来自提交v7，而文件已本地修改时，同一文件名不代表同一内容。执行补丁或引用证据应核对实际版本。

**本例条件：**独立文件filter.py：仓库r7返回False，磁盘未提交改成True，编辑器未保存又加条件。索引基于r7构建。

工作树

### 追问：全仓索引更新完再允许Agent工作是否最安全？

会降低延迟且可能阻塞不必要的任务。可采用候选索引定位后直接读取当前文件确认的策略：索引负责快找，实时读负责事实。高风险修改的关键依赖再明确检查版本，不必每次重建整个仓库。

### 追问：为什么只记录Git commit还不够？

未提交改动、生成代码、依赖锁文件、环境变量和测试配置都可能影响执行。验证证据至少要对应实际工作树状态与命令环境。[commit](../glossary.html#g170 "Git提交快照与当前工作目录的内容。 例：未提交修改意味着二者可能不同。")是重要标识，但不涵盖所有可变输入。

### 追问：源码更新后旧结论是不是全部作废？

不一定。只需重新验证受影响的事实与依赖。可以把知识绑定到具体模块/文件/符号，变化触发局部复核。全量遗忘浪费成本，永远不失效又危险；关键是依赖范围清楚。

### HEAD没变为什么证据已经过期？工作树、未保存buffer与索引快照

预备知识：[F30](../foundations/30.html) · [F33](../foundations/33.html) · [F34](../foundations/34.html)。阅读顺序：先确认运行契约，再看反例与修复，最后检验边界。

#### commit只标识提交，不标识当前全部事实

同一HEAD下文件可以有未提交修改；编辑器还可能有未保存buffer；构建产物与环境变量也可改变运行结果。把检索缓存key写成repo+HEAD，并不总能保证读到当前代码。Git工作树机制区分工作目录与共享仓库数据，不能把它理解为每个事实都由commit覆盖。[[GIT]](../engineering/sources.html#src-GIT "Git · git-worktree")

本书在临时目录把`x=1`改成`x=2`，固定“HEAD标签”不变，文件内容哈希改变。这个实验没有伪造Git提交，只用实际文件变化证明逻辑：仅提交身份不足以覆盖工作树状态。

#### 证据应描述它观察的那个世界

一份代码证据可记录路径、内容指纹、范围、仓库提交、工作树/文档版本以及读取时间；运行证据还包含命令、依赖、配置与输入fixture。没有必要为每个小任务建复杂数据库，但至少应能回答“这条测试究竟对应哪份文件”。

检索索引可能异步更新。用户刚改代码，语义索引还在旧快照时，应该对命中的关键文件重新读取，或明确索引版本。对于修改操作，不允许直接拿旧snippet的行号写当前文件。

#### 补丁的前置条件要和写入放在同一个受控过程

先读hash=r7，生成补丁期间别人改成r8；提交前检查还是r7，再原子替换。如果检查与替换之间仍允许另一个写者插入，就存在TOCTOU（检查时与使用时之间的变化）窗口。协作系统需共同遵守锁或使用支持版本条件更新的存储。

#### 追问：给每个Agent一个worktree就不会冲突吗？

它隔离各自文件修改，便于汇总，但最后合并可能有语义冲突；共享端口、数据库、包缓存和部分Git状态也没有自然隔离。依赖同一外部状态的测试还需独立fixture。[[GIT]](../engineering/sources.html#src-GIT "Git · git-worktree")

#### 追问：怎样避免把旧测试结果错贴到新补丁上？

记录测试启动和结束时验证的版本/指纹。所有预期修改完成后运行验收；若测试期间文件变了，结果应标为基于旧版本或不确定。展示“最后一次测试绿色”而不展示验证对象，会制造虚假安全感。

## Q067｜一个Bug应怎样逐步定位？为什么“多读源码”不是充分方法？

这题先认识什么Bug定位从可复现现象到候选代码，再排除反例。找到看起来可疑的函数不等于找到了根因。

[F29 · 从搜索结果到可信答案](../foundations/29.html)[F30 · 代码不是普通文档](../foundations/30.html)[F34 · 工程质量的基础](../foundations/34.html)

### 核心回答

先形成可观察失败，再提出可证伪假设，选择能区分假设的最小证据。代码阅读、测试和日志应服务于缩小原因集合，而不是无目的累积上下文。

### 以exclude不生效为例

用户现象：配置了`build/**`但仍打包build目录。候选原因可包括配置没加载、规则解析错误、路径规范化不一致、匹配结果被后续覆盖。先确认运行配置中有规则，排除第一类；再打印或测试匹配入口收到的路径，发现是绝对路径而规则针对相对路径；构造最小测试后复现。此时重点转向规范化与根目录语义，而不是继续读取无关打包模块。

如果只读到`fnmatch(path,pattern)`就直接换库，可能把根因掩盖，还引入新匹配语义。修复前先确认需求：规则按仓库根还是当前目录？路径分隔符如何处理？目录规则是否包含子文件？符号链接是否跟随？这些边界决定测试和补丁。

最小补丁后，先跑原失败案例，再跑针对相邻语义的回归。若测试仍失败，应依据新错误更新假设，不能重复同一改法。每次操作最好能回答“预期看到什么，结果不同说明什么”。

### 定位Bug：用能区分假设的输入，而不是盲目多读文件

**本例条件：**独立目录排除Bug：规则vendor/应排除vendor/a.py，不应排除myvendor/a.py。原实现把字符串包含关系当目录前缀。

反例
:   用来击穿错误实现的小输入。

假设
:   对错误原因的可验证解释。

分界
:   两种实现输出不同的位置。

定位Bug：用能区分假设的输入，而不是盲目多读文件

| 输入 | 期望 | 包含匹配的实际结果 |
| --- | --- | --- |
| vendor/a.py | 排除 | 排除：看不出错 |
| myvendor/a.py | 保留 | 排除：暴露误匹配 |
| src/vendor/a.py | 按约定规则判断 | 需先定义是根目录规则还是任意层目录 |

各行是独立对象或条件的对照，不暗示上一行的结果自动进入下一行。

#### 怎样把图中的变化读明白

第一行通过不能证明算法正确，因为正确实现和错误实现都能过。第二行才区分了它们。

第三行提醒：有时不是代码错而是需求没定义。先固定规则语义，再写测试，否则Agent只能猜。

确认根因后做最小修改并回归相邻边界，比继续读更多无关文件更有效。

**不要混淆：**修改后若仅新增第一行测试，依然无法防止原来的错误实现再次出现。

机制依据：[[HARNESS]](../sources.html#src-HARNESS) [[SWEBENCH]](../sources.html#src-SWEBENCH)。本例数字和宿主场景为明确给定的教学设定，不是商业模型输出或生产性能测量。

### exclude误删ab目录：从失败输入一步步到根因

**输入与条件。**要求排除目录a及其子目录，但保留ab。旧判断是path.startswith("a")；输入为a、a/x、ab/y。

| 步骤与对象 | 内部动作 | 中间结果 / 新状态 |
| --- | --- | --- |
| 1运行旧逻辑 | 三个字符串都以a开头 | ab/y被误判排除。 |
| 2写正确语义 | 规范化后path==a或path以a/开头 | 边界是目录分隔符，不是任意字符前缀。 |
| 3最小反例 | 用ab/y即可触发错误 | 不需要先重构整个路径系统。 |
| 4回归集合 | a→排除，a/x→排除，ab/y→保留 | 再加绝对/相对路径、分隔符规范化的实际需求。 |
| 5工程取舍 | 目录是否涉及软链或大小写 | 仅在部署平台与需求真实涉及时补对应规则。 |

**把过程连起来。**先把目标语义写成区分正确与错误实现的例子，再做最小必要修改。

**边界与反例。**字符串条件只对已规范化的教学POSIX路径成立；不能直接当作跨平台安全路径校验。

依据与适用范围：[[DERIVE]](../example-sources.html#ex-src-DERIVE)。示例输入和场景由本书明确设定。

### 追问：反证式分析是否意味着设计很多检查表？

不必。可以只保留两三个可区分假设和最便宜验证。反证的核心是允许事实推翻自己的解释，而不是把简单Bug升级成长期研究项目。

### 追问：什么时候需要扩大阅读范围？

局部行为正确但系统结果错误、涉及调用方契约、状态传播或并发时，应沿数据/控制依赖扩展。先明确缺什么证据，再读相关边界。宽泛阅读应由问题驱动，而不是默认步骤。

### 追问：模型提出合理根因，为什么仍要复现？

合理解释可能有多个，只有观察与可重复反例能区分。复现也为补丁提供验证：原版本失败、新版本通过。没有复现时仍可做有依据修复，但应清楚说明验证不足，不能把推测包装成已确认根因。

## Q068｜怎样让Agent“懂业务”，而不是每次只看局部代码？

这题先认识什么业务规则既来自代码也来自约定与数据；先记录适用条件和验收示例，再决定哪些知识值得成为长期指导。

[F24 · 状态、事件与检查点](../foundations/24.html)[F30 · 代码不是普通文档](../foundations/30.html)[F34 · 工程质量的基础](../foundations/34.html)

### 核心回答

把业务目标、不变量、关键流程、领域术语和实现入口连接起来，并保持可查询、可验证、可更新。业务理解不是把所有文档塞入Prompt，也不只是一份架构图。

### 建立从需求到实现的最短路径

例如“订单取消后不能重复退款”是业务不变量；它对应状态机、支付接口幂等键、数据库约束和测试。Agent处理退款Bug时，需要知道这个不变量，再找到执行路径和验证方式。文档只写“系统使用微服务架构”几乎不能指导正确修改。

可用轻量入口文件说明核心对象、边界、常见任务与代码路径；具体模块文档记录为什么这样设计、哪些替代方案被拒绝、当前例外。决策记录应该简短并带适用条件，不是每个变量命名都写ADR。

代码、测试、运行指标和文档彼此核对。文档说“最多重试三次”，代码常量是五次，不能自动选文档或代码为真；需判断当前环境与目标规范，再决定这是文档过期还是实现缺陷。

### 业务规则要有可执行的例外，而不只是一句口号

**本例条件：**独立业务：退款通常不能超过已付款，但已退款金额也必须扣除。订单付款100、已退40，本次申请70。金额单位为教学点数。

业务不变量
:   所有允许操作都应满足的约束。

当前状态
:   规则在这一笔操作前的真实数据。

验收例
:   具体输入与预期结果。

业务规则要有可执行的例外，而不只是一句口号

| 规则层 | 计算或证据 | 结论 |
| --- | --- | --- |
| 模糊说明 | 退款不超过付款 | 70≤100，看似允许 |
| 完整约束 | 本次≤已付−已退 | 可退100−40=60 |
| 本次70 | 70>60 | 应拒绝或调整 |
| 并发条件 | 另一退款也可能改变已退 | 提交时需按当前状态原子校验 |

各行是独立对象或条件的对照，不暗示上一行的结果自动进入下一行。

#### 怎样把图中的变化读明白

懂业务不是把文档读得多，而是能把“约束、例外、状态、验证”连成明确判断。

业务知识应放在可维护规则与测试中；Agent检索到规则后仍要读取当前订单状态。

为了展示并发风险可以先用两次请求的时间线，不能把这条规则仅写成模型提示而没有执行端保护。

**不要混淆：**付款100不变不代表可退额不变；忽略已退和在途操作会把静态知识误当动态事实。

机制依据：[[HARNESS]](../sources.html#src-HARNESS) [[REVIEW]](../sources.html#src-REVIEW)。本例数字和宿主场景为明确给定的教学设定，不是商业模型输出或生产性能测量。

### 业务规则在测试里，为什么只读函数体不够

**输入与条件。**函数返回折扣，注释写“会员优惠”；测试明确：普通会员5%，高级会员10%，活动期间不可叠加。

| 步骤与对象 | 内部动作 | 中间结果 / 新状态 |
| --- | --- | --- |
| 1只读实现 | 发现两条折扣分支 | 还不知道不叠加是否重要约束。 |
| 2读测试 | 找到活动优惠与会员优惠冲突用例 | 得到优先级的可执行证据。 |
| 3读需求 | 核对测试是否仍对应当前业务 | 旧测试不是永远正确的权威。 |
| 4修改验证 | 新方案在活动+高级会员组合上运行 | 防止把两个单独正确分支相加成错误结果。 |
| 5报告 | 说明采用哪条规则、证据版本与验证结果 | 不是只说“代码更简洁”。 |

**把过程连起来。**实现、测试、需求与运行行为相互校验；只选其中一类容易错过业务约束。

**边界与反例。**折扣政策为虚构数据，不暗示任何真实企业规则。

### 追问：业务知识适合长期记忆还是仓库文档？

团队共享且应随版本变化的知识通常适合仓库或权威知识库；个人偏好和跨项目经验可放个人记忆；当前任务暂态放Checkpoint。相同事实重复存很多份会增加冲突，应保持权威来源并让记忆指向它。

### 追问：新人导读怎样兼顾易读与内部深度？

先给业务流程和核心对象，再链接具体模块、状态转移、数据结构和失败案例。不能只列目录，也不能开头就让读者读几千行源码。渐进式不是删掉细节，而是让细节有明确入口和前置知识。

### 追问：如何知道这些文档真的提高了Agent质量？

选真实业务任务，对比没有入口文档、完整大文档、按需结构化入口三组，测必要证据读取、错误业务假设、任务成功和成本。文档数量增长本身不是能力增长。
