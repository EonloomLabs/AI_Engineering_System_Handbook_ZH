## Q109｜Scaling Laws和Chinchilla究竟说明什么？为什么不能死记一个Token/参数比例？

这题先认识什么Scaling law是特定设置下的经验关系，不是无限外推定律；参数、数据、算力与质量一起决定效果。

[F16 · 一次训练从头到尾](../foundations/16.html)[F20 · 低秩、量化、专家](../foundations/20.html)[F21 · 算得快与装得下](../foundations/21.html)[F36 · 别被几个百分点骗了](../foundations/36.html)

### 核心回答

Scaling laws研究模型规模、数据与计算预算怎样影响损失；计算最优讨论在给定预算和假设下如何分配参数与训练[Token](../glossary.html#g027 "模型分词器使用的片段单位。 例：可能是词、词的一部分、标点或部分字节。")。它是经验拟合与优化问题，不是对所有架构、数据质量和部署目标恒定成立的比例定律。[[SCALING]](../sources.html#src-SCALING "来源说明")[[CHINCHILLA]](../sources.html#src-CHINCHILLA "来源说明")

### 用一个简化目标推导预算分配

假设损失可近似为`L=E+A/N^α+B/D^β`，其中N为参数量、D为训练Token数。再假设训练计算`C=kND`，则`D=C/(kN)`，代入得到：

```
L(N)=E + A·N^(−α) + B·(kN/C)^β
```

对N求导并令零，有：

```
αA·N^(−α) = βB·(k/C)^β·N^β
N* = [αA/(βB)]^(1/(α+β)) · (C/k)^(β/(α+β))
D* = C/(kN*)
```

这说明最优分配依赖拟合系数、指数与预算模型。若数据重复、质量变化、训练配方或架构改变，原拟合未必继续适用。若实际目标包含大量后续推理成本，较小模型训练更久也可能在总生命周期成本上更合适，而不只是最小化一次训练损失。

不要把预训练损失提升直接等同某个[Agent](../glossary.html#g136 "根据任务与观察调用模型和工具、持续推进的执行系统。 例：不只是一次写得很长的Prompt。")任务成功率提升。中间还经过后训练、工具适配、检索、执行和验证。一个更低困惑度模型可能仍不擅长特定协议或高风险操作。

先认识这里的对象与符号

[FLOPs与FLOP/s：数量与速率](../concepts.html#concept-flops)
:   FLOPs通常表示浮点运算数量；FLOP/s表示每秒的运算速率。论文或厂商对乘加计一次还是两次可能不同，需要固定口径。不能只用总运算量除理论峰值就承诺真实耗时：搬运、排队、通信和实际利用率也有成本。

### 规模规律是条件下的拟合，不是永远适用的配方

**本例条件：**独立预算图：可用计算预算固定，可在更大模型N和更多数据D之间分配。仅用C≈6ND这一常见简化训练估算讨论取舍，不给真实模型最佳比例。

N
:   参数数量。

D
:   训练Token量。

拟合条件
:   架构、数据质量、优化方式和预算范围。

规模规律是条件下的拟合，不是永远适用的配方

| 选择 | 固定C下的变化 | 仍需考虑 |
| --- | --- | --- |
| 把N翻倍 | 在简化式里D约减半 | 是否数据不足 |
| 把D翻倍 | N约减半 | 容量是否足够 |
| 延长训练小模型 | 推理可能更便宜 | 训练目标与部署目标不同 |
| 换数据质量或架构 | 原拟合可能不再适用 | 重新测量而非死记比例 |

各行是独立对象或条件的对照，不暗示上一行的结果自动进入下一行。

#### 怎样把图中的变化读明白

公式是成本近似，不是质量公式。相同6ND也可能因数据、优化和架构不同取得不同损失。

训练计算最优与部署总成本最优不是同一个目标：上线调用次数很大时，推理费用会影响模型大小选择。

阅读报告要先看研究范围与实测点，再看曲线外推，不能把一个时期的比例当通用常数。

**不要混淆：**把经验规律当精确物理定律，会在新架构、重复数据或不同训练长度下产生错误预算。

### 固定训练预算翻倍参数，为什么数据可能减半

**输入与条件。**用非常粗略的稠密模型训练近似C≈6ND。原N=10亿参数，D=200亿Token，则C≈1.2×10^20 FLOPs。

| 步骤与对象 | 内部动作 | 中间结果 / 新状态 |
| --- | --- | --- |
| 1预算固定 | C不变 | 允许的N×D乘积近似不变。 |
| 2参数翻倍 | N变20亿 | D必须降到100亿，才能维持该近似预算。 |
| 3能力取舍 | 更多参数但更少训练数据 | 不能只凭参数量断定更好。 |
| 4最优分配 | 依数据质量、模型形状、优化与目标衡量 | 经验缩放规律不是无条件物理定律。 |
| 5工程现实 | 推理频率很高时 | 训练最优和整个生命周期成本最优也可能不同。 |

**把过程连起来。**规模、数据与计算预算要联合讨论；“更大”本身不是完整训练方案。

**边界与反例。**C≈6ND是特定假设下的粗略估算，忽略部分注意力、嵌入等开销；不声称复现任何论文精确最优比例。

依据与适用范围：[[DERIVE]](../example-sources.html#ex-src-DERIVE)。示例输入和场景由本书明确设定。

### 追问：计算公式C≈6ND是否精确？

先认识这里的对象与符号

[MoE、专家与路由器](../concepts.html#concept-moe)
:   MoE是包含多套子网络的模型结构；路由器为当前Token表示选择或加权少数专家。专家通常是数值子网络，不是被赋予“数学老师”等提示词的聊天Agent。独立例：有4个专家，每Token选2个，表示某次只激活其中2条专家路径；仍需保存模型设计要求的参数与路由状态。

它是特定稠密Transformer训练条件下常用的近似量级估算，忽略或简化了部分注意力、嵌入、通信等成本。长上下文、[MoE](../glossary.html#g126 "根据输入选择部分专家子网络参与计算的架构。 例：总参数与本次激活参数分开统计。")和不同实现会改变实际成本。做容量规划要回到具体算子和硬件测量。

### 追问：同样Token数量的数据价值一样吗？

不一样。重复、噪声、领域覆盖、质量和混合比例都会影响有效学习。把劣质数据规模扩大，不保证等价于新增独立高质量信息。还要防止测试污染让能力看起来变强。

### 追问：公司只有很少私有数据，是不是应该训练基础模型？

通常先比较检索、提示、工具、技能或微调是否足够。基础预训练需要的数据、计算与验证投入远大于写一个领域Prompt。真正需求是最新知识还是行为适配，决定应该改哪层，而不是“私有”二字自动推出从零训练。

### 训练计算最优，为什么不一定是产品全生命周期最便宜？

预备知识：[F20](../foundations/20.html) · [F21](../foundations/21.html) · [F38](../foundations/38.html)。阅读顺序：先确认运行契约，再看反例与修复，最后检验边界。

#### 先说清楚“最优”固定了什么预算

Chinchilla研究比较给定训练计算下模型规模和数据量的分配。[[SCALE]](../engineering/sources.html#src-SCALE "Hoffmann et al. · Training Compute-Optimal Large Language Models") 它不是在替每个产品同时优化上线后亿次请求的延迟、显存和服务成本。把某个训练数据/参数比例背成永恒法则，会丢掉研究条件。

产品的总成本至少包括训练、数据、部署、推理、维护与失败返工。一个训练更贵但推理更便宜的模型，在请求量足够大时可能反而总成本更低；反过来，低流量实验不一定值得大额训练投入。

#### 一个明确的盈亏平衡算例

假设方案B比A多花1000单位训练成本，每次请求省0.01，其他条件暂相同。需要100000次请求才收回差额。请求少于这个数时更贵，多于它才可能更便宜。数字只是教学代数，不是当前API价格或论文结果；质量不相等时还需加入失败与人工成本。

#### 为什么参数更少也不保证推理更快

实际延迟受序列长度、batch、内存带宽、通信、内核支持与调度影响。vLLM调优文档中的KV抢占与prefill策略就是系统层影响的例子。[[SCHED]](../engineering/sources.html#src-SCHED "vLLM · Optimization and Tuning") 把模型参数量单独作为延迟预测，会错过服务瓶颈。

数据规模同样不是唯一变量：重复文本、多样性、质量和目标域匹配都会改变学习效果。“训练Token翻倍”不等于独立信息翻倍，不能不看数据构成就套经验曲线。

#### 追问：研究结论是否过时就不能用了？

历史研究仍可提供方法：控制变量、比较预算分配、拟合并验证。但是当架构、数据与硬件改变时，经验常数和最佳点要重新估计。使用时引用研究条件，不把当年设置写成产品默认配置。

#### 追问：如何做一个足够小的工程决策实验？

固定任务集和质量底线，比较少数候选在真实输入/输出长度分布下的成功成本、p95与资源；再用预计流量计算生命周期范围。先排除明显不满足质量或内存约束的方案，不必一开始搭建庞大模型路由平台。

## Q110｜MLA和GQA有什么本质区别？低秩KV为何可以减少缓存？

这题先认识什么MLA压缩可缓存的潜在表示，GQA共享KV头，区别在变换与缓存结构；不要只因显存变小就视为同法。

[F07 · 模型最常做的算术](../foundations/07.html)[F11 · Attention逐步计算](../foundations/11.html)[F19 · KV Cache从零解释](../foundations/19.html)[F20 · 低秩、量化、专家](../foundations/20.html)

### 核心回答

先认识这里的对象与符号

[Query、Key、Value：三种中间数值表示](../concepts.html#concept-qkv)
:   q是接收信息的一行查询表示；k是可读位置提供的一行匹配表示；v是该位置供混合的一行内容表示。大写Q/K/V把多行收集成表。它们由输入与参数计算得到，分别承担打分与提供内容的职责。某个q与两个k点积得到两个分数；softmax得到两个份额；这些份额分别乘两行v，再相加。这里不生成搜索词，也不直接选答案。

[MHA、MQA、GQA：头怎样共享](../concepts.html#concept-heads)
:   一个注意力头是一套匹配并聚合内容的路径。MHA常让每个Query头有自己的K/V头；MQA让多个Query头共用一组K/V；GQA在两者之间，分组共享。它们是结构选择，不是运行时随便改一个开关。独立形状例：8个Query头、2个K/V头，若均匀分组，每4个Query头共享1组K/V；缓存按K/V头数记账。

先认识这里的对象与符号

[MLA：学习得到的低维K/V表示](../concepts.html#concept-mla)
:   MLA指多头潜在注意力的一类架构。用较低维的潜在表示联合组织K/V相关内容，并按设计处理位置部分。它改变模型表示与参数结构，不只是把普通KV文件用ZIP压缩。读c=xW\_down时，c是这次计算的潜在向量，W\_down是学到的降维系数表；后续如何重构或吸收投影须按具体架构解释。

[GQA](../glossary.html#g127 "不同查询头与K/V头共享方式的注意力结构。 例：共享更多K/V可减少缓存，但不保证质量完全相同。")通过多个[Query](../glossary.html#g072 "当前位置用于与候选比较的一组数。 例：q=[1,0]不是用户原话，而是投影后的表示。")头共享较少的K/V头减少缓存；MLA通过学习的低维潜在表示联合表达K/V，并对位置部分作专门设计。MLA是模型架构与训练的一部分，不是把任意现有模型的KV事后压缩就保证等价。[[GQA]](../sources.html#src-GQA "来源说明")[[V3]](../sources.html#src-V3 "来源说明")

### 从矩阵乘法理解低秩表示

先认识这里的对象与符号

[SwiGLU、Wg/Wu/Wd：两路变换再合成](../concepts.html#concept-swiglu)
:   这是门控前馈结构。Wg生成要过SiLU的一路，Wu生成另一条内容路径，两路逐元素相乘，再用Wd映回原宽度。这些W是三组参数，不是三个Agent。读(SiLU(XWg)⊙XWu)Wd时，先算XWg和XWu，再SiLU，再⊙，最后乘Wd。每个位置独立用同一组参数。

采用列向量约定，设某位置隐藏向量为h，先计算`c=W_down h`，c的维度d\_c小于全部K/V头展开后的维度。内容[Key](../glossary.html#g073 "每个可读位置用于被查询比较的一组数。 例：与Q点积得到匹配分数。")和[Value](../glossary.html#g074 "每个可读位置将被加权汇集的内容表示。 例：这里V不是词表大小。")可表示为`k_i=W_upK,i c`、`v_i=W_upV,i c`。若只考虑内容分数：

```
q_iᵀ k_i = q_iᵀ W_upK,i c = (W_upK,iᵀ q_i)ᵀ c
```

因此可以把Query变换到潜在空间，再与缓存c计算分数，避免始终显式保存完整K。Value加权和也有：

[Σ：按下标逐项求和](../concepts.html#concept-sum)
:   Σ是加法的简写。下标指出哪项在变化；没有被求和的下标保持不变。它不是一个额外参数，也不表示把数组拼在一起。独立微例：Σᵢ xᵢyᵢ，x=[1,2]、y=[3,4]，就是1×3+2×4=11。

### 追问：为什么RoPE不能随便吸收到一个固定投影里？

[RoPE](../glossary.html#g082 "通过按位置旋转成对坐标来引入位置信息的方法。 例：二维90度旋转把[2,3]变为[-3,2]。")依赖位置。若把位置旋转与内容上投影混在一起，变换通常随位置变化，无法简单用一个固定矩阵在所有历史位置复用。解耦位置分支是为了保留位置建模同时维持低秩缓存的便利。

### 追问：MLA就是KV量化吗？

不是。量化减少每个数的表示位数；MLA改变需要缓存的表示维度与结构。两者理论上可以组合，但误差、算子支持和效果需要单独验证，不能把一种技术的收益直接乘上另一种技术的宣传倍率。

### 追问：MoE、MLA、FlashAttention各改哪一层？

先认识这里的对象与符号

[FlashAttention：改变中间数据存取方式](../concepts.html#concept-flash)
:   通过分块和在线归一化等方式，避免把完整注意力分数/权重矩阵长期写到较慢显存；目标仍是同一个注意力运算，浮点舍入可随运算次序变化。它不是把Token永久压缩，也不是跳过所有Key。区分“不把整张表落显存”与“没有进行这些数学计算”。

MoE改变前馈计算的稀疏选择；MLA改变注意力表示；[FlashAttention](../glossary.html#g131 "通过分块和更有效内存访问计算注意力的一类实现。 例：不是稀疏注意力，也不是把旧历史摘要掉。")优化注意力计算的IO与中间存储。它们解决不同瓶颈，可以出现在同一系统，也不互相等价。

## Q111｜In-Context Learning到底是不是“学习”？为什么换几个示例就会改变行为？

这题先认识什么上下文学习是在当前输入条件下表现出模式，不等于每次都更新参数；复杂能力来自训练与推理共同作用。

[F03 · 文字为什么要先变成Token编号](../foundations/03.html)[F10 · 神经网络最小模型](../foundations/10.html)[F16 · 一次训练从头到尾](../foundations/16.html)[F26 · 上下文组装](../foundations/26.html)

### 核心回答

通常的推理过程中模型参数不更新，但输入示例改变了隐藏状态和条件分布，因此表现出任务适应。这称为上下文学习；它不同于通过梯度更新参数的训练，也不同于把经验写入外部长期记忆。[[GPT3]](../sources.html#src-GPT3 "来源说明")[[TR]](../sources.html#src-TR "来源说明")

### 以标签映射为例追踪变化

假设输入给出“正面评论→标签A，负面评论→标签B”的示例。模型接收这些示例后，后续位置通过注意力利用示例中的对应关系；最终分类Token的[logits](../glossary.html#g091 "输出投影给各词表候选的未归一化分数。 例：可以是负数，还不是概率或Token编号。")由包含这些信息的隐藏状态产生。示例删除或会话重置后，这个局部映射可能不再被提供，因为权重并没有因该请求永久改变。

示例选择影响模型推断出的任务：标签是否平衡、格式是否一致、例子是否覆盖边界、顺序是否造成偏置。如果所有例子都使用同一标签，模型可能把输出格式学成固定答案。错误示例也可能污染当前行为。优秀Few-shot不是堆数量，而是提供任务规则、边界与输出契约的有效信息。

“模型记住我的项目”需要继续问：是当前上下文仍携带信息，客户端重新加载了文件，检索系统取回了记忆，还是模型真的经过微调？只有区分这些机制，才能正确设计恢复、删除和隐私控制。

### In-Context Learning改变本次条件，不等于改了权重文件

**本例条件：**独立分类提示：给两个例子“好→正向”“坏→负向”，然后问“优秀”。同一模型参数未更新，但输入里新增了任务规则。

上下文适应
:   根据当前示例推断任务模式。

参数学习
:   通过训练更新权重。

持久记忆
:   外部系统把信息再次提供给后续会话。

In-Context Learning改变本次条件，不等于改了权重文件

| 运行 | 参数是否改 | 本次输入 |
| --- | --- | --- |
| 未给例子 | 否 | 只有“优秀” |
| 加入两例 | 否 | 例子+问题，条件已变 |
| 新会话不带例子 | 否 | 先前条件可能不再可见 |
| 真正微调 | 是，按梯度更新 | 训练数据进入参数更新过程 |

各行是独立对象或条件的对照，不暗示上一行的结果自动进入下一行。

#### 怎样把图中的变化读明白

把同一个函数放在不同输入条件下，输出改变，并不要求函数本身变了。这样能解释“刚教它一个格式就会用”。

这不是否认模型在内部执行复杂适应，而是明确可观察机制：正常推理没有因此执行权重优化。

示例顺序、标签质量与任务分布可能影响结果；几个示例不能保证跨任务永久学会。

**不要混淆：**把聊天里的纠正称为永久训练，容易让用户误以为新会话自动保留所有规则。

机制依据：[[GPT3]](../sources.html#src-GPT3)。本例数字和宿主场景为明确给定的教学设定，不是商业模型输出或生产性能测量。

### 追问：每次对话都会更新厂商模型参数吗？

不能这样推断。单次推理、产品记忆和厂商离线训练是不同流程；数据使用政策取决于具体产品和配置，不能从模型“记得某句话”推断它已在线更新权重。本书不推测未公开的数据处理实现。

### 追问：上下文越长，Few-shot越多就越好吗？

更多例子可能帮助覆盖，也可能引入冗余、冲突和位置效应。需要在固定任务集上比较示例数量、选择策略和成本。若错误来自缺少代码事实，增加格式示例未必有用，应该补证据。

### 追问：Skill与Few-shot有什么关系？

[Skill](../glossary.html#g174 "供Agent按需使用的专业指导及关联资源。 例：不同于模型新增了一组权重。")可以包含说明、示例、资源和脚本；被加载后，这些内容成为上下文或工具支持的一部分。它不自动改变参数，也不保证模型严格执行。Skill价值要通过任务行为验证，而不是靠文件存在确认。

## Q112｜面对一个新框架、新论文或Agent失败，如何判断应该改哪一层？

这题先认识什么用输入、模型、工具、状态、证据和验证逐层诊断，选择最小有效修复；不要因为不确定就无界增加检索和Review。

[F24 · 状态、事件与检查点](../foundations/24.html)[F29 · 从搜索结果到可信答案](../foundations/29.html)[F33 · 重试、幂等和事务](../foundations/33.html)[F34 · 工程质量的基础](../foundations/34.html)[F35 · 评测指标的分母](../foundations/35.html)[F38 · 看懂生产运行](../foundations/38.html)[F40 · 从基础概念到系统分析](../foundations/40.html)

### 核心回答

先定位失败发生在信息、模型、协议、执行、状态还是验收，再选择最小能改变原因的措施。论文与框架提供候选机制，不替代因果诊断；工程改动要保留基线和反例，证明没有用复杂度掩盖问题。[[EVALS]](../sources.html#src-EVALS "来源说明")[[HARNESS]](../sources.html#src-HARNESS "来源说明")

### 从一个错误答案逆向回查

第一步确认任务定义：用户要求的到底是什么，成功如何判断？第二步看证据是否存在、是否有权限、版本是否正确。第三步看证据有没有被检索到并进入最终模型请求；“工具读过”不等于“当前模型仍看见”。第四步检查模型输出是否正确表达动作，协议和参数是否完整。

第五步核验外部执行与持久状态是否一致，尤其超时和中断。第六步检查验证是否针对最终版本、是否真正运行。只有这些条件基本正确仍稳定失败，才更有理由把瓶颈归因于模型能力，尝试更强模型、任务拆分或后训练。

阅读新论文时，把“作者解决的问题—关键假设—改动的对象—实验条件—局限”连起来。若研究针对静态文档问答，却被用来证明动态代码修改可靠，适用范围就跨得太远。若新框架只把已有机制包装成多层类，不产生任务质量或效率收益，未必值得迁移。

### 先找到最早错误边界，再决定换模型还是改系统

**本例条件：**独立Agent失败：最终回答“生产timeout=10”，真实规则为30。可能原因有检索漏条件、压缩丢“测试”、生成误用或工具状态过期。

最早错误边界
:   流水线中第一次从正确输入得到不适用内容的位置。

消融
:   只移除或更换一个机制，观察变化。

最小修复
:   针对已证实原因改动，避免无关复杂化。

先找到最早错误边界，再决定换模型还是改系统

| 核查点 | 查到什么 | 对应改动层 |
| --- | --- | --- |
| 原文与索引块 | 表头“仅测试”在切块时丢了 | 改解析/切块 |
| 召回结果 | 条件完整，压缩摘要丢了 | 改压缩保真 |
| 模型请求 | 生产30明确存在，输出仍10 | 改提示/模型并评测 |
| 执行日志 | 读的是旧版本配置 | 改时效与状态核验 |

#### 怎样把图中的变化读明白

不要先选喜欢的技术，再把所有问题解释成需要它。四种原因可能产生同一个错误答案，但修复位置不同。

每次固定输入、版本与验收，只改变一处，再看真实结果和回归。

“系统能力更强”应落到任务成功、代价和可恢复性，而不是流程变长、图变复杂。

**不要混淆：**新框架演示成功不证明能解决你的失败；先要求一个能区分新旧方案的具体反例。

### 追问：怎样避免把复杂任务过度简化？

检查跨模块不变量、未知副作用、权限边界和不可逆操作。若这些尚不明确，直接改一行可能只是把风险藏起来。简单不是少步骤，而是没有无效步骤；必要分析和验证应保留。

### 追问：怎样判断自己真正学会了？

给一个未见过的任务，能逐步说明对象、数据流、关键状态、失败窗口和验证方式，并能指出哪些结论尚无证据。能把运行过程讲清、把错误定位到层、把修复收益验证出来，比仅背出术语更接近实际能力。

工程深挖 · E56 · 接续Q112

### 深度排障的终点不是“换更强模型”，而是找出失效的不变量

预备知识：[F34](../foundations/34.html) · [F35](../foundations/35.html) · [F38](../foundations/38.html) · [F40](../foundations/40.html)。阅读顺序：先确认运行契约，再看反例与修复，最后检验边界。

#### 把系统拆成可干预的因果链

对于一次失败，先写明用户验收结果，再沿输入证据、检索、上下文组装、模型输出、工具执行、状态回写和验证链定位。每层都问：它应该保持什么不变量，实际哪里破坏？“模型不够聪明”太宽，无法指导最小修复。

可用受控oracle替换诊断：把真实正确证据直接提供给模型，测试检索是否是瓶颈；把已知正确工具参数直接交执行器，检查执行边界；把最终产物直接交验证器，检查评分器是否会误判。**这些替换用于定位，不可把oracle条件下的成功率当部署成绩。** Agent评测的真实outcome与基础设施控制原则支撑这种分层比较。[[EVAL]](../engineering/sources.html#src-EVAL "Anthropic · Demystifying evals for AI agents") [[NOISE]](../engineering/sources.html#src-NOISE "Anthropic · Quantifying infrastructure noise in agentic coding evals")

#### 单因素没收益，也可能存在交互

本书教学表：旧检索+旧Prompt成功率0.6，新检索+旧Prompt0.6，旧检索+新Prompt0.6，两者同时新才0.9。交互项`0.9−0.6−0.6+0.6=0.3`。这不是实测产品数据，而是说明：新证据只有被新组装逻辑正确利用时才有效；单看某个模块独立A/B可能错过组合依赖。

反过来，同时改五处后提高也无法知道哪一处有用。根据怀疑的依赖做有限组合实验，避免全排列无意义耗费。以真实失败样本和最小可证伪假设为起点。

#### 改动量与风险也属于结论

若一个掩码取反就能修复所有相关反例，不需要重写整套Agent；若底层权限模型错误，靠再加一句Prompt不够。判断修复层级要依证据，而不是偏好更复杂架构。验收包括目标修复、相邻回归、成本与新失败模式。

#### 追问：怎样把排障经验写进记忆而不过拟合？

记录触发条件、失效机制、原始证据、最小修复、有效版本、反例和失效条件。不要只写“以后遇到问题都增加上下文”之类宽泛命令。下一次环境不同先核对前提，不把一次成功升级成永恒规则。

#### 追问：一个“资深八股文答案”最少应包含什么？

先准确定义对象与边界；再走一遍关键状态或计算；给能区分正确与错误实现的反例；说明修复为什么有效、代价是什么、在哪些条件下失效；最后能指出依据与验证路径。只背术语、流程图或“最佳实践”清单都不足以回答连续追问。

#### 最终验收问题

给你一份失败trace，能否指出下一步最便宜、最有辨别力的检查？如果答案总是“重跑、换模型、加更多资料、再加一个审查Agent”，说明还没有把机制学习转成工程判断。

工程机制与失败边界

## 怎样把知识图谱变成工程判断，而不是概念大全？

### 图谱的最小可用单位是可检查的关系

“Agent—工具—记忆”三个词连在一起几乎没有信息。更有用的边是：`模型提议 --必须经校验--> 执行器`，`后置钩子 --不回滚--> 已完成副作用`，`压缩候选 --依赖版本--> 历史快照`。每条边注明来源、适用版本和反例。

### 把问题放回图中定位

Agent重复改同一文件，可能是结果没回填、任务状态没持久化、摘要把完成改成未完成、重试键不稳定或子任务重复派发。先从可见症状沿依赖边寻找断点。直接加一个“不要重复”的Prompt只能掩盖机制问题。

### 三种不同结论

事实：源码某函数在handler返回之后处理后置钩子。推论：后置拒绝不能阻止此前已发生的外部动作。建议：敏感操作应在执行前校验，并对结果未知提供核验或幂等路径。三者必须分开，不能把建议写成产品已经具备的保证。

### 变更时怎样使用图谱

修改工具Schema，要回归参数组装、钩子改写、授权绑定、执行和结果回填。修改压缩，要回归关键约束、历史版本、在途调用和恢复。修改记忆，要回归抽取、租约、产物核验、来源撤回和使用时失效。图谱帮助确定影响范围，不要求每个小修改重跑全系统所有测试。

### 不值得做的设计也要能删掉

一项机制没有对应失败模式，没有评测收益，却增加调用、状态和维护成本，就不应因为看起来完整而保留。高级工程判断是知道何时需要复杂机制，也知道何时简单直接执行更好。[[A01]](../engineering/agent-evidence.html#source-A01)[[A07]](../engineering/agent-evidence.html#source-A07)

### 知识图谱的每条边也有证据等级

“ToolRouter包含可见规格”是代码关系；“后置钩子不能回滚已有副作用”是执行顺序结论；“对高风险操作再增加核验”是工程建议。三种关系需要不同的验证方法，不能都画成相同的“官方要求”。

本轮图谱给边附上固定源码范围、官方文档章节或原创推导标签，并把未取得原文的旧记录留作历史而非继续引用。读图时先看边的谓词与条件，再看来源。测试通过只支持所运行的教学用例，不能替代源码阅读、Rust集成测试或商业服务核验。
