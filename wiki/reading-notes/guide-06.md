## 用Claude Code理解真实Agent产品

本篇对应How Claude Code Works。官方说明把获取上下文、行动与验证连接成循环，并提供项目指导、工具、上下文管理和子Agent等机制。具体支持与默认行为受版本和配置影响。[[S068]](sources.html#S068)[[S069]](sources.html#S069)

学习产品时不要只记命令，还要知道命令影响哪一层：当前对话、项目指导、工具授权、子Agent上下文还是外部环境。

工程机制与失败边界

## 产品行为与代码事实对照

对照同一任务的实际请求、工具日志和最终产物；开源可追函数，闭源只陈述公开文档及可观察事实。

**关键边界：**不要推测隐藏Prompt或把某个历史工程文章当成所有当前会话的固定算法。

**顺着源码或工程依据继续追：**把实现事实、经验报告、产品文档和教学设计分开。 不只检查顺利路径，也核对取消、版本变化与结果未知时的行为。

完整机制与连续例子见 [开源Codex与Claude工程文章怎样对照，才不制造冲突？](../chapters/12.html#agent-practice-products)；本节仍保留原有推导与实验，两处说明使用不同层次而不互相替代。

**证据与理解边界：**同名功能跨产品可能语义不同；固定提交、文档说明、历史文章和教学推导需分开。

## 指令、记忆与权限必须分开

项目指令提供指导，自动记忆保留可复用信息，权限配置限制执行。前两者是信息，后者应由产品和工具机制落实。模型“知道不能改”并不等于系统已经阻止写入。[[S070]](sources.html#S070)[[S074]](sources.html#S074)

对CLAUDE.md与AGENTS.md等文件，当前支持存在条件，不能使用跨版本绝对说法。正确检查包括文件位置、共存关系、实际加载以及是否遵循。

### 子Agent继承什么，要逐字段检查而不是说“全继承”

**本例条件：**独立主子Agent实验：主任务有规则R、证据E、工具集合T和凭据P。是否传给子任务由真实产品配置决定，下图是待核对的清单，不伪造默认行为。

继承
:   新上下文实际获得的内容与能力。

独立上下文
:   有自己消息历史，不等于没有任何配置。

授权
:   执行器给予的权限，不是任务文本。

子Agent继承什么，要逐字段检查而不是说“全继承”

| 字段 | 应查证的问题 | 证据位置 |
| --- | --- | --- |
| 规则R | 是否自动载入项目说明 | 子请求或可见配置 |
| 证据E | 主Agent读过的代码是否转交 | 子上下文材料清单 |
| 工具T | 允许哪些工具 | 子Agent工具配置 |
| 凭据P | 是否有下游访问身份 | 执行结果/鉴权日志 |
| 完成回传 | 返回结论还是工件与证据 | 交接内容 |

各行是独立对象或条件的对照，不暗示上一行的结果自动进入下一行。

#### 怎样把图中的变化读明白

主Agent说“去修同一个问题”只给了目标，可能没给根因证据；子Agent因此重新搜索，不一定是能力变差。

工具权限可以比父级更窄。不能靠在子任务文字里写“沿用全部权限”来扩大实际能力。

用可复查探针确认每一列，结论标明产品入口与版本；不要把一次行为推广到所有版本。

**不要混淆：**为了省Token只回传“已完成”，会丢掉文件版本、失败项和测试证据，主Agent无法验证成果。

机制依据：[[SUBAGENTS]](../sources.html#src-SUBAGENTS) [[CLAUDE]](../sources.html#src-CLAUDE)。本例数字和宿主场景为明确给定的教学设定，不是商业模型输出或生产性能测量。

## 子Agent的收益与损失

独立上下文可以隔离大量调查内容，但主Agent只收到结果时，可能失去关键条件。委派需要目标、范围、已知事实和返回证据，而不是一个标题。[[S071]](sources.html#S071)

原创委派示例：“只读调查Windows路径分隔符，不修改代码；返回实际调用位置、已运行测试、证据和未确认事项。”这比“你是Windows专家，全面分析”更容易验收。

## Skills与Hooks不是同一种执行方式

Skill组织专业方法和资源，是否被选中与正文是否有效需要分别评价。Hook在生命周期节点执行程序化逻辑，适合确定性检查，但也可能耗时或失败。[[S072]](sources.html#S072)[[S073]](sources.html#S073)

原创例子：路径规范排查放Skill，提交前运行已有静态检查可以交给Hook或CI。不要把所有语义判断硬写进Hook，也不要把必须禁止的操作仅写进Skill。

## 如何观察质量问题

当结果变差，分别检查模型配置、输入范围、历史清理、工具结果和验证。官方质量复盘说明Harness变化也可能影响产品体验，不能把所有回退归因于模型参数。[[S141]](sources.html#S141)

**练习：**对短新会话与长历史会话运行同一测试任务，保存已读证据、压缩事件和结果。若只有长会话退化，优先调查状态与上下文，而不是立即增加更多提示。

完成本篇后，应能使用产品功能做机制实验，同时明确哪些内部细节没有公开证据。

运行示例 · G06

### 子Agent只收到摘要，为什么它不知道主Agent的限制

**输入与条件。**主任务有约束“只读，不修改文件”。父Agent委派“调查配置问题”，子Agent拥有独立上下文。

| 步骤与对象 | 内部动作 | 中间结果 / 新状态 |
| --- | --- | --- |
| 1父上下文 | 用户原话明确禁止修改 | 限制在父会话可见。 |
| 2委派消息 | 只写“调查配置问题” | 不能假设子会话自动包含整段原历史。 |
| 3最小交接 | 追加只读范围、具体问题、仓库版本和证据路径 | 不必复制无关长对话。 |
| 4工具限制 | 宿主对子任务只提供只读能力 | 自然语言要求与工具权限共同约束。 |
| 5返回整合 | 子Agent提供发现、证据和未解决问题 | 父Agent仍负责用户整体目标。 |

**把过程连起来。**独立上下文节省父上下文成本，同时也需要有意识地传递必要约束。

**边界与反例。**这是独立子Agent模式的风险示例，不断言任何当前产品的默认继承字段；配置必须按公开文档与实际请求核查。
