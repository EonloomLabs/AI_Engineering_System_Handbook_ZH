## 把一次Codex任务展开为多轮输入

本篇对应Codex Agent Loop的公开机制。以下轨迹是原创教学示例，不是真实产品日志，也不声称展示隐藏Prompt。模型与工具交替工作，Harness维护调用和结果。[[S004]](sources.html#S004)

```
第1轮：目标 + 项目指导 + 工具定义
       → 模型请求搜索exclude
第2轮：加入搜索结果
       → 模型请求读取过滤器和测试
第3轮：加入源码与复现结果
       → 模型提出补丁
第4轮：加入补丁应用结果
       → 模型请求测试
第5轮：加入测试观察
       → 继续修复或给出有证据的交付
```

工程机制与失败边界

## 不可变请求与可变授权

把规则R3、工具T8和环境E2绑定到同一请求后，在模型返回前撤销写权限。解释哪些解释性信息仍来自快照，哪些授权必须按执行时状态重新检查。

**关键边界：**快照一致性与授权新鲜度是不同目标；不能以保持一致为理由继续执行已撤销操作。

**顺着源码或工程依据继续追：**消除规则、工具列表与实际执行环境错配。 不只检查顺利路径，也核对取消、版本变化与结果未知时的行为。

同一请求绑定解释对象，执行时仍检查授权对象请求S7真正执行时规则R3不能偷偷换成R4解释旧提议工具定义T8用对应分派语义证据file@r7检测是否已变r8授权允许测试环境若撤销则拒绝执行

| 对象 | 请求S7 | 真正执行时 |
| --- | --- | --- |
| 规则 | R3 | 不能偷偷换成R4解释旧提议 |
| 工具定义 | T8 | 用对应分派语义 |
| 证据 | file@r7 | 检测是否已变r8 |
| 授权 | 允许测试环境 | 若撤销则拒绝执行 |

同一请求绑定解释对象，执行时仍检查授权。数值与状态属于本节明确设定的教学例；不是生产性能或商业模型实测。

完整机制与连续例子见 [为什么每次模型调用都需要一致的上下文快照？](../chapters/09.html#agent-practice-snapshot)；本节仍保留原有推导与实验，两处说明使用不同层次而不互相替代。

**证据与理解边界：**请求会固定模型、工具及环境选择；实际访问仍须按当前授权核对，快照不是冻结一切权限。

## 输入组装决定模型“知道什么”

工作目录存在源码，不代表源码进入输入。工具定义告诉模型能做什么，不代表动作已发生。历史中一句“测试可能通过”也不能变成已通过状态。

因此调试Agent时，应分别检查可访问、已读取、已解释和已验证。缺证据先修检索与输入；有证据但误用，再考虑提示、模型或验证方式。[[S045]](sources.html#S045)[[S102]](sources.html#S102)

### 读源码时，把“注册、暴露、构造调用、分派”拆开

**本例条件：**本图是对本书已注明固定提交的Codex代码阅读方法，不宣称当前所有版本内部相同。用工具名read\_file作为教学占位，不把它声称为快照中的具体原生工具名。

registry
:   宿主持有的运行时实现集合。

model-visible specs
:   本轮给模型看的能力说明。

dispatch
:   把已构造的调用交到对应执行实现。

读源码时，把“注册、暴露、构造调用、分派”拆开

| 可观察阶段 | 应查看的对象 | 不能越级推出什么 |
| --- | --- | --- |
| 注册 | registry存在实现 | 不代表本轮可见 |
| 暴露 | 本轮specs包含名字或可延迟发现 | 不代表模型已调用 |
| 模型返回 | 工具名+call\_id+payload | 不代表已经授权成功 |
| 构造调用 | 内部ToolCall/Invocation | 不代表handler执行完成 |
| 分派与返回 | handler结果和状态 | 还需判断用户任务是否满足 |

各行是独立对象或条件的对照，不暗示上一行的结果自动进入下一行。

#### 怎样把图中的变化读明白

沿着一个调用ID或工具身份穿过各阶段，比只搜索一次“工具名存在”更能定位缺失环节。

阅读函数名应配合调用方、参数和测试；单个router片段不能证明所有沙箱和权限路径。

压缩替换历史是另一条链，需单独看快照、候选摘要、提交与并发新事件，不能因为有compact函数就推断无损。

**不要混淆：**厂商未公开的系统Prompt、内部推理或后台调度，不应从日志外观反推成事实。

## 工具输出如何被利用

返回应包含足够上下文与明确错误类型。文件不存在、权限不足和文件为空不能都表示成空字符串。模型看到不同观察，才可能选择合适后续动作。[[S058]](sources.html#S058)

原创例子：搜索结果只有“filter.py”，模型需再猜路径；返回“路径、匹配行、片段、是否截断”更容易定位。返回整个仓库则可能造成另一种噪声问题。

## 长任务为何需要压缩与外置

每轮结果累积，历史可能变长。压缩保留任务连续性，但不能保证完整恢复所有细节。重要原始日志与版本应外置并保留引用。[[S089]](sources.html#S089)[[S084]](sources.html#S084)

不要把压缩看成模型重新学习了任务，也不要把缓存命中看成永久记忆。它们分别改变内容表示与计算复用。

## 运行状态如何与界面分离

App Server等接口让不同客户端围绕会话与事件交互。界面进度、模型意图和实际环境结果不应混为一谈。[[S064]](sources.html#S064)

**练习：**在补丁应用后断开客户端，恢复时先查看文件版本和执行记录，再决定是否继续。重复显示一条消息无妨，重复执行有副作用的动作却可能产生问题。

完成本篇后，应能从一条最终回答追溯必要动作和证据，而不是只凭模型自述判断任务完成。

运行示例 · G05

### 一个修复任务，为什么产生三次模型调用

**输入与条件。**任务是把 `config.json` 的超时从3改成5，工具有read、write、test。下面是确定的教学轨迹，而非真实模型自主运行。

| 步骤与对象 | 内部动作 | 中间结果 / 新状态 |
| --- | --- | --- |
| 1调用1输入 | 用户任务＋可用工具说明 | 模型提出read，尚未承诺文件已修改。 |
| 2工具1结果 | 读取版本v7，timeout=3 | 结果连同调用ID进入历史。 |
| 3调用2输入 | 任务＋read调用＋结果 | 模型提出在v7基础上写timeout=5。 |
| 4工具2结果 | 写入成功，得到v8 | 宿主仍未证明功能测试通过。 |
| 5调用3输入 | 新版本和测试返回pass | 模型归纳变更与验证；如果模型还需自行提出test，则还要增加一轮。 |
| 6计数区别 | 用户看见一个任务 | 后端可能有多次模型请求和多次工具操作。 |

**把过程连起来。**一轮模型调用的输出不是任务的全部生命周期；哪些工具由模型决策、哪些由宿主自动触发必须说清。

**边界与反例。**本例test由宿主固定触发，因此三次调用成立；不要与“每一步工具都须另一次模型提议”的配置混计。
