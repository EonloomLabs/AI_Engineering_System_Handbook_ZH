## Skill存在，为什么仍可能完全没用？

从“安装了技能”到“写出了更好的代码”，中间经过什么？

技能像可按需展开的工作说明，不是新训练的一层神经网络。只有它被发现、匹配、读取，并真正影响行动，才可能改善结果。把“加载成功”当作能力已经应用，会把中间几道故障都遮住。

**路由**决定当前任务调用哪份能力或资源。

**渐进加载**先提供描述，相关时再读完整内容和资源。

**有效应用**能从行动或结果中观察到技能要求的落实。

**输入与适用条件：**通用Skill运行示意，不假定Codex、Claude Code和Copilot的实现细节完全相同。

### 为什么需要

在需要时提供专业步骤，避免所有规则常驻上下文。

### 怎样实现

按发现→匹配→加载→执行→验证逐段诊断。

### 可能的代价与误解

过度加载引入冲突和成本；漏加载导致关键专业要求缺失。

### 如何判断是否做对

用该加载与不该加载的真实任务双向测路由，再测最终工程质量。

## 五种扩展能力不要混成一个大Prompt

**Instruction**提供应长期遵守的约束；**Skill**组织某类任务的专业流程与资源；**Tool**提供真实可执行能力；**Hook**在宿主事件点运行确定性动作；**Agent**围绕模型、工具和状态执行一项任务。

五种扩展能力不要混成一个大Prompt：逐项辨别

|  |  |
| --- | --- |
| 对象一 | Prompt：本轮指令 |
| 对象二 | Skill：可复用做法 |
| 对象三 | MCP：连接外部工具 |

**关键区别：**这些都是扩展Agent的方式，但解决的信息类型和执行边界不同。

**容易误解：**把所有内容塞成一个永久Prompt会造成干扰。

例如“遵守项目风格”适合指引；“如何调查内存泄漏”可写成Skill；“运行测试”是Tool；“写入前检查目录边界”可由Hook或执行器实现。把硬权限规则只写在Skill里，不会自动变成确定性限制。

## 路由是在作选择

**路由routing**决定当前任务该选哪项技能、哪个模型或哪个执行者。Skill的description是让宿主或模型判断相关性的一个入口，不是只要文件存在就必定加载。

**关键区别：**技能路由是选择与加载问题，不能只检查Skill是否存在于磁盘。

**容易误解：**相关技能未进入本轮上下文时，模型不一定会遵循它。

常见链条是：文件存在→被扫描发现→元数据进入候选→被选择→正文被读取→相关资源可用→执行中实际应用。任何一步断开，都可能表现为“技能没生效”。

## 漏加载与过度加载为何都不好

该用路径处理技能时没用，可能漏掉平台边界；只改错别字却加载完整架构审查，会增加无关规则、耗时与冲突。

漏加载与过度加载为何都不好：逐项辨别

|  |  |
| --- | --- |
| 方案／对象 A | 漏加载：缺必要流程 |
| 方案／对象 B | 过度加载：增加无关文本 |
| 方案／对象 C | 目标是恰到好处 |

**关键区别：**技能召回率和误加载率都影响质量与效率，不能只追求“加载越多”。

**容易误解：**语义相似不代表必须加载。

**精确率precision**关注选出的项目中多少真正相关；**召回率recall**关注真正该选的项目找到了多少。正式计算在F35。路由追求任务合适，不是只最大化其中一个数。

理解衔接

## Skill与子Agent不是两种同义的外挂

Skill提供一套方法和资源；子Agent是另一条任务执行上下文。主Agent加载了Skill，不保证子Agent也读到了它；子Agent收到父任务摘要，不保证继承工具连接。交接时具体写目标、证据、允许动作、输出与验收。简单修改不必拆给多个Agent；先证明拆分减少了时间或错误，而不是只增加仪式。

把这一页的具体对象分清之后，再进入系统机制：[渐进加载的Skill怎样从“文件”变成实际能力？](../chapters/19.html#agent-practice-skills)。这里不要求先知道完整源码；先能按状态表复述每一步发生了什么。

**证据与理解边界：**技能正文保留、工具许可延续和子Agent预载各有条件；文件存在或之前调用成功都不足以证明本轮已应用。

## 子Agent不是主Agent的一份完全复制

主Agent可能把一个子目标、必要证据和工具权限交给子Agent。子Agent有自己的上下文与执行轨迹，再返回结果。它未必继承主Agent全部历史、未提交状态和MCP配置。

**关键区别：**子Agent的工具权限、上下文和记忆不应假设与主Agent完全相同。

**容易误解：**交接时若省掉关键证据，会导致子任务误判。



先认识这里的对象与符号

[Handoff与agent-as-tool](../concepts.html#concept-handoff)
:   Handoff是把控制权交给另一个Agent；agent-as-tool把子Agent当作可调用组件，结果返回当前控制者。Orchestrator是负责分配与整合的协调程序或Agent。委派时需要任务、边界、证据和完成条件；不要求把主会话所有历史照搬过去。

**交接handoff**要说清目标、证据范围、已确认事实、未确认假设、输出要求及何时算完成。只给“调查问题”四个字，可能让子Agent重复检索、走错范围或形成不兼容结论。

## 用一个DAG算并行是否值得

先认识这里的对象与符号

[DAG、依赖与关键路径](../concepts.html#concept-dag)
:   DAG是有方向且没有环的任务依赖图。箭头A→B表示B依赖A完成；关键路径是在给定任务时长与依赖下决定最早完成时间的最长依赖链。独立例：A需2秒，B/C依赖A分别需3/5秒且可并行，则A后两者完成至少7秒，不是把2+3+5=10当墙钟时间。

假设A准备输入需2单位时间，B与C是独立检查各需3和4，D整合需1。串行总计10；B/C并行的理想关键路径是2+max(3,4)+1=7。

**关键区别：**并行省的是墙钟时间，不必然减少总Token或总工作量。

**容易误解：**有依赖的任务强行并行会制造冲突。

但若分派和整合多耗4单位，总计11，反而更慢。**关键路径**是依赖图中决定最短完成时间的最长必经链，不是任务数越多越快。

若B和C都改同一个文件，独立性还可能不成立，需要隔离、合并和再验证。计算并行与写入并行是两种风险。

## 独立Reviewer为什么也可能错

两个Agent使用相同模型、相同错误上下文和相同测试，可能重复同一偏差。“不是同一个对话”不等于统计独立。

有效审查更应增加不同证据：检查遗漏边界、运行相反测试、核验需求与版本。小错误可以在审查中直接修复并重测，不必每次重新启动完整分析流程。

## 模型路由怎样不只按价格选

更便宜的模型若导致更多返工，总任务成本可能更高。应结合真实任务成功率、工具使用质量、延迟和失败代价。不要把Prompt短当作任务简单；一句“修复并发一致性”可能需要很深分析。

本书给出的流程是设计选择，不要求给所有任务再增加固定等级和复杂配置。先从单Agent加适度工具做起，证据表明需要时再分工。

### 修正错别字与修复并发Bug，为什么不该加载同一套技能

**输入与条件。**任务A是改README中的“超时时常”为“超时时长”；任务B是两个工作线程重复提交同一操作。

| 步骤与对象 | 内部动作 | 中间结果 / 新状态 |
| --- | --- | --- |
| 1理解A目标 | 只有文档文字修改 | 读取相应段落，修改并核对diff即可。 |
| 2理解B缺口 | 涉及并发副作用和重试 | 需查执行状态、幂等身份和重复提交路径。 |
| 3选择资源 | A无需并发设计Skill；B需要相关专业流程 | 不是看到“项目”两个字就把全部技能装入上下文。 |
| 4分配执行 | A可单Agent直接完成；B视独立证据范围决定是否委派 | 分工必须带任务目标和必要证据。 |
| 5检查结果 | A看文字diff；B用重复/超时反例测试 | 同一个“完成”按钮后面应有不同验证。 |

**把过程连起来。**路由的目的不是让流程看起来丰富，而是恰好提供本任务缺少的专业判断。

**边界与反例。**这是工程决策示例，不声称所有任务可以由固定关键词可靠分类。
