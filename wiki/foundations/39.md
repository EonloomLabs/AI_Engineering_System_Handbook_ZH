## 图像表示与界面行动，是两层不同问题

为什么看得懂截图，也可能点错按钮？

图像编码解决“把视觉信息变成可计算表示”；界面控制解决“在真实软件的当前状态做正确动作”。静态图里的坐标、页面当前布局、点击结果必须连接起来。模型对图片的描述再流畅，也不能替代操作后确认。

**Patch**图像被切分出的一小块。

**视觉编码器**把像素处理成模型可用表示的网络。

**Grounding**把指令对象定位到具体界面元素或坐标。

**输入与适用条件：**仅4×4灰度像素与构造界面流程；不代表所有多模态模型的预处理实现，也不冒充真实浏览器操控结果。

## 图片在计算机里也是有形状的数据

先认识这里的对象与符号

[Patch、图像通道与视觉投影](../concepts.html#concept-patch)
:   图像中的patch是切分的小块，RGB是红绿蓝3个通道；软件工程中的patch则是代码补丁，两者同名。图像块展开后可通过可学习变换成为向量，不是查文字词表。独立图像例：16×16×3的一块含768个数，投影后可以变成d个特征。d由模型设计决定。

一张彩色图片可以表示为高H、宽W、颜色通道C的数字数组。RGB有3个通道；某些库用`[H,W,3]`，另一些模型用`[B,3,H,W]`，次序不同但需一致理解。

图片在计算机里也是有形状的数据：逐项辨别

|  |  |
| --- | --- |
| 对象一 | 图像像素[H,W,C] |
| 对象二 | 图像Patch |
| 对象三 | 视觉Token向量 |

**关键区别：**图像经过切块、编码和投影，才变成模型可联合处理的向量。

**容易误解：**图片不是先“翻译成一句文字”才一定能进入模型。

一个像素不是一句话；模型要用视觉处理模块把像素转换成能与后续网络配合的表示。这里的Embedding不再是对文字Token编号直接查同一张词表。

## 图像Patch怎样变成一串向量

一种教学路径是把224×224图片切成16×16小块，称为**patch**。每边14块，共196块。每块若有3通道，原始数字数为16×16×3=768。

**关键区别：**从像素块到向量是数值映射，不是按文字词表给每个像素编号。

**容易误解：**不同视觉编码器的Patch策略并不统一。

逐格算清：一个图像Patch究竟是多少数字

视觉Patch映射16×163个颜色通道共768个像素数值展平+投影768维原始块 → d维视觉表示d由视觉模型设计决定

步骤 1一个Patch覆盖16×16个像素位置。

步骤 2每个像素有3个RGB通道，所以原始数值有16×16×3=768个。

步骤 3展平只是重新排列这768个数。

步骤 4视觉投影可以把它映射到d个特征，d由模型架构决定。

RGB三通道和文字Token编号完全不同；视觉投影是数值变换，不是每个像素去查中文词表。

数值除特别标注外来自本章已明确设定的教学条件；示意图表达算法结构，不代表商业模型参数或实时GPU执行速度。

可以把每块展开成长度768的一排数，再通过学到的变换变成d个数，得到196个位置的表示，并配合位置机制。实际模型可能用不同尺寸、动态分辨率、视觉编码器或压缩器，本例不代表所有商业模型。

## 视觉表示怎样交给语言模型

**视觉编码器**处理图像；**投影器或适配模块**把视觉表示转成语言模型可用形式；也可能通过交叉注意力让语言侧读取视觉信息。最后输出文字仍涉及语言模型的生成过程。

**关键区别：**视觉模型可能有单独的编码器和连接模块，具体集成取决于架构。

**容易误解：**不能假设图像与文字共用一个原始Tokenizer。



先认识这里的对象与符号

[CLIP与图文对比学习](../concepts.html#concept-clip)
:   对比学习通过目标函数让配对表示更易匹配、非配对表示相对区分。CLIP式训练学习图文关联，不自动提供完整聊天生成能力或可靠桌面操作。同一图像与正确描述可作为正对，其他描述作为对照；相关性训练不等于每次生成结论都事实正确。

**CLIP**式图文对比训练让匹配图文的表示接近，提供视觉语言关联，但这不等于自动具备完整对话生成或可靠GUI操作能力。

## GUI Agent为什么要反复观察

GUI是图形用户界面。截图中某按钮在(x,y)，实际窗口缩放或滚动后位置可能改变。Agent需要“观察当前界面→提出动作→执行→再次观察核验”，而不是把首次看到的坐标一直播放。

**关键区别：**GUI Agent必须闭环观察，因为界面状态可能在操作后改变。

**容易误解：**截图识别的按钮坐标不一定在下一时刻仍有效。

截图尺寸与桌面坐标可能存在缩放：若截图宽1000而实际目标画布宽2000，简单同尺度示例中横坐标可能乘2；实际还要考虑偏移、窗口边界和平台设置，不能只凭比例盲点。

有可靠结构化API时，往往更易验证和控制；必须操作界面时才承担视觉定位与状态变化的额外不确定性。

## 模型自信、概率与校准

模型说“确定”是一种语言输出；下一Token概率是局部生成分布；**校准calibration**考察预测可信度与实际正确率是否匹配。

模型自信、概率与校准：逐项辨别

|  |  |
| --- | --- |
| 对象一 | 模型概率 |
| 对象二 | 真实正确率 |
| 对象三 | 校准度 |

**关键区别：**模型给出高概率不代表答案的事实正确率经过验证，尤其是整段回答。

**容易误解：**Token概率不能直接读成“这篇报告有80%正确”。

例如某组100项预测都被标为80%可信，若实际约80项正确，这一组在该统计意义上较校准。它不证明每项答案具体正确，也不保证换分布后仍校准。

**选择性回答**允许证据不足时继续检索、明确不确定或拒绝下结论。正确弃答与无意义回避也要由任务目标区分。

## 可解释性研究到底解释哪一层

先认识这里的对象与符号

[SAE、激活与可解释特征](../concepts.html#concept-sae)
:   SAE是稀疏自编码器，用较少活跃特征的组合重构模型激活。激活是本次计算的中间数值，不是完整自然语言推理记录。重构成功不自动证明某特征具有唯一因果含义。观察某特征与输出一起变化是线索；要判断因果，还需控制其他条件、干预与对照。

查看注意力权重、某些中间激活或稀疏特征，可以提供机制线索。**稀疏自编码器SAE**尝试用相对稀疏的特征组合重构激活；稀疏表示只让部分特征活跃，不等于每个特征天然对应唯一人类概念。

重构得好不自动证明因果解释正确；一个特征与某输出相关，也不证明它独自导致该输出。需要干预、对照和适用范围。

模型生成的文字解释也可能只是合理叙述，不能据此获得完整内部运算或隐含推理的真实记录。对实际工程，优先用可见输入、工具、版本和验证结果诊断，再谨慎使用内部解释研究。

先认识这里的对象与符号

[DPR、DPI与坐标单位](../concepts.html#concept-pixels)
:   DPR常表示设备像素与CSS像素的比例；DPI表示每英寸的点数。截图像素、界面逻辑坐标和屏幕坐标不一定同单位，还可能有缩放、裁剪与偏移。在明确DPR=2且其他映射一致的独立例中，CSS横坐标100对应200个设备像素；不能把这条条件化关系直接套到所有截图。

**输入与条件。**桌面原图1920×1080，为模型展示成960×540。按钮在展示图中的中心为(400,200)。先假设只有等比例缩放，没有裁剪、DPI或滚动偏移。

| 步骤与对象 | 内部动作 | 中间结果 / 新状态 |
| --- | --- | --- |
| 1记录变换 | 宽高都缩到1/2 | 坐标映射比例2。 |
| 2还原点击点 | 展示坐标乘2 | 原图对应(800,400)。 |
| 3执行前检查 | 确认截图仍是当前页面 | 页面已滚动时旧坐标失效。 |
| 4执行一次动作 | 点击后重新观察 | 检查按钮状态或结果页面，不凭点击回执判成功。 |

**边界与反例。**图像patch和坐标是概念示例，不代表所有视觉模型采用同样分块或所有操作工具接受原图像素坐标。

## 图片和界面也是会过期的证据

模型看到截图r7后，弹窗使界面变成r8。旧坐标已经不可靠。操作前确认当前界面，操作后再看真实结果。按钮被点击与保存成功不是同一件事。注意力热图、Token概率和模型自信也不是完整事实正确率；仍需要外部证据与明确不确定性。
