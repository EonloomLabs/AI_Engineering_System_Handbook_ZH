## 字符完整、事件完整、工具参数完整是三道关

为什么看到半段JSON时绝对不能执行？

网络像分批送到的纸条，分割点不遵守汉字或JSON边界。接收端先重组字节和字符，再按流协议重组事件，最后解析结构并确认该输出是否表示完整行动。花括号配平不够，因为字符串内部也可能有花括号。

**UTF-8**把字符表示成字节序列的编码。

**SSE**以事件形式持续传送文本数据的一种协议。

**Schema**描述字段和类型约束的结构规范，不保证字段事实正确。

## API只是程序间约定，不是智能本身

**API（应用程序接口）**规定一个程序怎样请求另一个程序提供能力。请求给出操作与参数，响应给出结果或错误。调用语言模型的API和调用数据库API都属于这种交互，区别在能力和返回内容。

API只是程序间约定，不是智能本身：逐项辨别

|  |  |
| --- | --- |
| 对象一 | UTF-8字节边界 |
| 对象二 | SSE事件边界 |
| 对象三 | 工具参数JSON完整性 |

**关键区别：**三种边界可能落在不同位置；收到网络分片不表示收到了完整事件。

**容易误解：**不能对半截JSON立刻执行工具。

先认识这里的对象与符号

[JSON：结构化文本，不是执行动作](../concepts.html#concept-json)
:   JSON是一种用对象、数组、字符串、数字等表达数据的文本格式。花括号对象把字段名映射到值，方括号数组保留项目顺序。解析JSON只得到数据，不会自动执行其中的工具名称。独立例：{"path":"a.py","limit":3}有两个字段；"3"是字符串而3是数值，Schema可以要求其中一种。

**JSON**是一种表示结构化数据的文本格式。花括号表示对象，键后面冒号给值；方括号表示列表；引号里的内容是字符串。例如：

先认识这里的对象与符号

[call\_id、item\_id、request\_id](../concepts.html#concept-identifiers)
:   这些是不同层对象的标识：工具调用、输出项、请求或响应。用来把增量和结果配回正确对象，不是模型输入的Token ID，也不天然是业务幂等键。两次read\_file可分别有c1与c2；结果返回顺序颠倒时仍按调用标识配对，而不是按工具名称猜。

```
{"name":"read_file","arguments":{"path":"demo.py"},"call_id":"c1"}
```

这里只是一段数据。**反序列化**是把这段文本解析成程序对象；**序列化**是把对象变成可以存储或传输的表示。解析成功不等于动作安全。

## Schema在检查什么

先认识这里的对象与符号

[Schema与Structured Outputs](../concepts.html#concept-schema)
:   Schema是一份字段和类型等结构规则；结构化输出机制让模型更容易返回符合规则的数据。字段合法仍不等于目标文件存在、已授权或业务正确。独立例：要求path为字符串；{"path":3}类型不合规则，{"path":"missing.py"}虽结构合规则仍可能找不到文件。

**Schema（结构约束）**可以要求path是字符串且必须提供，禁止某些额外字段。它能发现“path给成数组”之类形状错误，却不证明`demo.py`存在、当前用户有权读取、或者这真是需要调查的文件。

Schema在检查什么：逐项辨别

|  |  |
| --- | --- |
| 对象一 | API：接口契约 |
| 对象二 | Schema：结构要求 |
| 对象三 | Authorization：权限判断 |

**关键区别：**字段合法只能说明结构符合约定，不证明动作获得授权或业务正确。

**容易误解：**JSON解析通过不代表磁盘文件存在。

因此要区分语法合法、结构合法、业务适用、权限允许和执行成功。Structured Outputs主要提高结构符合约定的能力，不是事实保证或权限系统。

## 为什么网络一次读到的不是一个完整回答

发送方可能分多次发送，网络和客户端也可能以不同片段接收。**chunk（传输片段）**是这次拿到的一部分字节，不保证对应一个Token、一句中文或一条完整JSON。

**关键区别：**网络read可以在任意字节处切断，必须缓冲直到事件边界满足协议。

**容易误解：**不能把每次read返回的块当成一个完整消息。

逐格算清：流式响应：网络块不等于完整事件

流式协议缓冲同一个SSE事件可能被网络拆成任意边界的片段read①data: {"callread②\_id":"a"}\nread③\n（空行）直到协议事件帧完整后才交给解析器，不在read①执行半截JSON。

步骤 1网络第一次只收到data字段的前半段，此时不能解析成完整JSON。

步骤 2第二次收到剩余内容，可能仍没到SSE事件终止边界。

步骤 3接收到用于结束事件的空行后，事件帧才完整。

步骤 4事件完整后再解析结构化参数；字节边界、事件边界和JSON边界分开判断。

正确的层次是：先把字节流解码与缓冲，再识别完整协议事件，再解析其中的结构化参数。

数值除特别标注外来自本章已明确设定的教学条件；示意图表达算法结构，不代表商业模型参数或实时GPU执行速度。

例如JSON里有“学习”两个字，UTF-8字节可能恰好在一个汉字中间分开。单独把每个片段直接解成完整字符串可能报错或出现替换字符。需要能够保存未完成字符状态的增量解码。

## SSE的事件边界

先认识这里的对象与符号

[SSE、chunk、delta：不同的分片层](../concepts.html#concept-sse)
:   SSE是服务端发送事件的文本协议；网络chunk是这次收到的一段字节；delta是某个输出项的增量内容。三者边界不保证重合。一个完整事件也未必意味着完整工具参数。参数可能先收到{"path":"a，后收到.py"}；必须组装并等协议规定的完成条件，不能见到片段就执行。

**SSE（Server-Sent Events）**是一种服务器向客户端连续发送事件的文本协议。概念上，`data:`行提供数据，空行结束一条事件。实际标准还有多行字段、换行差异和其他规则。

**关键区别：**SSE按事件帧组织数据；多个网络包可能组成一个事件，一个包也可包含多个事件。

**容易误解：**流式输出并不保证一个Token对应一个网络事件。

正确处理通常至少有这些层：网络字节→增量文本→事件边界→事件数据解析→模型输出项重建。**这几层边界不能互相替代。**

模型的工具参数还可能分成多个delta，即增量片段。收到`{"path":"de`时显然不能执行；即使暂时拼成合法JSON，也仍需等待对应调用完成信号和宿主校验，而非提前猜最后参数。

## 沿同一个调用编号走过四层边界

把字节想成信件被拆开的碎片，但不要把“有一片纸”当成“信件完整”。程序先恢复字符，再按事件边界组合，随后按call\_id组装参数。两个调用交错时必须分别放进两个容器。完整JSON只让程序知道参数是什么；还要核对工具、权限与完成事件。网络断开后，已经执行的动作不会因为没收到最后几个字节就自动消失。

## call\_id为什么比工具名称重要

一次模型输出可能发起两个read\_file，分别读取a.py与b.py。结果返回顺序可能相反。用工具名称无法配对，必须使用**调用标识call\_id**或协议规定的输出项身份。

**关键区别：**同一个工具可以被多次调用，必须用调用ID识别哪份结果属于哪个请求。

**容易误解：**只按工具名匹配会混淆并发调用的响应。

响应完成、单个工具参数完成、某项工具执行完成，又是不同事件。取消请求也未必能撤回已经发生的外部副作用。

## 一个失败应归到哪层

连接失败是传输问题；JSON破损是解析问题；缺字段是结构问题；路径越界是授权问题；文件不存在是环境或业务问题；文件存在却被模型误解是后续推理问题。

将所有错误变成“工具失败，再试一次”会丢掉重要判断。可修正参数的错误适合反馈模型；权限禁止不应通过偷偷换更强工具绕开；写操作超时需要核验是否已经发生。

## 接口无状态不等于系统无记忆

无状态模型调用可以由应用显式重传历史；有状态接口可以使用会话或前次响应标识让服务组织状态。两者只是状态放在哪里和如何引用的差别，不自动保证全部历史一直在上下文里。

先认识这里的对象与符号

[LF、CRLF与EventSource](../concepts.html#concept-linebreak)
:   LF是换行字符，CRLF是回车再换行的组合。SSE规定事件行与空行的解释；EventSource是浏览器接收SSE的接口。只解析一种分隔符的教学代码不等于完整协议实现。实际网络片段可能恰好把CR和LF分开送达，解析器应按已实现的协议规则组装，不能直接把每个网络片段当一条事件。

### 把“学习.py”拆在一个汉字中间，为什么不能马上解析

**输入与条件。**一个事件内容是 `data: {"path":"学习.py"}`，后接两个换行。网络可能在“学”的UTF-8字节中间切开。

| 步骤与对象 | 内部动作 | 中间结果 / 新状态 |
| --- | --- | --- |
| 1先收一段字节 | 可能只收到某个汉字的前1或2个字节 | 增量UTF-8解码器保留残余，不制造替代字符。 |
| 2收齐字符 | 后续字节完成“学” | 解码得到部分文本，但JSON和事件可能仍未结束。 |
| 3识别事件边界 | 只有遇到空行才完成此SSE事件 | 不拿一次网络read当一次事件。 |
| 4解析数据 | 从data字段拼出完整JSON | 得到path字符串“学习.py”。 |
| 5等待调用完成 | 即使参数JSON完整，也要核对输出项完成语义 | 执行器仍需检查允许路径，不能只凭文本看起来合法就执行。 |

**把过程连起来。**字节边界、字符边界、JSON边界、事件边界和工具调用完成边界是不同层次。

**边界与反例。**配套程序测试LF分隔的教学SSE子集和所有二分字节切点；不是完整浏览器EventSource实现。
