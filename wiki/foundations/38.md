## Trace要告诉你因果，不只是时间戳

为何优化一个最显眼的步骤，整体却没变快？

执行轨迹像工程里的时间账，但更重要的是依赖关系。串行阶段会相加，并行阶段往往取关键路径；只有知道下一步在等谁，才能知道哪里值得优化。还要把排队、推理、工具、验证和重试分开，不能全算成模型慢。

**Trace**一条任务中各步骤及关联关系的记录。

**墙钟时间**从任务开始到结束真正经过多久。

**关键路径**决定完成时间的依赖链。

**吞吐**单位时间完成多少任务。

**输入与适用条件：**固定教学秒数，无真实产品耗时数据。第4帧只改变工具A时长，其他条件保持不变。

## 一次任务到底慢在哪里

总时间可能包括排队、上下文检索、模型输入处理、生成、工具等待、重试和验证。只记录“总计60秒”不能说明该换模型、改检索还是减少工具轮次。

一次任务到底慢在哪里：逐项辨别

|  |  |
| --- | --- |
| 对象一 | Trace：请求链路 |
| 对象二 | Log：具体事件 |
| 对象三 | Metrics：整体量化 |

**关键区别：**三类观测互相补充，Trace帮助定位一项任务在哪个步骤耗时或出错。

**容易误解：**只有一串时间戳但缺调用ID，很难还原因果顺序。

**Trace（调用轨迹）**把同一任务的相关步骤关联；**Span**记录一个具体操作的开始、结束与属性；**Log日志**记录事件细节；**Metric指标**汇总大量运行的统计值。三种观察互补。

## 用一条教学轨迹分账

```
排队2秒
检索1秒
模型调用5秒
工具测试8秒
模型总结2秒
总计18秒（这个例子假定顺序执行）
```

先认识这里的对象与符号

[DAG、依赖与关键路径](../concepts.html#concept-dag)
:   DAG是有方向且没有环的任务依赖图。箭头A→B表示B依赖A完成；关键路径是在给定任务时长与依赖下决定最早完成时间的最长依赖链。独立例：A需2秒，B/C依赖A分别需3/5秒且可并行，则A后两者完成至少7秒，不是把2+3+5=10当墙钟时间。

若工具测试是最大项，仅压缩最后总结的Token不会把总时长降低一半。若步骤并行，总时间要看关键路径，不能把每个span耗时盲目相加。

**关键区别：**总耗时可能被工具等待、网络和排队主导，不一定是模型生成慢。

**容易误解：**并行跨度不能把各操作耗时直接相加当墙钟时间。

逐格算清：18秒任务：先按时间分账，再决定优化哪段

任务时间分账本例假设所有阶段严格串行，因而总耗时可相加排队2s检索1s模型5s测试8s总结2s工具测试8秒是最大项；仅缩短最后总结通常无法让总时长减半。

步骤 1排队2秒，检索1秒，模型5秒。

步骤 2工具测试8秒，模型总结2秒。

步骤 3本例明确假设全部串行，总时间2+1+5+8+2=18秒。

步骤 4测试阶段最长；只压缩最后总结不可能直接让总时长减半。

这只是串行教学轨迹。真实Agent可能并行、排队和重试；比较时必须先弄清依赖关系再谈关键路径。

数值除特别标注外来自本章已明确设定的教学条件；示意图表达算法结构，不代表商业模型参数或实时GPU执行速度。

## TTFT、TPOT与端到端延迟

先认识这里的对象与符号

[TTFT、TPOT、p95与吞吐](../concepts.html#concept-latency)
:   TTFT是请求到首个输出Token的延迟；TPOT描述后续每Token时间的统计；p95是某窗口里约95%观测不超过的分位数；吞吐是单位时间完成量。要说明计时起止。首字快不代表任务快：工具执行可能还要很久。理论峰值吞吐也不等于某个用户的延迟。

**TTFT**是从请求开始到第一个输出Token到达的时间；**TPOT**描述后续每Token生成时间的某种统计；**端到端延迟**是用户任务整体完成时间。

**关键区别：**优化前必须测量，不应仅凭Token数量判断慢在哪里。

**容易误解：**微优化非关键路径步骤不一定降低最终完成时间。

首字出来很快，后续工具执行很慢，用户仍会觉得任务慢。输出很多无用文字可以让界面显得活跃，却不改善完成时间。

## 吞吐与延迟不是一对同义词

**吞吐量throughput**是一段时间完成多少工作；**延迟latency**是一项工作等待多久。批量处理可能提高吞吐，却增加部分请求排队时间。

吞吐与延迟不是一对同义词：逐项辨别

|  |  |
| --- | --- |
| 对象一 | TTFT：首Token延迟 |
| 对象二 | TPOT：每输出Token耗时 |
| 对象三 | E2E：任务总延迟 |

**关键区别：**三个指标观察不同层面，TTFT和TPOT好也不保证多工具任务快。

**容易误解：**不能把端到端任务耗时归因成单次Decode速度。

当请求到达速度逼近系统可处理速度，排队可能迅速变长。平均值还会掩盖尾部慢请求；**p95**表示某统计窗口中约95%的观测不超过该值，不是最大值。

先认识这里的对象与符号

[Little定律：L=λW的局部记号](../concepts.html#concept-little)
:   队列记账中，L表示平均在系统中的任务数，λ是平均到达率，W是平均停留时间；在稳定等适用条件下L=λW。这里W不是投影矩阵，L不是模型层数。独立例：每秒平均到达2项、平均停留3秒，则平均在系统约6项；不能拿瞬时尖峰直接替代长期平均。

在稳定系统和相应条件下，Little定律常写`L=λW`：平均在系统中的任务数=平均到达率×平均停留时间。它帮助核对队列与延迟，但不是无条件适用于任何瞬时波动的精确预测。

## 成本应算整个任务

模型输入、输出、缓存命中、工具、失败重试和人工介入都可能有成本。不要只比较“每百万Token价格”，忽略便宜模型导致的多轮返工。

成本应算整个任务：逐项辨别

|  |  |
| --- | --- |
| 方案／对象 A | 吞吐：单位时间总产出 |
| 方案／对象 B | 延迟：单请求等多久 |
| 方案／对象 C | 并发提高时两者可能背离 |

**关键区别：**更大batch通常提高吞吐，但排队和长短请求竞争可能拖慢个别请求。

**容易误解：**只看tokens/s会忽略用户体验。

也不要为了降低Token把关键证据删掉。更好的目标是在满足质量与风险要求下，减少无效读取、重复分析、无进展调用和不必要审查。

## SLI、SLO是什么

先认识这里的对象与符号

[SLI、SLO与错误预算](../concepts.html#concept-slo)
:   SLI是实际测量的服务水平指标；SLO是该指标的目标；错误预算是相应目标允许的失败空间。它们是服务运行管理对象，不是模型参数。“API返回200”可能不是用户成功；有些业务应以限定时间内正确完成任务的比例定义指标。

**SLI**是服务水平指标，例如规定时间内正确完成的请求比例；**SLO**是该指标目标，例如某业务对可靠性和时间的要求。目标应连接用户结果，而不是只保证API返回200。

**错误预算**描述在可靠性目标允许范围内可承受的失败量，用于平衡变更速度和稳定性。这是管理思路，不要求个人实验也建立复杂运营平台。

## 灰度、回滚和版本组合

**灰度发布canary**先让小范围流量使用新版本，观察后再扩大；**回滚**退回已知较稳定的配置。Agent系统版本可能包含模型、Prompt、工具、Skill、索引、权限与记忆规则，不能只记模型名。

若新版本已写入错误记忆或修改外部系统，仅换回旧模型未必消除影响。需要核验派生数据和副作用，必要时单独修复。

追踪也要保护隐私：默认不要保存全部敏感Prompt和凭据。记录足够定位问题的身份、版本和脱敏证据，比无条件日志越多越好更合理。

### 两条工具并行时，为什么总耗时不能直接相加

**输入与条件。**读取配置需要3秒，读取测试需要5秒，两者可以同时开始；之后模型整合2秒。时间是构造的。

| 步骤与对象 | 内部动作 | 中间结果 / 新状态 |
| --- | --- | --- |
| 1t=0 | 两个只读工具同时启动 | 两个分支都从0计时。 |
| 2t=3 | 配置先完成 | 测试仍在运行。 |
| 3t=5 | 测试完成 | 汇合点现在才具备两份证据。 |
| 4t=5到7 | 模型整合 | 墙钟总耗时7秒。 |
| 5比较两本账 | 工具耗时和=3+5=8秒；模型再2秒 | 工作量和10秒，但关键路径是max(3,5)+2=7秒。 |

**把过程连起来。**Trace要保留父子关系与时间区间，才能区分“做了多少工作”和“用户等了多久”。

**边界与反例。**真实并发会受资源争用、限流和通信影响，不能拿本例推导固定加速比。

## 先画出等待时间，再谈加速

模型2秒，A工具5秒和B工具3秒并行，最后汇总1秒，用户大约等8秒。把B加速到1秒，A仍需5秒，总等待可能不变；A才在关键路径。成本应把失败、重试和废弃摘要都算上。Trace记录因果关系和版本，但不应该无条件保存密钥与全部私人输入。

优化关键路径才改变墙钟环节时长（教学秒）串并行关系模型2串行工具A5与B并行工具B3与A并行汇总1等待A/B墙钟82+max(5,3)+1

| 环节 | 时长（教学秒） | 串并行关系 |
| --- | --- | --- |
| 模型 | 2 | 串行 |
| 工具A | 5 | 与B并行 |
| 工具B | 3 | 与A并行 |
| 汇总 | 1 | 等待A/B |
| 墙钟 | 8 | 2+max(5,3)+1 |
