## 读指标，先问它的分母是谁

为什么精确率高不等于证据找全了？

分子看起来都是“找对了多少”，分母却在回答不同问题。精确率从已拿回的内容看浪费；召回率从真正需要的内容看遗漏。Agent任务成功率又是另一层结果，不能把检索指标直接当作整个任务成功率。

**TP**该选且确实选中的项。

**FP**不该选却选中的项。

**FN**应该选却漏掉的项。

**评测单位**一次任务、一次运行、一个文档或一个位置，必须先定清。

### 为什么需要

用准确的指标发现遗漏或浪费，而不被单个漂亮百分比误导。

### 怎样实现

明确任务集与单位，再计算分子分母，同时看下游任务表现。

### 可能的代价与误解

一题跑十次不是十道独立题；重试成功率与单次成功率也不同。

### 如何判断是否做对

从原始记录重算指标，逐项检查是否重复计数或遗漏失败。

## 先给评测单位起清楚名字

**Task**是一项有明确目标和判据的任务；**Trial**是对它的一次尝试；**Trace**是尝试过程中模型、工具和状态的轨迹；**Outcome**是最后结果；**Grader**是评分规则或执行评分的程序/模型。

先给评测单位起清楚名字：逐项辨别

|  |  |
| --- | --- |
| 对象一 | 样本单位：一次任务 |
| 对象二 | 成功次数：分子 |
| 对象三 | 总任务数：分母 |

**关键区别：**指标解释前要说清分母，否则百分比几乎没有比较价值。

**容易误解：**不能把工具调用成功率冒充端到端任务成功率。

同一Task可以跑多次Trial。把一个Task重试十次后成功，不能简单当成“一次运行成功”，否则分母被改变了。

## 成功率先用真实次数算

20个任务各跑一次，18个满足判据，经验成功率是18/20=90%。这个数依赖任务选择、环境、超时和允许重试次数。若只挑容易任务，90%不能代表所有业务。

**关键区别：**成功率的基本单位是任务还是运行，应在统计前固定。

**容易误解：**某一次任务重复跑很多次会改变样本权重。

统计一个长任务要不要部分得分，也应事先定义。临时为了让新系统分数更高而改判据，就难以公平比较。

## 精确率和召回率用集合手算

假设真正相关的文档有5篇，系统返回4篇，其中3篇相关。

精确率和召回率用集合手算：逐项辨别

|  |  |
| --- | --- |
| 方案／对象 A | Precision：预测为真中多少真 |
| 方案／对象 B | Recall：真实应找到中找回多少 |
| 方案／对象 C | 两个分母不同 |

**关键区别：**精确率在乎误报，召回率在乎漏报；检索和路由经常需要二者平衡。

**容易误解：**两个指标不是简单互补到100%。

逐格算清：精确率和召回率为什么分母不同

精确率与召回率的两个分母实际相关共5篇，系统返回4篇，其中3篇相关、1篇不相关。返回集合（4篇）相关1相关2相关3不相关Precision = 3 / 4 = 75%Recall = 3 / 5 = 60%

步骤 1真正相关的文档有5篇。

步骤 2系统返回4篇，其中3篇确实相关、1篇不相关。

步骤 3精确率=3÷4=75%，分母是返回数量。

步骤 4召回率=3÷5=60%，分母是真正相关数量。

两者的分子都是找到的3篇相关文档，但分母分别是返回4篇和实际相关5篇。

数值除特别标注外来自本章已明确设定的教学条件；示意图表达算法结构，不代表商业模型参数或实时GPU执行速度。

```
精确率precision = 找到的相关数 / 返回总数 = 3/4 = 75%
召回率recall    = 找到的相关数 / 应找相关总数 = 3/5 = 60%
```

多返回一些文档，可能提高召回，也可能降低精确率并增加上下文负担。只返回最确定的一篇，精确率可能高但漏很多必要证据。

先认识这里的对象与符号

[Top-k、Top-p与重新归一化](../concepts.html#concept-topk)
:   Top-k保留概率最高的k项；Top-p按概率降序保留累计概率达到阈值的候选前缀。用于抽样时，被保留的候选需按剩余总质量重新归一化。这里k是候选数量，p是累计概率阈值；不是注意力Key表K，也不是表示维度d\_k。

[Precision、Recall、MRR与nDCG](../concepts.html#concept-metrics)
:   精确率看返回结果中有多少相关；召回率看应找相关中找到了多少；MRR平均第一个正确项的排名倒数；nDCG考虑相关程度和排序位置并相对理想排序归一化。独立例：应找5篇，返回4篇其中3篇相关，精确率3/4，召回率3/5。不要把这两个分母互换。

**Top-k**表示只看排名前k个结果，不是信心等级；**Recall@k**是在这个截断下看召回。

## 排得靠前也有区别

两个检索系统都找到了正确文档，一个排第一，一个排第二十，下游成本不同。**MRR**看第一个正确结果排名的倒数并平均；正确项第一是1，第二是1/2。

排得靠前也有区别：逐项辨别

|  |  |
| --- | --- |
| 对象一 | Recall@k |
| 对象二 | MRR |
| 对象三 | nDCG |

**关键区别：**前k个有没有找回、首个相关结果排第几、相关结果排序质量，是不同问题。

**容易误解：**只看召回不一定反映下游能否得到足够证据。

**nDCG**同时考虑相关性等级与位置折扣，并相对理想排序归一化。不同指标回答不同问题，不需要所有项目同时优化所有指标。关键是它是否关联最终任务成功。

## pass@1、pass@k、pass^k的区别

用简化假设：某个任务每次独立成功概率p=0.8。

先认识这里的对象与符号

[pass@k与pass^k](../concepts.html#concept-passk)
:   pass@k类指标通常关心k次尝试至少一次成功；pass^k类指标强调多次全成功。具体估计口径看基准，不能把一次成功后停止与每次都可靠混为一谈。独立同概率假设p=0.8，3次至少一成=0.992，3次全成=0.512。真实任务相关或难度不同则需另算。

```
一次成功：pass@1 = 0.8
三次至少成功一次：1−(1−0.8)^3 = 0.992
三次全部成功：0.8^3 = 0.512
```

通常用pass@k表达k个候选至少一个成功的能力，pass^k类指标强调多次都成功的可靠性。实际论文或基准会给出具体估计方法，不能把这里的独立同概率推导无条件套到所有混合任务。

pass@1、pass@k、pass^k的区别：逐项辨别

|  |  |
| --- | --- |
| 方案／对象 A | pass@1：单次成功 |
| 方案／对象 B | pass@k：至少一次成功 |
| 方案／对象 C | pass^k：多次都成功 |

**关键区别：**它们衡量不同的可靠性要求，不能因为数字都含k就混在一起。

**容易误解：**若各次运行不独立，简单的理论公式可能不适用。

也不能在没有可靠判据时，假设“生成k份一定能选出正确那份”。找到成功候选还依赖验证器。

## 先确定分母，再讨论提升

20道任务、每题3次运行，是20个任务和60个尝试，不应混成60个独立任务。一次成功率、三次至少一次成功、三次全部成功问的是不同问题。旧版和新版要用同一组任务配对：修复了哪题、又破坏了哪题，比只有一个总体百分比更有解释力。

同一20题上的配对结果旧版结果新版成功新版失败旧版成功12：都对1：退化旧版失败5：修复2：都错总成功新版17/20旧版13/20

| 旧版结果 | 新版成功 | 新版失败 |
| --- | --- | --- |
| 旧版成功 | 12：都对 | 1：退化 |
| 旧版失败 | 5：修复 | 2：都错 |
| 总成功 | 新版17/20 | 旧版13/20 |

同一20题上的配对结果。数值与状态属于本节明确设定的教学例；不是生产性能或商业模型实测。

把这一页的具体对象分清之后，再进入系统机制：[pass@k、pass^k和一次成功率为什么不能混用？](../chapters/23.html#agent-practice-eval)。这里不要求先知道完整源码；先能按状态表复述每一步发生了什么。

**证据与理解边界：**分别记录任务、一次尝试、执行轨迹与环境结果；资源限制和未重置状态都会混淆比较。

## 质量与成本必须一起看

新策略成功率相同但读了十倍文件，未必值得；更便宜的模型让失败重试大增，也未必更经济。**每成功任务成本**应把失败尝试和相关工具成本纳入分子，而不是只看成功那次Token。

同时记录用户可见延迟、输入输出量、检索范围和人工接管。流程更复杂或思考更长不是能力指标。

## 评测前怎样冻结条件

明确任务集、输入版本、环境、模型与Prompt版本、工具、超时、重试预算和判据，再比较。训练、调参和评测集合应有边界，避免把已知测试答案当新能力。

你不必先建庞大平台。先收集真实失败和代表性任务，人工核验判据，保存运行轨迹，再逐步扩充。数字有分母、有范围、有证据，比一个漂亮总分更有用。

### 同一组结果，把四个分母分别数清

**输入与条件。**系统执行10个任务成功8个；某次搜索返回A、X、Y，而全部必要证据是A、B。

| 步骤与对象 | 内部动作 | 中间结果 / 新状态 |
| --- | --- | --- |
| 1任务成功率 | 8个成功÷10个任务 | 80%。 |
| 2检索精确率 | 返回3份里只有A相关 | 1/3≈33.3%。 |
| 3检索召回率 | 所需2份里找到A | 1/2=50%。 |
| 4至少一次成功 | 若每次独立成功率0.8，试3次 | 1−0.2³=0.992。 |
| 5三次都成功 | 在同样独立假设下 | 0.8³=0.512；与“至少一次”不是同一个指标。 |

**把过程连起来。**不能拿高任务成功率代替证据召回，也不能拿多次尝试里的最好一次冒充单次可靠性。

**边界与反例。**独立同分布是假设，不是Agent运行天然满足的性质。
