## 数据搬到GPU，改变的是位置而不是含义

“装得下”和“算得快”为什么不是同一回事？

CPU与GPU可先理解成不同的计算场地。数据必须到达实际执行算子的设备，才能参与运算；搬过去并不自动变聪明。数据类型决定每个数怎样存、可表示范围和精度，不能只看“数字还是原来那个数字”。

**字节**内存占用的计量单位。

**精度**数值表示的细致程度；低精度会有舍入。

**带宽**每秒最多能搬多少数据。

**输入与适用条件：**只计算B=2、T=3、d=4的一份编号/特征张量，不计算模型总内存、驱动开销和GPU实测速度。

## 同一个数有三种不同的问题

看一份形状`[2,3,4]`的数据，要分别问：它怎么排列（shape）、每个数怎样存（dtype）、存在哪里并由谁算（device）。这三项不能互相代替。


<span id="fdiag-06-01"></span>


同一个数有三种不同的问题：逐项辨别

|  |  |
| --- | --- |
| 对象一 | 数值：2 |
| 对象二 | 类型：整数/浮点 |
| 对象三 | 位置：CPU/GPU内存 |

**关键区别：**同一个值可以用不同类型保存，也可以位于不同设备；它们是不同属性。

**容易误解：**搬到GPU不会自动把整数变成语义向量。

**CPU**是执行通用程序的处理器；**GPU**擅长在合适的运算上并行处理大量数字。**设备device**是计算框架用来标识执行或存储位置的概念，例如CPU或某块GPU。把数据放到GPU，不会自动使它变得更有语义，只是让相应硬件能够进行后续计算。


<span id="foundations-06-s2"></span>


## 整数编号与浮点特征为何类型不同

Token ID用于找表中哪一行，通常采用框架支持的整数类型；Embedding权重和输出常用浮点类型。**浮点数**是一种用有限位数近似表示含小数数值的方式，它不是任意精度的实数。


<span id="fdiag-06-02"></span>


整数编号与浮点特征为何类型不同：逐项辨别

|  |  |
| --- | --- |
| 方案／对象 A | input\_ids：整数编号 |
| 方案／对象 B | Embedding权重：浮点数 |
| 方案／对象 C | 后续隐藏状态：浮点数 |

**关键区别：**编号用于索引，参数和激活用于乘加，常见数据类型由用途决定。

**容易误解：**不是所有模型数据都是一个dtype，也不是所有东西都在显存。

`int64`表示每个整数用64位，即8字节；`float32`通常每个数用32位，即4字节；FP16和BF16各用16位，即2字节，但指数和有效数字的安排不同，表示范围和精细程度不能只看位数。实际算子支持什么类型，要看具体实现。

改变类型会改变内存与数值误差；改变shape是改变排列解释；改变device是改变执行位置。这些动作不是同一件事。


<span id="foundations-06-s3"></span>


## 对较大规模的表示算一遍存储

`[2,128]`共有256个编号。按int64存储，仅编号数据为`256×8=2048`字节。


<span id="fdiag-06-03"></span>


**关键区别：**先算元素数量再乘每个元素所占字节，得到这份激活张量占用。

**容易误解：**这个2MiB只描述一份张量，不能代替整个模型显存预算。

查表结果`[2,128,4096]`有1,048,576个数。若每个占2字节，仅这份结果为2,097,152字节，即2 MiB。MiB以1024为进制，1 MiB=1024×1024字节；十进制MB则是1,000,000字节。

**这不是整个模型只需2 MiB。** E本身、所有层权重、中间结果、KV缓存及运行工作区都还没算。估内存必须列出对象，而不是看到一个张量大小就推断总显存。


<span id="foundations-06-s4"></span>


## 一次常见执行的实际顺序

程序先准备模型参数和计算环境，再把本批ID与必要标记交给计算框架。对于独立显存的GPU，需要把参与运算的数据安排到兼容设备上；否则框架可能报设备不一致，而不是自动替你完成所有搬运。


<span id="fdiag-06-04"></span>


一次常见执行的实际顺序：逐项辨别

|  |  |
| --- | --- |
| 起点 | 准备输入编号 |
| 处理中 | 把参数/数据放到执行设备 |
| 新状态 | Embedding查表得到向量 |

**关键区别：**“放设备”和“查表”是可拆开的操作；实际实现和内存移动策略因框架不同。

**容易误解：**不要写死“先复制所有数据然后才开始算”作为所有系统唯一流程。

随后调用Embedding操作：根据ID读取权重表对应行，生成本批表示。接着运行网络的矩阵运算。生成结束后，有些结果会被取回CPU用于文本处理或界面显示。

这只是常见逻辑次序，不是所有底层系统都真的进行同样的物理复制。统一内存、模型分片和卸载会改变细节；本课先建立“运算需要访问到数据”的概念。

## 数据类型和设备是实现条件，不是语义

本模型在CPU使用float64，方便手算与有限差分核对；并不是语言模型部署都应该用float64。编号是整数，参数和激活是浮点数。放到GPU只改变在哪里计算；量化则会改变数值表示，二者不是同一个操作。

本实验没有偏置，没有Dropout，没有输入输出权重共享。后续公式中看不到b不是漏写；如果改成真实模型包含这些模块，必须相应补全计算。配置与权重文件必须一起看，不能仅用“Transformer”一个名字断定结构。

依据：[tiny\_model.py:33–46](../reference/model-code.md#tiny_model-L33)；[对应参数、前向及梯度记录](../labs/model-values.md)。

## 为什么小任务放GPU有时不快

传输、调度和启动一次运算都有成本。若真正的计算只有几个数字，准备与搬运可能比计算本身还贵。GPU吞吐强，不等于每个小操作延迟都低。


<span id="fdiag-06-05"></span>


为什么小任务放GPU有时不快：逐项辨别

|  |  |
| --- | --- |
| 方案／对象 A | 小规模CPU计算 |
| 方案／对象 B | GPU计算需传输/调度 |
| 方案／对象 C | 总耗时可能不降 |

**关键区别：**GPU单次算得快，但小任务的启动、搬运和同步可能占主导。

**容易误解：**单看理论算力不能预测端到端请求延迟。

还有一个常见计时陷阱：某些GPU调用是异步的，即CPU发出指令后即可继续，GPU还没做完。只量函数返回时间可能量到“排队指令”的时间，而非计算完成时间。测性能时需要按框架要求等待或使用设备计时机制。


<span id="foundations-06-s6"></span>


## 现在把“组批、放设备、查表”连起来

组批解决“这次一起算哪些输入”；补齐和标记解决“不同长度怎么摆”；device解决“在哪里算”；dtype解决“每个数怎样存”；Embedding解决“编号对应哪排数”。每一步的职责都不同，因此每一种错误的排查也不同。

### 把同一个张量搬到设备，数值和占用如何分别变化

局部核对例：以下输入以本例列出的条件为准，不能把它的中间值接到贯通模型的计算记录中。

**输入与条件。**从小例子 `[2,3]` 的6个整数，查出 `[2,3,4]` 的24个浮点数。假设ID用int64，每个8字节；浮点输出用FP32，每个4字节。

| 步骤与对象 | 内部动作 | 中间结果 / 新状态 |
| --- | --- | --- |
| 1算编号存储 | `6×8` | 48字节，只算数据本体。 |
| 2算表示存储 | `24×4` | 96字节；维度和dtype共同决定占用。 |
| 3拷贝到GPU | 把相同数据搬到另一设备 | 形状仍是 `[2,3,4]`；搬运不等于自动增加语义。 |
| 4改用FP16 | 相同24个数，每个2字节 | 本体48字节，但小数可能发生舍入；这与单纯搬设备不同。 |
| 5放大规模 | B=2、T=128、d=4096 | ID有256个整数；输出有1,048,576个数，FP16为2,097,152字节，即2MiB。 |

**把过程连起来。**先问存几个数，再问每数几字节，最后问在哪个设备；这三件事不能混成一个“维度变大”。

**边界与反例。**估算不包括张量对象、分配器、模型权重、缓存和中间结果；不是运行整个模型所需显存。
