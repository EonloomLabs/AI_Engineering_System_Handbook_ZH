## 从两个候选列表，走到可用证据

“相关”与“足以回答”中间还差哪几步？

多个检索入口可能互补。融合处理“哪些候选值得优先看”；重排对少量候选作更细比较；证据核验处理“这段话是否真的支持当前结论”。三个阶段目标不同，不能用一个相似度分数替代全部判断。

**RRF**通过名次而非原始分数融合候选列表的方法。

**重排**对召回后的候选重新作相关性排序。

**证据充分性**材料能否支持问题要求的结论和条件。

### 为什么需要

精确词项与语义线索各有盲区，组合能提供互补候选。

### 怎样实现

先融合候选，再核实原文与元数据，必要时补查缺失证据。

### 可能的代价与误解

提高Top-k可能把更多无关内容塞入上下文；检索器成绩提升不一定带来任务成功率提升。

### 如何判断是否做对

分别测召回、排名和最终回答支持度；不要只测最终一项或只测搜索分数。

## 召回和重排为什么分两步

**召回candidate retrieval**先从大量材料中找出一个较小候选集合，追求别漏掉关键材料，同时控制成本。**重排reranking**再用更细的相关性判断排列这些候选。

**关键区别：**先扩大相关候选覆盖，再用成本更高的方法排序，可平衡成本和质量。

**容易误解：**重排不能凭空找回从未召回的资料。

候选集合没有包含正确文档，重排器就无法凭空找回它。重排更强不等于整个检索管线更完整。

## 关键词和向量怎样一起用

关键词擅长精确名称，向量擅长部分语义匹配。**混合检索hybrid retrieval**把两条或多条路径的结果组合。

关键词和向量怎样一起用：逐项辨别

|  |  |
| --- | --- |
| 对象一 | 关键词检索 |
| 对象二 | 向量检索 |
| 对象三 | 融合排序RRF |

**关键区别：**关键词擅长精确术语，向量擅长语义相近，用融合减少单一路径偏差。

**容易误解：**不同来源的同一文档应注意去重与版本。

先认识这里的对象与符号

[BM25及N、df、k₁、b](../concepts.html#concept-bm25)
:   BM25是词项检索打分公式。常见记号N是文档总数，df是含该词的文档数，tf是当前文档词频，|D|是当前文档长度，avgdl是平均长度；k₁和b是词频饱和与长度修正的设置。k₁不是Key向量k₁，b也不是神经网络偏置。分数只用于给候选排序，不能把8.2解释为82%正确率。

[RRF：按排名融合](../concepts.html#concept-rrf)
:   RRF对某文档在每条召回路径上的排名r贡献1/(c+r)，再相加。c是平滑常数，r通常从1开始；没进入某条路径的候选不凭空获得该路贡献。独立例：c=10，某文档两路排名1、3，得1/11+1/13约0.167832。不是把BM25和余弦的原始分数相加。

直接把BM25分数8.2加到余弦0.7上不一定有意义，因为量纲和分布不同。**RRF（倒数排名融合）**按排名而不是原始分数融合。一种形式是对每条路径贡献`1/(c+排名)`，再相加。

例如取教学常数c=10，文档A在两条路径分别排1、3，得`1/11+1/13≈0.1678`；文档B分别排2、1，得`1/12+1/11≈0.1742`，因此B略靠前。这个值不是正确概率。候选只出现于一条路径时，另一条不凭空加分。

## Cross-encoder为什么更细也更贵

先认识这里的对象与符号

[bi-encoder、cross-encoder与重排](../concepts.html#concept-rerank)
:   双编码器分别编码查询与文档，可以预存文档向量；交叉编码器共同处理一对查询与文档，做更细判断，通常每对都要算。重排仅排序已经召回的候选。遗漏的正确文档不在候选集内，再强的重排器也不能直接把它排第一；需要先补召回。

**双编码器bi-encoder**分别把查询和文档变成向量，再快速比较，可以预存文档向量。**交叉编码器cross-encoder**把查询与候选文档一起交给模型，允许更细的词项互动，但每对都要计算，通常更适合较小候选集合。

**关键区别：**重排可更细看查询与文章交互，但每个候选都计算，成本通常更高。

**容易误解：**不要把重排分数直接当最终答案真值。



先认识这里的对象与符号

[ColBERT与MaxSim](../concepts.html#concept-colbert)
:   ColBERT类方法为查询和文档保留多个Token向量，再做后期交互。常见MaxSim让每个查询Token取与文档Token的最大相似度，再汇总。它不是“整篇文档只有一个向量”的双编码检索，也不是生成模型每层的自注意力输出。

**ColBERT**一类方法保留多Token表示后进行细粒度交互，处在另外的计算与存储取舍点。不要只把它们按“高级程度”排顺序，要看规模、预算和任务。

## 相关不等于足够回答

用户问“新版能否自动重试写请求”。找到一篇“重试概述”只证明主题相关，还要知道版本、写操作是否幂等、哪些错误允许重试、如何处理超时后的未知结果。

相关不等于足够回答：逐项辨别

|  |  |
| --- | --- |
| 方案／对象 A | “相关”：提到主题 |
| 方案／对象 B | “充分”：含关键条件 |
| 方案／对象 C | 真正回答要满足后者 |

**关键区别：**一段文档即使高度相关，也可能没给出版本、单位或例外条件。

**容易误解：**只引用高相似度片段，不能自动补齐缺失事实。

**证据充分性**是相对于要回答的具体断言而言：每个结论是否有适用条件和支持材料，而不只是“搜到几篇相关文章”。

引用也应该绑定具体断言。给一整段包含多个无关推断的话挂一个来源，未必能证明所有内容。

## 查询改写和假设文档的边界

**查询改写**把用户问题变成更适合搜索的表达，但不能把“可能是缓存问题”改写成“已确认缓存损坏”。改写中的假设仍是假设。

**关键区别：**改写能找到不同说法，但必须保留用户原约束与实体。

**容易误解：**改写扩大主题范围也可能引入虚假相关。



先认识这里的对象与符号

[HyDE：假设文本只用于找材料](../concepts.html#concept-hyde)
:   用模型生成一份假设性的回答或文档，将其表示用于检索。这份生成文本是寻找证据的辅助，不是已经找到的事实来源。模型猜“可能是缓存失效”，可以据此扩大搜索；没有真实证据前不能写成“缓存失效已确认”。

[GraphRAG、RAPTOR与组织层次](../concepts.html#concept-graphrag)
:   GraphRAG类方法利用实体关系及社区等组织信息；RAPTOR利用分层聚类与摘要支持检索。它们引入额外派生信息，也引入更新、来源和错误传播问题。源文档改变时，旧摘要或图中的关系可能过期。改了原文并不证明所有派生索引已同步更新。

**HyDE**利用生成的假设性文档帮助检索；该文档是检索辅助，不是实际证据。**RAPTOR**用分层摘要组织检索；**GraphRAG**利用实体关系或社区摘要等组织跨文档信息。它们解决不同失败模式，增加结构也会带来更新和错误传播成本。

## 一次RAG链路怎样不漏层

**RAG（检索增强生成）**不是一个新的基础模型种类，而是先取证据再让生成模型利用证据的系统方式。可以这样检查：

```
问题与权限范围
-> 查询理解
-> 候选召回
-> 版本和权限检查
-> 融合与重排
-> 补齐必要上下文
-> 判断证据足够与否
-> 生成并绑定引用
-> 核验关键结论
```

具体过滤可发生在多个阶段；关键是未经授权的数据不能进入不该看见它的组件。

## 为什么答案很像真的，却仍然错

可能切块丢了否定句，索引混了版本，召回漏了例外，重排偏好旧文，或模型把建议写成强制规范。每层都要有可观察证据；单纯换一个更大的生成模型可能只让错误表达更流畅。

### 把两个榜单融合，再检查是否足够回答

**输入与条件。**关键词检索返回 `[A,B,C]`，向量检索返回 `[B,C,D]`。取RRF常数60，每榜单名次从1开始。问题需要同时找到配置A与测试B。

| 步骤与对象 | 内部动作 | 中间结果 / 新状态 |
| --- | --- | --- |
| 1计算A | 只在第1榜单排1 | 得 `1/61≈0.016393`。 |
| 2计算B | 分别排2和1 | 得 `1/62+1/61≈0.032522`。 |
| 3计算C与D | C排3和2；D只排3 | C约0.032002，D约0.015873。 |
| 4融合排序 | 按总分降序 | 得到 `[B,C,A,D]`。 |
| 5只取前2的后果 | 上下文只放B、C | 虽有高相关结果，仍缺配置A，无法完成需要A与B的核验。 |

**把过程连起来。**排序高不等于证据齐全；知道问题需要哪些事实，才能判断取几个结果够用。

**边界与反例。**两个榜单为教学设定，不是实际Embedding服务返回值；RRF算术是真实执行。

## 排在第一的结果也可能不能用

假设D2在两路搜索融合后最高，但D2适用于旧版本，当前问题是新版本。它相关却不适用。正确流程先看相关性，再看版本、权限、条件和证据是否覆盖问题。两块内容来自同一原文不能自动算作两份独立支持。回答之前，把每个结论指向具体证据；缺哪一项就继续查或缩小结论。
