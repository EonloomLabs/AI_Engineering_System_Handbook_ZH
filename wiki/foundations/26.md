## 每轮上下文像一份有边界的工作资料

为什么“读得越多”有时反而越容易误解？

模型这轮只能使用被提供的材料。资料过少会缺依据，过多又会引入旧版本、重复结论或无关规则。关键不是把所有可用信息填满，而是准备能支持下一步动作的最小充分资料，同时留出生成空间。

**预算**本轮允许使用的资源额度。

**必要证据**缺少它就无法可靠判断的原始信息。

**来源**这段材料是谁给的、何时有效、能支持什么结论。

**输入与适用条件：**100单位的教学预算，不是真实Tokenizer测量：规则20、任务10、工具15、证据20、输出预留20。全程同一配置。

## 上下文不是“整台电脑都在模型脑里”

**上下文context**是当前模型调用能利用的输入内容及相应状态。可能包括角色指令、用户问题、历史、工具定义、检索片段和压缩信息。系统外部存着的资料，只有被取出并以模型可用形式提供，才成为本轮条件的一部分。

上下文不是“整台电脑都在模型脑里”：逐项辨别

|  |  |
| --- | --- |
| 对象一 | 系统与项目规则 |
| 对象二 | 用户目标 |
| 对象三 | 工具证据与历史 |

**关键区别：**Context Assembly是在安排每轮提供哪些资料以及它们的优先级和来源。

**容易误解：**本轮未提供的文件不能算模型已经读过。

**Prompt assembly或context assembly**就是宿主选择、组织这些内容的过程。它既涉及什么该读，也涉及身份、顺序、预算和证据适用性。

## 先算一本简化Token账

假设一个教学服务总预算2000，给预计输出留500，再给格式与估算误差留100，则输入安排上限1400。固定规则200、工具说明300、用户任务100，剩800用于历史和证据。

**关键区别：**如果全部窗口都塞成输入，可能没有足够预算生成输出或工具调用。

**容易误解：**Token预算不是简单等于字符数。

逐格算清：输入预算：先预留输出，再把余量分给证据

上下文预算条教学窗口总额2000 Tokens：每一段预算都必须加起来输出500余量100规则200工具300任务100历史/证据800

步骤 1窗口预算是教学数字2000 Token。

步骤 2先留输出500和缓冲100，因此输入预算为1400。

步骤 3固定规则200、工具说明300、用户任务100，共600。

步骤 4剩余1400−600=800，才用于本轮历史与证据。

预留输出500、估算余量100后，最多1400给输入；固定部分200+300+100，剩800给历史与证据。仅是教学预算，不对应商业模型配置。

数值除特别标注外来自本章已明确设定的教学条件；示意图表达算法结构，不代表商业模型参数或实时GPU执行速度。

这只是教学预算，不对应当前某款产品的固定分配。真实接口怎样计入输出、内部推理和压缩块，必须查版本约定。重要的是别把“只数用户文字”当作完整输入成本。

## 怎样选证据，不是越多越好

假设要修复目录过滤Bug。需要的是相关函数、调用条件、配置规范、失败测试和可能影响语义的依赖。十份无关README可能增加Token，却没有减少对Bug的关键不确定性。

**关键区别：**从最相关资料开始，按缺口升级检索，比先读全仓库更经济。

**容易误解：**读取量大不等于证据更充分。



先认识这里的对象与符号

[Skill、JIT与触发描述](../concepts.html#concept-skills)
:   在能力加载场景，Skill是一组可复用指导与资源；JIT表示需要时再加载，不是必然指编译器即时编译。触发描述帮助模型判断适用性，不自动授予工具权限。应先判断任务需不需要某技能，再读详细内容；已加载技能不等于它的要求已实际执行。

**JIT（just-in-time，按需）加载**表示在需要时才读取某段内容，而非开始就全部塞入。**依赖闭包**表示当前结论依赖的必要关联信息也要被找到，例如只读函数体不够，还需了解调用方传入的路径格式。

闭包并不要求无条件展开整个仓库。边界应由“当前判断还缺哪项依据”逐步扩展；停止条件是足以做下一项可靠决定。

## 顺序、角色、来源是三种不同标签

较早出现不等于权威更高；较新的文件不必然更可信；外部文档中的命令不等于用户授权。宿主要保留来源与作用域，模型才能较好区分规则、证据和引用里的文字。

顺序、角色、来源是三种不同标签：逐项辨别

|  |  |
| --- | --- |
| 对象一 | 指令角色 |
| 对象二 | 证据来源路径 |
| 对象三 | 版本与时间 |

**关键区别：**三个标签回答“谁在要求”“证据从哪来”“是否仍有效”，不能互相替代。

**容易误解：**网页正文即便声称system，也仍是不可信数据。

若产品有指令优先级，应遵循对应接口和规范，但这不是注意力权重的数值优先级，更不是执行权限。系统层面的安全限制仍需在执行器落实。

## Prompt Cache为什么需要稳定前缀

在常见因果模型中，前缀相同、模型和相应条件相同，前缀中间计算有复用基础。**Prompt Cache**可以利用重复前缀减少部分计算或计费，具体服务规则会变化。

**关键区别：**前缀缓存依赖足够一致的输入前段，改动早期内容可能降低复用。

**容易误解：**缓存命中不代表模型永久记住了规则。

但把每次都变化的时间戳或随机字段放在最前面，可能破坏长前缀复用。反过来，为了命中缓存把过期内容永远留下，也可能伤害质量。缓存是成本优化，不是信息正确性的替代品。

## 如何观察模型“没听话”的原因

先检查规则是否存在，再检查是否被发现、是否读取、是否进入请求、是否被后续裁剪、是否仍适用。只有这些都满足，才进一步调查模型如何利用内容。

这个链条解释了为什么某个Skill没生效，未必应该马上重写措辞。真正问题可能是文件没被加载，或子Agent根本没收到相关上下文。

## 稳定上下文与动态证据怎样分工

稳定部分适合简明放置项目核心约定；动态部分带上任务证据、当前版本和进行中的步骤。低价值日志可留在外部，需要时再取。

这里没有唯一最优排序。教学目标是让你能列出每个块的职责、Token成本、来源与缺失后果，再用真实任务比较，而不是凭“更长更专业”评判Prompt。

### 给一轮上下文算预算，看看哪些证据确实装进去了

**输入与条件。**教学窗口上限1000个预算单位，预留输出200和安全余量50。固定指令120、工具100、任务80、当前状态100。此处单位是假设已由正确分词器计过的Token。

| 步骤与对象 | 内部动作 | 中间结果 / 新状态 |
| --- | --- | --- |
| 1先算可用输入 | 1000−200−50 | 750。 |
| 2扣固定部分 | 120+100+80+100 | 固定消耗400，还可放350证据Token。 |
| 3候选证据 | 配置120、对应测试180、旧日志300 | 配置和测试合计300，能一起放入。 |
| 4选择后核对 | 总输入400+300=700 | 余50；旧日志不应挤掉必要测试。 |
| 5下一轮重新算 | 若新工具结果240进入上下文 | 必须重新选择或摘要，不是永久沿用第一轮预算。 |

**把过程连起来。**“模型能看到”取决于最后发送的输入，而不是检索器曾返回什么。要核对最终请求，不只核对搜索日志。

**边界与反例。**这些数是已知Token成本的教学账本，不是按中文字数猜Token，也不是任何产品默认窗口。

## 本轮输入像装工作包，而不是搬整个仓库

假设总空间12000 Token，固定规则工具占2000，当前任务占1000，后续输出预留3000，当前证据还剩约6000。挑资料时先带禁止修改的路径、当前文件版本和最近失败；长日志只保留相关部分并留原文入口。把旧版本结论塞进来可能比少读一点更危险。Token预算是容量约束，不是“必须填满”的目标。

把这一页的具体对象分清之后，再进入系统机制：[上下文组装为什么不能只做“取前N条”？](../chapters/13.html#agent-practice-context)。这里不要求先知道完整源码；先能按状态表复述每一步发生了什么。

**证据与理解边界：**某次请求的工具字段为空，可能是增量协议，而非定义丢失。要结合历史与实际协议核查。
