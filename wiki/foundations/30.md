## 代码检索不能只靠“语义相近”

grep、AST、LSP、调用图各自看到什么？

同一个函数名可能出现在注释、字符串、不同模块的同名函数中。文本搜索先定位线索，语法分析区分结构，语言服务帮助解析具体符号，运行和测试才告诉你这条路径是否真的触发。它们像不同视角的检查，不是越多越好地全部跑一遍。

**AST**按语言语法组织的代码结构树。

**LSP**让编辑器查询符号、引用和诊断等信息的协议。

**调用图**以函数为节点、可能的调用为边的关系图。

**输入与适用条件：**以foo为教学符号，不指向用户仓库。调用图可能受动态调用、条件编译与运行配置影响。

## 先从一行代码看不同观察层

`total = price * count`是一串文本，也有结构：左边是赋值目标，右边是乘法表达式，price和count是变量。文本搜索能找到字符，语法分析能识别关系，两者提供的信息不同。

先从一行代码看不同观察层：逐项辨别

|  |  |
| --- | --- |
| 对象一 | 文本层：字符串匹配 |
| 对象二 | 语法层：AST结构 |
| 对象三 | 语义层：符号和类型 |

**关键区别：**代码可以从文本、结构、符号三层观察；每层能回答的问题不同。

**容易误解：**找到同名函数不等于找到调用时实际绑定的实现。

**AST（抽象语法树）**把代码组织成语法节点，例如赋值节点下面有乘法节点。**符号symbol**是函数、变量、类型等语言实体；同名字符串可能指向不同符号，所以全文匹配不总能替代语言理解。

## LSP不是自动懂业务的模型

**LSP（语言服务器协议）**让编辑器向语言服务请求“定义在哪、有哪些引用、是否存在类型错误”等能力。它是通信协议，实际分析由对应语言服务完成。

**关键区别：**语言服务使用项目结构和语言规则定位定义与引用，不是“理解业务需求”的模型。

**容易误解：**宏、动态反射和生成代码仍可能超出静态分析能力。

“找到函数定义”与“知道生产环境传进了什么数据”仍不同。类型系统可以排除部分错误，但某个配置导致的运行问题可能需要日志、测试或真实输入。

## 代码里的位置、版本与执行结果要对上

搜索到foo只是定位候选。必须知道当前文件、函数定义、调用方和工作树版本。Agent写了补丁后，旧测试结果不再直接适用；即使commit没变，未提交文件已经变化。阅读LSP位置时还要知道字符计数单位，不能把中文和表情的字节数当成协议列号。能解析代码不等于已经验证代码。

| 证据 | 绑定对象 | 失效条件 |
| --- | --- | --- |
| 补丁 | r7旧文本 | 文件已被改成r8 |
| 测试 | 工作树哈希+命令 | 测试后再修改 |
| 诊断 | 环境+运行输入 | 配置与数据变化 |

源码与证据版本链。数值与状态属于本节明确设定的教学例；不是生产性能或商业模型实测。

## 图、节点和边怎样读

**图graph**由节点和边组成。函数是节点，调用关系是从调用方到被调用方的有向边。调用图帮助理解影响范围。

**关键区别：**代码依赖图把“谁调用谁”“谁影响谁”表示为节点与边。

**容易误解：**图上连通不等于运行时必然执行该路径。



先认识这里的对象与符号

[DAG、依赖与关键路径](../concepts.html#concept-dag)
:   DAG是有方向且没有环的任务依赖图。箭头A→B表示B依赖A完成；关键路径是在给定任务时长与依赖下决定最早完成时间的最长依赖链。独立例：A需2秒，B/C依赖A分别需3/5秒且可并行，则A后两者完成至少7秒，不是把2+3+5=10当墙钟时间。

**DAG（有向无环图）**是没有沿箭头绕回自己的依赖图。例如A完成后才能B，A完成后也可C，最后D依赖B和C。它适合安排任务先后，而不是神经网络独有概念。

“依赖闭包”就是沿必要边追到足以解释当前问题的关联；“静态调用图”由源码推断，“动态调用关系”来自实际执行。动态分派、反射和插件会让静态图不完全等同真实路径。

## Git的几种状态为什么都重要

**commit（提交）**固定一份历史快照；**分支branch**是指向某条提交演进的引用；**工作树working tree**是当前检出的文件及未提交修改；编辑器里未保存的文本又可能还没进入磁盘。

Git的几种状态为什么都重要：逐项辨别

|  |  |
| --- | --- |
| 对象一 | 工作区未提交文件 |
| 对象二 | 暂存区Index |
| 对象三 | Git提交快照 |

**关键区别：**看到哪个版本代码必须交代清楚，否则验证可能针对不同对象。

**容易误解：**Git历史记录不包含未提交修改。

Agent读取提交A的索引，但修改的是带本地更改的工作树，就可能依据过期内容生成补丁。相同路径不代表相同版本。

先认识这里的对象与符号

[Patch、图像通道与视觉投影](../concepts.html#concept-patch)
:   图像中的patch是切分的小块，RGB是红绿蓝3个通道；软件工程中的patch则是代码补丁，两者同名。图像块展开后可通过可学习变换成为向量，不是查文字词表。独立图像例：16×16×3的一块含768个数，投影后可以变成d个特征。d由模型设计决定。

**diff或patch**描述修改前后哪些内容改变。补丁能应用，只说明某种文本或结构匹配成功，不证明业务语义正确。

## 一次Bug定位的具体顺序

先用失败输入或报错建立可重复现象；定位相关入口与函数；阅读调用者如何传参数；检查配置、版本和边界条件；提出候选原因；用最小实验区分；修改后对当前版本验证。

**关键区别：**Bug定位优先用低成本确定性工具收缩范围，再逐步扩大。

**容易误解：**先扫全仓库可能降低信息密度。

例如“目录exclude不生效”，只读字符串比较函数可能看不出问题。需要知道路径是否已规范化、目录规则是否应匹配分隔符边界、Windows和Unix分隔是否统一。这些是业务与环境前提，不是模型多读几个随机文件就能自动补足。

## “懂业务”需要什么资料

业务对象、核心不变量、术语、外部依赖、异常处理和验收例子，比大量历史闲聊更直接。**不变量invariant**是在允许操作过程中应始终成立的条件，例如“不能修改公共签名”或“已提交记录必须可追溯”。

这些规则可以存于项目文档和测试中，通过按需检索提供。把全部业务知识塞进一份无限增长的Prompt，会带来检索和维护问题。

## 编译、测试和运行证据怎样配合

编译检查部分语法与类型约束；单元测试检查特定局部行为；集成测试检查组件配合；生产日志反映实际环境事件。每种证据都有范围，不能用其中一个覆盖全部。

所以代码检索的最终目标不是“找到最多文件”，而是为当前修改获得最小充分、版本正确、可验证的依据。

### 同一个函数名，文本命中为何不等于真实调用

**输入与条件。**文件a.py定义 `build()`；b.py有注释“build可能失败”；c.py写 `from a import build; build()`。

| 步骤与对象 | 内部动作 | 中间结果 / 新状态 |
| --- | --- | --- |
| 1文本搜索 | 搜索build | 三个文件都可命中，注释也算。 |
| 2语法分析 | 区分函数定义、注释与调用节点 | b.py没有执行build的调用。 |
| 3绑定分析 | 解析c.py的导入关系 | 该调用指向a.py中的build，不是任意同名函数。 |
| 4核对运行入口 | 确认c.py是否在本次任务执行路径上 | 静态有调用也不意味着本次真的运行。 |
| 5查看运行证据 | 测试或日志记录调用发生与版本 | 与静态结构合起来确定问题位置。 |

**把过程连起来。**grep找字面，AST找结构，语言服务找部分语义绑定，运行证据说明某次实际发生了什么。

**边界与反例。**这是小型静态Python示例；动态导入、反射、生成代码和不完整项目会增加不确定性。
