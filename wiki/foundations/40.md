## 先找错误发生在哪层，再谈换模型

什么时候该改Prompt、检索、记忆或模型？

一个错误答案可以来自不同原因。模型根本没拿到新版本时，增加推理时间不能补出缺失事实；检索已经拿到新版本却被旧记忆覆盖时，需要修上下文与记忆使用规则。选择修复层应跟随证据，而不是看到失败就再加一个Agent。

**归因**用证据判断导致现象的环节。

**消融**改变或移除一个因素，看现象如何变化。

**最小有效修复**能处理已确认问题而不扩大无关复杂度的改动。

**输入与适用条件：**独立诊断例：当前版本r8的timeout=30，旧版本r7为10；核对错误发生在同步、检索、摘要还是生成层，不将单次改善视为因果证明。

| 现象 | 先写清楚哪句话错、正确证据是什么，避免只说“感觉变差”。 | 参见本步解释 |
| 定位输入 | 若原始证据没进入系统，先处理数据链路，不责怪模型不会推理。 | 参见本步解释 |

| 最小修复 | 保持模型和其他环节不变，修一个被证据支持的环节。 | 参见本步解释 |

## 先问失败发生在哪一层

“AI没有修好Bug”可能是没读到相关文件、读到旧版本、缺少业务条件、模型推断错误、工具没有权限、修改执行结果未知，或测试判据太弱。这些原因不能统一用“换更大模型”解决。

**关键区别：**先找责任层，才能避免看到质量问题就马上换模型或叠加Review。

**容易误解：**未经证据就优化，可能把简单任务复杂化。

沿运行链逐步问：输入是什么？宿主给了哪些信息？模型产生什么输出？执行器做了什么？环境变成什么？验证能证明到哪里？这就是把前面基础知识变成诊断能力。

## 一个完整但不过度复杂的调查

现象：Agent说修改完成，测试仍失败。

先核对目标是否明确，以及测试是否确实对应当前需求；再核对最终工作树与Agent读过的版本；检查工具响应与真实文件是否一致；然后看模型是否读到了关键调用方；最后才分析推理或算法实现。

**关键区别：**调查要能复现，不应在无界搜索中循环。

**容易误解：**工具失败反复重试不能代替升级或跳过策略。

若证据显示工具根本没写成功，没必要先评审模型的深层Attention。若文件和环境正确，但逻辑遗漏边界，就补反例、改实现并回归。诊断深度由故障证据决定。

## Prompt、RAG、Memory、Skill和Fine-tuning怎样选

| 观察到的缺口 | 优先考虑 | 不是它能直接解决的事 |
| --- | --- | --- |
| 任务表述含糊 | 明确目标与验收，改输入 | 无法自动修复工具权限 |
| 缺当前事实 | 检索和版本化证据 | 不保证模型一定正确利用 |
| 跨任务经验反复丢失 | 可追溯长期记忆 | 不等于更新参数 |
| 稳定专业流程缺失 | Skill及合适工具 | 不应取代硬安全边界 |
| 特定行为分布长期不理想 | 评测后考虑微调 | 不适合当实时数据库 |
| 执行与恢复不可靠 | Harness、状态和幂等设计 | 不是多写提示就确定正确 |

这些技术可组合，但每加一层要指出一个实际失败模式和验证方式，否则只是在增加系统复杂度。

Prompt、RAG、Memory、Skill和Fine-tuning怎样选：逐项辨别

|  |  |
| --- | --- |
| 对象一 | Prompt：表达任务 |
| 对象二 | RAG：取外部事实 |
| 对象三 | Memory：跨任务保留 |

**关键区别：**不同机制解决不同缺口，选错工具只会增添上下文与维护负担。

**容易误解：**需要最新代码时应先查仓库，不是去微调模型记住它。

## 为什么读完基础还需要高级追问

会手算两个向量的点积，只是进入Attention的门槛；还需理解多头、位置、梯度、缓存和内核。会定义幂等，也还需理解并发、状态持久化和跨系统边界。

为什么读完基础还需要高级追问：逐项辨别

|  |  |
| --- | --- |
| 方案／对象 A | 基础课：会解释对象 |
| 方案／对象 B | 高级课：会看实现细节 |
| 方案／对象 C | 工程实践：会设计与验证 |

**关键区别：**学习深度体现在从概念推到代码状态、失效边界和可复现证据。

**容易误解：**名词数量多不代表理解了系统内部。

系统篇的28章和112题继续展开这些机制。基础课负责解释它们用到的语言和运算，高级题负责追问边界、推导、反例及工程取舍。两层不是同一份内容换标题。

## 面试式回答怎样不变成背口诀

解释一个机制时，至少给出：为什么需要它、输入输出是什么、内部步骤怎样走、一个小例子、一个会失败的条件，以及怎么验证。遇到没有公开的产品内部，就说明可观察到的部分和未知边界。

**关键区别：**面试式回答最好有可追问的推导链，而不是只给术语定义。

**容易误解：**背结论时不懂适用条件容易给出错误工程建议。

例如回答“KV缓存为什么能复用”，不能只有“减少重复计算”；要能说出因果前缀不变、各层分别保存、位置与权重约束、新Token尚未计算的一位差，以及全量与增量对照测试。

## 深度不以术语数衡量

把整个词汇表背完，仍可能不懂一个请求在哪里丢了数据；只会一个小模型，也未必能判断生产权限和版本问题。真正深度是跨层连接，但每次连接都保留对象、条件和证据。

推荐的阅读方式是先在基础例子上走通，再进入相关高级问题。读到不认识的术语，可在本地释义中查看，并沿前置课返回，不需要跳去英文网页补整门课程。

## 怎样检验自己已经接上主线

先认识这里的对象与符号

[Query、Key、Value：三种中间数值表示](../concepts.html#concept-qkv)
:   q是接收信息的一行查询表示；k是可读位置提供的一行匹配表示；v是该位置供混合的一行内容表示。大写Q/K/V把多行收集成表。它们由输入与参数计算得到，分别承担打分与提供内容的职责。某个q与两个k点积得到两个分数；softmax得到两个份额；这些份额分别乘两行v，再相加。这里不生成搜索词，也不直接选答案。

合上正文，解释从两条文字到`[2,3,4]`发生了什么；再解释模型怎样用Q/K/V产生新表示；再解释它如何提出工具调用，以及宿主怎样判断动作完成。最后拿一个真实任务，说出你会收集哪份证据来区分两种候选原因。

如果其中某一段说不清，返回对应课重算小例子即可，不必从头再背全部文章。这是一条可以定位知识缺口的路线，而不是要求一次吞下所有知识。

### 把“答案错了”定位为一个可以修复的具体环节

**输入与条件。**问题是“项目A当前超时值”。资料中r1写3秒、r2写5秒。系统回答3秒。

| 步骤与对象 | 内部动作 | 中间结果 / 新状态 |
| --- | --- | --- |
| 1检查源 | r2文件确实存在且可访问 | 不是资料完全缺失。 |
| 2检查候选 | 检索日志里已有r1、r2 | 不是召回不到新版本。 |
| 3检查最终输入 | 上下文组装只保留r1 | 信息在组装阶段丢失。 |
| 4做最小修复 | 按适用版本保留r2，重放相同任务 | 不要先换模型或新增多Agent。 |
| 5验证其他情况 | 再测问历史规则、项目B和缺日期的查询 | 避免“总选最新”破坏历史问题。 |

**把过程连起来。**把错误定位到有证据支持的环节，比给系统堆新技术更能形成可验证改进。

**边界与反例。**所有版本和结果为教学构造；重放可以验证此例机制，不能代替真实任务集评测。

理解衔接

## 用失败链定位，而不是立刻增加更多技术

任务失败时依次检查：需求是否明确、关键证据是否读到、是否进入实际请求、模型是否提出正确动作、执行器是否执行、结果是否回填、完成是否被验证。每次修复对应一个已定位断点。增加记忆、多Agent或审查之前，先写出它将减少哪种具体错误，再用同一任务集比较收益与代价。

把这一页的具体对象分清之后，再进入系统机制：[研究型Agent怎样避免“搜了很多，却没有形成结论”？](../chapters/26.html#agent-practice-research)。这里不要求先知道完整源码；先能按状态表复述每一步发生了什么。

**证据与理解边界：**多个转述同一原始来源并不构成独立证据；结论要回溯到真实取得的原文及条件。
