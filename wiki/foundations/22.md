## 把一个Agent任务拆成真正发生的几轮

同一句用户任务，为什么可能调用模型不止一次？

LLM生成下一步提议，宿主执行获准的动作，把结果再交给LLM。这是外层任务循环；每次模型调用内部还要经历逐Token生成。外层的一轮工具行动不等于内部生成一个Token，两种“循环”不能混用。

**调用标识**把某次工具请求与其结果连接的ID。

**工具结果**程序实际执行后返回的内容。

**上下文**本轮明确交给模型的信息，而非整个电脑状态。

### 为什么需要

模型可以借助工具获得新证据，而不把一切都塞入参数。

### 怎样实现

按请求、校验、执行、结果回填、继续决策组织循环。

### 可能的代价与误解

忘记回填工具结果会让模型重复请求；把输出文本当执行证明会误报完成。

### 如何判断是否做对

对照每轮模型输入和工具日志，确认结果与call\_id匹配。

## 先还原成普通程序

把**Agent**理解为一个围绕模型组织任务执行的系统：程序准备输入，调用模型，检查模型输出；如果输出要求用工具，就执行并把结果回填；如果已满足完成条件，就结束。

先还原成普通程序：逐项辨别

|  |  |
| --- | --- |
| 对象一 | 用户任务 |
| 对象二 | 模型：提议下一步 |
| 对象三 | 宿主：真正调用工具 |

**关键区别：**Agent是一种组织模型、工具、状态和反馈的程序系统。

**容易误解：**不是多了一种独立的新神经网络。

**Harness或宿主**是这套执行环境和控制逻辑的常用名称。模型负责生成候选动作或回答，宿主负责真正运行、保存状态和控制边界。不是模型内部突然长出了文件系统访问权限。

## 一个三次模型调用的完整例子

用户问：“文件里函数返回什么？”下面用教学消息，不对应某厂商全部API字段。

**关键区别：**模型先给出调用意图，宿主执行后下一轮才有新证据。

**容易误解：**模型写出工具名称不等于工具已执行。

**第一轮输入**包括用户问题、可用工具说明：“read\_file接受一个path，返回文件文本。”模型输出的是工具请求，例如`read_file(path='demo.py')`。此时文件尚未因此被读完。

**宿主执行**：检查路径允许访问，调用真实文件读取操作，得到`def answer(): return 42`，把结果与这次调用身份绑定。

**第二轮输入**包括原任务、前一轮工具请求及真实工具结果。模型现在可以根据源码答“返回42”，也可以提出进一步验证请求。假设它要求运行测试，宿主执行后返回测试输出。

**第三轮输入**含这份验证结果，模型组织最终回答。宿主仍应按照任务类型判断是否完成，不能只因为最后一句语气肯定就证明所有需求满足。

## 一轮、一回合和一个任务为什么要区分

先认识这里的对象与符号

[Thread、Turn、Session：运行层次](../concepts.html#concept-threadturn)
:   这些通常是宿主对会话和工作轮次的划分，不是神经网络的层。Thread可指一条会话，Turn可包含响应一次用户任务所需的多次模型/工具循环；具体边界取决于产品。不能把“本轮完成”直接等同“所有外部工具都已结束”；需要看实际事件和结果。

本书把一次模型请求及其输出叫**模型调用**。用户发一个问题到收到本次答复可称一轮用户交互；其中可能包含很多模型调用和工具执行。产品中的Turn、Step、Thread具体定义可能不同，阅读源码要看该项目的类型和生命周期。

**关键区别：**一次任务可以跨多轮模型调用；每轮输入都会受到前序工具结果影响。

**容易误解：**一个用户问题不等于一次模型调用。

**Thread或会话**通常保存相关交互的组织关系；**任务task**是要实现的用户目标。一个长任务可能跨多次会话，一个会话也可能包含多个任务。

## 工作流与自由Agent的区别

**工作流workflow**可由程序预设步骤，例如“先查缓存，再查数据库，再生成回答”；更自主的Agent把更多下一步选择交给模型。两者可以混合，不是只有完全自由行动才叫先进。

工作流与自由Agent的区别：逐项辨别

|  |  |
| --- | --- |
| 对象一 | Task：整个目标 |
| 对象二 | Turn：用户或代理的阶段 |
| 对象三 | Tool call：一次动作 |

**关键区别：**三个粒度必须分开记录，否则重试与恢复无法定位具体步骤。

**容易误解：**不同产品的Turn命名可能不同，需按当前系统定义理解。

固定流程有可预测性，自由选择有适应性；多加一个自主环节也增加错误和成本。简单需求已有明确路径时，没必要强制先规划、再多Agent研究、再反复审查。

## 什么叫工具，什么叫副作用

**工具tool**是宿主向模型提供的可调用能力。读文件、搜索、查数据库、运行测试都是工具形式。**副作用**是调用改变了外部世界，例如修改文件、发送邮件、提交代码。

什么叫工具，什么叫副作用：逐项辨别

|  |  |
| --- | --- |
| 方案／对象 A | Workflow：预设步骤 |
| 方案／对象 B | Agent：动态决策步骤 |
| 方案／对象 C | 两者可以组合 |

**关键区别：**明确任务通常用确定性流程更简单；复杂探索可让模型选择下一步。

**容易误解：**并非使用Agent越自由就一定越好。

模型生成一个工具名称不代表已完成副作用；副作用发生后响应丢失，也不代表它未发生。这就是F33要讲的unknown和幂等问题。

## 为什么Agent需要循环

在不知道文件内容时，模型无法可靠决定最终补丁；读完文件后才有新的信息。循环让“行动获得观察，观察改变下一步决策”成为可能。它不是为了让模型机械地多说几遍分析。

循环同时必须有结束条件、预算和无进展处理。比如相同搜索连续没有新证据时，就应该改变策略或报告缺口，而不是无限重复。

## 本书教学脚本的边界

离线演示可以让一个固定脚本依次返回预设工具请求，以展示消息怎样移动；这叫协议或控制流模拟，不是商业模型真实自主能力。只有接入真实模型并记录实测，才能讨论该模型在任务上的成功率。

### 读取—发现缺口—再读取：让一次工具结果决定下一步

**输入与条件。**用户问“为什么超时？”教学仓库中config写 `timeout=3`，日志写 `request elapsed=5`，单位均在文件头声明为秒。

| 步骤与对象 | 内部动作 | 中间结果 / 新状态 |
| --- | --- | --- |
| 1第1轮模型输入 | 任务＋read\_file工具说明 | 提议读取config。 |
| 2第1个工具结果 | 拿到timeout=3秒 | 只能确认配置，还不能知道真实请求是否超时。 |
| 3第2轮模型输入 | 追加config结果 | 提议读取日志，而不是直接猜网络坏了。 |
| 4第2个工具结果 | 日志耗时5秒 | 有了配置与运行记录两个证据。 |
| 5第3轮回答 | 对齐同一请求和同一版本 | 5大于3，可说明本次请求超过配置时限；仍不能仅据此确定为何耗时5秒。 |

**把过程连起来。**Agent循环的价值是根据已取得证据确定缺什么，而不是机械地多问模型几次。

**边界与反例。**动作序列是教学构造，不是实测模型自动选择；这里证据只支持“超过时限”，不支持猜测更深根因。

## 先把三份信息分开：用户要求、模型提议、工具事实

用户说“读config.txt中的timeout”。模型先拿到任务与read\_file说明，但文件内容还在磁盘上。模型输出call\_id=c7和path，仅仅是提议；宿主检查路径后真正读取，返回timeout=30并关联c7。下一次模型调用必须包含或能正确引用这条结果，才能回答30。若没有读取结果，模型说30只是猜测。这个例子里没有任何训练，参数通常不因这一轮读取而改变。

四种完成不互相替代对象此刻状态能证明什么模型响应已结束文本生成结束工具调用测试运行中尚无最终测试结果工作树已修改到r9仅证明内容改变任务目标待验证需要r9验收证据

| 对象 | 此刻状态 | 能证明什么 |
| --- | --- | --- |
| 模型响应 | 已结束 | 文本生成结束 |
| 工具调用 | 测试运行中 | 尚无最终测试结果 |
| 工作树 | 已修改到r9 | 仅证明内容改变 |
| 任务目标 | 待验证 | 需要r9验收证据 |

四种完成不互相替代。数值与状态属于本节明确设定的教学例；不是生产性能或商业模型实测。

把这一页的具体对象分清之后，再进入系统机制：[一次回答结束，为什么任务仍未完成？](../chapters/09.html#agent-practice-loop)。这里不要求先知道完整源码；先能按状态表复述每一步发生了什么。

**证据与理解边界：**模型响应结束只证明本次生成结束；工具结果和最终验收仍是两份独立证据。停止钩子检查也不能代替真实测试。
