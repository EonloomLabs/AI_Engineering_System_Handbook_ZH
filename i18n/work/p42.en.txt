6040	1. Text matching, syntax matching and semantic binding
12961	Full-text search answers "where does this string appear?"; an AST answers "what syntactic structure is at this position?"; name binding/type analysis answers "which definition does this identifier actually reference?" They are not equivalent. For example, two files may both contain
29295	, yet these may be a built-in function, method or imported alias; full-text search cannot disambiguate them.
9009	Tree-sitter queries locate syntax fragments by node structure and fields; they also expose error or missing nodes, making them useful for incomplete code under editing. LSP defines requests between clients and language services, including definitions, type definitions, references and diagnostics; check capabilities and implementation to establish whether a language server supports them and how accurately.
6926	An AST does not automatically provide a complete call graph. Dynamic attributes, reflection, dependency injection, generated code and runtime plugins can make static relationships incomplete. This book's Python AST experiment returns only function/class names and line ranges; it does not claim cross-file name resolution.
6275	2. An evidence path for "the skill did not load"
12920	Read the actual task record first to locate failure in discovery, selection, reading, injection or execution. Then locate the loading entry point and conditional branches; read the configuration types and callers that determine the branch; finally find tests for those conditions. This path follows a falsifiable hypothesis rather than traversing the whole root directory first.
12307	For example, suppose the candidate root cause is an incorrect cwd. Find how startup establishes cwd, how rule-discovery functions use it, and whether tests cover nested directories. Seeing only a function name
29423	does not prove it was called, much less that its return entered model input. Execution traces and the source-code chain establish evidence together.
18199	When a code path is unclear, text search cheaply finds error messages, configuration keys and log events; semantic retrieval maps "why does it not take effect?" to possible modules. The right approach usually combines methods rather than declaring one retrieval method a universal replacement for the rest.
6430	3. Chunking file and symbol indexes
19430	Fixed-character code chunks may cut through function signatures, exception handling or closures. AST-symbol chunking better respects structure, but large functions may remain too long and small functions may lose type and caller context. A reasonable index can store the main symbol text, parent scope, import summary, path and version, then expand related information on demand.
23511	A symbol name alone cannot be a global primary key: overloads, same-named classes, different files and different versions collide. Use repository+version+path+qualified symbol name as a locator, with a stable range attached. Line numbers are snapshot coordinates and may move after edits; display the version alongside them.
11958	Comments and documentation are evidence too, but conflicts with execution logic need investigation rather than automatically choosing the easier-to-read side. Test assertions express expectations and source code expresses current behavior; a mismatch may be the defect to fix. "The current code does this" does not mean the user must want it.
6529	4. Dependency graphs for change-impact analysis
15850	Graph nodes can be modules, functions, types, configuration or tests; edges may represent calls, imports, inheritance, data dependencies or coverage. Edge confidence varies: compiler-resolved direct references are usually stronger than text-based guesses; runtime traces cover only executed paths and do not establish that others are absent.
12480	After changing a function, inspect direct callers and argument/return contracts, then boundary uses and error handling; test selection can expand along dependencies. Missing static edges, dynamic paths, shared data and build configuration can still cause omissions. For high-risk changes, broaden regression checks after focused tests rather than treating the graph as absolute proof.
27244	This also explains why codebase RAG needs more than "find the most similar code snippet". Implementation needs combined evidence from definitions, calls, configuration and tests. RepoCoder studies iterative retrieval and generation together, but success on repository-completion benchmarks does not directly establish arbitrary bug-fixing capability.
6626	5. What Git history can explain
19737	Commit history helps identify when behavior appeared, the reasons at the time, related tests and rollback risks. It supports understanding current code rather than replacing it. An old decision may address constraints that no longer exist; making an old PR conclusion a permanent rule creates stale memory.
17301	For regressions, binary search can narrow the change that introduced the issue, but the environment and dependencies must be reproducible; otherwise, infrastructure noise may determine test passes and failures. Recording failing samples and commands is more useful than one commit alone. Commit messages may also be incomplete and need diffs and runnable evidence.
6708	6. Why "not found" does not mean nonexistent
19788	Search may be limited by ignore rules, file types, hidden directories, index delays, unfinished language-server analysis or query expressions. Negative conclusions need a search scope and method. For example, "no text references to this symbol were found in the current src directory" cannot become "the entire system never calls it".
18623	Expand searches to address gaps: add likely modules or configuration directories first, then inspect dynamic registration and generated code. Expanding indefinitely into every dependency also reduces efficiency. Stop when evidence supports the decision, or when remaining uncertainty is explicit and needs external material, rather than insisting on traversing every file.
6785	7. Writes still need control after evidence is retrieved
24206	After precise location, generate and verify the patch against the version read. 15869	In an IDE, specify whether unsaved editor buffers or disk files are authoritative; in a CLI, inspect existing user changes in the work tree and avoid overwriting them. AI development does not justify weaker change-isolation standards than ordinary software engineering.

6034	1. What real gains multiple agents offer
23223	Relatively independent searches can run in parallel, tasks can have separate contexts and tools, and some reviews can isolate the implementer's assumptions. Anthropic's research system provides a case of a main agent coordinating parallel sub-agent exploration; Agentless suggests structured, simple flows can also compete on some software tasks. Their tasks and settings differ, so neither establishes that "multiple agents are always better".
16198	Multiple agents add task descriptions, repeated retrieval, context handoffs, merging, conflict resolution and extra model calls. If everyone edits the same core logic, division may merely fragment continuous reasoning. On a small task, coordination may cost more than implementation.
6291	2. Estimate speedup from the critical path, not agent count
25639	Let p be the parallelizable share of work. With N executors, the ideal speedup bound is approximately
29466	; coordination, communication, duplication and merging make actual speed lower. This applies an Amdahl-style derivation, not a model experiment result.
11997	For two independently modified modules followed by integration, ideal time is the larger duration plus integration, not their sum. If the second needs an interface established by the first, a dependency edge prevents true parallelism. A task DAG should represent output dependencies, not mechanically impose three fixed layers of "analysis/implementation/review".
13055	Shared rate limits also break ideal parallelism. Four agents calling one external API may rate-limit each other; with a fixed token budget, more concurrency also reduces evidence available per task. Evaluate the complete task's wall-clock time and total resources rather than one fast subtask.

6423	3. What a delegation contract needs
16366	Delegation instructions need at least a goal, scope, current facts, necessary constraints, available tools, expected return form and completion conditions. Supply enough information without copying the whole main conversation. Mark important assumptions as unverified rather than teaching them to every sub-agent as facts.
27140	Returns should distinguish conclusions, evidence locations, actions taken and unresolved issues. A main agent receiving only polished summaries without original sources cannot judge conflicts or recheck them. For precise code, read the current version identified by the sub-agent rather than having it manually rewrite potentially incorrect source in its summary.
10740	Harnesses inherit context differently: some use independent context, others fork. Product configuration also determines tools and permissions. Verify the harness mechanism first; an abstract "inherits all permissions" statement in a skill does not implement it.

6540	4. Concurrent file access and integration boundaries
17557	For independent writes, branches or worktrees reduce direct overwrites but do not eliminate semantic conflicts. Separately passing patches may change shared interfaces, dependency versions or configuration behavior after merging. Reverify the current merged artifact rather than reusing green results from each branch.
17297	For changes to the same file, define ownership boundaries or serialize critical parts first. Content hashes/CAS prevent overwrites, but a human or agent must still understand conflicts after failure rather than automatically choose the last writer. Some tasks suit research-only sub-agents with centralized implementation by the main agent, reducing concurrent-write conflicts.
16336	If sub-agents can edit tests, the main agent must detect weakened tests. Verification resources need explicit ownership; high-risk acceptance can run outside the workspace or in a restricted environment. Before treating "all tests are green" as a result, confirm the tests still verify the original requirements.
6649	5. Independent reviews do not imply independent errors
15435	The same model, prompt and context can share incorrect premises. Showing the implementer's explanation first anchors the reviewer to its conclusion. Independent review can examine original requirements, the current diff and tests before implementation reasons, but adds reading cost and should be reserved for worthwhile tasks.
16231	Majority voting offers expected benefits only when errors are sufficiently independent and the voting target identifiable. If every agent trusts stale API documentation, voting cannot recover facts. Independent evidence, such as reading the current interface or running tests, may help more than adding a fifth identical reviewer.
17630	Fix and verify small issues within the current review rather than restarting analysis, design and review from the beginning. Return to design for changed goals or disruptive architecture decisions. Let risk, not ritual, drive the process.
6714	6. Cancellation, failure and partial completion
10281	One failed subtask need not invalidate everything. The main agent should know which artifacts are reusable and which depend on failed results. Tool actions may remain in flight after cancellation; wait for a confirmable terminal state or record unknown. Do not delete subtask logs to pretend nothing happened.
17576	For timeouts, read persisted evidence first to avoid redoing work; for loops without progress, change task boundaries or narrow the problem. Restarting an agent with the full history may merely repeat the same failure. Recovery should match error types rather than always say "try again".
6776	7. When not to split the task
23088	A clear goal, small change, concentrated evidence and cheap verification often need only one agent. Cross-language work, independent modules or broad research with independently checkable results may benefit more from parallelism. Actual dependencies and risk should support this judgment; every task does not need a complexity score.
29075	Acceptance question: four research agents produce four different conclusions. Should their views be averaged in a summary? No. Compare provenance, time, scope and evidence quality first; some differences reflect conditions and others real contradictions. Integration adjudicates evidence rather than compromising on wording.

23115	Goal: make code quality testable rather than asking the model to "act like a senior engineer". Experiment: actual file changes in Lesson 65, 8 functional tests and rejection of stale verification.
16288	Contracts express observable behavior, counterexamples expose errors, tests bind to versions, and review addresses risks tests miss.
6029	1. Define behavior before choosing a process
10259	Task success first depends on user needs, existing system constraints and behavior that must stay unchanged. For exclude, specify path bases, directory-rule matching, wildcard support, case sensitivity and separator semantics. Without a clear contract, AI-generated tests merely confirm the model's guesses.
10785	A simple change needs no pages of formal specifications, but ambiguities affecting results should be removed. Two or three executable examples often suffice; complex compatibility migrations need finer input, state and error semantics. Actual risk determines design depth.
17883	Engineering environments should also make builds, tests and architecture boundaries easy for agents to find. OpenAI's harness-engineering article emphasizes repository workflows with knowledge and verifiable constraints; SWE-agent research shows operating interfaces affect coding results. Neither implies buying a large orchestration platform.
6290	2. The testing pyramid and target errors
14124	Unit tests quickly locate local logic; integration tests check module boundaries, real storage and protocols; end-to-end tests verify user flows but are usually costlier and more environment-sensitive. Test combinations should cover risks, not a fixed numerical ratio.
12329	For example, testing only that
25214	is excluded does not catch incorrect basename handling of
23027	. Counterexamples need same-named files at different paths, directory boundaries, Windows separators, empty rules and parent traversal. Each assertion should match a contract or failure hypothesis rather than produce many duplicate happy paths.
22422	Record test commands, exit codes, test counts, skipped items and environments. Zero exit status with no tests discovered is not a functional pass; skipping critical tests for missing dependencies cannot be summarized as "all passed".
6427	3. Property-based and metamorphic testing
20609	Some behavior suits invariance checks: separator normalization preserves results; adding unrelated rules when none match preserves results; KV cache chunking preserves logits; changing the authorized user prevents reuse of someone else's cached results.
14934	Without complete expected answers, metamorphic testing derives output relationships through input transformations. It supplements example tests, but the relationship must be correct. "Adding any exclusion rule should preserve results" is false, because a matching rule should change them. Do not treat invented patterns as truths.
20012	Numerical implementations suit finite differences, conserved quantities, symmetry and high-precision baselines; agent flows suit fault injection, permission boundaries and version conflicts. Handing everything to LLM graders loses strong evidence available from deterministic mechanisms.
6522	4. Mutation: prove the tests really catch errors
18793	Remove a causal mask, reset RoPE positions, remove user identity from a cache key or make finish ignore versions, then rerun tests. Corresponding failures show sensitivity to the target errors. If deliberately introduced bugs leave everything green, tests cover lines but not semantics.
7948	Mutation scores alone cannot represent quality. Many mechanical mutations have no business meaning, and some equivalent transformations should not fail tests. Negative controls designed for real failure modes matter more than blindly trying to kill every mutation.
18372	Snapshot tests suit stable output contracts, but fixed hashes for natural-language descriptions, entire skills or unrelated formatting turn reasonable edits into regression noise. Bind tests to behavior that must remain, not the exact shape of a whole text.
6630	5. How review avoids an endless loop
7687	Google's review standard emphasizes improving overall code health rather than endless perfection. Reviews can focus on design, functionality, complexity, tests and readability; fix and reverify small issues directly instead of restarting design every time.
12090	Prioritize high-consequence issues: incorrect writes, races, transaction boundaries, broken compatibility, expanded permissions and weakened tests. Let existing project tools handle style where possible. Naming preferences must not obscure functional defects, and "not a major issue" must not dismiss real risk.
22665	Independent review suits complex or high-risk changes; simple configuration changes may need only focused tests. Compare review costs with the defects, rework and incidents avoided. Simplify a process that only lengthens tasks without observable gains.
6733	6. Verification freshness and artifact ownership
22458	Passing tests must match current code. Changing files afterward does not automatically preserve old results' validity. This book detects changes through file-version hashes; larger systems may reuse results by dependency scope, but need reliable dependencies and build caches. A model deciding "it is only a small change" cannot justify skipping necessary verification.
27174	Also protect uncommitted user changes, inspect the current diff scope, and identify generated files, lockfiles and configuration changes. A model may fix one issue while deleting intentionally retained code; check the final report against the actual diff rather than listing files from chat memory.
28400	Deployment is a separate action. Local test passes do not mean code is live; merging a PR does not establish production health; rollback viability depends on migrations and external side effects. State each stage's actual completion without inventing production verification.
6773	7. A concise but sufficient delivery
13534	Include what behavior changed, why it was needed, main impact scope, verification run and remaining limits. Complex tasks can add key decision reasons; simple tasks need not fill templates. If evidence is insufficient, identify the exact gap rather than end with a vague "further testing recommended".
29078	Acceptance question: a model patch passes every existing test but misses the user's new requirement. Where does responsibility lie? The tests omit the new contract and cannot replace requirements acceptance. Add tests for the new behavior and verify old behavior remains. AI engineering quality is still software engineering quality first.
