10525	Three kinds of failure should stay in different layers
12140	A transport failure</strong> means the request or the response may not have arrived; <strong>a JSON-RPC protocol error</strong> points to a problem with the request format, the method or protocol handling; <strong>isError in a tool result</strong> says the tool's business execution went wrong. 28007	Follow-up: the server says the tool is read-only. Can that be trusted as it stands?
15021	Only a trusted service and a reviewed implementation can support that kind of security judgement. An annotation or a description is metadata, not a sandbox. 27958	Follow-up: should every tool failure be returned to the model?
15182	Actionable business feedback should be returned; sensitive stack traces, credentials and attack payloads should not be exposed as they are. 27770	Follow-up: why can it not fall back automatically to a tool with more permission?
15712	Because the failure may be exactly the authorization boundary. Switching to a full-permission shell to reach the database after a restricted query is refused, for instance, goes around the user's authorization. A fallback should stay within equal or smaller permission; widening permission is a new decision, not ordinary fault tolerance.

12740	Define identity, audience and permission scope first
26093	Identity answers "who is calling", audience answers "which service the token is to be used by", and scope answers "which operations are allowed". A session_id is usually only used to correlate a session and cannot automatically prove any of the three. The MCP security guidance discusses risks such as token passthrough, the confused deputy and session hijacking explicitly.
27385	The confused deputy here can be read as "a deputy that has permission is led into exceeding its authority on someone else's behalf". Even if the user grants the deputy only read permission, a deputy that uses its own high-permission token to carry out whatever the model proposes may still cross the user's authorization boundary.
