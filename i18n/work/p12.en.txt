18369	Forgetting is a chain of propagation, not the deletion of one row
10343	One document can give rise to chunks, summaries, retrieval vectors, answer caches and long-term experience. Once the original is withdrawn or the user's permission is revoked, deleting only the document row still leaves the other derivatives able to feed the original content back into the model. This risk comes from data dependency; tool boundaries such as MCP also require identity and resource access to be handled continuously, not checked only on the first read.
21056	This section uses an independent teaching dependency graph: doc→chunk→summary→answer_cache and memory. Once doc is revoked, all five classes of object are marked invalid along the dependency closure. The local program's verification result contains five nodes. 15345	Revoking availability and deleting physically are not one step
22623	Physical deletion may complete asynchronously; until it does, revoked material must at least be kept from taking any further part in retrieval, cache hits and memory construction. If you rely only on a TTL cleanup once a day, there is still a window between the revocation and the cleanup. The read path should check the validity of the source or the permission version, rather than trusting that the derived record was authorized when it was created.
14830	Conversely, deleting every similar memory can also catch independent legitimate sources by mistake. The set of sources has to be kept: when a fact is supported by two independently permitted sources, whether it remains usable after one source is withdrawn is decided by the policy and the relation between the facts. Do not treat all similar text as coming from the same place.

8152	Q021｜Which stages does a skill pass through, from existing on disk to really affecting the output?
27439	What to know first for this question</span>Discovering a skill relies on metadata, loading the body makes it usable by the model, and running its resources is another layer of action again. A directory existing is no proof that it was loaded this turn.
24944	There are at least discovery, candidate selection, body loading, resource acquisition, actual execution and verification. A file existing does not mean it was discovered; a description matching does not mean the body was read; the body being read does not mean the key step was executed. Use this chain to explain "the skill had no effect", instead of guessing from the result alone.
22018	Every stage can fail on its own
14856	The discovery stage scans the supported directories and parses the metadata. An unsupported path or a malformed format makes the skill completely invisible. At the selection stage the model sees the name and the description and decides whether it is relevant to the current task; too broad a description can be selected wrongly, too narrow a one can be missed. The loading stage reads the body; if the file is too long, a reference is broken or the context is trimmed, the content actually in effect may be incomplete.
18619	The execution stage needs tools, permissions and current evidence. A database-performance
25239	asks for a query execution plan, but when the sub-
22153	has no database tool, the key step cannot be completed. The verification stage checks whether the final code or analysis reflects the relevant constraints, rather than requiring the skill's name to appear in the answer.
15743	A routing log can therefore record "which candidates were found, which one was chosen, what was read, what was executed, and why it stopped". This need not expose the full internal chain of thought; recording the observable actions and the grounds for them is enough.
10247	How a skill gets from a file on disk into the current action

12050	The task is a pytest assertion failure
12505	The candidate is relevant; if the task were fixing a typo in the documentation, it should not be forced in.
21822	Body loading
25880	Read the execution steps and the material they need
11803	This moves from "knowing the name" to "knowing the method".
24783	Capability check
22764	The environment has no pytest, or is read-only
25934	Adjust the verification plan and state the gap, rather than claiming it has been run.
24463	Accepting the result
22454	The test run matches the version as currently modified
8889	A skill having been read is no proof the task is done.
19079	Join the steps up.</strong> A skill's life cycle comes down in the end to real actions and evidence, not to an "already loaded" label.
26681	Limits and counterexamples.</strong> How discovery and automatic matching actually work is up to the product; this example follows the open skill organization concept and does not guarantee that every tool runs the same process automatically.
27807	Follow-up: why is having the model declare "I used skill X" in its answer not a good evaluation?
16463	It may declare it without executing it, and it may execute it without mentioning the name. Look at what was actually read, which tools were called and how the artifact behaves. 28049	Follow-up: what hidden costs does progressive loading have?
29028	Extra rounds of discovery and reading, wrong selections, context switching and broken references. For a short rule needed almost every time, loading it by default may be cheaper. 27720	Follow-up: once a skill's script has run successfully, does that mean the skill is done?
10633	No. The script may only produce candidates or intermediate files; the task still needs the result explained, its applicability verified, errors handled and the work delivered. Mechanical execution succeeding has to be told apart from the user's goal being met.

18722	Breaking "in effect" into five observable gates
20088	File exists → host discovers it → selected this turn → body and resources loaded → the key process actually executed. Every gate can fail. The skill description affects discovery and selection, but it cannot fix a path that is not scanned, an invalid file format, a sub-agent that was not preloaded, or insufficient tool permissions. Claude Code's documentation on skills and sub-agents reflects these different life cycles.
19975	In the teaching state exists and discovered are True, while selected, body_loaded and used are False. Recording only "the skill was discovered" mistakes the first half of the process for success. At that point routing is worth studying; if discovered is itself False, work through the files and the configuration first, and do not rewrite the trigger wording.
7746	JIT saves tokens only if the supplementary information really arrives in time
22507	Progressive loading means giving the metadata first and reading the body and resources when they are needed. Too broad a description triggers wrongly, too narrow a one fails to trigger; and too long a body may be trimmed or may swamp the task. The most useful record is not how many tokens were loaded, but whether the steps a key task needs really entered the context and were executed.
17729	Tools have a similar layering: registration, exposure, reachability and dispatch in the pinned Codex source are not one object.
5797	When a skill requires a tool but the sub-agent does not have that ability, enriching the skill's content further will not create the ability to execute.
25775	How to construct a routing regression set
19855	Collect real tasks that should trigger it, tasks that are close but should not, tasks that name it explicitly, and combined tasks. For each one, note "what specifically goes wrong if it is not loaded" and "what it costs if it is". Do not use loading everything for every task as a high-recall approach, or the test will only reward redundancy.
15474	Test the hidden dependencies at the same time: if the main agent selected the skill, does the sub-agent get the body it needs when it executes; do the resources' relative paths resolve against the right directory; does a change of description affect other skills of the same kind. What is being judged is the final task's quality and cost, not the accuracy of a static classification.
27969	Follow-up: does writing a required step into a skill make it enforced?
10955	No. A skill is guidance and resources supplied to the model; it is not a runtime constraint. If a step touches a security boundary or a deterministic acceptance condition, it should be realized by a program check or wrapped in a tool; not every recommendation has to be raised to a mandatory gate.
28022	Follow-up: now that the model is stronger, should an old skill be kept?
22981	Run an ablation test on real tasks. If the success rate does not drop and the time goes down once it is removed, it may be an outdated patch; if a particular boundary clearly regresses, keep the part that covers it. A skill does not grow more expert by piling up; it should maintain a gain that can be demonstrated.
7527	E37: how to read this result, instead of only looking at "passed"
28261	Read exists, discovered, selected and body_loaded one by one. The first boundary where true turns to false is usually worth fixing before rewriting the skill body again and again.
24876	Self-check:</strong> the skill file exists and was scanned, but the subtask did not carry out the test steps in it. What should the first reaction be?
12822	Check the selection, the body loading, the sub-agent's context and the tool permissions first, to establish which gate it broke at; you cannot put it down to a weak description straight away, and you cannot take "it was discovered" for "it was executed".
12922	Walk one concrete chain first
11916	The repository has
29168	, and that does not mean the review task has used it. It has to be discovered by the directory; the description has to match the task; the full instructions have to be read; the scripts or reference material have to be fetched as needed; and in the end the action has to follow them and get the right result. The first four steps are only conditions; it is the fifth that comes close to effective application.
22510	The point of progressive disclosure is to let the default context carry only the discovery information that is needed, rather than load every rule unconditionally. Anthropic's Skills design layers metadata, body and on-demand resources; it does not guarantee that routing never errs, and it does not turn documentation into permission.
15759	The pinned loading site in Codex
16134	handles explicit mentions, the snapshot of the skills directory, dependencies, warnings and the fragments to be injected; it also de-duplicates paths already injected. 19733	How to test the boundaries of a description
19973	Three classes of teaching sample: renaming one variable, which should not load a large architecture review; migrating a protocol across modules, which should load the relevant expert checks; and a user naming a particular skill, which should be handled by the product's semantics while still bounded by permissions. When comparing an old description with a new one, keep the tasks, the model, the tools and the other rules the same.
25564	Record the recall of the skills that were needed, the unnecessary loads, the extra tokens, task success and rework. Proving only that "20% fewer skills were loaded" does not establish an optimization, because essential knowledge may have been missed as well. Conversely, loading every skill for every task has high recall but may add conflict and interference.
11724	What belongs in a skill
23494	A stable, reusable procedure, how to use a tool, and acceptance criteria can go in; this file version, one lucky success and a deployment address that has expired belong in the task's evidence or in memory with a life cycle. A skill itself should have limits of application and failure examples, rather than accumulating more and more "must", "always" and "under all circumstances".
11271	Expertise still depends on the model's understanding, the quality of the material and execution feedback. A skill is not independent model training; do not describe "the documentation was loaded" as the parameters having learned a new ability.
18686	A skill body's lifetime is not the same as a tool permission's lifetime
7242	The documentation read for Claude Code distinguishes keeping the body from allowed-tools being a temporary permission: the body having entered the context does not mean the tool permission continues indefinitely. Whether it appears in the menu, whether the model can trigger it itself, and whether a sub-agent preloads it are governed by different fields too, and cannot be replaced by a single "enabled" boolean.
7276	Codex's explicit skill path reads the snapshot, handles MCP dependencies, obtains body fragments and warnings, and de-duplicates against paths already injected; the parent conversation in an isolated review is evidence, and should not be reinterpreted as this turn's user asking for a skill to be installed or invoked. This is the specific path of the function that was read; it does not cover every implicit skill-selection strategy.
19974	The teaching check uses two moments: at t0 the skill is read and this turn's permission obtained; at t1 a new user message begins. The body can still be cited, while the temporary permission may already have ended; before executing again you have to judge afresh by the current policy, and "I learned it earlier" does not entail "I am permitted to execute now".
8155	Q022｜How do you write a routing description that neither misses a borderline task nor triggers too often?
27460	What to know first for this question</span>A description has to state the tasks it suits and its boundaries; too broad and it loads wrongly, too narrow and the expertise is missed. Test it with positive, negative and borderline examples.
23659	Lesson 17 · From search results to a trustworthy answer</a><a class="pill" href="../foundations/32.html">Lesson 13 · Skills, routing and multi-agent</a><a class="pill" href="../foundations/35.html">Lesson 05 · The denominator of an evaluation metric
19730	A description should state a clear task intent, what it applies to and the key boundaries, and avoid merely piling up technical nouns or extending its range without limit. Routing quality comes from validating positive, negative and borderline examples against a real task distribution, not from copy that looks comprehensive.
23236	Look at an example that is easy to route wrongly
9474	"For all storage, database, cache, file, performance, security and architecture tasks" covers far too much: almost any backend change would trigger it. Conversely, "use only when the user explicitly says to optimize an SQL index" may miss the natural phrasing "the endpoint query is too slow, help me track it down".
20507	A more useful description can be built around intent: "use when the task needs analysis of database query plans, index choice, transaction isolation or persistence consistency; ordinary file reads and writes, and renaming a field with no database semantics, usually do not need it." This is still an example, not generally optimal wording. Let the boundary of expertise be corrected by actual evidence: a task looks simple at first, reading the code reveals that transactions are involved, and the expert skill is then escalated.
25730	An evaluation set includes clear positive examples, clear negative examples and blurred boundaries. Beyond whether the selection is right, look at what specific error a missed selection causes and at how much a wrong selection adds in extra
15620	and process steps. A case where something loads by mistake but does not affect the output differs in risk from one where transaction consistency is missed and a charge is taken twice.
9448	How a description saying "applies to all development tasks" leads to wrong loading
26224	Input and conditions.</strong> Candidate A is described as "improves engineering quality, suits all code tasks"; B as "analyzes concurrent shared state, races and lock ordering".
12023	Task 1
19858	Fix a spelling mistake in the README
7037	A matches it loosely all too easily; B is irrelevant.
12024	Task 2
12215	Concurrent balance deductions produce a negative number
7138	B is clearly relevant.
12025	Task 3
20170	Add a test for an ordinary pure function
25972	Being quality-related is not the same as having to load concurrency analysis.
19852	Tighten A's specific triggers and its non-applicable examples
10896	This is not compressing the description into an opaque abbreviation.
22915	Use the two metrics of necessary recall and unnecessary loading
14958	Reducing the amount loaded alone may also miss the tasks B should trigger on.
19228	Join the steps up.</strong> The boundary of a routing description needs positive examples and adjacent negative ones, not a heap of adjectives like "expert", "comprehensive" and "best".
26720	Limits and counterexamples.</strong> A teaching example cannot establish a real LLM's selection probabilities; those need measuring with the target model and a fixed task set.
27996	Follow-up: are a lot of hard classification levels needed?
10642	Not necessarily. You can keep the principle of "do the simple thing directly, and go deeper when the evidence shows it is complex", letting the model judge on the strength of evidence. Hard classification is worth adding only when a predictable error keeps recurring and there really is a gain; otherwise it may force open-ended tasks into boxes that do not fit.
27889	Follow-up: when several skills overlap, should they all be loaded?
12867	Establish the main problem and the expert boundaries actually needed first. An overlap may call for a combination, or it may just be a repeated description. After loading, check for conflicting instructions and duplicated work. If both skills demand a full independent analysis and review, stacking them directly may double the task's cost without producing new evidence.
27832	Follow-up: how do you prove that changing a description has not lowered expert recall?
15916	Compare the old and the new version on a fixed task set, looking above all at whether tasks that used to hit are now lost, and add real false-trigger negatives at the same time. Do not only verify that "the earlier wrong load has gone", or you may gain a false improvement in precision by writing the description extremely narrowly.
8158	Q023｜What should a skill, an instruction, a hook, a tool and an agent each be responsible for?
27457	What to know first for this question</span>An instruction guides behavior, a Skill makes a procedure reusable, a tool performs the action, and a Hook runs a program at a given point. State the actual shortcoming before choosing a mechanism.
23526	Lesson 01 · An agent is not another neural network</a><a class="pill" href="../foundations/25.html">Lesson 08 · Tools and MCP</a><a class="pill" href="../foundations/32.html">Lesson 13 · Skills, routing and multi-agent</a><a class="pill" href="../foundations/34.html">Lesson 04 · Foundations of engineering quality
7742	Instruction expresses a standing constraint; Skill supplies an expert method on demand; Tool performs a concrete action;␣
15971	runs programmatic logic at a fixed point; Agent carries an independent task's execution and its own context. Choose the mechanism by responsibility, and avoid writing the same logic out five times.
10332	Where a verification requirement belongs
9447	"All code follows the project format" can be stated in the project instructions; "when there is a database migration, check rollback and compatibility" can be a skill; "run the migration checker" is a tool; "run the deterministic format check automatically before a commit" can be carried out by a suitable hook/
18620	; "review the migration plan independently" can be delegated to an agent when the risk warrants it.
24928	Natural language suits open-ended judgment, and a deterministic program suits conditions that can be checked mechanically. Whether a file exists, whether a
20382	is valid, whether a command's exit code is zero: none of these need the model to guess. The model is good at judging which tests are relevant and whether the evidence supports a root cause, but the conclusion should still be bound by the facts the tools give.
18679	A skill citing a resource has to be sure the relative path, the version and the permissions are available. A tool permission cannot be extended because a skill's body says "access allowed". Nor is a hook safe by nature: the script it runs may hold the process's permissions, and needs the same review.
18462	To enforce a format check, write it into the prompt or use a hook?
26460	Input and conditions.</strong> The rule is that a format check has to run before a commit; the task also needs expert Python advice and a file-reading tool.
20457	An ordinary instruction
15551	State the constraint and the goal to the model
21749	The model can understand it, but that is no guarantee of deterministic execution.
19741	Supplies an expert procedure for handling Python problems
14970	Loaded only on relevant tasks.
19742	Supplies the actual ability to execute format_check()
25943	Calling it produces an exit code and a log.
7712	A hook or a fixed procedure
15934	Trigger the check deterministically before the commit event
17520	Better suited to a mechanical step that has to happen.
15921	Decide, on failure, which files to check, what to change and whether to retry
25959	It handles the dynamic action; it does not replace the format tool itself.
19252	Join the steps up.</strong> Choose a mechanism by what it carries: explanation, method, action, enforced timing or dynamic decision.
26642	Limits and counterexamples.</strong> Which events a hook can use, and whether it can block, depend on the product; do not assume that any given CLI offers the same abilities.
27762	Follow-up: why not put every check into a hook and enforce it?
29016	A frequent, expensive full check can slow a simple task down, and some checks need business judgment rather than a fixed script. A hook suits a cheap, deterministic, critical mechanical boundary. A risk-driven deep review should not be replaced by a fixed trigger frequency.
27719	Follow-up: can a skill be reused independently of a particular framework?
15128	You can write the domain principles, the operating steps and the resources as platform-independent content as far as possible, and then provide a light adapter for a specific tool. 27824	Follow-up: when does it need splitting into a separate agent?
12053	When the task has its own context, goals that can run in parallel, or genuine value in independent review; merely being long to explain does not necessarily need a sub-agent. 8163	Q024｜How does multi-model routing optimize cost without sacrificing quality? And why can a model not be chosen on prompt length alone?
27472	What to know first for this question</span>Model routing goes by task difficulty, risk and the measured cost per success; it does not fix strong and weak by a label for good. Escalating and downgrading both need evidence.

Prompt length only reflects the size of the input; it cannot stand for reasoning complexity. The goal is the cost per successful task under a quality constraint, not the cheapest single call.

12776	Write the cost per successful task out first
