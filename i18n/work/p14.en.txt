17600	Taking "add an exclude feature" apart into semantics you can check
25234	The base directory the rules are relative to, the semantics of wildcards, the behavior of an empty rule, the relationship between directories and files, case and separators, the handling of invalid input, and the precedence of the existing include rules all have to be stated. 12314	For instance, define it as: with no exclude configured the behavior does not change; a matching path does not enter the output; a non-matching path keeps its original order; the same input and configuration give a determinate output. 16909	Before implementing, run a case against the current code that ought to fail, to prove the gap in the requirement; after implementing, the same case should pass, and the adjacent regressions are then filled in. 7942	Mocks make tests fast and determinate and suit isolating local behavior; a real integration verifies the protocol, the configuration and the boundaries. Mock everything and you may miss the actual

22455	The set of tests selected, the environment they ran in, the version of the code under test, and an explicit acceptance predicate. 22440	Be especially careful when the tests themselves have been modified

27933	Follow-up: is it only professional if every test is run?
10643	Not necessarily. You can start with the smallest failing case and the affected regressions, then widen by risk. What matters is explaining what is covered and what is left out, not pretending that a limited set of tests amounts to proof about the whole system. A high-risk change across modules needs wider verification; a simple wording or configuration change need not mechanically trigger the expensive full chain.
28033	Follow-up: the model says it ran, but the log is gone — what then?
22644	The status should be "cannot be verified", not a pass by default. Do not make up a test output to round the report off: a delivery fact has to come from an actual execution.

8115	Q007｜When is a review worth it? How do you avoid an endless analysis—review—redesign loop?
27410	What to know first for this question</span> A review should examine the real risks and the current diff; a small problem can be fixed directly and verification added. Repeating a fixed round of analysis is not the same as improving quality.
8745	A review should find the important problems the implementer or the automated tests may have missed, and choose its depth by risk and evidence. A small local problem can be fixed and verified directly; only overturning a key design or widening the scope of impact calls for fresh analysis. The goal is better code health, not perfection in every detail.
19495	Choose the kind of review by the consequences of an error
10355	For a local change to a piece of wording or a private function, compilation and a targeted test may already be enough. A cross-module interface, concurrency, a data migration, permissions and an irreversible deployment are worth checking for invariants, compatibility and recovery. An independent reviewer is best given an explicit task — look for regressions in old callers, or for a race — rather than finding fault in general.
24965	If the review finds an unclear variable name or one missing boundary test, correcting it within the current task is enough. If it finds a mistaken architectural assumption, or a data model that cannot express the requirement, then go back to the design. Turning every low-risk comment into a new Analysis task creates communication cost and repeated context.
18064	Blocking problems should be separated from suggestions, but there is no need for an elaborate system of levels. Stating clearly what the problem will cause, what the evidence is and what the smallest fix would be is more useful than assigning an abstract risk score.
15493	Both change one line — so why does the review effort differ

27711	Follow-up: may a reviewer modify the code?
15152	Yes, as long as the task's authorization and the tools allow it and the change and its verification are recorded. The roles are separated to get an independent view, not to forbid fixing things. Correcting a clear small problem during the review is often more efficient; a major change still has to be coordinated with the main task, so that the direction is not quietly altered.
27892	Follow-up: do more rounds of review necessarily make things more reliable?
26849	The marginal gain usually depends on new evidence and a new point of view. Repeating the same check may produce nothing but arguments about style, and may introduce new errors. Watch the defects actually caught in the past and the cost of rework, and set an explicit stopping condition.
27943	Follow-up: how do you review for "over-engineering"?
28691	Ask of every new abstraction, rule, state or service: which concrete error does it prevent; what would happen without it; is there a simpler implementation; is its cost proportionate to the risk. A pattern being common is no reason to assume it must be used, and the pursuit of simplicity is no reason to delete a safety boundary that is genuinely needed.
