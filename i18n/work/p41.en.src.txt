6525	4. run_turn：一个用户轮次可以包含多次模型调用
25769	该函数先检查输入与上下文用量，必要时触发压缩，读取技能相关信息，记录用户输入和技能注入项目，然后进入模型调用循环。循环中还会处理运行期间追加的用户输入，基于当前历史构造本轮提示，并根据是否需要后续行动决定继续或结束。
11862	从工程角度看，用户的一次“修复问题”不是单次HTTP调用。工具输出、运行中追加约束、压缩后的历史都可能改变下一次输入。做性能统计时应以完整用户任务为顶层，不能只统计第一轮模型调用。
19284	把这段机制用于排障：若技能刚开始加载过，但后续未生效，需要看之后的历史是否保留、是否压缩、是否进入子Agent、是否被新证据覆盖。不能凭开头日志证明整个长任务一直保留完整技能内容。

27392	这里要谨慎：另有官方Compaction接口能返回不透明压缩项目；本地可读摘要与服务端不透明状态不是同一个实现。不能据一份旧源码宣称“Codex一定只把历史变成一段普通文字”。也不能因服务返回加密项目就断言“语义完全无损”。其内部表示未公开，业务保真仍要用后续任务验证。
22529	源码注释与代码行为发生张力时，应优先描述实际操作并保留疑问。例如删除历史开头项目如何影响前缀缓存，需要根据真实请求重算可复用前缀，不能只照抄“为了缓存”的注释便当成普遍结论。资深源码阅读包括验证注释，而不是把注释视为算法证明。

6047	1. 比较对象必须先明确
7235	Claude Code CLI、IDE中的聊天、Copilot CLI、GitHub托管编码Agent，并非同一个运行环境。某项工具、Skill、记忆或MCP功能在一个产品面可用，不能自动推到另一个。比较模型能力时，还要控制实际模型、可用工具、网络、仓库索引、权限和执行环境，否则观察到的是整套系统差异。
16881	官方文档公开了Claude Code的循环、上下文构成、自动清理与压缩、子Agent和记忆机制；Copilot CLI自定义Agent文档公开了profile与工具配置。两者并未提供所有内部Prompt和服务实现。对未公开部分，应写“未公开/未测”，而不是根据一次输出猜出固定算法。
6277	2. 上下文不是只有聊天记录
7237	Claude Code公开说明其上下文包含会话、工具结果、项目指令、记忆和按需加载内容，并存在清理旧工具输出与会话压缩机制。技能可先加载描述、使用时再读取内容。工具定义的发现方式也可能随产品实现变化，不能把一个旧版本的工具Token成本当作恒定值。
17809	工程上要区分“文件已存在于项目”“工具已经读过”“目前仍在模型上下文”“被保存在外部记忆”四种状态。一个大文件先被读过，经过压缩后可能只剩摘要；后续需要精确代码时，应重新读取原始位置，而不是要求模型凭摘要恢复源码。
17303	对多目录仓库，还应检查规则加载作用域。自动记忆与人工维护的项目指令具有不同生命周期，不能因为名字都含memory就视为同一权威。当前源码和用户明确要求应能纠正过期经验，而不是被历史摘要永久压住。
6424	3. 子Agent不应被笼统描述为“完整继承”或“完全空白”
7245	Claude Code文档描述独立子上下文，也存在fork当前会话的方式；委派模式不同，初始上下文不同。主Agent最终得到什么返回内容、工具调用是否留在子上下文、技能是否预加载，都需要按具体配置核实。
7302	Copilot CLI的自定义profile包含描述、提示、可选工具列表和MCP配置；文档说明未限定工具时可以访问可用工具集合。但“可用工具”仍受宿主配置、连接和权限影响，不代表系统里任何MCP服务都自动登录可用。
11861	从工程角度可拆成三层：工具发现决定看见哪些名称，Agent配置决定允许请求哪些工具，执行权限决定一次具体调用能否成功。模型选中工具是第四层。只修其中一层不能保证最终调用发生。

6527	4. 一套低成本、可复查的宿主行为探针
20839	本书没有在用户本机运行Codex、Claude或Copilot。下面是读者可自行执行的实验设计，不能当成已测结果：建立无秘密的样例仓库，根目录和子目录分别放一条无害、可辨认的规则；用同一简单任务在不同cwd启动；记录版本、加载提示与输出。然后显式调用一个只读自定义Agent，比较它能看到的工具和规则。
19559	探针不应让模型仅回答“我已经加载了技能”。应设置必须使用该规则才能满足的可验证结果，例如生成一个规定键名的JSON，但同时避免把该键名直接泄露到用户任务中。即使结果符合，也只能作为间接证据；若宿主支持加载日志或上下文显示，应结合更直接证据。
14203	压缩探针可以在长任务早期设置明确约束，中间加入正常工作记录，触发受支持的压缩，再让Agent继续一个依赖该约束的任务。还要保留未压缩对照、不同位置与重复试验。单次回忆成功不等于任何长任务都安全。
6643	5. 权限与检查点的误区
10335	一些工具提供文件编辑回退或会话恢复，但不应推断它能撤销外部邮件、远程部署或数据库写入。文件checkpoint、会话历史、执行日志与远程世界是不同状态空间。第63课的unknown状态在真实产品里同样需要考虑。
28465	配置“只读审查”也要检查工具能力。如果审查Agent能执行任意Shell，实际权限可能超过文字描述。应由执行器限制，而不是只写一句“不修改文件”。另一方面，不必对每次正常读文件都要求人工批准；用边界清晰的沙箱可以减少审批疲劳。
6732	6. 面向rd-skills这类扩展层的最佳取舍
18630	扩展层应该增加宿主欠缺的专业知识与准确路由，而不是重复实现宿主已有的会话、工具、持久化和权限系统。先确认具体失败发生在skill描述、加载边界、专业内容、返回证据还是宿主自身。若正确技能已可见但内容泛泛，继续优化router不会解决专业质量问题。
10333	一个高价值改动的例子：某技能在明确不相关任务误加载，添加适用边界及反例，并在误加载与必须加载任务上共同验证。一个低价值改动的例子：因为担心任何任务遗漏，默认加载所有专业资料，再额外建立多个路由Agent审查。后者同时增加上下文、延迟与冲突，必须有非常明确的实测收益才能成立。
6787	7. 比较结论应该如何书写

6046	1. 每轮输入都应有一个明确目的
6962	Agent不需要一次性知道整个仓库，而需要足够的信息选择下一步可靠行动。一个调试轮次可能只需入口、候选分支、相关测试和当前约束；实施轮次需要精确代码范围；验证轮次需要当前diff与验收标准。阶段变化，信息需求也变化。
10573	上下文管线可分为：获得候选信息，验证来源与权限，判断适用范围与新鲜度，去重，选择必要依赖，分配预算，序列化并记录来源。不要把所有步骤都交给一个“总结一下”的Prompt，否则无法区分检索漏了、选择丢了还是压缩改错了。
14653	原始证据与指导规则也应分区。网页里写“忽略前面指令”，只是外部文本，不应在序列化后变成高优先级命令。权限和来源标签必须由宿主生成，而不是相信文档自报的“最高权威”。
6294	2. 预算模型与依赖闭包

10160	。没有这些约束，仅按“语义相关度/Token”排序可能留下无法理解的碎片。
12280	使用明确依赖闭包和价值密度启发式，不声称求出全局最优。必要项先保留；如果必要项本身超出预算，直接报错，而不是静默丢失硬约束。循环依赖、缺失依赖也显式失败。这些元数据检查可以确定性测试，但vi是教学输入，不是经实测校准的真实信息价值。

6426	3. 小而完整，比碎片多更重要
12330	例子：调用点显示
29249	，函数定义解释path相对仓库根，测试说明末尾斜杠代表目录。三个片段共同定义行为。只保留调用点会误判字符串处理；只保留测试名没有断言，也不足以知道契约。
9454	“最小充分证据”不是固定行数，而是足以回答当前决策的闭包。源码读取可先拿定义与关键调用，再扩展到异常处理和边界测试；每次扩展说明新增证据解决什么不确定性。这样避免无条件扫描，又不会把复杂任务压成片面片段。
28667	长文件截断时要显示是否截断、总范围与继续读取位置。返回100行却不告诉模型后面还有逻辑，会造成虚假的完整性。工具提供范围精确的继续读取，比让模型凭截断结果下结论更可控。
6543	4. 权威、新鲜度与适用范围不是一个分数
22937	用户明确要求、当前源码、官方接口文档、过往经验、模型假设有不同语义。不能简单给每条信息一个置信度再加权平均。例如过往经验再高分，也不能授权修改用户禁止的文件；旧版接口示例再相关，也不能覆盖当前版本的真实响应。
19706	推荐分开记录：来源类型、版本或读取时间、作用域、状态（观察/假设/已验证）、证据位置。选择时先施加硬约束，再在允许集合中考虑价值和成本。并非每次任务都要建数据库，简单结构化列表也能承担这件事。
12463	信息冲突应保留冲突及解决条件。两个文档描述相反，先看版本和适用产品面；无法判定时不应在摘要中融合成一个看似确定的结论。保留“不确定的具体是什么”，比写泛泛的免责声明更有用。
6627	5. JIT加载的收益与失败方式
18682	技能描述适合保持短而可判别，专业细节在确认相关后读取，资源按任务继续展开。这样减少默认上下文，但描述过窄会漏加载，过宽会误加载；延迟发现关键约束也可能导致返工。
15728	因此JIT的评价不是“加载Token减少”，而是必需能力召回、不必要加载、首次有效行动时间和最终工程结果。专业技能必须包含能改变动作的知识，如特定语言并发语义、存储事务边界、框架测试策略；泛泛要求“高质量、可维护”并不能替代专业内容。
11956	代码注入与工具权限也不同。加载一个含MCP说明的Skill，不会自动授予MCP连接。应分别验证内容路由与工具路由。把权限故障误判为JIT失败，会造成错误设计。

17298	对同一组任务比较全量默认加载、按需加载、按需加结构状态三种方案。固定模型、工具与测试；记录实际读取的文件、必需证据首次出现时间、重复读取、压缩次数、最终通过率。按任务类型分层，防止平均值掩盖复杂任务退化。
27157	还可以做移除实验：拿掉一份参考后结果不变，说明它在当前任务集中的边际贡献可能有限；但不能据此证明所有未来任务都不需要。新增内容应有明确失败样本，删除内容也应保留对应回归样本。

6032	1. 压缩是一种有损的信息转换
14488	原历史H包含目标、工具反馈、尝试、假设和已验证事实。压缩函数得到C(H)，之后模型依据压缩状态继续行动。真正关心的是对未来任务分布Q，使用C(H)是否增加决策错误，而不是摘要与原文的字面相似度。一个很短的摘要可能保留全部当前关键条件，一个很长的摘要也可能丢掉唯一重要的否定词。
6996	Anthropic的上下文工程讨论了压缩、笔记与子Agent；OpenAI文档还有不透明压缩状态。它们说明压缩形式不止普通摘要，但都不能据形式自动推断下游任务无损。
20865	本书采用一个工程性目标：优先保留会影响后续动作的约束、结论状态、证据入口和未完成项。它不是普适最优压缩算法，而是可以通过任务恢复实验检验的设计。
6285	2. 最危险的损失不是少几个背景细节
14695	原记录：“怀疑Skill未加载；但日志未检查，不能认定。”坏摘要：“Skill未加载导致故障。”这里把假设提升成事实，后续会围绕错误根因修改系统。
14694	原记录：“仅调整description，不改变技能内容，也不新增router。”坏摘要：“优化技能路由。”这里丢失负约束，任务可能被扩大。
14696	原记录：“测试在commit A通过，之后改过B文件。”坏摘要：“测试全部通过。”这里丢失证据新鲜度，导致虚假完成。
10528	三类错误分别是认识状态改变、作用范围扩大、证据版本丢失。不能只用关键词召回测试它们，因为坏摘要仍含有Skill、路由、测试等原词。
6415	3. 一个可恢复状态应该存什么
27219	这不是要求每个五分钟任务建立十个文件。短任务可保持会话，只有跨窗口/跨会话或高风险任务才需要外部状态。字段的价值在于避免具体恢复错误，而不是完整填写表格。
29088	验证已确认事实是否引用存在的证据、证据版本是否与当前工件一致。它不能判断“证据文本是否真正支持结论”，那需要读取原始材料、专门语义判定或人工审查。把结构验证通过当成语义保真，是旧式模拟实验最容易造成的误解。
6535	4. 原始证据应该如何卸载和找回
16251	大日志、完整源码和长文档可放在外部，摘要只保留定位信息及关键片段。但定位信息要可用：仓库路径+版本+符号，比临时行号更稳定；工具结果ID若会过期，必须说明有效期或保存必要证据；只写“之前看过资料”无法恢复。
18042	并非所有原始内容都值得永久保存。可重新获取、成本低、没有决策影响的内容可以不保存；外部来源可能变动、重大决定依赖、恢复成本高的证据更值得留存。不要为了记忆而重复归档整个仓库，造成权限和维护负担。
28541	重新读取也应遵循权限和版本。某个旧工具结果当时允许访问，用户权限后来撤销，就不能因缓存里仍有副本而继续使用。压缩和记忆不会解除数据治理义务。
6636	5. 压缩成本的盈亏不只看Token差
25636	设压缩本次成本Cc，剩余k轮，压缩后每轮节省Si，但前缀缓存损失为Li，重新检索成本为Ri。粗略计算：
10213	。还需考虑压缩错误的返工成本和质量损失，不能将其默认为零。
12071	任务马上结束时，调用一次模型压缩可能没有回本。相反，历史很长且剩余步骤多时，适度压缩可能显著降低持续成本。更合理的触发考虑剩余工作、信息污染、预算余量与恢复难度，而不是只有固定占用百分比。
24639	缓存命中率下降并不表示压缩一定不值得；压缩后的上下文更小，后续多轮仍可能总体更便宜。也不能为保缓存保留过期错误。最终比较每个成功任务的总成本和质量。
6718	6. 怎样真正评价语义保真
13661	准备含不同类型约束的长任务，在压缩前后做三类测试：事实/约束恢复、证据定位、继续执行。加入否定条件、已撤销建议、版本冲突和未决副作用。问题应在实验前定义，避免看完摘要再挑它会答的题。
20687	未压缩历史作为对照，但它也可能因过长而退化，所以还可增加“人工整理的最小充分状态”上界参考。多次压缩要单独测试，因为摘要再摘要可能逐步强化错误。评测应记录错误类型，而不是只给一个总分。
17272	对于商业服务的不可读压缩项，不能直接审查内部内容；仍可把相同任务分叉，比较后续事实回答与实际工作完成。这是黑箱行为评价，不应伪称读取了内部压缩表示。

6043	1. 检索是一个分阶段的信息损失过程

6263	2. BM25：词频饱和与长度归一化
20866	本书采用一种常见的非负IDF形式：

6408	3. Dense Retrieval与向量空间
14791	双塔检索通常分别编码查询和文档，通过点积或余弦计算相关性。文档向量可以离线计算，查询向量在线计算；训练中的正例、负例和任务指令决定它适合怎样的相似关系。描述相似不等于事实相同，反义条件、版本号和精确标识符容易被语义近似掩盖。
16324	如果使用余弦，常见做法是归一化后点积；若索引按内积而向量没有按预期归一化，向量范数会影响排序。更换Embedding模型、维度、预处理或指令模板，通常需要重建相关索引，不能把不同空间的向量混在同一集合里。
7313	Cross-encoder让查询与文档共同编码，能做更细相关性判定，但候选对数量直接增加成本。它适合对已召回的小集合重排，无法找回从未进入候选的关键材料。ColBERT则保留多Token表示并做延迟交互，位于单向量效率与更细粒度匹配之间，存储和索引设计也相应复杂。
6517	4. ANN为何更快，也为何可能漏掉
24204	精确向量搜索扫描全部向量，容易建立正确性基线。近似最近邻索引用可控的召回损失换速度或存储。HNSW用分层图导航候选邻居；搜索候选集合更大通常提高召回但增加工作量。IVF先按粗聚类选择若干桶，再在桶内搜索；探测桶太少会漏，太多趋向扫描。PQ把向量分块编码为码本索引，减少存储但引入距离近似。
11157	不要把ANN检索的Recall@k与业务证据召回混为一谈。ANN指标可能只是与精确向量排序相比，证明近似索引没有丢太多邻居；若Embedding本来就没把正确文档排前，这个指标再高也不能保证业务成功。
12642	元数据过滤会影响ANN行为。如果先取全局top-k再过滤权限，可能只剩一两项，授权用户反而拿不到本可找到的材料。可采用权限预过滤、适当过取、分区或支持过滤的索引方案，但需测严格ACL与高选择性过滤下的召回和延迟。
6647	5. 混合检索如何融合
7085	BM25分数与余弦分数不一定同尺度，直接相加容易被某一信号支配。RRF只使用名次：
10090	。它简化跨分数标定，但也舍弃了分数间隔信息。c是调节头部权重的参数，不是神奇常数。
16972	实验实现对每个排名列表去重，防止同一检索器重复返回一个文档制造额外票数。版本不同的同名文档应保留清晰ID，不能错误合并。融合之后还可做去冗余或覆盖选择，但不能为了多样性删掉回答必要的第二份证据。
21307	查询改写与HyDE可以扩大语义召回：先形成可能的描述，再检索。但假设文档是查询辅助，不是真实证据；生成的错误前提不应进入最后答案的事实链。

6727	6. 索引是有生命周期的数据产品
12947	入库时保存来源ID、内容版本、片段位置、Embedding版本、权限与更新时间。修改或删除原文后，索引与缓存应同步失效；文档ACL变化同样需要处理。增量索引不是只添加新向量，还包括替换旧内容、删除、合并和冲突。

13861	删除敏感内容不能只从结果列表隐藏。如果摘要、答案缓存或长期记忆仍保留派生内容，也需要相应治理。检索安全是完整数据流问题，不是最后展示前的一次过滤。
