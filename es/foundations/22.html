Ilustración dinámica · Lección 01

Descomponer una tarea de un agente en los turnos que realmente ocurren

¿Por qué una misma tarea del usuario puede llamar al modelo más de una vez?

El LLM genera una propuesta del siguiente paso; el harness ejecuta la acción permitida y entrega el resultado de nuevo al LLM. Es el bucle externo de la tarea; dentro de cada llamada al modelo también hay generación token a token. Una acción de herramienta del bucle externo no equivale a generar un token en el interior; no se deben confundir ambos «bucles».

Identificador de llamada ID que enlaza solicitud de herramienta y resultado.
Resultado de herramienta Contenido devuelto tras ejecución real del programa.
Contexto Información entregada explícitamente al modelo en esta ronda, no todo el estado del ordenador.

Entrada y condiciones de aplicación: Tarea didáctica construida de solo lectura: config.txt contiene timeout=30. Los carriles muestran límites de responsabilidad; no se afirma haber invocado una API comercial real. Datos y orden de acciones son fijos.

Volver primero a un programa normal

Tomar Agent Entiéndelo como un sistema que organiza tareas alrededor del modelo: prepara entrada, invoca y comprueba la salida; si pide herramientas, las ejecuta e incorpora sus resultados; si cumple las condiciones de finalización, termina.

Reconstruir primero como un programa normal: distinguir elemento por elemento
Objeto unoTarea del usuario
Objeto dosModelo: proponer el siguiente paso
Objeto tresHarness: quien llama realmente a herramientas

Diferencia clave: Un agente es un sistema de programas que organiza modelos, herramientas, estado y retroalimentación.

Malentendido frecuente: no se añadió una nueva red neuronal independiente.

Harness o aplicación anfitriona son nombres habituales para este entorno de ejecución y su lógica de control. El modelo genera acciones candidatas o respuestas; la aplicación anfitriona ejecuta realmente, guarda el estado y controla los límites. No significa que al modelo le aparezcan de repente permisos internos de acceso al sistema de archivos.

Ejemplo completo de tres llamadas al modelo

El usuario pregunta: «¿Qué devuelve la función del archivo?». Los mensajes didácticos siguientes no representan todos los campos API de un proveedor.

Diferencia clave: El modelo propone primero la intención de llamada; solo tras ejecutarla la aplicación anfitriona habrá nueva evidencia en el siguiente turno.

Malentendido frecuente: escribir el nombre de una herramienta no significa haberla ejecutado.

La entrada de la primera ronda incluye la pregunta y herramientas disponibles: «read_file recibe un path y devuelve el texto del archivo». El modelo produce una solicitud, por ejemplo, read_file(path='demo.py'). En este punto, el archivo aún no se ha leído por ello.

Ejecución del harness: comprueba permiso de acceso a la ruta, lee el archivo real y obtiene def answer(): return 42, vinculando el resultado a la identidad de esta llamada.

La entrada de la segunda ronda incluye tarea original, solicitud previa y resultado real. El modelo puede responder «devuelve 42» desde el código o pedir verificación. Si solicita pruebas, la aplicación las ejecuta y devuelve su salida.

La entrada de la tercera ronda incluye esa validación y el modelo organiza la respuesta final. La aplicación debe juzgar finalización según la tarea; un tono seguro al final no demuestra todos los requisitos cumplidos.

Por qué distinguir ronda, turno y tarea

Conocer primero los objetos y símbolos de esta sección
Thread, Turn, Session: niveles de ejecución
Suelen ser divisiones del anfitrión para sesiones y turnos, no capas de la red neuronal. Thread puede ser una sesión y Turn varias rondas de modelo y herramientas para responder a una tarea; el límite concreto depende del producto. No se puede equiparar directamente «este turno ha terminado» con «todas las herramientas externas han terminado»; hay que examinar los eventos y resultados reales.

Este libro llama llamada al modelo a una solicitud al modelo y su salida. Desde que el usuario envía una pregunta hasta que recibe la respuesta puede hablarse de un turno de interacción; puede contener muchas llamadas al modelo y ejecuciones de herramientas. Las definiciones de Turn, Step y Thread varían entre productos; al leer el código, consulta los tipos y ciclos de vida del proyecto.

Diferencia clave: Una tarea puede abarcar varias llamadas al modelo; la entrada de cada turno depende de los resultados previos de herramientas.

Malentendido frecuente: una pregunta del usuario no equivale a una llamada al modelo.

Thread o sesión suele conservar la organización de las interacciones relacionadas; una tarea (task) es el objetivo del usuario que se quiere alcanzar. Una tarea larga puede abarcar varias sesiones y una sesión puede contener varias tareas.

Diferencia entre flujo y Agent libre

Un flujo workflow puede prefijar pasos por programa, como «caché, base de datos y generación»; un Agent más autónomo delega al modelo más elecciones siguientes. Pueden mezclarse: libertad total no es la única forma avanzada.

Diferencia entre flujo y Agent libre: distinguir cada caso
Objeto unoTask: el objetivo completo
Objeto dosTurn: fase del usuario o del agente
Objeto tresTool call: una acción

Diferencia clave: Las tres granularidades deben registrarse por separado; de lo contrario, los reintentos y la recuperación no localizan el paso concreto.

Malentendido frecuente: distintos productos nombran Turn de forma distinta; hay que seguir la definición del sistema actual.

Un flujo fijo aporta previsibilidad; la selección libre, adaptación. Añadir autonomía también añade errores y costes. Si una necesidad simple ya tiene una ruta clara, no hace falta imponer planificación, investigación multiagent y revisiones repetidas.

Qué son herramientas y efectos secundarios

Una herramienta tool es capacidad invocable que el harness ofrece al modelo. Leer, buscar, consultar bases o ejecutar pruebas son formas de herramienta. Un efecto secundario cambia el mundo externo, por ejemplo editar archivos, enviar correos o confirmar código.

Qué es una herramienta y qué es un efecto secundario: distinguir elemento por elemento
Solución / objeto AWorkflow: pasos predefinidos
Solución / objeto BAgente: pasos de decisión dinámicos
Solución / objeto CPueden combinarse

Diferencia clave: Las tareas claras suelen resolverse más sencillamente con flujos deterministas; en exploraciones complejas, el modelo puede elegir el siguiente paso.

Malentendido frecuente: más libertad del Agent no siempre es mejor.

Generar un nombre de herramienta no completa un efecto secundario; perder la respuesta después del efecto tampoco implica que no ocurriera. Es el problema de unknown e idempotencia que explica F33.

Por qué un Agent necesita bucle

Sin conocer el contenido del archivo, el modelo no puede determinar de forma fiable el parche final; leerlo proporciona información nueva. El bucle permite que «la acción obtenga observaciones y las observaciones cambien la decisión siguiente». No busca que el modelo repita mecánicamente su análisis.

El bucle necesita finalización, presupuesto y tratamiento del estancamiento. Si una búsqueda repetida no añade evidencia, cambia estrategia o informa de la carencia, sin repetir infinitamente.

Límites de los scripts didácticos del libro

Una demostración puede usar un guion fijo que devuelve solicitudes predefinidas para mostrar mensajes: es simulación de protocolo o control, no autonomía comercial real. Solo integrar un modelo real y medir permite hablar de su éxito en la tarea.

Ejemplo resuelto · Lección 01

Leer, descubrir una laguna y volver a leer: dejar que un resultado de herramienta determine el siguiente paso

Entrada y condiciones. El usuario pregunta «¿Por qué se agota el tiempo de espera?». En el repositorio didáctico, config contiene timeout=3, el registro indica request elapsed=5, con todas las unidades declaradas como segundos en la cabecera.

2 Resultado de la herramienta 1Obtener timeout=3 segundosSolo se confirma la configuración, no si la solicitud real agotó el tiempo de espera.

Conectar el proceso. El valor del bucle del agente es determinar qué falta según la evidencia obtenida, no preguntar mecánicamente más veces al modelo.

Límites y contraejemplos. La secuencia de acciones es una construcción didáctica, no una elección autónoma medida de un modelo; la evidencia solo apoya «se superó el límite», sin permitir adivinar causas más profundas.

Separar primero tres informaciones: petición, propuesta y hechos de herramientas

El usuario pide «leer timeout en config.txt». El modelo recibe tarea y descripción de read_file, pero el contenido sigue en disco.
