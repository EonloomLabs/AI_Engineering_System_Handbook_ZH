# 给了attention_mask，为什么右补齐生成仍可能读错logits？

### 掩码与输出采样地址解决不同问题
attention_mask限制Key侧读取；`logits[:, -1, :]`选的是输出张量最后一列。这两步没有逻辑蕴含关系。右补齐时最后一列可能对应PAD查询，掩码并不会自动把索引−1改成最后有效Token。Transformers的decoder-only生成教程因此要求相应路径使用左补齐。[[SRC:GENERATE]]

本地固定两条序列的有效表为`[1,1,0]`与`[1,1,1]`，最后有效索引应为1、2。构造候选分数后，正确选取得到类别`[1,1]`，无条件取末列得到`[0,1]`。这证明错误来自地址选择，不是softmax算错。

### 不要把长度减一写成万能公式
`mask.sum(-1)-1`只对“有效项从0开始连续排布”的右补齐布局给出最后有效索引。左补齐`[0,1,1]`的和为2，但最后有效下标是2而不是1。更通用的检查是用位置索引与有效标记求最后有效位置；真实生成器还要同时正确处理位置编码和缓存。
```python
positions = torch.arange(T).expand(B, T)
last_valid = positions.masked_fill(~valid, -1).max(dim=-1).values
if (last_valid < 0).any():
    raise ValueError('empty effective input')
next_logits = logits[torch.arange(B), last_valid]
```
这是教学自定义采样逻辑，不是建议绕过库的prepare_inputs_for_generation。接入现成generate时优先遵守该模型支持的padding约定。

### EOS作为PAD，为什么不会一开始就结束？
某些decoder-only模型缺少独立PAD，推理可把EOS用作左侧补齐项。**输入中出现该ID**与**本轮新生成该ID触发停止**是不同事件；有效mask决定输入角色。训练时更危险：如果按“所有ID等于EOS的地方都置−100”清标签，会同时擦掉真正需要学习的结束目标。应按padding位置而不是仅按ID值区分。[[SRC:GENERATE]]

### 追问：单条输入正常、batch后异常，先查什么？
先检查左右padding、真实长度、最后有效位置、position_ids、EOS/PAD共用和缓存偏移。把同一个样本单独跑与混入长短batch跑作对照，比直接归咎GPU非确定性更有定位力。不要让合成测试所有句子等长，否则这些bug永远不会出现。

### 追问：右补齐永远不能用于decoder模型吗？
不是。训练和自定义前向可以正确使用右补齐，只要掩码、标签和输出索引一致。问题发生在具体生成代码假设最后张量列是有效末位时；把某调用链约定扩大成模型数学定律，会产生新的误解。

## 自检
mask=[0,1,1]时，用sum(mask)-1取得最后有效Token会得到什么错误？

参考答案：和为2，减一得到1，但实际最后有效位置是2。该公式隐含右补齐假设；左补齐或稀疏有效位置必须按索引与mask求末位。
