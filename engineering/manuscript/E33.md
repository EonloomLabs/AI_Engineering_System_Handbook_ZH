# 代码位置的单位错一个，编辑就可能改错字符：UTF-8、UTF-16与版本号

### “character=3”先问单位是什么
LSP3.17的Position.character按初始化协商的PositionEncodingKind解释；UTF-16是默认且服务器必须支持的编码，UTF-8和UTF-32的计数含义不同。这一规则来自Microsoft规范的position.md，不是根据JavaScript字符串习惯猜出来的。[[SRC:LSP]]

固定字符串`a😀b`，b之前有2个Unicode码点、3个UTF-16 code unit、5个UTF-8字节。Python的普通字符串len、JavaScript常用的字符串长度、协议传输Content-Length和LSP位置因此可能给出不同数字。不要把中文英文测试通过当成Unicode位置处理正确。

### 从一个位置到一次安全编辑
先用协商编码解释起止位置，再按对应的文档快照转换到内部索引；范围采用协议约定的边界，不能把结束位置误当包含最后字符。随后核对文档版本，最后生成编辑。相同line/character在用户继续输入后可能指向完全不同内容。

本书实际计算上述三个长度，另将版本与内容指纹检查作为执行层约束。它没有启动真实语言服务器，因此不宣称通过某IDE兼容性认证。

### 版本冲突不能靠“附近搜索同名文本”盲目修复
如果收到的编辑基于版本7，而当前buffer已经版本8，直接应用可能覆盖用户新内容。自动重定位需要明确上下文和冲突策略；无法唯一判断时应重新获取范围或拒绝。模型给出的行号只是提议，不能绕过宿主的版本保护。

### 追问：文件落盘内容与编辑器buffer谁更权威？
要看动作对象。LSP常处理内存文档；shell测试通常读取磁盘。两个视图没同步时，模型可能分析buffer而测试旧文件。证据中应写“来源是内存版本还是工作树文件”，必要时显式保存或让验证读同一快照。

### 追问：为什么不用所有地方统一成字节偏移？
内部可以统一，但边界仍需精确转换；协议、编辑器和模型报告未必使用字节。统一存储单位不代表可以忽略输入单位。包含组合字符、emoji、CRLF和非BMP字符的测试能暴露隐藏假设。

## 自检
a😀b中b的起点，按UTF-16与UTF-8分别是多少？

参考答案：UTF-16是3个code unit：a占1，emoji占2；UTF-8是5字节：a占1，emoji占4。Unicode码点位置为2，三者不可混用。
