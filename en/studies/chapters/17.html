1. What real gains multiple agents offer

Relatively independent searches can run in parallel, tasks can have separate contexts and tools, and some reviews can isolate the implementer's assumptions. Anthropic's research system provides a case of a main agent coordinating parallel sub-agent exploration; Agentless suggests structured, simple flows can also compete on some software tasks. Their tasks and settings differ, so neither establishes that "multiple agents are always better".[N26][N47]

Multiple agents add task descriptions, repeated retrieval, context handoffs, merging, conflict resolution and extra model calls. If everyone edits the same core logic, division may merely fragment continuous reasoning. On a small task, coordination may cost more than implementation.

2. Estimate speedup from the critical path, not agent count

Let p be the parallelizable share of work. With N executors, the ideal speedup bound is approximately 1/[(1−p)+p/N]; coordination, communication, duplication and merging make actual speed lower. This applies an Amdahl-style derivation, not a model experiment result.

Start with the objects and symbols used here
DAG, dependencies and the critical path
A DAG is a task dependency graph that is directed and has no cycles. The arrow A→B means B depends on A finishing; the critical path is the longest dependency chain, the one that fixes the earliest finishing time given the task durations and dependencies. Independent example: A takes 2 seconds, B and C depend on A, take 3 and 5 seconds and can run in parallel, so finishing both after A takes at least 7 seconds — not 2+3+5=10 read as wall-clock time.

For two independently modified modules followed by integration, ideal time is the larger duration plus integration, not their sum. If the second needs an interface established by the first, a dependency edge prevents true parallelism. A task DAG should represent output dependencies, not mechanically impose three fixed layers of "analysis/implementation/review".

Shared rate limits also break ideal parallelism. Four agents calling one external API may rate-limit each other; with a fixed token budget, more concurrency also reduces evidence available per task. Evaluate the complete task's wall-clock time and total resources rather than one fast subtask.

Do not conflate: if B and C actually write the same file, they may not be safe to run in parallel; the task graph has to reflect resource conflicts, not just the business steps.

Key boundary: measure waiting gates, execution and collection separately; output order does not establish serial execution.

3. What a delegation contract needs

Delegation instructions need at least a goal, scope, current facts, necessary constraints, available tools, expected return form and completion conditions. Supply enough information without copying the whole main conversation. Mark important assumptions as unverified rather than teaching them to every sub-agent as facts.

Returns should distinguish conclusions, evidence locations, actions taken and unresolved issues. A main agent receiving only polished summaries without original sources cannot judge conflicts or recheck them. For precise code, read the current version identified by the sub-agent rather than having it manually rewrite potentially incorrect source in its summary.

Harnesses inherit context differently: some use independent context, others fork. Product configuration also determines tools and permissions. Verify the harness mechanism first; an abstract "inherits all permissions" statement in a skill does not implement it.[N21][N22]

A sub-agent does not naturally hold all of the parent agent's memory. The handoff package has to let it start from an explicit state, not merely from "have a look".

Do not conflate: deleting unfinished items to save tokens can leave two agents each believing the other has run the key test.

4. Concurrent file access and integration boundaries

For independent writes, branches or worktrees reduce direct overwrites but do not eliminate semantic conflicts. Separately passing patches may change shared interfaces, dependency versions or configuration behavior after merging. Reverify the current merged artifact rather than reusing green results from each branch.

Start with the objects and symbols used here
CAS, version checks and TOCTOU
CAS is a controlled operation that updates only after comparing that the expected version or value still matches. TOCTOU is the race in which something changes between the check and the use: a separate "look at the version, then write" is not automatically equivalent to an atomic CAS. If a patch was produced from version 7 and the version is already 8 at commit time, overwriting directly should be refused and the work redone; a concurrent insert between the comparison and the write has to be prevented as well.

For changes to the same file, define ownership boundaries or serialize critical parts first. Content hashes/CAS prevent overwrites, but a human or agent must still understand conflicts after failure rather than automatically choose the last writer. Some tasks suit research-only sub-agents with centralized implementation by the main agent, reducing concurrent-write conflicts.

If sub-agents can edit tests, the main agent must detect weakened tests. Verification resources need explicit ownership; high-risk acceptance can run outside the workspace or in a restricted environment. Before treating "all tests are green" as a result, confirm the tests still verify the original requirements.

What Git guarantees is the ability to merge text; it does not verify a business interface. Two "both passed" results belong to different artifacts and cannot be added up into a pass after the merge.

Do not conflate: isolating writes with several work trees does prevent overwriting, but it does not remove the final semantic integration.

5. Independent reviews do not imply independent errors

The same model, prompt and context can share incorrect premises. Showing the implementer's explanation first anchors the reviewer to its conclusion. Independent review can examine original requirements, the current diff and tests before implementation reasons, but adds reading cost and should be reserved for worthwhile tasks.

Majority voting offers expected benefits only when errors are sufficiently independent and the voting target identifiable. If every agent trusts stale API documentation, voting cannot recover facts. Independent evidence, such as reading the current interface or running tests, may help more than adding a fifth identical reviewer.

Fix and verify small issues within the current review rather than restarting analysis, design and review from the beginning. Return to design for changed goals or disruptive architecture decisions. Let risk, not ritual, drive the process.

An independent session and an independent error are different notions. The same model, the same input and the same test readily share blind spots.

A review task can be split into checking the contract, generating counterexamples and re-checking the run evidence, so that the extra work really does bring different evidence.

A2A can help systems discover one another and exchange task state; it does not automatically provide global transactions, permissions, or any guarantee that "more votes means true".

Do not conflate: dressing a majority vote up as a reliability certificate hides correlated failures, especially at high-risk but low-frequency boundaries.

6. Cancellation, failure and partial completion

One failed subtask need not invalidate everything. The main agent should know which artifacts are reusable and which depend on failed results. Tool actions may remain in flight after cancellation; wait for a confirmable terminal state or record unknown. Do not delete subtask logs to pretend nothing happened.

For timeouts, read persisted evidence first to avoid redoing work; for loops without progress, change task boundaries or narrow the problem. Restarting an agent with the full history may merely repeat the same failure. Recovery should match error types rather than always say "try again".

7. When not to split the task

A clear goal, small change, concentrated evidence and cheap verification often need only one agent. Cross-language work, independent modules or broad research with independently checkable results may benefit more from parallelism. Actual dependencies and risk should support this judgment; every task does not need a complexity score.

Acceptance question: four research agents produce four different conclusions. Should their views be averaged in a summary? No. Compare provenance, time, scope and evidence quality first; some differences reflect conditions and others real contradictions. Integration adjudicates evidence rather than compromising on wording.

With correlated errors, do not multiply three agents' probabilities as independent
