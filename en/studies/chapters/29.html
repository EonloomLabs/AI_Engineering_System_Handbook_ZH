Goal: respond to failure with competing explanations, distinguishing evidence and repairs at the correct layer rather than immediate model changes or more rules. These cases are author constructions, not confirmed incidents in the user's repository.

Case one: a Skill appears loaded, but the code lacks domain expertise

Observation: the log names the skill, but output ignores transaction timeouts. Explanations include metadata-only loading, a trimmed body, omitted content in a sub-agent, ineffective specialist content, visible but unused content, or tests not requiring this behavior.

First inspect loaded scope and skill text, then relevant risks in execution traces, and finally tasks triggering the error. Do not begin with another routing agent when selection may be correct. A repair may need only concrete transaction-boundary knowledge and its test.

Include transaction-handling and unrelated tasks in regressions so everything does not become distributed-systems analysis. Acceptance means fewer errors, not more mentions of "transactions".

Locating it layer by layer avoids the empty optimization of "the skill file is expertly written but never reached the model".

Conversely, loading a long set of instructions with no corresponding action is not effective application either; look at the task behavior and the result.

A skill's expertise should be verified against concrete failure cases, not measured by its length or its number of technical terms.

Do not conflate: the model replying "I used such-and-such skill" counts only as a claim; it is no substitute for a loading trace and evidence of execution.

Case two: work changes direction after compaction

Observation: "change only description" becomes executor refactoring after compaction. Explanations include lost prohibitions, promoted assumptions, overriding old memory, missing new user input or truncated subtask instructions.

Compare task state before and after compaction for retained prohibitions, and compare downstream delegation with the current authoritative goal. If harness compaction is opaque, fork an identical prefix and continue to test specific constraints. First persist a few key constraints and evidence locations rather than build a second full-history summarization service by default.

Include repeated compaction and new goal changes so old constraints do not prevent later authorized changes. Fidelity preserves time and authority correctly rather than freezing everything forever.

All three probes are short, yet they come closer to the real risk than surface word similarity does. Even when a summary uses the same words, it can reverse the direction of time and of negation.

The set of probes should define the important constraints before the real task; you cannot read the summary first and then ask only about the parts it happened to keep.

In the end the task also has to continue, with a check for repeated actions, changes beyond the permissions granted, or the wrong version being cited. Passing the questions is only a local signal.

Do not conflate: a model scoring its own summary highly is not fidelity, especially when the grader and the generator share the same blind spot.

Case three: relevant retrieval results are always outdated

Observation: terminology is right but API fields are obsolete. Causes may include stale indexes, semantic preference for old long documents, versionless cache keys, missing time filters in reranking or old evidence mixed during generation.

Trace current-document ingestion, candidate inclusion, post-filter retention, ranking / selection loss and final citations. Fixes may concern index generations and version filtering rather than a new embedding model.

Add same-named versions, rollbacks and historical queries to regression tests. Always choosing the latest record fails questions about old migration reasons. Lesson 19's valid time and time of knowledge distinguish these needs.

How to read the changes in the figure

It is not as simple as newer always being better; first settle "which artifact is the one we are going to change and verify".

Every piece of evidence carries a version; check the current content again before applying a patch, so that an old index does not overwrite the user's new change.

Index updates can be incremental, but deletions, renames and configuration changes also make the links stale, so watching for new files alone is not enough.

Do not conflate: recording only the branch name main is not enough to identify an artifact, because a branch moves; a commit or content fingerprint is needed, together with the necessary working-tree diff.

Case four: tests pass, but users still find problems

Tests may never have run, key cases may be skipped or weakened by the model, versions may be stale, new requirements uncovered, or environments unlike production. Read actual commands, counts, exit codes and artifact versions rather than the model summary alone.

Fix the cause: explicitly fail empty test sets, add assertions for new requirements, bind verification to current versions and isolate high-risk test resources. Do not mechanically add three natural-language Review rounds that may trust the same false green report.

Deliberately change files after testing, delete key assertions and cause timeouts, then observe success claims. Lesson 65 actually measures stale-verification rejection among these cases.

First check whether anything actually ran, then check which version was tested, and last check whether the cases can hit the target defect. All three gates are needed.

Mutation testing can deliberately put a wrong implementation back in; if everything is still green, the tests have no discriminating power.

Formatting, generating code or changing configuration after verification also changes the object, so the affected checks have to be run again or shown not to be affected.

Do not conflate: "the tests found no problem" cannot be rewritten as "there is no problem at all", least of all when both coverage and environment are limited.

Case five: slower tasks and more tokens

Separate model, tool, queue, retrieval, compaction and Review time first. Causes include agents rereading the same files, all skills loading by default, verbose output, retries, excessive model effort or slow external tools.

One targeted fix returns exact evidence locations from research subtasks so the main agent stops rediscovering the whole repository; another removes repeated redesign for small issues. Optimization requires lower cost without weaker expertise. Smaller input with more failures is not success.

Cover complex tasks so simple speedups do not hide oversimplification. Use cost per successful task as the main criterion rather than mean tokens.

"30% cheaper" describes the unit price of a call, not the result. Failures have cost money too, so the 35 units from the 50 successful runs cannot be the only numerator.

Case six: retries duplicate side effects

Observation: two tickets appear after a network timeout. Retries may generate new operation IDs, or the server lacks idempotency while the client treats unknown as failure. Repair requires business idempotency / reconciliation rather than a "do not repeat" prompt.

Disconnect after remote success but before client receipt, not merely before a call. This book's local-file crash experiment verifies a similar window, but remote operations need corresponding service capabilities; file hashes cannot simply be transferred.

How to read the changes in the figure

A local table can record "I sent it", but if the crash falls after the remote side commits and before the local entry is written, the local side still does not know. The downstream has to support deduplication by the same key, or results that can be verified.

Besides the key, the request parameters should be bound in as well; the same key with a different amount must not silently reuse the old result. The retention period and the conflict behavior belong in the contract.

"Exactly once" can usually only be spoken of within clear transaction and deduplication boundaries; it cannot be extrapolated from one local SQLite table to any external system.

Do not conflate: using the order number as the unique key is too coarse and wrongly merges several legitimate operations on the same order; a random number per request is too fine.

Mechanism basis:[IDEMPOTENT] [SQLITE]. The numbers and harness setting in this example are an explicitly given teaching construction, not commercial model output or a production performance measurement.

Engineering mechanisms and failure boundaries

A real crash window

Exit the child process after the write to the temporary SQLite has finished but before the harness log confirms it. On recovery, retry once with the same operation key and once with a new one, and compare how many times the side effect occurs.

Key boundary: the experiment touches only temporary local data; it cannot prove that a third-party service offers the same deduplication protocol.

Follow it further through the source or the engineering basis: use two independent commit points to understand an unknown result. Do not check only the path that goes well; check the behavior on cancellation, on a version change, and when the result is unknown.

For the full mechanism and a continuous example see Written successfully but not confirmed: how a retry becomes a duplicated side effect; this section keeps its own derivation and experiment, and the two accounts work at different levels rather than replacing each other.

Evidence and the limits of understanding: failure, cancellation and an unknown result cannot be merged into one state; safe retrying depends on downstream idempotence or verification, and the experiments in this book are not a product's exactly-once guarantee.

Verification basis:[C04] [C05] [C09] [A06]. The source is limited to commit 86e17e98c7f9 and the paths actually read; article experience, public documentation and original teaching experiments are labeled separately. See how it was obtained, what was read, and the limits.

Case seven: more memory makes errors more persistent

Observation: the system insists on old experience despite contrary current code. Inspect memory provenance, version, scope, write permissions and retrieval priority. A guess automatically saved as active may become a "verified rule" over repeated summaries.

Correct false authority and applicability first, then assess write policies. Reduce memory if necessary rather than add complex graphs. Regressions should include new evidence overturning old claims, revocations, conflicts and no matches; the system must be able to leave memory unused.

A unified diagnostic method

Connect symptoms, competing explanations, distinguishing evidence, minimal repairs and regressions. Every extra read should resolve important uncertainty, every code change a real failure. "Comprehensive optimization" without these links expands systems without improving capability.

Fix deterministic bugs with tests, information gaps with retrieval, expertise gaps with knowledge and execution gaps with the harness; consider models or training at capability limits. This is not an absolute ordering, but avoids blaming every issue on model intelligence.
