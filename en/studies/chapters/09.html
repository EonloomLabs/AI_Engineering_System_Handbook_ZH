1. Evidence scope and versions

Start with the objects and symbols used here
SSE, chunk, delta: different layers of fragmentation
SSE is the text protocol for server-sent events; a network chunk is the stretch of bytes received this time; a delta is the incremental content of one output item. Their boundaries are not guaranteed to coincide. One complete event does not necessarily mean complete tool arguments either. The arguments may arrive first as {"path":"a and then as .py"}; they have to be assembled and the protocol's completion condition awaited — seeing a fragment is no reason to execute.

Project rules, initial context, the loop and local compaction come from commit 99f47d6e9a3546c14c43af99c7a58fa6bd130548; SSE event conversion comes from another commit 2a68b74b9bf16b64e285495c1b149d7d6ac8bdf4. These are traceable reading anchors, not determinations of the version installed on the user's machine. The official Agent Loop article supplies an overview; source code supplies behavioral evidence for particular snapshots.[N01][N02][N03][N04][N05]

Files and key locations: project_doc.rs handles project-rule discovery and concatenation; codex.rs contains build_initial_context, run_turn, which organize initial items and execution turns; compact.rs manages one local summary-compaction path; sse/responses.rs converts service events into internal response events.

Distinguish "observed implementation", "documentation claims" and "author advice" when reading source. In particular, do not combine functions from different commits into a version that never existed, or infer all server-side system prompts and internal model state from a public client.

2. project_doc.rs: why rules may not enter the input

In the snapshot above, discover_project_doc_paths searches upward from cwd for a repository marker and builds a search chain from the repository root to the current directory; without a repository, it uses the current directory. Each directory selects one rule file according to candidate-filename priority. AGENTS.override.md precedes AGENTS.md, followed by configured fallback names. Reading is limited by the total project_doc_max_bytes budget; this is bytes, not tokens.[N02]

Rather than translate source line by line, this chapter uses an original diagnostic example: suppose root rules are long and the current directory also has specialist rules. In an implementation concatenating in path order under a total budget, earlier files may exhaust it. The model appears to "ignore specialist rules", but the rules may never have loaded; another "follow every rule" instruction cannot fix a byte budget.

If override and ordinary rules coexist in one directory, do not assume both are combined. Check candidate priority and whether only one file is selected per directory. Missing deeper rules may also reflect an unexpected starting cwd rather than model routing errors.

These mechanisms suggest regression cases: no rules, root rules, nested rules, override, fallback filenames, zero budget, truncation across byte boundaries and different cwd values. The source includes related tests; this book only reads them and does not claim to have run these Rust tests. New teaching experiments do not replace regression checks on the actual harness version.

How to read the changes in the figure

Each time, pick the smallest check that can tell the hypotheses apart. A wrong final behavior alone does not license the claim that the whole model does not understand the business.

Once it is found that the rule was never sent at all, polishing its wording further has no causal effect, because the model still cannot see it.

After the fix, run a regression with counterexamples of the same kind to confirm the problem is gone and that no other task has degraded; diagnosis should come back to a reproducible experiment.

Do not conflate: one chance success is not enough to prove the root cause has been fixed; the change under identical input conditions and the necessary repeat trials have to be recorded.

Engineering mechanisms and failure boundaries

An immutable request and mutable authorization

Bind rule R3, tool T8 and environment E2 to the same request, then revoke the write permission before the model returns. Explain which interpretive information still comes from the snapshot, and which authorization has to be re-checked against the state at execution time.

Key boundary: snapshot consistency and authorization freshness are different goals; staying consistent is no reason to go on executing an operation that has been revoked.

Follow it further through the source or the engineering basis: eliminate mismatches between the rules, the tool list and the actual execution environment. Do not check only the path that goes well; check the behavior on cancellation, on a version change, and when the result is unknown.

For the complete mechanism and the continuous example see Why does every model call need a consistent context snapshot?; this section keeps its original derivation and experiment, and the two accounts work at different levels rather than replacing each other.

Evidence and the limits of understanding: a request fixes the choice of model, tools and environment; actual access still has to be checked against the current authorization, and a snapshot does not freeze every permission.

3. Initial context is a sequence of typed items

Start with the objects and symbols used here
ToolRouter,ToolCall,ToolInvocation
These are program type names from the cited snapshot of the Codex source. ResponseItem stands for one model response; ToolCall stands for the data of a call waiting to be made; ToolInvocation combines the call with execution context such as the session and cancellation; ToolRouter is responsible for the relevant tool path. These objects are constructed and dispatched by the program; they are not tensors of the kind the model uses internally for Q/K/V. Field and permission handling must follow the pinned source cited, not be inferred from the names.

build_initial_context constructs developer-level instructions from execution policies in this snapshot, adding optional developer instructions, user project rules and environment information. It returns a collection of ResponseItem, not a final token array. The service may still apply invisible templates and system rules afterward.[N03]

Start with the objects and symbols used here
Schema and Structured Outputs
A schema is a set of structural rules about fields, types and the like; a structured-output mechanism makes it easier for the model to return data that follows those rules. Valid fields still do not mean that the target file exists, that access has been granted, or that the request is right for the business. Independent example: path is required to be a string; {"path":3} does not match the type rule, and {"path":"missing.py"} follows the structure yet may still find no file.

Ask what role and stage each item enters. Client-side project rules are usually a kind of user-context item; a filename resembling "system rules" must not confer unlimited authority. Tool Schemas may also be stored in a different field from chat text. Judge visibility at the actual request boundary rather than from chat bubbles shown in the UI.

For skill systems, the key lesson is to give specialist instructions an explicit entry point and distinguish "metadata discovered → full content read → used in the result" observably. Text on disk does not mean model visibility, and visibility does not mean correct execution.

4. run_turn: one user turn can contain multiple model calls

The function first checks input and context usage, triggers compaction if needed, reads skill-related information, records user input and skill-injection items, then enters the model-call loop. The loop also handles user input appended during execution, builds the current prompt from history and decides whether further action requires continuation or termination.[N03]

In engineering terms, one user request to "fix the issue" is not one HTTP call. Tool outputs, new constraints added while running and compacted history may all change the next input. Performance statistics should use the complete user task at the top level rather than count only the first model call.

Apply this to diagnosis: if a skill loaded initially but later had no effect, inspect whether subsequent history retained it, was compacted, entered a sub-agent or was superseded by new evidence. An opening log cannot prove the complete skill content remained throughout a long task.

Follow call c1: nothing on disk changes when the model produces the call item; the harness still has to take the executing action.

The next turn does not send the isolated number "30" on its own; it has to keep which call that number answers and which file version it came from, so that another tool's result is not spliced in.

Do not conflate: when the result is not filled back in, the model may ask to read it again. Check message assembly first, instead of putting every repeated call down to the model not being clever.

5. compact.rs: a local summary path is not all Codex compaction

One local path in the snapshot requests a summary, trims older items and retries when context exceeds the limit, then extracts the summary on success. It rebuilds history from the initial context and user messages fitting the budget and saves a compaction event. The code also explicitly warns that repeated compaction may affect accuracy.[N04]

Be careful: a separate official Compaction interface can return opaque compaction items; a readable local summary and opaque server state are different implementations. Old source does not establish that "Codex always turns history into plain text". Encrypted returned items also do not establish "completely lossless semantics". The internal representation is unpublished; continued tasks must verify business fidelity.[N06]

When comments and code behavior are in tension, describe actual operations first and preserve the question. For example, determine how deleting early history items affects prefix caching by recalculating the reusable prefix from actual requests, not by copying a "for caching" comment as a universal conclusion. Senior source reading includes checking comments, not treating them as algorithmic proofs.

How to read the changes in the figure

The problem is not that the summary is badly written but that it comes from an old version and yet replaced an object that had been updated. Content can be correct and still lose data because of the order of commits.

Pausing execution to form a safety boundary is the easiest thing to explain, but it costs throughput; concurrent compaction needs an explicit prefix range or a version-conditional update.

A tool call and its result have to be kept as a pair. You cannot keep only "c1 was called" while overwriting the c1 result that has just arrived.

Do not conflate: checking the version first and then writing without a lock still leaves room for a new event between the check and the write; a conditional commit has to be atomic to match.

Engineering mechanisms and failure boundaries

Checking the generation number when a candidate is installed

Summary S is based on the prefix e1—e3; e4 and e5 are appended while it is being generated. Appending can keep the suffix, whereas a rollback or a change of model or authorization identity invalidates the candidate.

Key boundary: a background request that is discarded can still cost money; both state correctness and usage accounting have to cover the failure path.

Follow it further through the source or the engineering basis: a verified merge is needed between the compaction candidate and the live history. Do not check only the path that goes well; check the behavior on cancellation, on a version change, and when the result is unknown.

6. SSE conversion: separate display content from executable items

In another pinned commit, process_responses_event handles text deltas, completed output items, failures and completion events separately; its tests include an error for a stream closed before a completion event. This matches the boundaries of the Lesson 60 teaching parser, but this book's implementation is not a Rust port and does not cover every event type.[N05]

Real products must also handle cancellation, reconnection, model features and compatible versions. When reading source, diagram the type chain "network event → internal event → history → tool runner → next request", then check each conversion for lost IDs, state or errors. Text appearing in the UI alone cannot establish state-machine correctness.

7. Turn source reading into your own diagnostic method

For "the sub-agent has no skills / MCP", verify in order: harness version and product interface, configuration-discovery paths, actual loading, available tools, delegation input construction, execution permissions and returned evidence. Do not invent an inheritance system to fix an unestablished defect.

Graduation means finding equivalent boundaries in another commit and identifying effects on context, skills and error recovery, rather than memorizing function names. Change only layers your extension owns: if the harness already implements execution, permissions and caching, do not rebuild an entire harness in the skill repository.
