Start with the objects and symbols used here
checkpoint: you must look at the object that was saved
A model checkpoint saves weights or training state; activation checkpointing saves a few intermediate nodes so they can be recomputed on the backward pass; an agent task checkpoint saves how far execution has got. The three share a name, but what they restore is entirely different. When you see "checkpoint", first ask whether it restores parameters, recomputes activations, or continues a task. An agent saving a summary does not update model weights.

Goal: design and evaluate task continuity after compaction rather than summary fluency alone. Experiment: validate_checkpoint checks only structure and versions; this book has not measured commercial models' semantic compaction of natural language.

1. Compaction is a lossy information transformation

Original history H contains goals, tool feedback, attempts, assumptions and verified facts. A compaction function produces C(H), from which the model continues acting. The question is whether C(H) increases decision errors over future task distribution Q, not its literal similarity to the original. A short summary may preserve every currently important condition; a long one may lose the sole crucial negation.

Anthropic discusses compaction, notes and sub-agents in context engineering; OpenAI also documents opaque compaction state. These show forms beyond ordinary summaries, but form alone cannot establish lossless downstream tasks.[N23][N06]

This book adopts an engineering objective: prioritize constraints, conclusion status, evidence entry points and unfinished work that affect later actions. This is not a universally optimal compaction algorithm, but a design testable through task recovery experiments.

Engineering mechanisms and failure boundaries

Checking the generation number when a candidate is installed

Summary S is based on the prefix e1—e3; e4 and e5 are appended while it is being generated. Appending can keep the suffix, whereas a rollback or a change of model or authorization identity invalidates the candidate.

Key boundary: a background request that is discarded can still cost money; both state correctness and usage accounting have to cover the failure path.

Follow it further through the source or the engineering basis: a verified merge is needed between the compaction candidate and the live history. Do not check only the path that goes well; check the behavior on cancellation, on a version change, and when the result is unknown.

For the complete mechanism and the continuous example see A tool result arrives while the summary is being generated asynchronously — how is data kept from being lost?; this section keeps its original derivation and experiment, and the two accounts work at different levels rather than replacing each other.

Evidence and the limits of understanding: the candidate covers only the old prefix, so installing it must verify identity and keep the live suffix; accepted in memory and persisted successfully are different boundaries.

2. The greatest danger is not losing a few background details

Original: "Suspect the Skill was not loaded, but logs are unchecked, so this is unconfirmed." Bad summary: "The unloaded Skill caused the failure." A hypothesis becomes fact, directing later edits toward a wrong root cause.

Original: "Change only description, without changing skill content or adding a router." Bad summary: "Optimize skill routing." Negative constraints disappear and scope may expand.

Original: "Tests passed on commit A; file B changed afterward." Bad summary: "All tests passed." Lost evidence freshness creates false completion.

These errors change epistemic status, expand scope and lose evidence versions respectively. Keyword-recall tests are insufficient because bad summaries still contain Skill, routing, tests and other original terms.

How to read the changes in the figure

All three probes are short, yet they come closer to the real risk than surface word similarity does. Even when a summary uses the same words, it can reverse the direction of time and of negation.

The set of probes should define the important constraints before the real task; you cannot read the summary first and then ask only about the parts it happened to keep.

In the end the task also has to continue, with a check for repeated actions, changes beyond the permissions granted, or the wrong version being cited. Passing the questions is only a local signal.

Do not conflate: a model scoring its own summary highly is not fidelity, especially when the grader and the generator share the same blind spot.

Not every five-minute task needs ten files. Short tasks can stay in a session; external state is needed only across windows / sessions or for high-risk tasks. Fields should prevent specific recovery errors rather than complete a form.

validate_checkpoint checks whether confirmed facts cite existing evidence and whether evidence versions match the current artifact. Confusing structural validity with semantic fidelity is a particularly easy misreading of older simulation experiments.

How to read the changes in the figure

The problem is not that the summary is badly written but that it comes from an old version and yet replaced an object that had been updated. Content can be correct and still lose data because of the order of commits.

Pausing execution to form a safety boundary is the easiest thing to explain, but it costs throughput; concurrent compaction needs an explicit prefix range or a version-conditional update.

A tool call and its result have to be kept as a pair. You cannot keep only "c1 was called" while overwriting the c1 result that has just arrived.

Do not conflate: checking the version first and then writing without a lock still leaves room for a new event between the check and the write; a conditional commit has to be atomic to match.

4. How to offload and retrieve original evidence

Keep large logs, full source and long documents externally, with locations and key excerpts in summaries. Locations must work: repository path + version + symbol is more stable than a temporary line number; expiring tool-result IDs need lifetimes or retained evidence. "Read some material earlier" cannot restore anything.

Not all originals deserve permanent retention. Cheaply reacquired material without decision impact can be omitted; mutable external sources, evidence underlying major decisions and costly-to-recover evidence merit retention more. Repeatedly archiving whole repositories for memory adds permission and maintenance burdens.

Rereading must respect permissions and versions. A formerly accessible tool result cannot remain usable merely because a cached copy survives revoked authorization. Compaction and memory do not remove data-governance duties.

A file path points to a location, a version to specific content. Both are needed to tell "the file can be found" from "the same evidence has been retrieved".

That the old version can be restored accurately only proves that the earlier judgment had a basis; the current file has already changed, and whether it still applies is the next check.

When a code snippet and a run log are kept together, label the environment of each, so that different versions are not stitched into a false causal chain.

Do not conflate: treating a summary as the original fact, and stacking summary upon summary over time, gradually strips an assumption of its source and lets it be misremembered as verified.

5. Compaction breaks even on more than token savings

Start with the objects and symbols used here
Σ: sum term by term over the subscript
Σ is shorthand for addition. The subscript says which term varies; a subscript that is not summed over stays fixed. It is not an extra parameter, and it does not mean concatenating arrays. Independent micro-example: Σᵢ xᵢyᵢ with x=[1,2] and y=[3,4] is just 1×3+2×4=11.

Let current compaction cost be Cc, remaining turns k, savings per compacted turn Si, prefix-cache loss Li and retrieval cost Ri. A rough calculation is:净节省=Σ(Si−Li−Ri)−Cc. Include rework and quality losses from compaction errors rather than assume zero.

A model call for compaction near task completion may not pay back. With long history and many remaining steps, moderate compaction may substantially reduce continuing cost. Better triggers consider remaining work, information contamination, budget margin and recovery difficulty, not just a fixed occupancy percentage.

Lower cache-hit rates do not necessarily make compaction unhelpful: smaller context may still cost less over later turns. Do not keep stale errors to preserve caching. Compare total cost and quality per successful task.

6. How to evaluate semantic fidelity

Prepare long tasks with varied constraints and test three things before and after compaction: fact / constraint recovery, evidence location and continued execution. Include negations, withdrawn suggestions, version conflicts and unresolved side effects. Define questions before the experiment rather than select ones the resulting summary can answer.

Use uncompacted history as a control, recognizing it too may degrade through length; add "manually organized minimal sufficient state" as an upper-bound reference. Test repeated compaction separately because summaries of summaries may reinforce errors. Record error types rather than only an overall score.

Opaque commercial compaction items cannot be inspected directly; fork identical tasks and compare later factual answers and actual completion. This is black-box behavioral evaluation, not a claim to have read the internal compressed representation.

Engineering case · D04

Failure experiment: catch compaction overwriting new events with two database connections

Even an excellent model summary can fail at the commit protocol

Connection A reads history revision=10 and starts compaction; connection B writes a tool-success event and updates revision to 11; A writes back its old summary. An unconditional UPDATE overwrites the new event with old state. This book actually creates two SQLite connections to reproduce the sequence and rejects stale commits with a conditional UPDATE.[SQLITE]

The SQL means "write only if current rev still equals the 10 I read"; 0 affected rows must be treated as a conflict rather than success just because no exception occurred. The final state retains [11, c7 succeeded]. This state evidence matters more than summary fluency.

Verify summary content and protocol windows

A server-side compaction interface may return a complete window with several item types; keep more than just the opaque item.[COMPACT] Keep model-compacted context separate from deterministic execution logs: the former supports understanding, the latter determines whether tools executed and retries are allowed.

When merging trailing events

The complete event tail after a snapshot can be retained, but check whether it overturns summary claims such as "unfinished / unauthorized". Appending one new tool result to an old summary may leave contradictory state. Regenerate the summary or use authoritative merge rules for structured control state. No single method is universal; acceptance requires the correct next step during recovery.

Regression cases

Cover late tool results, changed user goals, cancellation, permission changes and concurrent second compaction. Define permitted and forbidden next actions for each; shorter post-compaction text does not prove continuity.

7. A practical strategy and counterexamples

Start with harness-provided compaction while retaining concise authoritative task state and original-evidence entry points in the project. Add targeted safeguards only after repeated observed fidelity failures. Do not default to an extra summarizer agent every few turns, which may add latency, break caching and create competing state.

Acceptance question: why is remembering every pending task but forgetting ruled-out causes still dangerous? The agent may repeat disproved paths or promote old hypotheses again. Save a "failed experience" if it changes later retrieval or avoids costly mistakes, not because every attempt needs permanent storage.
