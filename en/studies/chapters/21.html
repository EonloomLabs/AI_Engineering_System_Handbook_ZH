Goal: find actual bottlenecks from a complete task trace and define runnable failure strategies. This does not require every local script to build a distributed observability platform.

Queuing, execution, retries, cancellation and recovery together form waiting time; traces should show these causal relationships.

1. A trace expresses causation, not only timestamps

The top-level span represents the user task; lower spans distinguish retrieval, model requests, tools, compaction, delegation and verification. Parallel subtasks should record causal relationships and parents, not simply sum durations into wall-clock time. Waiting between model output and tool execution may come from approval, queues or parsing, not all from a slow model.

OpenTelemetry offers generative-AI semantic conventions whose locations and fields evolve. This book uses stable concepts such as tasks, calls, tools and verification rather than hardcoding an unstable field as an eternal standard. Pin SDK and convention versions for production integration.[N82]

Logs handle discrete events, metrics aggregate health, and traces connect individual paths. Metrics alone cannot reconstruct a wrongly written file, while saving every original input may leak data. Define the minimum necessary evidence and its access controls.

Parallel spans in a trace cannot simply be added up into the user's waiting time

Conditions for this example: an independent task: the model plans from 0—2 s, then tool A runs from 2—7 s and tool B from 2—5 s, and finally the model consolidates from 7—10 s.

If the trace records only the time spent inside the tool, it may miss queuing, connection and response transfer, and the end-to-end figure will still not add up.

Every span should be linked to the task, the attempt, the tool ID and the artifact identity, so that slowness and errors can be tied to a specific operation.

Do not conflate: when the parent span already includes the child span's time, adding parent and child together counts that time twice.

Engineering mechanisms and failure boundaries

Quantiles and the cost of failures

Compute the overall p95 from 100 one-second requests and 2 hundred-second requests, and compare it with the average of the two groups' p95 values; separately compute the cost per success including failures.

Key boundary: quantiles must be merged from the original distribution or from mergeable statistics, never by a plain average.

Keep tracing through the source or the engineering basis: avoid blending totals, wall clock and percentiles into one metric. Do not check only the happy path; check the behavior on cancellation, on a version change and when the result is unknown as well.

For the full mechanism and a continuing example, see Work out the waiting, the usage and the cost of failure from one trace; this section retains its original derivations and experiments. The two explanations address different levels and do not replace one another.

Evidence and the limits of understanding: the current context length, the usage already spent and the length of the recoverable log are different things; a discarded summary and a failed attempt can cost resources too.

2. What to record to explain failures

Model-call records include model identity, prompt/tool versions, token usage, response state and duration; retrieval records include index versions, filters, result IDs and truncation; tool records include action IDs, target scope, prerequisite versions, results and error types; verification records include command/checker versions and artifact versions.

Logs need not expose complete prompts or internal reasoning. Sensitive originals can be stored at controlled locations with references in traces. Redaction must not remove every metadata field that explains an error, such as replacing distinct call IDs with one identical string and breaking the causal chain.

Task-success metrics must come from acceptance checks, not model self-reports. An HTTP 200 response containing a refusal or incomplete result requires service-request success and user-task success to be counted separately.

3. Queuing and rate limits are system problems

APIs often limit requests, tokens or concurrency, with values varying by service and account; the textbook should not hardcode current allowances. Clients should constrain in-flight requests, output budgets and retries, without multiple sub-agents each assuming access to the entire shared allowance.

Start with the objects and symbols used here
Schema and Structured Outputs
A schema is a set of structural rules about fields, types and the like; a structured-output mechanism makes it easier for the model to return data that follows those rules. Valid fields still do not mean that the target file exists, that access has been granted, or that the request is right for the business. Independent example: path is required to be a string; {"path":3} does not match the type rule, and {"path":"missing.py"} follows the structure yet may still find no file.
Backoff, jitter and cancellation
Backoff makes the interval between retries grow; jitter adds a random perturbation so that requests do not all retry at the same moment. A cancellation signal is notice that a stop has been requested; it does not withdraw external side effects already committed. A read-only request whose connection fails temporarily can be retried; when the result of a write request is unknown, verify first. "Retry for longer" is no substitute for permission or idempotence design.

Exponential backoff with jitter reduces synchronized retries but belongs only to retryable errors. Permission denials, schema errors and deterministic business failures should not trigger blind backoff; unknown external side effects need reconciliation. Total retry attempts, time and cost need upper bounds.

Queues also need backpressure: congested downstream tools cannot be met with ever more plans and candidate actions. Long tasks can save recoverable state and release expensive runtime resources; interactive tasks should prioritize acceptable latency. Scheduling should follow business priority, not allocate resources to whoever generates more tokens.

How to read the changes in the figure

Each request takes only 1 s of computation, yet the last user waits 3 s. Looking only at model time misses the queueing experience.

Raising concurrency can reduce waiting, but if every request slows down through contention for VRAM and bandwidth, throughput need not keep growing linearly.

Little's law ties the average number in flight, the arrival rate and the average time together in a stable system; it should not be applied mechanically to a queue that has lost stability or to a brief peak.

Do not conflate: turning concurrency up without limit is no substitute for rate limiting; the semantics of rejecting, queueing and degrading under overload should be stated.

4. How cancellation and timeouts propagate

After user cancellation, the main task should propagate signals to sub-agents, model requests and cancelable tools. Committed external actions may be irreversible and still need tracking to their final state. Distinguish "not started", "stopped", "completed but no further work" and "state unknown" in cancellation outcomes.

Layer timeouts too: connection timeout, idle-stream timeout, individual-tool timeout and whole-task budget. With little task budget left, do not start a large operation that cannot be canceled. Remaining time is not a hard guarantee, but must influence scheduling.

Recovery after a process restart reads persistent artifacts rather than asking the model where it left off. The model can interpret records but cannot create nonexistent execution facts. Lesson 63's action journal gives a minimal local example.

Engineering case · D08

Operations diagnosis: the critical path, retry amplification and state compatibility after a rollback

Calculate latency and cost separately

Parallel work of 3 and 5 seconds followed by a 2-second merge gives 7 seconds of wall-clock time and 10 seconds of total spans; shortening the noncritical branch need not improve the experience. Four tasks cost 12 and only 2 succeed, so cost per success is 6, not 1 after deleting failure costs. Interpret traces together with outcomes.[TRACE] [EVAL]

Retries and cancellation affect actual state

Three layers with 3 attempts each can amplify to 27 attempts; a shared deadline limits total waiting, but timeout still does not prove the downstream operation never committed. Check in-flight side effects after cancellation and after rollback alike.[IDEMP]

A common rollback-format trap

Old state schema1 has timeout_seconds=5; new state schema2 has timeout_ms=5000. Rolling back only a model or application may leave an old reader misinterpreting new values. The experiment explicitly reads both versions, normalizes each to 5000ms and rejects unknown schemas; it does not guess milliseconds because the number looks large.

The minimum scale of engineering practice

A small project can record versions and idempotent intent in a JSON manifest rather than immediately introducing a distributed event platform. Units, change times, failure states and final acceptance artifacts still need clarity. Complexity should come from actual failure modes, not making an architecture look senior.

Validation in the target environment is still needed

Network queues, actual server rate limits, GPU execution and multitenant loads were not stress-tested here. Local textbook tests prove limited properties of accounting and recovery strategies; they cannot replace actual SLO and capacity tests.

Retry, resume, replay and cancel mean different things for an action

Conditions for this example: an independent long task: op1 read a file successfully, the result of op2's file write is unknown, and op3's test has not started. After a restart, the judgment has to be made from this set of states.

Retry
Try the same operation again.
Resume
Continue an unfinished task from persisted state.
Replay
Replay the events or the computation; side effects must be treated separately.
Cancel
Asks that further progress stop; it does not undo effects already committed.

How to read the changes in the figure

Recovery does not continue from the last sentence of a chat summary; it checks the real state of the actions and the version of the environment.

Event replay is commonly used to rebuild state; if the event handler sends its messages again along the way, a pure rebuild turns into a second round of side effects.

A cancel signal should propagate to the tools and the subtasks, but whether a tool can stop depends on its own contract, and the report should keep the items that remain undetermined.

Do not conflate: implementing all four operations as "run the script again from the start" leaves the reliability of a long task entirely superficial.

5. Circuit breaking, degradation and human takeover

A persistently failing external service can be temporarily cut off by a circuit breaker to avoid exhausting budgets, but distinguish global failures from one resource's permission issue. Degradation may reduce optional retrieval, switch to read-only reports or seek human confirmation; it should not silently reduce quality while retaining a "Verified complete" label.

If the primary model is unavailable, a fallback also needs tool, context and structured-output compatibility checks. Unreadable compaction state may not transfer across models or vendors; preserve understandable task state and access to evidence instead of assuming arbitrary binary state is universal.

Human takeover needs the current goal, executed actions, pending side effects, current version and next step, not a whole unorganized chat history. The person taking over first needs to know what must not be repeated.

6. SLOs and error budgets

Start with the objects and symbols used here
SLI, SLO and the error budget
An SLI is a service level indicator that is actually measured; an SLO is the target for that indicator; the error budget is the room for failure that target allows. They are objects of service operation, not model parameters."The API returned 200" may not be success for the user; some businesses should define the indicator as the proportion of tasks completed correctly within a bounded time.

SLOs should center on user value, such as the share of permitted tasks completed within specified resources and time, or zero unauthorized high-risk actions. Availability, correctness, latency and security are different dimensions that may not combine into one number. Google SRE practices offer methods for defining user-perceived metrics and error budgets.[N51]

Mean latency can hide a few very slow tasks, requiring tail analysis; mean success rates can hide regressions in a language or high-risk scenario, requiring stratification. Alerts should be actionable: persistent tool-permission errors call for configuration checks, not a vague alarm that the model is insufficiently intelligent.

7. Incident reviews return to system boundaries

An agent repeatedly editing a file may result from timeout retries, crash windows, unpersisted state, unstable operation IDs or missing prerequisite versions. Find the smallest reproducible sequence, add the corresponding failure test, then decide which layer to fix. Stronger prompt requests for care cannot replace repaired execution semantics.

Acceptance question: four subtasks each take 30 seconds and the parent 40 seconds. Can you report 120 seconds of execution? 120 seconds may represent total subtask resource time, while user wall-clock time is 40 seconds. Both are useful but need clear names and cannot be interchanged to prove speedups.

1 Unbounded retryResend immediately after failureRequest volume has not fallen and may worsen rate limiting.
2 Exponential backoffAttempt 1 waits 1 second, attempt 2 waits 2 seconds, attempt 3 waits 4 secondsLimits each request's retry frequency.
3 Add jitterStagger randomly within the permitted intervalAvoid all 100 requests waking together every time.
4 Total budgetMaximum retries, deadline and cancellation signalDo not extend the task forever to "Guarantee success".
5 Side-effect checkWrites still need idempotency or verificationBackoff does not remove duplicate-execution risk.

Join the steps up. Reliability is more than extra attempts; retries need bounds from load, idempotency and user waiting.

Limits and counterexamples. 1/2/4 seconds are teaching parameters; real use should respect service retry guidance and business deadlines.
