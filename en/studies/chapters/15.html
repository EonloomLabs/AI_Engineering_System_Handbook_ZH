1. From cognitive categories to storage semantics

Start with the objects and symbols used here
semantic, episodic and procedural memory
Semantic memory keeps facts, episodic memory keeps experiences, procedural memory keeps conditional methods; working memory serves the current task. CoALA is a framework for analyzing this kind of cognitive architecture, and MemGPT studies how a limited context and external storage are organized."Patch p7 failed because a test was missing" is an experience; "Windows has to be supported for now" is a fact; "check the separator when changing path rules" is a conditional procedure, and must not be promoted straight into running the full test suite for every task.

CoALA organizes language agents through memory, action and decisions; MemGPT discusses layered management of limited context and external storage. They help establish structure, but are not production database schemas that must be copied.[N41][N42]

Working memory holds current-task state; episodic memory records specific experiences; semantic memory keeps reusable facts; procedural memory stores methods. Engineering concerns how each item is written, when it applies, what evidence supports it, and how it is retrieved and deleted. A skill file can carry procedural knowledge without every success automatically warranting a new skill.

Start with the objects and symbols used here
checkpoint: you must look at the object that was saved
A model checkpoint saves weights or training state; activation checkpointing saves a few intermediate nodes so they can be recomputed on the backward pass; an agent task checkpoint saves how far execution has got. The three share a name, but what they restore is entirely different. When you see "checkpoint", first ask whether it restores parameters, recomputes activations, or continues a task. An agent saving a summary does not update model weights.

Separate task checkpoints from long-term experience. The former need precise executed actions and unresolved states; the latter should distill information that changes future actions. Permanently storing entire task conversations in an experience database adds retrieval noise and many unproductive guesses.

2. When an experience is worth keeping

Let rediscovering a conclusion cost Cr, its estimated number of correct future reuses be n, writing/maintenance/retrieval cost Cm, and incorrect-reuse loss Ce. Rough net value is then nCr−Cm−Ce. This does not require exact probability calculations; it reminds us that memory also has costs.

For development projects, valuable memories often identify "where the entry point is", "which plausible path was falsified", "why a decision exists" or "which checks catch this error class". Low-value memories are often obvious from code, available in one search or general knowledge without conditions of use. Memory retrieval should replace repeated reading, not add to all existing context.

For example: "This version has a total byte budget for rule loading; if nested rules never enter input, inspect the budget and cwd first, with evidence from a specific commit and function." This changes the next action and is more useful than "remember to check skill loading". Changed code in a new version requires invalidating or rewriting the experience.

Engineering mechanisms and failure boundaries

The old worker comes back after the lease has expired

Worker A holds generation 1; after a timeout B takes generation 2; A recovers and tries to publish, and the conditional write must fail.

Key boundary: a process still being alive is no proof that it still has the right to publish; the model finishing its output is no proof that the artifact is valid.

Follow it further through the source or the engineering basis: tell the source events, the extracted candidates, the integrated artifact and verification at the point of use apart. Do not check only the path that goes well; check the behavior on cancellation, on a version change, and when the result is unknown.

3. Bi-temporality: when a fact is valid and when the system knows it

Suppose configuration changes on day 20, but the system receives evidence only on day 30. "What was the actual configuration on day 25?" and "what did the system know on day 25?" are different questions. One update timestamp cannot answer both.

This book uses valid_from/valid_to for a fact's validity interval, recorded_at for when the record enters the system, while retaining source versions. Queries with at and known_at distinguish late information. Validity intervals are left-closed and right-open so two versions do not automatically take effect at the same boundary instant.

Start with the objects and symbols used here
TTL, valid time and record time
A TTL is an expiry setting on storage or a cache; valid time is when a fact applies; record time is when the system came to know it. An expiry policy cannot stand in for verifying the fact and its source. A rule that takes effect on October 1 is only read on October 10: the business valid time counts from the 1st, while the time the system knew about it counts from the 10th.
Start with the objects and symbols used here
SQL, SQLite and the transaction object
SQL is the language for working with relational data; SQLite is a database engine that embeds into an application. Writing operational state into a database is a persistence action by the harness; it does not modify the model's neural network parameters. One transaction can save the business row in this database together with a pending-send record, but that does not let you infer that the mail service committed atomically along with it.

These are actual SQLite queries, not simulated model memory. The current implementation lacks full transaction-time history, retraction events, concurrent merging and natural-language conflict judgments; it shows how minimal metadata prevent temporal confusion. Whether production needs bi-temporality depends on retrospective queries and late updates; ordinary personal notes need not add it by default.

4. Do not blindly overwrite conflicts with "the latest entry"

Contradictory statements may differ in version, scope or time, or may contain actual errors. Separate these dimensions before deciding whether a conflict exists. With multiple valid conclusions under identical conditions, this book returns conflict instead of choosing one at random.

Model-extracted facts start as candidates and should not automatically become active because they sound fluent. Verification may come from current source, deterministic tests, authoritative documentation or human confirmation. Evidence strengths imply different uses, without requiring a complex grading system; explicit "verified / awaiting verification / invalid" states are usually enough.

Long-term memory must not override the user's clear current constraints. If the user requests no new agents this time, follow that goal even if past experience favors multiple agents. External pages or low-trust tool results especially cannot gain authority through "writing memory"; this is where memory poisoning and prompt injection intersect.

Conditions of use are also memory content

"Retry after a timeout" needs conditions: read-only operation, downstream idempotency or confirmation that execution did not occur. Saving it without conditions as general experience turns a past safe policy into a future dangerous action. Experience entries need at least triggers, provenance, versions, and success/failure boundaries, not just one affirmative recommendation.

Acceptance sequence

First write, retrieve and derive conclusions; then add newly evidenced facts effective retrospectively, retract original sources or change permissions; finally ask about past and present, checking retrieved evidence and final executable actions. Tests of one write and one recall rate cannot reveal this long-term drift.

Scope of guarantees

This experiment governs external records, not base-model parameters, and does not claim legal compliance with deletion requirements. Real systems must also include backups, logs, third-party storage and permission revocation in policy; extend the design for your environment rather than copying one teaching table directly.

5. Retrieval, reranking and context burden

Memory retrieval can narrow by project, module, task type, version and permissions before terms or vectors locate relevant entries. Relevance is not applicability; check lifecycle state before returning results. Whether source code needs reading after memory depends on task risk and information-change speed; current implementation details usually need rechecking.

Memory entries should link to evidence without always loading it in full. A short catalog can be an index, and a file system may suffice. Consider dedicated services or graph databases only when scale, queries or concurrency create actual bottlenecks.

When merging duplicates, keep provenance and conditions of use rather than blending similar experience from different versions into unconditional rules. Deletion and revoked permissions must also propagate to summaries, caches and indexes, not just the main table.

6. A-MEM, Mem0 and graph structures: read critically

A-MEM explores dynamic memory linking, organization and updates; Mem0 discusses extracting and maintaining scalable memory from conversations. Their experiments suggest potential in some organizational methods, but benchmarks, models, data and comparisons each have limits. Paper names or scores alone cannot determine suitability for a code repository.[N77][N78]

Graphs suit problems requiring combinations across relationships, but extracted edges may themselves be wrong, and updates and conflicts become more complex. If the task merely finds a historical root cause by module, a lightweight index may be better. Compare no-memory, static-rule and retrieval-on-demand baselines before adding graphs.

7. Evaluating whether memory really helps

Evaluations such as LongMemEval cover cross-session information use, time and updates, showing why memory evaluation needs more than one factual question.[N35] Real development evaluation should also test whether repeated errors decrease, the first useful location is found sooner, conflicts with current source are corrected, and stale advice is rejected.

Keep a no-memory control. If two searches originally complete a task, but new memory adds three model calls for extraction, retrieval and verification, a correct final result may still not justify it. Evaluate "which costs memory replaced", not merely the number of entries stored.

8. Acceptance questions

Can an experience that works three times in a row become a general rule? Not from the count alone. All three may share a template or version; examine task coverage, shared conditions, counterexamples and change risks. An upgraded rule must remain retractable and state when it should not be used.
