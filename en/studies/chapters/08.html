1. A minimal agent loop actually has three kinds of state

Conversation state describes what the model saw; task state describes goals, completed actions and pending issues; environment state describes actual file, database and service contents. They may disagree. The model remembering a test run does not mean it matches current code; a database record saying "Committing" does not mean the external commit has not occurred.

This book's minimal loop constructs context, gets model-proposed actions, validates, executes, records results, updates state, then decides whether to continue or stop. It need not introduce planning, review, memory and grading agents by default. Add a division of work only when a specific failure mode demonstrates its value.[N01][N30]

For diagnosis, internal events can distinguish proposed, authorized, started, succeeded, failed and unknown. These are local states for side-effect operations; an ordinary file read does not require a complex state database. Task scale and action risk determine persistence granularity.[N87]

2. Why unknown is necessary alongside success and failure

Timeline: a write request reaches a remote service, which executes successfully, but the connection breaks before returning the result. The client sees a timeout and cannot determine execution from local information alone. Treating timeout as failure and resending may create duplicate orders or emails; treating it as success may falsely report completion.

Correct recovery depends on external capabilities: if idempotency keys are supported, query or retry with the same business-operation key; if final state is readable, reconcile it; if neither is available, keep the outcome unknown and seek human confirmation. Retry count is not the core issue; semantics is.

Start with the objects and symbols used here
WAL, fsync and atomic replacement
WAL is the idea of writing a log first and then updating the data by protocol; fsync asks for a file's data to be synchronized to storage; an atomic rename, where it is supported, keeps readers from seeing a half-finished replacement. Visibility and durability after a crash are not the same guarantee. One file renaming successfully does not mean several files and a database committed together; durability also has to be checked against the platform, the directory and the storage behavior.

Local files have a similar window: the file was atomically replaced, but the process crashed before writing a completion log. The next execution must not inspect only log state started and edit again. Compare whether the current artifact already matches the intended result.

3. How this book implements its action journal

Start with the objects and symbols used here
SQL, SQLite and the transaction object
SQL is the language for working with relational data; SQLite is a database engine that embeds into an application. Writing operational state into a database is a persistence action by the harness; it does not modify the model's neural network parameters. One transaction can save the business row in this database together with a pending-send record, but that does not let you infer that the mail service committed atomically along with it.

journal.pyuses SQLite to record task_id/op_id, relative paths, before/after hashes and status. Before writing, it compares current content with expected. If an operation ID already exists with different arguments, reuse is rejected; if the file already equals the target content, recovery marks it reconciled rather than writing again.

The test does not simulate a crash by changing a boolean; it starts a subprocess and, after replacing the file, calls os._exit(75). The parent process then recovers and checks file contents and the journal. This verifies recovery across an actual local crash window. It does not verify power loss, directory fsync, concurrent writers, cross-database transactions or remote Exactly-once.

Start with the objects and symbols used here
ACID, transactions and isolation
A transaction puts a group of database operations inside a defined commit boundary. ACID stands for atomicity, consistency, isolation and durability; the guarantee you actually get also depends on the isolation level, the configuration and the resource boundary. A database transaction committing does not mean another mail service commits along with it. Writing the two operations into the same function does not automatically make a cross-system transaction.

A SQLite transaction constrains updates within its own database, but cannot automatically include external file replacement or remote APIs. Without a shared transaction, two systems need reconciliation, idempotency or compensation; writing transaction_id in a table does not grant atomicity.[N31]

4. Why compare-and-swap is more reliable than applying model patches directly

Start with the objects and symbols used here
CAS, version checks and TOCTOU
CAS is a controlled operation that updates only after comparing that the expected version or value still matches. TOCTOU is the race in which something changes between the check and the use: a separate "look at the version, then write" is not automatically equivalent to an atomic CAS. If a patch was produced from version 7 and the version is already 8 at commit time, overwriting directly should be refused and the work redone; a concurrent insert between the comparison and the write has to be prevented as well.
Start with the objects and symbols used here
HEAD, working tree, ETag and content fingerprint
Git's HEAD marks the commit or branch currently checked out; the working tree may still hold uncommitted changes. An ETag is a validator for an HTTP representation, and what it guarantees depends on the service. A content fingerprint is computed over the bytes; these kinds of version identity are not interchangeable. When the index comes from commit v7 but the file has been modified locally, the same file name does not mean the same content. Applying a patch or citing evidence should be checked against the version actually present.

The model generates a patch from version A while the user changes it to B. An executor that writes without checking overwrites the user's changes. CAS requires current content to still equal the expected content read earlier; otherwise it returns stale and rereads. Versions may use commits, ETags or content fingerprints, depending on artifact boundaries.

Content hashes have meaningful semantics for this concurrency precondition. Hardcoding the full hash of every skill document in tests so mere wording changes cause failure is usually a brittle snapshot. The same technique has different value in different places; neither reject it categorically nor overuse it everywhere.

This book's implementation is a single-writer reference without TOCTOU defenses against malicious processes. The filesystem may change between path checks and opening; production isolation needs directory handles, safe-open flags, containers/sandboxes or permission limits. Do not package a teaching CAS as a security product.

Engineering case · D03

Fault injection: killing the execution process the moment after the side effect commits

Why the experiment must actually exit the process

Raising an exception inside a function may trigger finally blocks, buffer flushes or test-framework recovery; it does not represent a process abruptly disappearing. This book's worker calls os._exit(17) after the downstream SQLite commit, deliberately leaving the confirmation journal at pending. Data is written only in a temporary directory, with no external account or actual payment.

Two databases model different atomic boundaries: external.sqlite stores effects, and journal.sqlite stores execution state. Recovery without an idempotency key writes a second effect; the stable-key path uses a downstream unique constraint to retain one. The experiment demonstrates boundaries, not coverage of network latency, distributed replication or multi-region failures.[SQLITE] [IDEMP]

Look for commit order when reading the source

Locate CREATE/INSERT and commit first, then the crash point and recovery conditions. If the crash occurs before the side-effect commit, both paths may execute only once, so the test cannot distinguish the window that actually needs protection. The valuable point is a fault location that kills an incorrect implementation.

Adapting an existing agent

Start with one specific tool that has side effects: define a business-intent ID and record a normalized argument fingerprint; distinguish not occurred, occurred and unknown in return states; use downstream deduplication when available, otherwise add verification and human recovery. Do not build a universal transaction platform for one local read-only search tool; publishing, deletion and commits still need more than natural-language summaries for tracking.

Unresolved boundaries

This experiment does not verify power-loss durability, database replication, unique-key expiry or consistency across repeated server responses. Production interfaces must also define idempotency retention, same-key/different-argument handling and whether late requests remain valid. The textbook provides a runnable minimal proof, not whole-system exactly-once certification.

Computes a stable identity digest for the final action, then changes the field order and the target environment in turn. Changing the field order should not change the logical identity; changing the target environment should invalidate the original approval.

Key boundary: do not approve a function name alone; the audit log records both what was actually executed and what was presented to the model.

How to read the changes in the figure

One write being "complete" can still mean the content is wrong. Atomicity only deals with a visible half-write; it is no proof that you were working from the latest version.

Checking the hash first and then writing without a lock some time later still leaves room for another process to change the file in between. The comparison and the update must be protected by the same coordinating mechanism.

A database transaction can only wrap the resources that take part in it; recovery and compensation still have to be designed across ordinary files, remote APIs and the database.

Do not conflate: rename/replace, CAS, transactions and fsync are not interchangeable terms: they concern visibility, conditional update, consistency and durability respectively.

5. Completion decisions should be tied to current artifacts

capstone.Harness Record artifact versions at test start and end. If the file changes after tests pass, the green result is invalid, and finish refuses to treat it as current evidence. Even edited comments invalidate this teaching hash; that is a conservative artifact-freshness choice. Large repositories can use dependency-aware strategies, but must prove the risk of omissions acceptable.

Test results also do not mean every user goal is met. A feature may pass tests but lack migration, documentation or deployment steps. Check necessary completion items against the task's original requirements, instead of demanding heavy deliverables for every project by default.

Recovery needs stopping conditions too. When the model hits the same tool failure twice with no new evidence or changed action, switch locating methods or explicitly report a block instead of looping until the budget is exhausted. Recoverable transient rate limits can use backoff; permission denials must not be bypassed by changing commands.

Mutation testing can deliberately put a wrong implementation back in; if everything is still green, the tests have no discriminating power.

Formatting, generating code or changing configuration after verification also changes the object, so the affected checks have to be run again or shown not to be affected.

Do not conflate: "the tests found no problem" cannot be rewritten as "there is no problem at all", least of all when both coverage and environment are limited.

Mechanism basis:[SWEBENCH] [HARNESS]. The numbers and harness setting in this example are an explicitly given teaching construction, not commercial model output or a production performance measurement.

6. Boundaries between a single agent and deterministic control

What belongs to the model? Uncertain locating, candidate plans, evidence connections and trade-offs. What belongs to the program? Parsing, authorization, file-version comparisons, idempotency keys, timeouts and billing budgets. Not every business judgment can be made deterministic, but reliably verifiable parts should not depend only on telling the model to "Be careful".

Planning can be a short task-state record rather than a separate agent. Review can check the diff and tests in current context without rereading the whole repository every time. A database can be a local file rather than beginning with an event-bus design. The goal is fewer actual failures, not the maximum number of architectural components.

7. Acceptance questions

A subprocess crashes after writing a file; on recovery, the file matches neither before nor after. What should happen? Treat it as an external edit or state conflict, stop overwriting, preserve evidence and investigate again. Do not guess which version is "more reasonable".

A cancellation request was sent; can every side effect immediately be declared stopped? No. The executor's cancellation support and the operation's state when cancellation arrives must be known. Irreversible external actions still need reconciliation. A reliable agent is first a reliable execution system, then a high-quality language model.
