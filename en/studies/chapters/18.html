Contracts express observable behavior, counterexamples expose errors, tests bind to versions, and review addresses risks tests miss.

Related step-by-step process: A test looks for counterexamples; it does not stamp code green. The rest of this section goes on to show the computation and the engineering limits in more detail.

1. Define behavior before choosing a process

Task success first depends on user needs, existing system constraints and behavior that must stay unchanged. For exclude, specify path bases, directory-rule matching, wildcard support, case sensitivity and separator semantics. Without a clear contract, AI-generated tests merely confirm the model's guesses.

A simple change needs no pages of formal specifications, but ambiguities affecting results should be removed. Two or three executable examples often suffice; complex compatibility migrations need finer input, state and error semantics. Actual risk determines design depth.

Engineering environments should also make builds, tests and architecture boundaries easy for agents to find. OpenAI's harness-engineering article emphasizes repository workflows with knowledge and verifiable constraints; SWE-agent research shows operating interfaces affect coding results. Neither implies buying a large orchestration platform.[N86][N79]

How to read the changes in the figure

The third row has to be defined first, or several different implementations could all claim to be reasonable. Acceptance turns the vague word "directory" into a precise scope.

A test should not only exercise the new path but also show that the matching scope was not widened and the interface not broken.

On that basis an agent can report which items passed and which lack evidence, instead of only saying "the feature is implemented".

Do not conflate: more acceptance conditions are not always better; keep the conditions that tell a genuinely wrong implementation apart, and avoid treating internal implementation details as an external contract.

2. The testing pyramid and target errors

Unit tests quickly locate local logic; integration tests check module boundaries, real storage and protocols; end-to-end tests verify user flows but are usually costlier and more environment-sensitive. Test combinations should cover risks, not a fixed numerical ratio.

For example, testing only that a.py is excluded does not catch incorrect basename handling of src/a.py. Counterexamples need same-named files at different paths, directory boundaries, Windows separators, empty rules and parent traversal. Each assertion should match a contract or failure hypothesis rather than produce many duplicate happy paths.

Record test commands, exit codes, test counts, skipped items and environments. Zero exit status with no tests discovered is not a functional pass; skipping critical tests for missing dependencies cannot be summarized as "all passed".

Engineering mechanisms and failure boundaries

Fix non-blocking problems directly

Split review findings into architectural errors and local naming problems; the latter go straight into implementation and verification, while the former change the plan first.

Key boundary: do not escalate every problem into a redesign; measure whether rework and defects really do go down.

Follow it further through the source or the engineering basis: connect the work with recoverable state, functional acceptance and minimal checkpoints. Do not check only the path that goes well; check the behavior on cancellation, on a version change, and when the result is unknown.

For the complete mechanism and the continuous example see How does a long task avoid starting over each time, or finishing falsely?; this section keeps its original derivation and experiment, and the two accounts work at different levels rather than replacing each other.

Evidence and the limits of understanding: more roles and reset policies for a long task are not better; after a model upgrade, compare against a trimmed-down mechanism instead of always applying the longest process.

Verification basis:[A06] [A13] [A01] [D07]. The source is limited to commit 86e17e98c7f9 and the paths actually read; article experience, public documentation and original teaching experiments are labeled separately. See how it was obtained, what was read, and the limits.

3. Property-based and metamorphic testing

Some behavior suits invariance checks: separator normalization preserves results; adding unrelated rules when none match preserves results; KV cache chunking preserves logits; changing the authorized user prevents reuse of someone else's cached results.

Without complete expected answers, metamorphic testing derives output relationships through input transformations. It supplements example tests, but the relationship must be correct. "Adding any exclusion rule should preserve results" is false, because a matching rule should change them. Do not treat invented patterns as truths.

Numerical implementations suit finite differences, conserved quantities, symmetry and high-precision baselines; agent flows suit fault injection, permission boundaries and version conflicts. Handing everything to LLM graders loses strong evidence available from deterministic mechanisms.

4. Mutation: prove the tests really catch errors

Remove a causal mask, reset RoPE positions, remove user identity from a cache key or make finish ignore versions, then rerun tests. Corresponding failures show sensitivity to the target errors. If deliberately introduced bugs leave everything green, tests cover lines but not semantics.

Mutation scores alone cannot represent quality. Many mechanical mutations have no business meaning, and some equivalent transformations should not fail tests. Negative controls designed for real failure modes matter more than blindly trying to kill every mutation.

Snapshot tests suit stable output contracts, but fixed hashes for natural-language descriptions, entire skills or unrelated formatting turn reasonable edits into regression noise. Bind tests to behavior that must remain, not the exact shape of a whole text.

5. How review avoids an endless loop

Google's review standard emphasizes improving overall code health rather than endless perfection. Reviews can focus on design, functionality, complexity, tests and readability; fix and reverify small issues directly instead of restarting design every time.[N50]

Prioritize high-consequence issues: incorrect writes, races, transaction boundaries, broken compatibility, expanded permissions and weakened tests. Let existing project tools handle style where possible. Naming preferences must not obscure functional defects, and "not a major issue" must not dismiss real risk.

Independent review suits complex or high-risk changes; simple configuration changes may need only focused tests. Compare review costs with the defects, rework and incidents avoided. Simplify a process that only lengthens tasks without observable gains.

How to read the changes in the figure

Proportionate review does not mean doing fewer tests; it means matching the strength of verification to the real risk.

An independent reviewer should have a definite checking task, such as looking for a race counterexample, rather than restating the author's explanation over again.

Measure what a review gains by the defects actually found, the rework and the time; do not take the length of the report or the number of rounds as quality.

Do not conflate: piling on more reviewers when the model is uncertain can let correlated errors be reinforced by more text; supply real evidence or change the method of verification instead.

6. Verification freshness and artifact ownership

Passing tests must match current code. Changing files afterward does not automatically preserve old results' validity. This book detects changes through file-version hashes; larger systems may reuse results by dependency scope, but need reliable dependencies and build caches. A model deciding "it is only a small change" cannot justify skipping necessary verification.

Also protect uncommitted user changes, inspect the current diff scope, and identify generated files, lockfiles and configuration changes. A model may fix one issue while deleting intentionally retained code; check the final report against the actual diff rather than listing files from chat memory.

Deployment is a separate action. Local test passes do not mean code is live; merging a PR does not establish production health; rollback viability depends on migrations and external side effects. State each stage's actual completion without inventing production verification.

How to read the changes in the figure

First check whether anything actually ran, then check which version was tested, and last check whether the cases can hit the target defect. All three gates are needed.

Mutation testing can deliberately put a wrong implementation back in; if everything is still green, the tests have no discriminating power.

Formatting, generating code or changing configuration after verification also changes the object, so the affected checks have to be run again or shown not to be affected.

Do not conflate: "the tests found no problem" cannot be rewritten as "there is no problem at all", least of all when both coverage and environment are limited.

7. A concise but sufficient delivery

Include what behavior changed, why it was needed, main impact scope, verification run and remaining limits. Complex tasks can add key decision reasons; simple tasks need not fill templates. If evidence is insufficient, identify the exact gap rather than end with a vague "further testing recommended".

Acceptance question: a model patch passes every existing test but misses the user's new requirement. Where does responsibility lie? The tests omit the new contract and cannot replace requirements acceptance. Add tests for the new behavior and verify old behavior remains. AI engineering quality is still software engineering quality first.
