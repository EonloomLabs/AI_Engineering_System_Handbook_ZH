Start from concrete objects and small examples, to understand the computation and the conditions under which it applies.

Start by separating two input settings

The long and short sentences "我爱学习" and "你爱" serve only to explain padding; PAD adds no real text. The worked training run always uses the two complete samples "我爱学习！" and "你爱学习！", with BOS/EOS added; they are the same length. The complete samples, the inputs and the labels are all set out explicitly below, and the IDs of the padding example are never treated as the training record of another model.

Step-by-step figures · Lesson 38

Batching does not blend two sentences into one

Will PAD, added to make things tidy, be mistaken by the model for content?

Batching is like feeding several exam papers into the machine together, yet each paper is still marked on its own. Padding makes them occupy the same number of positions; the table of valid positions tells the model which cells are only filler. A tidy array shape is no substitute for the real length information.

B How many inputs there are in this batch.
T How many positions the array allots to each input.
PAD A placeholder, not a word added to the original text.

Input and conditions of use: B=2, T=3, right padding. Visibility and output-position selection must follow this convention.

Why it is needed

Many tensor operations require regular shapes, and batching can improve device utilization.

How to implement it

Short sentences are padded out while still carrying their true length and a matching mask; which side a generation interface requires padding on must be checked separately.

Possible costs and misreadings

Padding with 0 but not masking, or taking the last column unconditionally, can each change the result for a short sentence.

How to tell whether it was done right

Runs the same sentence alone and then in a batch of mixed lengths, and checks its output at the valid positions.

Mechanism source:[PADDING] [SDPA]. The numbers and the run setting are a teaching example explicitly specified by this book; the cited source does not replace the explanation on this page.

"Batching" means letting several inputs be processed together

Processing "我爱学习" on its own is a single input. Putting "我爱学习" and "你爱" into the same computation is called a batch. This batch holds 2 inputs, so the batch size is B=2.

Key difference: Batching organizes several inputs into one device computation; it does not join two sentences into a single one.

Easy to misread: Different users' inputs in the same batch do not thereby share an attention context.

They are still two independent inputs; the second sentence is not appended to the first. The batch axis provides a way of organizing them to be "scheduled together", and the standard independent-sample computation does not let two samples read each other's content. Batching is never a reason to mix different users' contexts together.

The two ID sequences from the previous lesson are:

第0条：[1,2,3]      长度3
第1条：[4,2]        长度2

To lay them out as a regular rectangular table, every row has to be the same length. We set the length allotted for this batch to T=3 and pad the second row with one placeholder ID 0:

input_ids = [[1,2,3],
             [4,2,0]]
shape     = [2,3]

Padding adds placeholder items to a short input; it does not add meaningful new content to the original words. ID 0 happens to be PAD in this book; a real model may use a different PAD ID, and may need it handled according to the model configuration.

A true length and an allotted length are not the same thing

The second row's true length is still 2, while the table allots 3 positions. If a production system padded this whole batch to 128, the shape would be [2,128]; this is no proof that either original sentence contains 128 tokens.

Key difference: Padding the shorter sentence to the same length gives [[1,2,3],[4,2,0]].

Easy to misread: PAD is a placeholder, not text from the original sentence.

To tell the later computation which positions are real content, a second marker table goes with it:

is_real = [[1,1,1],
           [1,1,0]]

Here 1 marks a real position and 0 a padding position. This is the basis of the padding mask that comes later. For now, read "mask" as a marker that decides whether an item may take part in a computation; the full attention mask has to wait until F12 for its rows and columns to be explained properly.

How two sentences become ten training questions

Each complete sample has 6 items:

第0条：[6,1,2,3,5,7] = BOS 我 爱 学习 ！ EOS
第1条：[6,4,2,3,5,7] = BOS 你 爱 学习 ！ EOS

The input takes the first five items and the label the last five. This model shifts them only once, during data preparation:

Input positionPrefix it may useSupervision target
t=0BOS我 (你 in the other sample)
t=1BOS 我爱
t=2BOS 我 爱学习
t=3BOS 我 爱 学习！
t=4BOS 我 爱 学习 ！EOS

What difference does padding on the left or the right make

Right padding writes the second row as [4,2,0]; left padding would write it as [0,4,2]. Both can express "你爱", but the real positions sit in different columns.

What difference does padding on the left or the right make: item by item
Approach / object ATrue lengths: [3,2]
Approach / object BLength allotted in the tensor: 3
Approach / object CValid positions: 111 / 110

Key difference: Both the true valid length and the array width after padding have to be kept; the mask depends on the valid positions.

Easy to misread: An array with 3 columns does not mean the second sentence has 3 real tokens.

If a program always takes "the prediction in the last column" to continue generating, the last column of a right-padded row is PAD, and the wrong position may be taken. Some decoding flows therefore require left padding, or require the last valid position to be selected by the true length. Which strategy is correct depends on the generation code and the model's conventions, so neither side can be called the universally best approach.

This book's foundation examples use right padding because it is intuitive for a first reading; when generating, take the last valid position of each row explicitly, and do not simply copy [:, -1].

Padding is not truncation, and still less is it context compaction

Padding adds placeholders; truncation deletes part of an over-long input; summary compaction tries to replace a long history with a shorter description. Deleting real content can make a rule or a piece of evidence disappear; padding has no such purpose.

Padding is not truncation, and still less is it context compaction: item by item
Approach / object ARight padding: 4,2,0
Approach / object BLeft padding: 0,4,2
Approach / object CThe positions and the read-out position differ

Key difference: The padding side changes the index of a valid token in the array, and decoding has to handle that accordingly.

Easy to misread: The last column should not be taken blindly as the last valid token.

Batching also does not always have to force every request into the same rectangle. High-performance inference can group by length or organize variable lengths. This lesson uses an ordinary dense table to explain shape, and does not dress it up as the real internal storage of every service.

Why batching can be faster, and can also make one person wait longer

One set of parameters can compute over several inputs at once, which may use the hardware more fully. But waiting to fill a batch adds to the waiting time of some request. There is another kind of waste: padding one input of length 2 and one of length 1000 both to 1000 produces a great many padding positions.

Why batching can be faster, and can also make one person wait longer: item by item
Object onePadding: add placeholders
Object twoTruncation: drop a stretch of content
Object threeCompaction: keep a summary

Key difference: All three operations can change the input length, but they lose information by entirely different mechanisms.

Easy to misread: Do not call everything that "got shorter" compaction.

So larger B and T are not simply better. B says how many inputs are organized in parallel; T affects how many positions each one is allotted. Hardware, caches and queues come into the discussion later. For now it is enough to be able to write out the ID table and the valid-position table from a real input.

Why "你爱" has a 0 at the end without gaining an extra word

Local check example: the input below follows the conditions listed for this example, and its intermediate values cannot be joined to the calculation record of the worked model.

Input and conditions. The first sentence, "我爱学习", is [1,2,3]; the second sentence, "你爱", is [4,2]. We want to put them into the same two-row table.

Steps and objectsInternal actionIntermediate result / new state
1 Compare the lengthsThe two sentences have 3 and 2 tokensAllot a common length of 3; the true lengths must not both be recorded as 3.
2 Pad on the rightPut PAD, ID 0, at the end of the second rowThe ID table is [[1,2,3],[4,2,0]].
3 Record validityThe first row is all true; the end of the second row is falseThe valid-position table is [[1,1,1],[1,1,0]].
4 Choose the position when predictingThe first sentence takes index 2, the second index 1Index 2 of the second row is PAD and must not be taken as the position of 爱.
5 Work out the utilization5 real tokens in 6 allotted positionsThe placeholder share is 1/6; variable-length batching can be implemented differently and need not pad everything into a rectangle.

Join the steps up. The 0 marks a cell occupied for the sake of tidiness; it does not add new text to "你爱". Real tokens and placeholders must stay distinguishable throughout.

Limits and counterexamples. Some off-the-shelf generators require left padding; this example explains the object semantics of right padding, and makes no promise that every generation API picks the last valid position automatically.

Show the answerHide the answer
