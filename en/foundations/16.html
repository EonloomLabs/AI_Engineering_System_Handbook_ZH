Training: give every position a "what comes next" question

Why does training see the whole sentence while generation can only move forward?

In training the answers sit in the marking area of the paper, so the questions at every position can be prepared at once; the mask is what keeps the model from reading its own answer. In generation the later tokens have not been decided yet, and the prefix of the next question depends on the choice made for this one. The two share the causal prediction objective, but what is already known differs.

Label the true next token used for scoring.
Cross entropy in this example, the negative logarithm of the probability of the true target.
Number of valid targets the number of positions that actually take part in scoring; it need not equal the padded length.

Input and conditions of use: Label alignment uses a 5-item sequence; the single-position cross entropy and the PAD average are each an explicitly independent small example, and those probabilities are not passed off as coming from the model in the alignment figure.

Why it is needed

Use a clear prediction task to connect parameter updates to the relationships in a language sequence.

How to implement it

Shift the labels correctly, limit visibility, mask invalid targets and normalize by the number of valid ones.

Possible costs and misreadings

Peeking at the future produces pretty but false training results; duplicated or leaked training samples also overstate generalization.

How to tell whether it was done right

Verify every input position and target position on a tiny fixed sequence, then verify that PAD does not affect the effective loss.

First line up "what is to be predicted"

There is a token sequence [a,b,c,d]. Next-token training can be organized like this:

Key difference: In training the target moves one token to the right, and the model cannot steal the answer by looking at future labels.

Easy to misread: Getting the alignment between the input position and the supervised target position wrong trains the wrong task.

输入位置：a  b  c

Start with the objects and symbols used here
Labels, teacher forcing and shift
A label is the correct target to compare against; next-token training lines each input position up with the token after it. Teacher forcing computes with the real prefix from the data rather than replacing it with what was just sampled. Independent example: for the full sequence [a,b,c,d] the input [a,b,c] can be paired with the labels [b,c,d]. When the interface already shifts them, do not shift them a second time outside it.

The position of a predicts b from a, the position of b predicts c from ab, and the position of c predicts d from abc. A label is the correct answer to compare against this time; teacher forcing means using the real prefix from the data during training, rather than always using a prefix the model has just generated itself.

Why not predict a from the input a? Because that objective would become copying a known input rather than learning what comes next. A real model's API may shift the labels internally; shifting them again in outside code gets it wrong by two positions, so the boundary of responsibility has to be confirmed.

What teacher forcing actually "feeds" in

When training position t, the real prefix from the dataset is used, rather than letting the model draw a word first and then feed its own error onwards. This way of training, conditioning on the real history, is called teacher forcing. It allows the losses of many positions in one batch to be computed in parallel.

At inference time there is no real next word, so the only way to continue is with the result just selected. A low training loss therefore cannot automatically prove that long-form generation is stable: the prefix the model meets at inference may be an erroneous combination of its own making, which has already drifted away from the training distribution.

With only two sentences, why the final loss still cannot be 0

Position 0 of the input is BOS in both samples, but one target is "我" and the other is "你". With the same input and the same parameters, the model cannot give two mutually contradictory certain distributions. The most appropriate allocation is 0.5 each; the combined loss of these two questions is 2×ln2, which spread over the ten questions is ln2/5≈0.138629. When the training loss is later seen to stop at this order of magnitude, the ambiguity of the data should be understood first, rather than concluding immediately that the optimizer is broken.

Basis: tiny_model.py:14–21; Matching parameters, forward pass and gradient records.

Cross entropy starts from one correct candidate

Suppose the correct next token is c and the model gives it a probability of 0.8. One commonly used loss is−ln(0.8)≈0.2231. If it gives only 0.2, then−ln(0.2)≈1.6094, and the error is larger.

Key difference: The lower the probability of the correct item, the larger the penalty; the loss measures the probability the model assigns to the correct item.

Easy to misread: Cross entropy is not "the score minus the correct label's ID".

This negative log probability of the correct target is the cross-entropy loss under a single correct label. The closer the probability is to 1, the closer the loss is to 0; the smaller the probability given to the true label, the larger the penalty.

Start with the objects and symbols used here
Σ: sum term by term over the subscript
Σ is shorthand for addition. The subscript says which term varies; a subscript that is not summed over stays fixed. It is not an extra parameter, and it does not mean concatenating arrays. Independent micro-example: Σᵢ xᵢyᵢ with x=[1,2] and y=[3,4] is just 1×3+2×4=11.

If the correct candidate is expressed with one-hot, that is, a row of zeros the length of the vocabulary with only the correct item set to 1, written y, then the general form is L=−Σ_i y_i ln p_i. Because the other y_i are 0, only the correct item is left at the end.

Start with the objects and symbols used here
∂, ∇: partial derivative and gradient
∂L/∂w asks how the loss L changes when w changes a little while the other independent variables are held fixed. These rates of change across many parameters make up the gradient ∇L. They are derivative notation, not two ordinary numbers divided by each other. Independent micro-example: for L=w², the gradient at w=3 is 6. In the simplest update w←w−η×6, η is the learning rate.

The derivative with respect to the pre-softmax scores z simplifies to∂L/∂z_i=p_i−y_i. This explains why training pushes the score of the correct item up and the scores of the wrong items down; it then travels back through the output matrix and the layers to the earlier parameters.

How several positions and the padding are scored

The loss is computed for every valid target position and then summed or averaged. A PAD position should usually not be treated as a real language target; instruction tuning may also score only the assistant's output. This is what a loss mask is.

How several positions and the padding are scored: item-by-item distinctions
Approach / object AThere are 3 valid positions
Approach / object BPAD or ignored labels are not counted
Approach / object CThe denominator should be the total number of valid tokens

Key difference: When accumulating across micro-batches or across a distributed run, normalize by the total number of valid tokens.

Easy to misread: Averaging each batch separately and then taking an unweighted average of those averages can change the objective when the lengths differ.

If the real lengths differ from batch to batch, averaging per sample and averaging per valid token can give different weights. When reporting a loss, you have to know what the denominator is. A smaller number alone is no grounds for asserting that learning has improved.

Perplexity is commonly the exponential of the average negative log likelihood. It is only suitable for direct comparison when the tokenization, the data and the scoring conditions are comparable; it is not a single index of cleverness for any two models.

The training objective is not "the bigger the score the better"

The output head in F14 produces 8 candidate scores for every position. Raising all the scores alone would not change the softmax probabilities, and the model would be no better at predicting. What training needs is this: under each real prefix, give more probability to the corresponding real next token.

The label for item 0 at t=2 is 3, "学习", and the predicted probability is 0.207640682556. The negative-log loss for that question is:

ℓ[0,2] = −ln(p[0,2,3])
       = −ln(0.207640682556)
       ≈ 1.57194618082

The closer the probability is to 1, the closer the negative log is to 0; the closer the probability is to 0, the larger the penalty. An independent comparison: with the correct candidate at 0.5 the loss is ln2≈0.693147, and at 0.1 it is about 2.302585. This is a score against the training objective, not a direct assessment of the factual quality of a whole passage of text.

Why the cross-entropy formula can be written with logsumexp

Let one row of logits be z and the target ID be y:

pᵧ = exp(zᵧ) / Σⱼ exp(zⱼ)
−ln(pᵧ) = −ln(exp(zᵧ)) + ln(Σⱼ exp(zⱼ))
        = −zᵧ + logsumexp(z)

logsumexp(z) is not "take the log of each logit and add them up", but take the exponential of each logit, add them, and then take the log. For stability it is actually written m+ln(Σ exp(z−m)), with m=max(z). This preserves the same shift invariance as softmax, and avoids the numerical problem of computing a tiny probability first and then taking its log.

Basis: tiny_model.py:101–107; Matching parameters, forward pass and gradient records.

Why the gradient becomes p−onehot, and why the conclusion cannot just be memorized

For one score zⱼ, the derivative of the first term −zᵧ is: −1 if j=y, and 0 otherwise. The derivative of the second term with respect to zⱼ: differentiating the ln first gives 1/Σ exp(z), and then differentiating the sum of exponentials gives exp(zⱼ), and the product is exactly pⱼ.

So the derivative of one question with respect to zⱼ is pⱼ−1[j=y]. This training loss is the average over the ten questions, so each question is multiplied by a further 1/10. The onehot here only expresses "which column is the real target"; it is not a token embedding, and the code is not required to construct it explicitly first.

The gradient in the cell of the correct candidate is negative, so gradient descent will tend to raise its logit; the other cells are usually positive, which tends to lower theirs. What is actually adjusted, though, are the shared parameters, not this row of logits directly and permanently. The gradients of different training questions with respect to the same parameter also add up.

Basis: tiny_model.py:101–107; Matching parameters, forward pass and gradient records.

How shifting the logits relates to the row sums of the gradient

This row of Gz should sum to 0: the probabilities sum to 1, the onehot sums to 1, and subtracting and then dividing by N still gives 0. If all the logits are increased by the same number, the probabilities do not change and the loss does not change, so the rate of change along the "all-ones direction" is 0. It is a good numerical self-check, but passing it does not prove that the whole model implementation is correct.

The parameters have not been updated yet

At this point we have a scalar loss and the local gradient with respect to the logits. Making Wq, the embedding and the rest change requires propagating this effect back along the forward dependencies. The complete backward chain is in the training chapter of the system mechanisms, tracing from the output head all the way to the embedding; this section goes on to check how the optimizer uses these gradients.

Gradient accumulation computes and accumulates the gradients over several small batches before updating once, so as to simulate a larger effective batch; it does not make the activation storage for one extremely long input disappear by itself. How the gradients are scaled has to correspond to the way the loss is averaged.

Key difference: One training update has a definite order; when gradients are accumulated, zeroing and scaling matter especially.

Easy to misread: Zeroing the gradients and updating the parameters must not be swapped in the step diagram.

Why Adam keeps extra state

The training notation in this section: g is the gradient of the current parameter; m is a moving average of the gradient; v is a moving average of the squared gradient; β₁ and β₂ are the smoothing coefficients that are set; t is the optimization step number; a hat, as in m̂, denotes a bias-corrected quantity. The lowercase v here is not attention's Value, and β is not the shift parameter in LayerNorm. m and v are updated as the training steps proceed and take up extra storage; they are not token features of this input.

Key difference: Adam maintains statistics of the gradient history; it does not just subtract this round's gradient directly.

Easy to misread: Adam's extra state increases training memory, which cannot be estimated from the weight bytes alone.

Start with the objects and symbols used here
Optimizers, Adam and AdamW
An optimizer turns gradients into parameter updates. Adam also keeps, for every parameter, a moving average m of the gradient and a moving average v of the squared gradient; these are training state, not attention values. AdamW decouples weight decay from the adaptive gradient update. Independent first-step example: with g=2, old m=0 and β₁=0.9, the new m is 0.2, and after bias correction m_hat=2. The 0.2 cannot be taken as the full size of the update.

The simplest gradient descent uses only the current gradient g. Adam also keeps a smoothed average m of the gradient and a smoothed average v of the squared gradient, which help adjust the step size for each parameter. Schematically:

m新 = β1×m旧 + (1−β1)×g
v新 = β2×v旧 + (1−β2)×g²

β is a smoothing coefficient between 0 and 1, not a word meaning the model has learned. Because the initial value is often 0, the average is too small at the start, so a bias correction is applied. At the first step with g=2 and β1=0.9, for instance: m=0.2, and dividing by 1−0.9 gives the corrected 2.

The corrected m is then divided by the square root of the corrected v, and the update follows. AdamW treats weight decay as a decoupled operation. The complete formula is in the advanced chapters; this lesson explains "why m and v have to be stored as well" first, which also shows that training VRAM cannot be counted from the weights alone.

First say which stage really changed the model

loss.backward computes the gradients; optimizer.step applies the update. They are usually two calls. If the gradients have merely been computed without a step, generation behavior will not change by itself just because "the model has seen the answer".

The simplest SGD rule is w_new=w_old−ηg, where η is the learning rate and g is the current gradient of the parameter. A negative g increases w and a positive g decreases it; "descent" refers to the attempt to lower the loss, not to every parameter having to get smaller.

Which two extra tables AdamW keeps

Every parameter cell has two corresponding pieces of history: m, an exponential moving average of the gradient, and v, an exponential moving average of the squared gradient. The closer β is to 1, the more history is usually retained. What v stores is the squared gradient, not the variance of the parameter, and not a Value matrix.

m_t = β1 m_(t−1) + (1−β1) g_t
v_t = β2 v_(t−1) + (1−β2) g_t²
m̂_t = m_t / (1−β1^t)
v̂_t = v_t / (1−β2^t)
w_t = (1−ηλ) w_(t−1) − η m̂_t / (sqrt(v̂_t)+ε)

m and v start at 0, so early averages are biased towards 0, and the bias-correction denominator serves to cancel this effect of the initialization. ε prevents the denominator from being 0. Decoupled weight decay shrinks the parameters independently; it does not add λw into the gradient first and then compute m and v, which would be a different algorithm.

Once the parameters are updated, the intermediate results have to be recomputed

After the first update, the loss for the whole batch falls from 2.244673168 to 1.980760052. The next Q/K/V, RMS denominators, shares and logits all have to be recomputed with the new parameters; the old computational graph cannot be taken as the backward record for the new parameters.

Gradient accumulation deliberately merges the contributions of several micro-batches; it has to be told apart from the unintended accumulation caused by forgetting to clear the gradients.

What the learning rate, gradient clipping and AMP each do

The learning rate controls the size of the optimizer's update step; gradient clipping limits the overall magnitude of the gradients; mixed precision changes the numeric representation and the computation. Under AMP loss scaling, the official procedure is to unscale before clipping, or the threshold acts on gradients that have been artificially enlarged.

The worked model uses CPU float64, with neither AMP nor clipping enabled. What is described here is the production boundary; a GPU process that was not run is not dressed up as an experimental result.

Basis: tiny_model.py:195–219; Matching parameters, forward pass and gradient records.

Learning to train is not learning to generalize

The training set is used to update the parameters; the validation set is used to choose approaches and tune settings; the test set is used to evaluate relatively independently. Putting the test answers into training, or repeatedly tuning the prompt against test results, contaminates the evaluation.

Driving the loss very low on a fixed short sequence only shows that this training process learned that distribution; it is no grounds for claiming that the model can understand arbitrary language. A real engineering result also depends on new tasks, new data, stability and cost.

Start with the objects and symbols used here
BOS / EOS: sequence boundary markers
BOS is usually the special token for the start of a sequence and EOS the one for the end; a particular model or message template may use different names, counts and end markers. They are symbols in the input/output protocol, not proof of semantic correctness. Meeting an EOS does not automatically cut attention between two training samples; isolating the reads still needs a mask, or a sample boundary the implementation supports.

Running through the formula once is no grounds for declaring it learned

Now data preparation, the forward pass, the loss, the backward pass and AdamW go into a real loop. The experiment fixes two sequences and uses this same small batch at every step; there is no hidden data augmentation, and no pre-written continuation rule is passed off as model output.

Saving the training artifacts: what the weights must come with

This package saves weights_initial.json and weights_trained.json, which contain the model configuration and the parameter arrays. JSON was chosen so that every number can be inspected and so that the standard-library inference can load them too; it is not a recommendation to use JSON instead of an efficient weight format for large-scale models.

eval() is not the same as turning gradients off

model.eval() switches a module's training flag, so that dropout, for instance, no longer drops at random and BatchNorm uses its corresponding evaluation behavior. It is not an autograd switch. torch.no_grad() and torch.inference_mode() control the recording of gradients or a stricter inference optimization; they do not switch every module to eval by themselves either.

This model has no dropout and no BatchNorm, so train and eval give the same numbers, which does not mean every real model does. The package also has an independent dropout test: adding no_grad alone still zeroes at random; eval can make dropout behave as the identity; and gradient computation can still be enabled under eval.

Basis: tiny_model.py:101–107; Matching parameters, forward pass and gradient records.

Why dropout breaks "the same input gives the same output"

An independent rule: during training a proportion p of the activations are zeroed, and the items kept are usually scaled by 1/(1−p) so that the expectation is unchanged. At evaluation time there is no random zeroing and no further scaling up. One random forward pass and a forward pass without dropout cannot be required to agree cell by cell.

SDPA is a function interface, and its dropout_p is passed in by the caller. Even when the enclosing module is in eval, the correct value of 0 still has to be passed to disable it; it cannot be assumed that the function reads the enclosing state by itself.

Basis: tiny_model.py:101–107; Matching parameters, forward pass and gradient records.

Why gradient accumulation so often gets the denominator wrong

An independent loss example: micro-batch A has 2 valid questions, a total loss of 4 and an average of 2; micro-batch B has 8 valid questions, a total loss of 8 and an average of 1. The correct average over all 10 questions is (4+8)/10=1.2; averaging the two averages gives (2+1)/2=1.5. The relative weights of the corresponding gradients are changed too.

The numerator and the denominator must correspond to the same set of valid targets
Step / objectWhat actually changes at this step
Micro-batch A2 valid tokens; loss sum 4.
Micro-batch B8 valid tokens; loss sum 8.
Combined correctlyNumerator 4+8, denominator 2+8, average 1.2.
Combined wronglyAverage each one first, then take an equal-weight average of 2 and 1, giving 1.5.

This is an independent arithmetic comparison, not the loss at some actual training step of the worked model.

Distributed training also requires knowing whether gradient synchronization sums or averages, and whether the framework has already applied the scaling. Do not divide by the world size or the number of accumulation steps a second time. Hugging Face has publicly explained a fix for this kind of gradient-accumulation normalization; this book takes it as a historical lesson and does not claim the current library still has that defect.

What to validate in order to know the model has not peeked

Fix a prefix and change a later token: the logits at the prefix positions should not change; running the same sample on its own and putting it into a separate batch should give the same result; swapping the order of the batch should swap the results correspondingly. These check causality and sample isolation; they do not assess semantic ability.

This model's negative control deliberately turns the causal mask off, to confirm that the test for "a change in the future does not affect the prefix" catches the error. A correct implementation passing is not enough on its own: it also has to be known that the test fails when it meets a broken implementation.

Basis: tiny_model.py:101–107; Matching parameters, forward pass and gradient records.

The validation set, overfitting and the limits of this experiment

Formal training should have an isolated validation task, control of data leakage, evaluation on the target domain and reproducible data processing. The worked model uses two sentences over and over and has no credible generalization score. This book does not dress up the continuation accuracy on those same two sentences as a validation-set success rate.

Follow-up: how exactly is the parameter W "taught" by language data?

One sentence forms several real prefixes and next-token labels. The current W affects the probabilities in the forward pass, cross entropy scores the probability of the label, the backward chain rule computes the local effect of every cell of W on this loss, and the optimizer updates step by step according to those effects. No single step writes the meaning of a word directly into a column of labels.

Could input_ids and targets be made exactly the same, with the shift removed?

Show the answer
That would mainly train "predict the current token from itself", not the next-token conditional probability this book is about. The relationship between the input position, the visible prefix and the target position has to be explicit; the shift is usually done only once.

If two micro-batches have 2 and 8 valid tokens respectively, does averaging the two micro-batches' average losses equal the average over all 10 questions?

Show the answer
Generally not. The correct way is to add the two batches' valid loss sums and divide by 10; the two batch averages should be weighted by 2/10 and 8/10. An equal-weight average gives each token of the shorter micro-batch a larger weight.

Does saving the model parameters make it possible to resume AdamW training exactly?

Show the answer
Usually not. The optimizer's m and v, the step count, the scheduler, any necessary random state, the data progress and so on also have to be saved. Only loading for inference can do without this training state.

If the training-set loss falls and the same two sentences can be continued, does that prove a deployment to other sentences will also succeed?

Show the answer
No. This experiment has neither training coverage of language in general nor an independent evaluation; it serves to verify the computation and the file life cycle, not to prove generalization.

To save memory, wrapping the real training forward pass in no_grad and then calling loss.backward() on the loss — can all the parameters still be learned normally?

Show the answer
Usually not; the computational graph needed has been disabled and the gradient path is broken. Saving training VRAM should use explicit methods such as mixed precision, checkpointing or sharding, with the gradients verified, rather than simply turning off the differentiation that is needed.
