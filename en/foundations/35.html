When reading a metric, first ask what its denominator is

Why does high precision not mean all the evidence has been found?

The numerators all look like "how many were found correctly", but the denominators answer different questions. Precision looks at the waste among what has been brought back; recall looks at what was missed among what was really needed. An agent's task success rate is a result at yet another level, so a retrieval metric cannot be taken directly as the success rate of the whole task.

TP Items that should have been selected and indeed were.
FP An item that was selected when it should not have been.
FN Items that should have been selected but were missed.
Unit of evaluation A task, a run, a document or a position: establish which one first.

Input and conditions of use: This figure uses TP=6, FP=2 and FN=4 throughout; TN is undefined, so accuracy is not calculated. Percentages from different samples in other chapters cannot be directly combined.

Why it is needed

Use accurate metrics to find what was missed or wasted, instead of being misled by one pretty percentage.

How to implement it

State the task set and the units, then compute the numerator and the denominator, and look at downstream task performance at the same time.

Possible costs and misreadings

Running one question ten times is not ten independent questions; and a success rate with retries is not the same as a single-attempt success rate.

How to tell whether it was done right

Recompute the metric from the original records, checking item by item for double counting and for missed failures.

First give evaluation units clear names

Task is a task with a clear goal and criterion; Trial is one attempt at it; Trace is the trace of the model, tools and states during the attempt; Outcome is the final result; Grader is the grading rule or the program/model that performs the grading.

First give evaluation units clear names: distinguish them item by item
Object oneSample unit: one task
Object twoNumber of successes: numerator
Object threeTotal number of tasks: denominator

Key difference: state the denominator before interpreting a metric; otherwise, the percentage has almost no value for comparison.

Easy to misread: a tool-call success rate cannot be passed off as an end-to-end task success rate.

The same Task can have multiple Trials. If a Task succeeds after ten retries, that cannot simply be counted as "one successful run", because doing so changes the denominator.

Calculate success rate from actual counts first

Run each of 20 tasks once. If 18 meet the criterion, the empirical success rate is 18/20=90%. This number depends on task selection, the environment, timeouts and the allowed number of retries. If only easy tasks are selected, 90% cannot represent every business setting.

Key difference: whether the basic unit of success rate is a task or a run should be fixed before collecting statistics.

Easy to misread: running one particular task many times changes its sample weight.

Whether a long task receives partial credit should also be defined in advance. Changing the criteria on the fly to give the new system a higher score makes a fair comparison difficult.

Work out precision and recall by hand with sets

Suppose there are 5 truly relevant documents. The system returns 4, of which 3 are relevant.

Work out precision and recall by hand with sets: distinguish them item by item
Approach / object APrecision: how many predicted positives are truly positive
Approach / object BRecall: how many of the true items to find are retrieved
Approach / object CThe two denominators differ

Key difference: precision concerns false positives, while recall concerns false negatives; retrieval and routing often need to balance the two.

Easy to misread: the two metrics do not simply complement each other to 100%.

精确率precision = 找到的相关数 / 返回总数 = 3/4 = 75%
召回率recall    = 找到的相关数 / 应找相关总数 = 3/5 = 60%

Returning more documents may improve recall, but may also reduce precision and burden the context. Returning only the one most certain document may yield high precision while missing much of the necessary evidence.

Start with the objects and symbols used here
Top-k, Top-p and renormalization
Top-k keeps the k items with the highest probability; Top-p sorts by descending probability and keeps the leading candidates until the cumulative probability reaches a threshold. When used for sampling, the kept candidates have to be renormalized over the remaining total mass. Here k is a number of candidates and p a cumulative-probability threshold; k is not the attention Key table K, nor the representation width d_k.
Precision, Recall, MRR and nDCG
Precision looks at how many of the returned results are relevant; recall looks at how many of the relevant items that should have been found were found; MRR averages the reciprocal rank of the first correct item; nDCG takes the degree of relevance and the position in the order into account, and normalizes against the ideal ordering. Independent example: 5 documents should be found, 4 are returned and 3 of them are relevant, so precision is 3/4 and recall 3/5. Do not swap these two denominators.

Top-k means looking only at the top k results, not a confidence level; Recall@k measures recall at that cutoff.

High ranks can still differ

Two retrieval systems both find the correct document, but one ranks it first and the other twentieth. Their downstream costs differ. MRR takes the reciprocal of the rank of the first correct result and averages it; a correct item ranked first gives 1, and one ranked second gives 1/2.

High ranks can still differ: distinguish them item by item
Object oneRecall@k
Object twoMRR
Object threenDCG

Key difference: whether the top k retrieve an item, the rank of the first relevant result, and the ordering quality of relevant results are different questions.

Easy to misread: recall alone may not show whether downstream processing can obtain sufficient evidence.

nDCG considers relevance grades and position discounts together, and normalizes against the ideal ranking. Different metrics answer different questions; every project need not optimize every metric at once. The key is whether a metric relates to final task success.

How pass@1, pass@k and pass^k differ

Use a simplifying assumption: each attempt at a given task succeeds independently with probability p=0.8.

Start with the objects and symbols used here
pass@k and pass^k
pass@k-style metrics usually care about at least one success in k attempts; pass^k-style metrics stress succeeding every time. The exact basis of an estimate depends on the benchmark, and stopping after one success must not be conflated with being reliable every time. Under an independent, equal-probability assumption of p=0.8, at least one success in 3 attempts is 0.992 and all 3 succeeding is 0.512. If real tasks are correlated or differ in difficulty, it has to be computed differently.
一次成功：pass@1 = 0.8
三次至少成功一次：1−(1−0.8)^3 = 0.992
三次全部成功：0.8^3 = 0.512

pass@k usually expresses the ability to achieve at least one success among k candidates, while pass^k-type metrics emphasize the reliability of succeeding every time across multiple runs. Actual papers or benchmarks specify their estimation methods; the independent, equal-probability derivation here cannot be applied unconditionally to all mixed tasks.

How pass@1, pass@k and pass^k differ: distinguish them item by item
Approach / object Apass@1: success in one attempt
Approach / object Bpass@k: success at least once
Approach / object Cpass^k: success on every attempt

Key difference: they measure different reliability requirements and cannot be conflated just because their notation contains k.

Easy to misread: if the runs are not independent, the simple theoretical formulas may not apply.

Without a reliable criterion, you also cannot assume that "generating k answers guarantees the correct one can be selected". Finding a successful candidate also depends on a verifier.

Connecting the ideas

Establish the denominator before discussing improvement

20 tasks with 3 runs each means 20 tasks and 60 attempts; these should not be conflated with 60 independent tasks. Success on a single attempt, at least one success in three attempts, and success on all three attempts ask different questions. Pair the old and new versions on the same task set: which tasks were fixed and which were broken explains more than an overall percentage alone.

Once this page's concrete objects are clear, go on to the system mechanism: Why can pass@k, pass^k and a single-attempt success rate not be used interchangeably?. Knowing the full source first is not required; being able to retell from the state table what happened at each step is.

Evidence and the limits of understanding: record the task, a single attempt, the execution trace and the environment's result separately; resource limits and state that was not reset both confound a comparison.

Verification basis:[A07] [A12]. The source is limited to commit 86e17e98c7f9 and the paths actually read; article experience, public documentation and original teaching experiments are labeled separately. See how it was obtained, what was read, and the limits.

Quality and cost must be considered together

A new strategy with the same success rate but ten times as many file reads may not be worthwhile; a cheaper model that greatly increases failed retries may not be more economical. The numerator of Cost per successful task should include failed attempts and related tool costs, rather than considering only the tokens in the successful attempt.

Also record user-visible latency, input and output volume, retrieval scope and human takeover. A more complex flow or longer reasoning is not a measure of capability.

How to freeze conditions before evaluation

Specify the task set, input version, environment, model and prompt versions, tools, timeout, retry budget and criteria before comparing. Keep boundaries between training, tuning and evaluation sets to avoid treating known test answers as new capability.

You do not need to build a huge platform first. Begin by collecting real failures and representative tasks, checking the criteria manually and saving execution traces, then expand gradually. Numbers with a denominator, a scope and evidence are more useful than an attractive overall score.
