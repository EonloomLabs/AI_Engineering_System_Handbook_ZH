Text, bytes, tokens and IDs are four different things

Why can "one Chinese character" not be taken as "one generation step"?

A token is a piece picked out by the tokenization rules, and its ID is its address in the vocabulary. One token can span several characters, and it can also cover only part of a character's encoding. Merging "学习" into a single token for teaching is an explicitly stated demonstration rule, and must not be taken for how every model actually tokenizes.

Byte the unit in which text is stored and transmitted; in UTF-8 a Chinese character usually takes several bytes.
Token The unit of text a tokenizer works in.
Vocabulary The correspondence between pieces and IDs.

Why it is needed

Getting the counting unit straight keeps the context budget, the output length and the interface refresh from being run together.

How to implement it

Keep characters, bytes and tokens apart first

The 爱 you see is one character. Storing text in a computer needs an encoding rule; UTF-8, for instance, represents it as several bytes, and a byte is a storage unit of 8 binary digits. One character need not occupy just one byte.

Key difference: this correspondence table is a minimal vocabulary the book sets by hand; a real tokenizer may cut out different fragments.

Easy to misread: one Chinese character is not necessarily one token.

Token is the unit of fragment a tokenizer handles. A tokenizer is the tool that turns text into a sequence of token IDs by agreed rules, and decodes IDs back into text. A token may cover a word, part of a word, punctuation, a space, or even only some of the bytes of one character, so it is not the same as a character count.

Inside, the model handles numbers, not the glyphs on the screen. The tokenizer answers "which item of the vocabulary is it" first, and the embedding that follows answers "which row of numbers represents that item". The two steps must not be merged into one vague "turn it into a vector".

First tell two kinds of "encoding" apart:

Any integer ends up stored in the computer as 0 and 1 bits; the decimal ID 2, for instance, can be stored as an 8-bit unsigned integer 00000010. That says how the machine stores an integer, not how a language model represents the meaning of "爱".

The token ID 2 means looking up item number 2 in the vocabulary. The model can later use that ID to take a row of floating-point numbers, decimals and negatives included, out of the embedding parameter table. It is not the same as 2 compiled into a string of 0s and 1s. F05 puts binary, One-hot and embeddings side by side, one at a time.

To make the hand computation easy, the following small vocabulary is defined.<PAD> is the special item for a slot to be filled later.

Suppose the teaching tokenization rule splits "我爱学习" into "我", "爱" and "学习"; that gives [1,2,3]; splitting "你爱" into "你" and "爱" gives [4,2]. The size of an ID carries no size of meaning: 4 is not cleverer than 1, and 4−1=3 cannot be used to derive "你 minus 我 equals 学习".

This part shows the ordinary fragments plus PAD, six items in all; full training additionally uses the two boundary markers BOS and EOS. IDs 0—5 stay the same, and the next subsection lists the complete eight-item table.

The vocabulary has 6 items, written N=6. Later you will also see papers use V for the vocabulary size; in attention, V stands for the Value matrix instead. This book uses N in the basic examples so that you do not confuse the two.

Fix the vocabulary first; the IDs cannot change afterwards

A model does not do matrix multiplication on Chinese characters directly. First a teaching tokenizer, defined by hand and checkable item by item, splits this corpus into "我/爱/学习/！". A real tokenizer may split it differently; this lesson makes no claim to reproduce any product's token IDs.

"学习" here is one token; "！" is one token too. BOS/EOS are dedicated symbols; the literal string B, O, S is not split into three items. The vocabulary has 8 items, which does not mean the training sentences have 8 positions in all.

BPE's "learning the vocabulary" and "encoding the input" are not the same stage

BPE is a common family of subword construction methods. Starting from basic symbols, it counts adjacent symbol combinations in the training corpus over and over, then picks a combination and merges it. If, for instance, a b are often adjacent in the corpus, the item ab can be added, and the next round of combinations counted again. This stage produces the vocabulary and the merge rules.

Key difference: the first step decides the split boundaries; only the second gives the fragments integer IDs from the vocabulary.

Easy to misread: an ID is an address; 1 does not mean more important than 3.

When a tokenizer that has already been prepared is used, it does not recount all the text in the world every time a sentence arrives. It splits the new input into existing fragments by fixed rules and looks their IDs up. A real implementation also has pre-tokenization, special markers and possibly normalization steps; it is not to be read as splitting words at will.

Why is it so hard for code to estimate tokens from a character count? Because user_id and the random string x7b9q2 have different subword combinations available; newlines, indentation and spaces can affect the split too. A real budget has to use the counting rules of the model in question; the teaching vocabulary is only there to explain the mechanism.

How a chat role becomes part of the input

Chat starts out as messages with roles — "what the user asks", "what the assistant answers". A chat template is what organizes those roles and the body into the form the model knew during training. The template may add control markers for the start of a role and the end of a message, and those markers can take up tokens too.

Key difference: methods such as BPE learn the rules first and then use them; online inference generally does not retrain the vocabulary on the spot.

Easy to misread: meeting a new word does not reorder the existing vocabulary IDs each time.

Writing "system:" in an ordinary string does not automatically make it a real system role; how the model interface organizes messages decides how the service handles it. Concatenating the chat bubbles a person sees, word for word, is no ground for claiming to have reproduced a commercial service's final input.

What has not happened yet once encoding is done

When you have [1,2,3], all that has been found is the IDs; there is no contextual representation for each position yet, no next-token probability has been computed, and no external file has been read. Tokenization converts the representation; it is not "understanding completed".

What has not happened yet once encoding is done: item by item
Object oneUser message
Object twoSystem / developer rules
Object threeTool definitions and history

Key difference: the harness organizes this content by message role and by the model interface, and only then does it enter the model's input sequence.

Easy to misread: what the chat bubbles do not show should not be guessed at as a particular vendor's internal template.

Decoding back has its boundaries too: some processing folds case or normalizes the text, and some tokens decoded on their own are not complete characters. In code tasks, keep "means the same" apart from "the same original bytes".

Encode "我爱学习", then decode it back unchanged

Input and conditions. A fixed teaching vocabulary:我→1，爱→2，学习→3，你→4，PAD→0; this example explicitly treats "学习" as one token. It does not stand for any particular model's real tokenization.

Steps and objectsInternal actionIntermediate result / new state
1 Split into fragments"我爱学习" is split into "我/爱/学习"Four Chinese characters, three tokens: the character count and the token count differ.
2 Look the IDs upLook each one up in the vocabulary in turnGives [1,2,3], and the embedding has not been looked up yet.
3 Encode the other sentence"你爱" is split into "你/爱"Gives [4,2]; "爱" has the same ID in both sentences.
4 Look the vocabulary up in reverse[1,2,3] corresponds to "我/爱/学习"Joining by this example's rule restores "我爱学习".
5 Look at the byte levelThe UTF-8 bytes of "我" in hexadecimal are E6 88 91This is character storage; it is not the token ID 1, and it is not an embedding feature.

Join the steps up. The tokenization rule has to be given first, then the vocabulary IDs, before you can know which sentence a list actually stands for. Do not guess at the meaning of text from the size of the integers.

Limits and counterexamples. A real tokenizer also involves spaces, bytes, special tokens and normalization; this example verifies only the encoding chain of this one explicit vocabulary.

Worked example · X11

When BPE merges, why the pair on the left is not always the one chosen

Local check example: the input below follows the conditions listed for this example, and its intermediate values cannot be joined to the calculation record of the worked model.

Input and conditions. The input character sequence is [a,b,c]. Suppose two merge rules have been learned: b+c at priority 0 and a+b at priority 1, the smaller number taking precedence. In the vocabulary a has ID 1 and bc has ID 5.

Steps and objectsInternal actionIntermediate result / new state
1 List the candidatesThe adjacent pairs at this point are (a,b) and (b,c)Their priorities come out as 1 and 0.
2 Choose by the ruleMerge (b,c), at priority 0, firstThe sequence becomes [a,bc]; the original (a,b) cannot be used as well, because b has already been merged into bc.
3 Find the adjacent pairs againNow there is only (a,bc)Supposing there is no merge rule for it, this stops.
4 Look up the final IDsa→1,bc→5The output is [1,5], not [ID of ab, ID of c].

Join the steps up. BPE at inference time uses the order of the rules it has already learned; the original adjacency is not the merge priority. After each merge, which candidates are adjacent changes.

Limits and counterexamples. The character is the basic unit for teaching here; a real byte-level BPE may start from bytes, and it still has to respect special tokens and pre-tokenization rules.
