Each turn's context is like a working file with a boundary

Why does "reading more" sometimes make misreading more likely?

This turn the model can use only the material it is given. Too little material leaves it without a basis; too much brings in old versions, repeated conclusions or irrelevant rules. The point is not to fill the space with every piece of information available, but to prepare the minimally sufficient material that can support the next action, while leaving room for generation.

Budget The resource allowance available for this turn.
Necessary evidence Original information without which a reliable judgment cannot be made.
Source Who provided this material, when it applies, and what conclusions it supports.

Input and conditions of use: A teaching budget of 100 units, not a real tokenizer measurement: rules 20, task 10, tools 15, evidence 20, output reserve 20. The configuration stays the same throughout.

Context does not mean "the entire computer is in the model's head"

Context is the input content and associated state that the current model call can use. It may include role instructions, user questions, history, tool definitions, retrieved excerpts and compacted information. Material stored outside the system becomes part of this turn's conditions only after it is retrieved and supplied in a form the model can use.

Context does not mean "the entire computer is in the model's head": item by item
Object oneSystem and project rules
Object twoUser goal
Object threeTool evidence and history

Key difference: Context Assembly arranges which material is supplied each turn, with its priorities and sources.

Easy to misread: a file not supplied this turn cannot be counted as already read by the model.

Prompt assembly or context assembly is the process by which the harness selects and organizes this content. It involves what should be read as well as identity, order, budgets and whether evidence applies.

Work out a simplified token budget first

Suppose a teaching service has a total budget of 2000, reserves 500 for expected output and 100 for formatting and estimation error, leaving an input limit of 1400. Fixed rules take 200, tool descriptions 300 and the user task 100, leaving 800 for history and evidence.

Key difference: filling the entire window with input may leave insufficient budget to generate output or tool calls.

Easy to misread: a token budget is not simply a character count.

This is only a teaching budget, not a fixed allocation for any current product. How a real interface counts output, internal reasoning and compaction blocks must be checked against its version's specification. What matters is not mistaking "count only the user's text" for the full input cost.

Choosing evidence: more is not always better

Suppose you are fixing a directory-filtering bug. You need the relevant functions, calling conditions, configuration rules, failing tests and dependencies that may affect semantics. Ten irrelevant README files may add tokens without reducing the key uncertainty about the bug.

Key difference: starting with the most relevant material and expanding retrieval as gaps emerge is more economical than reading the whole repository first.

Easy to misread: reading more does not necessarily make the evidence sufficient.

Start with the objects and symbols used here
Skill, JIT and the trigger description
In a capability-loading setting, a Skill is a reusable set of guidance and resources; JIT means loading only when needed, and does not necessarily mean a compiler's just-in-time compilation. A trigger description helps the model judge whether something applies; it does not grant tool permissions by itself. First judge whether the task needs a given skill, then read the details; a loaded skill is not the same as its requirements having actually been carried out.

JIT (just-in-time, on-demand) loading means reading content only when needed instead of putting it all in at the start. Dependency closure means finding the necessary related information on which the current conclusion depends; for example, reading a function body alone may be insufficient without knowing the path format passed by its caller.

Closure does not require expanding the whole repository unconditionally. Extend the boundary step by step by asking which basis the current judgment still lacks; stop when there is enough to make the next reliable decision.

Order, role and source are three different labels

Appearing earlier does not mean greater authority; a newer file is not necessarily more trustworthy; a command in an external document is not user authorization. The harness must preserve source and scope so the model can better distinguish rules, evidence and quoted text.

Order, role and source are three different labels: item by item
Object oneInstruction role
Object twoEvidence source path
Object threeVersion and time

Key difference: the three labels answer "Who is asking?", "Where did the evidence come from?" and "Is it still valid?"; they cannot replace one another.

Easy to misread: a web page's body remains untrusted data even if it claims to be system.

If a product has an instruction hierarchy, follow the corresponding interface and specification; this is not a numerical priority in attention weights, still less permission to execute. System-level security restrictions still need enforcement in the executor.

Why prompt cache needs a stable prefix

In common causal models, the same prefix, model and relevant conditions provide a basis for reusing intermediate prefix computations. Prompt Cache Repeated prefixes can reduce some computation or billing; the specific service rules may change.

Key difference: prefix caching depends on a sufficiently consistent initial input segment; changing early content may reduce reuse.

Easy to misread: a cache hit does not mean the model has permanently memorized the rules.

But placing a timestamp or random field that changes every time at the very start may disrupt reuse of a long prefix. Conversely, keeping stale content forever for cache hits may hurt quality. Caching optimizes cost; it cannot replace correct information.

How to observe why the model "did not follow instructions"

First check whether the rule exists, then whether it was discovered, read, included in the request, trimmed later, and still applicable. Only after all these conditions are met should you investigate how the model uses the content.

This chain explains why a skill failing to take effect does not necessarily call for an immediate rewrite. The real problem may be that the file was not loaded or that the sub-agent never received the relevant context.

How stable context and dynamic evidence divide the work

The stable part suits concise core project conventions; the dynamic part carries task evidence, the current version and steps in progress. Low-value logs can stay outside and be retrieved when needed.

There is no single best order here. The teaching goal is to let you list each block's responsibility, token cost, source and consequences if missing, then compare on real tasks, instead of judging a prompt by whether it is "longer and more professional".

Connecting the ideas

This turn's input is like packing a work bag, not moving the whole repository

Suppose the total space is 12000 tokens, fixed rules and tools take 2000, the current task takes 1000, and 3000 is reserved for later output, leaving about 6000 for current evidence. Select material by first including paths that must not be edited, current file versions and recent failures; keep only the relevant parts of long logs and retain access to the originals. Including conclusions from an old version may be more dangerous than reading a little less. A token budget is a capacity constraint, not a target that must be filled.

Once this page's concrete objects are clear, go on to the system mechanism: Why can assembling context not just be "take the first N items"?. Knowing the full source first is not required; being able to retell from the state table what happened at each step is.

Evidence and the limits of understanding: an empty tool field on one request may be the delta protocol rather than a lost definition. Check it against the history and the actual protocol.
