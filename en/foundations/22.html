Break one agent task into the turns that actually happen

Why can one user task call the model more than once?

The LLM generates the next proposal, the harness carries out the approved action and hands the result back to the LLM. That is the outer task loop; inside each model call there is still token-by-token generation. One outer round of tool action is not the same as generating one token inside, and the two kinds of "loop" must not be conflated.

Call ID An ID linking a particular tool request to its result.
Tool result Content returned after actual execution by the program.
Context Information explicitly given to the model this round, not the entire computer state.

Input and conditions of use: Constructed read-only teaching task: config.txt contains timeout=30. Swimlanes show responsibilities without claiming a real commercial API call; data and action order are fixed.

Why it is needed

A model can obtain new evidence through tools instead of stuffing everything into its parameters.

How to implement it

Organizes the loop as request, validation, execution, writing the result back, and deciding whether to carry on.

Possible costs and misreadings

Forgetting to write the tool result back makes the model request it again; treating the output text as proof of execution reports completion falsely.

How to tell whether it was done right

Cross-checks each turn's model input against the tool log and confirms that the result matches its call_id.

Start by treating it as an ordinary program

Take Agent Understand it as a system that organizes task execution around a model: the program prepares the input, calls the model and checks its output; if the output requests a tool, it runs the tool and feeds the result back in; if the completion conditions are met, it stops.

Start by treating it as an ordinary program: item by item
Object oneUser task
Object twoModel: proposes the next step
Object threeHarness: actually calls the tool

Key difference: an agent is a software system that organizes models, tools, state and feedback.

Easy to misread: this does not introduce a new, independent kind of neural network.

Harness is a common name for this execution environment and control logic. The model generates candidate actions or answers; the harness actually runs them, saves state and controls the boundaries. Filesystem access permissions have not suddenly appeared inside the model.

A complete example with three model calls

The user asks, "What does the function in the file return?" The following teaching messages do not correspond to all the API fields of any one vendor.

Key difference: the model first expresses the intent to make a call; new evidence is available in the next turn only after the harness executes it.

Easy to misread: the model writing a tool name does not mean that the tool has run.

The first turn's input includes the user's question and the available tool's description: "read_file accepts a path and returns the file's text." The model outputs a tool request, for example read_file(path='demo.py'). At this point, the file has not yet been read as a result.

The harness executes: it checks that access to the path is allowed, performs an actual file read and gets def answer(): return 42, binding the result to the identity of this call.

The second turn's input includes the original task, the previous turn's tool request and the actual tool result. The model can now answer "It returns 42" based on the source, or request further verification. Suppose it requests a test run; the harness runs the tests and returns their output.

The third turn's input includes this verification result, and the model composes the final answer. The harness should still judge completion according to the task type; a confident final sentence alone does not prove that every requirement has been met.

Why distinguish a model call, an interaction turn and a task

Start with the objects and symbols used here
Thread, turn, session: the levels of a run
These are usually the harness's divisions of a conversation and of units of work, not layers of a neural network. A thread can mean one conversation, and a turn can contain the several model and tool cycles needed to answer one user task; where the boundaries fall depends on the product."This turn is done" cannot be equated with "every external tool has finished"; that takes looking at the actual events and results.

This book calls one model request and its output a model call. The interval from a user asking a question to receiving the reply can be called one turn of user interaction; it may contain many model calls and tool executions. Products may define Turn, Step and Thread differently. When reading source code, check that project's types and lifecycles.

Key difference: a task can span multiple model calls; each turn's input is affected by earlier tool results.

Easy to misread: one user question does not equal one model call.

A thread or session usually preserves the organizational relationships between related interactions; a task is the user goal to achieve. A long task may span multiple sessions, and one session may contain multiple tasks.

Workflows versus autonomous agents

A workflow can have its steps preset by the program, for example, "Check the cache, then query the database, then generate an answer"; a more autonomous agent leaves more choices about the next step to the model. The two can be combined; complete freedom of action is not the only sign of progress.

Workflows versus autonomous agents: item by item
Object oneTask: the whole goal
Object twoTurn: a user or agent phase
Object threeTool call: one action

Key difference: the three levels of granularity must be recorded separately, or retries and recovery cannot locate the specific step.

Easy to misread: different products may name a Turn differently; interpret it according to the current system's definition.

A fixed process offers predictability, while free choice offers adaptability; adding an autonomous step also adds opportunities for error and extra cost. When a simple requirement already has a clear path, there is no need to mandate planning, then multi-agent research, then repeated review.

What is a tool, and what is a side effect

A tool is a callable capability that the harness offers to the model. Reading files, searching, querying databases and running tests are all forms of tools. A side effect is a change that a call makes to the external world, such as editing a file, sending an email or committing code.

What is a tool, and what is a side effect: item by item
Approach / object AWorkflow: preset steps
Approach / object BAgent: steps chosen dynamically
Approach / object CThe two can be combined

Key difference: a deterministic process is usually simpler for a well-defined task; for complex exploration, the model can choose the next step.

Easy to misread: giving an agent more freedom is not necessarily better.

The model generating a tool name does not mean a side effect has completed; losing the response after a side effect occurs does not mean it never happened. These are the unknown-outcome and idempotency problems covered in F33.

Why an agent needs a loop

Without knowing the file's contents, the model cannot reliably decide on the final patch; reading the file provides new information. The loop makes it possible for actions to yield observations, and for observations to change the next decision. Its purpose is not to make the model mechanically repeat its analysis.

The loop must also have stopping conditions, budgets and handling for a lack of progress. For example, if the same search repeatedly yields no new evidence, it should change strategy or report the gap instead of repeating forever.

The limits of this book's teaching scripts

An offline demo can have a fixed script return preset tool requests in sequence to show how messages move; this is a protocol or control-flow simulation, not a commercial model's actual autonomous capability. Discussing that model's success rate on the task requires connecting a real model and recording measurements.

Read, find the gap, read again: let one tool result decide the next step

Input and conditions. The user asks "why did it time out?" In the teaching repository the config says timeout=3, and the log says request elapsed=5, both declared as seconds in the file header.

Connecting the ideas

Keep three kinds of information separate first: user requirements, model proposals and tool facts

The user says, "Read timeout from config.txt." The model first receives the task and the read_file description, while the file's contents are still on disk. Its output of call_id=c7 and a path is only a proposal; the harness checks the path, actually reads the file, and returns timeout=30 associated with c7. The next model call must include or correctly reference that result to answer 30. Without a read result, the model saying 30 is only a guess. This example involves no training, and the parameters usually do not change because of this read.

Once this page's concrete objects are clear, go on to the system mechanism: One answer has finished — so why is the task still not done?. Knowing the full source first is not required; being able to retell from the state table what happened at each step is.

Evidence and the limits of understanding: the end of the model's response proves only that this generation has ended; the tool result and the final acceptance remain two separate pieces of evidence. A stop-hook check is no substitute for a real test either.
