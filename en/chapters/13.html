Prerequisites for this chapter

A context budget is how a limited number of input slots is allocated. Rules, evidence, history and tool descriptions compete for the space; work out which facts the current problem needs first, then optimize how they are put in and how they are cached.

Each question in this chapter lists the groundwork it needs. You can take the matching Foundations lesson first, or use the self-check to confirm how well you have it.

Lesson 37 · Why text has to become token IDs firstLesson 02 · State, events and checkpointsLesson 08 · Tools and MCPLesson 11 · Assembling contextLesson 22 · Compaction is not magicLesson 13 · Skills, routing and multi-agent

A quick check before the deep reading: with a total budget of 100 units, 20 for fixed rules, 30 reserved for output and 10 for tools, work out that 40 is left for evidence, and say which kind of content would change the conclusion if it were removed.

A term with a dotted underline can be clicked for a quick reference. Read the definition of a letter in a formula first; do not let a guessed abbreviation stand in for the derivation.

Context engineering is not "summarize the material and put it in the prompt". It covers selection, permission filtering, version checking, filling in dependencies, ordering, budgeting and rendering. The object model and the algorithm below are a teaching design; no claim is made that some closed-source product adopts them field by field.

Q017｜Which objects should make up one turn of model input? How should the budget be computed?

What to know first for this question Each turn's context is a limited set of input, not the whole repository. Fixed rules, tool descriptions, working state and evidence get different budgets.
Lesson 37 · Why text has to become token IDs firstLesson 02 · State, events and checkpointsLesson 11 · Assembling context

Core answer

Treat the task constraints, the tool definitions, the evidence, the history of actions, the current state and the open problem as different context objects, then select and render them for this turn's goal. The budget has to leave room for output, tool feedback and later actions; the nominal window cannot be filled entirely with input. Products differ in exactly how they count input, output and reasoning Token s, so this should be calibrated against the interface's own rules.[CONTEXT][REASON]

A context object you can check

{"id":"e17","kind":"code_evidence","source":"src/filter.py",
 "revision":"r42","range":[60,95],"trust":"repository_data",
 "purpose":"解释exclude分支","depends_on":["type-config"],
 "content":"……","expires_on_change":true}

These fields are not there to be elaborate; they answer a few practical questions: what this passage is, where it came from, which version it is about, why this turn needs it, and what it depends on. A simple project can keep only id/source/revision/content; add the field whose absence causes a concrete error.

Let W be the total budget available to the model, O what is reserved for this turn's output, R the margin for tool results and S the protocol and safety margin; the selectable input budget is then roughly B=W−O−R−S. If the interface constrains maximum output and context separately, check each of them rather than leaning on one formula. The real token count should come from the target model or service's own counting; a character count is only a rough estimate.

Start with the objects and symbols used here
Schema and Structured Outputs
A schema is a set of structural rules about fields, types and the like; a structured-output mechanism makes it easier for the model to return data that follows those rules. Valid fields still do not mean that the target file exists, that access has been granted, or that the request is right for the business. Independent example: path is required to be a string; {"path":3} does not match the type rule, and {"path":"missing.py"} follows the structure yet may still find no file.

Next come this turn's goal and the key constraints that cannot be left out, then the tools needed now and their schema, the confirmed state and the evidence. Chat history is not ordered mechanically by "the newer the more important": a rule raised very early, "do not change the public API", can matter more than the ten most recent useless search results. Irrelevant failed exploration can be compacted or moved out of the context, while undecided side effects and negative conclusions have to be kept.

In a context budget, subtract the space that must be kept before selecting material

Conditions for this example: an independent teaching window of 100 budget units. The unit here is a simplified budget, not a real token count for any model. Rules take 20, tools 10, the task 10, the output reserve 20 and the safety margin 5, leaving the rest for evidence.

How to read the changes in the figure

Set aside the output and the necessary constraints first, and only then discuss which files to choose. If all the evidence is packed in first, you may end up having to cut the rules, or left with no room to generate.

Whether evidence A and B are sufficient also depends on what the content relies on; the 35 units are not better the fuller they are, since irrelevant material takes up budget without making the question any more answerable.

The real window and the rules for reasoning tokens vary with the API and the model. This example is only budget arithmetic; it supports no inference about product pricing or real capacity.

Do not conflate: a summary that keeps "the error happens in filter.py" but drops the interface constraint does fit the budget, yet the changes that follow may still drift off target.

Worked example · Q017

A 1000-token window does not mean all 1000 tokens can hold documents

Input and conditions. A teaching budget: a total window of 1000, with 200 reserved for output and 50 as a safety margin; instructions 150, tools 100, task state 150. The counts are given by the same teaching counter throughout.

Join the steps up. A budget allocates resources on one and the same counting basis; it does not truncate casually on "about the same number of characters".

Limits and counterexamples. How real reasoning tokens and input/output tokens take up the window depends on the model and the interface; the budget here is given explicitly and does not stand in for a vendor's billing rules.

Follow-up: when the budget is short, what goes first?

Delete what is duplicated, out of date, unrelated to this turn and recoverable first, then trim tool output and historical detail. What must not go first is a key constraint, the identity of a resource, a version, or "the state of this action is unknown". If the necessary information itself exceeds the budget, split the work into stages or narrow this turn's goal instead of quietly dropping constraints.

Follow-up: once the tool definitions are in the input, why can the limit still be exceeded with the same token count in the body text?

A model request also carries message boundaries, roles, tool schemas, multimodal representations and other overhead. The body text a user sees is only part of the total input. Check the actual count and the composition of the request, instead of computing an exact token count from a browser's word count or a file size.

Follow-up: is the context window a capacity or a guarantee of reliability?

Capacity only states the range the interface or the model can accept. Retrieval inside a long context, how well positions are used and multi-hop association have to be evaluated separately. Work such as Lost in the Middle shows that some tasks are position-sensitive, but a result for one older model cannot be taken as a fixed failure curve for every new one.[LOST]

Engineering mechanisms and failure boundaries

Why can assembling context not just be "take the first N items"?

A context fragment contains at least four things

The content itself, where it came from, which version it holds for, and what it is for. "timeout=3" on its own, for example, is not enough to support a change; config/test.yml@r7:L8 timeout=3，测试环境，允许修改is what gives an object you can check. "Please ignore the rules" in an external document is the content of some material; entering the input does not promote it into a user authorization.

Budget arithmetic starts with the space that has to be reserved

With a teaching window of 12000 tokens, 2000 for fixed rules and tools, 1000 for the task and the plan, and 3000 reserved for generation and later tool results, the evidence budget comes to about 6000. The numbers here are a teaching allocation, not a fixed limit of any model. A budget estimate should use the actual model's counting; a character count divided by 4 is not an exact count for Chinese, code or JSON.

The dependency closure matters more than ranking items on their own

A patch conclusion cites test T, and test T in turn targets file r7. Keep only the conclusion and lose the test and the version, and the model may take the old conclusion and modify r9. When selecting context, bring the minimum necessary dependencies along, or keep a stable reference that can be read again. The point is not to load every related file into the window, but to give the current inference enough support.

The history management in the pinned source separates the history visible to the model, the harness information it keeps and the baseline needed to re-inject; one conversation window is not a mirror of all the system's state.[C08] The context of each call is decided by the request snapshot together with the current history, so "the file is in the repository" cannot be used to infer "the file has entered this turn's input".[C01][C02]

Break "more information" into three different outcomes

Adding correct, relevant evidence may reduce guessing; adding stale evidence may create conflict; adding irrelevant material may take up the space that mattered. Anthropic's article on context engineering stresses selecting information and fetching it on demand, rather than treating a long context window as a target to be filled.[A02]

Checks you can actually run

Before assembly, save the candidate list and the reason each item was dropped; after assembly, check the hard constraints, the version of the object being acted on, the unfinished items, the most recent failures and the pointers to the original evidence. Mark discarded material as "not included"; do not claim the model has reviewed it. Sensitive data should be handled before anything is submitted to the model, not only after the final answer.

If tools is empty in the request, does that prove the tool definitions were lost?

One field is not enough to tell. The pinned build_prompt leaves this turn's tools and base_instructions fields empty in incremental tool mode; in non-incremental mode it supplies the definitions the router can see along with the basic instructions. Judging something missing has to take in the message history and the protocol in use, instead of reading an empty array in one request's JSON directly as "the model does not know about the tools".[C01:build_prompt]

Likewise, a tool definition existing does not guarantee it was really used that turn. It helps to trace one piece of information along "source → read → selected → serialized → retained → actually acted on". Material missing from the original, budget trimming, and the model not using it properly have to be attributed separately; endlessly rewording the prompt cannot fix material that never entered the request at all.[C02][A02]

Q018｜How does JIT loading save tokens without missing anything essential? Why does the "dependency closure" have to be filled in?

What to know first for this question Loading on demand supplies a description good enough to choose from first, then reads the full resource. The dependency closure makes sure that when a piece of evidence is used, the conditions needed to understand it come with it.
Lesson 08 · Tools and MCPLesson 11 · Assembling contextLesson 13 · Skills, routing and multi-agent

Core answer

Load a discoverable lightweight index first and read the specific content once the need is established; after content is selected, fill in the dependencies needed to understand and act on it. What is saved is irrelevant loading by default, not the necessary premises. A dependency closure means that when a conclusion or an action is kept, the definitions, evidence and constraints needed to explain it are kept too.

A counterexample: reading one fragment of a function

The retrieval hit: if config.exclude: return skip(item). Read that one line alone and a model may conclude that a non-empty exclude always skips; in fact exclude may be a filter object whose boolean conversion is decided by a custom type, and skip may have side effects as well. Understanding this fragment takes at least the config type, the calling conditions and the related tests.

Start with the objects and symbols used here
Skill, JIT and the trigger description
In a capability-loading setting, a Skill is a reusable set of guidance and resources; JIT means loading only when needed, and does not necessarily mean a compiler's just-in-time compilation. A trigger description helps the model judge whether something applies; it does not grant tool permissions by itself. First judge whether the task needs a given skill, then read the details; a loaded skill is not the same as its requirements having actually been carried out.

Likewise, when a skill description says "run the review by the team's rules" but gives no path to the team rules, JIT-loading that far is still not enough. A summary that says "option B is ruled out" without keeping the basis for ruling it out lets a later model explore B all over again. A short reason and a reference to the evidence can be kept, with the detailed log fetched on demand.

Start with the objects and symbols used here
Top-k, Top-p and renormalization
Top-k keeps the k items with the highest probability; Top-p sorts by descending probability and keeps the leading candidates until the cumulative probability reaches a threshold. When used for sampling, the kept candidates have to be renormalized over the remaining total mass. Here k is a number of candidates and p a cumulative-probability threshold; k is not the attention Key table K, nor the representation width d_k.

One teaching selection procedure runs: pick candidates by relevance to the task; expand the necessary dependencies of each; de-duplicate; check versions and permissions; compute the budget; and when it does not fit, adjust this turn's scope or demote the non-critical items. If selection is done purely by similarity with Top-k, you may pick several fragments that look related yet cannot be assembled into a usable chain of evidence.

Start with the objects and symbols used here
call_id,item_id,request_id
These are identifiers for objects at different layers: a tool call, an output item, a request or a response. They match increments and results back to the right object; they are not the token IDs of the model input, and they are not business idempotency keys by nature. Two read_file calls can carry c1 and c2; when the results come back in the reverse order they are still paired by call identifier, not guessed by tool name.

Follow-up: can a dependency closure expand without limit until it covers the whole repository?

That risk is real, which is why the current problem has to be the boundary. Needing the semantics of a type does not mean reading the whole module the type lives in; needing to confirm one caller does not mean enumerating every caller in history. Choose the smallest evidence that can settle the current hypothesis, then expand as new questions arise, rather than exhausting every dependency in advance.

Follow-up: how do you know a dependency was left out?

Watch for the model using undefined terms, guessing the units of an argument, being unable to say where a conclusion came from, or reading back over the same thing repeatedly. A more direct method is to mark the necessary evidence in an evaluation task and check whether retrieval and the context contain it. The point is not that production must always have perfect labels, but to build a regression set from real failures.

Follow-up: how do you order JIT and summarizing?

Not loading irrelevant content in the first place is often cheaper than loading it and then spending a model call to compact it; but once a long history has accumulated, a summary is worth having. For key code just retrieved, summarizing too early can lose the precise conditions, and keeping the original fragment is usually better. JIT, trimming, summarizing and moving content out of the context are different operations, and the choice should follow the object.

The context budget is not just the files already read: tool results, the generation and evidence dependencies all have to be reserved for as well

Prerequisite: Lesson 11 · Lesson 17. Reading order: confirm the run contract first, then look at the counterexamples and the fix, and finally test the limits.

A budget is "the space available" minus "what has to be reserved", not the window's upper limit

Take a teaching window of 1000 units, with 200 for fixed rules and tool specs, 200 for generating the plan and 250 for the expected next tool result; the evidence budget is then only 350. The units are used for demonstration; they do not pretend that a character count equals a real token. In practice, check against the model's tokenizer and the interface's counting rules, and include visible usage limits such as opaque state.[RESP]

If all you do is窗口−当前用户文本, the current request may go out and then blow the window the moment tool results come back. The compaction interface has an input-length limit of its own, so you cannot count on "just compacting it endlessly" once the limit is already exceeded.[COMPACT]

Fragments are not scraps of paper that can be packed greedily on their own

An interface declaration is 200 units and the real implementation 300, 500 in all; the budget is 350. Keep only the declaration and the answer "the feature is already implemented" has nothing behind it. A dependency closure is the set of material that has to come along for a piece of evidence to be understood correctly. The engineering choice this book offers here is to treat the declaration and the implementation as one group, or to read a smaller relevant range of the implementation first; a high relevance score does not justify selecting half of it.

Likewise, an error log and the matching code version, one configuration and the higher-priority configuration that overrides it, a conclusion and the conditions that negate it, may all have to be kept together. Whether a summary can stand in for one of them depends on whether the later task needs exact verification.

Replace a whole-repository scan with a minimum sufficient evidence plan

Write down the proposition to be proved first: for example, "do the directory rules exclude descendants recursively?" Then find the rule parsing, the matching function and the failing test; there is no need to read in every function of the same name. If the evidence is not enough, expand in a chosen direction. Record at each step why this material was read and what it confirmed or ruled out, which gives an auditable stopping condition for the search.

Follow-up: is keeping a file path the same as keeping the evidence?

A path is only a locator; a file may have moved, changed or become unreadable. Record at least the version or a fingerprint of the content, the relevant range and the key facts. When exact code is needed, read the current content again; a path in a summary does not authorize execution by itself, still less prove that an old test applies to a new working tree.

Follow-up: when the budget is too small, is a larger-window model the only option?

First cut irrelevant history, trim duplicated tool output and reuse verifiable state, then assess whether a larger window is needed. Splitting a task has a handoff loss of its own: independent subtasks can be separated, while a tightly coupled problem should not be broken into pieces that each lack context. What is being measured is the success rate and the total cost of finishing the task, not the smallest token count per turn.

Q019｜Why does a prompt cache require a stable prefix? How do you work out what compaction gains and loses for the cache?

What to know first for this question A prompt cache reuses the computation for an identical prefix, while compaction changes the input; shortening the tokens and raising the cache hit rate do not always move in the same direction.
Lesson 58 · KV cache explained from scratchLesson 11 · Assembling context

Core answer

Reusable model computation depends on an identical effective prefix and on the service's rules. A change early in the prefix affects the contextualized computation after it; stable system instructions, a stable tool set and fixed material all help reuse. A summary shortens the input, yet it may replace history that would have hit the cache, so in the short term the computation has to be done again. The exact cache scope, retention time and price vary with the product.[PCACHE]

Understand the prefix through its dependencies

Lesson 60 has already shown that an old position keeps the same K/V only while the prefix, the parameters and so on are unchanged. Put a timestamp that changes every turn right at the front, and the tokens and positions after it may change; even if a long stretch of body text is identical, it is not necessarily reused. A stable prefix should hold what is genuinely stable and needed every turn, rather than keeping irrelevant information forever for the sake of the cache.

Let u be the unit price of uncached input, c the unit price of a cache read, w the cost of writing or establishing the cache, P the prefix length and n the number of later reuses. Looking at the input part alone, the cached option comes to about P*w+n*P*c, the uncached option to about (n+1)*P*u. The break-even condition is P*w+nPc < (n+1)Pu. A real service may cache automatically with no separate write price, or follow different rules, so these symbols are there for reasoning, not as a price quote.

Compaction also adds the cost K of the compaction call and the risk of later errors. Suppose most of the history hit the cache each turn before compaction: afterwards it is shorter but entirely uncached the first time, so the first turn may not be cheaper, and the gain from the reduced length only shows after several turns. Latency behaves similarly, and compaction may raise quality by cutting noise or lower it by dropping evidence.

Start with the objects and symbols used here
I: the identity matrix
In a matrix formula I is usually the identity matrix: 1 on the diagonal and 0 everywhere else. At a compatible size, multiplying a vector or a matrix by I leaves the numbers unchanged. Wq=Wk=I is a special case chosen deliberately; one cannot infer from it that the projections of a real model are all the same. Independent micro-example: I=[[1,0],[0,1]], and [3,-2]I=[3,-2]. I here is not the position subscript written as the letter i.

A cached prefix reuses an identical leading segment, not "roughly the same meaning"

Conditions for this example: independent token sequences: request A=[R1,R2,T1,U1]; request B=[R1,R2,T1,U2]; request C=[R1,new,T1,U2]. Only whether the prefixes agree is compared; no particular service's retention time or billing is assumed.

Follow-up: is stuffing all the material in ahead of time and waiting for the cache the best strategy?

No. A cache reduces repeated computation or billing; it does not remove irrelevant information from the logical context, nor does it solve the window being occupied. Content goes stale, and it can also affect how the model uses its attention. Show that material is worth being there this turn first, then optimize reuse.

Follow-up: why does identical text not necessarily hit?

The model or the adapter may have changed, the tool schema or the ordering may have changed, the actual serialization may differ, or the cache may have expired, been evicted or been isolated to a different tenant or route. Identical user text is only part of the necessary condition. Watch the cache usage the service reports rather than comparing strings on the client.

Follow-up: should the cache hit rate be optimized to 100%?

A hit must not be bought at the cost of fresh data and relevance to the task. A new question each turn, and tool results, are different by nature. What is worth more is the hit rate on the stable, reusable part, the cost of a successful task and the latency, rather than defining the denominator so that it looks good.

The meaning has not changed and yet the cache misses: how an exact prefix, the tool specifications and dynamic fields affect one another

Prerequisite: Lesson 58 · Lesson 11. Reading order: confirm the run contract first, then look at the counterexamples and the fix, and finally test the limits.

What a cache compares is not "it reads the same to a human"

Prefix caching reuses the computation of an identical leading segment that meets the service's specific conditions; it does not treat two passages as equal because their wording is close in meaning. OpenAI's caching guide describes exact prefixes and model-related controls; thresholds, retention times and billing change, so they should not be written down as eternal numbers.[PCACHE]

For example{"a":1,"b":2}and{"b":2,"a":1}parse to equal objects while their strings and token sequences differ. A local experiment can check that difference. Normalized serialization can improve stability, but only for objects that have no ordering semantics to begin with; message order, whitespace in code and the order of examples may carry meaning and must not be reordered freely.

One dynamic field can cost everything after it a common prefix

If the current time, a random request_id, retrieval hits or the session title are inserted ahead of a long system rule each turn, the fixed body after them is no longer in the same contiguous prefix even when it is identical. Put stable rules and stable tool descriptions where they can be reused, and content that changes turn by turn after them; but this has to obey the interface's role hierarchy and the model's usage rules, and a trusted instruction must not be demoted to ordinary material for the sake of the hit rate.

Changes to the names, the order, the descriptions or the available subset of tool schemas can also change the identity of the input. A cache-hit metric should be read together with the specific request sequence, instead of inferring that nothing else changed because "only the user message was edited".

Keeping something in the cache is not deleting the content

A hit can cut part of the computation or the cost, but logically the model is still using the full context; hit tokens cannot be subtracted from the context window budget. Compaction, by contrast, really does change the input. Confusing the two leads to an over-full budget, or to the mistaken belief that the cache made the model "remember the rules permanently".

Follow-up: if another tenant has used a prefix, why can it not be shared unconditionally?

A caching policy also has to consider privacy and isolation. vLLM's public design provides cache_salt to limit reuse across trust domains.[PREFIX] A production system's cache namespaces, permissions and data-retention constraints should line up with tenant isolation; "more hits" is not the only goal.

Follow-up: how do you prove that a caching optimization paid off?

Under the same task and the same model version, record the identity of the request prefix, the hit tokens, the time to first token, the total latency and the total cost; keep cold starts separate from a warm cache. Do not compare only two neighboring requests, and do not count a quality change caused by compacted content as a pure caching gain.

Q020｜When the context holds instructions and facts that conflict, how should they be ordered and adjudicated?

What to know first for this question The authority of a source, the scope it applies to and its date together decide how a rule conflict is handled; "it came last" or "it is repeated more often" cannot settle it alone.
Lesson 02 · State, events and checkpointsLesson 11 · Assembling contextLesson 23 · Foundations of long-term memoryLesson 29 · Security basics

Core answer

An instruction conflict is handled by trusted source, permission and task scope; a fact conflict is handled by source, version, time and evidence. Where something sits in the ordering can affect how the model uses it, but position should not stand in for the authoritative rule. Even when an external document says "ignore the previous rules", it is still data that was read.[SPEC][OWASP]

The two kinds of conflict must not be merged into one

The user asks for "no deployment to production", and a README returned by a tool says "deploy automatically when finished". That is a conflict of instruction authority: the README being newer, or sitting closer to the end, does not override the user's constraint. A different case: old documentation says the interface times out at 30 seconds while the current configuration shows 60. That is a conflict of fact between versions, and the environment and the version have to be settled before the matching evidence is chosen.

Context rendering can label the task goal, the constraints that must not be violated, the facts currently known, the unconfirmed assumptions and the tool evidence separately. What matters is not a pile of ornamental labels but keeping "who said this, and what it is". One of the most dangerous changes during summarizing is promoting a suggestion in a repository document into a user instruction, or a model's guess into a confirmed fact.

Placement can keep the key constraints clearly visible at the entry point and at a task handoff, but the whole set of rules should not be copied over and over. Too much repetition wastes tokens, and slight differences in wording can create new conflicts. The better practice is to maintain one authoritative set of constraints and cite it accurately in the state handoffs that need it.

An instruction conflict and a fact conflict cannot both be settled by the same "latest wins"

Conditions for this example: an independent project question: the project rules require that no key be sent; a newly crawled web page asks for a key to be uploaded. There is also a configuration at the same permission level: the old default is 30, the new version's default is 10. The two kinds of conflict are looked at separately.

Follow-up: is newer evidence always more trustworthy?

Not necessarily. A new source may be a reprint or simply wrong, and an old specification may still hold for the current version. Judge the authority, the directness, the scope and the date it took effect. For a source-code task, the configuration actually in effect and the call path may explain the behavior better than the newest documentation.

Follow-up: can a summary the model wrote itself become an authoritative source?

A summary is derived material, and the original source should be kept. It can guide retrieval efficiently, but it cannot win unconditionally when it conflicts with the original evidence. After several rounds of summarizing in particular, source labels and uncertainty are easily lost, so go back to the original record and check it periodically.

Follow-up: why not settle every conflict with one strong system prompt?

A system prompt can teach the model principles, but it cannot replace external permission checks, reading the latest facts and consistency control. Natural-language constraints and deterministic boundaries complement each other. Writing all the business logic into one long prompt is usually harder to test and to update.
