Training in the system mechanisms: from the loss down to every group of parameters

The Foundations course has already carried one training run through. This page opens no separate learning path; it returns to the parameters from before that same update and computes, item by item, the gradients of the output head, the normalization, the FFN, the residuals, attention and the embedding, checking how contributions to shared parameters accumulate and where the AdamW update stops. The implementation, the records and the negative controls correspond to one another.

Prerequisites for this chapter

Start with the objects and symbols used here
Optimizers, Adam and AdamW
An optimizer turns gradients into parameter updates. Adam also keeps, for every parameter, a moving average m of the gradient and a moving average v of the squared gradient; these are training state, not attention values. AdamW decouples weight decay from the adaptive gradient update. Independent first-step example: with g=2, old m=0 and β₁=0.9, the new m is 0.2, and after bias correction m_hat=2. The 0.2 cannot be taken as the full size of the update.

Training has to define "what we want it to predict" first; only then is there an error and a direction to update in. A gradient is the local effect a small change in a parameter has on the loss; Adam keeps statistics of past gradients, and model parameters, activations and optimizer state are different stored objects.

In a training batch the input and the correct continuation are already given, so the prediction error can be computed for many positions together, while the causal mask still forbids peeking at the future. Q080｜What does next-token training actually predict? How do the labels shift, and which positions is the loss computed on?

What to know first for this question The current position predicts the next one, so the training labels have to be offset accordingly. The error on padding and on non-target regions can be masked out, but the valid conditioning must not be removed along with it.
Lesson 37 · Why text has to become token IDs firstLesson 44 · Probability, exponentials and softmaxLesson 53 · One training run end to end

Core answer

Start with the objects and symbols used here
RLHF, the reward model and the policy
RLHF refers broadly to processes that train behavior using human feedback. A reward model scores behavior such as an answer; the policy is the probability model that actually produces actions. Their jobs differ, and a high reward is not automatically factual correctness. Independent example: if the reward model prefers long answers, the policy may learn to write at length without being more accurate; the reward criterion therefore needs to be validated.

At position i the model reads the prefix no further than i and outputs the distribution for position i+1; the training code aligns the logits with the true Token shifted one position to the right. Every known prefix can be processed in parallel in one forward pass, and the causal mask prevents any peeking at the future. The model minimizes the negative log probability of the true token; it does not directly compare the edit distance between the generated sentence and the answer.[TR][RLHF]

Walk the alignment through with five tokens

Start with the objects and symbols used here
BOS / EOS: sequence boundary markers
BOS is usually the special token for the start of a sequence and EOS the one for the end; a particular model or message template may use different names, counts and end markers. They are symbols in the input/output protocol, not proof of semantic correctness. Meeting an EOS does not automatically cut attention between two training samples; isolating the reads still needs a mask, or a sample boundary the implementation supports.

Let the training sequence be [BOS, 我, 爱, 编程, EOS]. A common implementation takes the whole stretch as the input and then aligns it as follows when the loss is computed:

logits position Visible input The label it should predict
0 BOS 我
1 BOS,我 爱
2 BOS,我,爱 programming
3 BOS,我,爱,programming EOS

The last position has no following label, so it usually does not count towards this stretch of loss. An equivalent way to write it is to take the first four tokens as the input and the last four as the labels; do not shift once in the data processing and again inside the model, or it turns into predicting the token after the next one.

For position t the model obtains the vocabulary logits z_t, turns them into probabilities p_t, and the loss is ℓ_t = −log p_t[y_t]. If the probability of the correct token is 0.1, the loss is about 2.3026; if it rises to 0.8, the loss is about 0.2231. The loss of one batch is usually the average over the valid label positions. Here "valid" is decided by the loss mask, which is not the same as the attention mask.

SFT samples can be用户问题 + 助手答案. Some recipes compute the loss only on the assistant's answer positions, yet those positions may still attend to the user's question. Setting the labels at the user positions to ignore is not the same as deleting the question from the input. The data code has to maintain the role boundaries, the end markers, padding and the ignored labels all correctly at once.[CHAT]

How to read the changes in the figure

The second row does not train the model to "say 爱 whenever it sees 爱"; it raises the probability of 学习 after the prefix 我爱. Input and labels have the same shape, which does not mean their contents must match cell by cell.

The whole training text is given in advance, so all three places can be computed together in one forward pass, yet the mask still keeps the earlier positions from peeking at the answer that comes later.

If the losses at the valid positions are 1, 2 and 3, the average loss is 6/3=2; adding one ignored PAD cannot turn that into 6/4.

Do not conflate: when accumulating over batches the number of valid targets differs, so averaging the per-batch means changes the weighting. Normalize by the total loss and the total number of valid targets.

Follow-up: why does generation still go astray when training accuracy looks good?

Training usually uses the true prefix, while inference uses the model's own. After one step picks the wrong token, what follows may enter states that appeared rarely in training; this difference between the training and the generation conditions is usually called exposure bias. Another reason is that the loss is averaged over tokens, so improvements in format and fluency can mask a few high-risk factual errors. Validation cannot look at the training loss alone: the model also has to generate on its own, and the complete task result has to be checked.

Follow-up: can perplexity compare two models with different tokenizers directly?

Generally they cannot be compared directly. Perplexity is usually exp(平均Token负对数似然); one Tokenizer splits the same text into more tokens, so the unit being averaged is no longer the same. Comparing across tokenizers requires an explicit normalization by bytes, by characters or by a unified evaluation setting, with the dataset controlled as well. PPL on different corpora also cannot be taken as one leaderboard of overall ability on a single scale.

Follow-up: when several samples are concatenated for training, does inserting EOS isolate the information?

EOS is a token; it does not establish isolation in the computation by itself. With an ordinary causal mask, the later sample can still see the earlier one. Whether such cross-sample attention is allowed is a matter of training design; if strict independence is required, use a block attention mask or a boundary mechanism the implementation supports, and handle the position IDs. Keep "learning to stop at EOS" separate from "explicitly cutting the attention".

Why two contributions appear here on the backward pass

One and the same R affects the final loss through both the direct main path and the FFN branch, and the two effects are later summed at R. Likewise X both travels the residual and goes through N1 into Q/K/V. Keeping only one of those gradients changes the training.

Q082｜Once the loss is computed, how are the parameters updated? And why is AdamW not just the gradient times the learning rate?

What to know first for this question A gradient points in the local uphill direction; the optimizer adjusts the parameters in the opposite direction. AdamW also maintains gradient statistics and weight decay, so resuming training is not just loading the weights.
Lesson 52 · Only the calculus you will actually useLesson 53 · One training run end to end

Core answer

Backpropagation follows the chain rule over the computation graph, computing the parameter gradients layer by layer from the loss; the optimizer obtains the update from the gradients and from its own history. AdamW maintains first- and second-moment exponential moving averages of the gradients, and decouples weight decay from the adaptive gradient update. Caches, gradients and optimizer state are different objects.[ADAMW]

From the output projection all the way back to the embedding

Start with the objects and symbols used here
∂, ∇: partial derivative and gradient
∂L/∂w asks how the loss L changes when w changes a little while the other independent variables are held fixed. These rates of change across many parameters make up the gradient ∇L. They are derivative notation, not two ordinary numbers divided by each other. Independent micro-example: for L=w², the gradient at w=3 is 6. In the simplest update w←w−η×6, η is the learning rate.

Let the final hidden state be h and the output matrix W, so that z=hW. For softmax cross entropy,∂ℓ/∂z = p−one_hot(y). If the probability of the correct class is too low, the gradient on that class's logit is negative, and gradient descent pushes that logit up. This is the first step from a probability prediction to a parameter adjustment.

Next,∂ℓ/∂W = hᵀ(p−y), ∂ℓ/∂h = (p−y)Wᵀ. The latter term continues through the final normalization, through each layer's FFN, Attention and residual branch, and finally to the Embedding. The gradients of the residual branches have to be added together, and when a shared parameter is used in several places its gradients accumulate as well. What automatic differentiation does is combine these local derivatives; it does not search for "which neuron knows this fact".

One common way of writing AdamW is:

m_t = β1 m_(t−1) + (1−β1) g_t
v_t = β2 v_(t−1) + (1−β2) g_t²
m_hat = m_t / (1−β1^t)
v_hat = v_t / (1−β2^t)
θ_t = θ_(t−1) − η m_hat/(sqrt(v_hat)+ε) − η λ θ_(t−1)
Start with the objects and symbols used here
Mixed precision, loss scaling and master weights
Mixed precision uses different numeric formats for different computations or states. A master copy of the weights can be kept at higher precision as the baseline for updates; loss scaling enlarges the loss before the backward pass and then scales the gradients back down, lowering the risk of underflow at some low precisions. This is not multiplying the learning rate up at will. Whether master weights or loss scaling are actually needed depends on the precision format, the optimizer and the implementation.

Squaring and division are element-wise operations. m smooths the direction of the gradient, v estimates the scale of the squared gradient, and the bias correction handles the bias caused by the initial state being zero. The weight-decay term is not mixed into g first and then scaled by v, which makes it different from the usual case of "adding an L2 penalty into Adam's loss". Which parameters decay, where ε goes and how mixed precision maintains the master weights all depend on the implementation.

AdamW's "historical state" is accounted for separately from this step's gradient

Follow-up: why does zeroing the gradients matter?

Many training frameworks accumulate by default into.grad. That is convenient for gradient accumulation, but in an ordinary one-step-one-update loop, forgetting to zero it piles the gradients of the previous steps on unintentionally. Conversely, zeroing before every micro-batch destroys accumulation that was intended. The right place is usually just before or just after one effective optimizer step, not mechanically on the first line of every loop.

Follow-up: what does gradient clipping change? And why can it not fix every NaN?

Global-norm clipping scales the whole gradient vector down proportionally when the gradient norm exceeds a threshold, which limits very large updates. It does not repair illegal forward values that have already occurred, a fully masked softmax, a division by zero or corrupted data. Under mixed precision the loss scaling also has to be undone at the right moment before clipping, or the threshold is in the wrong units. When a NaN appears, locate the earliest illegal tensor instead of only lowering the learning rate and hoping.

Follow-up: is loading the weights enough to resume training?

Start with the objects and symbols used here
checkpoint: you must look at the object that was saved
A model checkpoint saves weights or training state; activation checkpointing saves a few intermediate nodes so they can be recomputed on the backward pass; an agent task checkpoint saves how far execution has got. The three share a name, but what they restore is entirely different. When you see "checkpoint", first ask whether it restores parameters, recomputes activations, or continues a task. An agent saving a summary does not update model weights.

Continuing along the same training trajectory usually also requires restoring the optimizer's m/v, the learning-rate scheduler, the step count, the position in the data sampling and the random state; distributed training further involves the sharding and the global progress. Loading the weights alone can start a new optimization process, but that is not seamless continuation. An inference deployment generally does not need the optimizer state, which is why a training checkpoint and an inference weight package can differ markedly in size.

Mixed precision and recomputation: the wrong order makes the optimizer quietly take a wrong step

Prerequisite: Lesson 52 · Lesson 53 · Lesson 62. Reading order: confirm the run contract first, then look at the counterexamples and the fix, and finally test the limits.

Scaling the gradient is a numerical measure, not a change to the learning rate

The loss scaling in AMP scales the loss up first, so that smaller gradients are easier to represent in low precision; the gradients should be restored before the update. The official PyTorch example explicitly requires an unscale before gradients are inspected or clipped, and attention to the timing while gradients are being accumulated.[AMP]

Minimal counterexample: a true gradient of 10, a scale factor of 100 and a clipping threshold of 1. Restore first and then clip, and the gradient is 1; clip 1000 down to 1 first and then divide by 100, and the gradient becomes 0.01. Both are finite and both can produce an update, but they differ by a factor of 100. This book's CPU test verifies this algebra; it is not taken as a measurement of GPU AMP.

Different frameworks wrap up how the scheduler counts steps, so it cannot simply be asserted that every microbatch should advance it. What matters most is recording four different counts: samples seen, backward passes, attempted updates and updates actually performed. A learning rate that changes while the parameters do not may be a step skipped because of overflow, not necessarily a model that is not learning.

Activation checkpointing runs your function a second time

Recomputation does not read a snapshot from disk; it re-executes part of the forward pass during the backward pass. If the function writes files, increments a global counter, consumes uncontrolled random numbers or reads a global configuration that has since changed, it can disagree with the original forward pass. The official documentation states the limits for RNG saving, device changes and the reentrant mode.[CHECKPOINT]

This book applies a non-reentrant checkpoint to sin(x)*x, records that the function is called more than once, and checks that against the analytic gradient. Taking the monitoring count of "the function ran once" directly as a sample count is then wrong. Side effects should be moved out of any region that can be recomputed wherever possible.

Follow-up: can training be resumed from the model weights alone?

It can restore some inference function, but not necessarily the same training trajectory. The optimizer momentum, the scaler, the scheduler, the random state, the data cursor and which microbatch the accumulation had reached may all be necessary. Record the level of guarantee the restore gives: continued training, approximately the same training, or strict reproduction; do not call them all "lossless restore".

Follow-up: why can checkpointing not be wrapped around any function at all?

It trades recomputation for activation memory, and requires the recomputation to preserve the semantics that matter. How a random mask is restored, calls across devices, and changes to parameters between the two forward passes all have to be checked. It also adds computation; where memory is plentiful and compute is the limit it can be slower, so the gain should be measured at the same batch size and on the target device.

Step one: in the RMSNorm backward pass, do not forget that the denominator depends on the input

Let a single row be y_j=g_j x_j/r, where r=sqrt(mean(x²)+ε), with G_y as the upstream. First write u_j=G_yj g_j. Now compute the effect of any input cell x_i: on the one hand it changes its own numerator directly, and on the other it changes the r that all the outputs share.

G_xi = u_i/r − x_i × mean_j(u_j x_j) / r³
G_gj = Σ_b,t G_y[b,t,j] × x[b,t,j]/r[b,t]

The second term comes from dr/dx_i=x_i/(d r) and d(1/r)/dr=−1/r², and then the effects of all the output cells on that denominator are added up. Writing only the first term amounts to treating r wrongly as a constant; the numbers and the direction of learning can differ noticeably.

This model has three independent scale parameters, g1, g2 and gf. Apply this rule separately to the final norm, the norm before the FFN and the norm before attention; the r or the gradient from one of them must not be handed straight to another.

Step four: why a term is subtracted in the softmax backward pass

For one row A=softmax(S) the local derivative is ∂A_j/∂S_i=A_j(1[i=j]−A_i). Every output in this row depends on every score, so G_Si has to add up the effects of all the outputs:

c is one weighted-average scalar for the current row. At masked positions A=0, so the gradient along this path is 0. It is not a matter of multiplying each cell independently by A(1−A) and being done; that would miss the off-diagonal terms.

Q083｜What happens to pre-training data before it reaches the model? And why does data quality become a systems problem?
What to know first for this question The training set is used to update the parameters, the validation set to select and the test set for the final check. Duplication and contamination can make a score look higher without it standing for generalization.
Lesson 53 · One training run end to endLesson 05 · The denominator of an evaluation metric


Core answer


Training is not as simple as "feeding in internet text". Data acquisition, licensing and privacy handling, cleaning, deduplication, mixed sampling, tokenization, sharding and the training/validation split together decide the distribution the model sees. The statistics have to be observed at several stages of the processing chain, not merely recorded as a final total token count.[CHINCHILLA]


The full life cycle of one document


Save the original source and the collection version first, then extract the main text; HTML navigation, repeated footers, mojibake and machine-generated junk make the gradient learn meaningless patterns over and over. Language, format, quality and sensitive-data handling follow. Filters also introduce a selection bias: too strong a preference for one style of writing can wrongly remove professional forums, colloquial speech or rare languages.


Deduplication has to distinguish at least exact duplicates, near-duplicates and rewrites from the same source. An exact hash can only identify identical bytes; near-duplicate methods usually work from fragment features or similarity, together with a threshold. Too wide a threshold throws away valuable independent samples, too narrow a one keeps batches of templates. Deduplication not only saves compute, it also affects memorization and the risk of evaluation contamination.


Next the sampling mixture is set by data source, language, code and difficulty, converted into tokens and packed into training sequences. A large raw volume from one source does not mean it should carry the same training weight; repeated sampling makes the actual training distribution differ from the distribution on disk. What should be recorded is "how many tokens of each kind of data were actually consumed in training", not just how much was downloaded.


An evaluation set should be isolated at the level where sources may be shared. Splitting adjacent functions from the same repository randomly between training and test can make the result mainly reflect projects already seen; putting different sites' reposts of one problem on either side can still leak. For a code Agent, a further distinction is needed between contamination of the model's training, leakage from the retrieval store and exposure in the test itself; these three paths are not the same.

Follow-up: why can more data lower some ability instead?


The training objective optimizes an expectation over the mixed distribution. New data changes the proportions: it can dilute the high-quality tasks that were there, and it can introduce contradictions, noise or a shift in style. A falling total loss does not guarantee that every task subset improves, which is why validation sets separated by language, task and risk category are needed. Data scale and data quality cannot stand in for each other as a single number.


Follow-up: is the knowledge cutoff one uniform timestamp in a database?


Usually not. Different sources were collected and mixed at different times, and post-training may follow the training; the model may also obtain more recent facts from a tool. Whether it knows a particular thing cannot be inferred from one "cutoff date" alone. An engineering system should hand live facts to retrieval that has sources and can be updated, rather than rely on the model's spoken promise that "I know the latest".


Follow-up: can training-data deduplication and agent-memory deduplication use the same method?


Their purposes differ. Corpus deduplication mainly controls the sample distribution and the contamination; memory deduplication also has to preserve a fact's scope of application, its time, its evidence and its negations. "The interface needs a retry" and "this interface must not be retried automatically" are close in wording and still cannot be merged. Similarity can be reused to find candidates, but it cannot be used directly to rule on knowledge equivalence.


Q084｜Why does training use more VRAM than inference? What do gradient accumulation, checkpointing and sharding each save?
What to know first for this question Parameters are the model's long-term numbers, activations are the result of this computation, and the optimizer state records update statistics; the three differ in quantity, precision and life cycle.
Lesson 40 · What "putting it on the device" meansLesson 53 · One training run end to endLesson 62 · Computing fast and fitting in memory


Core answer


Besides the parameters, training also has to keep the gradients, the optimizer state and the activations used for the backward pass; inference usually has none of these objects, though a long context needs the KV cache. Different optimization techniques target different objects, so "saving VRAM" must not be treated as one and the same thing.


Estimate from a list of objects, instead of memorizing one fixed multiple


Take one teaching configuration: low-precision parameters 2 bytes, low-precision gradients 2 bytes, FP32 master weights 4 bytes and Adam's two FP32 states 8 bytes, for about 16 bytes per parameter, not yet counting activations, temporary buffers and communication. Some implementations have no separate master weights, keep the gradients in FP32 or quantize the optimizer, and then this factor changes. When estimating, list the objects and their dtype first, then multiply by the parameter count.


What the activations occupy depends on the batch, the sequence length, the number of layers and the kernel. If standard attention explicitly stores [B,H,T,T] it becomes very expensive; a more memory-frugal kernel avoids materializing it. Activation checkpointing, by contrast, does not store some of the intermediate values and runs part of the forward pass again during the backward pass, trading compute for VRAM. It is not the same concept as "saving a model checkpoint file".[FLASH]


Start with the objects and symbols used here
Dropout: the rule that randomly zeroes values during training
The common inverted dropout zeroes elements at random during training with drop probability p, and divides the kept ones by 1-p so that the expected scale is preserved. Evaluation mode usually turns this random operation off; the underlying function may require the caller to pass p=0 explicitly. Independent example: with p=0.5, a value of 2 comes out as 4 if it is kept in a given mask and as 0 if it is dropped. This is not training permanently deleting the corresponding model parameter.
Gradient accumulation cuts a large batch into K micro-batches, with consecutive backward passes but a delayed update. If every micro-batch contains the same number of valid tokens, dividing the loss by K usually gives the corresponding average gradient; when the valid token counts differ, mechanically averaging each micro-batch's average loss changes the sample weights. Normalize by the total number of valid tokens instead. Dropout randomness, the order of floating-point accumulation and the like also keep the numbers from matching exactly.


Start with the objects and symbols used here
DP, TP, PP, ZeRO and FSDP
Data parallelism lets several copies of the model process different samples and synchronize their gradients; tensor parallelism splits the parameters and the computation of a single operator; pipeline parallelism puts different layers on different devices. ZeRO/FSDP-style techniques also shard parameters, gradients or optimizer state. What they split differs: dividing one layer's matrix in two is not the same as giving two independent user tasks to two agents.
Sharding the parameters, gradients and optimizer state addresses the redundancy across devices; tensor parallel splits the matrix computation inside a layer; pipeline parallel splits by layer; data parallel processes different samples and then synchronizes the gradients. They can be combined, but their communication and scheduling costs differ. Lesson 63 goes on to take apart the parallelism on the inference side.

Follow-up: does quantizing to 4bit mean every part of training's memory becomes a quarter?


Start with the objects and symbols used here
LoRA, low rank and r
LoRA represents part of a weight increment as the product of two smaller matrices instead of retraining the whole large matrix. r is the inner dimension, and it bounds the maximum rank of that product. Where sources use a row-vector or a column-vector convention, the left-right order of A and B can differ. Micro-example in the right-multiplication convention: with W[4,6], the increment A[4,2]B[2,6] is still [4,6]; r=2. A here is not the table of attention shares.
No. Quantization usually changes mainly the storage of the base weights; the backward activations, the adapters, the optimizer, the quantization scales and the temporary dequantization computation still occupy memory. QLoRA freezes the quantized base and trains low-rank adapters, so it is not the case that any 4bit weights can be updated as full parameters directly.[QLORA]


Follow-up: is a smaller training learning rate always safer?


A small learning rate reduces the change per step, but it can also fail to learn within the budget; a large batch, accumulation, warmup and changes in the data all change what scale is appropriate. In engineering terms, look at the gradient norm, the update-to-weight ratio, the validation loss per task and numerical anomalies. Training instability cannot be removed by a single "conservative parameter".

The hidden bias in gradient accumulation: is the average taken over batches, or over valid tokens?
Prerequisite: Lesson 52 · Lesson 53 · Lesson 05. Reading order: confirm the runtime contract first, then look at the counterexamples and the fix, and finally test the limits.
This is an engineering problem that has been fixed in public


Hugging Face publicly described the loss-normalization problem in gradient accumulation on 2024-10-16: when small batches have different numbers of valid tokens, averaging each batch's average loss is not the average of the loss over all the tokens. What is re-checked here is the basis of that historical fix, not a claim that current Transformers still carries the bug. [GRAD]


Let microbatch j (the small batch processed in memory at one time) have a loss sum of S_j and n_j valid tokens. If the objective is to give every valid token equal weight, it should beΣS_j / Σn_j, not mean(S_j/n_j). The latter gives every token in a small batch a larger weight.


The same set of numbers shows that both the loss and the gradient change


Take two batches: loss sums of 2 and 3, token counts of 1 and 3. The correct loss is 5/4=1.25, while the wrong mean is (2/1+3/3)/2=1.5. This is not a display-precision error; the objective function has changed.


This book verifies it further with real autograd: the parameter w starts at 1; the first batch has a single squared error against target 0, and the second has three squared errors against target 2. Averaged over the 4 tokens the gradient is −1; averaging each batch first and then averaging those gives 0. The wrong implementation decides "nothing needs to change at this step", while the correct one increases w. Checking whether the loss curve is smooth does not reveal this at all.


Correct accumulation needs the normalization basis to be known first


You can obtain the total number of valid tokens across all the small batches in this round first, then divide each batch's sum loss by that same total and run the backward pass. If it cannot be known in advance, you can accumulate gradients that have not been mean-scaled and then scale them consistently by the valid total accumulated; but this has to work together with AMP, gradient clipping, the optimizer and the distributed reduction, and it cannot be settled by "adding a constant" after the wrong scaling.


For D DDP ranks that average the gradients by default, to obtain全局梯度和 / 全局Token数N, each rank's local loss sum should be scaled by D/N, and only once DDP has divided by D as well is the target reached. If an upper-level Trainer has already done this, multiplying by D by hand repeats it. The algebra here assumes the default averaging reduction; re-derive it when a communication hook or a framework policy changes.


How the pinned historical source carries out this fix


Merge commit c1c7e89620b43f0924148e267a6da5d38450ce1f's loss_utils.py, when num_items_in_batch is provided, sums first and then divides by that denominator; the CausalLM path shifts the logits/labels first.[HFPR] The function does not prove on the caller's behalf that the count passed in is correct; you still have to track whether it covers this accumulation group, whether it excludes the ignored items and whether it matches the targets after the shift. The parameter name contains batch, which does not mean it is necessarily "the number of samples".


Inequivalence does not come from the denominator alone


Even with the normalization correct, dropout, BatchNorm, the timing of gradient clipping and the order of floating-point reduction can keep small-batch accumulation from matching one large batch bit for bit. The first step of acceptance is to switch off randomness and cross-sample statistics and compare the gradients on the same samples; the second is to restore the real training factors one at a time. Do not use "it is normal for them not to match exactly" to cover up a wrong denominator.


Follow-up: is averaging per sample always wrong?


Not necessarily. If the product objective really is to give every sample equal weight rather than every token, a per-sample average can be reasonable. The error lies in claiming to optimize a token-average objective while actually optimizing another one. Whether long and short answers should carry equal weight is a modeling decision; write it down and keep the training and evaluation bases consistent.


Follow-up: what if a whole microbatch is masked out by ignore_index?


Its valid count is 0. That batch's sum can be 0, but 0/0 must not be computed for it on its own and then accumulated. When the global valid count is 0, skip it or report a data error, and handle the scheduler and the statistics counts; do not create a NaN and go on updating.
