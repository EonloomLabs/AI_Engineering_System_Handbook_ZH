Prerequisites for this chapter

Inference splits into processing the input you already have and then producing new tokens one at a time. The output scores are not vocabulary IDs, and the probabilities are not the accuracy of the answer; sampling picks an ID out of the distribution, and decoding turns that ID back into text.

Each question in this chapter lists the groundwork it needs. You can take the matching Foundations lesson first, or use the self-check to confirm how well you have it.

Q089｜What is the difference between prefill and decode? When is the first output token produced?

What to know first for this question Prefill processes the prefix that is already known, and decode uses it to generate new tokens. Both stages use the model parameters; what differs is how the input is organized and which results can be reused.
Lesson 57 · From the last row of numbers to one token, and on to a whole answerLesson 58 · KV cache explained from scratch

Core answer

Prefill: it processes the whole known input prefix and builds the cache at every layer; the scores at the last input position (logits) can already predict the first new token. Once that token has been sampled, it is the next decode that sends it through all the layers as input and predicts the token after that. The output is not thought out in one go and then sent in installments.[CACHE][TR]

Three generation steps, followed through by time and position

Suppose the prompt is x0,x1,x2,x3, of length P=4. What we want to generate is y0,y1,y2.

Moment Tokens fed into the network this time Positions computed this time What the KV holds afterwards Which output picks the next token
Prefill x0…x3 0…3 x0…x3 Sample y0 from the logits at position 3
Decode 1 y0 4 x0…x3,y0 Sample y1 from the logits at position 4
Decode 2 y1 5 x0…x3,y0,y1 Sample y2 from the logits at position 5

In the table y2 has been sampled, but y2 has not yet passed through the network as input, so the cache does not contain it yet. If generation continues, y2 is only processed at the next step. This "one-step offset" affects the cache length, the stopping condition and the recovery logic. Do not read "how many tokens have been emitted" as "how many output tokens have entered the KV". A particular service may wrap these steps up, but the underlying dependency on these conditions remains.

Why can prefill compute several positions together? Because the input tokens are all known already, so each layer handles many positions at once through matrix operations, and the causal mask then forbids any dependence on the future. Why can standard decode not produce the next 100 real tokens in one go? Because y1 depends on the sampled y0 and y2 depends on y1; a token that has not been selected yet is unknown and cannot be used directly as the next layer's input.

Start with the objects and symbols used here
Query, Key, Value: three intermediate numeric representations
q is one row of query representation for the position receiving information; k is one row of matching representation offered by a readable position; v is one row of content representation that position contributes to the mix. Capital Q/K/V collect several rows into tables. They are computed from the input and the parameters, and they carry the separate jobs of scoring and of supplying content. One q dotted with two k gives two scores; softmax turns them into two shares; those shares multiply the two rows of v, and the results are added. Nothing here generates a search term, and nothing here picks an answer directly.

Every model layer still runs during generation. What the KV cache saves is the repeated computation for old positions; it does not mean that a new token passes only through the last layer. Each new position has its own Q/K/V at layer l and reads from that layer's own history cache.

The token just selected has not yet entered the turn of computation that is its own

How to read the changes in the figure

By the end of the first row the interface may already be showing 学习, but the cache still holds only 我、爱. Selection and processing happen between two neighboring rounds.

When only "学习" is sent on the next turn, the old information comes from the KV in each layer; it is not that the model guesses the next token from this one token alone.

Once EOS has been selected, generation usually stops right there; this example does not put EOS through another round. The number of outputs, the amount of visible text and the cache length can therefore all differ.

Do not conflate: counting a new token into the cache and then sending it in again as new input appends it twice; go by the actual processing log, not by where the character count on screen updates.

Follow-up: why can training predict a whole stretch in parallel?

Start with the objects and symbols used here
Labels, teacher forcing and shift
A label is the correct target to compare against; next-token training lines each input position up with the token after it. Teacher forcing computes with the real prefix from the data rather than replacing it with what was just sampled. Independent example: for the full sequence [a,b,c,d] the input [a,b,c] can be paired with the labels [b,c,d]. When the interface already shifts them, do not shift them a second time outside it.

Training uses the real prefix for teacher forcing: the target at position i is known, so the conditional probabilities at different positions can be computed at the same time. Inference uses the model's own generated prefix, where the previous choice changes the input that follows. This is also one source of the possible gap between the training distribution and the generation distribution; it does not mean that copying labels during training buys reliable inference.

Follow-up: if each decode takes only one token as input, how does the model know the whole question?

That token uses its Q at each layer to read that layer's historical K/V, and those caches hold the contextualized computation of the original prefix. A short input tensor does not mean short conditioning information. If the cache is lost, the service has to rebuild the prefix or use some other supported state; handing over one isolated token and expecting the same distribution will not work.

Follow-up: does a streaming display mean that every character on screen corresponds to one decode?

Not necessarily. A token can cover several characters or an incomplete byte sequence, a service may send increments in batches, and network chunks have nothing to do with token boundaries. The visible text may also leave out internal reasoning tokens. The granularity of the UI display, of network events and of the model's token generation must be kept apart.

Engineering deep dive · E07 · continues Q013

With attention_mask supplied, why can right-padded generation still read the wrong logits?

Prerequisite: Lesson 38 · Lesson 47 · Lesson 57. Reading order: confirm the runtime contract first, then look at the counterexamples and the fix, and finally test the limits.

The mask and the address the output is sampled from solve different problems

attention_mask limits reading on the key side; logits[:, -1, :] picks the last column of the output tensor. There is no logical entailment between the two steps. With right padding the last column may correspond to a PAD query, and the mask will not automatically turn index −1 into the last valid token. The Transformers tutorial on decoder-only generation therefore requires left padding on that path.[GENERATE]

Two sequences are fixed locally with validity tables [1,1,0] and [1,1,1], so the last valid indices should be 1 and 2. With the candidate scores built, the correct selection yields classes [1,1], while taking the last column unconditionally yields [0,1]. That shows the error comes from choosing the address, not from softmax computing wrongly.

Do not write length-minus-one as a universal formula

mask.sum(-1)-1 gives the last valid index only for a right-padded layout in which "the valid items sit contiguously from 0". For left padding,[0,1,1] sums to 2, but the last valid subscript is 2, not 1. A more general check derives the last valid position from the position indices together with the validity flags; a real generator also has to get the position encoding and the cache right at the same time.

positions = torch.arange(T).expand(B, T)
last_valid = positions.masked_fill(~valid, -1).max(dim=-1).values
if (last_valid < 0).any():
    raise ValueError('empty effective input')
next_logits = logits[torch.arange(B), last_valid]

This is custom sampling logic written for teaching; it is not a recommendation to bypass the library's prepare_inputs_for_generation. When plugging into a ready-made generate, follow the padding convention that the model supports.

EOS used as PAD: why does generation not stop right at the start?

Some decoder-only models have no separate PAD, so inference can use EOS as the left padding item. That ID appearing in the input and that ID being newly generated this round and triggering a stop are different events; the validity mask decides the input's role. During training it is more dangerous: clearing labels by "setting −100 everywhere the ID equals EOS" also erases the end target that really has to be learned. The distinction should follow the padding positions, not the ID value alone.[GENERATE]

Follow-up: a single input works but a batch misbehaves — what should be checked first?

Check left and right padding, the real lengths, the last valid position, position_ids, EOS/PAD sharing and the cache offset. Running the same sample alone and then mixed into a batch of long and short sequences locates the problem better than blaming GPU nondeterminism. Do not let a synthetic test give every sentence the same length, or these bugs will never show up.

Follow-up: can right padding never be used with a decoder model?

No. Training and a custom forward pass can use right padding correctly, as long as the mask, the labels and the output index agree. The problem arises when a particular piece of generation code assumes that the last tensor column is the last valid one; turning one call chain's convention into a mathematical law about models creates a new misunderstanding.

Follow-up: why can many positions be trained in parallel while generation still goes one at a time?

In training every real prefix is known, so all rows can be computed at once under the constraints of the mask; in generation the next round's input comes from this round's actual choice and does not exist yet. Do not read training's one row of logits per position as predicting several unknown future words at once.

Q090｜How do temperature, top-k and top-p change the output? And why is a temperature of 0 still not a hundred percent reproducible?

What to know first for this question Temperature changes the scale of the scores first, top-k filters by count and top-p filters by cumulative probability; after filtering, renormalization is still needed, and which candidate gets drawn is not fixed for ever.
Lesson 44 · Probability, exponentials and softmaxLesson 57 · From the last row of numbers to one token, and on to a whole answer

Core answer

Start with the objects and symbols used here
Top-k, Top-p and renormalization
Top-k keeps the k items with the highest probability; Top-p sorts by descending probability and keeps the leading candidates until the cumulative probability reaches a threshold. When used for sampling, the kept candidates have to be renormalized over the remaining total mass. Here k is a number of candidates and p a cumulative-probability threshold; k is not the attention Key table K, nor the representation width d_k.

The model gives vocabulary logits first; the decoding strategy then turns them into a candidate distribution and selects a token. Temperature scales how sharp the distribution is, Top-k: a cap on the number of candidates, Top-p: a cap on the cumulative probability covered by the high-probability candidates. They affect exploration and diversity; they provide no guarantee of factual correctness.[GENERATION]

Top-k keeps the k items with the highest probability and then normalizes. Top-p sorts by probability first, takes the smallest prefix set whose cumulative probability reaches the threshold, and then normalizes. For example, with probabilities [0.55,0.25,0.15,0.05], p=0.8, a common implementation keeps the first two items; with p=0.9 the third has to be kept as well. The boundary cases, the minimum number kept and the order relative to other processors all depend on the implementation.

A temperature of 0, in an interface (API), usually denotes a convention for some kind of greedy selection, not a literal division by 0. Greedy selection takes the largest logit at each step, which is a local decision; it does not guarantee the highest probability over the whole sequence, let alone the best task quality. Beam search explores several candidate prefixes, but for an open-ended answer it can also lead to repetition or unnatural text, so search width is no universal quality knob.

Follow-up: why can results still differ with a fixed seed?

The seed controls part of the random sampling. A change in the model version, the request template, tool content, parallel kernels, the order of floating-point reduction or the service configuration can still change the logits. Candidates that are nearly tied can swap places over a tiny numerical difference; once one token changes, the prefix that follows changes too and the difference grows. Fix the conditions you can control first, and only then discuss how reproducible things are.

Follow-up: can a repetition penalty solve repetitive output?

It can adjust the tendency to select tokens that have already appeared, but repetition can also come from the prompt, the stopping condition, the training distribution or the task itself. Repeated symbols and variables in code may be the correct output, and too strong a penalty will break the code. First establish whether the repetition is a content problem or a protocol loop, then choose where to fix it: in decoding, or in the host framework (Harness).

Follow-up: should many sampling parameters be tuned at once?

Changing several dimensions at once is a poor idea, because attribution then becomes very hard. Decide first how stable and how exploratory the output needs to be for the task, fix a baseline, then change one key parameter and watch the real success rate. APIs and models support parameters differently, so an example from one open model cannot be applied unchanged to every inference service.

Temperature, top-p and banned words: why may "the parameters are all the same" still not be the same sampling algorithm?

Compare the order, not just the parameter values

A generator's selector is usually a chain of score processors: repetition penalty, constraint mask, temperature, top-k/top-p, renormalization and sampling. They are not naturally interchangeable functions. If a version upgrade changes the order, the defaults or an inherited generation_config, a different strategy may run even though the two parameters you wrote by hand are the same. What has to be recorded is the effective configuration and the actual order of processing. [GENERATE]

With [2,1,0] fixed, one counterexample to commutativity

This example does not change F09's candidates or scores. At temperature 1 the probabilities are about [0.665241,0.244728,0.090031]. With a top-p threshold of 0.6 the first item is already enough, so only A is kept. If the temperature is changed to 2 first, the probabilities are about [0.506480,0.307196,0.186324], and a threshold of 0.6 then requires keeping both A and B.

So "temperature first, then top-p" and "truncate on the original distribution first, then raise the temperature" give different candidate sets. In the second case, once only A is left, raising the temperature will not bring the discarded B back. This is a mathematical counterexample, not a claim that every library uses the wrong order. When debugging, print the number of surviving candidates, the top items and the probability sum after each processor.

What to do when constraints forbid every candidate

A structured grammar, banned words, length and EOS rules can all apply at once. When one step is negative infinity everywhere, it is not acceptable to go on with an ordinary softmax and then sample after turning NaN into 0. Spell out which constraint may be relaxed, whether to terminate as a failure, and whether to request a regeneration. Constraint priority is a product policy; silently breaking a permission or grammar rule is not an acceptable numerical fallback.

Keep precision error and strategy differences apart

If two candidate scores are very close, a difference of floating-point backend can change the argmax; if the outputs diverge widely even though the inputs were far apart to begin with, check the tensors, the mask and the processors first. PyTorch notes that the numerical result of fused attention can differ slightly between backends.[SDPA] Do not call every inconsistent result "random", and do not require every piece of hardware to produce a string identical word for word before it counts as correct.

Follow-up: is temperature=0 the same as dividing softmax by 0?

It cannot be implemented that way. Products usually use it to express a deterministic choice or a separate branch; division by 0 is not a legitimate temperature scaling in mathematics. When using an API, check whether that model allows 0 and what it means there; when implementing it yourself, take an explicit argmax and define the rule for ties at the maximum.

Follow-up: how can a stable test be written for a sampling module?

Test the candidate set, the normalization of the distribution, the interval selected for a given random number, and whether the frequency statistics fall in a reasonable range — each of them separately. A fixed random seed is for replay, but one draw that happens to pick A is no proof that the distribution is right. Comparing distributions across implementations, and one deterministic step worked out by hand, localize a problem better than a snapshot of a whole sentence.

Top-k and top-p are not the same filter

Top-k keeps the k candidates with the highest scores and then normalizes among them. With k=2 the baseline keeps A and B, and the probabilities become about [0.731058579,0.268941421,0].

Q091｜How does the model know the answer has ended? What is the difference between EOS, a stop string, a length limit and the end of a tool call?

What to know first for this question The end token, a textual stop string, the cap on output length and a cancellation signal come from different mechanisms; whether generation really finished has to be judged from the returned status as well.
Lesson 57 · From the last row of numbers to one token, and on to a whole answerLesson 07 · APIs and streaming protocols

Core answer

The end may come from the model sampling an end marker, or from the service terminating because it reached the length cap, hit a stop condition, produced output that has to be handed to a tool, was canceled or raised an error. "No more text arriving" does not mean "the answer is complete", still less "the task is done".[GENERATION][STREAM][TOOLS]

Four layers of end semantics

Start with the objects and symbols used here
BOS / EOS: sequence boundary markers
BOS is usually the special token for the start of a sequence and EOS the one for the end; a particular model or message template may use different names, counts and end markers. They are symbols in the input/output protocol, not proof of semantic correctness. Meeting an EOS does not automatically cut attention between two training samples; isolating the reads still needs a mask, or a sample boundary the implementation supports.

The first layer is the end of the token sequence. The model can assign a probability to the end-of-sequence token (EOS) or to a message-end token and sample it; which marker that is depends on the template. The end marker is trained as well; it is not an independent prover that knows every user requirement has been met.

Start with the objects and symbols used here
JSON: structured text, not an action being executed
JSON is a text format that expresses data as objects, arrays, strings, numbers and so on. A braced object maps field names to values; a bracketed array keeps the order of its items. Parsing JSON only yields data; it does not automatically run a tool name inside it. Independent example: {"path":"a.py","limit":3} has two fields; "3" is a string while 3 is a number, and a schema can require either one.

The second layer is the end of the model response. A service may terminate because of the maximum output budget; that case usually carries an incomplete status or one related to length. A half-finished payload (JSON), an unclosed code block or unfinished tool arguments cannot be treated as a valid result just because the connection closed. A stop string is usually detected by decoding or by post-processing in the service; it can span several tokens, so the boundary has to be maintained.

Start with the objects and symbols used here
call_id,item_id,request_id
These are identifiers for objects at different layers: a tool call, an output item, a request or a response. They match increments and results back to the right object; they are not the token IDs of the model input, and they are not business idempotency keys by nature. Two read_file calls can carry c1 and c2; when the results come back in the reverse order they are still paired by call identifier, not guessed by tool name.

The third layer is the tool handoff. Once the model has generated one complete call item, the current inference may pause and hand control to the harness. When the tool is done, the result is appended and the next inference is started. This is one stage of a loop finishing, not the user's task finishing. The returned call_id exists precisely to tie which call got which result.

The fourth layer is business completion. The result of a coding task is mainly the current files and the test evidence, not a sentence saying "fixed". If the final answer appears but the tests were never run, the files were never written, or the outcome of an external operation is unknown, the task may still not be done.

Q092｜What actually happens when a reasoning model "thinks a while longer"? And how does that relate to multi-agent setups and CoT?

What to know first for this question The reasoning compute budget can exceed the length of the answer that is finally shown. Whether more computation helps should be judged by the task success rate, not by how long the answer is.
Lesson 57 · From the last row of numbers to one token, and on to a whole answerLesson 54 · The math that comes before post-trainingLesson 05 · The denominator of an evaluation metric

Core answer

A reasoning model can improve its results on some tasks with extra inference-time computation; how much of the internal mechanism and state is published varies from product to product. An ordinary multi-turn loop (Agent) goes about it differently: it adds information and execution steps through external tools and repeated model calls. CoT, search, self-consistency, multi-agent setups and the reasoning budget sit at different levels and cannot all be lumped together as "thinking more".[REASON][R1][REACT]

Four kinds of extra computation, distinguished

The first is producing more intermediate reasoning within the same generation. Later tokens can use the earlier intermediate results, but an error can be carried along too. More length does not automatically guarantee valid reasoning; how the model was trained and how the task is structured both matter.

The second is sampling several answers repeatedly and then choosing among them by consistency or with a verifier. It uses several generation paths and needs reliable aggregation; if every path rests on the same wrong fact, the majority vote is still wrong. Aggregation is a completely different problem for a programmatically checkable question than for an open research question.

The third is searching over candidate states: Tree of Thoughts-style methods, for instance, generate, evaluate, keep or prune explicitly. What it gains depends on whether the evaluator can recognize the better branch, and the number of branches and the depth both raise the cost. Without a reliable evaluator, the search may prune the correct path too early.

The fourth is an agent calling external tools: reading the current source, running the tests, querying a database. This is not simply more internal reasoning; it brings in new evidence the model did not have. For "why does the current code fail", one correct test run or file read can be worth more than ten times as much reasoning without evidence.

5 Verify the gainCompare against the same failure case and the same result criterionMore generated text does not mean a more accurate root cause.

Join the steps up. The internal reasoning budget, external information and multi-agent orchestration change the computation, the evidence and the organization respectively.

Limits and counterexamples. Nothing here claims that the visible text equals the model's internal reasoning, and no hidden reasoning process is disclosed or invented.

The best first greedy step does not make the two-step sequence the most probable

Input and conditions. At the first step P(A)=0.6 and P(B)=0.4. If A has been chosen, the second step has P(E|A)=0.51 and P(F|A)=0.49; if B has been chosen, P(D|B)=0.99 and P(F|B)=0.01. Only a fixed length of 2 is compared.

Follow-up: are reasoning tokens a complete record of the model's real thinking?

That cannot be inferred. The visible explanation, a reasoning summary and the model's internal computation are not a complete audit trail in one-to-one correspondence. The exact form of the hidden content and the training mechanism behind it may not be public. Engineering diagnosis should work from observable inputs, tools, outputs, state and tests, and must not take a self-report for the whole causal explanation.

Follow-up: does a complex task always call for the highest reasoning effort?

Look at the bottleneck first. Missing evidence, an unavailable tool or a permission error will not resolve themselves at a higher effort. High effort may suit a complex derivation or a comparison of approaches, but it adds latency and cost; measure the gain on real tasks of the same kind. For a simple, low-risk task, piling on reasoning and extra rounds of review in the name of "rigor" is usually wrong.

Follow-up: if the model corrects a mistake within the current conversation, has it learned?

It can be called in-context adaptation or a behavior correction, but ordinary inference has not updated any parameter as a result. Whether it survives the end of the session depends on an external memory or a training system. Writing feedback into the history, persisting experience and fine-tuning the weights are three different operations, each needing its own design for storage, permissions and verification.

No: the full unit interval cannot be used as it is. The candidate probabilities have to be renormalized, or equivalently the sampling has to happen over the interval of the correct total mass. Otherwise a random number in the tail has no candidate to match, or the result comes out biased.
