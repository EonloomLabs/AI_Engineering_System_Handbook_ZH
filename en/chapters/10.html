Prerequisites for this chapter

The network does not deliver a complete answer in one go. Bytes, text fragments, structured events and the tool-call object are different boundaries; seeing one closing brace is not the same as one valid tool call having been completed.

Each question in this chapter lists the groundwork it needs. You can take the matching Foundations lesson first, or use the self-check to confirm how well you have it.

Start with the objects and symbols used here
JSON: structured text, not an action being executed
JSON is a text format that expresses data as objects, arrays, strings, numbers and so on. A braced object maps field names to values; a bracketed array keeps the order of its items. Parsing JSON only yields data; it does not automatically run a tool name inside it. Independent example: {"path":"a.py","limit":3} has two fields; "3" is a string while 3 is a number, and a schema can require either one.

A quick check before the deep reading: cut a message containing both Chinese and JSON into incomplete byte fragments, and work out where it should be buffered, where it should be parsed, and where execution may finally be allowed.

A term with a dotted underline can be clicked for a quick reference. Read the definition of a letter in a formula first; do not let a guessed abbreviation stand in for the derivation.

The JSON in this chapter is a simplified teaching object; for a product API, the specific fields are as its own documentation states. What matters is the different completion semantics from bytes, to events, to the call item, to the business side effect.

Start by separating receiving a stretch of network bytes, assembling one SSE event, obtaining complete JSON, and confirming that a tool call is finished. Execution is considered only after the last of these conforms to the protocol in structure and passes the permission check. If the four layers are run together, half an argument can be taken for a real command.

Q009｜With Function Calling, who actually calls the function? How does the model know the tool's arguments?

What to know first for this question A tool schema describes the shape of the arguments, the call ID is used to match up the receipt, and the executor also checks permissions and business meaning. Valid JSON is only the first gate.
Lesson 07 · APIs and streaming protocolsLesson 08 · Tools and MCP

Core answer

A tool definition exposes the name, the description of what it does and the structure of its arguments to the model; the model generates the intent to call and the arguments, and only the application, or the execution environment entrusted with it, actually calls the tool. The model does not hold a pointer to your Python function. Only when the tool result enters the context again does the information feedback close.[TOOLS]

Converting one read_file layer by layer

Start with the objects and symbols used here
Schema and Structured Outputs
A schema is a set of structural rules about fields, types and the like; a structured-output mechanism makes it easier for the model to return data that follows those rules. Valid fields still do not mean that the target file exists, that access has been granted, or that the request is right for the business. Independent example: path is required to be a string; {"path":3} does not match the type rule, and {"path":"missing.py"} follows the structure yet may still find no file.

A developer registers read_file(path,start_line,end_line), noting that path accepts only repository-relative paths and that the line numbers are one-based with inclusive endpoints. Harness sends the supported schema and the description to the model; the model may then return:

Start with the objects and symbols used here
call_id,item_id,request_id
These are identifiers for objects at different layers: a tool call, an output item, a request or a response. They match increments and results back to the right object; they are not the token IDs of the model input, and they are not business idempotency keys by nature. Two read_file calls can carry c1 and c2; when the results come back in the reverse order they are still paired by call identifier, not guessed by tool name.
{"type":"function_call","name":"read_file","call_id":"c7",
 "arguments":"{\"path\":\"src/filter.py\",\"start_line\":40,\"end_line\":80}"}

The executor first confirms that the call item is complete, then parses the arguments string; it validates field types, ranges and the existence of the tool; it resolves the actual path and checks authorization; it calls the file-reading implementation; and it wraps the result as a tool output tied to c7. The return must at least let the model tell apart "the content of lines 40—80", "the file does not exist", "the path was refused" and "the result was truncated".

A tool's name and description affect which tool is chosen, but what a tool can do is decided by its implementation. A description that says "can read any file" must not widen the process's permissions; conversely, runtime authorization for one directory does not mean the model naturally knows which tool is available. Discovery, selection and execution are three separate links.

Conditions for this example: an independent local function read_file(path). The model returns call_id=c7, name=read_file, arguments={"path":"config.txt"}; the tool result is then filled back in under that same c7.

How to read the changes in the figure

The arguments in the output are often an encoded JSON string and have to be parsed first. The function name exists in the model's text; it does not make the language runtime execute anything by itself.

An executor must not eval arbitrary code supplied by the model in place of whitelisted dispatch; what the model can choose and what the executor really exposes have to correspond.

When returning an error, state whether the action happened, so that the model fixes the arguments instead of blindly resending a side effect.

Do not conflate: treating a name that is not on the whitelist as an ordinary retryable network error hides a problem with the capability boundary.

Engineering mechanisms and failure boundaries

Why can a pre-check and a post-check not replace each other?

One ordering is enough to change the security conclusion

The teaching action: write one record into a temporary table. With the pre-execution hook refusing first, the record count stays 0; with execution first and the post-execution hook refusing afterwards, the record count is already 1. Both paths can show the model "blocked", yet the external facts differ.

In the dispatch_any_with_state path of the Codex source pinned for this round, a pre-execution hook can block the call before the handler; rewriting the input additionally requires the matching tool to support rebuilding the call object. The post-execution hook runs only when the handler has succeeded and supplies post-execution metadata; a post-execution block refuses the result, and the feedback path can change the text the model sees. This must not be stretched into every tool supporting arbitrary replacement of results.[C09:dispatch_any_with_state] A post-execution hook is not an automatic transaction rollback. If the downstream does not support undo, no amount of strictness in reviewing the result can make an earlier action disappear.

Once the arguments are rewritten, is the earlier approval still valid

Suppose the user approves "change the test environment timeout to 30", and the hook then changes the environment field to production. If the approval is bound only to the tool name and not to the complete normalized arguments, the system has transferred one approval to a different action. A correct design binds the authorization to the object finally executed, or re-authorizes once a sensitive argument has been rewritten.

This is an engineering requirement; it does not claim that every product naturally implements the same authorization fingerprint. When reading the code, keep tracking where the rewrite happens, whether validation sits before or after the rewrite, at which layer the approval result is used, and whether a retry may change the arguments.

What each of the three kinds of hook is good for

Position Work it suits What it cannot promise
Before execution Restricting paths, normalizing arguments, resource admission, required approval Cannot prove that a future operation will succeed
After execution Redacting the result, recording evidence, spotting anomalies, deciding whether to let the model continue Cannot deny a side effect that has already happened outside
Task wrap-up Checking the acceptance conditions, unhandled errors, output requirements Cannot stand in for tests or for downstream verification

Logs also need two separate views

The feedback the model sees may already have been redacted, summarized or replaced; the audit log may keep real execution information of a different scope. Do not treat replaced text as the original tool output, and do not persist secrets unconditionally for the sake of "traceability". Record at least the call ID, a digest of the final arguments, the execution status, the post-execution feedback, the scope of authorization and the version of the actual object.

A local experiment should assert the side-effect count and the state visible to the model separately. Asserting only that "the model received blocked" misses the error that matters most.

Worked example · Q009

The model outputs a function name, so who actually executed it

Input and conditions. The tool description is read_file(path). The model's response contains the function name read_file, the arguments {"path":"config.json"} and call_id=c1.

Steps and objectsInternal actionIntermediate result / new state
1 Receive the outputThe harness gets one structured call itemJSON by itself does not open a file.
2 ValidateChecks that the tool is registered, that the argument is a path string, and that the path is within the permitted rangeIf any one of them fails, nothing is executed.
3 DispatchThe harness looks the read_file implementation up in the registryIt really calls the operating system to read the file.
4 Return the observationBuilds the result that corresponds to call_id=c1This guarantees that the model can later attribute the result to the original request.

Join the steps up. The model is responsible for proposing the action, and the harness for carrying it out, for permissions and for feedback; between them there has to be a boundary that can be checked.

Limits and counterexamples. The fields and the roles of a tool call vary by API, and c1 is a teaching ID. Do not take the illustrative JSON for the complete request body of every product.

Follow-up: why does the tool schema itself also consume context?

The model has to understand the names, the fields and the descriptions, and they must enter the request in some representation the model can use. Many tools with long descriptions add to the input burden and make the choice harder. Discovery on demand can shrink the default tool set, but it introduces discovery failures; test recall of the tools actually required and the loading of unnecessary ones, instead of unconditionally stuffing every tool in.

Follow-up: is returning a single string as the tool result enough?

For simple cases it is, but the boundaries have to be clear. Writing both errors and successes as free text makes it easy for the model to misread them; structured fields can express status, path, version, truncated, next_range and so on, alongside readable content. More structure is not better in itself — the fields should serve the decisions that actually follow.

Follow-up: what is the relation between training research such as Toolformer and API Function Calling?

The former studies how a model learns abilities such as using tools while processing text; the latter is an engineering interface on which the model and the application exchange the intent to call. Supporting the interface does not mean a given model was trained with the method of a particular paper, nor does it guarantee that it chooses accurately among your set of tools. When the training sources are not public, a training recipe cannot be inferred backwards from the interface.

Q010｜Why can streaming output not be executed as soon as half a JSON arrives? How exactly is SSE parsed?

What to know first for this question A network fragment may cut in the middle of a Chinese character, or deliver only half a JSON field. Restore the bytes to text first, then assemble events according to the protocol, and only then execute.
Lesson 37 · Why text has to become token IDs firstLesson 07 · APIs and streaming protocols

Core answer

Start with the objects and symbols used here
SSE, chunk, delta: different layers of fragmentation
SSE is the text protocol for server-sent events; a network chunk is the stretch of bytes received this time; a delta is the incremental content of one output item. Their boundaries are not guaranteed to coincide. One complete event does not necessarily mean complete tool arguments either. The arguments may arrive first as {"path":"a and then as .py"}; they have to be assembled and the protocol's completion condition awaited — seeing a fragment is no reason to execute.

A network chunk, a UTF-8 character, an SSE event, a JSON object and the model's call item have different boundaries. Parse incrementally, layer by layer; accumulate the arguments of one and the same call; and execute only once an explicit completion status has arrived and validation has passed. The end of the connection does not necessarily mean that generation completed normally.[STREAM][SSE]

How one stretch of Chinese tool arguments gets split up

Suppose the arguments contain"path":"资料/说明.md". A Chinese character is made of several UTF-8 bytes, and the network may cut a chunk in the middle of a character. If every chunk is decoded on its own, it may raise an error or insert a replacement character. Use an incremental UTF-8 decoder that keeps the unfinished bytes.

Once the bytes have become text, the lines still have to be accumulated according to the SSE rules. Several data: lines make up the data of one and the same event, and only a blank line dispatches the event; a comment heartbeat is not business data. The JSON inside an event may describe "a new fragment for some call's arguments" rather than a complete call. Attach each delta to the right buffer by item identity, call index or the interface's own convention; fragments from several concurrent tools must not be mixed together.

Suppose the events arrive in this order:

item_created: c7 / read_file
arguments_delta(c7): {"path":"src/
arguments_delta(c7): filter.py","start_line":40,
arguments_delta(c7): "end_line":80}
arguments_done(c7)
response_completed

Only once the arguments are complete is there an object that can be validated. arguments_done, the completion of the output item and the completion of the whole response are different events; whether a complete tool item may be executed early depends on the product's protocol and on the execution policy. The most conservative teaching implementation waits for that call and for the necessary response status to complete, and produces no side effect from a JSON guessed into completeness.

Start with the objects and symbols used here
LF, CRLF and EventSource
LF is the line-feed character, and CRLF is a carriage return followed by a line feed. SSE lays down how event lines and blank lines are interpreted; EventSource is the browser's interface for receiving SSE. Teaching code that parses only one kind of separator is not a complete protocol implementation. Follow-up: what if the complete JSON has already appeared but the rest has not finished?

Being closed syntactically is not the same as being semantically final. The model or the protocol may go on to send other fields, a cancellation or a failure notice, or several calls may not all be there yet. The moment of execution has to follow the event contract, not a guess from counting brackets. For read-only prefetching an undoable optimization can be designed, but a write must not be executed speculatively.

Follow-up: after a disconnection, can splicing on a newly generated result restore it?

Not necessarily. Real event resumption needs protocol support such as a stable response identity and a cursor or sequence number; starting generation again may produce different arguments. The old half JSON and the new answer cannot simply be spliced together. Decide explicitly whether you are recovering the old response, resending an idempotent request or starting a new generation, and handle execution deduplication for each case separately.

Follow-up: how do you test that a stream parser works on more than well-behaved chunks?

Split the same byte stream at every possible position, especially inside UTF-8, an escape character, a line break and a JSON boundary; inject heartbeats, duplicate events, interleaved tool items, truncation and an error ending; check that the final object is the same and that an unfinished call is never executed. What the test aims at is the invariants of the protocol, not a few fixed sample strings.

Streaming tool calls: complete UTF-8, complete JSON and a complete call are three different things

Do not let network fragmentation decide the boundary of a business action

One Chinese character may fall across two byte chunks; one SSE event may span several network chunks; and one tool-argument object may arrive through several delta events. These are three different levels. The correct pipeline is incremental byte decoding, protocol event assembly, accumulating arguments per call item, recognizing the completion status the protocol defines, and then validating and executing.[TOOLS]

An error one ASCII test cannot cover

{"text":"爱"}has a different number of UTF-8 bytes than it has string characters. This book feeds it byte by byte to Python's incremental UTF-8 decoder and recovers the JSON correctly in the end; decoding each chunk independently may throw an error in the middle of a Chinese character or lose characters. Tests must include multi-byte content, CRLF boundaries, blank-line boundaries and escape characters, not only short English JSON.

The arguments of several calls cannot share one global buffer

Fixed interleaved events: A receives{"x":, B receives{"y":, A receives 1}, B receives 2}. Accumulating them separately by A and B gives two valid objects; splicing them into one string in arrival order is wrong. A real interface may carry item_id, output_index and call_id at the same time; they serve different purposes, and the display order must not be taken for business identity.[TOOLS]

Syntax can be complete early, but execution still needs the protocol and the policy to allow it

Some prefix can already be parsed by json.loads, and that does not mean no further field will be added or that the state will not change. Wait for the argument-completion event that the interface in question defines and handle the refused, incomplete, canceled and failed paths. A synchronous conservative implementation may execute only after it has confirmed that the whole response is acceptable; a protocol that supports asynchronous tools may allow a completed call to be executed while the model is still producing output, so not every interface can be required to wait for the end of the turn.[STRUCT]

The local test takes an explicitly conservative policy: even when the argument JSON is valid and carries a done marker, it does not execute if the response as a whole is incomplete. This test proves that local policy; it does not pass itself off as the event semantics of every API.

Follow-up: a reconnection delivers the events again, so how do you avoid executing twice?

Start by separating the identity of the transport event from the intent of the business operation. Deduplicating by item status cannot replace idempotence downstream: if the confirmation is lost after the first execution succeeded, the regenerated call_id may be different. You need a stable business-level identifier of intent to control the side effect, and an argument fingerprint kept to verify "same key, same intent".

Follow-up: can the streaming display and tool execution share one string?

Better not. The display layer may show partial text; the execution layer has to handle structure, status, authorization and logging. Letting the UI's incremental concatenator take on the executor's duties turns truncation, escaping and unknown fields into real side effects.

Engineering mechanisms and failure boundaries

Streaming back: when can the arguments really be executed?

The four boundaries cannot be merged

What the network returns is byte fragments. The UTF-8 bytes of one Chinese character may fall into two fragments; one SSE event may span several; and one tool-argument JSON may be split into several incremental events. Finally, the completion of one tool call item is not the completion of the whole model response either.

Let the call be numbered c7, with the tool arguments split into {"path":"a and .py"}. The first fragment is not bad JSON; it is simply not complete yet. Do not parse each fragment as JSON and treat the failure as an error by the model, and still less execute because one closing brace was found. A string can contain braces; and later events may still supply extra fields, a refusal or an incomplete ending.

One important ordering in the pinned source

Codex's handling of a completed output item first records the tool call in the session history, and then enters either the immediate-dispatch or the deferred-dispatch path. So even if it is canceled later, a call that already exists in the history still needs an associated result or an explanation that it was canceled; no dangling call may be left without a matching output.[C05:handle_output_item_done]

Two abnormal paths

The first: c7's arguments are complete, but the cancellation happens before admission. The file is unchanged, and it can be recorded as not executed. The second: c7 has already written the file, and the network then drops. Here it must not simply be marked as not executed and retried; the file, or the status of the downstream request, should be verified first. One error code is not enough to express two different facts.

In the exercise, split the events into different byte fragments and let c7 and c8 arrive interleaved; then verify that each set of arguments is correct, that any one call enters execution at most once, and that an early EOF produces no conclusion of success. A complete tool item and a complete response are not the same completion event

An assembled SSE event, assembled tool arguments and the end of the response stream are three layers of boundary. The Codex path that was read records the call once the completed tool item arrives, and then chooses immediate or deferred execution; it does not require every call to wait for the whole response stream to close. Q011｜When parallel tool results return out of order, how are they paired? Which errors can be left to the model to fix?

What to know first for this question Parallel calls may return in a different order, so they have to be paired by ID and not by position in the array; duplicate receipts and timeouts also bring in deduplication and the unknown state.
Lesson 07 · APIs and streaming protocolsLesson 02 · State, events and checkpointsLesson 26 · Retries, idempotence and transactions

Core answer

Calls and results should be paired by a stable call identity, not by the order of return or by the tool's name. A recoverable argument or business error should come with precise feedback; a permission refusal, an unknown side effect and a damaged protocol cannot simply be left to the model to retry without limit.

Looking at two calls of the same tool name

The model simultaneously calls read_file(a.py) and read_file(b.py), with the IDs c1 and c2. b.py returns first. On the rule "the first result corresponds to the first call", the model takes file B for file A, and a later patch may change the wrong thing. The correct way is to keep call_id→name,args,status,result, and to assemble the output according to the protocol; one and the same tool name cannot uniquely identify a call.

Status can distinguish created, validated, running, succeeded, failed and unknown. unknown means the client cannot confirm whether the side effect happened; it is not another name for failure. If creating a ticket remotely times out, for instance, you must not immediately create another one with a new ID. A query or an idempotent recovery is needed.

An error return should preserve the action that can be taken: FILE_NOT_FOUND means the path can be relocated, INVALID_RANGE means the range can be adjusted, PERMISSION_DENIED calls for changing the authorization or choosing a permitted path, VERSION_CONFLICT means the new version has to be read again. Wrapping every error as "try again" leaves the model searching the error space blindly.

Follow-up: are several tool calls naturally parallelizable?

No. Reading two independent files usually is; creating a branch and then switching to it, or writing a file and then testing it, have dependencies; and two writes may contend for the same resource. Whether a tool is read-only is only part of the information — the specific arguments and the shared state decide the conflict. A harness needs a concurrency policy; the model emitting several calls in one output is no proof of safety.

Follow-up: the tool returns success after a cancellation, so which one should you believe?

A cancellation request only asks for a stop; the tool may already have finished, or may not be interruptible. Go by the actual side effect and the protocol status, recording cancel_requested and the final result instead of merging the two into one boolean. A remote release or payment especially cannot be treated as rolled back just because the local wait stopped.

Follow-up: is a full stack trace returned to the model better the more detail it gives?

Not necessarily. A full stack trace may leak keys or internal paths, or drown the error that matters. Keep the error class, the relevant context, whether it can be retried, and a reference to the evidence; land the raw log safely and fetch it back by scope when needed. Trimming should keep the error and the closing summary, not only the first few hundred characters of the log.

Q012｜How do Structured Outputs constrain generation? Why does conforming to the Schema still not mean it can be executed?

What to know first for this question Structured output restricts the form; it does not prove the numbers are right. A refusal by the model, a truncated output and a failed business check should each have their own handling path.
Lesson 44 · Probability, exponentials and softmaxLesson 07 · APIs and streaming protocolsLesson 08 · Tools and MCP

Core answer

A structured-output mechanism restricts generation to the format and types of a supported schema, often by means such as constrained decoding. It reduces parse failures, but it does not prove that a field is factually true, that the business conditions hold, or that execution has been authorized. Refusals, truncation, incompleteness and the interface's range of support still have to be handled.[STRUCTURED]

Taking the four layers of validation apart

The first layer is syntax: can the JSON be parsed. The second is structure: are the required fields present, and do the types and enums match the schema. The third is business: is the amount reasonable, does the date satisfy the rules, is the file version consistent. The fourth is authorization: is the current identity allowed to perform this action on this particular resource.

For example{"action":"delete","path":"/data/important"}fully conforms to action enum[read,delete],path string, yet it may still exceed its permissions. Even if the schema allows only "a repository-relative path",../, symbolic links and a path that changes at execution time still require validation of the real path. In the model's output, approved:true cannot be used as the basis for approval.

The intuition behind constrained decoding is this: given the current output prefix and the grammar state, mask the disallowed next Token, then choose from the allowed set. Which schemas are really supported, how they are compiled and how errors behave are decided by the implementation; do not invent a claim that every vendor uses the same grammar engine internally. As for the relation between a number and reality, the grammar state alone cannot query a database to verify it.

Once the schema passes, two layers of checking remain: business validity and authorization

Follow-up: why are JSON Mode and a schema constraint not guarantees at the same level?

"Generate valid JSON" limits only the syntax; a schema can also limit the fields, types, enums and so on. A valid JSON array may not be the required object at all. Even with a schema, an application should handle compatible versions and unsupported constraints explicitly, rather than assume that every JSON Schema keyword is supported.

Follow-up: can the application-level validation be deleted to save code?

The permission and business validation should not be deleted. The model service is one source of input, and errors, version changes or a bypassed call can all happen. A deterministic boundary can usually stay simple — one type parse, a path-range check, a version condition and an authorization check — and there is no need to build a complicated framework for it.

Follow-up: why is a structured answer sometimes more prone to "filling in every field"?

If the schema makes every field required and there is no unknown, null or insufficient-evidence state, the model may be forced to fill in a value. A design should allow something missing to be stated honestly, and should say which fields may be empty and what kind of source is needed. Completeness of form and completeness of knowledge must not be run together.

Why can strict JSON still not drive a database write directly?

How far the schema's guarantee reaches

A schema constrains fields, types and part of the value structure; it does not guarantee that the file exists, that the amount is right, that the user is authorized, or that the record version is still valid. Strict output may also come with refusals and incomplete responses, which have to be handled explicitly.[STRUCT] Substituting "the structure conforms" for "the business can execute it" merges the interface layer with the authorization layer.

Missing, null and an empty string should be different states

Hypothesis note field is required to be present but allowed to be null.{"path":"a.py"}is missing the field, and is not the same structure as{"path":"a.py","note":null}; an empty string may in turn mean that the user explicitly cleared it. If an adapter fills every missing field with null automatically, it may disguise an omission by the model as a valid decision. In database PATCH semantics, "do not change the field" and "change it to an empty value" are especially dangerous.

The local experiment verified this distinction, and showed that the structurally valid secret.txt is still refused by the local permission set. What is tested is the structural rules and the business boundary; it is not claimed that the remote Structured Outputs API was used.

A business write goes through at least three different checks

The first is the schema and parsing; the second is business validity after normalization, for instance the path, the record ID, numeric units and the relations between arguments; the third is the current identity, the permissions, the target version and the risk of the operation. If the target changes between the checks passing and the actual write, a conditional write or transaction protection is needed as well.

Do not take the is_authorized:true supplied by the model as evidence of authorization. Authorization is decided by a trusted executor for a real user and a real resource; the MCP security guidance likewise stresses the trust boundaries of tokens, resources and proxies.[MCPSEC]

Follow-up: the enum constraint already limits it to read/write, so why is it still dangerous?

write is a class of operation; it does not say which tenant, which version, which fields or how much data is written. One and the same operation name covers a great many different risks. Tool design should make the most common safe operations explicit and the necessary permissions checkable, and avoid offering one unrestricted do-anything function and then constraining it by prompt.

Follow-up: should a failed validation automatically let the model fix the JSON?

A purely structural error can have the precise error returned and be retried within a limited budget; an authorization refusal cannot be talked around by rewording. Distinguish a retryable format error, data that needs refreshing, a permission that needs the user's confirmation, and something permanently unsupported. Unifying every error into "please try again" manufactures retry loops and the risk of exceeding permissions.
