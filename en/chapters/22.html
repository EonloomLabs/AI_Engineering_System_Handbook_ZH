Prerequisites for this chapter

Code that runs is not the same as a correct feature, and passing the tests also depends on whether the tests can detect the original defect. Find a counterexample first, then verify the change, then prove that the evidence really does correspond to the current version of the code.

Each question in this chapter lists the groundwork it needs. You can take the matching Foundations lesson first, or use the self-check to confirm how well you have it.

Lesson 02 · State, events and checkpointsLesson 18 · Code is not an ordinary documentLesson 26 · Retries, idempotence and transactionsLesson 04 · Foundations of engineering qualityLesson 05 · The denominator of an evaluation metric

A quick check before the deep reading: put a fake implementation that always returns success into the tests, and see whether everything still comes out green. If it does, strengthen the tests' discriminating power first, rather than adding more samples of the same kind.

A term with a dotted underline can be clicked for a quick reference. Read the definition of a letter in a formula first; do not let a guessed abbreviation stand in for the derivation.

This chapter takes "best practice" apart into the situations it suits and the behavior that can be verified. There is no fixed long chain of Analysis→Task→Review that is optimal for every task.

Q005｜How do you turn a vague requirement into completion conditions an agent can verify?

What to know first for this question Acceptance turns a vague requirement into behavior that can be checked: write the normal case, the boundary case and the counterexample first, then judge whether the change is necessary.
Lesson 18 · Code is not an ordinary documentLesson 04 · Foundations of engineering quality

Core answer

Start by stating the expected behavior, the boundary conditions, the constraints that may not change, and the observable way of verifying it. Tests are not an afterthought written at the end; they are one way of turning a requirement into facts that can be checked. But not every aspect of design quality can be covered by tests.

Taking "add an exclude feature" apart into semantics you can check

The base directory the rules are relative to, the semantics of wildcards, the behavior of an empty rule, the relationship between directories and files, case and separators, the handling of invalid input, and the precedence of the existing include rules all have to be stated. Not every one of them needs a new mechanism; work out what is actually needed from the existing design and the user's goal first.

For instance, define it as: with no exclude configured the behavior does not change; a matching path does not enter the output; a non-matching path keeps its original order; the same input and configuration give a determinate output. From that you can build ordinary cases, boundary cases and property tests. If the user did not ask for a new matching syntax, a complex DSL should not be introduced on your own initiative.

Before implementing, run a case against the current code that ought to fail, to prove the gap in the requirement; after implementing, the same case should pass, and the adjacent regressions are then filled in. For a production failure that cannot be reproduced locally, state the substitute evidence and its limits, and do not treat "no error was reported" as completion.

A completion condition should include "what must not change", not just one successful example

Conditions for this example: an independent requirement: the directory exclude supports vendor/. The semantics adopted are explicitly a prefix at the repository root, not extended to matching directories at every level.

How to read the changes in the figure

The third row has to be defined first, or several different implementations could all claim to be reasonable. Acceptance turns the vague word "directory" into a precise scope.

A test should not only exercise the new path but also show that the matching scope was not widened and the interface not broken.

On that basis an agent can report which items passed and which lack evidence, instead of only saying "the feature is implemented".

Do not conflate: more acceptance conditions are not always better; keep the conditions that tell a genuinely wrong implementation apart, and avoid treating internal implementation details as an external contract.

Follow-up: do acceptance criteria make a small task more complicated?

They can be just one or two sentences that state the behavior, with no dedicated document or sign-off. The complexity comes from the risk in the requirement, not from the name. Renaming one field may need only a build and the matching test; a change to the payment state machine needs more boundaries.

Follow-up: if the model writes its own tests, does it end up proving itself right?

That risk exists. The implementation and the tests can share the same misunderstanding. Tests can be generated from the user's requirement, an old bug, an independent reference implementation or an invariant, with a hidden or independent verification held back. Passing the tests shows that those assertions are satisfied; it does not prove that the assertions cover the whole intent.

Follow-up: how do you stop an agent from quietly widening the scope?

Compare the final diff with the authorized goal, and check for new dependencies, public interfaces, data migrations and unrelated formatting. The scope constraint can be stated at the start of the task, and at the end a mechanical check can be combined with a human or model review. The point is not to forbid every reasonable refactor, but to require that it be necessary and evidenced.

Engineering mechanisms and failure boundaries

How does a long task avoid starting over each time, or finishing falsely?

A long task has two kinds of progress at once

"The approach has been discussed" is cognitive progress; "the file was written, the feature was verified, the artifact was published" is progress in the environment. When a session resumes, both have to be checked, rather than trusting the previous turn's summary alone. A trustworthy checkpoint contains the goal, the constraints, the current version, the parts that are finished and evidenced, the parts that are not, the most recent failure, and the next step.

A feature list is not a decorative row of ticks

The teaching feature "exclude the vendor directory" needs at least one success case and one counterexample: it should exclude vendor/a.py, but it should not wrongly exclude src/vendor_util.py. Testing only that "the function raises no error" does not cover the requirement. A feature's status goes from not implemented → implemented → verified, and each step should have a matching artifact and test; jumping to verified because the model wrote a sentence of explanation is not allowed.

Anthropic's practice for long-task harnesses describes the problems of initializing the environment, recording progress, working incrementally and verifying; the application-development case goes further in stressing feedback and acceptance. What this book takes from them is the constraints; it does not treat a case study's fixed role configuration as an architecture every project must have.[A06][A13]

How a review avoids wasteful loops

Separate blocking problems from minor corrections. An error that affects the requirement, data safety, an architecture boundary or compatibility is worth redesigning for; a local naming issue or a simple patch that is already clear can be fixed directly and the relevant tests then run. Do not restart the whole analysis → design → review process every time a small problem turns up.

When stopping the retries is allowed

Two consecutive turns with no new evidence and the same action can trigger a judgment of stalling; that count is only a teaching policy, and a real policy should be adjusted to the task. Evidence lost beyond recovery should be marked unrecoverable, and the work should continue from the facts that are available or report the gap, rather than entering an endless "restore the history" loop.

The smallest recoverable delivery

Record the final work tree, the diff, the test results, the items not run and the way to roll back. Do not promote every bit of progress to long-term memory; temporary task state stays in the checkpoint, and only stable experience that has been verified across tasks is considered for a skill or an experience store.

A long-task framework also needs experiments that remove a mechanism

The resets, stage splits or paired roles an older model needed do not automatically suit a newer one. The long-task articles read here include an instance of orchestration being simplified after the model changed. The right approach is not to copy a role diagram over, but to remove one mechanism on the same task set and compare completion quality, regressions, time taken and recovery from failure.[A13]

This book recommends writing acceptance as externally checkable conditions, rather than "the model thinks it is good". An independent evaluator also has to be calibrated against standard samples; for goals about style, concrete typography and interaction requirements can be listed; for code, bind the final version, the set of tests and the range that was not verified. For a small task, make the change and verify it; for a complex one, add planning and an independent check as well.[A06][D07]

Q006｜Why can all-green tests still be a false completion? How do you spot weak tests and stale verification?

What to know first for this question A test has to tell a correct implementation from a wrong one. Compilation, static checks, unit tests, integration tests and property tests supply different evidence, so counting the number of tests is not enough.
Lesson 04 · Foundations of engineering qualityLesson 05 · The denominator of an evaluation metric

Core answer

A test may not have run the target, may have been skipped, may assert too weakly, may have verified an old version, or may have had the wrong environment. The test command, the number actually executed, the exit status, the version and the meaning of the assertions have to be joined up, instead of looking at one green icon.

Six counterexamples that look like success

The command pointed at the wrong directory, so 0 tests ran; the filter expression ran only unrelated cases; a failing test was marked skip; the assertion checked only that the result was non-empty and not that the path was excluded; the tests ran before the patch and were not rerun after it; the mock always returned success, so the real branch was never taken.

Stronger verification shows which tests ran, which were skipped and why, whether the target failure can be reproduced on the old version, whether the new version passes, and whether the final version and the log agree. For important logic you can use mutation test: deliberately invert a key condition or remove the idempotence check, and the test should fail. If everything is still green, the assertions are not protecting that behavior.

A property test can cover a large range of input relationships, for example "adding an exclude rule should not make a path that was already excluded reappear" — but only if the requirement really does satisfy that monotonicity. A wrong property restricts legitimate behavior, so it has to be proved first, or its conditions of use stated.

A green test has to be bound to "it really ran" and "the current version"

How to read the changes in the figure

First check whether anything actually ran, then check which version was tested, and last check whether the cases can hit the target defect. All three gates are needed.

Mutation testing can deliberately put a wrong implementation back in; if everything is still green, the tests have no discriminating power.

Formatting, generating code or changing configuration after verification also changes the object, so the affected checks have to be run again or shown not to be affected.

Do not conflate: "the tests found no problem" cannot be rewritten as "there is no problem at all", least of all when both coverage and environment are limited.

Follow-up: is 100% coverage enough?

Line coverage says only that a line was executed, not that an assertion checked the right result; branch coverage is finer, but still cannot cover every combination of state, concurrency and business meaning. Coverage helps find gaps; it is not a certificate of quality.

Follow-up: how do you choose between mocks and real integration tests?

Mocks make tests fast and determinate and suit isolating local behavior; a real integration verifies the protocol, the configuration and the boundaries. Mock everything and you may miss the actual API format and the transactional behavior; go end to end for everything and the feedback is slow and easily unstable. Layer it by risk; there is no need to build a full environment for every function.

Follow-up: if only a comment changes after the tests, does everything have to be rerun?

Usually a full rerun is not needed, but you have to confirm that only non-executing content really changed. Tests, configuration, code-generation input or embedded instructions sometimes look like text yet affect behavior. The scope of verification should match the actual impact, avoiding both empty formality and a missed piece of executable meaning.

Engineering deep dive · E43 · continues Q086

The test command exits 0 — so why may not a single effective test have run?

Prerequisite: Lesson 18 · Lesson 04. Reading order: confirm the run contract first, then look at the counterexamples and the fix, and finally test the limits.

An exit code answers far less than "the task is correct"

The official pytest documentation distinguishes the exit codes: collecting no tests is usually 5.[PYTEST] But another counterexample this book actually ran is this: with a test entirely skipped, pytest exits 0. So "returncode==0" is not enough to prove that an effective test was executed, still less that the relevant boundary is covered.

This subprocess experiment created an empty test directory and a directory holding only a skipped test, and observed 5 and 0 respectively. The result log is saved with this book; it describes this installation's environment, and does not generalize every test framework to behave as pytest does.

A green light should be bound to four objects

The set of tests selected, the environment they ran in, the version of the code under test, and an explicit acceptance predicate. The same command string can execute a different set depending on the working directory, marker filtering, environment variables or a change of dependency. Pasting one "all passed" log without recording collected/passed/skipped/failed is delivery evidence that cannot be fully verified.

You also have to prevent the case where the tests ran before the change, the model then reformatted or patched again, and the old green light is still cited at the end. An unchanged Git HEAD does not mean the contents of the work tree are unchanged; the tests should be bound to the final contents or to an explicit snapshot of the tree.[GIT]

Be especially careful when the tests themselves have been modified

An agent that changes an assertion to make the test pass may have done nothing but move the criterion. Tell a legitimate update of the expected behavior apart from a weakening of acceptance. A critical requirement should have an independent oracle (the source that decides correctness) — an existing contract, a human label or an external interface specification — and not something the same generating process can rewrite at will.

Follow-up: is it only professional if every test is run?

Not necessarily. You can start with the smallest failing case and the affected regressions, then widen by risk. What matters is explaining what is covered and what is left out, not pretending that a limited set of tests amounts to proof about the whole system. A high-risk change across modules needs wider verification; a simple wording or configuration change need not mechanically trigger the expensive full chain.

Follow-up: the model says it ran, but the log is gone — what then?

The status should be "cannot be verified", not a pass by default. If it is safe and the cost is acceptable, rerun the current version; if it cannot be rerun, state the limit explicitly and keep it. Do not make up a test output to round the report off: a delivery fact has to come from an actual execution.

Q007｜When is a review worth it? How do you avoid an endless analysis—review—redesign loop?

What to know first for this question A review should examine the real risks and the current diff; a small problem can be fixed directly and verification added. Repeating a fixed round of analysis is not the same as improving quality.
Lesson 02 · State, events and checkpointsLesson 18 · Code is not an ordinary documentLesson 04 · Foundations of engineering quality

Core answer

A review should find the important problems the implementer or the automated tests may have missed, and choose its depth by risk and evidence. A small local problem can be fixed and verified directly; only overturning a key design or widening the scope of impact calls for fresh analysis. The goal is better code health, not perfection in every detail.[REVIEW]

Choose the kind of review by the consequences of an error

For a local change to a piece of wording or a private function, compilation and a targeted test may already be enough. A cross-module interface, concurrency, a data migration, permissions and an irreversible deployment are worth checking for invariants, compatibility and recovery. An independent reviewer is best given an explicit task — look for regressions in old callers, or for a race — rather than finding fault in general.

If the review finds an unclear variable name or one missing boundary test, correcting it within the current task is enough. If it finds a mistaken architectural assumption, or a data model that cannot express the requirement, then go back to the design. Turning every low-risk comment into a new Analysis task creates communication cost and repeated context.

Blocking problems should be separated from suggestions, but there is no need for an elaborate system of levels. Stating clearly what the problem will cause, what the evidence is and what the smallest fix would be is more useful than assigning an abstract risk score.

Whether a review is worth it depends on new evidence, not on always doing one more round

Conditions for this example: two independent changes: A fixes a typo in a document; B changes concurrent stock deduction. The verification each one needs is compared, rather than forcing every task through the same heavy process.

Follow-up: may a reviewer modify the code?

Yes, as long as the task's authorization and the tools allow it and the change and its verification are recorded. The roles are separated to get an independent view, not to forbid fixing things. Correcting a clear small problem during the review is often more efficient; a major change still has to be coordinated with the main task, so that the direction is not quietly altered.

Follow-up: do more rounds of review necessarily make things more reliable?

The marginal gain usually depends on new evidence and a new point of view. Repeating the same check may produce nothing but arguments about style, and may introduce new errors. Watch the defects actually caught in the past and the cost of rework, and set an explicit stopping condition.

Follow-up: how do you review for "over-engineering"?

Ask of every new abstraction, rule, state or service: which concrete error does it prevent; what would happen without it; is there a simpler implementation; is its cost proportionate to the risk. A pattern being common is no reason to assume it must be used, and the pursuit of simplicity is no reason to delete a safety boundary that is genuinely needed.

Q008｜Why should testing a skill or a prompt not rely heavily on hash snapshots? What should be tested instead?

What to know first for this question A snapshot or a fingerprint detects a change of content or form, not business meaning on its own. The evidence has to correspond to the current artifact and environment.
Lesson 18 · Code is not an ordinary documentLesson 04 · Foundations of engineering qualityLesson 05 · The denominator of an evaluation metric

Core answer

A text hash proves the content bytes have not changed; it does not prove the behavior is right. For a skill description or a prompt that will reasonably evolve, too many hash tests turn ordinary editing into the chore of updating fingerprints. Test discovery, routing, the necessary constraints and real task behavior first; an exact hash suits an artifact identity that really is required to be immutable.

Telling four kinds of test target apart

Start with the objects and symbols used here
Schema and Structured Outputs
A schema is a set of structural rules about fields, types and the like; a structured-output mechanism makes it easier for the model to return data that follows those rules. Valid fields still do not mean that the target file exists, that access has been granted, or that the request is right for the business. Independent example: path is required to be a string; {"path":3} does not match the type rule, and {"path":"missing.py"} follows the structure yet may still find no file.

A syntax test checks that the SKILL metadata can be parsed, that the required fields are there and that the referenced files exist. A structure test checks the relationships between resources and that the tool schema is valid. A behavior test gives a task and observes whether the necessary skill is selected and whether the relevant verification runs. An integration test compares code results, regressions and cost on real repository tasks.

Start with the objects and symbols used here
SQL, SQLite and the transaction object
SQL is the language for working with relational data; SQLite is a database engine that embeds into an application. Writing operational state into a database is a persistence action by the harness; it does not modify the model's neural network parameters. One transaction can save the business row in this database together with a pending-send record, but that does not let you infer that the mail service committed atomically along with it.

A description that changes "database query" to "SQL and database queries" changes the hash, yet the feature may be better; a behavior test should allow that kind of improvement. Conversely, after one critical prohibition is deleted the document is still correctly formatted, and only the matching negative case exposes the risk.

A few snapshots can be kept to review the overall change, but treat a snapshot as an aid to review rather than the only quality gate. For an execution script, a fixed evidence bundle or a cache key, a content hash still has a clear use; do not read an objection to brittle tests as a ban on every hash.

Test the prompt's behavioral contract; do not treat every byte as a business requirement

Conditions for this example: an independent skill update: "check the directory rules first" becomes "check the path-matching boundary first". The method has not changed, but the text hash has. Another update deleted "the public signature must not be modified", and the hash changed too.

Follow-up: LLM routing is non-deterministic, so how can a behavior test be stable?

Separate the deterministic configuration check from the statistical evaluation of routing. Fix the model, the prompt, the task and the budget, run it many times or over enough tasks, and report the distribution and the boundary failures. Do not require identical wording every time; attend to the choices and results that must hold.

Follow-up: does correct routing show that code quality has improved?

No. A loaded skill may go unused, or the skill itself may be poor and lead to too much process. Downstream task metrics are needed. Routing is an intermediate metric; in the end it still comes down to correctness, engineering soundness and cost.

Follow-up: how do you build the smallest effective regression set?

Collect a few high-value cases from real failures, covering the original problem, the boundary counterexample and a scenario that is unaffected. With each change, add the test that prevents a regression of the same kind, rather than a new structural assertion for every sentence. Update it as the distribution of failures shifts, instead of piling up ineffective cases without end.

Engineering deep dive · E44 · continues Q088

A snapshot that looks unchanged does not mean the property is intact: how can a test be made to kill a wrong implementation?

Prerequisite: Lesson 04 · Lesson 05. Reading order: confirm the runtime contract first, then look at the counterexamples and the fix, and finally test the limits.

First separate an example's result from a business invariant

A snapshot test compares one representation of the output; a property test checks a constraint that a class of inputs should always satisfy. Both are usable, but both depend on the oracle being right. For the exclude rules, for instance, the property might be that no descendant of a forbidden directory may appear in the result; saving one screenshot of a list that "looks right" does not cover the path boundaries.

This book's smallest mutation example: the correct rule x>0 is changed to x>=0. If the test uses only 1 and 2, both implementations pass; once −1, 0 and 1 are added, the boundary at 0 kills the wrong implementation. Mutation testing exists to check whether the tests can find a plausible error constructed in advance, not simply to run more often.

Generating the code and then the answer from the same source yourself produces correlated blind spots

If the implementation and the expected test result both come from the same mistaken assumption, they can prove each other perfectly. An independent oracle may be an existing compatibility constraint, a trusted parser, a reference implementation, a human business rule or a mathematical property that has been checked. Work on agent evaluation also stresses the difference between the scorer and the result in the real environment.[EVAL]

Choose counterexamples causally connected to the change at hand

For a change to a mask, test an inverted visibility and a fully forbidden row; for a change to the cache, test a position offset and an invalidated prefix; for a change to recovery, test the case where the side effect happened but the confirmation was lost; for a change to retrieval, test too few candidates left after the ACL. Do not pile up a mass of unrelated unit tests and treat the count as depth.

Follow-up: does killing more mutants guarantee there are no bugs?

No. The set of mutants is only the class of errors you thought of, and it may miss a business risk. Report the error model that is covered and the environments still untested; a sample from a critical real failure is worth more than randomly manufactured, meaningless syntax errors.

Follow-up: does a small problem found in review have to go through the whole design process again?

Usually not. If the goal and the architecture do not change, the fix can be carried straight into the implementation and verified in a targeted way. Only when a major mistaken assumption or a high-risk design flaw comes to light should you go back up a level. Engineering discipline should reduce defects, not manufacture a useless analysis—review—analysis-again loop.

A reusable acceptance record

Record the original failing input, the result the wrong implementation produced, the independent basis for the correct behavior, the final version and the commands used to check it, and at least one counterexample that would let a weak test pass by mistake. That is more auditable than a line saying "checked thoroughly, no problems", and it also makes better material to settle into experience.
