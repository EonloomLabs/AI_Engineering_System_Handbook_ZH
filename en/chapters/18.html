Prerequisites for this chapter

What memory has to keep is information that carries a source, conditions and a time, not "something the model once said". Working state, project facts and rules learned from experience are each updated differently.

Q045｜What is the difference between working memory, episodic memory, semantic memory and procedural memory?

What to know first for this question Working state, events experienced, stable facts and execution experience need different storage strategies; they cannot all be stuffed into one ever-growing summary.
Lesson 02 · State, events and checkpointsLesson 22 · Compaction is not magicLesson 23 · Foundations of long-term memory

Core answer

Working memory supports the current task; episodic memory records specific experiences; semantic memory keeps relatively stable facts; procedural memory keeps reusable ways of doing things. The classification helps decide when to write, how to query and when to expire; it does not force you to build four kinds of database.

One and the same bug produces four different kinds of information

Current working memory: "filter.py has been located; next, add tests". Episodic memory: "in a task in 2026, absolute paths did not match the relative rule, which made exclude fail; the patch and the test are in PR X". Semantic memory: "in this project, exclusion rules are interpreted relative to the repository root". Procedural memory: "when checking a file-filtering problem, first check the path baseline, the separator and the semantics of the rule".

These four are not interchangeable. Working memory loses value once the task ends; episodic memory keeps the concrete evidence; a semantic fact can expire as the project changes; procedural experience transfers, but it must carry its conditions and must not turn into "every filtering bug is a path problem".

Parametric memory is model capability formed by training, and is not the same as an application's external memory. External storage can be updated and audited, but it needs reliable retrieval. Putting the whole history into the context is the simplest extension of working memory, yet it runs into limits of length, cost and interference between pieces of information.

Keep the four kinds of memory in different places and a temporary hypothesis will not be taken for a permanent rule

Conditions for this example: an independent repository task: a bug is being located, a similar error was fixed once before, the project forbids changing the API, and a set of reproduction steps exists.

How to read the changes in the figure

"I remember this fixed it last time" is one episode; it does not follow that every similar error message has the same root cause.

Working state goes stale once the task is done, while project rules may apply for a long time; their retention periods and retrieval methods therefore differ.

A memory system does not require building a complex graph database first; define the type, the source, the scope of use and the way to withdraw an entry first.

Do not conflate: writing a guess from the model's own reflection into the permanent semantic store makes later tasks fetch the same error again and again.

Follow-up: are memory and RAG the same thing?

RAG is a class of mechanism that retrieves external knowledge and then uses it to help generate, whereas a memory system also covers writing from interactions, updating, conflict handling and forgetting. Memory retrieval can use RAG, but being able to read documents does not by itself build up experience.

Follow-up: why is "experience" summarized by the model so prone to overfitting?

One success may be due to a particular environment, an accidental path or insufficient testing. If the summary drops the conditions, it promotes a local practice into a general rule. A piece of experience needs at least the setting, the action, the outcome, the evidence and the known limits on record; only after it has been reused several times does its effect decide whether it should be raised to a default procedure.

Follow-up: is more long-term memory always better?

No. Duplicate, conflicting and expired memories add retrieval noise and context load. The core metrics are fewer repeated mistakes, better task quality and a lower cost of rebuilding context, not the number of memory entries.

Q046｜Which judgments should a piece of information pass through on its way from a conversation into long-term memory?

What to know first for this question Before writing to memory, verify the source, the scope and any duplication or conflict. A success the model reports of itself is not a verified fact.
Lesson 17 · From search results to a trustworthy answerLesson 23 · Foundations of long-term memoryLesson 05 · The denominator of an evaluation metric

Core answer

First identify the candidate fact or experience, verify the source and the range it applies to, check for duplication and conflict, then choose to add it, update it, hold it as pending confirmation, or not store it. Everything the model produces in an answer cannot be stored automatically as fact.

The write chain for one candidate

The user states explicitly that "project logs are kept for 7 days", which is a project constraint coming from the user; the tool configuration shows that production keeps them for 30 days, which is a fact about the implementation. When the two conflict, you cannot simply let the newer text overwrite the older: you have to judge whether the user is setting a new target or describing the current situation. Memory can keep "the target requirement is 7 days" and "the current production configuration is 30 days" separately, marked as needing adjustment.

Start with the objects and symbols used here
OAuth, scope and authorization
In an authorization setting, OAuth lets an application obtain access credentials according to what was granted; a scope declares one class of access range, and the resource service should still check the specific permission. In a memory or task setting, scope can instead mean only the range over which something applies, and must not be conflated with a login credential. Being granted "read the calendar" is not being granted the deletion of every event; a successful connection is no proof that an operation was approved.
TTL, valid time and record time
A TTL is an expiry setting on storage or a cache; valid time is when a fact applies; record time is when the system came to know it. An expiry policy cannot stand in for verifying the fact and its source. A rule that takes effect on October 1 is only read on October 10: the business valid time counts from the 1st, while the time the system knew about it counts from the 10th.

A lightweight structure can be used when writing: subject, predicate, value, scope, valid_time, source, status. For a piece of experience, add conditions and outcome as well. The fields should answer real needs; there is no need to apply a complex knowledge graph mechanically.

To check for duplicates, first find the candidates on the same subject or in the same range, then compare the meaning. The same conclusion from two independent pieces of evidence can have its evidence references merged; similar wording in a different environment should not be merged; a negation relationship should be treated as a conflict. The model can help with extraction and comparison, but an important authoritative fact is best given a definite identity and confirmed by a person or a tool.

How to read the changes in the figure

An extractor will produce fields that look tidy, but tidy fields are no proof that the fact holds. The scope must not be wider than the original wording.

Temporary information needs a re-check trigger or an expiry policy; keeping it for good can turn a short-lived experiment into a long-term constraint.

Before writing, check for duplication, for conflict and for privacy restrictions; after writing, it must still be possible to withdraw it on the evidence.

Do not conflate: "the model summarized it" is not an independent source. If the summary drops "in this project" and "for now", later retrieval will widen the error.

Follow-up: when is it all right not to store something?

Temporary state, data that is easy to look up again and changes fast, guesses with no evidence, small talk of no future use, and sensitive information whose storage risk outweighs its benefit may all not be worth long-term memory. Leaving out a worthless write is more effective than cleaning up afterwards.

Follow-up: does automatic memory mean the model changes the rules by itself?

Storing a candidate experience and activating an execution rule should be kept apart. Evidence may be allowed to accumulate automatically, but verified rules, hypotheses awaiting confirmation and explicit user instructions should have different statuses. Otherwise one bad summary can affect every later task at once.

Follow-up: what can go wrong when memory is written asynchronously?

A write delay means a fact that has just been corrected is not in force yet and the old memory is still retrieved; concurrent writes can overwrite new content. Visibility, versions and a conflict policy have to be defined. Not every application needs strong consistency, but you have to know when what you read is a stale state.

Engineering mechanisms and failure boundaries

Why is writing memory a pipeline with leases and acceptance?

A conclusion from a chat cannot be promoted straight into a long-term fact

"pytest passed this time", for instance, holds only for one file version and one set of tests, and should not be stored as "there is nothing wrong with this module". A usable memory should include the content, the source, the scope, the time it happened or took effect, the time it became known, its trust status and the conditions under which it expires. A checkpoint for the current task answers "how far did we get"; long-term memory answers "when, later on, may this be consulted".

The two stages in the pinned Codex source

The startup logic is constrained by whether the session is temporary, by feature switches, by the identity of the main thread, and by database and directory conditions.[C13] The first stage screens the eligible history sources and extracts from them concurrently; the result may be a valid output, or it may be a success with nothing worth keeping. The latter should not be treated as an error and retried without end.[C14]

The second stage has a global task lease: it prepares the workspace, synchronizes the candidates, computes the differences, and then decides whether a consolidation worker is needed. When there is no new difference and the existing artifact is valid, one model call can be skipped. Once the worker has finished, you still have to shut it down, verify the artifact, check that the lease is still held and advance the watermark before publication counts as a success.[C15]

Why a lease is not a boolean lock

A lease carries an owner and an expiry time. Once an old worker is stuck, a new worker may take out a new lease; when the old worker comes back, it must not go on to publish its old result. The final write has to carry the ownership condition. A heartbeat only extends the validity period; it does not prove the work itself is correct. The watermark states the range of sources already taken in; it does not mean the model "remembers all of it".

Isolation, too, has to be read branch by branch

The pinned consolidation worker switches off some tools, memory and collaboration abilities in order to reduce recursive feedback; but the sandbox branch is still affected by the type of the parent environment. Seeing one restricted branch is no reason to write "every memory worker always forces the same sandbox".[C15]

Verify again at the point of use

The memory says the test command is pytest tests/old, but the directory was deleted after a change of repository version; the entry should be expired or confirmed again, rather than explained away so that the old memory still holds. When a user withdraws a fact, deleting the original record is not enough: the summaries, vectors and experience rules generated from it also have to be traced through their source dependencies and expired.

The local experiment builds two competing workers out of lease generations and source versions, and confirms that the old owner cannot commit. It does not run a production memory service or model extraction; what it verifies is the boundary of the control state.

The actual run of stage one builds the request context first and takes the candidates afterwards, even though the summary comment puts the order differently. Stage two is not "the model has written the file, so it has succeeded": first the worker is ended, then the artifact and the lease are checked, and last the Git baseline and the database record are updated. If the shutdown fails, the code as read keeps the lease and waits for it to expire, so that the old process and the new worker do not modify things in parallel.[C14][C15]

Updating the Git baseline and marking success in the database are two operations, and should not be drawn in a textbook as one transaction guaranteed to be atomic. A teaching counterexample: the baseline succeeds and the database registration fails, and recovery should check both rather than unconditionally run consolidation again or unconditionally declare the publication done. The watermark only states the range of sources taken in; it does not prove that a remembered fact is true.

The isolation configuration has branches too: a managed sandbox can be restricted to the local memory root with no network; where the parent configuration says Disabled or External explicitly, the relevant branch keeps that choice. Picking out the strictest passage is no reason to claim that "all background memory is always without a network".[C15:agent::get_config]

Q047｜How are conflicts between old and new memory handled? Why do Valid time and Recorded time have to be kept apart?

What to know first for this question Valid time says when a fact applies; recorded time says when the system knew it. Different retrospective questions can give different query results.
Lesson 02 · State, events and checkpointsLesson 23 · Foundations of long-term memory

Core answer

Valid time is the time over which a fact applies in reality, and Recorded time is when the system knew or recorded it. Only by keeping the two apart can you answer both "what was the fact at the time" and "what did the system know at the time". A newer record does not necessarily stand for a more up-to-date fact about reality.

Seeing both times through a late message

On 10 October the system records "a timeout of 30 seconds". On 17 October a notice arrives: "it was changed to 60 seconds with effect from 12 October". The new fact's valid time is the 12th and its recorded time is the 17th. A query for the actual configuration on 14 October should answer 60 seconds; a review of "why did the system suggest 30 seconds on 14 October" has to take in that it had not yet received the new message.

If the original record is simply overwritten using updated_at, the old state of knowledge disappears and historical decisions can no longer be explained. A light implementation can keep version records and a supersedes relation, without necessarily needing a full temporal database. For high-risk tasks you should also tell the target policy, the actual deployment and the observed value apart, because they may hold different values at the same time.

One order for handling conflicts is: the same object? the same environment or version? the same valid time? is the source entitled to change this fact? is the new record a correction, an exception or additional evidence? Only after answering these do you decide to overwrite, to keep both, or to mark the matter unresolved.

Valid time and record time are two separate questions

Conditions for this example: independent teaching dates: on 3 October it becomes known that a rule takes effect from 1 October; on 8 October it becomes known that it was in fact revoked from 5 October. These are not real user records.

Follow-up: does a user's latest instruction always override older experience?

Within a task constraint that this user is entitled to decide and whose scope is clear, a new instruction should usually change an old preference; but a low-trust web page must not be allowed to pass itself off as a user instruction, and a new requirement for project A must not override project B. Authority and scope come before mere chronological order.

Follow-up: once a wrong memory is deleted, what about the summaries derived from it?

The summaries, rules and caches that depend on it have to be expired or regenerated. Deleting only the original entry while keeping "the experience summarized from the old entry" lets the error go on spreading. Recording source dependencies is not just for tidy citation; it is also what makes a revocation propagate.

Follow-up: when a conflict arises, can it all be left to the LLM's free judgment?

For low-risk text the model may offer candidate explanations; critical identity, time, version and authorization are best constrained by structured information. An LLM is good at comparing meaning, but it should not override a highly authoritative fact on the strength of linguistic confidence. When no decision can be reached, keeping the conflict is more reliable than manufacturing a false unified conclusion.

Engineering deep dive · E35 · continues Q071

"When it was true" and "when it became known": the two times in memory have to be kept apart

Prerequisite: Lesson 02 · Lesson 23. Reading order: confirm the run contract first, then the counterexamples and the fix, and test the limits last.

updated_at alone loses two different questions

A fact's valid time answers "from which day was it true in reality"; the recorded time answers "from which day did the system know this". The two are different. LongMemEval lists temporal reasoning, knowledge updating and abstention as separate abilities, a reminder that recall cannot go by content similarity alone.[MEMEVAL] The bi-temporal structure in this section is an engineering design given by this book; it is not a claim that the paper specifies this database schema.

One fixed example answering two kinds of query

On day 1 the quota is known to be 10; only on day 8 does a notice arrive: from day 5 the quota had in fact been changed to 20. Asked "what was the quota as known on day 6", the answer should be 10; asked "looking back now, what value actually applied on day 6", it should be 20. If the update simply overwrites 10 with 20, the system can never answer the first question correctly again.

The local test filters events by valid_at and known_at respectively, giving 10 and 20. The "day numbers" here are only a teaching order, not real user data.

The data structure has to express a correction, not just a new value

Keep the source, the object it applies to, the valid interval, the recorded interval, the evidence version, the status and the supersedes relation. Intervals should as far as possible use the explicit half-open convention [start,end), so that a boundary moment does not belong to the old and the new entry at once. A correction, an ordinary change and a revocation should be distinct: a correction may state that the past record was simply wrong, whereas an ordinary change does not deny that the old value once held.

A database being able to write atomically does not mean it understands any of this meaning; a transaction only protects field updates that were designed correctly.[SQLITE] Conflict handling has to go by the authority of the source, the time and the range of application; it does not settle every knowledge conflict by "last write wins".

Follow-up: always overwriting old information with new is simpler, so why is it not enough?

Because "I live in Tokyo now" does not conflict with "I lived in Beijing last year"; and "the budget changes to 20 from next month" should not affect this month straight away. Crude overwriting flattens the time conditions, and tends to make answers look as if they remember a great deal while using the wrong period every time.

Follow-up: what do you do when sources contradict each other and there is no ranking of authority?

Keep the conflict status and the evidence on each side, check with the user where necessary, and do not manufacture a fact out of the model's confidence score. Without sufficient grounds, the answer should be "not yet determined", which is not the same problem as a failure to retrieve the memory. An evaluation should include cases where abstaining is the correct answer.

Q048｜How does memory retrieval avoid picking up the wrong project or an expired rule? And when should something be forgotten?

What to know first for this question Once a memory has been fetched, its validity still has to be confirmed; updating, expiring and deleting are ordinary functions, not optional trimmings added after retrieval is done.
Lesson 16 · Retrieval, to begin withLesson 17 · From search results to a trustworthy answerLesson 23 · Foundations of long-term memoryLesson 05 · The denominator of an evaluation metric

Core answer

Filter first by identity, project, task type, time and valid status, then run the relevance retrieval and any reranking needed, and check the key sources before use. Forgetting serves to reduce expired and low-value information; it should not damage what auditing requires or evidence that is still cited.

The full chain from query to use

The task is "fix the duplicated refund execution in project A". Restrict to the user and project A first, exclude expired rules, and retrieve experience to do with idempotence and refunds. The candidates may include a payment incident in project B; close as that may be in meaning, it cannot be treated directly as a rule for A. It can serve as a general point to watch, but its limits of application have to be kept.

Once a memory has been chosen, turn it into context usable now: one concise piece of experience, its conditions of use, an entry point to the evidence, and its relationship to the current version. If the experience depends on the behavior of an old interface, read the current code before deciding whether it applies. "It worked last time" is no reason to skip checking the boundaries of what has changed.

Forgetting can be handled by life cycle: temporary task state expires; a stable fact is superseded by a new version; duplicate entries are merged; low-value experience long unused is archived; an entry shown to be false is marked revoked. Deleting sensitive information also has to run through backups, indexes and derived data, and the specific retention requirements should be decided by the application's policy.

Follow-up: is a memory used often recently necessarily important?

Not necessarily. A retrieval preference can make one wrong memory used more and more, which becomes self-reinforcing. Value should be judged by actual help and evidence, not by the number of accesses alone. A rare but critical safety boundary may also go uncalled for a long time, and should not be deleted for being infrequent.

Follow-up: how do you test whether a memory system really works?

Use cross-session tasks, late corrections, multi-project isolation, and conflict and forgetting tests. Compare task completion and error rates with no memory, with the raw history and with curated memory; benchmarks such as LongMemEval offer ways of thinking about how to evaluate memory ability, but your own project still needs a comparison on real tasks.[LONGMEM]

Follow-up: when should you stop adding more memory machinery?

When new machinery does not reduce repeated mistakes or the cost of rebuilding, yet adds maintenance, retrieval noise and latency, it is time to simplify. One versioned document plus a lean index may suit a small team better than a complex Memory Service. Complexity should be driven by problems that have actually appeared.

Engineering deep dive · E36 · continues Q072

Deleting the original text is not forgetting: summaries, caches and experience entries depend on it too

Prerequisite: Lesson 22 · Lesson 23 · Lesson 29. Reading order: confirm the run contract first, then the counterexamples and the fix, and test the limits last.

Forgetting is a chain of propagation, not the deletion of one row

One document can give rise to chunks, summaries, retrieval vectors, answer caches and long-term experience. Once the original is withdrawn or the user's permission is revoked, deleting only the document row still leaves the other derivatives able to feed the original content back into the model. This risk comes from data dependency; tool boundaries such as MCP also require identity and resource access to be handled continuously, not checked only on the first read.[MCPSEC]

This section uses an independent teaching dependency graph: doc→chunk→summary→answer_cache and memory. Once doc is revoked, all five classes of object are marked invalid along the dependency closure. The local program's verification result contains five nodes. It is not connected to real user data, and this graph is not treated as legal compliance certification.

Revoking availability and deleting physically are not one step

Physical deletion may complete asynchronously; until it does, revoked material must at least be kept from taking any further part in retrieval, cache hits and memory construction. If you rely only on a TTL cleanup once a day, there is still a window between the revocation and the cleanup. The read path should check the validity of the source or the permission version, rather than trusting that the derived record was authorized when it was created.

Conversely, deleting every similar memory can also catch independent legitimate sources by mistake. The set of sources has to be kept: when a fact is supported by two independently permitted sources, whether it remains usable after one source is withdrawn is decided by the policy and the relation between the facts. Do not treat all similar text as coming from the same place.

Updating and forgetting have to be evaluated too

LongMemEval explicitly covers knowledge updating and the ability to abstain.[MEMEVAL] For an engineering system you should go further and add timing tests of "remember, then withdraw, then ask"; testing only first-time recall rewards unlimited memory. Record the retrieval hits, what was actually fed into the prompt and the final answer, to confirm that the model did not merely happen not to say it.

Follow-up: can deleting external memory delete knowledge in the model's parameters?

That does not follow. Controlling the availability of external storage, deleting training data and unlearning at the parameter level are different problems. What this book guarantees here reaches only as far as the controllable chain of external derivatives; it makes no claim to have changed what the base model has already learned in its parameters.

Follow-up: if an experience entry does not store the original text, does it still need a source?

It does. A piece of experience may come from one root-cause analysis of an error; without a source and conditions of use, it cannot be expired once the code is upgraded or the conclusion withdrawn. Storing a lean conclusion does not exempt you from evidence governance; it makes a traceable compression relation all the more necessary.
