Prerequisites for this chapter

Only by dividing a run into observable spans can you find whether the slowness is in the queue, the model, the tools or rework. Cost should be computed per successfully completed task, and read together with quality and tail latency.

Each question in this chapter lists the groundwork it needs. You can take the matching Foundations lesson first, or use the self-check to confirm how well you have it.

Lesson 62 · Computing fast and fitting in memoryLesson 02 · State, events and checkpointsLesson 26 · Retries, idempotence and transactionsLesson 05 · The denominator of an evaluation metricLesson 31 · Do not be fooled by a few percentLesson 29 · Security basicsLesson 33 · Reading a production run

A quick check before the deep reading: when reading a trace, rebuild the dependencies first — independent parallel spans are not simply added up — and count the actual consumption of a failed task just the same.

A term with a dotted underline can be clicked for a quick reference. Read the definition of a letter in a formula first; do not let a guessed abbreviation stand in for the derivation.

This chapter does not treat "add logs, set up monitoring" as the answer. We want to be able to separate waiting, the model, the tools, recovery and verification in the trace of one slow task, and to explain at which stage the system comes close to its capacity limit. All the numbers are teaching assumptions, not a vendor quotation or a production measurement.

Q065｜How should one agent task record its trace, so that "slow, expensive, wrong" can be located?

What to know first for this question A trace holds spans, times and dependencies, which locate where one task spent its time. Sensitive information in a log should be kept to a minimum.
Lesson 02 · State, events and checkpointsLesson 33 · Reading a production run

Core answer

Take one user task as the logical root, with retrieval, model calls, tool execution, compaction and verification as sub-operations; record the causal relations, the input versions, the output status and the resource consumption. Trace answers "what happened this time", metrics answer "how things are overall", and logs and evidence objects answer "what the details actually were". None of the three can replace another.[SRE][OTEL]

The objects in one trace, and the keys that link them

Let task t7 go through retrieval r2, a model request m3, a tool call c19 and a recovery rec1. m3 produces c19, but c19 may be executed by another worker process. Correlation should rest on stable IDs, rather than guessing from "the times look about right" that they belong together.

任务 t7
  检索 r2：索引 rev42，命中 doc8@v3
  模型 m3：上下文 manifest17，生成 tool-call c19
  执行 c19：资源 fileA@r42 → 结果 unknown
  核验 rec1：读取 fileA@r43，确认副作用已发生
  模型 m4：看到核验结果，不重复修改
  验证 v9：在工作区 r43 上运行测试

For every model call, distinguish at least the model requested, the model identifier returned, the input volume, the observable cached volume, the output volume, the response status and the elapsed time. Whether reasoning usage is itemized separately, and how it is billed, depends on the interface; it should not be guessed from the length of the final text. For every tool call, record a summary of the arguments or a controlled reference to them, the permission outcome, the execution status and the external operation ID. Full sensitive arguments should not enter a public log by default.

Start with the objects and symbols used here
DAG, dependencies and the critical path
A DAG is a task dependency graph that is directed and has no cycles. The arrow A→B means B depends on A finishing; the critical path is the longest dependency chain, the one that fixes the earliest finishing time given the task durations and dependencies. Independent example: A takes 2 seconds, B and C depend on A, take 3 and 5 seconds and can run in parallel, so finishing both after A takes at least 7 seconds — not 2+3+5=10 read as wall-clock time.

If two tools run in parallel and take 8 seconds and 10 seconds, 18 seconds cannot be taken as the user's wait over that stretch; the critical path is more like 10 seconds plus the scheduling cost. If there is queue waiting between the spans but only the execution function is instrumented, monitoring will show "the tools are fast" while the user still waits a long time. Record the enqueue, the start and the finish separately.

Parallel spans in a trace cannot simply be added up into the user's waiting time

Conditions for this example: an independent task: the model plans from 0—2 s, then tool A runs from 2—7 s and tool B from 2—5 s, and finally the model consolidates from 7—10 s.

Span

How to read the changes in the figure

The horizontal axis uses real illustrative times, and A and B overlap. What the user waits for is the last dependency to finish, not the sum of the two tool times.

If the trace records only the time spent inside the tool, it may miss queuing, connection and response transfer, and the end-to-end figure will still not add up.

Every span should be linked to the task, the attempt, the tool ID and the artifact identity, so that slowness and errors can be tied to a specific operation.

Do not conflate: when the parent span already includes the child span's time, adding parent and child together counts that time twice.

Worked example · Q065

Three spans in the trace add up to 10 seconds — why did the task take only 7

Input and conditions. Retrieval spans A=[0,3] seconds and B=[0,5] seconds, consolidation C=[5,7] seconds, parent task=[0,7] seconds.

Steps and objectsInternal actionIntermediate result / new state
1 Sum the span durations3+5+210 seconds, the accumulated duration of the individual operations.
2 Take the task's wall clock7−07 seconds.
3 Critical pathC follows B5+2=7, and A is not the current critical path.
4 Optimize ACut the 3 seconds to 1With B still at 5 seconds, the whole task is still 7 seconds.
5 Optimize BCut the 5 seconds to 2Now the wait on A is 3 seconds and the task becomes 5 seconds, not 4.

Join the steps up. Optimization should follow the critical path and the dependencies, rather than starting with whichever span is easiest to shorten.

Limits and counterexamples. This is a deterministic timeline that ignores resource contention; in an asynchronous trace, the parent-child relation still has to be told apart from the actual waiting dependency.

Basis and scope of use:[DERIVE]. The example input and setting are stated explicitly by this book.

Follow-up: without storing the full prompt, can missing context still be debugged?

You can store a context manifest: fragment IDs, source versions, roles, the reason each was loaded, the Token estimate, the trimming state and the final ordering. It cannot reconstruct all of the text, but it can reveal that "a file that should have been loaded never entered the request". When the content itself has to be replayed, use an evidence store with permissions and limited retention. Keeping the manifest apart from the body is a compromise between diagnostic power and privacy.

Follow-up: why should user IDs and full prompts not go into metric labels?

There are enormous numbers of such values, so they produce high-cardinality time series that raise storage and query costs; they can also leak information. Metrics suit a limited set, such as the tool category, the result type or the version group. Put a single task's high-cardinality fields in a controlled trace or log, and jump there from a metric anomaly to look.

Follow-up: who should decide what counts as "success" in a trace?

Model API success only means the call completed; a tool success only means the tool returned success; task success should be decided by the acceptance result. The root span is best at keeping both the termination reason and the business acceptance result. Otherwise "an answer was generated" covers up zero tests, partial completion or a failed external write.

Engineering mechanisms and failure boundaries

Work out the waiting, the usage and the cost of failure from one trace

One request has at least three kinds of time

The user's wait is wall clock; the model's computation is the inference span; the total tool work is the durations of the individual actions added up. With concurrency the total can be greater than the wall clock. Ordered collection, queues, locks and retries can add waiting too, and none of that shows up in the execution time of a single tool handler.[C04]

A teaching trace: the model 2 seconds, tools A at 5 seconds and B at 3 seconds in parallel, aggregation 1 second, a wall clock of about 8 seconds and 8 seconds of total tool work. Optimizing A to 4 seconds makes the wall clock 7; shrinking only B to 1 second leaves it at 8. Look at the critical path first, then decide which part to optimize.

Quantiles cannot simply be averaged

When two groups of requests have different sample sizes, the average of their two p95s is not the overall p95. The overall figure should be computed from the raw latency distribution or from a mergeable statistical structure. Recording only the mean hides the long tail; reporting only p95 is no substitute for the sample size, the error rate and the timeout policy.

The cost per successful task must include the failures

In a teaching case, 10 requests cost 20 yuan in all and 7 meet the bar, so this batch's total cost per successful result is 20/7, not the average fee of the 7 successful calls alone. A discarded compaction candidate, a model request that completed after a cancellation and a tool retry can all still consume resources. The pinned asynchronous compaction path deals specifically with the wind-down and the usage, which shows that "the result was not used" is not "there was no cost".[C06]

A trace has to join things up and also avoid leaking secrets

A correlation ID links the user task, the model call, the tool call and the downstream operation; version fields link the rules, the model, the tools, the evidence and the index. By default record only the necessary summary and hashes, redact sensitive content and set a retention policy. Full observability is not keeping prompts forever.

Canary releases and rollback

Update the model, the prompt, the tools and the index at once and a problem is hard to attribute. Each version should form a configuration that can be rolled back; a rollback is not only replacing code — the memory, the checkpoints, the index format and the new state all have to be checked for compatibility. Data written by the new version need not be readable correctly by the old one.

Record the size of the session window separately from the money already spent

The pinned implementation provides a SpendingOnly path for usage reported on a response that did not complete; even when a background summary goes unused, the calls that did complete still have to be settled. "The current window got smaller" must not be written down as "the total spend went down too", and the length of a recoverable session log must not be taken directly as the model's current context length.[C06][C16:record_incomplete_response_usage]

A teaching ledger fixes the cost of three attempts at 2, 3 and 5, of which only one task finally succeeds, so the total spend is 10, not the 5 of the last attempt. Cost per success, queueing delay and the critical path each have their own denominator. Real billing also has to be worked out from the usage the service returns and the pricing version; this book gives no fixed commercial unit price.

Q066｜Why is "cheap per token" not the same as "cheap to get the work done"? How should cost be computed?

What to know first for this question The total cost includes failures, retries and tools, and the cost per successful task is the total consumption divided by the number of successes. Cheap tokens on one call do not make the whole thing cheap.
Lesson 62 · Computing fast and fitting in memoryLesson 05 · The denominator of an evaluation metricLesson 33 · Reading a production run

Core answer

The unit of cost should be one task that meets the quality requirement, not one model request. The total cost covers successful and failed attempts, retrieval, tools, verification, human rework and the resources to run it all; caching, model routing and parallelism only mean something when quality and total cost are compared together.[LATENCY][PCACHE][EVALS]

From a single request's bill to the cost of a task

Let the uncached input, the cached input and the output of call i be uᵢ,cᵢ,oᵢ, with unit prices pᵤ,p꜀,pₒ; the model cost is then the sum over all calls of pᵤuᵢ+p꜀cᵢ+pₒoᵢ. If the product charges separately for cache writes, tools or anything else, those items have to be added according to that product's own accounting basis; an unknown fee cannot be taken as zero by default.

Two teaching options: A costs 1 unit per attempt with a success rate of 0.8; B costs 0.6 per attempt with a success rate of 0.4. Assuming independent, identically distributed retries after a failure, no limit on retries and the same quality on success, the expected number of attempts before a success is 1/p, so the costs are 1.25 and 1.5 respectively. B is cheaper per attempt and yet dearer per success. In reality the independence assumption often fails: repeated runs that lack the same evidence may go on failing, so this formula must not be used blindly to predict a production bill.

In practice, compare on the same task set: total spend, number of successes, failure types, the quantiles of total latency, and how much human intervention was needed. Look at simple and complex tasks in separate strata as well; an overall mean can hide a cheap model's clear degradation on one class of high-risk task.

The numerator of cost per successful task must include failures and rework

Conditions for this example: an independent 100-task experiment: option A costs 1 unit per run and succeeds 80 times; option B costs 0.7 units per run and succeeds 50 times, with no retry after a failure. For now count only the call charges and ignore human cost.

How to read the changes in the figure

"30% cheaper" describes the unit price of a call, not the result. Failures have cost money too, so the 35 units from the 50 successful runs cannot be the only numerator.

A real comparison must also count retries, verification, tool charges and the human handling required, and report latency and unacceptable errors alongside.

Within the same budget, a few more attempts may raise the success rate, but a task with side effects cannot be repeated unconditionally.

Do not conflate: comparing input token counts alone misses the output, the internal reasoning, the tools and the cost of failures.

Follow-up: is a higher cache hit rate always better?

Not necessarily. Carrying a large irrelevant history along can raise the cache hit rate, while adding logical context, attention reads during decoding, or distraction. A cache hit is an intermediate metric; in the end it is still quality, the bill and the elapsed time that count. Deleting a useless prefix may give up one hit and yet lower the long-run cost afterwards.

Follow-up: when does choosing a stronger model actually cost less?

When the stronger model markedly reduces wrong tool calls, useless searches, rework or human review. This has to be confirmed in a controlled experiment that holds the task and the tool conditions fixed. It cannot be settled from the model's name or from one impressive case; nor should a simple deterministic task default to the largest reasoning budget.

Follow-up: when the budget runs out, should the verification step be dropped?

Usually you narrow what is promised, or stop making further changes, rather than dressing an unverified result up as finished. Budget for verification and winding down can be set aside; if it is already short, report what is done, what is unverified, the risks and where to resume from. An unverified result that "looks finished" may pass the cost on to whoever maintains it next.

Engineering deep dive · E49 · continues Q098

Wall clock, total span duration, p95, cost per success: the metric names look alike, and computing the wrong one means choosing the wrong optimization

Prerequisite: Lesson 05 · Lesson 33. Reading order: confirm the run contract first, then the counterexamples and the fix, and test the limits last.

Parallel durations cannot simply be added up

Two retrieval branches start at the same time and take 3 seconds and 5 seconds, after which the aggregation takes 2. The end-to-end critical path is max(3,5)+2=7秒, whereas adding up the durations of all the child spans gives 10 seconds. Parent-child and parallel relations in a trace are there to explain the time, not to have every segment added up indiscriminately.[TRACE]

Shortening the 3-second branch to 1 second still leaves the end-to-end time at 7 seconds; only shortening the 5-second branch can change the critical path. Draw the dependency graph before optimizing, or a great deal of work will go in while the user's wait stays the same.

The average of p95s is not the overall p95

This book defines the quantile by nearest rank, to avoid confusion between different interpolation conventions. 100 fast requests each take 1 and 10 slow ones each take 100; the two groups' p95s are 1 and 100, averaging 50.5, but the p95 of all 110 together is 100. Averaging p95 straight across machines or tenants produces an overall experience that nobody had.

Aggregate mergeable distribution data or histograms, and state the bucketing and the sampling error. A global quantile cannot be reconstructed from one p95 scalar per instance.

The cost of failures also belongs in the cost per successful task

Four tasks cost [1,1,5,5] and only the first two succeed. The whole thing spends 12 for 2 successes, so the unit cost per successful task is 6; counting only the successful calls reports 1. The latter hides the waste of the failures and may reward an unreliable option that is cheap per attempt. An evaluation should include both the final outcome and the attempts actually made.[EVAL]

Follow-up: does more logging locate everything?

No. A long log without correlation IDs, versions, start and end times and an error classification is harder to use, not easier. Sensitive prompts and tool arguments also need redaction and access control. Logs, spans and metrics each have their use, and not every user ID can go into a high-cardinality monitoring label.

Follow-up: should the queue time be subtracted from the model's latency?

They can be separated for diagnosis, but the user-facing end-to-end latency has to include the queue. Otherwise, under overload, "model inference is still fast" while the user keeps waiting. Designing for overload in SRE has to attend to queueing and deadlines, not only to how fast the device executes.[SRE]

Q067｜Does more concurrency always mean more throughput? How is agent latency understood through queueing?

What to know first for this question A queue holds the waiting tasks, rate limiting controls the input rate, and backpressure keeps an overload from piling up further; retries amplify the request volume.
Lesson 62 · Computing fast and fitting in memoryLesson 26 · Retries, idempotence and transactionsLesson 33 · Reading a production run

Core answer

Start with the objects and symbols used here
SLI, SLO and the error budget
An SLI is a service level indicator that is actually measured; an SLO is the target for that indicator; the error budget is the room for failure that target allows. They are objects of service operation, not model parameters."The API returned 200" may not be success for the user; some businesses should define the indicator as the proportion of tasks completed correctly within a bounded time.
Little's law: L=λW as local notation
In queue accounting, L is the average number of tasks in the system, λ is the average arrival rate and W is the average time spent in it; under applicable conditions such as stability, L=λW. Here W is not a projection matrix, and L is not the number of model layers. Independent example: with 2 items arriving per second on average and an average stay of 3 seconds, about 6 items are in the system on average; an instantaneous spike cannot simply stand in for the long-run average.

Concurrency helps raise utilization only while there is resource headroom; beyond the capacity of the model, the tools, the database or the quota, new tasks mostly go into the queue. In a stable system, Little's law L=λW ties together the average number of tasks in flight, the average arrival rate and the average time in the system, but it is not an unconditional guarantee for capacity planning.[SRE][SLO]

From a request's arrival to its departure

A task is queued when it arrives and waits for a free execution slot; once it has one, it may still wait for a model quota or an external tool. A task that holds an expensive worker process while waiting a long time on a remote network lowers resource utilization. Recoverable task state can be decoupled from short-lived execution resources, but that brings in persistence and scheduling complexity, and everything should not be split apart at the outset for the sake of a tidy architecture.

A teaching example: 2 tasks arrive per second on average and stay 30 seconds on average, so within a stable observation window about 60 are in flight. With only 20 synchronous worker slots, whether the system is stable depends on how long each task actually occupies a slot, and it cannot be worked out from the latency of the final answer alone. If each slot is fully occupied for 30 seconds, the theoretical ceiling on the service rate is about 20/30, below the arrival rate of 2, and the backlog will go on growing.

Tail latency comes from long tasks, variance in service time, head-of-line blocking, retry storms and resource contention. Separate queues or quotas for short interactive tasks and long batch tasks reduce the interference between them; but priority must not starve low-priority tasks indefinitely. There should be a maximum wait, propagation of cancellation, backpressure and an explicit refusal, rather than accepting work without limit.

Enough average throughput does not mean peak requests avoid the queue

Conditions for this example: an independent, simplified single service slot: each request takes 1 s, all three requests arrive at t=0, and service is first-come, first-served; the network is not included.

Follow-up: why can a longer timeout make a failure worse?

It lengthens how long resources are held and how long an in-flight request lives. When something downstream slows down, the upstream goes on accepting work and waiting longer, until memory, connections and worker slots are all full. A timeout should match the semantics of the task and the end-to-end deadline, retries should have an overall budget, and each layer must not multiply the retry count independently.

Follow-up: CPU utilization is low, so why is there still a queue?

The bottleneck may be GPU VRAM, KV capacity, the per-minute token quota, concurrency on an external API, a database lock or a human approval. Monitoring should cover the queues and the scarce resources, not just the CPU. With a lot of waiting-type tasks you can even get the combination of very low CPU and a very poor user experience.

Follow-up: should an SLO specify only the P95 response time?

It should also include goals for task correctness, availability or human intervention, and define which tasks go into the denominator. Otherwise a system can "optimize latency" by refusing quickly or returning an empty answer. For a long asynchronous task, the acceptance latency, the real progress and the final completion can be kept apart; an ordinary web-response metric does not fit it.

Q068｜What exactly has to be versioned when an agent system goes live? Why is a rollback not just switching the model back?

What to know first for this question A release should bind the versions of the model, the prompt, the tools, the index and so on; after a canary comparison the whole combination can be rolled back, rather than one line of prompt undone.

Core answer

Start with the objects and symbols used here
Schema and Structured Outputs
A schema is a set of structural rules about fields, types and the like; a structured-output mechanism makes it easier for the model to return data that follows those rules. Valid fields still do not mean that the target file exists, that access has been granted, or that the request is right for the business. Independent example: path is required to be a string; {"path":3} does not match the type rule, and {"path":"missing.py"} follows the structure yet may still find no file.

The final behavior is determined by the model, the prompt, the tool Schema, the skills, the retrieval index, the memory policy, the permissions, the runner and the evaluation rules, all together. A release has to save a traceable combination and watch the results in a canary; a rollback must deal with the state already written and with external side effects, not merely switch the model name.[EVALS][SLO]

A version list that can explain a regression

Start with the objects and symbols used here
checkpoint: you must look at the object that was saved
A model checkpoint saves weights or training state; activation checkpointing saves a few intermediate nodes so they can be recomputed on the backward pass; an agent task checkpoint saves how far execution has got. The three share a name, but what they restore is entirely different. When you see "checkpoint", first ask whether it restores parameters, recomputes activations, or continues a task. An agent saving a summary does not update model weights.

Suppose the model, the compaction summary format and the code index are all replaced on the same day and the success rate drops. Without a version list the causes are hard to tell apart; changing only a few attributable variables at a time, running the offline regression first and then watching a small amount of real traffic, makes the judgment easier. A canary is not handing a dangerous operation out to a few users at random; a high-risk capability still needs permissions and acceptance in place first.

Before rolling back, check whether the memory and the checkpoints written by the new version can be read by the old one. If the summary schema changed, the old runner misreading "unknown" as "failed" may lead to a duplicate write. An external order, an email or a deployment is not undone just because the program was rolled back; they have to be checked and compensated according to the business semantics. A safer rollback may be to stop new write operations and keep read-only checking with a person taking over, rather than going on running incompatible old code.

In a matrix formula I is usually the identity matrix: 1 on the diagonal and 0 everywhere else. At a compatible size, multiplying a vector or a matrix by I leaves the numbers unchanged. Follow-up: why can the latest benchmark score not be the only basis for putting a model live?

A benchmark's tasks, tools, resources and success criteria need not match yours. Put the candidate model into your own Harness and your own historical failure set and test it there, checking structured output, tool compliance, long context and cost in particular. A public score offers a signal for shortlisting; it does not replace local acceptance.

If that prompt affects production behavior, the exact content should be traceable; but there is no need for a complex approval layer around every wording change. Versioning is for attribution and rollback, and how deep the approval goes depends on the risk. Do not read "traceable" as "a multi-level review every time".

Follow-up: how do you know the optimization can stop?

Once the main failure modes have been dealt with, and a further mechanism brings no discernible gain on representative tasks, or a gain smaller than its cost and maintenance risk, piling on more rules should stop. Keep the monitoring and the flow of real failures coming back, and wait for new evidence to trigger a change. That fits the engineering goal better than chasing a perfect process forever.

Engineering deep dive · E50 · continues Q100

Why can rolling back the model name alone leave things in a worse tangle? A system version is a set of vectors

Prerequisite: Lesson 02 · Lesson 18 · Lesson 33. Reading order: confirm the run contract first, then the counterexamples and the fix, and test the limits last.

The same model name does not mean the same system

Behavior is determined together by the model weights or service version, the tokenizer, the message template, the tool schema, the skill, the index generation, the memory rules, the application code and the grader. Recording only model=m1 cannot explain a regression brought by the template going t1→t2 or the index going i1→i2. The model interface, cache identity and work-tree evidence all show this dependence on many components.[RESP] [PREFIX] [GIT]

This book uses the version vector{model:m1,template:t1,index:i1,tools:s1}to compare against an i2 in which only the index changed: the model name is the same but the joint fingerprint differs. The fingerprint is no proof of quality, but it is the least identification needed for replay and attribution.

A rollback has to account for tasks in flight

The new version has already issued tool calls, written memory in the new format or produced state in the new schema, and the old code may not be able to read it. Switching straight back to the old model does not undo those actions. Keep apart the rollback of routing for new tasks, the policy for continuing or canceling tasks in flight, data format compatibility, and the reconciliation of side effects. Where necessary, use forward-compatible reading or pause the writes, rather than forcing the old logic to take everything over.

The grouping in a canary has to be explainable

Split traffic by user, task type or a stable hash, so that one long task does not switch between prompt or tool versions unplanned partway through. Record which samples belong to which version combination, and compare the success rate, the tail latency and the risk events under the same task distribution. If the index or the cache is shared, say whether that can contaminate the two arms of the comparison.

Follow-up: why does replaying the same prompt still not guarantee an exact reproduction?

The server-side model, the random state, the external data behind the tools and the infrastructure can all change, and some state is invisible. Keep apart a replayable request, a replayable environment and bit-for-bit reproduction. Keeping enough evidence improves the ability to troubleshoot, but it must not be claimed that hidden internal state has been saved in full.

Follow-up: which version information should not go into metric labels?

Fine-grained request IDs, long hashes and arbitrary file paths can lead to high cardinality. Metrics should keep a limited set of release numbers and categories, while the detailed joint fingerprint goes into a trace or a controlled log. Observability design has to balance cost, privacy and searchability, rather than printing without limit.

The smallest runnable rollback check

Before the release, have the old and the new version each read a state fixture produced by the other; simulate an action of the new version that completes only after the rollback; and check whether the idempotency key, the target version and the approval still match. Testing that the home page opens is not enough to show that an agent task recovers safely.
