Prerequisites for this chapter

Several agents are not one brain split into several for free. For every subtask you have to supply information, bring evidence back and integrate the result; and a shared file adds the problem of concurrent overwriting.

Each question in this chapter lists the groundwork it needs. You can take the matching Foundations lesson first, or use the self-check to confirm how well you have it.

Multi-Agent is not copying one problem out to more models. It brings in separate contexts, concurrent tasks, merging and recovery, and it can also amplify duplicated work and correlated errors.[MULTI]

Q053｜What does a sub-agent receive, and what does the main agent get back? What should a handoff package contain?

What to know first for this question A sub-agent isolates context but costs a handoff: the goal, the evidence, the permissions and the return format all have to be clear; parallelism suits loosely coupled work.
Lesson 02 · State, events and checkpointsLesson 11 · Assembling contextLesson 13 · Skills, routing and multi-agent

Core answer

A sub-agent usually receives an explicit task, the context it needs and the tool configuration available to it; it should not be assumed to hold the main agent's whole history and permissions automatically. What it returns should contain the conclusion, the evidence, the artifacts and the open questions. A handoff is a process of selecting information, and so it can be lossy by nature.[SUBAGENTS]

A handoff that can be acted on, and one that cannot

"Have a look at the database problem for me" is too broad. A more actionable teaching handoff is: the goal is to confirm whether the duplicated refund was caused by a retry; the scope is the payment module and its callers; do not modify code; the current observation is that the same order shows two remote requests; provide the relevant trace ID; return a falsifiable root cause, the evidence paths and the points left unconfirmed.

Returning "a retry caused it" is still not enough. It should say which branch was seen in which version, which log line shows the same business ID twice, whether two independent orders have been ruled out, and what test is needed. Only then can the main agent make its change on the strength of the result, instead of redoing the whole investigation.

A handoff cannot be endlessly detailed, or a multi-agent setup is merely copying a large context around. Pass in the key facts and the references that locate them, and let the sub-agent read more as it needs to; what finally comes back is a compacted summary of the evidence plus original output that can be traced. The problem of summary fidelity is present in a multi-agent handoff just as much.

A handoff package must at least let whoever takes over know the evidence and the unfinished actions

Conditions for this example: an independent main-agent delegation: the sub-agent verifies the exclude patch and is not allowed to write files. The main agent has already changed filter.py to r8, and the tests have not been run yet.

How to read the changes in the figure

A subagent does not naturally hold all of the parent agent's memory. The handoff package has to let it start from an explicit state, not merely from "have a look".

A short summary can be kept and the original evidence read through a reference; the whole parent history need not be copied, but the constraints and the versions must not be lost.

What is reported back needs both a conclusion and an artifact that can be verified. "No problems" on its own cannot support a final delivery.

Do not conflate: deleting unfinished items to save tokens can leave two agents each believing the other has run the key test.

Follow-up: is handing the sub-agent's whole conversation back the safest thing to do?

Keeping the full text as a traceable record is worth doing, but putting all of it into the main context can swamp the task. The main thread needs the conclusion, the evidence and the open items, and can expand the full text when it has to. The job of the original record and the job of the current context should be kept apart.

Follow-up: can a sub-agent's conclusion be written straight into long-term memory?

The source and the result should be confirmed first. A sub-agent guesses and misreads too, and promoting an unverified conclusion straight into memory propagates the error. It can be saved as a candidate experience, and activated once the main task's result and evidence support it.

Follow-up: why do permissions have to be checked explicitly?

A sub-agent's run environment, set of tools and approval mode can all differ. Without the permission it should report the gap, instead of pretending to be done or switching to higher privileges to get around it. A handoff package describes a task; it cannot grant permission on an external system by itself.

Engineering mechanisms and failure boundaries

How do several agents run in parallel, and how is loss at handoff avoided?

Start by working out an example that really can run in parallel

In the teaching example, task A takes 4 time units to look at the callers and B takes 6 to look at the callee; consolidating takes 2. When they are fully independent, running them in sequence is 12 and in parallel 8. But if the handoff and the re-checking add 5, parallel becomes 13, which is slower instead. The numbers are teaching time units, not a measurement of any model.

Anthropic's multi-agent research practice stresses the coordinator, the subtask goals, the scope of the output and the integration of evidence, and it also notes that parallelism suits certain decomposable work; its results on research tasks should not be taken directly as a guarantee for coding tasks.[A04]

The output contract matters more than the role name

"You are the expert, have a look" is too vague. A better handoff writes down which version to check, the read and write scope allowed, the specific questions that must be answered, where the evidence is, which paths have been ruled out, what cannot be confirmed, and how long the result may be. A sub-agent returning "no problem" is not evidence; returning r7:caller.py:L20 together with the test command is what makes it checkable.

Messages with the same name are not the same kind of control

The pinned Codex communication path distinguishes input that triggers a new turn from internal messages that trigger no turn; for a child thread that has not been loaded yet, a message can be queued. A message submitted successfully has not thereby been read by the model, still less has the subtask finished.[C11] A handoff record should distinguish queued, delivered, started, completed and validated, rather than a single sent.

Two kinds of merge conflict

A textual conflict: two agents write the same file at the same time. A semantic conflict: one changes the interface while the other changes the call site against the old interface, and even with entirely different files the combination is still wrong. The way to handle it is an explicit dependency DAG, explicit owners, an explicit baseline version, and whole-system verification after the merge. Only independent research subtasks can safely be analyzed separately and then pooled; shared writes call for more care.

There is no need to force every small task through analysis—implementation—review

Adding an agent should answer a real need: isolating context, exploring in parallel, or verifying independently. When a simple change has already been located and has a direct test, several rounds of handoff may be no more than reading the same thing again. Measure rework, success rate and total time with paired tasks; the complexity of a process is not a measure of professionalism.

A sub-agent's message being accepted does not mean it has started work

In the Codex path that was read, a message to a receiver that is not loaded and carrying trigger_turn=false can simply be put into the mailbox, returning a submission_id. What that ID proves is acceptance, not that the task has started, and still less that it has finished. Forked history is also filtered type by type, so the parent thread's cumulative usage is not taken directly as the child's newly added usage.[C11][C12]

A teaching handoff has to write out the result contract: the paths returned, the baseline version, a summary of the changes and the test evidence, for instance. Putting two independent reviewers in different contexts can reduce how much they cue each other, but it cannot be claimed to make them statistically independent; a shared model, shared material or the same wrong assumption still produces correlated failures. Before adding an agent, prove that the task can be split and that whoever consolidates has enough evidence to accept it.[A04][A13]

Q054｜How does a task DAG decide what runs in parallel? Why is cutting it finer not necessarily faster?

What to know first for this question A DAG is a directed acyclic dependency graph whose edges state what must come before what; the critical path fixes the ideal shortest time, which is not the simple sum of the task durations.
Lesson 62 · Computing fast and fitting in memoryLesson 13 · Skills, routing and multi-agentLesson 26 · Retries, idempotence and transactions

Core answer

Start with the objects and symbols used here
DAG, dependencies and the critical path
A DAG is a task dependency graph that is directed and has no cycles. The arrow A→B means B depends on A finishing; the critical path is the longest dependency chain, the one that fixes the earliest finishing time given the task durations and dependencies. Independent example: A takes 2 seconds, B and C depend on A, take 3 and 5 seconds and can run in parallel, so finishing both after A takes at least 7 seconds — not 2+3+5=10 read as wall-clock time.

DAG states the dependencies between subtasks, and only a task whose input is already satisfied and whose resources do not clash can safely run in parallel. The total latency is affected by the critical path, the coordination overhead and contention for resources; splitting work adds handoff and merge costs and does not raise quality by itself.

Work out a simple critical path

Task A takes 2 units of time to locate the interface, B takes 4 to change the implementation, C takes 3 to add tests, and D takes 2 to verify the integration. If C depends on B in order to know the new contract, the chain A→B→C→D comes to 11. If the contract is already settled after A, B and C can run independently in parallel, giving roughly A2+max(B4,C3)+D2=8, with communication and conflicts not yet counted.

If every handoff adds 1 and B and C changing the same file costs 2 units to merge, the 3 units saved in theory can be eaten up entirely. Worse, the parallel tasks may understand the contract differently and the work has to be redone. A task's independence has to come from stable input and boundaries, not from splitting a title across several lines.

Different subtasks share the model's rate limit, the tool server, the database and the Git work tree. Even when they are logically independent, they can contend for resources. Scheduling should have a concurrency cap and a cancellation mechanism, so that one user task does not use up the entire quota.

The longest dependency path in a DAG decides the earliest that parallel tasks can finish

How to read the changes in the figure

B is the longer branch in this graph. Optimizing C from 3 down to 1 still leaves D waiting for B to reach 6, so the total is still 7.

Real delegation also adds time for start-up, gathering evidence, handoff and conflict handling; the 7 in the figure is an ideal time with no extra overhead.

Cutting the work into more nodes can create more opportunities for parallelism, and can also add communication across the boundaries; a speed-up cannot be inferred from the number of agents alone.

Do not conflate: if B and C actually write the same file, they may not be safe to run in parallel; the task graph has to reflect resource conflicts, not just the business steps.

Follow-up: should the DAG be planned out in full before starting?

A task with clear dependencies can be planned in advance; exploratory work should be allowed to adjust as it goes. Splitting out dozens of nodes too early may rest on wrong assumptions and produce execution that leads nowhere. You can finish the most critical locating work first, and then parallelize the parts that really are independent.

Follow-up: how is every subtask kept from repeating Analysis→Task→Review?

Pool the shared analysis and constraints into reusable evidence, and let a subtask fill in only its local gaps; choose verification by risk instead of copying the whole process mechanically. A small problem can be fixed directly in implementation or in review, and only a change to a core assumption or boundary calls for going back to redesign.

Follow-up: how is a multi-agent speed-up counted fairly?

Compare, at the same quality target, wall-clock time, total Token, model calls and tool resources; do not look only at when the longest subtask finishes. Ignoring the total cost that parallelism consumes creates the illusion of "faster and cheaper".

Engineering mechanisms and failure boundaries

Why can tools running in parallel finish earlier and show their results later?

Two reads and one write

The teaching harness receives A reading a file, B looking at the log and C changing the configuration. A needs 30 ms and B needs 10 ms. B can finish first, but to keep the order of the messages the harness still prints A and then B. That is no proof that B did not run in parallel; equally, showing two "start" lines is no proof that the two really occupied resources at the same time.

The pinned Codex path creates an asynchronous task once it has received the call; whether parallelism is allowed is decided by the tool's registration information, and by default it cannot be assumed that every tool can run in parallel. A shared read-write gate lets the parallel paths in the safe category coexist, while a serial path has to take the exclusive gate. Waiting for admission and actually executing are timed separately.[C04:handle_tool_call_with_source] This path keeps execution separate from consuming the future's result, and records that the execution result is ready. The particular timeline of A and B being backfilled in order here is a teaching comparison, and is not passed off as a uniform display order for every Codex client and message type. The times of the action finishing, the result being consumed and the backfill should be checked separately.[C04]

A wrong performance calculation

A at 30 ms and B at 10 ms overlap completely, so the ideal computation stretch is about 30 ms of wall clock and 40 ms of total work. With another 5 ms of admission and 8 ms of consolidation, the task's wall clock is at least about 43 ms. You cannot say "two tasks of 30 ms each, so two threads must take 15 ms"; nor can parallel spans be added up straight into the user's waiting time.

A declaration of parallelism is no proof about side effects

Two tools writing different files can still have a semantic dependency: A changes the protocol definition while B generates the caller from the old protocol. The file paths do not clash, but the tests fail once the two are combined. Safe parallelism needs the read set, the write set, the versions and the task dependencies all considered together; a lock at tool level can only settle the range of conflict it was designed to cover.

Cancellation behavior has to be understood layer by layer

A cancellation while waiting at the gate can come before the action has started; a cancellation once the handler has finished but the result is still in the queue must not let the result be dressed up as never having happened. Some actions have to go on tidying up after being canceled, while others can be aborted. Canceling a coroutine is not canceling a request an external system has already received.[C04]

The trace should separate at least: queuing started, admission granted, action started, action finished, result collected, backfill finished. Otherwise one case of "the model is slow" may really be queuing, waiting on a mutex, or an earlier task blocking the ordered collection of results.

Allowing parallelism is a scheduling declaration, not a semantic proof

A read-write gate can constrain the calls that runtime manages, but it cannot know by itself whether two remote APIs contend for the same business object. A parallel flag should be reviewed together with the actual handler, the side effects and the external version constraints. A teaching counterexample: two calls are both marked as parallelizable, but each reads the balance and then deducts from it; with no atomic constraint downstream, a local read lock cannot keep the business figure from going over.[C04]

A performance record divides into "queuing—admission—execution—result ready—consumption—backfill". When action B has finished and still shows nothing, the cause may be the order of consumption, or an earlier action blocking it; the model's computation should not be blamed straight away. The timing model here is a tool for engineering analysis, not an assertion about every UI refresh policy in any product.

Q055｜When several agents change the same repository, how are overwrites and wrong merges avoided?

What to know first for this question Independent files can be divided up, while shared changes need their versions and their merging coordinated. Several agents all returning success is no guarantee that the merged result holds.
Lesson 02 · State, events and checkpointsLesson 18 · Code is not an ordinary documentLesson 13 · Skills, routing and multi-agentLesson 26 · Retries, idempotence and transactions

Core answer

Isolate the work trees or state the write scope explicitly, record the shared baseline, and verify the merged version again. Git reporting no conflict says only that the text can be merged; it says nothing about semantic correctness.

A semantic conflict with no textual conflict

Agent A changes a function's return value from a list to an iterator, and Agent B adds len(result). The two of them change different files and Git can merge automatically, but it may fail at run time. The shared interface contract matters more than the file boundary. Fix the contract as far as possible before parallel tasks begin, and notify the dependent tasks when the contract changes.

Isolating the work trees avoids direct overwriting, but the merge still has to happen. Every subtask saves its baseline, its diff and its test evidence; at integration, check the difference in baselines, the conflicts and the related dependencies; after the merge, run tests that cover the interacting behavior. Each subtask's tests passing is not the combination passing.

For simple edits to the same shared file, overwriting can be avoided by going serially or by using a version condition. No elaborate branch system has to be created for every small task; what matters is being clear about who holds the write permission and when, and how to recover after a conflict.

Start with the objects and symbols used here
WAL, fsync and atomic replacement
WAL is the idea of writing a log first and then updating the data by protocol; fsync asks for a file's data to be synchronized to storage; an atomic rename, where it is supported, keeps readers from seeing a half-finished replacement. Visibility and durability after a crash are not the same guarantee. One file renaming successfully does not mean several files and a database committed together; durability also has to be checked against the platform, the directory and the storage behavior.

Different files with no textual conflict can still produce a semantic conflict

Follow-up: why can the main agent not simply believe a sub-agent's "tested"?

The tests may have been run against the version on a child branch, and the merge changes the conditions. The evidence has to carry the command, the working directory, the version and the result, with the necessary verification added on the final integrated version. A verbal report is not a verification credential anyone can reuse.

Follow-up: can a model that resolves conflicts automatically commit straight away?

Resolving a conflict is itself a new code change, and needs its semantics checked and its tests run. The model may pick one side and drop the other side's functionality. A high-risk conflict can be made to require human review, while an ordinary local conflict can be resolved and verified inside the same task, with no need for endless replanning.

Follow-up: do parallel reads carry a consistency risk as well?

Yes. When one agent reads a file while another is changing it, the set of evidence it gets can straddle two versions. Read-only investigation should also know the extent of its snapshot; critical analysis is best based on a stable version, or the relevant files should be read again before the conclusion is used.

Engineering deep dive · E39 · continues Q079

Two people change different files — so why does it still break after the merge?

Prerequisite: Lesson 18 · Lesson 13 · Lesson 04. Reading order: confirm the run contract first, then look at the counterexamples and the fix, and finally test the limits.

No textual conflict does not mean the contracts are compatible

Agent A changes the producer field to timeout_ms, while Agent B still consumes according to timeout_s. The two agents edit different files and Git may merge smoothly, yet the integration call throws KeyError, or more dangerously treats 5000 milliseconds as 5000 seconds. This book's program reproduces the first of those failures with a fixed-field example, and does not call it a real incident in any open-source project.

The boundaries of parallel tasks should be drawn around contracts, shared state and dependencies, not just file names. Data structures, API signatures, configuration precedence, version formats and the database schema can all reach across files.

A worktree solves part of the isolation

A Git worktree separates the working directories, which makes it easier for an agent to commit and merge independently, but it shares part of the repository's data, and it does not isolate an external database, service ports, temporary directories, the package cache or test accounts by itself.[GIT] If parallel tests all use the same fixed port, an intermittent failure may come from the environments interfering with each other rather than from the patch logic.

A handoff package has to be bound to the object being accepted

It contains at least the baseline, the changes, the interface agreement, the checks that were run, the risks not covered and a fingerprint of the result. Handing over a line saying "I have fixed it" is not enough. Whoever owns the merge runs the integration verification on the final combined version; each branch being green does not imply the combined version is green.

Follow-up: is locking every shared file enough?

A file lock prevents some write races but not a semantic conflict, and a lock also depends on every participant honoring it. For changes with strong dependencies, coordinating the interface design serially may take less time than repairing a parallel conflict afterwards. To decide whether to split a task, compare the work that really is independent against the cost of the handoff.

Follow-up: can one agent be dedicated to doing the merging?

It can, but it too needs the complete contract and the current evidence. Adding a role does not remove the loss of information by itself; give it the real test environment after the merge, rather than only the sub-agents' summaries. The result should be a final code state that can be verified, not a prettier account of the merge.

Q056｜Why can an independent reviewer still make the same mistake? What does A2A solve, and what does it not?

What to know first for this question The value of an independent review comes from different evidence and a different angle of checking, not from a change of name. Agent communication across systems also needs a real protocol and real authorization.
Lesson 08 · Tools and MCPLesson 13 · Skills, routing and multi-agentLesson 04 · Foundations of engineering qualityLesson 05 · The denominator of an evaluation metric

Core answer

Different agents may share the model, the prompt, the evidence and the biases, so their errors are correlated; one more reviewer is not an independent insurance policy on probability. A cross-agent communication protocol can standardize discovery, messages and task status, but it does not settle the credibility of the evidence, the permissions or the correctness of the conclusion.[MULTI]

Make the review supply new information rather than a second agreement

If the reviewer sees the implementer's full reasoning first, it readily confirms along the same path. Let it judge independently from the requirements, the diff and the tests first, and read the explanation afterwards; give it a different goal, such as looking for counterexamples, compatibility edges or concurrency, rather than a vague "see whether there is a problem". Independence comes from the evidence and the method of checking, not merely from a different agent name.

A deterministic check is often more independent than asking another model: type checking, property tests, a build, static analysis or a real run. A model is good for the design judgments those tools struggle to cover, but it also raises false alarms. What a review gains has to be measured against missed findings, false alarms and the cost of rework together.

An A2A-style protocol is concerned with capability discovery between agents and with exchanging messages, tasks and artifacts. MCP leans toward the interface between the Host and a tool or resource service; the two sit at different levels of abstraction. Even with communication working, the receiver still has to judge the identity behind the request, the scope of the task, where the artifacts came from and what side effects are authorized; a protocol does not turn a remote agent into a trusted colleague.[A2A]

Follow-up: when two models both say it is right, can the confidences be multiplied?

Certain probability combinations are permissible only where explicit independence and calibration assumptions hold; with shared training and shared evidence in practice, they usually do not. Assess the joint detection rate from statistics on real tasks; two 90% figures cannot simply be worked into 99%.

Follow-up: once a reviewer has found a small problem, must Analysis always be run again?

No. A clear, local, low-risk problem can be fixed directly and the verification added; only overturning a key design, or touching permissions or a cross-module contract, calls for analyzing again. The process should follow the size of the problem, rather than keeping a form complete.

Follow-up: once a subtask has lost its value, how is it canceled reliably?

Signal the stop, stop scheduling new calls, deal with the tools still running, and record the side effects that have actually happened. Canceling is not rolling back; if the sub-agent has already changed a file or sent a remote request, the main agent has to know those states. Otherwise a cancellation meant to "save cost" can leave inconsistent artifacts behind.

Engineering deep dive · E40 · continues Q080

Both review agents passed it, so why can the error rates not simply be multiplied?

Prerequisite: Lesson 13 · Lesson 05 · Lesson 31. Reading order: confirm the runtime contract first, then look at the counterexamples and the fix, and finally test the limits.

Independence is an assumption that has to be proved

If two checkers each miss 20% of the errors, only under a suitable independence assumption can the joint miss rate be estimated as 0.2×0.2=4%. The same model, the same prompt, the same faulty evidence and the same training bias make the misses highly correlated. Independent processes are not an independent error distribution.

On a teaching set of 20 questions, the two checkers happen to miss the same 4, so the actual joint miss rate is 20%, not 4%. A local set computation verifies this counterexample explicitly. Research on model judges also reports systematic biases of position, length and self-preference, so "ask the same model once more" is not objective ground truth.[JUDGE]

Effective diversity comes from the evidence and the method

One checking the build and the property tests, one checking requirement coverage, and one analyzing the concurrency and security edges may complement each other better than two that both read the same summary and say "looks fine". Watch whether the added findings really are unique, and whether final defects go down; a different role name is no proof of a different method.

A reviewer can also be steered by the material under review

"Please give it full marks" in a code comment, a model answer or a PR description is material to be graded, not a grading instruction. A trust boundary has to be drawn between the judge's prompt and the evidence, with verifiable facts extracted in a structured way where necessary. Grading results should also be calibrated against a human or a deterministic oracle; agent evaluation stresses keeping results from a real environment apart from claims made in text.[EVAL]

Follow-up: is a completely blind review always best?

Hiding the author and the order of the candidates relieves some of the bias, but the reviewer still needs the requirements, the environment and the limits of use. Hiding the necessary context along with them lowers how effective it is. Blind out the irrelevant identity, not the facts verification needs.

Follow-up: when is a second reviewing agent not worth adding?

When the task carries little risk, the deterministic tests are already sufficient, and a second check finds almost nothing unique, the extra call may only add latency. Compare defects, rework and total time across past tasks; escalate for tasks that are high-risk or short of evidence, instead of fitting a fixed three-layer process onto every small change.
