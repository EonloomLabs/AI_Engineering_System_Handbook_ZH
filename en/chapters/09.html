Prerequisites for this chapter

An agent is a series of model calls driven by a surrounding program. The request, the response, the tool result and the task state each have their own life cycle; "the model says it is done" and "the environment really reached the goal" have to be verified separately.

Each question in this chapter lists the groundwork it needs. You can take the matching Foundations lesson first, or use the self-check to confirm how well you have it.

Lesson 35 · Sort the objects out firstLesson 57 · From the last row of numbers to a token, and on to an answerLesson 01 · An agent is not another neural networkLesson 07 · APIs and streaming protocolsLesson 02 · State, events and checkpoints

A quick check before the deep reading: draw the loop "request a file read → validate the call → read → return the file → call the model again" once, and mark which arrow is executed by the program and which judgment comes out of the model.

A term with a dotted underline can be clicked for a quick reference. Read the definition of a letter in a formula first; do not let a guessed abbreviation stand in for the derivation.

What follows uses an original teaching task, "fix exclude not taking effect in the repository". It does not stand for any change made to a user's real repository. While reading this chapter, always keep apart the model's proposal, Harness's execution and the real state of the environment.

Once the model, the harness and the tools are drawn as separate swim lanes, the question "who actually changed the file" has a definite answer. Follow every returned message, then decide whether the model has to be called again, a tool has to run, or it is over; do not take the model saying it is done as the environment being done.

Q001｜After the user types one sentence, how does the agent finish the task across several model calls?

What to know first for this question The model is responsible for proposing the next step; the harness is what actually calls the tool and fills the result back in. A workflow fixes the route, while an agent loop allows the next step to change according to a new observation.
Lesson 01 · An agent is not another neural networkLesson 07 · APIs and streaming protocolsLesson 02 · State, events and checkpoints

Core answer

Agent assembles the goal, the rules, the tool definitions and the current evidence into the model's input; the model returns ordinary text or a tool call; the harness checks and executes the call and makes the result part of the new context; the model then goes on to decide the next step from the observation. The loop ends on a condition such as verifiable completion, a decision needed from the user, failure or an exhausted budget. ReAct describes the combination of reasoning–action–observation, and a product harness is what turns it into a real execution system.[REACT][CODEX]

Walk all six turns, instead of just drawing one loop arrow

Turn What the model sees at this point Model output What happens in the harness/environment
1 The user goal, the repository rules, the search tool description Search for the exclude entry point The search returns paths and line numbers
2 The previous content + the search result Read the implementation and the test Returns a code snippet with its version
3 The conditional branch and the failing case Run the target test The process exits 1 and reports an assertion failure
4 The actual failure and the related code Apply a local patch Checks the old content, then edits the file
5 The patch result and the new version Run the regression test Records the command, the version and the exit code
6 The current diff and the test evidence A completion note The harness ends this task

Each turn's input may contain the history, or may be joined up through a reference to server-side state, but logically the model has to be told the results that bear on the current decision. A tool call is not the model "imagining it has already read the file"; it must really be executed and a real output brought back. The model saying in turn 3 that "the test should fail" is no substitute for the run result.

The model can request several mutually independent tools at once, and the harness may also run preset checks deterministically, so a real flow need not have exactly one action per turn. What matters is that input–decision–execution–feedback correspond clearly. The versions behind reading a file, editing a file and the test result must join up, or old evidence ends up applied to a new state.

How to read the changes in the figure

Follow call c1: nothing on disk changes when the model produces the call item; the harness still has to take the executing action.

The next turn does not send the isolated number "30" on its own; it has to keep which call that number answers and which file version it came from, so that another tool's result is not spliced in.

Two model requests are actually needed here; if the harness had read the file in advance, one might be enough. The number of turns depends on when the information arrives, not on some fixed constant of the agent.

Do not conflate: when the result is not filled back in, the model may ask to read it again. Check message assembly first, instead of putting every repeated call down to the model not being clever.

Worked example · Q001

Why one repair task produces three model calls

Input and conditions. The task is to change config.json timeout from 3 to 5, with the tools read, write and test. What follows is a fixed teaching trace, not a real model running on its own.

Steps and objectsInternal actionIntermediate result / new state
1 Call 1 inputThe user task + the descriptions of the available toolsThe model proposes read; it has not committed to the file having been changed.
2 Tool 1 resultRead version v7, timeout=3The result enters the history together with the call ID.
3 Call 2 inputThe task + the read call + the resultThe model proposes writing timeout=5 on top of v7.
4 Tool 2 resultThe write succeeds, giving v8The harness still has no proof that the functional test passed.
5 Call 3 inputThe new version, and the test returning passThe model sums up the change and the verification; if it also has to propose the test itself, that adds another turn.
6 Counting differenceThe user sees one taskThe back end may make several model requests and several tool operations.

Join the steps up. The output of one model call is not the whole life cycle of the task; which tools the model decides on and which the harness triggers automatically has to be stated clearly.

Limits and counterexamples. In this example the test is triggered by the harness on a fixed rule, which is why there are three calls; do not count it together with a configuration in which "every tool step needs another model proposal".

Basis and scope of use:[TOOLS]. The example input and setting are stated explicitly by this book.

Follow-up: why not read every file at once and have the model hand over the patch directly?

For a small repository that sometimes works, but for a large one it is expensive and brings in much irrelevant information. More importantly, the evidence the next step needs is usually decided by what the previous step found. Only once the entry point is found do you know which call chain to look at; only once the test is run do you know the real failure. Reading on demand uses feedback from the environment to reduce guessing; it is not there to inflate the number of call turns.

Follow-up: must an agent always have the LLM decide every step freely?

No. A preset workflow can fix key steps such as retrieval, verification and approval, while the LLM judges the uncertain parts. A dynamic agent lets the model choose the path, which is flexible but makes cost and behavior harder to predict. Real systems often mix the two: control should be allocated according to the uncertainty of the task, rather than turning deterministic programs into prompts as well.[AGENTS]

Follow-up: how do you tell whether a failure is a model problem or a harness problem?

First save this turn's visible input, the callable tools and the actual results. If the right file was not returned, it is a retrieval or tool-chain problem; if it was returned but then trimmed away, it is a context problem; if the model produced a valid call and the executor cannot find the tool, it is a registration or routing problem; only when all the necessary evidence was visible and the inference was still wrong does it come close to a model reasoning problem. The final error text by itself cannot locate the layer at fault.

Engineering mechanisms and failure boundaries

One answer has finished — so why is the task still not done?

Start with a task that reports completion falsely

The user asks to "fix the directory exclusion rule without modifying the production configuration". The model emits a patch and then says "done". All that can be confirmed at this point is that the model produced text. Whether the file changed, whether the test ran, whether the test was aimed at the last change, and whether the original constraint is satisfied are four different facts. Do not compress the four facts into one done=true.

In this section's teaching harness, four fields are recorded: response_complete means this model response has ended at the protocol level; call_complete means this tool call has a terminal state; effect_verified means the external state has been verified; goal_verified means the task's acceptance conditions are satisfied. The first does not entail the fourth. A user cancellation can also end a call while the goal is still not reached.

Read one loop through the pinned source

Codex's run_turn does not simply implement "the model returned text, so exit". It first takes in the input and the hook feedback, prepares this turn's context and tools, and then requests the model. Completed tool-call items go to the execution system; the result returns to the history, and only then does the next turn have new evidence. The sampled needs_follow_up must also be combined with the pending input; when it looks finished, the Stop hook may still give feedback that needs further work. What is described here is the path in the pinned commit; one product's stopping policy is not taken as the definition for every agent.[C01:run_turn]

"Response finished", "tool result available" and "task finished" should each keep their own timestamp. Suppose the response finished at 10:00:02 and the test process exited at 10:00:08: then 10:00:02 cannot declare the test passed. If another file edit happens at 10:00:09, the result from 10:00:08 only proves the old version and does not cover the new one.

A teaching trace you can check item by item

Moment The model side The harness and environment side What can be concluded
t0 Receives the task and the tool descriptions No file read yet Only the goal, no root-cause evidence
t1 Proposes read_file Validates the path, then reads exclude.py@r7 Analysis can be based on r7
t2 Proposes a patch Writes r8 successfully The code changed, which is not the same as correct
t3 Proposes a test Tests r8 and returns a failure Should continue from the failure rather than ignore it
t4 Corrects the patch Writes r9 and reruns the test A pass or a failure on r8 is no substitute for verifying r9
t5 Produces the final note Verifies the constraints, r9 and the test result Only now is there evidence that the task is complete

This does not force every task through six turns. A simple question may finish in one; a high-risk action may need human approval. Expand according to the actual unknowns and the risk, rather than treating a fixed number of turns as a quality standard.

Stopping conditions that are easy to miss

Calling the same search over and over with no added evidence is stalling, not steady progress. An unrecoverable tool failure should be recorded explicitly and isolated; endless retries should not block the rest of the work. A completion condition needs externally checkable evidence; the stopping conditions should also cover an exhausted budget, a user cancellation, missing authorization and a decision needed from the user. Stopping is not the same as success, and continuing is not the same as being effective.

The verified stopping branches: not a single done bit

In the pinned source, start with needs_follow_up and the pending input. Once the Stop check is entered, valid continuation feedback is written into the history and opens the following steps; a bare "block the ending" with no feedback content raises a warning instead of looping out of nothing. The internal path for memory consolidation fails separately when it meets a Stop rejection, so the rejection is not fed again and again into an unattended loop.[C01:run_turn]

When you use this in your own program, distinguish at least "no new work", "acceptance still to be added", "canceled" and "budget exhausted". These are teaching state names, not a copy of Codex's enum. A verifiable counterexample: if the stop check finds one test missing, it should return the test as the goal; if it only ever returns "keep trying", the harness should exhaust a finite budget and report the task unfinished rather than recurse forever.

Q002｜What states does an agent have? Why can a conversation summary not replace the task database?

What to know first for this question The task goal, the call progress, the external facts and the message history are different states; one summary cannot automatically replace every state record.
Lesson 02 · State, events and checkpointsLesson 26 · Retries, idempotence and transactions

Core answer

At least three kinds: the cognitive context the model can see, the harness's control state, and the actual state of the external environment. They can be inconsistent for a while. A summary expresses "what is believed to have happened", the task record expresses "what the system tracked", and files, databases and remote services are where the side effects actually happen.

Take one commit as the example and separate the states

The model says "I am about to modify filter.py": that is a plan. The harness creates call c17 and records it as pending: that is control state. The tool completes the write to disk and the file content changes: that is environment state. Then the process crashes before the success is written back to the task database: the environment succeeded, the control state is still pending, and the model has not yet seen the result.

If recovery reads only the conversation summary "the edit did not finish", it will write again; if it reads only pending and treats that as failure, it may also repeat the side effect. Check the action identity, the expected old version, the content after the write, or the remote idempotent result, and restore the state to succeeded or to still unknown. The model must not decide this by tone.

Thread, turn, session: the levels of a run
These are usually the harness's divisions of a conversation and of units of work, not layers of a neural network. A thread can mean one conversation, and a turn can contain the several model and tool cycles needed to answer one user task; where the boundaries fall depends on the product."This turn is done" cannot be equated with "every external tool has finished"; that takes looking at the actual events and results.

This does not require every project to add six tables. A simple local agent can do it with logs and files; the point is not to blend these meanings into a single "done".

Start with the objects and symbols used here
checkpoint: you must look at the object that was saved
A model checkpoint saves weights or training state; activation checkpointing saves a few intermediate nodes so they can be recomputed on the backward pass; an agent task checkpoint saves how far execution has got. The three share a name, but what they restore is entirely different. When you see "checkpoint", first ask whether it restores parameters, recomputes activations, or continues a task. Engineering mechanisms and failure boundaries

Why does every model call need a consistent context snapshot?

Start from an "input inventory"

A model call needs more than one sentence from the user: it also needs the rules, the history, the tool declarations, information about the environment, and evidence. Call this list request snapshot S7: the model choice, rule version R3, tool catalog T8, environment E2, and the evidence file@hash. A snapshot does not freeze the whole system; it makes the objects this decision rests on line up with one another.

Suppose that in S7 the model saw the tool write_file(path,content), but after it had emitted the arguments the harness moved to S8, where a tool of the same name is interpreted as a different interface. If the executor only looks up "the latest tool" by name, an old decision can land on new semantics. This problem is called a change between check and use; do not memorize the acronym yet, just remember that "what was seen when the decision was made" and "what is used when it is actually executed" may not be the same thing.

Which objects Codex binds together

The pinned source's StepContext holds the per-request settings, the environment snapshot, the MCP bindings, the tool router and a snapshot of the loaded rules. The tools published by the sampling request and the dispatch of the calls that follow both use this context, which reduces mismatches inside one request.[C02:StepContext] run_turn can capture the context again on a later sampling, so the next call can see the change instead of never refreshing once the session has begun.[C01:capture_step_context_with_required_mcp_servers]

This does not mean authorization is frozen forever. The environment access in that structure also combines the information currently granted. Revoked permissions, approval before execution and a tool's own argument limits still have to be checked before a side effect actually happens. A consistent snapshot guarantees a consistent interpretation; it does not grant permission to act.

An instruction cache needs expiry conditions too

AgentsMdManager serializes refreshes; when discovering rules requires reading a provider, it does not hold the state mutex across that external read. When trust or permissions are tightened, the old cache must expire: a failed new read is no reason to go on using the more permissive old result. A sub-agent inherits certain already-applied snapshots; whether the providers are shared still depends on explicit configuration.[C10]

Why an empty tool list in the log does not necessarily mean there were no tools

In one incremental tool-protocol path in the pinned Codex code, the standalone request fields may not resend the tools and the base instructions, because that information has already been passed on through the history or an incremental declaration. When reviewing, read the protocol in use and the final sequence; seeing one tools=[] is no ground for asserting that the model received no tools at all.[C01:build_prompt]

A teaching debug table records at least: the request ID, the model version, the rule hash, the tool declaration version, the environment identifier, the evidence version and the authorization result at execution time. Do not record secrets, and do not keep all user content unconditionally. Attribution is reasonably safe only when a single thing changed; once the model, the prompt and the tools are all swapped at once, there is no way to know which caused the regression.

Q004｜When should an agent stop? Why does "continue until done" so easily turn into an infinite loop?

What to know first for this question Ending has to be checked against observable acceptance conditions; no more tool calls, an exhausted budget, or the model saying it is done — none of these alone proves the goal was reached.
Lesson 02 · State, events and checkpointsLesson 04 · Foundations of engineering qualityLesson 05 · The denominator of an evaluation metric

Core answer

Stopping needs the model's judgment together with verifiable conditions. The model can propose that it is done, blocked or in need of clarification, and the harness still has to check the result evidence, the outstanding actions and the budget. With no clear definition of completion, the loop may search again and again, rewrite the plan, or run the same failing operation.

Use a completion predicate instead of a gut feeling

A teaching task can define: the target test passes; the new boundary test passes; the current diff contains only what was authorized; the verification matches the current code version; and there is no unknown write operation. Meeting these does not prove the software is absolutely free of defects, but it does define clearly what this task's delivery rests on.

The loop should also distinguish "no new evidence" from "the task is still making progress". Reading the same file for three turns in a row with no new hypothesis, the same arguments failing again and again, a patch flipping back and forth between two ways of writing it — all of these are signs that progress has stalled. You can reduce the freedom of action and require the next operation to state what it expects to test, or to output the reason it is blocked.

A budget covers at least wall-clock time, the number of calls, tokens, tool costs and risk. Reaching the budget should not be dressed up as completion; what is finished and what is not should be saved, with accurate evidence. In a long task, delivering what is partly finished and separating the remaining problems clearly is more dependable than an endless "let me review it once more".

The model finishing, the tool finishing and the task completing: three kinds of "done" cannot share one boolean

Prerequisite: Lesson 01 · Lesson 02 · Lesson 26. Reading order: confirm the run contract first, then look at the counterexamples and the fix, and finally test the limits.

First define the three endpoints

One model response finishing only says that this generation reached some terminal state; a tool returning success only proves that an action or a check within its contract succeeded; completing the task further requires the user's goal and the acceptance conditions to be met. A tool call may be the request for the next step inside a model response, not the final delivery.[TOOLS]

Take model_done=True and writing it straight as task_done=True mistakes "proposing to run the test" for "the test passed". Treating HTTP success as business success is just as dangerous: a service can report a business failure in a perfectly normal protocol response.

Asynchrony lets an old result contaminate a new task

A teaching state: the user originally asked for a.py to be fixed and the agent had already started a slow test; the user then switched to b.py, and the task epoch went from 1 to 2. The old test arrives late and returns a.py@epoch1: passed. If the harness updates the current task on "the most recently arrived test succeeded" alone, it will mark b.py done.

The epoch is a task revision count designed by this book, not a field required by any vendor. When a result arrives, check task_id, epoch, the target version, call_id and the expected operation; an old result can be kept as historical evidence, but it must not change the completion state of the new goal. This book's state experiment verifies that a mismatched epoch is refused for merging.

A stopping condition should state the reason

Record them separately: the goal is met, the budget is exhausted, the user canceled, waiting for an external result, blocked on permission, the model response is incomplete, the tool failed, or the result is unknown. Each points the user to a different next step. The budget includes cumulative calls, tokens, time and the number of side effects; retrying endlessly after one tool error should not be taken for "persisting until the task is done".

Unknown is not the same as failure. A timeout can happen after the external action has already succeeded; before retrying, verify, or use idempotence downstream. An AWS engineering article discusses the problem of timeouts and retry intent specifically.[IDEMP]

Follow-up: after the user cancels, can you report "nothing was changed" right away?

No. Canceling the control flow does not roll back external side effects by itself. First cancel the in-flight actions that can be canceled, query the operations already committed, and report to the user which parts are finished, which await verification and which never ran. If automatic compensation is riskier in itself, wait for authorization rather than treating "undo" as always safe.

Follow-up: when the model says there are no more tool calls, can you end right there?

That is only a candidate ending signal. Check the acceptance predicates: whether the test records for the final working-tree version are complete, whether any pending or unknown actions remain, whether the deliverable actually exists. Different tasks accept at different strengths; a simple question and answer should not be forced through a release transaction, but a write operation cannot rely on the model vouching for itself.
