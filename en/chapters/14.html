Prerequisites for this chapter

Compaction trades a long history for a short state, and usually loses information. Confirmed facts, hypotheses still awaiting verification, real side effects and the location of the original evidence have to be kept apart; a fluent summary must not be taken for an exact snapshot of the task.

Each question in this chapter lists the groundwork it needs. You can take the matching Foundations lesson first, or use the self-check to confirm how well you have it.

This chapter follows one long task and gives the whole process: before compaction, the candidate summary, verification and recovery. No published method can guarantee that one short summary keeps every detail some future question might need; the workable goal is to protect the key state for the task at hand and to keep the original evidence recoverable.

Q041｜What is the fundamental difference between compaction, truncation, prompt cache and external memory?

What to know first for this question A summary extracts state from the history, trimming simply removes fragments, and offloading puts the material where it can be read again; they lose and recover things in different ways.
Lesson 02 · State, events and checkpointsLesson 11 · Assembling contextLesson 22 · Compaction is not magic

Core answer

Truncation deletes part of the content outright; summary compaction rewrites the original content as a shorter representation, usually with loss; a dedicated compaction interface may produce an opaque, service-specific state; a prompt cache reuses computation without changing the logical input; external memory puts content outside the context, from where it has to be retrieved again. These five things cannot all be lumped together as "the model remembered".[COMPACT][CONTEXT]

Five outcomes for one and the same history

The long task already has 40 turns: 20 files read, 3 root causes ruled out, 2 files changed, tests run. The latest goal is to fill in the edge cases.

Truncating the first 30 turns outright can also delete the original constraint "do not change the public API". The summary keeps "exclude fixed, tests passed", which looks tidy but loses which version the tests belong to, which tests they were, whether any were skipped, and one remote action that is still unconfirmed. Offloading the full log keeps only a path, which can be recovered, but the model's next step has to know when to read which part of it. A cache may make the computation over the 40 turns of original text cheaper, yet that text still occupies logical context and attention-processing room.

How to read the changes in the figure

Start by asking "does the next turn's logical input change". A cache usually reuses computation, while compaction and truncation change directly what the model is able to read.

What a summary keeps is a restatement; what a citation of the original keeps is the ability to get back to the evidence. The two complement each other, but when a citation goes dead one cannot pretend the summary holds every detail.

The most critical constraints and the unfinished actions should be stored separately in structured form, rather than existing only inside one long block of summary.

Do not conflate: calling compaction a "lossless cache" leaves the reader thinking that every detail can still be recovered automatically inside the model.

Follow-up: is an opaque compaction block necessarily more reliable than a text summary?

Being unreadable settles nothing on its own. A dedicated state may suit the model's further processing better, and it may carry product-specific information, but the quality of the following task still has to be tested. Unreadable means that human inspection works differently; it does not mean lossless in the mathematical sense. Keep the key state and evidence on the application side; do not entrust everything to a representation you cannot see.

Follow-up: is compacting the history to 10% of its original size enough?

The compaction ratio is only a measure of length. Dropping 90% of repetitive logs may do no harm, while dropping the one line "deleting the database is not allowed" may be serious. Define what fidelity applies to, and the risks, before tuning the ratio. No fixed proportion is a universally correct target.

Follow-up: after compaction, can the model still recall details that were not saved?

It may guess from the context and from what it learned in training, but a guess must not be counted as recovery. If the original evidence is still there, a tool can read it again; if it has been deleted and compaction did not keep it, there is no dependable basis. In engineering terms, state "unknown" rather than let the model fill in a plausible-sounding history.

Engineering deep dive · E27 · continues Q053

Why can the result of compaction not keep only the item that "looks most condensed"?

Prerequisite: Lesson 02 · Lesson 22. Reading order: confirm the run contract first, then look at the counterexamples and the fix, and finally test the limits.

What the compaction interface returns is a new context contract

The OpenAI compaction guide read for this section describes a canonical output window: the result of compaction may contain both retained input items and an opaque compaction item, and it should be passed on whole, as the interface requires. Picking out encrypted_content alone and discarding the other items breaks the meaning of the returned window.[COMPACT]

The teaching counterexample has two output items: the user message "do not publish" and an opaque compaction item. Keeping only the last of them gives no ground to infer that "do not publish" has been encoded into it again; the caller cannot guess at black-box content. Use the complete window the service returns as input data, and resend the stable control fields you need separately, instead of inventing your own shortest way of splicing things together.[RESP]

Keep the summary and the execution log separately

The task contains the question "has calling c7 already produced a side effect", and it is the execution log that should record states such as pending/running/unknown/succeeded. A model summary can aid understanding, but it must not become the only truth about an external transaction. A summary that says "done" must not override the executor's unknown; a summary that drops "publishing is forbidden" must not remove the permission restriction either.

Three storage layers show up here: the original evidence stays traceable, the model context can be compacted, and the execution-control state needs deterministic persistence. This does not require a database for every question and answer; it requires the three to be kept apart whenever a task has irreversible side effects.

Why negative facts are especially easy to lose

"the tests were not run", "authorization has not been granted", "not the root cause" and "do not modify the public API" are all states that decide what happens next. A compaction test that asks only for the final conclusion misses them. List the propositions to be kept in a three-valued true/false/unknown table and check it after compaction; unknown must not silently become false, nor attempted become done.

Follow-up: is a higher compaction ratio always better?

The shorter it gets, the more potential detail is usually lost. The right metrics include whether key constraints survive, the cost of looking the evidence up again, the success rate of the following task, repeated work and the total cost of calls; the compaction call itself also costs something. Watching only the drop in tokens rewards throwing too much away.

Follow-up: once the new context is in hand, should the old window be deleted right away?

Follow the product's retention policy, but do not discard the only piece of evidence while it cannot be verified or recovered. The full history can be moved to controlled external storage with only the necessary index put back into the model; the retention of sensitive content, the permissions on it and its deletion at expiry carry constraints of their own. Keeping all data indefinitely in the name of "recoverability" is not acceptable.

Engineering mechanisms and failure boundaries

A tool result arrives while the summary is being generated asynchronously — how is data kept from being lost?

Use the history numbers to see the race condition

The teaching history starts out as [e1,e2,e3]. A background job takes this prefix and generates summary S. While it is being generated, a new tool result e4 and a user addition e5 are already written into the live history. Replacing the whole list with S outright makes e4 and e5 disappear. The correct target is a verified [S,e4,e5], not a blind replacement.

Nor may the suffix be appended unconditionally. Suppose a rollback happened in the meantime: e2 has been undone while the old summary S still carries e2's conclusion, and S should then be invalidated. Append-only and destructive rewrite have to be told apart, and the candidate has to be checked against the history version, the model, the compaction configuration and the authorized identity it was generated from.

Key boundaries in the pinned Codex source

Asynchronous compaction is enabled only for particular feature combinations and provider paths; it is not uniform behavior across all sessions. The routing, history and budget conditions are checked before it starts, and the candidate is tied to a history version, a model identifier, a compaction hash and an authorized-owner generation.[C06] The install stage also checks the model and the compaction hash; then, inside the lock in replace_compacted_history it checks the history-rewrite generation, the prefix length and the authorized-owner generation, and keeps the live suffix as it stands at that moment. If the window is still over budget after the install, processing may continue in the foreground; the suffix is not dropped blindly.[C07][C16:replace_compacted_history]

Canceling this turn does not necessarily cancel a session-level compaction started earlier. The pinned test separates "no new task is started after a cancellation" from "work already started may still finish and be reused". That is only this path's choice of lifecycle; it cannot be generalized into all background tasks ignoring cancellation.[C06][C18]

Why the failure path has to be billed too

A candidate may end up unused while the generation request has already consumed computation. Shutting down means canceling and winding up, and it also means dealing with usage already reported. Counting only "summaries that were installed successfully" underestimates the cost of the system.

A summary is not an execution log

What has to be kept: the task goal, the forbidden actions, the confirmed versions and conclusions, the hypotheses not yet confirmed, the unfinished tools, the reasons for failure, the next step and the location of the evidence. Compacting "the production configuration must not be changed" into "the configuration may be changed", or "the tests have not been run yet" into "the tests are done", changes what happens next. Complete summary fields are no proof of complete meaning; design counterexamples for negation, ordering, conditions and versions.

The merge experiment in this book verifies only the teaching history structure and the invalidation check; it does not simulate a proprietary remote compaction result. Some services return an unreadable state, and that must not be described as lossless compaction from which all the original text can be recovered.

A successful install has one more persistence boundary that is often missed

Q042｜In what order should one safe compaction run? Why avoid replacing while execution is still going on?

What to know first for this question Build the candidate compaction state first, then verify it and switch over, so that you never have half an old history and half a new summary. The record of external actions should be checked independently.
Lesson 02 · State, events and checkpointsLesson 22 · Compaction is not magicLesson 26 · Retries, idempotence and transactions

Core answer

Fix a consistent history/state snapshot first, then produce a compaction candidate, verify the key invariants, build the new context and switch over; if verification fails, keep the old state or roll back. Compaction is not a matter of calling a summarizing model and overwriting a string. Codex's pinned source snapshot shows one concrete path for rebuilding and replacing the history, but the transactional checks in this section are a general teaching design.[CODEX-SRC]

The seven-step process, and what failure at each step costs

  1. Choose the boundary. Compact when the tool calls have finished and the goal of the stage is clear, if you can. If an action is still running/unknown, its state has to be carried over explicitly and must not vanish.
  2. Freeze a snapshot. Record the history version v and the current task version. If new messages arrive during compaction, either queue them or merge them again before the switch; otherwise a new constraint from the user gets overwritten.
  3. Extract the key objects. The goal, the negative constraints, the verified facts, the citations of evidence, the completed actions, the open questions and the next step. The key objects can come from structured state; they need not rest entirely on the model's recollection.
  4. Generate the candidate. Require that unconfirmed hypotheses are not promoted into facts, and that sources and versions are kept. With a dedicated API, follow its input/output state contract.
  5. Check the invariants. Are the key IDs and constraints present, is an unknown action still unknown, are the evidence versions consistent, has a negation been lost.
  6. Rebuild the context. Put back the fixed instructions you need, the tool definitions, the current environment and the candidate compaction state; avoid duplication, and avoid raising permissions by mistake.
  7. Switch conditionally. Switch only while the original snapshot version is still valid, and save the index of the old records together with the compaction version. A failed compaction must not empty a valid history.

These seven steps do not mean that every chat tool needs a complex database. A short task may not compact at all; a lightweight implementation can use a write-once new file and an atomic rename; stronger version conditions are needed only once concurrency and long-running tasks are involved.

Start with the objects and symbols used here
call_id,item_id,request_id
These are identifiers for objects at different layers: a tool call, an output item, a request or a response. They match increments and results back to the right object; they are not the token IDs of the model input, and they are not business idempotency keys by nature. Two read_file calls can carry c1 and c2; when the results come back in the reverse order they are still paired by call identifier, not guessed by tool name.

Follow-up: when is the best moment to trigger compaction?

Weigh the remaining window, the expected next tool result, the stage boundaries, how relevant the history still is, and what the cache gains or loses. Triggering only at 100% of the window is too late, because the compaction call itself also has to process the history; too early wastes cost or drops a detail that was about to be used. A threshold is a safety line, not the only signal.

Follow-up: what if the compaction call itself exceeds the limit?

You can first clear out verbose tool output that is clearly recoverable, extract the key state chunk by chunk, or use a supported server-side mechanism. Deleting the earliest content without checking is not an option, because the earliest may hold a fundamental constraint. A product may have its own degradation path; when studying source code, read its error branches rather than assume that compaction always succeeds.

Follow-up: why can repeated summarizing drift away from the truth?

A later round usually takes the earlier summary as input, so once an early uncertainty or detail is lost, it can be carried on as a settled, simplified conclusion and reinforced. The remedy is not an ever longer summary but traceable evidence, a stable table of facts and a periodic check against the original text; for an important conclusion, avoid citing only "the previous summary".

Look at the timeline first: the problem is not the summary's prose

If t4 overwrites version 11, the tool result that has just arrived disappears. On its next turn the model may repeat the operation, and even produce the side effect a second time. This race is a counterexample constructed by this book from the design of concurrent state; it is not a claim that the accident happened in some commercial compaction service.

An atomic replacement is still not enough

Replacing the whole file with one rename only guarantees that no reader sees half the content; it does not guarantee that the basis for the replacement is still fresh. At commit time, "which history version the summary is based on" has to be compared. In the local experiment snapshot=10 and current=11, so the CAS (compare-and-swap) condition fails and the stale summary is refused.

One workable design treats compaction as producing a "new base": read an immutable prefix snapshot, form the summary in the background, and at commit time either confirm that the version is unchanged or splice on the tail of events that came after the snapshot, correctly. The splice has to keep the call/result dependencies; it cannot cut by message count alone. If the tail changes a key conclusion in the summary, the summary can be abandoned and recomputed.

The control state should stay consistent ahead of the model history

The execution log records that c7 has finished, so if the update to the model history fails, the system can still rebuild from the log. That is safer than trusting a pending state in the summary. A database transaction can protect the version pointer and the event commit inside the same database, but it does not automatically coordinate side effects in external files or in a model service.[SQLITE] The compaction interface itself supplies context output; it should not be misused as the whole task state machine.[COMPACT]

Follow-up: a global lock that waits for the summary is the simplest thing; why is it not always done?

It does avoid some races, but it can block tool results, user cancellations and the progress of a long task, and it raises tail latency. For a short flow it is acceptable; a long call suits a snapshot plus a version check better. Choose on the basis of the task's concurrency and recovery needs, not to force in a complex event system for the sake of an "advanced architecture".

Follow-up: repeated compaction drifts over time — how is that tested?

Construct a fixed history that contains counterexamples, negations, constraints and unknown states, compact it several times over and check the table of propositions; also carry on with a small task that depends on the old evidence. High text similarity is no proof that the state is faithful, and conversely a change of wording does not necessarily lose information. Pin each failure down to a proposition and a source event.

Q043｜How is the original evidence found again after compaction? How do the summary and external storage work together?

What to know first for this question A citation of evidence has to be able to locate both the original text and its version. A summary of content that carries no qualifying conditions and no record of what was withdrawn turns an old hypothesis into a new fact.
Lesson 22 · Compaction is not magicLesson 18 · Code is not an ordinary documentLesson 23 · Foundations of long-term memory

Core answer

A summary should keep enough locating information, and the conditions that trigger a read; external storage keeps the original evidence and its version. Recovery means reading the matching record again and checking whether it still applies, not letting the model expand on the summary. A citation has to be resolvable, authorizable and verifiable.

Follow one citation of evidence all the way down

The summary says E12=filter.py@r42:60-95. When the next step is to edit the current r44, the model must not treat r42 as the current code. Harness, or the tool, should read the matching region of r44 and check whether the relevant logic has changed; the r42 evidence can still explain the historical root cause, but the patch has to target the current version.

A log citation needs its range and its meaning too. For example L8: command=pytest test_config_load, revision=r42, exit=0, not just/tmp/log.txt. A temporary file may already have been cleaned up, and a path may have been overwritten. For a long-running task, important logs should live in storage with an explicit lifecycle, or a small enough copy of the key output should be kept.

A recovery can be triggered by a concrete question: about to modify a function that was discussed earlier, finding the current summary at odds with the source, needing to state publicly that a test passed, reconsidering an option already ruled out. Without such a trigger there is no need to read the whole history back in, or the gain from compaction is canceled out.

Follow-up: does a citation always need to include a hash?

No. A version number, an immutable object ID, or a controlled repository commit is often enough already. A hash is valuable for identifying exact content, but not every statement needs a signature, a chain of checksums and a complex structure added to it. Let "would a change in the content lead to a wrong action" decide how strong the verification should be; a hash is also no proof that the content itself is correct.

Follow-up: does the original evidence have to be kept forever?

Not necessarily. How long it is kept has to do with reproduction, compliance, privacy and cost. Short-lived noise can be cleared out early; key decisions, irreversible actions and the basis of long-term experience deserve suitable retention. Before deleting, invalidate or migrate the citations that depend on it, rather than leave behind a dead link that still looks usable.

Follow-up: with RAG in place, can the task summary be skipped?

RAG is good at finding content for a question, but it does not necessarily know the current progress, which actions have been carried out, or which results are unknown. A task summary provides the control view of "what should be done now"; retrieval provides the evidence view of "where to look when it is needed". The two complement each other, and semantic retrieval cannot replace a log of side effects.

Q044｜How is compaction fidelity evaluated? Why is comparing the summary with the original text for similarity not enough?

What to know first for this question The quality of compaction is not one number, the ratio. Check which constraints survive, whether the facts are accurate, whether the to-dos can be recovered and how execution continues afterwards, and keep a simulated check apart from the effect on a real model.
Lesson 22 · Compaction is not magicLesson 05 · The denominator of an evaluation metricLesson 31 · Do not be fooled by a few percent

Core answer

Compaction should be evaluated on whether the key facts and constraints survive, on errors newly introduced, on the consistency of the state, and on execution really continuing after compaction. Similarity of wording does not mean that the information needed for action is kept; a very short but accurate state table may be more dependable than a long retelling.

Build a check task that can be reproduced

Prepare a set of questions before compaction whose answers the history fixes: which API must not be modified? Which hypothesis has been ruled out? What version is the current file? Did the tests pass, fail, or not run? Which remote action has an unknown result? Tie every question to its evidence, so that the judge does not score from impressions.

After compaction, let the system answer and take the next step using the new state alone. The check cannot rest on "the keyword is still there":不需要回滚and需要回滚both contain "rollback"; "the tests have passed" and "the tests have not passed yet" look alike on the surface and mean the opposite. Negation, conditions, quantities, ordering and the identity of resources all have to be checked.

Use at least three experiment groups: the full history, an unprotected summary, and a summary with structured state and citations of evidence. Under the same task and the same budget, compare the rate at which the work is completed afterwards, repeated operations, violations of key constraints, Token, and time. Run it several times to observe the randomness; results for a real commercial model can only be reported by actually calling it, and this package offers only the method and deterministic counterexamples — it does not fabricate win rates of that kind.

Follow-up: how is overfitting the summary to known check questions avoided?

Hold back some follow-up questions that took no part in designing the summary, and add constraints from different tasks and different positions; use real continued execution rather than only answers to fixed questions. Known check questions can serve as a floor, but they cannot prove that nothing is lost for every future question.

Follow-up: when is it better to keep the longer context?

While fine-grained code changes are under way, when several original fragments have to be compared, or when details will be checked over and over in the short term, keeping the original text may beat a summary. When a task is about to end, an extra compaction call may also gain nothing. Compaction is a means, not a rite that every long conversation has to perform.

Follow-up: can a strict standard for "lossless compaction" be given?

If the requirement is that all the information in the original can be recovered for any future query, a short summary generally cannot guarantee it. It is more practical to define a set of task-relevant invariants and the sources that can be recovered, and to state how well they survive those checks. A strict boundary is worth more in engineering than a vague promise to "keep all the important information".
