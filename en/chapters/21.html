Prerequisites for this chapter

Retrying a request deals with an unstable network, but the external action may already have happened. An idempotency key identifies the same business action; a transaction guarantees certain atomic properties for a group of changes; neither of them covers every external system out of thin air.

Each question in this chapter lists the groundwork it needs. You can take the matching Foundations lesson first, or use the self-check to confirm how well you have it.

A quick check before the deep reading: list the three states "not executed yet", "executed and a receipt received" and "possibly executed with no receipt received", and then decide for each whether it may be retried.

A term with a dotted underline can be clicked for a quick reference. Read the definition of a letter in a formula first; do not let a guessed abbreviation stand in for the derivation.

The more an LLM can execute on its own, the more "it suggests trying again" has to be told apart from "executing again is safe". This chapter follows the failure window of one write operation, and does not treat a model's self-reflection as a transaction mechanism.

Q049｜Why must there be an unknown state after a tool times out? Why not mark it failed straight away?

What to know first for this question An unknown result calls for checking the facts first; a retry of the same business action uses a stable identifier, and generating a new key each time to look idempotent will not do.
Lesson 07 · APIs and streaming protocolsLesson 02 · State, events and checkpointsLesson 26 · Retries, idempotence and transactions

Core answer

A timeout means only that the caller did not get a definite result within the deadline; it is no proof that the side effect did not happen. unknown means the result of execution cannot be confirmed yet; it stops the system from wrongly equating "no success seen" with "safe to redo".[IDEMPOTENT]

Five moments in the creation of one ticket

T1: the client records that it is about to create, with the business action ID a17. T2: the request reaches the server. T3: the server writes the ticket into the database. T4: the success response is lost in the network. T5: the client times out.

If the client now marks it failed and retries with a new ID, the server creates a second ticket. The model seeing two results and then deleting one is not necessarily equivalent either: a notification, an audit entry or an external sync may already have happened. Correct recovery queries or retries under the same idempotent identity, or checks the existing result against a business uniqueness condition; where it cannot be settled, it stays unknown and asks for appropriate handling by a person.

By contrast, if the request fails at the local argument-validation stage, no side effect was executed, and the arguments can usually be adjusted and tried again. Where the failure happened decides how to recover, so the error structure should carry the execution stage that is known, instead of one string "error".

The place where a timeout appears is between "request" and "response"

Conditions for this example: an independent message-sending example: the business operation op-7 reaches the remote side, which commits it, but the success response is lost in the network. The message service in the figure is a teaching assumption, not a real send.

How to read the changes in the figure

Look at the second row: the remote side succeeding and the local side knowing it succeeded are two different things. The network can cut between them.

Writing unknown down as failed and sending it again produces a second message on a service that does not support idempotence.

How you recover depends on what the remote side can do: query by business key, retry idempotently with the same key, or reconcile by hand. A longer summary cannot close this information gap.

Do not conflate: limiting the client to one retry limits how often it repeats; it does not guarantee exactly once in principle.

Worked example · Q049

The request timed out but the counter has already gone up by 1: what state is that

Input and conditions. An external counter starts at 10. Operation op7 asks for 1 to be added, the server takes it to 11, and the success response is lost in the network.

Steps and objectsInternal actionIntermediate result / new state
1 What the client observesWait times outIt proves only that no usable response arrived in time.
2 The external factThe counter is already 11That is no reason to mark it "not executed".
3 The safe stateRecord op7=unknownKeep the operation's identity, the content of the request and the way to check it.
4 Recovery by queryLook up the external operation record by op7If 11 is found to have succeeded, move to succeeded; if it clearly was not committed, it may be retried by the rules.
5 A dangerous retrySwitching to a new ID op8 and adding 1 againThe counter reaches 12 and the duplicated side effect appears.

Join the steps up. Success, failure, in progress and result unknown have to be distinguished; a timeout is an observation about communication, not a fact about execution.

Limits and counterexamples. Where the external system offers no operation lookup and no idempotency, checking by hand may be the only option; an internal log cannot guarantee exactly once on its own.

Basis and scope of use:[DERIVE]. The example input and setting are stated explicitly by this book.

Follow-up: can every read-only query be retried without thinking?

A read is usually low-risk, but there is still billing, rate limiting and change over time; some nominal queries trigger a cache refresh or a background task. A retry should have a deadline and backoff, and should keep the context of the same logical query as far as possible. Do not let an infrastructure failure consume LLM turns without end.

Follow-up: the model says "I checked and it was not created" — does that clear the unknown?

There is evidence only if it really called a trustworthy query and the query's scope was wide enough to confirm. A promise in natural language is no substitute for checking the remote state. Watch out for eventual consistency as well: an object just created may not be found for a while, which is no reason to create it again straight away.

Follow-up: does an unknown state make the system too conservative?

It should be used only at a side-effect boundary that genuinely is uncertain. A low-risk, repeatable computation needs no elaborate handling; an irreversible or expensive write deserves care. An explicit unknown is more precise than forbidding every retry, and safer than retrying blind.

Q050｜How is an idempotency key designed? Why can a local deduplication table not guarantee Exactly Once across systems?

What to know first for this question CAS compares the version before updating; replacing a file atomically covers only the switch of files, and does not roll back an external database or a network side effect along with it.
Lesson 18 · Code is not an ordinary documentLesson 26 · Retries, idempotence and transactions

Core answer

An idempotency key identifies one business intent, so that a repeated request returns the same single result or is rejected as a conflict. What matters is whether the deduplication record and the actual side effect sit inside the same boundary where consistency can be guaranteed. Writing one local line saying "done" does not remove the crash window between the remote side effect and the record.[IDEMPOTENT]

Look at two wrong orderings

Write the local done first and then call the remote side: if the crash comes after done is written, the remote side never executed at all, yet recovery skips it, and the operation is lost. Call the remote side first and then write done: if the crash comes after the remote side succeeded, there is no local done, recovery retries, and the operation happens twice. Whatever the order, a gap remains across two independent systems.

If the remote side supports idempotency keys natively, the client makes its request with a stable key, and the remote side saves the key, the request's semantics and the result inside its own transaction boundary, so a duplicate can be handled safely. The same key with different arguments should be recognized as a conflict, and the old result must not be returned quietly. A key also needs a scope, a retention time and an expiry policy, so that different users or different business intents do not collide.

Start with the objects and symbols used here
Outbox, saga and compensation
The outbox persists the business change together with the message waiting to be sent, and a dispatcher forwards it afterwards; a saga organizes the steps across services into a compensable flow. They are designs for reliability across a boundary, not a natural guarantee that the remote side executes exactly once. An email already sent usually cannot make the recipient "not have read it". Compensation may be sending a correction notice, which is not the same as really undoing an effect in the past.

A local transaction can atomically write the business data and the outbox event, and a worker process sends it afterwards; the sending itself can still happen twice, so the receiver often needs deduplication or idempotent handling. So-called exactly-once usually holds only inside a clearly defined processing boundary, failure model and retention policy; it is not a free end-to-end guarantee across the whole internet.

An idempotency key is bound to one business intent, not to each HTTP attempt

How to read the changes in the figure

A local table can record "I sent it", but if the crash falls after the remote side commits and before the local entry is written, the local side still does not know. The downstream has to support deduplication by the same key, or results that can be verified.

Besides the key, the request parameters should be bound in as well; the same key with a different amount must not silently reuse the old result. The retention period and the conflict behavior belong in the contract.

"Exactly once" can usually only be spoken of within clear transaction and deduplication boundaries; it cannot be extrapolated from one local SQLite table to any external system.

Do not conflate: using the order number as the unique key is too coarse and wrongly merges several legitimate operations on the same order; a random number per request is too fine.

Worked example · Q050

Why an idempotency key also has to be bound to the arguments and the result

Input and conditions. The service supports the request key k7; the first time, the arguments are account u7 plus 10, and the resulting balance is 110.

Steps and objectsInternal actionIntermediate result / new state

2 Retry with the same key and the same argumentsk7 and plus 10 are submitted againThe existing result 110 is returned, and it does not go on to 120.

Join the steps up. Idempotency is a contract made up of the operation's identity, consistency of the arguments, persistence of the result and the retention policy together.

Limits and counterexamples. The balance is a teaching state and no real financial operation is carried out; an exactly-once effect has to state the transaction boundary and the boundary of the external system.

Basis and scope of use:[SQLITE]. The example input and setting are stated explicitly by this book.

Follow-up: can an idempotency key be a hash of all the arguments?

Sometimes it can serve as an identity for the content, but the same arguments may stand for two legitimate, independent intents, such as two payments of the same amount; and on a retry a change in some irrelevant field can give a different hash. It is safer for the application to generate a logical operation ID and bind the key arguments to that ID. A hash is not a substitute for business intent.

Follow-up: is it all right for the model to generate a new UUID every time?

If this is a retry of the same operation, a new UUID gets around the deduplication. The action's identity should be generated by the Harness when the intent is first settled, and kept persistently so that later retries reuse it; the model may propose an action, but it should not rebuild an idempotent identity at will.

Follow-up: is a compensating operation the same as a rollback?

Not quite. A refund, an unpublish or the deletion of a duplicate ticket may not undo a notification already sent or an observation made outside. Compensation is a new business action, with its own permission, failure and audit needs. Do not treat "compensate if something goes wrong" as a reason to execute repeatedly without constraint.

Engineering deep dive · E41 · continues Q082

The external action succeeded but the log never got to confirm it: why can a local transaction not guarantee exactly-once execution?

Prerequisite: Lesson 02 · Lesson 26. Reading order: confirm the run contract first, then look at the counterexamples and the fix, and finally test the limits.

Start by drawing the two persistent systems

The executor's log is in a local database and the real side effect is in a downstream service. These are two commit boundaries. Putting the log inside a SQLite transaction controls only the log's own commit; it cannot control the external action atomically. SQLite's transaction scope does not take in arbitrary file writes or network calls.[SQLITE]

The critical failure window is as follows:

日志：job7=pending
→ 下游动作提交成功
→ 进程崩溃（尚未把日志改为done）
→ 重启看到job7仍pending
→ 直接再执行一次

From the log it reads as "never completed", from downstream as "completed once". What a timeout or a crash produces is unknown, which is not failure.

This book really ran this window

The experiment starts a separate child process and uses two local SQLite databases that share no transaction to stand in for the log and the downstream side. After the downstream commit it runs os._exit(17), deliberately skipping the confirmation; it then restarts and recovers. The path with no idempotency key produces 2 side effects; the path where the downstream side puts a uniqueness constraint on a stable intent key produces only 1.

This result comes from a real process and database experiment run here, not from an imagined description; but two local databases are not a production distributed service, and nothing in it supports a claim that a networked system already has end-to-end exactly-once.

An idempotency key has to be consumed atomically by the side that really produces the side effect

If "I have used this key" is recorded only in the executor's log, there is still a window between the check and the downstream commit. The ideal downstream interface takes the intent key, the validation of the arguments and the side effect into its own atomic boundary, and returns a result consistent with the operation already executed. AWS's engineering article stresses the difference between the caller's intent, a retry, a late-arriving request, and the same key with a different intent.[IDEMP]

If the downstream side does not support idempotency, verification can go through a query for a unique business record; where no unique identification is possible, all that is left is to keep it unknown and hand over to a person, with no promise that nothing is duplicated. An outbox can keep the local state and the pending event consistent, but whatever finally consumes the message still needs deduplication or idempotency.

Follow-up: is generating a new UUID on every retry not safer?

It does exactly the opposite: it dresses the same intent up as a new action. A stable key should cover one business intent and be carried over by retries; a new key is for when the user really starts a second action. "The same key with changed arguments" also has to be rejected, or duplication and modification get confused.

Follow-up: does idempotency mean returning exactly the same bytes every time?

No. In business terms the same result can carry a different request-tracing ID; but the response should state clearly that the operation has completed, which business object it belongs to, and what the current state is. Idempotency defines the semantics of the side effect, not merely equality of HTTP text.

Engineering mechanisms and failure boundaries

Written successfully but not confirmed: how a retry becomes a duplicated side effect

Start by keeping the two ledgers apart

Ledger one is the downstream world: the file has been replaced, the email has been sent. Ledger two is the agent's own execution log, for instance call=c7, state=succeeded. The two are usually not inside the same transaction. When the crash comes after the downstream commit succeeds and before the agent's log is updated, recovery knows only that "there is no record of success", not that "there was no successful action".

Split the state out explicitly into proposed → admitted → running → succeeded/failed/unknown. unknown does not mean it must have failed, and does not mean success may be declared. It means that it has to be checked, that an idempotency mechanism has to be used, or that a human decision has to be asked for.

What one retry key should stand for

In the teaching example the operation key K is decided by the logical identity of the action, not generated as a UUID for each network attempt. A retry uses the same K, and only when the downstream side checks inside one transaction whether K has been handled and saves the result can deduplication be reliable. Saving "I remember doing it" locally in the agent does not cover the window where the local side crashes after the downstream commit.

Crash point The downstream fact Log Recovery action
Before admission Not executed proposed It can be started after revalidation

A subtle distinction in file operations

Atomic replacement keeps a reader from seeing half a file, but it does not prevent overwriting someone else's update by itself. Read r7, build a patch, have someone else write r8 in the meantime, then replace atomically, and r8 can still be overwritten. Use a coordinated version check and replacement, or storage that supports conditional updates. Computing a hash before the check and then writing without a lock still leaves a race.

A retry has a budget too

Three retries in the HTTP client, three in the tool layer and three more in the agent can produce 27 attempts in the worst case, not 3. Tell a transient failure, a permanent argument error, a permission denial and an unknown result apart; share one total budget, back off, and keep the original error. Do not write "keep going until it succeeds" as a loop with no terminal state.

The local verification uses temporary files or SQLite rather than real payments and real email. It demonstrates how the state machine and the idempotency algorithm behave under a constructed fault; it does not show that any external service offers the same guarantee.

Even with a cancellation receipt in hand, the external fact cannot be erased

Code can cancel a call that has not been admitted yet, and it may also go on tidying up after certain actions have completed. For external side effects such as a database write, a publication or a payment, the real guarantee for a retry has to rest on a downstream unique key, a conditional update or a business check. Codex's local cancellation path is not an exactly-once protocol for every external system.[C04][C09]

The temporary-SQLite counterexample in the tests shipped with this book deliberately separates the commit from the confirmation: the action is committed and the process exits before the confirmation is written; a second execution without a stable business key duplicates the side effect. The experiment is an original teaching program, not a run of the Codex executor. The right question at recovery is "has the downstream side already accepted this business action", not "does the model still remember doing it".

Q051｜How do CAS and atomic replacement keep a local file change from being overwritten? How does that work together with a database transaction?

What to know first for this question Recovery reads the persisted events and the current external state and reconciles them; it is not just restoring the conversation. Propagating a cancellation also needs it made clear which actions can no longer be revoked.
Lesson 02 · State, events and checkpointsLesson 26 · Retries, idempotence and transactionsLesson 33 · Reading a production run

Core answer

Start with the objects and symbols used here
CAS, version checks and TOCTOU
CAS is a controlled operation that updates only after comparing that the expected version or value still matches. TOCTOU is the race in which something changes between the check and the use: a separate "look at the version, then write" is not automatically equivalent to an atomic CAS. If a patch was produced from version 7 and the version is already 8 at commit time, overwriting directly should be refused and the work redone; a concurrent insert between the comparison and the write has to be prevented as well.
WAL, fsync and atomic replacement
WAL is the idea of writing a log first and then updating the data by protocol; fsync asks for a file's data to be synchronized to storage; an atomic rename, where it is supported, keeps readers from seeing a half-finished replacement. Visibility and durability after a crash are not the same guarantee. One file renaming successfully does not mean several files and a database committed together; durability also has to be checked against the platform, the directory and the storage behavior.

CAS-style update applies the change only while the current version still equals the expected version; atomic replacement keeps a reader from seeing half a file. They address concurrent overwriting and visibility respectively, but they cannot by themselves make the file system and another database into one atomic transaction.[SQLITE]

An editor's safe write chain

Read the file content old and the version v; produce new from old; write to a temporary file in the same directory; flush and fsync where needed; under a controlled concurrency policy, confirm again that the current version is still v; replace the target atomically; record the new version and the result of the action. The rename and persistence semantics of different operating systems and file systems have to be looked up in their implementations; one Python function cannot be taken as a cross-platform guarantee against power loss.

Note that between "check the version first, then replace" there can still be a TOCTOU window. If several writers are at work at once, you need a lock, a controlled single writer, or storage that really supports conditional writes. Comparing a hash once inside the application cannot by itself stop someone else changing the file after the check.

When the file has been replaced but the task database has not recorded the success, recovery can compare whether the target content equals the new content that action expected, and then record the result afterwards; if the file has been changed by someone else again, it cannot simply be replayed. Keeping the old version and the expected new version helps tell executed, not executed and conflicting apart. Not every file operation has to be raised into an elaborate transaction, but a shared critical file should have an explicit policy.

Start with the objects and symbols used here
ACID, transactions and isolation
A transaction puts a group of database operations inside a defined commit boundary. ACID stands for atomicity, consistency, isolation and durability; the guarantee you actually get also depends on the isolation level, the configuration and the resource boundary. A database transaction committing does not mean another mail service commits along with it. Writing the two operations into the same function does not automatically make a cross-system transaction.

One write being "complete" can still mean the content is wrong. Atomicity only deals with a visible half-write; it is no proof that you were working from the latest version.

Checking the hash first and then writing without a lock some time later still leaves room for another process to change the file in between. The comparison and the update must be protected by the same coordinating mechanism.

Follow-up: why does formatting after the tests pass also call for care?

Formatting or code generation still changes the object that was verified, and can introduce a change in meaning, a difference in environment or an incomplete write. The simple, safe procedure is to finish every intended change and then verify against the final state; if something is changed after verification, at least rerun the affected checks.

Follow-up: can a database transaction protect a shell command?

A database transaction protects only the reads and writes inside it. A shell changing a file, calling the network or sending a notification is not inside the transaction, and a database rollback cannot undo those side effects. Do not wrap a transaction around an external command and then claim end-to-end atomicity.

Follow-up: after a CAS conflict, can the model be left to merge automatically?

It can be a new step in the task, but it has to read the latest content first, understand both sides' changes again and verify them. A conflict must not be treated as a transient error and retried unchanged. The result of an automatic merge also needs a new version condition, to prevent another overwrite.

Q052｜How does a long task continue after a restart? What are Retry, Resume, Replay and Cancel?

What to know first for this question A retry policy has to be designed separately for read-only, idempotent, irreversible and unknown-result cases; backoff reduces the pressure but does not settle a duplicated business action.
Lesson 07 · APIs and streaming protocolsLesson 26 · Retries, idempotence and transactionsLesson 29 · Security basics

Core answer

Retry attempts an operation again; Resume continues a task from a known state; Replay plays the records back to rebuild or to diagnose; Cancel asks for the remaining work to stop. They are not interchangeable, and in particular replaying a log must not turn automatically into executing the side effect again.

A recovery procedure follows the facts

At startup, read the task goal, the current checkpoint and the outstanding calls; check whether the actual artifacts exist and whether the versions match; query for any unknown side effects; rebuild the smallest sufficient model context; and continue only from the next unfinished step. A read-only result already obtained can be reused within its validity, and a write already completed should not be redone because the chat history is missing.

When replay is used for debugging, recorded tool results can stand in for real execution, to see how the model or the harness handles them. If a replay has to reach a real external system, the environment and the permissions have to be isolated explicitly, so that "testing the recovery" does not send the email or deploy again.

Canceling has to stop new actions, propagate the cancellation signal to the tools still running, and wait for or record the final state. The model's generation stopping, the UI closing, the process exiting and the remote task stopping are different events. The user no longer seeing progress does not mean the task has been rolled back.

Start with the objects and symbols used here
checkpoint: you must look at the object that was saved
A model checkpoint saves weights or training state; activation checkpointing saves a few intermediate nodes so they can be recomputed on the backward pass; an agent task checkpoint saves how far execution has got. The three share a name, but what they restore is entirely different. When you see "checkpoint", first ask whether it restores parameters, recomputes activations, or continues a task. An agent saving a summary does not update model weights.

Retry, resume, replay and cancel mean different things for an action

Follow-up: why does exponential backoff also need random jitter?

When a great many clients fail at the same moment and then retry on the same schedule, they hit the service in sync all over again. Random jitter spreads the retry times out. There should also be a maximum number of attempts, an overall deadline and a classification of errors, so that a permission or argument error is not backed off again and again.

Follow-up: how often should a checkpoint be taken?

Start with the objects and symbols used here
I: the identity matrix
In a matrix formula I is usually the identity matrix: 1 on the diagonal and 0 everywhere else. At a compatible size, multiplying a vector or a matrix by I leaves the numbers unchanged. Wq=Wk=I is a special case chosen deliberately; one cannot infer from it that the projections of a real model are all the same. Independent micro-example: I=[[1,0],[0,1]], and [3,-2]I=[3,-2]. I here is not the position subscript written as the letter i.

It depends on the cost of redoing the work and the risk of side effects. Persisting at every Token is usually unnecessary; the key stages, expensive computations and either side of an external write are more worth saving. Too high a frequency adds I/O and complexity, too low a frequency adds to what recovery loses.

Follow-up: how is a successful recovery verified?

Check that no side effect was duplicated, that no necessary step was skipped, that the key constraints still hold, that the artifact versions agree, and that the final verification really ran. "The program can start again" on its own is not a successful recovery of the task.

Engineering deep dive · E42 · continues Q084

Three layers each retrying three times: why does the bottom one get hit 27 times?

Prerequisite: Lesson 26 · Lesson 33. Reading order: confirm the run contract first, then the counterexamples and the fix, and test the limits last.

A retry budget has to be counted along the call chain

"Retry three times" here means specifically at most 3 attempts per layer, so that the first attempt and the number of retries are not mixed together. The outer agent makes 3 attempts, the SDK makes 3 per attempt, and the proxy makes 3 more per attempt, so the worst case is 3×3×3=27 leaf calls. That number is a local enumeration and multiplication under fixed assumptions, not any service's default.

Retry amplification can add pressure during a failure and turn a brief error into sustained overload. SRE practice on handling overload stresses queues, useful work and deadlines; health is not recovered through an unbounded backlog.[SRE]

One call needs a shared deadline

With 30 seconds set independently at every layer, retries layer upon layer can drag the user's wait out into minutes. Pass the remaining deadline down, so that a child call's timeout does not exceed the budget left; backoff and jitter spend that budget too. Before deciding to retry, check the kind of error, whether the action is idempotent, the time left, the cumulative count and the current authorization together.

Backoff deals with requests arriving in sync, not with a non-idempotent side effect. If the result is unknown after a call times out, check it first or carry the downstream idempotency key over; a key should not be swapped automatically to "get around the duplicate". The same key with different arguments has to be rejected explicitly.[IDEMP]

Canceling is not withdrawing a request that has already reached the downstream side

After the user cancels or the task epoch changes, stop starting new actions; an action in flight may already have committed, and should be recorded and checked. The recovery logic has to distinguish not started, started with an unknown outcome, and finished; writing canceled for all of them erases the changes that really happened.

Follow-up: which errors are suitable for a retry?

A transient connection failure, or rate limiting explicitly marked as retryable, may be suitable, but confirm first whether the call could already have executed. An invalid argument, a permission denial or an incompatible schema will usually not improve by being sent again unchanged. If the model is to change the arguments, that counts as a new decision step and the permissions have to be verified again, rather than being a transparent retry in the SDK.

Follow-up: how is "recovery fails → recover again → endless loop" avoided?

A recovery action gets a budget and a state it can end in as well. Where the missing evidence really does make recovery impossible, mark the scope, keep the risk on record, and skip it or hand it to a person, rather than letting one broken task block all the work behind it. A read-only task that can continue and a side-effecting task that cannot be retried have to be handled separately.

The acceptance procedure

Inject a dropped connection, rate limiting, a slow response, a timeout after the commit, a user cancellation and a late-arriving old result; then check the actual number of downstream calls, the idempotency key, the total wall-clock time and the final state. Mocking a single "return 500 then 200" is not enough to show that recovery is correct.
