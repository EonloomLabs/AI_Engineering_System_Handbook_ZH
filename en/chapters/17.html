Prerequisites for this chapter

Source code has language structure and version relationships. A text search finds characters, an AST finds syntactic structure, and LSP understands symbols and types; compiling and testing provide run evidence. No single method can replace the other layers.

Each question in this chapter lists the groundwork it needs. You can take the matching Foundations lesson first, or use the self-check to confirm how well you have it.

A quick check before the deep reading: for two modules with a function named foo, say why a regular expression confuses them, what a definition-and-reference relationship adds, and why a language service can also be incomplete when the dependencies are not loaded.

A term with a dotted underline can be clicked for a quick reference. Read the definition of a letter in a formula first; do not let a guessed abbreviation stand in for the derivation.

A code base is not an ordinary collection of articles. Identifiers, types, module relationships, build configuration, versions and the execution environment provide clues more precise than a semantic vector, but those clues have limits too.

Q037｜What does each of grep, AST, LSP and the call graph know? Why can they not stand in for one another?

What to know first for this question A regular expression finds text, an AST finds syntactic structure, and LSP finds the language's semantic relationships. Dynamic loading, macros and generated code all affect how complete static analysis can be.
Lesson 18 · Code is not an ordinary document

Core answer

grep looks for text patterns; AST describes syntactic structure; LSP provides capabilities such as definitions, references and type diagnostics through a language service; a call graph describes possible or already observed call relationships. Text occurring is not a symbol reference, correct syntax is not correct types, and statically reachable is not actually happening at run time.[TREESITTER][LSP]

Searching along a function name

Search filter_items, and it can hit the function definition, comments, strings and test data. grep is fast and general, but it does not know which of them are the same symbol. An AST can recognize function declarations and call expressions and rule out some comment and string noise; but a syntax tree alone need not resolve import aliases, generics or dispatch at run time.

A language service combines the project configuration, the dependencies and type information to resolve one use site to its specific definition. Functions with the same name in two different modules should not be mixed together. If the build configuration is wrong, the dependencies are not installed, or the language server has not finished indexing, the result can also be missing or out of date.

A static call graph helps widen the scope of impact, but reflection, dependency injection, dynamic imports, function pointers and polymorphism make it incomplete or conservatively too broad. A run trace only shows the path this one input took, and it cannot prove that other paths do not exist. Reliable location usually combines text, structure, type and run evidence.

grep, AST, LSP and run logs each answer questions at a different layer

Conditions for this example: an independent code example: two modules both define parse; somewhere obj.parse() is called. Finding the string parse alone cannot settle which implementation is called at run time.

How to read the changes in the figure

No layer is a universal replacement for the one before it. grep is good for narrowing the range quickly, an AST rules out textual noise, a language service adds static semantics, and run evidence checks the actual path.

One run establishes one path; that is not proof that every input takes only this path. A diagnostic report should state the sample input and the environment.

When a layer fails, identify why: a parse failure may be a grammar version and a wrong jump may be the project configuration, so neither has to be attributed to the model.

Do not conflate: the character positions LSP returns follow an encoding convention of their own; a UTF-16 offset cannot be taken as a Python character index without conversion.

Worked example · Q037

The name foo appears three times, so why do grep and LSP give different sets

Input and conditions. File a defines foo, file b imports a.foo and calls it, and file c defines another local foo inside a function; a comment mentions foo as well.

Steps and objectsInternal actionIntermediate result / new state
1 Text searchSearch for the string fooThis gives the definition, the call, the local namesake and the comment.
2 Syntactic filteringThe AST recognizes Call nodesComments can be dropped, but calls with the same name may still belong to different bindings.
3 Symbol resolutionLSP looks up the references to a.fooIt should associate b's call and should not mix in c's local foo.
4 Run evidenceIf the call is generated dynamically from a stringStatic references may miss it; check the registration and the actual logs.
5 Scope of the changeDetermine the callers from the bindings and the testsNot every occurrence of the text foo can be replaced mechanically.

Join the steps up. Equal text, equal syntactic role and equal symbol identity are progressively stronger but different relationships.

Limits and counterexamples. LSP accuracy depends on the language service and the project configuration; for dynamic languages, reflection and generated code, static analysis is not guaranteed to be exhaustive.

Basis and scope of use:[DERIVE]. The example input and setting are stated explicitly by this book.

Follow-up: does Tree-sitter parsing successfully mean the code compiles?

No. It is concerned with syntactic structure and can tolerate an incomplete editing state; type errors, link errors, missing dependencies and run-time exceptions need other tools. Treating an AST as a complete semantic database misses the engineering configuration layer.

Follow-up: why is looking up references more valuable than grepping the whole repository?

When the language service is configured correctly, it returns references by symbol identity, which cuts down false hits on the same name and can follow aliases and modules. But dynamic patterns it does not support may still be missed; choose according to the language and the project, and never take zero references as absolute proof that nothing uses it.

Follow-up: when is a plain grep best?

When the error code, configuration key, log text, file name or exact function name is known, a low-cost text search is often the most effective way in. Narrow the scope with cheap tools first, then go deeper with semantic and type tools. A more advanced technique is not the one that should run first.

Engineering deep dive · E33 · continues Q065

Get the unit of a code position wrong by one and an edit can change the wrong characters: UTF-8, UTF-16 and version numbers

Prerequisite: Lesson 37 · Lesson 07 · Lesson 18. Reading order: confirm the run contract first, then look at the counterexamples and the fix, and finally test the limits.

"character=3": ask what the unit is first

Position.character in LSP 3.17 is interpreted according to the PositionEncodingKind negotiated at initialization; UTF-16 is the default and the encoding a server must support, and the counts mean different things in UTF-8 and UTF-32. This rule comes from position.md in the Microsoft specification; it was not guessed from the habits of JavaScript strings.[LSP]

The fixed string a😀b, where before b there are 2 Unicode code points, 3 UTF-16 code units and 5 UTF-8 bytes. Python's plain string len, the string length commonly used in JavaScript, the Content-Length of the protocol transport and an LSP position can therefore give different numbers. Do not take tests passing for Chinese and English as proof that Unicode positions are handled correctly.

From one position to one safe edit

Interpret the start and end positions with the negotiated encoding first, then convert them to internal indices against the matching document snapshot; take the range boundaries the protocol agrees on, and do not mistake the end position for including the last character. Then check the document version, and generate the edit last. The same line and character can point at entirely different content once the user has typed more.

This book actually computes the three lengths above, and additionally makes the version and content-fingerprint check a constraint at the execution layer. It did not start a real language server, so it claims no certification of compatibility with any IDE.

A version conflict cannot be fixed blindly by "searching nearby for the same text"

If the edit received is based on version 7 while the buffer is already at version 8, applying it directly may overwrite the user's new content. Automatic relocation needs explicit context and a conflict policy; where no unique judgment is possible, fetch the range again or refuse. The line numbers the model gives are only a proposal, and they cannot bypass the harness's version protection.

Follow-up: which is authoritative, the content on disk or the editor's buffer?

It depends on what the action acts on. LSP usually works with in-memory documents; a shell test usually reads the disk. When the two views are out of sync, the model may analyze the buffer while the test runs the old file. The evidence should say "the source is the in-memory version" or "the source is the work-tree file", and where necessary save explicitly or have the verification read the same snapshot.

Follow-up: why not unify everything on byte offsets?

Internally they can be unified, but the boundaries still need exact conversion; the protocol, the editor and the model's reports need not use bytes. A unified unit of storage does not mean the input's unit can be ignored. Tests containing combining characters, emoji, CRLF and non-BMP characters expose hidden assumptions.

Engineering mechanisms and failure boundaries

Why does code evidence need the work-tree version, and not just the commit?

The commit can be the same and the file still different

The user has uncommitted changes, and the agent writes files one after another during the task too. Two test runs can both record commit abc while the things actually tested were the work trees r7 and r9. Record the content hash of the affected files, the command run, the environment and the set of tests, not just the branch name.

From a text search to a verifiable change

Narrow the scope first with the path, the error message and exact symbols; then, where needed, look up definitions and references with an AST or LSP; and verify the hypothesis with run evidence at the end. A syntax tree can express structure, but it does not automatically know about dynamic loading, run-time configuration or generated files. An LSP position also depends on the encoding unit negotiated in the protocol: a UTF-16 position cannot be taken unconditionally for a UTF-8 byte offset.

The three preconditions for a patch

The teaching patch P targets line 12 of r7. Before it is really applied, check that the target is still r7, that the expected old text is still there, and that the path is still within the permitted range. If the file has become r8, an old line number cannot be relied on to overwrite blindly. A patch tool finding similar context automatically is no proof of semantic correctness either; after applying it, still look at the diff and the tests.

Why a passing test stops holding once something is changed afterwards

A test-result object should be bound to source_hash + command + environment + test_selection. Formatting or generating code after it passes means at least re-verifying the affected part. An exit code of 0 also has to be checked for everything being skipped, no tests being collected, the command being wrapped wrongly, or an environment variable having changed the scope of the tests.

Anthropic's engineering for long-running tasks stresses recoverable progress and verifiable functionality rather than merely writing "done"; the large-scale parallel coding case likewise depends on tests and coordination. A case shows the value of one engineering approach; it does not mean every task should adopt large-scale parallelism.[A06][A15]

A delivery should answer four questions

What was changed, why it was changed, which evidence supports it, and what is still unverified. State "the static checks pass" and "verified by an actual run" separately; when a check cannot be run, record the reason and the risk, rather than writing "not run" down as "passed".

Reading, changing and testing must point at the same object

A fixed teaching example: read sees r7, the patch produces r8, and the test runs r8; if formatting then produces r9, the delivery cannot go on marking the r8 test as r9 having passed. This principle does not require a whole-repository retest for every small change; it requires the coverage of the verification to match the last change made.

The article on engineering for long-running tasks stresses recoverable artifacts and real tests, but it does not provide a test selector that suits every language. How an AST, LSP or dependency graph helps narrow the scope still needs the language tools' own definitions and evidence from the current work tree; a general article about a harness is not used here as the source for a specific conclusion about the LSP protocol.[A06][D07]

Verification basis:[A06] [A15] [D07] [C02]. The source is limited to commit 86e17e98c7f9 and the paths actually read; article experience, public documentation and original teaching experiments are labeled separately. See how it was obtained, what was read, and the limits.

Q038｜How does a code index handle Git versions, the work tree and unsaved files?

What to know first for this question The repository snapshot, the uncommitted files in the workspace and the run-time dependencies together decide the actual program; citing a commit alone is not enough to stand for the version being executed.
Lesson 02 · State, events and checkpointsLesson 18 · Code is not an ordinary documentLesson 04 · Foundations of engineering quality

Core answer

One repository can have a commit snapshot, a work tree on disk, unsaved buffers in the editor and a background index all at once. Agent has to know which layer the current evidence comes from, and which layer the edits and the tests act on. The same path does not mean the same content.

Four conflicting copies of "the same file"

On main the file filter.py is at version r10, the user has changed it locally to r11 without committing, the editor holds a further unsaved r12, and the index is still r10. The agent reads r10 from the index, generates a patch and writes it to disk over r11; the user then saves the editor's r12 over the agent's patch. Even though no single step reports an error, the final result is wrong.

Start with the objects and symbols used here
IDE, CLI, UI and DOM
IDE is the integrated development environment, CLI the command-line interface, UI the user interface, and DOM the tree of structural objects of a web document. The code, selection and page information that each entry point attaches automatically can differ. The model seeing the selected function in the IDE does not mean the same task in the CLI has received that function; check this turn's input objects first.

A safe read interface should return the content's source and version identifier wherever it can. When editing, check the expected old content or the version; and which copy of the code a test actually runs, in the work tree or in the build environment, has to be stated as well. For an IDE integration, a workspace overlay can be designed so that unsaved content is read first, but one cannot assume that every tool shares that overlay automatically.

Incremental indexing has to handle file modifications, deletions, renames and changes to generated files. Going by mtime alone can miss unusual timestamps or caching problems; going by path alone will misidentify a rename. An implementation can combine version and content identifiers, but it need not build a complex whole-repository signature for every simple search.

Start with the objects and symbols used here
HEAD, working tree, ETag and content fingerprint
Git's HEAD marks the commit or branch currently checked out; the working tree may still hold uncommitted changes. An ETag is a validator for an HTTP representation, and what it guarantees depends on the service. A content fingerprint is computed over the bytes; these kinds of version identity are not interchangeable. When the index comes from commit v7 but the file has been modified locally, the same file name does not mean the same content. Applying a patch or citing evidence should be checked against the version actually present.

Follow-up: is it safest to let the agent work only once the whole-repository index has finished updating?

That lowers latency and may block tasks that need no blocking. One can instead locate candidates with the index and then read the current file to confirm: the index is for finding things fast, the live read is for the facts. For a high-risk change, check the version of the key dependencies explicitly; there is no need to rebuild the whole repository every time.

Follow-up: why is recording the Git commit alone not enough?

Uncommitted changes, generated code, dependency lock files, environment variables and test configuration can all affect execution. Verification evidence must at least correspond to the actual state of the work tree and the command's environment. commit is an important identifier, but it does not cover every mutable input.

Follow-up: once the source is updated, are all the old conclusions void?

Not necessarily. Only the affected facts and dependencies have to be verified again. Knowledge can be bound to a specific module, file or symbol, so that a change triggers a local re-check. Forgetting everything wastes cost, and never expiring is dangerous; what matters is that the scope of the dependency is clear.

Engineering deep dive · E34 · continues Q066

HEAD has not moved, so why is the evidence already stale? The working tree, the unsaved buffer and the index snapshot

Prerequisite: Lesson 18 · Lesson 26 · Lesson 04. Reading order: confirm the run contract first, then look at the counterexamples and the fix, and finally test the limits.

A commit identifies the commit, not every current fact

Under the same HEAD a file can have uncommitted changes; the editor may also hold an unsaved buffer; and build artifacts and environment variables can change the result of a run too. Writing the retrieval cache key as repo+HEAD does not always guarantee that the current code is what gets read. Git's work-tree mechanism separates the working directory from the shared repository data, and it must not be understood as every fact being covered by the commit.[GIT]

In a temporary directory this book changes x=1 to x=2, keeping the "HEAD label" fixed while the file's content hash changes. This experiment did not fake a Git commit; it uses an actual file change alone to prove the logic: commit identity is not enough to cover the state of the work tree.

Evidence should describe the world it observed

One piece of code evidence can record the path, the content fingerprint, the range, the repository commit, the work-tree or document version, and the time it was read; run evidence also includes the command, the dependencies, the configuration and the input fixture. There is no need to build a complex database for every small task, but it should at least be able to answer "which file exactly does this test correspond to".

A retrieval index may update asynchronously. When the user has just changed the code while the semantic index is still on the old snapshot, the key files that were hit should be read again, or the index version stated. For a modifying operation, taking the line numbers from an old snippet and writing the current file is not allowed.

A patch's preconditions have to sit in the same controlled process as the write

First read hash=r7; while the patch is being generated someone changes it to r8; check before committing that it is still r7, then replace atomically. If another writer can still slip in between the check and the replacement, there is a TOCTOU (a change between the time of check and the time of use) window. A collaborative system needs everyone to honor the same lock, or to use storage that supports a conditional update on version.

Follow-up: does giving each agent its own worktree avoid conflicts?

It isolates each one's file changes and makes them easier to collect, but the final merge can still have semantic conflicts; shared ports, databases, package caches and parts of the Git state have no natural isolation either. Tests that depend on the same external state still need their own fixtures.[GIT]

Follow-up: how do you avoid pasting an old test result onto a new patch?

Record the version or fingerprint verified when the test started and when it ended. Run the acceptance tests once all the intended changes are complete; if a file changed during the test, the result should be marked as based on the old version or as uncertain. Showing "the last test was green" without showing what was verified manufactures a false sense of safety.

Q039｜How should a bug be located step by step? Why is "read more source" not a sufficient method?

What to know first for this question Locating a bug goes from a reproducible symptom to candidate code, and then rules candidates out with counterexamples. Finding a function that looks suspicious is not the same as finding the root cause.
Lesson 17 · From search results to a trustworthy answerLesson 18 · Code is not an ordinary documentLesson 04 · Foundations of engineering quality

Core answer

Form an observable failure first, then propose a falsifiable hypothesis, and choose the smallest evidence that can tell the hypotheses apart. Reading code, tests and logs should serve to narrow the set of causes, not to pile up context aimlessly.

Take exclude having no effect as an example

What the user sees: they configured build/**but the build directory still gets packaged. Candidate causes include the configuration not being loaded, a rule being parsed wrongly, inconsistent path normalization, and the match result being overwritten later. First confirm that the rule is present in the running configuration, which rules the first one out; then print or test the paths the matching entry point receives, and find that they are absolute while the rule targets relative paths; build a minimal test and reproduce it. At that point the focus turns to normalization and the meaning of the root directory, rather than to reading more of the unrelated packaging module.

If one reads only fnmatch(path,pattern) and swaps the library straight away, the root cause may be buried and new matching semantics introduced. Before fixing it, settle the requirement: are rules relative to the repository root or to the current directory? How are path separators handled? Does a directory rule include the files below it? Are symbolic links followed? These boundaries decide the test and the patch.

After the minimal patch, run the original failing case first, then the regressions aimed at the neighboring semantics. If a test still fails, update the hypothesis from the new error instead of repeating the same change. Every step should ideally answer "what do I expect to see, and what does a different result mean".

Follow-up: does analysis by refutation mean designing a lot of checklists?

No. Two or three distinguishable hypotheses and the cheapest verification are enough. The heart of refutation is letting the facts overturn your own explanation, not promoting a simple bug into a long-term research project.

Follow-up: when does the reading have to be widened?

When local behavior is correct but the system's result is wrong, or when a caller's contract, state propagation or concurrency is involved, extend along the data and control dependencies. Make clear what evidence is missing first, then read the relevant boundaries. Broad reading should be driven by the problem, not be the default step.

Follow-up: the model proposes a plausible root cause, so why reproduce it anyway?

There can be several plausible explanations; only observation and a repeatable counterexample can tell them apart. Reproducing also gives the patch its verification: the old version fails, the new one passes. Without a reproduction a well-grounded fix is still possible, but the shortfall in verification should be stated clearly, and a guess must not be dressed up as a confirmed root cause.

Q040｜How do you get an agent to "understand the business" instead of only ever looking at local code?

What to know first for this question Business rules come from the code as well as from conventions and data; record the conditions of use and the acceptance examples first, then decide which knowledge is worth becoming long-term guidance.
Lesson 02 · State, events and checkpointsLesson 18 · Code is not an ordinary documentLesson 04 · Foundations of engineering quality

Core answer

Connect the business goals, the invariants, the key flows, the domain terms and the implementation entry points, and keep them queryable, verifiable and updatable. Understanding the business is not stuffing every document into the prompt, and it is not an architecture diagram either.

Build the shortest path from requirement to implementation

For example, "there must be no second refund once an order is canceled" is a business invariant; it corresponds to a state machine, an idempotency key on the payment interface, a database constraint and tests. When an agent works on a refund bug, it needs to know this invariant, and then to find the execution path and the way to verify it. A document that says only "the system uses a microservice architecture" can hardly guide a correct change.

A lightweight entry file can describe the core objects, the boundaries, the common tasks and the code paths; the documents for a particular module record why it was designed this way, which alternatives were rejected, and the exceptions that hold at present. A decision record should be short and carry its conditions of use; not every variable name needs an ADR.

Code, tests, run-time metrics and documents check one another. When a document says "at most three retries" while the constant in the code is five, neither the document nor the code can be taken as true automatically; judge the current environment and the target specification, then decide whether the document is out of date or the implementation is defective.

A business rule needs an exception that can be executed, not just a slogan

Follow-up: does business knowledge belong in long-term memory or in the repository's documents?

Knowledge that the team shares and that should change with the version usually belongs in the repository or an authoritative knowledge base; personal preferences and experience that crosses projects can go in personal memory; what is transient to the current task goes in the checkpoint. Storing the same fact in many places increases conflict, so keep one authoritative source and have memory point at it.

Follow-up: how can an onboarding guide be both easy to read and deep enough internally?

Give the business flow and the core objects first, then link to the specific modules, state transitions, data structures and failure cases. It cannot be only a table of contents, and it cannot ask the reader to read thousands of lines of source at the start. Progressive does not mean deleting the detail; it means giving the detail a clear entry point and prerequisites.

Follow-up: how do you know these documents really improved the agent's quality?

Choose real business tasks and compare three groups — no entry document, one complete large document, and a structured entry point loaded on demand — measuring the reading of the necessary evidence, wrong business assumptions, task success and cost. Growth in the number of documents is not growth in capability.
