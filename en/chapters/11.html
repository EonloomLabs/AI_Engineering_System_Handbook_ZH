Prerequisites for this chapter

Connecting to the server, discovering the tool, being cleared to use it and actually executing it are four separate gates. Knowing that a tool exists does not mean the current model sees it, still less that the current identity holds every permission for it.

Each question in this chapter lists the groundwork it needs. You can take the matching Foundations lesson first, or use the self-check to confirm how well you have it.

Start with the objects and symbols used here
Schema and Structured Outputs
A schema is a set of structural rules about fields, types and the like; a structured-output mechanism makes it easier for the model to return data that follows those rules. Valid fields still do not mean that the target file exists, that access has been granted, or that the request is right for the business. Independent example: path is required to be a string; {"path":3} does not match the type rule, and {"path":"missing.py"} follows the structure yet may still find no file.

A quick check before the deep reading: use "the calendar can be connected, but only read and not written" to explain the different responsibilities of transport, tool schema, authorization and execution.

A term with a dotted underline can be clicked for a quick reference. Read the definition of a letter in a formula first; do not let a guessed abbreviation stand in for the derivation.

This chapter's MCP messages use the explicitly pinned 2025-11-25 specification to explain the basic life cycle; it is not claimed to be the only current version. Documentation and extensions in 2026 may add capabilities; while studying, keep the stable principles separate from the version field.[MCP-LIFE]

Follow this chapter through its objects and states

MCP handles connection and capability description; it does not decide authorization on the business's behalf. Draw "the tool exists", "it is visible to the model this turn" and "the current user may execute it" as three checkpoints first, then look at the schema and the protocol details, and you will not mistake successful discovery for having permission.

Q013｜When designing tools for an agent, should they be split into many small tools or made into one all-purpose tool?

What to know first for this question MCP is a set of conventions for a host interacting with an external server; it is not model parameters or long-term memory. Host, Client and Server are a division of labor, not three models.
Lesson 07 · APIs and streaming protocolsLesson 08 · Tools and MCP

Core answer

Tool granularity should match the decisions the model really makes and the boundaries the system can verify. Too fine adds turns and assembly work; too coarse hides side effects and the reasons for errors. A good tool offers clear input, controlled output, distinguishable failures and suitable idempotency/version conditions, not just a name that sounds good.

Comparing three repository interfaces

run_shell(command) is extremely flexible, but its parameter space is huge, its output easily runs long, and its security boundary depends on the execution environment. read_line(file,n) is too fine: reading one stretch of context takes dozens of calls. read_file_range(path,start,end) usually makes it easier for the model to fetch exactly one block of evidence, and it can return the position of the next stretch, the file version and a truncation marker.

Start with the objects and symbols used here
d_k, d_v, Dh: the width of each row of representation
d_k is how many components one Query/Key vector has; d_v is how many components one Value vector has. Dh, or d_h, is the single-head width in some chapters. They are size integers, not the k-th Key or some Value number. Shape micro-example: with Q[2,3], K[5,3] and V[5,4], the scores are [2,5] and the output [2,4]. A pairing width of 3 for Q/K with a Value width of 4 is still legitimate.
Patch, image channels and the visual projection
A patch in an image is a small block cut out of it, and RGB is the 3 channels red, green and blue; a patch in software engineering is a code patch — the same word for both. An image block, once flattened, can become a vector through a learnable transformation; it is not a lookup in a text vocabulary. Independent image example: one 16×16×3 block holds 768 numbers, and after projection it can become d features. d is fixed by the model design.

Write tools involve trade-offs just the same. replace_entire_file is simple but easily overwrites someone else's changes; apply_patch can express a local change, but may match the wrong place when the old fragment is not unique; an editing interface that carries expected_version and explicit positioning makes conflicts easier to detect, but then versions have to be managed. There is no need to impose a complex protocol on a one-off temporary file, but writes to a shared repository deserve stronger conditions.

Output should be designed for the task that follows. A search tool returns files, line numbers, fragments and stable references, not the whole repository text; a test tool returns the command, the working directory, the version, the exit code, the pass/fail/skip counts and the location of the log, not just "success". Some flows can combine a common, well-determined sequence of steps into one tool, but it must not hide a write action that needs the user's authorization.

Start with the objects and symbols used here
SQL, SQLite and the transaction object
SQL is the language for working with relational data; SQLite is a database engine that embeds into an application. Writing operational state into a database is a persistence action by the harness; it does not modify the model's neural network parameters. One transaction can save the business row in this database together with a pending-send record, but that does not let you infer that the mail service committed atomically along with it.

Tool granularity should follow the common unit of work, rather than the idea that fewer functions is better

Conditions for this example: an independent order-lookup task: look up order O7 and return its status. Three tool boundaries are compared — "SQL over the whole database", "a business query" and "extremely fine field-by-field reads"; this is not any real database.

How to read the changes in the figure

A business query packages the known fixed steps into the program, so the model guesses less about details that do not matter.

But writing every business action as one all-purpose tool(mode,payload) hides the boundaries again and makes it hard for the schema to express the different parameter combinations.

The best granularity has to be tested on real tasks: look at the missing-field rate, the number of call turns, failure recovery and permission scope together, rather than only counting tools.

Do not conflate: "fewer tools" is not the goal; only cutting down hard-to-understand choices and unnecessary handoffs can raise the success rate.

Limits and counterexamples. This is an interface-design example; it does not claim that a purpose-built tool is better on every task. That needs an evaluation on representative tasks.

Follow-up: does a more detailed tool description always mean the model uses it better?

A moderate number of examples and boundaries helps; large amounts of repeated explanation add context and may create conflicts. Explain first what is easy to get wrong: units, paths, inclusive/exclusive boundaries, pagination and side effects. Improving the description from failed samples works better than writing an encyclopedia entry.

Follow-up: why does renaming a tool affect quality?

The name takes part in how the model understands and chooses, and it may also be depended on by past state, skill or automation. A change is not only an API compile problem; it may also change the probability of selection. Functional compatibility, an updated description and a routing regression test are all needed, not just a check that the function still exists.

Follow-up: why does letting the model run code to call tools in bulk save tokens?

The model can generate a program that filters, loops and aggregates inside the execution environment, returning only the necessary result to the context and keeping a great deal of intermediate data from traveling back and forth. But the execution environment has gained stronger capability, so it must have resource and permission boundaries; running code also introduces program errors. It suits data processing that can be programmed, and does not mean every tool call should be rewritten as a script.

Engineering mechanisms and failure boundaries

The tool exists, the model sees it, it can be called, it is authorized: four layers of checking

Why the same tool is "installed but unusable"

Lay the four layers out first: the registry holds an implementation; the tool description enters this turn's visible catalog; the model can find it, either by calling it directly or along a discovery path; and at execution time the action is authorized. The four are a graded series of checks, not four synonyms.

In the pinned Codex, ToolRouter keeps the registry and the model-visible specs separately. Direct exposure, deferred discovery, reachable in code mode and hidden are different states. Counting registrations alone does not prove the model can discover a tool; a deferred tool also needs a working search entry point and discoverable information.[C03:ToolRouter] The name and arguments the model generates are converted by build_tool_call into different internal payloads, and the call types a harness supports are not limited to one kind of function JSON.[C03:build_tool_call]

What a good schema solves, and what it does not

A schema can constrain path to be a string and limit to be a positive integer. It does not prove that the file exists, that the path has not escaped its boundary, or that the user agreed to an overwrite. path='src/../secrets/key'can be structurally valid and still needs normalization and an authorization check. Name collisions also have to be handled at registration time; an external tool must not silently take over the identity of a protected internal tool. The pinned registry normalizes names and handles reserved ones, and an external name must not be treated as a trusted identity.[C09]

Tool design affects the reasoning load

Anthropic's article on tool engineering stresses meaningful names, clear boundaries and return content that is useful and restrained. Do not simply wrap an existing API as it stands into dozens of tools with similar names. In the teaching example, making "read a file and return the path, the version, the requested lines and a truncation marker" into one stable tool is usually easier to verify than returning arbitrary JSON for the whole repository.[A03]

Code execution can let a large amount of data be filtered inside the execution environment before it is returned to the model, which cuts down the context being hauled around; but that does not automatically reduce permission risk. Running the code, reaching downstream, redacting results and capping resources remain the harness's responsibility. What tool discovery saves is the cost of descriptions by default; it does not mean tools can be added without limit at no retrieval or security cost.[A09][A10]

The four checks are not a straight line that has to be walked in order

Direct tools, deferred tool search and Code Mode are different exposure surfaces. ToolRouter::exposes_tool checks several paths; build_tool_call distinguishes an ordinary function, a custom call and a tool search executed by the client; some hosted calls do not reach the same local handler. The number of registrations is therefore neither the number visible to the model this turn nor the number of authorized actions.[C03]

Check it against a counterexample: tool T is registered in the catalog, but policy keeps it hidden, and successful registration is no reason to report that "the model can use T". Conversely, T may not be in the initial array of direct tools and still be found through a legitimate deferred search. A diagnosis has to follow the exposure surface that tool actually takes, rather than only printing one global list.

Q014｜Which messages does MCP go through from connection to calling a tool? Who are the Host, the Client and the Server?

What to know first for this question A tool is a callable action, a resource is readable content, and a prompt template is reusable input material; discovering a capability and exposing it each turn are not the same step.
Lesson 08 · Tools and MCPLesson 13 · Skills, routing and multi-agent

Core answer

Host is the application that carries the Agent and the user interaction; MCP Client is the component inside the Host that communicates with one particular Server; the Server exposes capabilities such as tools and resources. After connecting, the protocol version and the capabilities are negotiated first, and only then does normal operation begin; discovering tools does not mean they are all fed to the model automatically.[MCP][MCP-LIFE]

Walking one read-only query through in protocol order

What follows is a reduced set of teaching messages; the names and versions are an example configuration.

{"jsonrpc":"2.0","id":1,"method":"initialize",
 "params":{"protocolVersion":"2025-11-25","capabilities":{},
 "clientInfo":{"name":"study-host","version":"1.0"}}}

The Server answers with the same id, returning the protocol version it supports, serverInfo and, for example, the tools capability. The Client checks whether that is compatible, then sends the id-less notifications/initialized, which says that initialization is complete. A request has an id so the response can be matched to it; a notification expects no corresponding response.

Next the Client sends tools/list, and the Server returns the tool names, description, inputSchema and possibly a nextCursor. If there is pagination, requests continue until the needed discovery is complete. The Host converts the selected tool definitions into a form the model interface supports; this step is Host policy, not the Server directly controlling the model's prompt.

After the model proposes search_docs(query), the Host checks authorization and parameters, and the Client sends:

{"jsonrpc":"2.0","id":2,"method":"tools/call",
 "params":{"name":"search_docs","arguments":{"query":"部署步骤"}}}
Start with the objects and symbols used here
call_id、item_id、request_id
These are identifiers for objects at different layers: a tool call, an output item, a request or a response. They match increments and results back to the right object; they are not the token IDs of the model input, and they are not business idempotency keys by nature. Two read_file calls can carry c1 and c2; when the results come back in the reverse order they are still paired by call identifier, not guessed by tool name.
Start with the objects and symbols used here
JSON: structured text, not an action being executed
JSON is a text format that expresses data as objects, arrays, strings, numbers and so on. A braced object maps field names to values; a bracketed array keeps the order of its items. Parsing JSON only yields data; it does not automatically run a tool name inside it. Independent example: {"path":"a.py","limit":3} has two fields; "3" is a string while 3 is a number, and a schema can require either one.

The Server returns a result or a protocol error. The Host then converts the content into a model tool result, tied to the call_id on the model side. MCP's JSON-RPC id and the call_id on the model side belong to different protocol layers; an application may map between them, but must not assume the two are naturally the same.

JSON-RPC, stdio and HTTP
JSON-RPC lays down how a method, its arguments, an identifier and a result are represented in JSON; stdio communicates over a process's standard input and output; HTTP is a network request protocol at another layer. The name of a protocol carries no permission with it. When stdout carries protocol messages, ordinary debug logs should be kept out of that stream and usually go to stderr; otherwise even legitimate logs can break message parsing.

Follow-up: in stdio mode, why can logs not just be written to stdout?

stdout is used to carry the protocol messages, and ordinary logs mixed into it break parsing. Logs should go through the agreed logging mechanism or to stderr. HTTP transport, on the other hand, has its own set of connection, identity and session requirements. A different transport does not change the tool schema semantics, but it does change the deployment and the failure modes.

Follow-up: when the protocol versions are incompatible, can a call still be attempted?

Compatibility must not be assumed. Initialization exists precisely to establish a common interpretation. The client needs to check whether the version the server returns is supported; otherwise it should exit or follow an explicit compatibility policy. Treating every difference as an ordinary parameter error and letting the model guess turns a protocol problem into pointless Token consumption.

Follow-up: why is a capability declaration not the same as security authorization?

capabilities states which protocol features each side supports; it does not prove that the current user can read every resource or execute every tool. The Server still has to authenticate and authorize, and the Host still has to control which capabilities go to the model and when a side effect is approved. When tool annotations come from an untrusted Server, they cannot be taken as security fact.[MCP-TOOLS]

MCP connects but the tools are missing: how are initialization, pagination and the error levels checked one by one?

Prerequisite: Lesson 07 · Lesson 08. Reading order: confirm the run contract first, then look at the counterexamples and the fix, and finally test the limits.

A successful connection only reaches the transport layer

Under the MCP2025-11-25 protocol pinned for this section, the client first negotiates the version and the capabilities, completes the initialization life cycle, and only then uses the corresponding business capabilities. TCP or stdio being connected does not mean that the two sides already agree on the protocol version, the tool capabilities and the notification conventions.[MCPLIFE]

Record the transport type, the negotiated version, both sides' capabilities and the initialized state. The protocol version is a fact about the run; it must not be inferred from "the package name looks new".

tools/list must not be assumed to have only one page

Tool enumeration may carry a nextCursor. The teaching service returns only read plus a pointer to the next page on the first page, and write on the second. Taking only the first page leads to the wrong conclusion that "the system has no write tool"; at that point, going on to improve the tool descriptions is pointless. The local simulation verifies that a complete traversal gives read and write. Changes to the tool list also have to be handled through capability negotiation, with notifications such as listChanged; the first snapshot cannot be used forever.[MCPTOOLS]

Three kinds of failure should stay in different layers

A transport failure means the request or the response may not have arrived; a JSON-RPC protocol error points to a problem with the request format, the method or protocol handling; isError in a tool result says the tool's business execution went wrong. Turning the last of these into plain natural language, "seems to have succeeded", loses the structured state; treating the first as business not executed can make a retry dangerous.

A tool can quite normally return a result that carries an error status, so HTTP success and successful JSON parsing do not entail tool success. Which particular error may be retried depends on whether the action happened, whether it is idempotent and whether it is still within the authorized scope.

stdio carries an engineering constraint that is easy to overlook

When stdout carries the protocol message stream, debug logs cannot be written into that same stream, breaking its frames. Put diagnostic output on the agreed log channel, and have the protocol parser report the source clearly when it meets an invalid frame. Do not lump every error of this kind together as "the tool will not connect"; keeping the event boundary before and after initialization makes them easier to locate.

Follow-up: if a tool annotation says read-only, can the harness skip review?

A remote declaration cannot be trusted as a matter of course. An annotation can help orchestration, but it is not proof of authorization; the harness should still limit side effects through its capability implementation and its permission boundaries. The tool description of a third-party service may also be untrusted input.

Follow-up: can upgrading the protocol fix a missing-tools problem by itself?

Not necessarily. A missed page, a cache that was not invalidated, a tool-name filter and a permission exclusion can all produce the same symptom. Judge from the logs which layer it was lost in first, then decide whether to upgrade. A version migration needs a compatibility matrix; not every anomaly should be treated as a bug in the old version.

Q015｜What are MCP Tools, Resources, Prompts and Skills?

What to know first for this question Initialization negotiates capabilities, discovery lists the interfaces, and only a call executes an action. The process, the network connection and authentication each fail in their own way, and an error has to be matched to the right layer.
Lesson 07 · APIs and streaming protocolsLesson 08 · Tools and MCPLesson 26 · Retries, idempotence and transactions

Core answer

Tools provide callable actions; Resources provide readable data objects; Prompts provide parameterizable prompt templates; Skills organize reusable task knowledge, instructions and resources. MCP solves the interconnection of interfaces and Skills solve the discovery and loading of a professional working method; the two can work together but do not replace each other.[MCP][SKILLS]

Compared against one case of "investigating a live error"

An error log can be a resource, or it can be returned by a query tool; searching the run log is a tool; an "incident post-mortem template" can be a prompt; "how to locate concurrent duplicate writes, and which evidence to check" can be a skill. A skill may require a particular MCP tool, but that does not automatically install the Server, grant credentials or guarantee that a sub-agent inherits it.

Progressive loading usually lets the model see compact metadata first, reads the detailed instructions once relevance is confirmed, and only reads the attached material when execution reaches a particular step. This reduces the default context, but the discovery path has to be kept. If the name is too general and the description has no trigger condition, the model may never read the content that would really help.

A resource link is only a reference. Whether the link can be read, whose identity it is read under, and whether a separate capability is needed are all for an actual tool to settle. Putting a URI into the model's input does not give the model the bytes of the file. When a resource version changes, a summary already saved may also be out of date.

Follow-up: why is "once MCP is installed the model should know everything" the wrong expectation?

Connection, discovery, exposure and selection are different stages. The Host may load only some of the tools, miss a page, or hit a name collision; the model may also have no intention of making the call. Check the logs stage by stage, rather than putting a call that never happened down to the model not being clever enough.

Follow-up: can MCP let different agents share a complete memory?

It can expose a read/write interface for memory, but it does not automatically define memory semantics, conflict handling, visibility scope or a compaction policy. Two agents may access different namespaces even on the same Server; shared storage also brings contention and contamination. Being connected by a protocol is not the same as agreeing on what is known.

Follow-up: when is plain REST enough?

When there are few tools, the application is a single one and a stable SDK already exists, wrapping REST directly may be the simplest thing. When discovery has to be reused across several Hosts, and the resource and tool interfaces standardized, MCP is worth more. Judge the technical choice by what the integration gains; there is no need to deploy a full protocol service for one local function.

Q016｜How should MCP errors be layered? Where are the identity and network boundaries?

What to know first for this question An OAuth scope constrains the actions that were granted, and the server should also check what the object belongs to. Combining tools programmatically can cut down interaction, but the wider the execution surface, the more constraint it needs.
Lesson 08 · Tools and MCPLesson 26 · Retries, idempotence and transactionsLesson 29 · Security basics

Core answer

Distinguish transport, protocol, tool execution, business and authorization problems. They differ in retry, in what is exposed to the model and in how they recover. A remote Server usually has its own permissions and environment; a local shell sandbox cannot be assumed to constrain remote MCP operations.[MCP-TOOLS][CODEX]

Working back from one timeout to where it may have happened

If the connection failed to establish, the request may not have been sent; if the Server received the request but a downstream call timed out, the side effect may already have happened; if the Server finished executing but the response was lost, the client sees only a wait that timed out. All three can show up as "timeout", but they differ in whether a retry is safe.

An unknown method or a format error at the JSON-RPC layer is not the same as a tool result with isError:true. The latter can indicate a query syntax error, a business condition not met and so on, letting the model correct exactly what is wrong. HTTP401/403, certificate problems and a process exit should be handled by the connection and permission layers, and must not be papered over by the model changing business parameters.

The identity chain has to be traced as well: who the user is, whose credentials the Host uses, who the Server acts for when it reaches downstream, and whether the tool result contains another tenant's data. If a shared service account has too much permission, the model only has to construct a different resource_id to cross the boundary; schema validation will not stop that access.

Follow-up: the server says the tool is read-only. Can that be trusted as it stands?

Only a trusted service and a reviewed implementation can support that kind of security judgment. An annotation or a description is metadata, not a sandbox. A query can also trigger a side effect through malicious input, or send sensitive data onto the network. Real control is needed over the implementation, the target address and resource permissions.

Follow-up: should every tool failure be returned to the model?

Actionable business feedback should be returned; sensitive stack traces, credentials and attack payloads should not be exposed as they are. An unrecoverable infrastructure failure can simply end the task or degrade it, instead of letting the model guess again and again. Return a concise error category and the known execution state, and keep the original log for those with permission to diagnose.

Follow-up: why can it not fall back automatically to a tool with more permission?

Because the failure may be exactly the authorization boundary. Switching to a full-permission shell to reach the database after a restricted query is refused, for instance, goes around the user's authorization. A fallback should stay within equal or smaller permission; widening permission is a new decision, not ordinary fault tolerance.

Token audience, permission scope and session ID: three kinds of "credential" that cannot stand in for one another

Prerequisite: Lesson 08 · Lesson 29. Reading order: confirm the run contract first, then the counterexamples and the fix, and test the limits last.

Define identity, audience and permission scope first

Identity answers "who is calling", audience answers "which service the token is to be used by", and scope answers "which operations are allowed". A session_id is usually only used to correlate a session and cannot automatically prove any of the three. The MCP security guidance discusses risks such as token passthrough, the confused deputy and session hijacking explicitly.[MCPSEC]

The confused deputy here can be read as "a deputy that has permission is led into exceeding its authority on someone else's behalf". Even if the user grants the deputy only read permission, a deputy that uses its own high-permission token to carry out whatever the model proposes may still cross the user's authorization boundary.

How a token that looks legitimate comes to be wrongly accepted

Suppose the claims, whose signature a trusted library has already verified, are aud=service-A, scope=[read], sub=u1. If service-B accepts it just because it sees read, it has ignored that the token was not issued to it. Conversely, a correct aud with a scope that does not include write still cannot write. The local test only checks the policy logic over already-verified claims; it does not implement JWT signature verification, and is no proof that production OAuth is secure.

A downstream call needs a legitimate token for the downstream resource, or an explicitly permitted exchange mechanism; passing the upstream token through unchanged must not be treated as general authorization. The origin, the target resource and the user's intent should all be traceable.

Do not let the model decide what is authorized

The model may suggest tools and resources, but trusted code has to normalize the target, check the tenant and the user, and limit the network range that can be reached. URL redirects, changes in DNS resolution and access to internal addresses can all break a plain string allowlist; the actual protection comes from the network and runtime implementation, and cannot be replaced by telling the model "do not access the internal network".

Follow-up: is a user confirmation dialog enough on its own?

A confirmation must be bound to the specific action and its parameters. If the user confirms reading file a and the executor then accepts the model changing it to writing file b, confirmation and execution have come apart. The approval evidence should be bound to a normalized intent fingerprint, the target version and a validity period; see the concrete test in E48.

Follow-up: if the servers are all on the internal network, is scope still worth distinguishing?

Yes. A position on the internal network is not a user identity, and does not mean every service may act for every user. Least privilege and resource-level validation serve to limit the impact of one component being compromised or of the model acting wrongly; they are not only a defense against attacks from the public internet.
