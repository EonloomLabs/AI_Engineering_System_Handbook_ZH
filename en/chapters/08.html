Prerequisites for this chapter

Serving performance is not only how many tokens are generated per second; it also covers queuing, the first character, tools and recovery time. Parallelism may save wall-clock time and it may also add communication; higher throughput is no guarantee that any one person's response comes back faster.

Each question in this chapter lists the groundwork it needs. You can take the matching Foundations lesson first, or use the self-check to confirm how well you have it.

A quick check before the deep reading: change the serial task 2+3+4+1 into 2+max(3,4)+1, then add a coordination overhead of 4, and see for yourself how parallelism turns from an advantage into a disadvantage.

The model's forward pass is only one part of serving. How long a request waits in the queue, which other requests it runs with, whether its KV gets preempted, and when the output comes back all decide the speed the user feels.

Q097｜What is the difference between continuous batching and an ordinary batch? Why does prefill interfere with decode?

What to know first for this question Dynamic batching adjusts the set of active requests between generation steps; waiting to fill a batch and hardware utilization are a trade-off, and a fixed batch is not always the fastest.
Lesson 38 · Batching and paddingLesson 58 · KV cache explained from scratchLesson 62 · Computing fast and fitting in memoryLesson 33 · Reading a production run

Core answer

An ordinary static batch usually waits for a whole group of requests to finish before switching to the next; continuous batching dynamically removes completed requests and admits new ones between generation iterations, raising device utilization. A long Prefill computation competes with short decode iterations for the device, so the scheduling policy has to weigh the latency of the first Token, the interval between later tokens and overall throughput.[PAGED]

Tracking four requests

A needs to generate 100 tokens, B only 5. In a static batch B finishes quickly, but it may go on holding its fixed batch slot while A has not finished. Iteration-level scheduling lets C in once B finishes; C completes its prefill first and then joins the later decode steps. If D suddenly arrives with an extremely long prompt, doing its prefill in one go may occupy a fairly long amount of GPU time, stalling the token output of A and C.

Chunked prefill processes D's input in chunks, so the scheduler can fit decode steps for existing requests between the chunks. This reduces some blocking, but D needs more scheduling rounds to build its complete prefix, and scheduling and cache management become more complex. How a particular engine blends prefill with decode, and how large the token budget per round is, are version and configuration behavior, not one algorithm shared by every service.

A scheduler is usually constrained at the same time by the maximum batch token count, KV capacity, queue priority and request length. Limiting by the number of requests alone is not enough: a 100-token request and a 100k-token request cost very different resources. It also has to keep short tasks from jumping the queue forever and starving the long ones.

How to read the changes in the figure

With a fixed whole-batch policy, slot 0 may wait for B after A finishes; continuous batching lets C use that gap, which raises device utilization.

C is deliberately set here to have finished prefill; otherwise admitting C would also mean handling a long input, which could crowd out B while it is decoding. Real scheduling has to deal with that interference.

Comparing performance means looking at throughput, the wait for the first token and the interval per token together; more tasks may be done overall while one short request is still slowed by queueing.

Do not conflate: the three steps being drawn the same height is schematic; it does not mean each step takes the same number of milliseconds, still less that this is a measured speed-up of a product.

Follow-up: does high throughput mean an individual user is served faster?

Start with the objects and symbols used here
TTFT, TPOT, p95 and throughput
TTFT is the latency from the request to the first output token; TPOT describes the statistics of the time per token after that; p95 is the quantile that about 95% of observations in a given window do not exceed; throughput is the amount completed per unit of time. Say where the timing starts and stops. A fast first character does not mean a fast task: tool execution may still take a long time. Nor does theoretical peak throughput equal the latency one user sees.

Not necessarily. A larger batch may raise total tokens/s, but it adds queuing and waiting at every step. Interactive online use usually cares about the tail quantiles of TTFT and of the token interval; offline batch processing cares more about unit cost and total throughput. The serving goal has to be fixed first, and only then the scheduling parameters chosen.

Follow-up: could every request be prefilled first and only then decoded?

That might reduce some scheduling complexity, but it would leave requests that are already ready waiting for later long inputs. Conversely, giving decode absolute priority would leave new requests without a first token for a long time. Scheduling allocates waiting under limited compute and KV capacity; there is no single fixed rule that is optimal for every load.

Follow-up: why can client retries make a service slower?

If a timed-out request is still running on the server, a client retry may create a duplicate task, add to the queue and the KV load, and so cause still more timeouts. Request identity, cancellation semantics and the server's ability to deduplicate have to be made explicit, together with backoff and an overall deadline. A retry is not a free fault-tolerance button.

Engineering deep dive · E15 · continues Q029

Throughput falls while the GPU is busy: it may be KV preemption and recomputation, not a shortage of compute

Prerequisite: Lesson 58 · Lesson 62 · Lesson 33. Reading order: confirm the run contract first, then the counterexamples and the fix, and test the limits last.

The number of requests is not a sufficient measure of cache capacity

The same 3 requests with lengths [4,4,3] occupy 11 slots; appending one token to each at the next step makes 14. If capacity is only 12, "it fits" now does not mean it will still fit at the next step. Real capacity is also multiplied by the number of layers, the number of K/V heads, the width per head and the dtype, and is affected by paging, prefix sharing and other VRAM use.

The official vLLM tuning documentation discusses preemption and recomputation when KV runs short explicitly; they can keep the system moving forward, but they add end-to-end latency.[SCHED] This is the concrete mechanism to look at when inspecting a service; not every instance of high latency should be put down to "the model is slow at inference".

Follow the causal chain that matches the symptom you see

If there is no first token for a long time after a request arrives, start by separating queuing, prefill and the first output; if output has started but keeps stalling, look at decode scheduling, the preemption count, the currently active tokens and recomputation. If GPU utilization is high but useful output is low, repeated prefill may be eating the work. Looking only at total tokens/s can also hide the cost of recomputation.

Chunked prefill is not costless magic

A long prompt occupies the device in one go and holds back streaming requests that are already running. Splitting prefill into chunks lets it interleave with decode, and the current vLLM design describes the priority policy involved.[SCHED] But chunks that are too small add scheduling overhead, and leaning too far toward decode makes TTFT worse for new long requests. Look at TTFT, inter-token latency, completed-request throughput and tail waiting at the same time, at the very least; one average cannot optimize every experience.

Order of operations and verification

First fix the input-length/output-length distribution, the arrival rate and the cancellation rate in the load, and record capacity and preemption; only then change one budget or concurrency parameter. Raising GPU memory utilization, reducing concurrency, adjusting the token budget and widening parallelism each carry risk, and should not all be changed at once followed by "it got faster". Keep OOMs, timeouts and failed requests in the denominator.

Follow-up: does simply raising max_num_seqs make things faster?

It raises the ceiling on concurrency; it does not create KV capacity or bandwidth out of nothing, and set too high it triggers preemption instead. If the device was idle before, throughput may improve; if it was already cache-limited, things may get worse. Judge by the actual active tokens and capacity, not by the apparent growth in the request count.

Follow-up: does a prefix-cache hit reduce the history read at every decode step?

It reduces the work of rebuilding the prefix K/V; a new query usually still has to read the relevant past K/V. A cache does not turn long-context attention into constant time. The longer the history, the more storage and reading remain the critical resources.[PREFIX]

Separate the four accounts first

Parameter storage, temporary activations, gradient/optimizer state and the KV cache are different objects. Training often saves activations for the backward pass and maintains gradients and Adam state; generative inference usually needs no optimizer state, but a long context may take up a great deal of KV.

For the worked model, the 236 float64 parameters are 1888 bytes of raw values; gradients of the same size add another 1888 bytes, and one copy each of Adam m/v adds a further 3776 bytes. This is array bookkeeping only: it excludes activations, framework objects, the allocator and temporary memory, and it is certainly not a measured process RSS.

KV cache: trading memory for repeated computation of the history

It keeps the past K/V that has already been computed, on the condition that the corresponding prefix and parameters are still valid. As the cache grows with a long context, VRAM use and the amount read grow with it. Do not look only at the 1 new token fed in at each step and assume the reading work is independent of history length too.

FlashAttention: the same objective, different intermediate storage access

A straightforward conceptual implementation forms the whole T×T table of scores and weights explicitly; the blocked algorithm handles local blocks in a more suitable level of storage, maintains online softmax statistics, and avoids writing large intermediate tables back to VRAM over and over. It is not Top-k sparse attention, and it is not "looking at only a few positions".

An independent online-statistics formula: there is already a maximum m, an exponential sum l and a weighted sum of values o; with a new block maximum m_b, take m'=max(m,m_b), multiply the old statistics by exp(m−m') first, and accumulate the new block's contribution as exp(s−m'). At the end o/l corresponds to the result of the full softmax weighting. Concatenating each block's local probabilities directly, without reconciling the normalization constant again, gives the wrong answer.

PagedAttention and continuous batching: managing storage and scheduling

Paged management cuts logically contiguous KV into physical blocks, reducing the waste caused by reserving contiguous space for different growth lengths; it does not change the mathematical definition of attention. Continuous batching can let a new request join as soon as one completes, raising device utilization; it also brings in trade-offs between scheduling, prefill/decode interference and tail latency.

Q098｜How are TTFT, TPOT and end-to-end latency taken apart? How is Roofline used to locate the bottleneck?

What to know first for this question Arithmetic intensity compares the amount of computation with the amount of data moved, and the bandwidth ceiling is not the compute ceiling. Latency to the first character and the latency of each later token have to be diagnosed separately.
Lesson 40 · What "putting it on the device" meansLesson 42 · The arithmetic a model does mostLesson 62 · Computing fast and fitting in memoryLesson 33 · Reading a production run

Core answer

TTFT is the time from the request to the first output token, including queuing, prefill and so on; TPOT describes the average or a quantile of the latency for generating later tokens; the total time for a task also includes retrieval, tools and multi-turn calls. Roofline uses the amount of computation and the amount of data moved to estimate whether something is compute-bound or bandwidth-bound, but it is only an upper-bound model and does not replace measurement.

For a single generation one can write roughly T ≈ T_queue + T_prefill + M*t_decode, but the real time per decode step varies with length and batch, and preemption may be mixed in. The first token may come from the prefill's final logits, so a whole extra decode step should not be counted on top of it. Streaming improves the perceived wait, but it does not automatically reduce the total computation.

Start with the objects and symbols used here
HBM, SRAM and bandwidth
HBM here means the larger high-bandwidth memory on a GPU; the related on-chip SRAM is usually smaller and closer to the computation. Bandwidth is how many bytes can be moved in a given time; arithmetic intensity is the ratio of computation to data moved. Independent accounting: 100 operations against 10 bytes moved is about 10 operations per byte. It is not a measurement of real hardware performance.

A simplified Roofline estimate: given F floating-point operations, R bytes of memory transfer, an effective device compute rate C and a bandwidth B, the time is not less than max(F/C,R/B). If the arithmetic intensity F/R is smaller than the hardware's C/B, bandwidth is the more likely constraint. The large matrix multiplications of prefill usually make better use of the compute; low-batch decode often involves a great deal of weight/KV reading and may be more affected by bandwidth. In practice communication, scheduling, kernel launches and cache hits have an effect as well.

A teaching example: one step needs to read 20GB of data at an effective bandwidth of 1TB/s, so the data-movement lower bound alone is about 20ms; even doubling the theoretical compute rate would not necessarily improve that term. Follow-up: does cutting input tokens always save more time than cutting output tokens?

Not necessarily. Input can be processed in parallel during prefill, while output has an autoregressive dependency; shortening the output saves many decode steps and is often very effective. But the prefill and the later KV reading that an extremely long input brings can also dominate. Cache hits matter too: editing a prefix may force a recomputation of content that could have been reused. Optimization should be checked against the actual trace, rather than by counting total tokens alone.

Follow-up: why do users still complain when average latency has fallen?

Possibly P95/P99 has got worse, long tasks are being preempted, or tools occasionally time out. An average hides the tail and the differences between request types. Slice by context length, output length, tool type, cache hit, tenant/region and so on, while watching the sample size and privacy.

Follow-up: which optimizations only move the work somewhere else?

Offline precomputation, cache warming, an extra compression model and parallel retrieval can all reduce the interactive wait, but they add background computation, storage or load on other requests. The total cost and resource use per successful task should be counted, rather than only watching some local span get shorter.

Q099｜Why can speculative decoding be faster and still preserve the target distribution?

What to know first for this question The draft proposes candidates first and the target model verifies them. Preserving the target distribution needs the right acceptance probability and a correction after a rejection; it is not just a matter of whether the two models agree.
Lesson 44 · Probability, exponentials and softmaxLesson 57 · From the last row of numbers to one token, and on to a whole answerLesson 62 · Computing fast and fitting in memory

Core answer

A cheap draft model first proposes several candidate tokens, and the target model then verifies those positions in one pass; when enough of the draft is accepted, the serial calls to the target model are reduced. Standard stochastic speculative decoding uses an acceptance probability and residual sampling after a rejection, so that the final distribution matches the target sampling distribution instead of blindly adopting the draft.[SPECULATIVE]

Deriving correctness from the single-step distribution

With a target distribution p and a draft distribution q, first sample x~q, and accept it with probability min(1,p(x)/q(x)). The probability that the accepted path lands on x is therefore min(p(x),q(x)). The remaining target mass is max(p(x)−q(x),0); on a rejection, sampling from this residual distribution once normalized puts the target's shortfall back.

Example: p=[0.6,0.3,0.1], q=[0.4,0.4,0.2], so the acceptance rates of the three candidates are [1,0.75,0.5], the accepted mass is [0.4,0.3,0.1], the total rejection probability is 0.2; the residual sits entirely on the first candidate, so the final result is still [0.6,0.3,0.1]. The calculation script in this package checks this identity.

With several tokens, the draft proposes K tokens from the prefix it has generated itself, and the target model computes the distributions at those conditioned positions in parallel. They are checked in order, and after the first rejection the rest of the draft cannot be kept, because the conditioning prefix has changed. The corresponding cache has to be rolled back and generation continued from the corrected position. When everything is accepted, an extra token can also be taken from the target distribution; the exact protocol depends on the implementation.

It is the compensation when a draft is rejected that keeps the target distribution from being skewed

Follow-up: why is a longer draft not necessarily faster?

Generating the draft itself has a cost, and later tokens are the more likely to be discarded once an earlier one is rejected; verifying a long block also consumes compute and KV. The best length depends on the acceptance rate, the draft/target speeds and the hardware. A shift in the task distribution can cost a draft model that was effective before its advantage.

Follow-up: on which distribution should temperature and Top-p be handled?

Start with the objects and symbols used here
Top-k, Top-p and renormalization
Top-k keeps the k items with the highest probability; Top-p sorts by descending probability and keeps the leading candidates until the cumulative probability reaches a threshold. When used for sampling, the kept candidates have to be renormalized over the remaining total mass. Here k is a number of candidates and p a cumulative-probability threshold; k is not the attention Key table K, nor the representation width d_k.

The acceptance and residual formulas have to correspond to the target distribution one actually wants to sample from, and to the actual draft distribution. If the target has already had Top-p applied but the ratio still uses the original softmax, distribution consistency may be broken. Greedy speculation has its own simpler matching rule, and the stochastic sampling formula and greedy verification must not be mixed at will.

Follow-up: why does preserving the distribution not guarantee the same token-by-token output as ordinary generation?

The same distribution does not mean the same path from the same random seed. The order in which random numbers are consumed, the floating-point arithmetic and the implementation may all differ. The correct promise is equivalence of distribution under the algorithm's conditions, not a bit-for-bit identical string under arbitrary settings, and certainly not that the answer is factually correct.

After speculative sampling has rejected a draft, why can it not simply draw again from the target distribution?

Prerequisite: Lesson 44 · Lesson 57. Reading order: confirm the runtime contract first, then look at the counterexamples and the fix, and finally test the limits.

Preserving the distribution is an algorithmic constraint; a high draft accuracy is not enough

Let the target model's distribution be p and the draft distribution be q; once the draft proposes x, it is accepted with probability min(1,p(x)/q(x)). On a rejection, resampling has to follow a residual distribution proportional to max(p−q,0); the support set and the total also have to be handled correctly. What is discussed here is stochastic speculative sampling, not token-by-token greedy verification. The original research describes an exact sampling method that preserves the target distribution.[SPEC]

Two candidates are enough to expose the error

Fix p=[0.8,0.2] and q=[0.2,0.8]. Draft A has probability 0.2 and is always accepted; draft B has probability 0.8 but is accepted with only 0.25, an accepted mass of 0.2. The accepted part is therefore [A:0.2,B:0.2], leaving a rejection probability of 0.6.

The correct residual is [0.6,0] normalized, that is, all of it goes to A, so the final result is [0.8,0.2]. If a rejection is followed by drawing straight from p, the final A is 0.2+0.6×0.8=0.68 and B is 0.2+0.6×0.2=0.32. That is still a legitimate distribution, but it is no longer the target model. The program enumerates the probability mass to verify these two results, so it does not depend on random sampling error.

A multi-token draft also brings state rollback with it

If the draft proposes k tokens and only the first r are accepted, both the target KV and the draft KV have to be trimmed to the correct prefix before the replacement token is handled. The K/V of the draft after the rejection must not be left in the visible cache. If a multi-token batch is used for verification, check which successor token each position predicts, to avoid an off-by-one.

Where the speed-up comes from, and when it disappears

The target model can verify several known draft positions in parallel, reducing expensive serial rounds. But generating the draft costs something too, and there may be no gain when the acceptance rate is low, the target verification is expensive or the batch scheduling does not suit it. A correctness proof concerns only the distribution; it does not automatically prove the latency got better. Real throughput and latency have to be compared under the same target distribution and task constraints.

Follow-up: is comparing the final sentences for a match enough to accept it?

Not for stochastic sampling: two draws from the same distribution can perfectly well give different sentences. Use a finite vocabulary for an exact probability-mass check first, then measure the empirical distribution, and check the cache trimming and the stopping separately. Greedy mode has its own dedicated equivalence condition, and the verification rules must not be mixed.

Follow-up: what about p/q when q(x)=0?

The draft cannot propose that x under q, so the acceptance ratio only has to be computed at the proposal points that actually lie in the draft's support set; the target mass the draft cannot cover is corrected through the residual and the like. An implementation should still check explicitly for floating-point underflow and invalid probabilities, rather than passing a division-by-zero nan further down.

Q100｜What do DP, TP, PP, ZeRO and prefill/decode separation each split?

What to know first for this question Data parallelism replicates the model to handle different samples; tensor parallelism splits the operations; pipelining splits the layers; sharding the state reduces duplicated storage. Communication is a cost too.
Lesson 40 · What "putting it on the device" meansLesson 42 · The arithmetic a model does mostLesson 53 · One training run end to endLesson 62 · Computing fast and fitting in memory

Core answer

Start with the objects and symbols used here
DP, TP, PP, ZeRO and FSDP
Data parallelism lets several copies of the model process different samples and synchronize their gradients; tensor parallelism splits the parameters and the computation of a single operator; pipeline parallelism puts different layers on different devices. ZeRO/FSDP-style techniques also shard parameters, gradients or optimizer state. What they split differs: dividing one layer's matrix in two is not the same as giving two independent user tasks to two agents.

Data Parallel replicates the model to handle different data; Tensor Parallel splits the tensor computation inside a layer; Pipeline Parallel segments it by layer; ZeRO-style techniques split redundant training state; prefill/decode separation lets different resources take on the two inference phases. They act on different objects with different communication patterns, so one should not simply memorize "spread the model across several cards".

Explaining TP and PP with one forward pass

A large linear layer Y=XW can be split across several devices by the output columns of W, with each card computing part of the output; if a later layer needs the complete Y, that takes communication or a matching sharded layout. Splitting along the input dimension instead produces several partial sums, which have to be reduced. attention heads and the FFN intermediate dimension: how these are split decides when all-reduce/all-gather happens, and not every layer can simply concatenate the results.

PP puts the first few layers on device A and the later ones on B. A micro-batch goes through A first, and its activations are then sent to B; several micro-batches can form a pipeline, but there are bubbles at the start and the end. Unbalanced computation across the stages makes the fast device wait for the slow one; and inference on a single autoregressive sequence still has to pass through every stage again at each token.

DP suits parallel processing when there are several requests or samples; if a single model does not fit on one card, plain DP does not solve that. In training each replica has to synchronize gradients; in inference independent replicas can usually serve requests independently. ZeRO/FSDP shard the optimizer, the gradients and even the parameters, reducing duplication across training replicas, but they have to communicate to fetch the relevant part when the computation needs it.

With prefill/decode separation, the prefill device finishes computing and then sends the KV and other necessary state to the decode device. The resources can be optimized separately for throughput and for bandwidth, but the KV transfer can be large: the example in lesson 60 gives 4GiB for a single 32k sequence. If the network is slow, the context short or the request volume small, the gain from separation may be offset by the transfer and the queuing.

Compare the speed-up on a real task and the cost per successful task, rather than using the number of GPUs as a measure of capability.

Follow-up: why can a change in the TP degree affect reproducibility?

Sharding and reduction change the order of floating-point additions, and a tiny change in a logit can change which token wins at the margin. Different kernels may also be used. A correctness test should keep the three levels of numeric tolerance, generation distribution and task result apart, rather than demanding that every parallel topology agree character for character.

Follow-up: do application engineers need to implement these kernels?

Not necessarily, but they do need to know which bottleneck a setting affects. For example, when API latency is dominated by a remote tool, studying TP will not fix it; when a local deployment runs out of KV, look at the context, the concurrency and state management. The point of going deeper into the principles is to be able to locate the boundary correctly, not to rewrite every layer yourself.

Further basis for the distributed-training and parallelism part of this chapter: the PyTorch tensor-parallel documentation and the original ZeRO paper.[TP][ZERO]

First ask which boundary the error happens at

"The model's output is wrong" is not enough on its own to tell whether the learning rate, attention or sampling is at fault. Confirm the identity of the input and the weights first, then check the shared forward pass, and then decide whether it is a training-only step or a generation-only step. Changing ten places at once makes even a correct fix hard to attribute.

Why "the gradient is not 0" is nowhere near enough

A wrong denominator, a missing residual path or a wrong mask can all produce non-zero gradients and make some losses go down. A test should check specific values, relations and an independent comparison, not merely whether there is a .grad.

The gradient comparison in this package is done parameter by parameter at the same initial values and on the same batch; the hand-written backward pass uses the mathematical rules, autograd uses the framework's record, and the finite difference estimates from the difference between real forward passes. The three complement each other, but they can also agree if all of them use the same wrong training objective, so the input and the meaning of the objective still need human interpretation.

Basis: tiny_model.py:53–98; Matching parameters, forward pass and gradient records.

Why negative controls are needed

An implementation that passes one test may simply have assertions that are too weak. After deliberately turning the causal mask off, using the wrong cache position, applying softmax twice or mixing in stale KV, the test should observe a difference. That shows the test can at least identify these specific faults.

The bad implementations in this book are used only for temporary local comparison; they are not saved as the default model and are not mixed into the official weights. The report states clearly which path is the deliberately wrong one, so that readers do not take a wrong formula for a recommended method.

How to choose a numeric tolerance

float64 on the CPU helps with comparison, but not every value has to agree to the last bit. A change in the order of softmax, normalization and matrix accumulation can cause small rounding differences; float16/bfloat16 or a fused kernel can differ more. Look at the absolute error, the relative error, the magnitude of the values and the task result together, and keep non-smooth places such as the ReLU kink in mind.

Replacing every NaN with 0 and then declaring the test passed is forbidden. Confirm the cause first: a fully masked row, overflow, division by zero, contaminated data and so on. Asserting finiteness is where locating the problem starts, not a complete fix.

Follow-up: which changes can claim to preserve the same computational objective?

When the conditions are met, a causal KV cache, correct blocked exact attention and storage paging can preserve the same objective, allowing the floating-point differences the implementation causes; quantization introduces an approximation; Top-k and temperature change the decoding distribution; replacing GQA or the FFN changes the architecture; LoRA training changes the parameters. Identify the type first, and only then is it clear whether consistency, task quality or system performance is what should be evaluated.

When VRAM runs short, are using no_grad and using activation checkpointing the same thing?

Show the answer
No. Training has to keep or rebuild the chain for differentiation; no_grad turns off the recording that is needed and so breaks training. Activation checkpointing restores the necessary intermediate values by recomputing them before the backward pass, and the goal is still a correct gradient.

A test finds a very small difference between the cache and the full computation — can it simply be ignored?

Show the answer
Start with the magnitude of the error, the precision, the kernel and the gap between the candidate scores. If two candidates are almost level, a small error can change the greedy result; if a position or a mask is misaligned, the source has to be explained however small the difference. A tolerance needs its conditions; it cannot all be waved away as "floating-point error".

Acceptance 1: using this book's specific vocabulary, turn "我爱学习！" into training input and labels, and say where peeking at the future is prevented.

Show the answer
The complete sequence is [6,1,2,3,5,7]; the input is [6,1,2,3,5] and the target [1,2,3,5,7]. Attention in row t allows only s≤t, and the label does not enter that row's forward pass; the per-position norm and the FFN do not mix across the future.

Acceptance 2: write out the dependency from the loss down to Wq[0,0]; "autograd" on its own is not an acceptable answer.

Show the answer
L→Gz=(p−onehot)/10→U back to the final F→RMSNorm to H→the residual/FFN merging into R→Wo to mix→G_A→softmax to G_S→the scaled dot product to G_Q→Σ_b,t N1[b,t,0]G_Q[b,t,0]. The K/V and residual paths for earlier inputs have to be merged in as well; at these initial values G_Wq[0,0] is about −0.002217527833.

Acceptance 3: after 学习 is selected for the first time, why is the cache length 3 while the sequence length is 4?

Show the answer
The first forward pass handles only the three positions BOS, 我 and 爱. 学习 is no more than an ID selected from the output distribution; it has not yet gone through E/P and the layer computation as an input. Its K/V is appended only when the next round processes it.

Acceptance 4: the loss after these 400 steps is about 0.13948 — why should it not be forced down to 0 the moment it is seen to be non-zero?

Show the answer
The same BOS prefix is followed with equal frequency by 我/你, so the irreducible ambiguity gives a lower bound of ln2/5≈0.138629 averaged over the ten questions. The data and the objective have to be understood; not every non-zero loss comes from an implementation error.

Acceptance 5: the model is 30% faster on the GPU and the small CPU model's forward pass is unchanged — does that prove the deployment has no regression?

Show the answer
No. The numeric behavior on the target hardware, the actual batch and length distributions, the cache and the mode, quality and tail latency all have to be checked. Consistency in the CPU teaching setup verifies only the mechanism concerned; it is not a guarantee of production quality or speed.
