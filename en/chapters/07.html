Prerequisites for this chapter

Start with the objects and symbols used here
FlashAttention: changing how intermediate data is stored and read
By means such as tiling and online normalization, it avoids keeping the full attention score/weight matrix in slower VRAM for long; the target is still the same attention computation, and floating-point rounding can vary with the order of operations. It does not compress tokens permanently, and it does not skip any Key. Keep "not writing the whole table to VRAM" apart from "not doing this arithmetic at all".
PagedAttention: managing K/V storage in pages
Store a logically contiguous K/V sequence in several physical blocks, located through a block table. It mainly changes how the storage is managed and shared; it does not replace the attention formula with an algorithm that means something else. Independent example: logical positions 0—3 are in physical block 7 and 4—7 in block 2; logical position 4 need not physically follow position 3.

A cache keeps old computation that can be reused; FlashAttention moves less intermediate data; a paged cache changes how storage is managed. All three can improve efficiency, but they are not the same algorithm, and none of them should be understood as compressing meaning.

Q093｜Why can historical K/V be cached while Q usually is not? Give a layer-by-layer explanation.

What to know first for this question Under the causal premise an old position never reads a new one, so the K/V of the old layers can be reused. Changing the history, the model or the definition of position breaks that premise.
Lesson 46 · Attention step by stepLesson 47 · A mask is not a black boxLesson 48 · Position IDs and RoPELesson 58 · KV cache explained from scratch

Core answer

In a causal decoder, the hidden state at an old position depends only on itself and on what precedes it in the sequence (Token); appending a new token does not change those old states. The K/V that each layer projects for the old positions therefore do not change either. A new position needs only its own Q, with which to query that layer's historical K/V; the old outputs that the old Q produced have already been computed and usually do not need to be used again.[CACHE][TR]

"Cache the history" is not a sufficient account

Take it by induction. For the old tokens at layer 0, the embedding, together with the position encoding, does not change. Suppose the layer-l input does not change at the old positions; since the causal mask forbids looking at the newly added position, the set of inputs the old positions attend to (attention) does not change, so the attention output does not change either; FFN, together with normalization, acts on exactly the same inputs as before, so the residual result does not change. The old state at layer l+1 therefore does not change, and the induction holds.

Start with the objects and symbols used here
Wo / W_O: the attention output projection
The parameter matrix that concatenates the attention heads' outputs and then converts them to the width the main network needs. It is still a table of coefficients: not the shares from softmax, and not the vocabulary output head Wout. If two heads each output 2 numbers, the concatenation is 4 wide; multiplying on the right by Wo of shape [4,6] gives 6 numbers, matching the residual width. This is an independent example about shapes.

When a new token is generated, at layer l it first obtains that layer's normalized state and computes q_new,k_new,v_new, appends the new K/V to that layer's cache, performs q_new @ K_allᵀ, softmax, and the weighted sum, then goes on through Wo, the residual and the FFN into the next layer. Only once every layer has been computed do we get the scores that predict the token after that (logits). The cache is not one text vector shared across layers; it is a separate K/V array for every layer.

Start with the objects and symbols used here
d_k, d_v, Dh: the width of each row of representation
d_k is how many components one Query/Key vector has; d_v is how many components one Value vector has. Dh, or d_h, is the single-head width in some chapters. They are size integers, not the k-th Key or some Value number. Shape micro-example: with Q[2,3], K[5,3] and V[5,4], the scores are [2,5] and the output [2,4]. A pairing width of 3 for Q/K with a Value width of 4 is still legitimate.

If only the topmost K/V were saved, the next token would not find the historical representations it needs in the lower layers. If the old Q were saved but not the K/V, that old Q still could not let a new position recover the historical content. A common cache layout gives K and V one array each of shape [B,H_kv,T,Dh], where a kernel may use a different memory arrangement, but the semantic axes should not be confused.

Start with the objects and symbols used here
Query, Key, Value: three intermediate numeric representations
q is one row of query representation for the position receiving information; k is one row of matching representation offered by a readable position; v is one row of content representation that position contributes to the mix. Capital Q/K/V collect several rows into tables. They are computed from the input and the parameters, and they carry the separate jobs of scoring and of supplying content. One q dotted with two k gives two scores; softmax turns them into two shares; those shares multiply the two rows of v, and the results are added. Nothing here generates a search term, and nothing here picks an answer directly.

How to read the changes in the figure

The proof runs forward from the first layer: the old positions cannot see the new d, so the old representations in the first layer are unchanged; the old inputs to the second layer are therefore unchanged too, and so it holds layer by layer.

The old Q was mainly used to compute the output at the old positions. Only the new output for d is required now, and no read needs to be issued with the old Q again, which is why K/V is usually cached and Q is not.

Changing the model parameters, the template or the old positions breaks the premise for reuse. "The same session" is not a mathematical condition for cache validity.

Do not conflate: with bidirectional attention an old position may see newly added content, so this causal-cache argument cannot be applied unconditionally.

Worked example · Q093

A layer-by-layer proof, from causal dependency, of why old K/V do not change

Input and conditions. A two-layer model first processes tokens A and B, then appends C. Every layer is a causal layer with fixed weights, and neither normalization nor the FFN mixes across positions.

Steps and objectsInternal actionIntermediate result / new state
1 Layer 0 inputThe embeddings and positions of A and B are unchangedThe old input is the same.
2 Layer 0 visible setA sees only A; B sees only A and BThe appended C is not within what the old queries can see.
3 Layer 0 resultNeither the old input nor the visible set changesThe layer-0 outputs of A and B do not change.
4 Layer 1 inputComes from the old layer-0 resultSo the K/V of A and B at layer 1 do not change either.
5 What happens for the new CAt each layer only C's Q/K/V are computed, and that layer's A/B cache is consultedNot only the top layer is consulted.
6 CounterexampleB is changed to D but the cache for B and everything after it is still reusedThe premise of causal dependency is broken; recomputation has to start at the change.

Join the steps up. The cache holds because of a conclusion about dependency, not because something happened in the past and is therefore valid for ever.

Limits and counterexamples. A bidirectional model, statistics computed across positions or a dynamic position transform each need their own proof; this example is limited to standard fixed causal layers.

Follow-up: after the 100th token of the prompt is edited, which caches can still be used?

Start with the objects and symbols used here
Schema and Structured Outputs
A schema is a set of structural rules about fields, types and the like; a structured-output mechanism makes it easier for the model to return data that follows those rules. Valid fields still do not mean that the target file exists, that access has been granted, or that the request is right for the business. Independent example: path is required to be a string; {"path":3} does not match the type rule, and {"path":"missing.py"} follows the structure yet may still find no file.

Under the same weights, template, positions and runtime constraints, the caches for tokens 0 through 99 may still be reusable; the 100th and everything that depends on it have changed and need recomputing. What is meant here is the model's actual token prefix, not the identical characters a human eye sees. Changing the system instruction, the tool definition (schema), the adapter or the position rules can change the prefix earlier than that. One cannot simply replace the cache for the edited token and keep every contextualized state after it.

Follow-up: why does training usually not reuse KV across optimization steps?

Once the weights have been updated, the old K/V are no longer what the new parameters compute for the old prefix; and training needs the matching computation graph and gradients. Using an old cache in a forward pass with new weights breaks the consistency of the objective. At inference time, no_grad and fixed parameters are the usual premises for caching, so an inference optimization should not be dropped into an ordinary training loop.

Follow-up: which models cannot be cached directly by this proof?

In a bidirectional encoder an old position can depend on later tokens, so appending input changes the old states; some architectures that normalize across tokens, transform positions dynamically or modify the history also need their own analysis. Sliding windows, recurrent state and hybrid models each have their own state mechanism. The proof in this chapter applies to standard causal layers with a fixed prefix and fixed parameters; it cannot be stretched into a claim that every model caches the same way.

Engineering deep dive · E13 · continues Q025

Two dangers in sharing a cache: an incomplete identity, and aliasing of mutable objects

Prerequisite: Lesson 58 · Lesson 02 · Lesson 26. Reading order: confirm the run contract first, then look at the counterexamples and the fix, and finally test the limits.

A cache hit has to prove that "what was computed is the same function"

K/V come from the prefix and the model's computation; they are not an inherent property of the token string. The same tokens can give different K/V under different weights, adapters, position configurations or multimodal features. vLLM's block cache design uses a prefix chain plus extra identity information, and offers a per-request salt to confine reuse to one trust domain.[PREFIX]

So a cache key is not just "a string hash of today's question". At a minimum, state the computation identity, the exact prefix, the representation layout and the valid positions; fields the server already isolates by namespace need not be repeated in every key, but the isolation condition has to really exist. A tenant salt that limits sharing is not an authentication system: knowing the salt must not grant access to the data.

How shared memory creates cross-request contamination

The teaching program prefix=[1,2,3]; a=prefix; b=prefix lets two requests hold the same mutable list. Once A appends 4, B "sees" 4 as well. Real KV are larger block arrays, but the aliasing problem is the same: a shared complete prefix can be reused read-only, while the appendable tail block needs copy-on-write, exclusive ownership or reference management, depending on the implementation.

This book reproduces the problem with real Python objects, then uses a separate copy of the tail so that B is still [1,2,3]. The experiment explains the risk of mutable sharing; it does not claim to reproduce any particular vLLM bug. Sharing a full block, appending to a partially filled block, and the lifecycle of release should each be verified separately.

Problems a hash alone cannot solve

Even with the right key there can still be a stale pointer, a read that continues after a block has been reclaimed, a writer that misses a lock, or a layout revision that consumers have not picked up. Hash collisions are a separate level; a cryptographic hash can lower the collision risk, but it cannot fix reference counting or a concurrency race.

Follow-up: why do caches usually insist on a contiguous prefix?

In an autoregressive layer the representation at a position depends on the visible content before it. Change one token in the middle and the K/V of many later positions can change, even where the IDs did not. Reusing "the same fragment" without regard for the prefix dependency is wrong; what has to be proved is that the context depended on is the same, not merely that a repeated piece of text has been found.[CACHE]

Follow-up: does a shared prefix have security side effects?

It can. The difference in response time between a hit and a miss can leak the existence of shared state; vLLM's cache_salt is one design for isolating by trust domain. It brings a trade-off between sharing rate and isolation. Do not assume a performance optimization is inherently unrelated to security, and do not claim that one salt solves every side channel.

Evidence for troubleshooting

Record the hit length, the computation identity, the lifecycle of block references, and the comparison result with the cache turned off. A sensitive prompt should not be logged in clear text for the sake of diagnosis. When cross-request inconsistency appears, reproduce "two branches sharing a prefix and each appending a different token" first, rather than only running sequential generation for a single request.

E13: how to read this result, rather than only looking at "pass"

First check that the cache key carries the identity of the model, the adapter, the prefix and the positions; then check whether two requests are accidentally sharing a mutable object. Reuse under an identical key that should not have been reused, and cross-writing caused by object aliasing, are two independent kinds of cache bug.

Q094｜How much computation does a KV cache actually save, and how much VRAM does it take?

What to know first for this question The total cache size counts both K and V, the number of layers, the number of positions, the number of KV heads, the width per head and the bytes per element. Do not put the number of query heads in place of the shared KV head count.
Lesson 36 · A row of numbers, a table and a stack of tablesLesson 40 · What "putting it on the device" meansLesson 58 · KV cache explained from scratch

Core answer

It avoids running the projections, the FFN and the old queries' attention over the whole history again and again; a new query still has to read the historical K/V. The attention in one decode still grows with the cached length, and the generation process as a whole is not unconditionally linear. The memory footprint comes from the number of layers, batch, the number of KV heads, the length, the head dimension and the element type (dtype).

Taking the complexity apart

Start with the objects and symbols used here
O(·): the order of growth with size
Big O expresses an upper bound on the order of growth with size, usually leaving constants and smaller terms out. It has to be said which variables are growing, and whether the count is for a single step or for the whole sequence. O here is not the attention output matrix. When the length doubles, the leading term T² becomes four times as large; but the time actually taken also depends on fixed overhead, memory and hardware utilization, so big O alone is no promise of a measured speed.

Let the model width be d, the prefix P, and M the number of tokens generated. Ignoring constants, the linear projections and FFN of a full forward pass over length T for one layer cost about O(Td²), and attention about O(T²d). Without a cache, every generated step redoes an ever longer prefix.

With the cache in place, Prefill, as before, still processes P positions; each decode does only the new token's projections and FFN, about O(d²), plus the attention of the new Q against T cached K/V, about O(Td). Over M steps the attention comes to roughly O((PM+M²)d), with a further O(Md²) of in-layer computation. That is far less than repeating full forward passes, but it cannot be stated as "KV turns attention from quadratic into linear for ever". Any discussion of complexity has to say whether it is one step or the whole stretch, and whether P is fixed or P and M grow together.

The usual estimate for the cache size in bytes is:

KV bytes = 2 × L × B × T × H_kv × Dh × bytes_per_element

The 2 in front comes from K and V. Teaching example: L=32, B=1, T=32768, H_kv=8, Dh=128, FP16, 2 bytes per element: the result is 4GiB, and each extra token adds about 128KiB. Changing to 32 KV heads with everything else the same makes it 16GiB. The estimate excludes the weights, page fragmentation, workspace and service metadata. How many concurrent requests a device can really take cannot be found by dividing total VRAM by this number alone.

Start with the objects and symbols used here
MHA, MQA, GQA: how heads are shared
An attention head is one path that matches and then aggregates content. MHA usually gives every query head its own K/V head; MQA has several query heads share one group of K/V; GQA sits between them, sharing by group. These are structural choices, not a switch to be flipped at run time. Independent shape example: 8 query heads and 2 K/V heads, grouped evenly, means every 4 query heads share 1 group of K/V; the cache is accounted for by the number of K/V heads.

A cache is counted in bytes; the compute it saves is a separate account

Follow-up: why can long-context decode be limited by memory bandwidth?

The new query needs relatively little computation but has to read a great deal of historical K/V layer by layer; if the arithmetic intensity is low, transfer speed sets the total time. A larger batch can improve the reuse of some weight reads, but it also increases the total KV and the service latency. GPU-level peak throughput being high does not mean that a single long-context request is bound to be faster; that depends on the actual kernels and memory access.

Follow-up: are KV quantization and weight quantization the same optimization?

They quantize different objects. Weight quantization mainly reduces the storage and reading of model parameters; KV quantization mainly reduces the dynamic state that grows with context and concurrency. Error in K changes the attention scores and error in V changes the aggregated result, and both can affect how long-range information is used. Evaluate across different lengths and tasks instead of looking only at the quality of short answers.

Follow-up: how are a prompt cache and a KV cache related?

KV is the form the computation state takes; a prompt cache is a product or system capability by which a service reuses the computation for a repeated prefix, and underneath it may draw on state such as KV. A cache hit has to satisfy the service's rules; a persistent session does not make a hit automatic. API-level billing for cached tokens is not a one-to-one visible mapping onto where the KV physically resides.[PCACHE]

Q095｜Why does FlashAttention save memory? And how is softmax computed without storing the full attention matrix?

What to know first for this question FlashAttention still computes the same attention objective; what it mainly avoids is writing a huge intermediate matrix back to VRAM. Before taking on online normalization, be sure you can shift softmax by its maximum.
Lesson 42 · The arithmetic a model does mostLesson 44 · Probability, exponentials and softmaxLesson 46 · Attention step by stepLesson 62 · Computing fast and fitting in memory

Core answer

FlashAttention: the attention computation is organized in blocks and the faster on-chip memory is used, so the full T×T score and probability matrices are not written back to high-bandwidth memory over and over. It keeps per-query normalization statistics with an online softmax and computes the same kind of exact attention; it is not an approximate retrieval that drops low-weight items.[FLASH]

Deriving the online softmax merge

For one fixed query, take a batch of scores s_j and value vectors v_j. Three quantities are maintained: the current maximum m, the sum of exponentials l, and the unnormalized weighted sum u.

Start with the objects and symbols used here
Σ: sum term by term over the subscript
Σ is shorthand for addition. The subscript says which term varies; a subscript that is not summed over stays fixed. It is not an extra parameter, and it does not mean concatenating arrays. Independent micro-example: Σᵢ xᵢyᵢ with x=[1,2] and y=[3,4] is just 1×3+2×4=11.
m = max(s_j)
l = Σ exp(s_j−m)
u = Σ exp(s_j−m) v_j
最终输出 o = u/l

The statistics of the old block are m_old,l_old,u_old, the maximum score of the new block is m_b. Setting m_new=max(m_old,m_b), then:

α = exp(m_old−m_new)
l_new = α l_old + Σnew exp(s_j−m_new)
u_new = α u_old + Σnew exp(s_j−m_new) v_j

The key point is that when the maximum changes, the old statistics have to be rescaled along with it. Otherwise different blocks use different normalization baselines and the result no longer equals the full softmax. For each query, walk the K/V blocks and divide by l at the end. A matrix kernel processes query blocks in parallel and fuses operations such as the mask and the scaling; the backward pass in training can recompute the blocks it needs from a small amount of saved statistics instead of storing the entire probability matrix.

An example: if the old block has only score 1 and value 2, then m=1,l=1,u=2. With a new block of score 3 and value 10, after merging m=3 and l=exp (−2)+1 and u=2exp(−2)+10, giving an output of about 9.0464. If the old u is not multiplied by exp(−2), the output is plainly wrong.

Follow-up: if the algorithm is exact, why can the results differ bit for bit?

Start with the objects and symbols used here
LoRA, low rank and r
LoRA represents part of a weight increment as the product of two smaller matrices instead of retraining the whole large matrix. r is the inner dimension, and it bounds the maximum rank of that product. Where sources use a row-vector or a column-vector convention, the left-right order of A and B can differ. Micro-example in the right-multiplication convention: with W[4,6], the increment A[4,2]B[2,6] is still [4,6]; r=2. A here is not the table of attention shares.

They are equivalent in real-number mathematics, while the order of floating-point additions, the accumulation precision and kernel fusion introduce tiny errors. "Exact attention" is mainly a contrast with sparse or low-rank approximation; it is not a promise of bit-for-bit agreement across different hardware. Verification should set a reasonable numerical tolerance and distinguish randomness from numerical rounding.

Follow-up: can FlashAttention replace a KV cache?

No. The first optimizes how one attention is computed and how its data is moved; the second avoids recomputing historical state at the next step. The two are usually complementary. Fast attention without KV still recomputes; KV with an inefficient kernel can still move too much data.

Follow-up: does it turn the time complexity from O(T²) into O(T)?

The number of pairs in standard dense attention is still quadratic; what is reduced is memory traffic and intermediate storage. The speedup differs with hardware and length. Carrying one experimental speedup figure from a paper straight over to your own model and GPU is not rigorous; benchmark prefill and decode separately for real.

Why must online softmax rescale the old running totals instead of averaging each block's answer?

Prerequisite: Lesson 44 · Lesson 46 · Lesson 62. Reading order: confirm the run contract first, then look at the counterexamples and the fix, and finally test the limits.

The real difficulty is not "cutting the big matrix into small pieces"

Even after blocking, the globally normalized result for the same softmax row still has to come out. Taking a separate softmax per block and then averaging is equivalent to forcing every block to carry the same total weight, so a block with very high scores and one with very low scores are treated alike. Exact attention implementations of the FlashAttention kind have to maintain normalization statistics across blocks rather than change the attention objective. Different kernels may still end up differing by floating-point rounding.[SDPA]

Tracking three accumulated objects

For the scores s and values v already processed, maintain: m=the current maximum score, l=Σexp(s−m), o=Σexp(s−m)v. o is the unnormalized content sum, not the final output. When the new block's maximum moves the baseline to m′, every old term has to be multiplied by exp(m−m′), because they were counted against the old baseline.

m′ = max(m, 新块最大值)
l′ = exp(m−m′)·l + Σ新块 exp(s−m′)
o′ = exp(m−m′)·o + Σ新块 exp(s−m′)·v
最后输出 = o′ / l′

Updating the maximum without rescaling the old l and o adds numbers measured against different baselines and gives the wrong distribution. This is an invariant of the normalization state, not an implementation detail to be dropped at will.

A counterexample with fixed high scores

With scores [1000,1001,1008,1007] and values [1,0], [0,1], [2,0], [0,2] in order, the whole-row result is about [1.461030,0.538059]. Normalizing the two blocks separately and then averaging gives [0.865529,0.634471], which is plainly not equivalent.

The program shipped with this book accumulates with block lengths of 1, 2, 3 and 4, and each agrees with the stable whole-row softmax to within 1e−12. The test deliberately uses input whose per-block maximum grows sharply from one block to the next; if every block had the same maximum, a missing rescaling could stay hidden.

Masking and mixed precision need extra checks

When a block is fully masked, the difference of infinities must not be allowed to become NaN; it has to be stated that this block contributes nothing to the statistics. A row that is fully masked in the end is still handled as in E04. With FP16 or BF16 input, the precision used for the intermediate statistics affects both the result and the cost; do not infer bit-for-bit agreement on a GPU from this book's double-precision Python results.

Follow-up: is correct blocking always faster?

No. An interpreted implementation on small CPU arrays can be slower. Speedup depends on the device's memory hierarchy, on how parallelism is organized and on kernel fusion; verifying correctness and benchmarking performance are two different jobs. A report has to list the device, the dtype, the length, the batch, the mask, the forward and backward passes and the memory together, not just "n times faster".[SCHED]

Follow-up: if the full weights are not stored, how does the backward pass obtain its gradients?

An implementation can keep the necessary statistics and recompute local blocks on the backward pass, trading that for lower intermediate storage. You have to look at what the kernel you use saves and how it restores things; "no big matrix" does not mean there is too little gradient information, nor that the backward pass needs no extra computation.

Q096｜What exactly does PagedAttention "page"? And why does it raise concurrency?

What to know first for this question Paging puts a logically contiguous cache into physical blocks; a page table records the mapping, and a shared prefix has to take copy-on-write into account. It is not a summary that deletes historical tokens.
Lesson 40 · What "putting it on the device" meansLesson 58 · KV cache explained from scratchLesson 62 · Computing fast and fitting in memory

Core answer

Paging divides each sequence's logically contiguous KV into fixed-size blocks mapped onto a pool of physical KV blocks. Blocks are allocated on demand as the sequence grows, so no large contiguous stretch of VRAM has to be reserved; several requests and a shared prefix can use memory more flexibly. It mainly changes how KV is stored, managed and addressed; it does not change the order of tokens the model sees.[PAGED]

An example with a block size of 4

Request A already has 10 tokens and needs 3 logical blocks. The block table might be A:[7,2,19], pointing at physical blocks 7, 2 and 19 respectively. Logical position 5 lies in logical block 1 at offset 1 within the block, and the access actually goes to offset 1 of physical block 2. Appending A's 11th and 12th tokens fills block 19; only the 13th token needs a new block.

Request B can use physical blocks 3 and 15, with no need to be contiguous with A at all. When a request ends, its references are released and the blocks return to the pool. The last block may have internal fragmentation, but that is usually easier to control than reserving a large stretch per request for the maximum length. The kernel uses the block table to access K/V along the logical sequence, and the positions, lengths and mask all have to stay correct.

If A and B have exactly the same prefix, the prefix blocks can be shared with an increased reference count wherever the implementation's rules allow. Writing a new token into a shared, partially filled last block may require copy-on-write; otherwise A's append contaminates B. The prefix hash also has to carry enough information to distinguish the effective identity — the model, the token prefix, the adapter and so on — and sharing must not go by the human input text alone.

Paging changes physical placement, not the logical order of the tokens

Paging mainly changes memory management. The position rules, the visible range and the Key/Value contents must still match the original sequence; tokens must not be reordered because the storage is scattered.

Do not conflate: the last block is only half used, so there is still internal fragmentation. Paging is not zero waste, and it is not ordinary disk swap standing in for VRAM.

Mechanism basis:[PAGED]. The numbers and harness setting in this example are an explicitly given teaching construction, not commercial model output or a production performance measurement.

Follow-up: why is a smaller block not necessarily better?

Small blocks reduce tail fragmentation but raise the cost of the block table, of addressing and of management; large blocks reduce metadata but waste more space at the tail. The best size depends on the length distribution, the kernel and the device. Paging is not free operating-system magic; it is a concrete trade-off in data layout.

Follow-up: what can a service do when memory runs short?

It can pause or preempt some requests, move state to other storage, recompute the prefix, or refuse new requests. Each policy affects tail latency and throughput. Simply raising the maximum concurrency can trigger repeated swapping out and recomputation, making everything slower overall. Watch KV occupancy, the number of preemptions, queuing time and the rate of successful completion.

Follow-up: is PagedAttention the same as prefix caching?

Paging provides infrastructure suited to sharing and management, while prefix caching decides when an identical prefix is recognized, retained and reused. The two are related but distinct: one can page without caching across requests, and prefix reuse can be implemented with other memory management as well. Do not credit one mechanism's gains to the other's name.
