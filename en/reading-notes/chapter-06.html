When comparing coding products, start from the same public, diagnosable chain: how the context is composed, what the model proposes, how the harness executes, how the result is filled back in, how state is recovered. Whatever a closed-source product has not published about its internals stays unknown; the teaching swimlanes are not a joint claim about the line-by-line source of all three products.

Product mechanisms and public evidence

Start with the objects and symbols used here
IDE, CLI, UI and DOM
IDE is the integrated development environment, CLI the command-line interface, UI the user interface, and DOM the tree of structural objects of a web document. The code, selection and page information that each entry point attaches automatically can differ. The model seeing the selected function in the IDE does not mean the same task in the CLI has received that function; check this turn's input objects first.

Codex, Claude Code and Copilot include clients, models, tools and services, and keep changing. Public documentation describes capabilities, open-source code describes an implementation at a particular version, and one log proves only one run. Interface behavior cannot reveal a hidden prompt, and CLI rules cannot be applied to every IDE or cloud environment.[S004][S068][S076]

This chapter explains mechanisms using material available on the verification date, 2026-10-17; it does not guarantee that every account and version is the same. Specific source filenames, model lists and default thresholds are not stated as facts without verification.

Codex: how each turn's input is formed

Codex's public Agent Loop describes input preparation, dispatch of model output, tool execution and feeding results back in. Search results, file contents, patches and test results enter context dynamically during the loop; they are not all knowledge inherently contained in the user's initial prompt.[S004]

For a hypothetical exclude task, turn 1 selects search, turn 2 sees the matches and reads code, turn 3 generates a change, and turn 4 checks tests. Visible content differs each turn and before and after compaction. Diagnosing a failure therefore requires asking "What did it actually see at this point?", not only "Was the initial request long enough?"

The open-source repository can be used to trace configuration, sessions, message construction, tool dispatch and state saving. This book has not audited a complete commit and does not treat historical file paths from an article as fixed current interfaces.[S066]

Engineering mechanisms and failure boundaries

Product behavior against the facts of the code

Compare the actual requests, tool logs and final artifacts of the same task; with open source the functions can be traced, while for closed source only public documentation and observable facts can be stated.

Key boundary: do not speculate about hidden prompts, or take one historical engineering article as the fixed algorithm for every current session.

Keep tracing through the source or the engineering basis: keep implementation fact, experience reports, product documentation and teaching construction apart. Do not check only the happy path; check the behavior on cancellation, on a version change and when the result is unknown as well.

For the complete mechanism and the continuous example see How can the open-source Codex and the Claude engineering articles be read against each other without manufacturing a conflict?; this section keeps its original derivation and experiment, and the two accounts work at different levels rather than replacing each other.

Evidence and the limits of understanding: a feature with the same name can mean different things in different products; keep the pinned commit, the documentation, older articles and teaching derivations apart.

App Server and a managed harness

Start with the objects and symbols used here
Thread, turn, session: the levels of a run
These are usually the harness's divisions of a conversation and of units of work, not layers of a neural network. A thread can mean one conversation, and a turn can contain the several model and tool cycles needed to answer one user task; where the boundaries fall depends on the product."This turn is done" cannot be equated with "every external tool has finished"; that takes looking at the actual events and results.

The public description of Codex App Server connects clients to the core through a bidirectional protocol and organizes interactions with Thread, Turn and Item. Understand the layers of an ongoing session, the progress of one request and intermediate events, instead of only memorizing field names. Client disconnection, cancellation, approval and reconnection all need representation.[S064]

Original insight: progress shown by the interface should not be the only place task facts are stored. Terminal and desktop interfaces can share a core, but permissions and task state must remain stable. A managed Agents API places some session management, orchestration and recovery with the service; the application must still provide tools and execution boundaries.[S067]

Harness Engineering: the environment can improve quality too

OpenAI's engineering article comes from a particular team's case. It emphasizes organizing knowledge so it can be discovered in the repository and maintaining important boundaries through executable checks, instead of piling every rule into an enormous entry file. The case's results cannot be extrapolated into a promise of efficiency for every project.[S065]

Original application: the entry point tells the agent about project structure, key constraints and test entry points; domain rules belong in their corresponding directories; stable, important restrictions are enforced with tests and static checks. For exclude, specifying whether paths are relative to the repository root or the configuration directory is more useful than repeatedly writing "You are a professional engineer".

Claude Code: context and memory

The official description organizes work around gathering context, acting and verifying. Long sessions manage tool results and history; skills can be expanded on demand; sub-agents can work in separate contexts and return results. These are harness mechanisms, not the model's attention structure.[S068][S069][S071]

CLAUDE.md, automatic memory and AGENTS.md support must be checked against the version and configuration. The current documentation describes conditional AGENTS.md loading; it must not be described as something every version always reads, nor should the outdated claim that it is never supported be retained. Project instructions and automatic memory are both context, not program configuration that cannot be violated.[S070]

A sub-agent should not receive all its parent's history and permissions by default. Delegation needs a goal, boundaries, evidence requirements and a result format. The main agent must still judge whether a returned summary omits key restrictions. Hooks perform deterministic actions at lifecycle points; the permission system restricts resources, and a skill cannot replace those boundaries.[S071][S073][S074]

Copilot: identify the surface first

Copilot CLI, IDE interaction and other agent capabilities are not identical. Instructions, skills, custom agents, hooks, MCP and plugins each have their responsibilities and support scope; support on one surface does not imply support on all surfaces.[S076][S079]

The CLI offers context inspection and compaction capabilities, but one compaction output cannot prove the internal algorithm. A custom agent organizes role configuration, a skill organizes task methods and resources, and a plugin packages them for distribution. Which tasks memory spans and how evidence is verified depend on current product rules.[S077][S080][S081][S082]

Programmatic calls also need to handle exit codes, output structure, authorization and noninteractive behavior. A final terminal line saying "Done" is insufficient to judge a script successful; verify the target files and tests.[S083]

A comparison experiment across three products

An original experiment fixes the repository, bug and acceptance conditions, and records the first read, necessary evidence, modification scope, tool failures, compaction, delegation, total cost and outcome. End-to-end comparisons may use different models and harnesses; mechanism comparisons should hold variables fixed as far as possible. The combined differences cannot all be attributed to the model.

A 6.1 · Codex input assembly and execution loop

Related material: Unrolling the Codex Agent Loop

Codex's public loop connects input preparation, model output, tool execution and result feedback. The model can propose a search or edit; the harness handles dispatch, permissions and state. This does not give the model direct access to the operating system.

A 6.2 · Codex App Server and session primitives

Related material: Unlocking the Codex Harness

The Codex App Server article introduces the interface between core runtime capabilities and clients, using primitives such as Thread, Turn and Item to organize sessions and events. These concepts distinguish an ongoing session, a single interaction and the different outputs produced along the way.

Interface display and execution facts should be kept separate. After a client disconnects, a screen that has stopped updating does not mean the task has necessarily stopped; receiving a progress event does not mean the final state is complete. Specific recovery behavior depends on the protocol and implementation.

A 6.3 · An engineering environment for agents

Related material: Harness Engineering

Harness Engineering discusses building an environment where agents can discover knowledge, execute work and verify results easily. It comes from a particular team's practice; its output scale or efficiency cannot be extrapolated to arbitrary repositories.

Entry guidance works well as a map; detailed rules belong where they are relevant; stable, important boundaries can be enforced with tests or static checks. This makes necessary information easier for the model to obtain, instead of relying on an endlessly growing manual to remember everything.

B 6.4 · How to read Codex's public implementation

Related material: OpenAI Codex Repository

Codex's public repository is useful for studying the connections between configuration, sessions, input construction, tool dispatch and state management. This book has not audited a commit file by file and therefore does not present unconfirmed current source symbols as facts.

Pin a version when reading source, trace downward from a runnable entry point, and verify your understanding with tests or logs. A documentation architecture description may lag behind or precede a commit's implementation, and filenames can change.

Start with the objects and symbols used here
ToolRouter,ToolCall,ToolInvocation
These are program type names from the cited snapshot of the Codex source. ResponseItem stands for one model response; ToolCall stands for the data of a call waiting to be made; ToolInvocation combines the call with execution context such as the session and cancellation; ToolRouter is responsible for the relevant tool path. These objects are constructed and dispatched by the program; they are not tensors of the kind the model uses internally for Q/K/V. Field and permission handling must follow the pinned source cited, not be inferred from the names.

B 6.20 · Combining and distributing plugins

Related material: About GitHub Copilot Plugins

Plugins can organize and distribute extensions such as skills, agents, hooks or tool connections. They primarily package and connect capabilities; installation does not mean each capability will be called or automatically authorized.

Scripts, network services and configuration introduced by a plugin are part of the supply chain. Check their source, version, permissions and conflicts with existing rules.
