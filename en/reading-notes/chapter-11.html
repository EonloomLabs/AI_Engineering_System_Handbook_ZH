Define verifiable completion first

AI software engineering aligns requirements, implementation and evidence rather than generating as much code as possible. SWE-agent studies the operating interface, long-running harness research studies progress across sessions, and traditional testing and review provide quality foundations; none can replace the others.[S130][S132][S133]

Original exclude completion standard: nested paths work, old top-level behavior stays unchanged, invalid configuration produces explicit errors, related tests pass, and there are no unrelated interface changes. "Looks professional" can reward stacked abstractions; "all tests pass" may also be false completion if the tests are too weak.

The smallest sufficient change

Understand the goal→find evidence→reproduce→define boundaries→change→verify→deliver is a practical approach, not a fixed approval system. Simple tasks can proceed continuously; complex tasks expand when evidence is insufficient. The smallest sufficient change is not mechanically the fewest lines, but a change that meets the goal with reasonable risk.[S136][S137]

Original examples: inconsistent path bases can be normalized before the call or inside the matcher. The choice depends on responsibilities, callers and compatibility, not a new global framework for uniformity's sake. Fewer unrelated formatting changes help review, but structural issues that actually prevent correctness must still be addressed.

Test behavior rather than accommodating the implementation

Unit tests help locate issues, integration tests verify boundaries, and end-to-end tests verify user paths. The testing pyramid is a principle about cost and feedback, not a fixed numerical recipe.[S138]

For exclude, unit tests cover normalization, integration tests cover configuration and file lists, and end-to-end tests cover artifacts. Also verify files that should not be excluded, so "filter everything" does not pass one-sided assertions. Tie test records to code versions; adding patch B after A passes does not automatically extend the old results to the new version.

CI runs checks and feedback consistently; it does not prove every untested behavior correct. An agent should not delete tests it does not understand to get a green status, unless requirements have actually changed and evidence is sufficient.[S139]

Engineering mechanisms and failure boundaries

Fix non-blocking problems directly

Split review findings into architectural errors and local naming problems; the latter go straight into implementation and verification, while the former change the plan first.

Key boundary: do not escalate every problem into a redesign; measure whether rework and defects really do go down.

Follow it further through the source or the engineering basis: connect the work with recoverable state, functional acceptance and minimal checkpoints. Do not check only the path that goes well; check the behavior on cancellation, on a version change, and when the result is unknown.

For the complete mechanism and the continuous example see How does a long task avoid starting over each time, or finishing falsely?; this section keeps its original derivation and experiment, and the two accounts work at different levels rather than replacing each other.

Evidence and the limits of understanding: more roles and reset policies for a long task are not better; after a model upgrade, compare against a trimmed-down mechanism instead of always applying the longest process.

Verification basis:[A06] [A13] [A01] [D07]. The source is limited to commit 86e17e98c7f9 and the paths actually read; article experience, public documentation and original teaching experiments are labeled separately. See how it was obtained, what was read, and the limits.

Review does not seek endless perfection

Google's standards emphasize improving overall code health and distinguishing important issues from personal preferences. Review should focus on design, functionality, complexity and tests rather than indefinitely blocking imperfect but reasonable progress.[S136][S137]

An original process can let reviewers directly fix small, clear issues and verify them; cross-module issues or ambiguous goals go back for handling. Independent review adds value by finding new important problems, not by adding another role name. Repeated reviews without new evidence may only increase latency.

Long tasks need handoff artifacts

Early long-task harness cases used initialization and incremental-development responsibilities alongside progress records, feature lists and version history. Later experiments explored combinations of planning, generation and evaluation, adjusting context-reset strategies as model capability changed. These are conditional cases, not requirements that every project use identical file names and roles.[S130][S131][S142]

An original minimal handoff includes the current runnable state, completed and incomplete requirements, decision reasons, verification evidence and next steps. A small bug does not need hundreds of acceptance items first. Multi-agent compiler cases offer lessons in task division and testing; code volume does not establish that arbitrary scenarios can run without human management.[S134]

Quality loss can also come from the harness

On 2026-04-23, Anthropic reviewed product-layer changes, including the effects of reasoning effort, handling of older reasoning, and verbosity constraints on quality. It distinguished affected product layers from the API situation at the time; it is not a universal explanation for every quality fluctuation.[S141]

Original lesson: version the model, prompt, tools, trimming and environment; test long sessions and recovery scenarios; use ablations to locate causes. Testing only newly created short sessions may miss state-dependent failures.

Decision records and delivery

An ADR records context, choices and consequences. It suits important decisions that may be questioned again; not every variable needs documentation. Delivery should state actual changes, verification results, unverified parts and risks rather than a vague "everything is complete".[S140][S135]

Self-check: do passing tests eliminate the need for review? Not necessarily; it depends on uncovered risks. Is more review always better? No. Consider the marginal defects found and the cost of rework.

A 11.1 · Development across contexts

Related material: Effective Harnesses for Long-Running Agents

The long-running harness article studies how agents keep developing applications across multiple contexts, maintaining progress through initialization, incremental tasks and handoff records. It concerns specific experiments, not a file and role checklist every project must copy.

A long conversation is not the only persistent state. Requirements, code versions, test results and next steps should be reconfirmable in a new session to avoid repeatedly starting from zero.

Start with the objects and symbols used here
checkpoint: you must look at the object that was saved
A model checkpoint saves weights or training state; activation checkpointing saves a few intermediate nodes so they can be recomputed on the backward pass; an agent task checkpoint saves how far execution has got. The three share a name, but what they restore is entirely different. When you see "checkpoint", first ask whether it restores parameters, recomputes activations, or continues a task. An agent saving a summary does not update model weights.

A 11.3 · Computer interfaces for agents

Related material: SWE-agent

SWE-agent studies how computer interaction interfaces designed for agents affect automated software engineering. Search, reading, editing and testing tool design affects whether the model can act effectively.

The same model may perform differently with different tool interfaces. Oversized tool output, unclear editing feedback and missing error messages all increase failure probability.

Start with the objects and symbols used here
SQL, SQLite and the transaction object
SQL is the language for working with relational data; SQLite is a database engine that embeds into an application. Writing operational state into a database is a persistence action by the harness; it does not modify the model's neural network parameters. One transaction can save the business row in this database together with a pending-send record, but that does not let you infer that the mail service committed atomically along with it.

B 11.6 · Using agents for code review

Related material: Copilot Agentic Code Review

Start with the objects and symbols used here
IDE, CLI, UI and DOM
IDE is the integrated development environment, CLI the command-line interface, UI the user interface, and DOM the tree of structural objects of a web document. The code, selection and page information that each entry point attaches automatically can differ. The model seeing the selected function in the IDE does not mean the same task in the CLI has received that function; check this turn's input objects first.

Copilot's agentic code-review feature offers a product entry point for finding and handling issues, but cannot replace project acceptance. Check support and permissions for the specific CLI version.

Review results must distinguish actual defects, risk notices and style suggestions. Model-raised issues may also be wrong; verify them against source code, specifications and tests.

A 11.9 · The testing pyramid

Related material: The Practical Test Pyramid

The testing pyramid explains differences in scope, speed and maintenance cost among test levels. Unit, integration and end-to-end tests complement one another; no fixed numerical ratio suits every project.

Tests should verify behavior rather than lock down implementation details. Excessive dependence on internal structure makes reasonable refactors break tests frequently, while testing only the final interface can make faults hard to locate.

B 11.10 · Continuous integration and feedback speed
