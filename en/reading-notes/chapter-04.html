Messages, instructions, structured outputs and tool calls

Follow this chapter through its objects and states

Start by separating receiving a stretch of network bytes, assembling one SSE event, obtaining complete JSON, and confirming that a tool call is finished. Execution is considered only after the last of these conforms to the protocol in structure and passes the permission check. If the four layers are run together, half an argument can be taken for a real command.

The input the model actually receives

A message interface includes roles, content blocks, tool definitions and other configuration, not just free text. The client may add repository rules and task state, and the server may organize the input further. The visible chat history is not the complete request, much less all internal processing.[S045][S047][S049]

稳定约束：只改授权工作区
项目知识：构建入口、路径语义、测试命令
工具定义：搜索、读文件、补丁、测试
用户目标：修复exclude嵌套路径
工作状态：已复现，尚未修改
证据：当前源码与实际测试结果

This is a vendor-independent teaching structure and cannot be used directly as an API request. Every piece of information needs provenance; a model assumption must not silently become a "confirmed fact".

Instruction hierarchy and trust boundaries

The Model Spec describes expected behavior; it is not a runtime permission system. This text explains the concepts using verifiable historical versions, without claiming they represent the latest behavior of every model. Lower-trust content can provide facts but cannot authorize itself; higher-priority instructions constrain behavior but do not make their external facts eternally correct.[S028]

A source-code comment asking for environment variables to be uploaded is still external text. The tool executor should check permissions rather than relying only on "please be safe" in the prompt. Source labels help organize information, but cannot replace actual access control.

Three levels of guarantee for structured outputs

Start with the objects and symbols used here
Schema and Structured Outputs
A schema is a set of structural rules about fields, types and the like; a structured-output mechanism makes it easier for the model to return data that follows those rules. Valid fields still do not mean that the target file exists, that access has been granted, or that the request is right for the business. Independent example: path is required to be a string; {"path":3} does not match the type rule, and {"path":"missing.py"} follows the structure yet may still find no file.
Start with the objects and symbols used here
JSON: structured text, not an action being executed
JSON is a text format that expresses data as objects, arrays, strings, numbers and so on. A braced object maps field names to values; a bracketed array keeps the order of its items. Parsing JSON only yields data; it does not automatically run a tool name inside it. Independent example: {"path":"a.py","limit":3} has two fields; "3" is a string while 3 is a number, and a schema can require either one.

Valid JSON guarantees syntax; a schema guarantees constraints such as structure, types and enumerations; facts, citations and business states within fields still need verification. The schema should allow real states such as insufficient evidence and tool failure, so intermediate results are not forced to masquerade as completion.[S048]

{"status":"needs_evidence","suspected_file":"pipeline/filter.py",
 "evidence_ids":[],"next_action":"read_file"}

This is an original business example, not a requirement of any product. After parsing, also check truncation, refusal, whether field references exist, and whether files fall outside allowed paths. A confidence value from 0 to 1 is merely numerically valid; it does not automatically mean a calibrated probability.

The complete protocol for tool calls

The model proposes a tool name and arguments, the application validates and executes them, and the result returns to the model with an association ID; the model then decides whether to continue or answer. A generated call has not necessarily executed, and a successful return does not mean the whole task is complete.[S047]

候选调用 → 参数校验 → 授权与范围校验
       → 执行 → 记录成功或失败 → 回填观察

Distinguish a nonexistent file, lack of permission, timeout and an empty file when handling read failures. Check dependencies before parallel calls: independent searches can run in parallel, but a patch based on code not yet read cannot be generated in parallel unconditionally.

Engineering mechanisms and failure boundaries

Discoverable and authorizable

Construct a tool that registers successfully but is not exposed, then one that is exposed successfully but may not be used, and require the diagnostic report to give a different repair path for each.

Key boundary: do not fix a discovery problem by widening permissions, and do not fix an unloaded tool by rewriting the prompt.

Follow it further through the source or the engineering basis: explain the real limits of tool routing. Do not check only the path that goes well; check the behavior on cancellation, on a version change, and when the result is unknown.

For the full mechanism and continuing examples, see The tool exists, the model sees it, it can be called, it is authorized: four layers of checking. This section retains its original derivations and experiments; the two explanations work at different levels and do not replace each other.

Evidence and the limits of understanding: direct exposure, delayed discovery and a code call are different exposure surfaces; registered, visible, callable and authorized are not equivalent to one another.

Streaming output and reasoning state

A streaming response may contain text, argument fragments and end events. A partial JSON object is not authorization to execute: assemble the complete call according to the protocol, then validate it. High-risk writes especially must not execute while arguments are still arriving.[S049]

Reasoning models may use invisible or protected state; pass it as the interface requires, without fabricating it. The final text's length does not equal total reasoning usage, and an explanation may not be a verbatim record of the internal process.[S037][S051]

Engineering mechanisms and failure boundaries

The protocol boundary and the business boundary

Interleave the argument fragments of two call_ids, then cut the stream once the first tool item has completed. Check separately that the arguments do not cross wires, that the finished tool is not lost from the account, and that the response as a whole is not misjudged a success.

Key boundary: a network EOF, one item finishing and business success must each be recorded separately; before any automatic recovery, confirm which side effects have already happened.

Keep tracing through the source or the engineering basis: keep bytes, events, complete output items and the whole response apart. Do not check only the happy path; check the behavior on cancellation, on a version change and when the result is unknown as well.

For the complete mechanism and the continuous example see Streaming back: when can the arguments really be executed?; this section keeps its original derivation and experiment, and the two accounts work at different levels rather than replacing each other.

Evidence and the limits of understanding: one tool item being complete is not the whole response ending; a call that is already in the history but was canceled still has to have a corresponding result, and a fragment of the arguments must not be taken for a complete action.

Verification basis:[C01] [C05] [D01]. The source is limited to commit 86e17e98c7f9 and the paths actually read; article experience, public documentation and original teaching experiments are labeled separately. See how it was obtained, what was read, and the limits.

Prompt versions and experiments

An original experiment compares three inputs: a repair request alone; the request with explicit goals and necessary source code; and those plus a lengthy fixed process. Measure accuracy, missed tests, total rounds and human takeover. The longer version may help complex tasks and hurt simple ones, requiring statistics by category.

Record at least the prompt version, model configuration, tool schemas and task samples. Saving only the final answer cannot explain a regression. Prompt tools manage organization; they cannot replace evaluation design.[S046][S144]

Self-check: can the model saying it ran tests count as test evidence? No. Tool results are required. Can a strict schema prevent fabricated citations? No. The citations must also be checked for existence and support for the conclusion.

A 4.1 · Prompt engineering basics

Related material: Prompt Engineering

Prompt engineering organizes task goals, constraints, background and output requirements. Clear structure helps the model understand, but wording is not a deterministic program and cannot guarantee every requirement is followed.

Provide enough necessary evidence rather than piling up generic slogans. A role description can supply style or perspective but cannot replace actual project conventions. Output requirements should also allow insufficient evidence and incomplete states.

A 4.2 · Prompt organization and version management

Related material: Prompting

Prompt management involves templates, variables, reuse and versions. Reuse reduces repeated organization work, but the evidence and constraints needed by different tasks must still be distinguished; a template should not become a fixed, lengthy process for every situation.

Prompt evaluation must record the model, tool definitions, task samples and configuration; otherwise, output differences cannot be attributed. Template variables also need proper escaping and provenance labels to keep external data from mixing with high-trust instructions.

A 4.3 · Input trust and instruction conflicts

Related material: Model Spec

Instruction priority resolves conflicting requests from different sources; factual credibility concerns whether content is true. These dimensions cannot replace each other: correct external evidence does not give it authority to rewrite the user's goal.

The book uses a verified historical Model Spec to explain normative concepts, without claiming the specification guarantees zero model errors in practice. Tool authorization should still be enforced by the program, rather than delegated entirely to the model.

A 4.4 · Function-calling protocol

Related material: Function Calling

Function calling passes the tool name and arguments proposed by the model to the application for execution, then associates the result with the original call. A model-generated call is not actual execution, and successful execution does not mean the whole task is complete.

Arguments require syntax, type, business-rule and permission checks. Returns should distinguish success, no results, timeout, insufficient permissions and other states rather than conflating them as empty text. Association IDs help handle multiple or parallel calls.

A 4.5 · Structured outputs and constraints

Related material: Structured Outputs

Structured outputs constrain format and field types, not the truth of field contents. Valid JSON, schema compliance and business validity are three levels.

Schema design should include real states such as missing evidence, unverified results and tool failure. Allowing only successful conclusions may force the model to place an intermediate state in the wrong category. Refusal and truncation also need separate handling.

B 4.6 · Streaming responses and event assembly

Related material: Streaming API Responses

Streaming responses deliver text, arguments or events in batches. Receiving a portion does not establish that a complete object exists; follow the protocol's completion signals and error states.

Tool arguments may span multiple fragments; do not guess completion using fragile string rules. High-risk actions especially must wait for complete arguments, authorization and validation, rather than operating unconditionally as generation streams in.

Start with the objects and symbols used here
SSE, chunk, delta: different layers of fragmentation
SSE is the text protocol for server-sent events; a network chunk is the stretch of bytes received this time; a delta is the incremental content of one output item. Their boundaries are not guaranteed to coincide. One complete event does not necessarily mean complete tool arguments either. The arguments may arrive first as {"path":"a and then as .py"}; they have to be assembled and the protocol's completion condition awaited — seeing a fragment is no reason to execute.

B 4.8 · Extended reasoning and state continuity

Related material: Extended Thinking

Extended Thinking involves additional model reasoning and its interface state. Visible reasoning summaries, final answers and protected state should not be conflated into ordinary chat text.
