Observe the task's causal structure

A trace connects the model, tools, retrieval, handoffs and verification within one task; a span represents an operation; an event records a point in time; metrics aggregate distributions. Agents SDK and OpenTelemetry offer tracing entry points, but standard fields and their stability need verification against the version.[S165][S166][S167]

Parallel spans overlap and cannot simply be summed into wall-clock time. Large volumes of logs without correlation IDs may still fail to explain a failure.

Metrics start from user goals

Start with the objects and symbols used here
TTFT, TPOT, p95 and throughput
TTFT is the latency from the request to the first output token; TPOT describes the statistics of the time per token after that; p95 is the quantile that about 95% of observations in a given window do not exceed; throughput is the amount completed per unit of time. Say where the timing starts and stops. A fast first character does not mean a fast task: tool execution may still take a long time. Nor does theoretical peak throughput equal the latency one user sees.

TTFT is the wait for the first token, generation throughput is output speed, and tool latency comes from external dependencies; total duration reflects the whole task. Both means and high percentiles matter. Saying "Starting work" quickly does not mean finishing quickly. SRE emphasizes defining monitoring and objectives through user-visible behavior.[S168][S169]

Quality should cover goal fulfillment, regressions, security and human takeover; distinguish input, cache, output, tools and execution resources in costs. Products bill differently, and token counts are not a universal currency.[S170][S172]

Cost per successful task and model routing

Original idealized example: A costs 1 yuan per attempt with a success rate of 50%; B costs 1.5 yuan with a success rate of 90%. Using the rough approximation cost/success rate, A costs 2 yuan and B about 1.67 yuan. Actual retry correlations, human costs and task distributions change the conclusion.

Routing can consider complexity, risk, context and verification capability, but must count its own cost and the handoff when switching. Sending small tasks to a cheap model is a strategy to test, not a theorem. Reasoning budgets should also follow the quality–cost curve rather than maximize thought length.[S172][S038]

Engineering mechanisms and failure boundaries

A model-routing ablation

Keep the tools and the evidence the same, and change only the model or the upgrade condition; compare whole strategies, not a single per-token price.

Key boundary: the input you save must not cost you key evidence or the authorization boundary.

Follow it further through the source or the engineering basis: look at task quality, latency, cost and maintenance burden together. Do not check only the path that goes well; check the behavior on cancellation, on a version change, and when the result is unknown.

For the full mechanism and a continuing example, see Optimization locates the bottleneck first; it is not about chasing fewer tokens; this section retains its original derivations and experiments. The two explanations address different levels and do not replace one another.

Evidence and the limits of understanding: Optimize by finding the bottleneck first; the original text on the think tool was later updated to prefer extended thinking in most situations, so the old advice is not a permanently necessary component.

Rate limits, timeouts and retries

Rate limits may apply to requests, tokens or other resources. Transient failures can use backoff with jitter; invalid arguments and insufficient permissions should not be retried blindly. After a side-effect timeout, query the actual state before deciding whether to resend.[S171]

Canceling a model request does not guarantee the tool process stops. Task-level and operation-level timeouts, cancellation propagation, idempotency and deduplication are needed. Unlimited retries are uncontrolled risk, not continued work.

Sessions, executors and storage

The Managed Agents case decouples session events, the harness and the sandbox, reducing coupling to execution-environment failures. A small local agent need not split immediately into several services, but can keep interfaces clear and gradually add recovery capability.[S142]

Logs must distinguish intent from executed facts. "Preparing to run tests" is not a result. Event replay usually restores state and should not unconditionally repeat every side effect.

SLOs and degradation

Start with the objects and symbols used here
SLI, SLO and the error budget
An SLI is a service level indicator that is actually measured; an SLO is the target for that indicator; the error budget is the room for failure that target allows. They are objects of service operation, not model parameters."The API returned 200" may not be success for the user; some businesses should define the indicator as the proportion of tasks completed correctly within a bounded time.

An SLO must state task scope, the success definition, time window and budget. Read-only Q&A and automatic editing should have different objectives. When dependencies are unavailable, the system can degrade to evidence and suggestions without claiming execution; when permissions are insufficient, stop the corresponding action while completing independent parts where possible.[S169]

Alerts should point to user impact that needs attention. One recoverable timeout may not warrant disturbing a person; sustained failures, abnormal costs, unauthorized actions and lost state deserve more attention. Trace data also needs redaction and retention policies.

Optimization order

Find the bottleneck first: frequent round trips suggest checking tool granularity; noise suggests retrieval; long output suggests requirements; repeated retries suggest the environment; insufficient capability suggests the model or evidence. Aggregating tool results in code may save context but also increases execution complexity, so verify it for the task.[S173]

Self-check: is reducing call count always good? No; necessary verification may be removed. Does HTTP success mean agent success? No; check the business goal.

A 14.1 · Tracing models, tools and handoffs

Related material: Agents SDK Tracing

Tracing connects model calls, tool executions, handoffs and other steps into a task trace. It helps explain the process, but the existence of records does not mean their content is complete or their conclusions correct.

Distinguish tasks, spans, events and final outcomes. Parallel steps may overlap, so durations cannot simply be added. Sensitive prompts and credentials should not be logged indiscriminately.

Engineering mechanisms and failure boundaries

Quantiles and the cost of failures

Compute the overall p95 from 100 one-second requests and 2 hundred-second requests, and compare it with the average of the two groups' p95 values; separately compute the cost per success including failures.

Key boundary: quantiles must be merged from the original distribution or from mergeable statistics, never by a plain average.

Keep tracing through the source or the engineering basis: avoid blending totals, wall clock and percentiles into one metric. Do not check only the happy path; check the behavior on cancellation, on a version change and when the result is unknown as well.

For the complete mechanism and the continuous example see Work out the waiting, the usage and the cost of failure from one trace; this section keeps its original derivation and experiment, and the two accounts work at different levels rather than replacing each other.

A 14.3 · Model and agent spans

Related material: OpenTelemetry GenAI Spans

GenAI span conventions describe how to represent model or agent operations. Parent-child relationships and time boundaries determine whether execution structure can be reconstructed correctly.

Asynchronous and parallel tasks especially need clear associations; a span ending may mean only that a request ended, not that the external business action finally completed.

Start with the objects and symbols used here
DAG, dependencies and the critical path
A DAG is a task dependency graph that is directed and has no cycles. The arrow A→B means B depends on A finishing; the critical path is the longest dependency chain, the one that fixes the earliest finishing time given the task durations and dependencies. Independent example: A takes 2 seconds, B and C depend on A, take 3 and 5 seconds and can run in parallel, so finishing both after A takes at least 7 seconds — not 2+3+5=10 read as wall-clock time.

B 14.4 · Choosing monitoring signals

Related material: Google SRE Monitoring

SRE monitoring emphasizes choosing signals from service behavior and user impact. Logs, metrics and alerts each have a purpose; collecting more does not necessarily make problems easier to find.

Agent monitoring should track task success, tail latency, sustained failures and human takeover, beyond API return codes. A model returning 200 without completing the task is still a user-level failure.

B 14.5 · Service objectives and error budgets

Related material: Google SRE Implementing SLOs

An SLO defines a service objective as a measurable agreement; an error budget helps interpret the allowed room for failure and the risk of changes. Metrics must state their scope, time window and success conditions.

Agent tasks vary widely; read-only Q&A and automatic edits should not be forced into identical objectives. Speed and quality both need consideration.

A 14.7 · Rate limits, backoff and budgets

Related material: Rate Limits

Rate limits may apply to requests, tokens or other resource dimensions. Retries must respect service feedback and distinguish transient failures from permanent errors.

Start with the objects and symbols used here
Backoff, jitter and cancellation
Backoff makes the interval between retries grow; jitter adds a random perturbation so that requests do not all retry at the same moment. A cancellation signal is notice that a stop has been requested; it does not withdraw external side effects already committed. A read-only request whose connection fails temporarily can be retried; when the result of a write request is unknown, verify first. "Retry for longer" is no substitute for permission or idempotence design.

Exponential backoff and jitter can reduce synchronized retries, but cannot fix invalid arguments or insufficient authorization. Before retrying an action with side effects, also confirm whether it has already run.

B 14.11 · Tool combinations and cost boundaries

Related material: Claude Tool Combinations

Tool combinations affect how information flows to the model. Filtering large results through code may reduce context; returning results directly is simpler but may introduce redundancy.

Combination capabilities depend on product support, permissions and the execution environment. Do not assume all tools can run arbitrarily in parallel or share state.

Start with the objects and symbols used here
SQL, SQLite and the transaction object
SQL is the language for working with relational data; SQLite is a database engine that embeds into an application. Writing operational state into a database is a persistence action by the harness; it does not modify the model's neural network parameters. One transaction can save the business row in this database together with a pending-send record, but that does not let you infer that the mail service committed atomically along with it.
