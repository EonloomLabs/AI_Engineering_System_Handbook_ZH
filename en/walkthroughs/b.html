Start with the objects and symbols used here
JSON: structured text, not an action being executed
JSON is a text format that expresses data as objects, arrays, strings, numbers and so on. A braced object maps field names to values; a bracketed array keeps the order of its items. Parsing JSON only yields data; it does not automatically run a tool name inside it. Independent example: {"path":"a.py","limit":3} has two fields; "3" is a string while 3 is a number, and a schema can require either one.

The following is an author-designed protocol-level teaching trace, not an actual conversation exported from a commercial LLM. The tool structure is a simplified custom Harness format that need not match any vendor's JSON fields exactly. It answers: "When an Agent calls the model repeatedly, what exactly is supplied and returned each time, and how does the program use it?"[TOOLS][CODEX][COMPACT]

Task: repair path handling in exclude. Constraints: match patterns against project-root-relative paths; do not change inclusion rules; do not commit or deploy. Retaining the final two prevents a code fix from expanding into unauthorized delivery actions.

B.1｜Before starting: four kinds of object held by the harness

Start with the objects and symbols used here
Patch, image channels and the visual projection
A patch in an image is a small block cut out of it, and RGB is the 3 channels red, green and blue; a patch in software engineering is a code patch — the same word for both. An image block, once flattened, can become a vector through a learnable transformation; it is not a lookup in a text vocabulary. Independent image example: one 16×16×3 block holds 768 numbers, and after projection it can become d features. d is fixed by the model design.
{
  "task_id":"t7",
  "goal":"修复exclude路径处理",
  "constraints":["按项目根目录相对路径匹配","保留包含规则","不提交、不部署"],
  "workspace":{"root":"/work/demo","revision":"r42"},
  "tools":["search_code","read_file","apply_patch","run_tests","inspect_operation"],
  "state":{"phase":"investigate","pending_calls":[],"verified":[]}
}

This is not the only format in which everything is fed directly to the model. Task objects, permission objects, workspace state and the tool registry can be stored separately. Model input is a selection rendered from those objects; the executor must retain actual permissions rather than accept the model saying an action is allowed.

The first turn has no source evidence yet. The main agent can retrieve before guessing a patch. If the frontend already attached relevant source, analysis could begin directly; this example takes the unattached path to show the full retrieval loop.

B.2｜Model call M1: why input needs tool schemas

Start with the objects and symbols used here
OAuth, scope and authorization
In an authorization setting, OAuth lets an application obtain access credentials according to what was granted; a scope declares one class of access range, and the resource service should still check the specific permission. In a memory or task setting, scope can instead mean only the range over which something applies, and must not be conflated with a login credential. Being granted "read the calendar" is not being granted the deletion of every event; a successful connection is no proof that an operation was approved.

Start with the objects and symbols used here
Schema and Structured Outputs
A schema is a set of structural rules about fields, types and the like; a structured-output mechanism makes it easier for the model to return data that follows those rules. Valid fields still do not mean that the target file exists, that access has been granted, or that the request is right for the business. Independent example: path is required to be a string; {"path":3} does not match the type rule, and {"path":"missing.py"} follows the structure yet may still find no file.

Schema tells the model which actions it may express and what the arguments are named. Actual systems may expose only some tools and discover others on demand. A tool's presence in the registry does not require its full definition in every turn's context.

M1's output is not the final answer, but:

Start with the objects and symbols used here
call_id,item_id,request_id
These are identifiers for objects at different layers: a tool call, an output item, a request or a response. They match increments and results back to the right object; they are not the token IDs of the model input, and they are not business idempotency keys by nature. Two read_file calls can carry c1 and c2; when the results come back in the reverse order they are still paired by call identifier, not guessed by tool name.
{"kind":"tool_call","call_id":"c1","name":"search_code",
 "arguments":{"query":"exclude","path_scope":"pipeline"}}

The harness parses response items, checks tool existence, complete arguments and permitted call scope, then executes. Generating this JSON did not directly read the disk.

Engineering mechanisms and failure boundaries

Arguments rewritten after approval

Computes a stable identity digest for the final action, then changes the field order and the target environment in turn. Changing the field order should not change the logical identity; changing the target environment should invalidate the original approval.

Key boundary: do not approve a function name alone; the audit log records both what was actually executed and what was presented to the model.

Follow it further through the source or the engineering basis: be especially wary of "the result was rejected" being misread as "the action did not happen". Do not check only the path that goes well; check the behavior on cancellation, on a version change, and when the result is unknown.

For the full mechanism and a continuing example, see Why can a pre-check and a post-check not replace each other?; this section retains its original derivations and experiments. The two explanations address different levels and do not replace one another.

Evidence and the limits of understanding: By the time a post-hoc check runs, the action may already be complete. The semantics of a post-hoc block differ between Codex and Claude Code; and even where the result is redacted, the original log still has to be checked.

Verification basis:[C09] [C01] [D04]. The source is limited to commit 86e17e98c7f9 and the paths actually read; article experience, public documentation and original teaching experiments are labeled separately. See how it was obtained, what was read, and the limits.

Returned excerpts locate code but do not establish the full control flow. Explicitly mark truncated results instead of treating the first few as everything. Recording r42 lets later steps judge whether evidence still matches the current workspace.

The harness pairs M1's tool call with T1's result by call_id and adds them to history. Worked model 2 must at least see the original task, constraints, c1 and its result; it may also see the current plan, without copying every internal tool log.

How c1 joins M1's action to T1's evidence

Retains task t7 and workspace r42: c1 is search_code, not read_file; tool identity has not changed here.

The same c1 spans call and return; simultaneous tool returns must also be assigned by ID, not arrival order.

Search hits locate files without establishing that complete control flow was read. M2's c2/c3 reads are therefore a next step based on an identified evidence gap.

B.4｜Model call M2: specify the missing evidence

M2 issues two reads from the locations found:

[
 {"kind":"tool_call","call_id":"c2","name":"read_file",
  "arguments":{"path":"pipeline/filter.py","start_line":1,"end_line":70}},
 {"kind":"tool_call","call_id":"c3","name":"read_file",
  "arguments":{"path":"tests/test_filter.py","start_line":1,"end_line":60}}
]

They are independent read-only operations and may run in parallel, but every result must retain its own ID. c3 arriving first does not make it belong to c2. The harness must not match first arrival to first call.

Suppose the following teaching code is read:

from fnmatch import fnmatchcase

def excluded(path, patterns):
    return any(fnmatchcase(path, pattern) for pattern in patterns)

def select_files(root, files, patterns):
    return [p for p in files if not excluded(str(p), patterns)]

An unused root is not yet proof of the sole error. Check whether files contains absolute or relative paths, the meaning of patterns and path-separator rules. An unused argument is a clue, not proof of the root cause.

c2 and c3 can run in parallel, but the results must not be numbered in order of arrival

B.5｜Model call M3: from a candidate explanation to falsifiable checks

Express hypotheses as checkable relationships:

H1：匹配函数本身不支持此模式。
H2：调用方把绝对路径传入了相对模式匹配。
H3：测试期望与已确定的产品语义不一致。

In this teaching trace, run two independent assertions: relative path generated/a.py should match generated/*; the same file's absolute path/work/demo/generated/a.py does not match this relative pattern. Also confirm that the requested product semantics really are root-relative paths. This supports H2 and weakens H1 and H3 with the corresponding evidence.

M3 outputs test call c4, not "I have verified it":

{"kind":"tool_call","call_id":"c4","name":"run_tests",
 "arguments":{"target":"tests/test_filter.py","revision":"r42"}}

Results should include the command, return code, number of tests actually run and failing assertions. This teaching trace assumes the original failure was observed; its example text is not an actual repository test report. Runnable mechanism experiments are in further reading, and deterministic protocol tests in the calculation and execution-chain experiments. The two sets state their own inputs and result scopes.

B.6｜Model call M4: a patch describes changes, not results

The candidate fix should convert paths to root-relative form at the right boundary and specify handling of paths outside the root. relative_to may fail; do not silently swallow exceptions just to avoid errors or redesign every path semantic without a requirement.

{"kind":"tool_call","call_id":"c19","name":"apply_patch",
 "arguments":{
  "path":"pipeline/filter.py",
  "expected_revision":"r42",
  "patch_ref":"patch/p1",
  "purpose":"仅在匹配前构造根目录相对路径"
 }}

The executor checks versions and patch preconditions, then edits the file. Three states now differ: the model proposes p1, the executor starts c19, and the file actually becomes r43. They cannot collapse into "Fixed".

If another user changed the file to r42b, expected_revision does not match; reject or reread and coordinate. Overwriting from an old excerpt destroys user changes. A concurrency window remains between version check and write and must be addressed with the storage mechanism; reading a hash then writing in Python does not automatically remove the race.

B.7｜The key failure window: the file changed but the success result was lost

Suppose c19 finished replacing the file, but the runner crashed before recording success. Model and task state know only of the timeout; the external file is already r43.

时间t1：记录 c19 pending
时间t2：执行 c19，文件 r42 → r43
时间t3：进程中断，成功响应未送达
时间t4：恢复时看到 c19 尚未确认

Marking c19 failed and retrying directly may edit the file again; marking it succeeded may lie under a different failure window. The correct state is unknown: verification is needed.

The recovery process calls inspect_operation or reads the target version/patch effect. With external idempotency keys, query using c19 or a separate business key; for local files, check target content and whether the intended change was applied. Retry under appropriate conditions only when evidence shows it did not occur.

This cannot promise that a local table alone implements distributed exactly-once. If the state table and external side effect share no atomic transaction, a window remains. Engineering aims to establish outcomes, avoid dangerous repetition and provide controlled recovery when the result cannot be determined.

After recovery, verify p1's effect before proceeding; neither repeat it directly nor guess success. Keep unknown if verification itself fails.

B.8｜Long sessions need compaction: what must not be lost

History may now contain many searches, whole-file reads and failed attempts. Later work most needs the goal, constraints, confirmed root cause, current file version, unconfirmed operations, test state and evidence locations.

The exclude issue is fixed and ready to deliver.

B.9｜Compaction is a state transition, not deleting history in place

First obtain history snapshot version H17, then generate candidate summary C18. Check key constraints, tool-call pairing, unknown state and evidence references. Rebuild stable system instructions, necessary tool definitions and the summary, then conditionally replace current context.

If a user adds an instruction during summarization, history becomes H18; a summary based on H17 must not blindly overwrite the new message. Append the message to the new context or reconcile the snapshot as the runner specifies. This is concurrent state updating, not something solved by asking the model to summarize more carefully.

After compaction, model request M5 should include original authorization scope, the recovery state above, verification tools and the latest observation. Old source blocks need not remain loaded permanently; the model can reread them by evidence ID when needed. Cache hits may change, affecting cost without justifying incorrect context retention.

"File exists" alone does not prove the patch was applied. A partial match with p1 requires identifying partial edits, external concurrency or insufficient verification, not forcing success. Result schemas need uncertainty rather than only true/false forcing a choice.

B.11｜Model call M6: tests must bind to r43

M6 calls test c21; results should identify which tests actually ran on r43. If they pass, check modification scope and user constraints for final delivery. Code changed during testing invalidates automatic proof of the new version and requires rechecking the affected scope.

A final answer can give root cause, modification scope, verification evidence and remaining limits. It must not claim a commit or deployment: the user forbade both and neither happened here. Completion means the required fix is confirmed, relevant verification is done, no important side effects await verification, and permissions were respected.

There is no fixed requirement for another independent review round. Low risk and sufficient evidence allow stopping; unresolved cross-module semantics or concurrency risks call for targeted verification. Review gains value from eliminating specific risks, not the process name.

B.12｜Interview follow-up: is the full history resent each turn

Not necessarily. Clients may send full logical history or reference service-stored responses/sessions; the service still builds context usable this turn. Continuous logical history, incremental network transmission and computation-cache hits are three independent dimensions.

With opaque compaction state, clients may not inspect retained internal content field by field, making external persistent constraints, operation results and evidence references more important. Do not rest every engineering guarantee on an uninspectable summary block.

Another follow-up asks whether sub-agents inherit these tools and state automatically. Do not assume so. Check product and configuration, explicitly handing over the minimum evidence and permissions needed. That the main agent has MCP does not mean every sub-agent can access it; a sub-agent saying "Done" does not establish that the final workspace has been integrated and tested.
