This complete system-diagnosis example uses author-constructed data, not a company incident review or measured evaluation of any model version. Practice eliminating competing explanations layer by layer rather than blaming a less intelligent model intuitively.[EVALS][SRE][HARNESS]

Scenario: after a context-policy update, similar repairs seem slower and sometimes repeat edits to already-fixed files. Some propose a stronger model, others another Review Agent; others would double context. What should happen first?

Choose the component by where the failure happens: if the information was never retrieved, change retrieval first; if the evidence was there but read wrongly, look at the context and the model; if the outcome of an execution is unknown, check the state first. Do not add Memory, multi-agent and Review all at once and then guess which one helped.

D.1｜Turn subjective feedback into observable goals

Define three symptoms: longer completion time, repeated logical actions and genuinely worse final outcomes. Do not rely on perception or claim optimization merely because average Token decreases.

Collect old and new traces on the same representative tasks, recording model, prompt, tool, index, compaction and runner versions. If models changed too, acknowledge confounding rather than attribute everything to compaction.

Here the model and executor are unchanged, but history is compacted earlier, summary templates shortened and more skills loaded by default. These are three variables requiring separate checks.

The contradiction arises when the summary converts unknown to failed. unknown means the effect is unconfirmed; failed usually encourages retries. The words differ little but have different execution consequences.

Even perfect adherence to this summary produces wrong actions. The cause is wrong supplied state, not merely "the model did not listen". Preserve unconfirmed operations structurally, prevent compaction from changing their meaning and check actual effects before continuing.

Why was c19's response lost? Network or process issues still need repair, but "never time out" cannot eliminate every distributed failure window. Reliability must handle lost responses rather than only hope for fewer.

D.4｜Minimal experiments that distinguish hypotheses

Candidates: H1 weaker new model, H2 state lost in summary, H3 skill overload, H4 test-environment noise.

For the same known failure trace, prepare original history, the faulty summary, a summary preserving unknown, and that corrected summary plus operation verification. Fix model, visible tools and task; observe next actions. Errors tracking summary state rather than model version support H2 more strongly.

Test the runner too: reject direct start from unknown; only verified_not_applied permits an appropriate retry, while verified_applied leads to verification rather than another edit. Package state-machine witness tests cover this local rule without claiming commercial models choose correctly.

Do not select only one success. Cover applied, unapplied, partially applied and verification-failed cases. Otherwise a fix may merely guess every unknown succeeded, trading one error for another.

D.5｜Why extra skills can create misleading cost-reduction metrics

Suppose 40K uncached input becomes a 20K summary, but resident skills add 10K per turn. Input still falls slightly, yet compaction adds one model call and repeated actions two rounds; total time and cost may rise.

Sum uncached, cached and output fees across every turn, including failure rework. Comparing the last pre-compaction turn with the first afterward is insufficient. Stable prefixes and tool-output trimming also affect bills.

Excess skills may change task interpretation or create conflicts. Inspect the final request manifest: selection reasons, overlap and long guides better read in relevant portions on demand. Gather irrelevant-loading examples and missed-required-skill counterexamples before narrowing descriptions, so one fix does not damage specialist recall.

Engineering mechanisms and failure boundaries

Quantiles and the cost of failures

Compute the overall p95 from 100 one-second requests and 2 hundred-second requests, and compare it with the average of the two groups' p95 values; separately compute the cost per success including failures.

Key boundary: quantiles must be merged from the original distribution or from mergeable statistics, never by a plain average.

Keep tracing through the source or the engineering basis: avoid blending totals, wall clock and percentiles into one metric. Do not check only the happy path; check the behavior on cancellation, on a version change and when the result is unknown as well.

D.6｜Break time down by critical path rather than sum every duration

Two read-only searches taking 3 and 4 seconds in parallel may mean about 4 seconds of waiting; serially they take 7 seconds. Task Trace should record actual dependencies rather than totals by operation category alone.

Start with the objects and symbols used here
DAG, dependencies and the critical path
A DAG is a task dependency graph that is directed and has no cycles. The arrow A→B means B depends on A finishing; the critical path is the longest dependency chain, the one that fixes the earliest finishing time given the task durations and dependencies. Independent example: A takes 2 seconds, B and C depend on A, take 3 and 5 seconds and can run in parallel, so finishing both after A takes at least 7 seconds — not 2+3+5=10 read as wall-clock time.

The compaction from 13 to 20 seconds lies on the critical path and cannot hide behind later model work. If saved Prefill time is less than these 7 seconds and only one turn remains, compaction may cost more than it saves. Longer tasks may benefit through lower later context costs; trigger by remaining work rather than one occupancy threshold for every task.

M2's 20-to-31-second span may include queues, Prefill, internal reasoning and output transfer. Without server breakdowns, do not invent components from 11 seconds. Only end-to-end call time is confirmed; other explanations await verification.

D.7｜Match repairs to causes rather than refactor the platform

Minimal changes may preserve structured pending/unknown operations, make these states non-droppable summary facts, verify before recovery, add version preconditions and bind tests to final versions. Each addresses the observed failure window.

Large memory databases, layered contracts, per-step signatures or more agents are not necessarily needed. Correct existing task-state storage where available. Transactions and remote idempotency depend on actual side-effect boundaries, not one example requiring identical architectures everywhere.

For skill overload, reduce irrelevant resident content while preserving required recall; for early compaction, consider stage and recent outputs rather than only thresholds. Make optimizations independently switchable to locate regressions.

D.8｜Show improved quality rather than a few chance successes

Use paired comparisons on representative fixed tasks, running both versions under controlled environments and budgets. Repeat stochastic runs reasonably and analyze by task cluster; repeated attempts on one task are not wholly independent tasks.

Teaching two-by-two table: among 100 tasks, both versions pass 70, only old passes 5, only new passes 10, and both fail 15. Old passes 75 and new 80, apparently gaining 5 percentage points; the paired difference actually rests on the 15 discordant tasks, 5 versus 10. Limited samples do not establish stable major gains from 5 percentage points alone.

Costs include every attempt. A version completing only simple tasks may reduce mean duration among successes without improving user goals. Report coverage, success, failure types and complexity strata together; mark infrastructure faults separately from model capability.

The same 100 questions compared: besides the success rate, which two cells should you look at

Use D.8, without mixing Foundations or other independent 20-question examples.

Old passes 70+5=75, new 70+10=80. The net 5 tasks come from discordant counts 5 and 10, not every one of 100 tasks improving by 5%.

Inspect regression types and risks and handle repeats at task level. One +5-percentage-point result is not a stable, universal gain worth releasing.

D.9｜Release and rollback: can old state keep errors alive?

Start with the objects and symbols used here
checkpoint: you must look at the object that was saved
A model checkpoint saves weights or training state; activation checkpointing saves a few intermediate nodes so they can be recomputed on the backward pass; an agent task checkpoint saves how far execution has got. The three share a name, but what they restore is entirely different. When you see "checkpoint", first ask whether it restores parameters, recomputes activations, or continues a task. An agent saving a summary does not update model weights.

After a runner release, old checkpoints may still label unknown operations "failed". New summary templates do not repair existing tasks automatically. Identify affected versions and states, then verify or pause under controlled policies rather than blindly retry every failure.

Start with the objects and symbols used here
Schema and Structured Outputs
A schema is a set of structural rules about fields, types and the like; a structured-output mechanism makes it easier for the model to return data that follows those rules. Valid fields still do not mean that the target file exists, that access has been granted, or that the request is right for the business. Independent example: path is required to be a string; {"path":3} does not match the type rule, and {"path":"missing.py"} follows the structure yet may still find no file.

Rollback needs more than old prompts. If new state schema contains unknown that the old version cannot understand, rollback may reintroduce dangerous duplicates. Compatible reads, migrations and explicit stopping provide more real recovery capability than a rollback button.

During gradual rollout, monitor the verification rate of unknown operations, duplicates, task success, total cost and latency rather than only API error counts. Respond with targeted degradation, such as disabling writes but retaining read-only diagnosis, rather than autonomous work in uncertain state.

Before rolling the code back, check whether the old code understands the new state

Options include compatible reads, explicit migration, read-only degradation or pausing incompatible tasks. Choose by action boundaries, not just the ability to click rollback.

D.10｜Six follow-up questions and directions for complete answers

Question: why not reread every file after compaction? Rereading restores some current facts at high cost, but not past external effects absent from source. Recover evidence and unresolved operations relevant to the next step first; current code is not complete history.

Question: can a stronger model find summary errors automatically? Only if summaries or other evidence reveal contradictions. Consistent "failed" input cannot reliably reveal changed files to any model. Capability cannot replace missing observations.

Question: do retries on every tool improve reliability? Distinguish read-only idempotent operations from side effects; timeouts do not prove nonexecution. Operation semantics, idempotency keys or result queries matter; retry counts do not create reliability.

Question: can passing tests justify ignoring duplicate actions? No. Repeated edits may be harmless by chance or cause extra external effects, confused history or future risks. Evaluate code outcomes and side effects separately; one green state cannot cover everything.

Question: why not let a Reviewer decide what unknown means? It also needs real evidence. Reviewers can propose checks but gain no external facts through role names. Another model does not remove information gaps.

Question: which layer actually improves? Execution state and context handoff are the main repair; selective loading and compaction timing are secondary. No evidence requires changed model parameters. Locating measures by layer avoids expensive irrelevant optimization.

D.11｜Condense system diagnosis into an interview statement

Fix tasks and versions and define observable failure. Compare model input, output, tool ledgers and external state in traces to locate the earliest factual inconsistency. Distinguish causes with controlled counterexamples, fix necessary state and verification boundaries, then run paired regressions and gradual rollout. Models, context, tools, memory and workflows are adjustable, but not every failure requires rebuilding all of them.

Be ready to expand every object, time and branch behind that statement. Memorizing it is insufficient; "what if the file changed but the response vanished?" should lead to unknown, verification, idempotency boundaries, compaction retention and final-version acceptance.
