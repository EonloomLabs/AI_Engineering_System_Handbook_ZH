Why can one user task call the model more than once?

The LLM generates the next proposal, the harness carries out the approved action and hands the result back to the LLM. That is the outer task loop; inside each model call there is still token-by-token generation. One outer round of tool action is not the same as generating one token inside, and the two kinds of "loop" must not be conflated.

Call ID An ID linking a particular tool request to its result.
Tool result Content returned after actual execution by the program.
Context Information explicitly given to the model this round, not the entire computer state.

Input and conditions of use: Constructed read-only teaching task: config.txt contains timeout=30. Swimlanes show responsibilities without claiming a real commercial API call; data and action order are fixed.

1. 1. User task: read timeout in config.txt

The model has not seen the file on disk yet. Keep the task the user gave apart from what the environment actually contains.

未读取

2. 2. Model request: task＋read_file tool definition

A tool definition tells the model what it may propose; it grants no unlimited access.

提供工具

3. 3. Model output: call_id=c1, path=config.txt

This is only a request; it cannot yet be claimed that the file has been read. The call identifier matches the later result to this request.

请求待执行

4. 4. The harness validates, then reads the file

Once the path, permission and argument checks have passed, the program performs the file read; the model does not open the disk itself.

正在读取

5. 5. Tool result: timeout=30

This example presupposes that the file really does contain timeout=30. The returned result can be used to answer, but a successful read does not mean the file was modified.

读取成功

6. 6. Next input: original task＋call＋result

A second model call happens within the same user task. What has been added is actual evidence, so there is no need to go back to pretending and guessing.

证据入上下文

7. 7. Model answer: configured timeout is 30

This answer rests on the tool result in this example, not merely on general knowledge in the model's parameters.

回答完成

8. 8. The harness displays the answer; task ends

The final message ends this demonstration task; whether the output is complete and whether other tasks with side effects succeeded have to be judged separately.

结束

Why it is needed

A model can obtain new evidence through tools instead of stuffing everything into its parameters.

How to implement it

Organizes the loop as request, validation, execution, writing the result back, and deciding whether to carry on.

Possible costs and misreadings

Forgetting to write the tool result back makes the model request it again; treating the output text as proof of execution reports completion falsely.

How to tell whether it was done right

Cross-checks each turn's model input against the tool log and confirms that the result matches its call_id.
