JSON：構造化されたテキストであり、操作の実行ではない
JSONは、オブジェクト・配列・文字列・数値などでデータを表すテキスト形式です。波括弧のオブジェクトは、フィールド名を値へ対応させ、角括弧の配列は項目の順序を保ちます。JSONを解析して得るのはデータだけであり、中のツール名を自動的に実行することはありません。独立した例：{"path":"a.py","limit":3}には、二つのフィールドがあります。"3"は文字列、3は数値であり、Schemaはいずれかを要求できます。

以下は著者が設計したプロトコルレベルの教育用トレースであり、商用LLMの実行からエクスポートした実際のセッションではありません。ツール構造は簡略化したHarness独自形式で、特定の提供元のJSONフィールドと完全に一致する必要はありません。これは「Agentがモデルを複数回呼ぶとき、毎回具体的に何を渡し、何を受け取り、プログラムがどう利用するか」に答えるためのものです。[TOOLS][CODEX][COMPACT]

タスクはexclude機能のパス処理の修正です。制約は、パターンをプロジェクトのルートからの相対パスで照合し、包含規則は変更せず、コミットもデプロイもしないことです。最後の二項を残すのは、「コードを修正する」ことが、認可されていない納品操作へ拡大されるのを防ぐためです。

SchemaとStructured Outputs
Schemaは、フィールドや型などの構造上の規則です。構造化出力の仕組みは、規則に沿うデータをモデルが返しやすくします。フィールドが正当でも、対象ファイルの存在・認可・業務上の正しさとは同じではありません。独立した例：pathに文字列を要求するなら、{"path":3}は型が規則に合わず、{"path":"missing.py"}は構造が合っていても、ファイルが見つからないかもしれません。

Schemaは、どんな操作を表せるか、引数の名前は何かをモデルに伝えます。実際のシステムでは一部のツールだけを公開し、ほかのツールはディスカバリーの仕組みで必要に応じて読み込むかもしれません。ツールがすでにレジストリにあっても、毎ターンその完全な定義をコンテキストに入れる必要はありません。

工学的な仕組みと失敗に至る境界

承認後の引数の書き換え

最終的な操作から安定した識別用ダイジェストを計算し、フィールド順と対象環境を別々に変えます。フィールド順が変わっても論理的な識別は変わらず、対象環境が変われば元の承認は無効になる必要があります。

重要な境界：関数名だけを承認してはいけません。監査ログには実際の実行と、モデルに提示した結果の両方を記録します。

ソースコードや工学的根拠をさらにたどる：「結果の受け入れ拒否」が「操作は未発生」と誤読されることに、特に注意します。正常な経路だけでなく、キャンセル、バージョンの変化、結果不明の場合の振る舞いも照合します。

完全な仕組みと連続した例は、事前チェックと事後チェックを互いに代用できないのはなぜか？を参照してください。この節にも従来の導出と実験を残します。二か所の説明は異なる層を扱い、互いに代替するものではありません。

証拠と理解の限界：事後の確認時には、操作が完了済みの場合があります。CodexとClaude Codeでは、事後のblockの意味が異なります。結果をマスキングするときは、元のログも確認する必要があります。

検証の根拠：[C09] [C01] [D04]。ソースコードの確認範囲はコミット86e17e98c7f9と読んだパスに限ります。記事に記された経験、公開ドキュメント、独自の教育用実験は区別して示します。取得方法、読んだ範囲、制限を確認する。

B.4｜モデル呼び出しM2：次に不足する証拠の範囲を明確にする

M2は位置の結果に基づき、二つの読み取り操作を出します：

[
 {"kind":"tool_call","call_id":"c2","name":"read_file",
  "arguments":{"path":"pipeline/filter.py","start_line":1,"end_line":70}},
 {"kind":"tool_call","call_id":"c3","name":"read_file",
  "arguments":{"path":"tests/test_filter.py","start_line":1,"end_line":60}}
]

これらは読み取り専用で互いに依存しないため、並行に実行できますが、各結果には自身のIDを残す必要があります。c3が先に返っても、それがc2に属するわけではありません。ハーネスは「最初に戻ったものが最初の呼び出し」と対応付けるべきではありません。

次の教育用コードを読んだとします：

from fnmatch import fnmatchcase

def excluded(path, patterns):
    return any(fnmatchcase(path, pattern) for pattern in patterns)

def select_files(root, files, patterns):
    return [p for p in files if not excluded(str(p), patterns)]

この時点では、未使用のrootが唯一の誤りだとすぐ断定できません。filesに渡されるのが絶対パスか相対パスか、patternsの意味は何か、パスの区切り文字の規則はどうかを確認する必要があります。未使用の引数は手がかりであり、根本原因の証明ではありません。

c2とc3は並列に実行できるが、結果を到着順に誤ったIDへ対応付けてはいけない

M2の二つの読み取り専用呼び出しとr42を引き継ぎ、どちらが先に完了するかは仮定しません。

c2とc3は並列に実行できるが、結果を到着順に誤ったIDへ対応付けてはいけない
呼び出しID読み取るべきファイル結果の帰属規則
c2pipeline/filter.py、第1—70行c2の返却は実装の証拠欄だけに入れる
c3tests/test_filter.py、第1—60行c3の返却はテストの証拠欄だけに入れる
c3が先に着いても最初に出したc2と見なしてはいけない配列の位置でなく、call_idで関連付ける

並行実行が変えるのは待ち方であり、各操作の識別情報は失われません。ソースファイルとテストファイルを混同すると、モデルは存在しない実装に基づいて判断する可能性があります。

二つの読み取り専用操作は比較的独立しているため並行実行できます。ただし、後のパッチの書き込みは引き続きバージョンに結び付ける必要があります。読み取りが並行だからといって、その後のすべての書き込みまで並行にしてはいけません。

B.5｜モデル呼び出しM3：候補の説明から、反証可能な検査へ

検証すべき仮説を、検査可能な関係として書きます：

H1：匹配函数本身不支持此模式。
H2：调用方把绝对路径传入了相对模式匹配。
H3：测试期望与已确定的产品语义不一致。

この教育用トレースでは、独立した二つのアサーションを実行します。相対パスのgenerated/a.pyはgenerated/*に一致すべきですが、同じファイルの絶対パス/work/demo/generated/a.pyはこの相対パターンに一致しません。さらに、ユーザーが指定した製品の意味が本当にルートからの相対パスか確認します。これでH2が支持され、H1とH3はそれぞれの証拠で弱まります。

M3が出力するのはテスト実行の呼び出しc4であり、「検証済みです」ではありません：

{"kind":"tool_call","call_id":"c4","name":"run_tests",
 "arguments":{"target":"tests/test_filter.py","revision":"r42"}}

結果には、コマンド、リターンコード、実際に実行したテスト数、失敗したアサーションを含めるべきです。ここでの教育用トレースは、元の失敗が観察済みだと仮定しています。このページの例のテキストを、実際のリポジトリのテスト報告と見なしてはいけません。実行可能な仕組みの実験は発展読書を、決定的なプロトコルテストは計算と実行の連鎖の実験を参照してください。二組の例は、それぞれ入力条件と結果の範囲を説明します。

B.6｜モデル呼び出しM4：パッチが表すのは変更であり、結果ではない

修正候補では、正しい境界でパスをルートからの相対形式に変換し、ルートの外のパスの扱いを明示します。relative_toは失敗するかもしれません。エラーを出さないために例外を黙って握りつぶしたり、要求がないのにパスの意味全体を再設計したりしてはいけません。

{"kind":"tool_call","call_id":"c19","name":"apply_patch",
 "arguments":{
  "path":"pipeline/filter.py",
  "expected_revision":"r42",
  "patch_ref":"patch/p1",
  "purpose":"仅在匹配前构造根目录相对路径"
 }}

実行器はバージョンとパッチの前提を検査してからファイルを変更します。ここには三つの異なる状態があります。モデルがp1を提案し、実行器がc19を開始し、ファイルが実際にr43へ変わります。これらを一つの「修正済み」にまとめてはいけません。

別のユーザーが先にファイルをr42bへ変えた場合、expected_revisionが一致しないため、拒否するか、読み直して調整すべきです。古い断片に基づいて直接上書きすると、ユーザーの変更を壊します。バージョンの検査と書き込みの間にも並行処理の隙間があるため、ストレージの仕組みと組み合わせる必要があります。Pythonで「ハッシュを読んでから書く」だけでは、競合は自動的に解消しません。

B.7｜最も重要な障害の発生範囲：ファイルは変わったが、成功の結果が失われた

c19がファイルの置き換えを終えたものの、ランナーが成功を記録する前にクラッシュしたとします。モデルとタスク状態が知るのはタイムアウトだけで、外部のファイルはすでにr43です。

时间t1：记录 c19 pending
时间t2：执行 c19，文件 r42 → r43
时间t3：进程中断，成功响应未送达
时间t4：恢复时看到 c19 尚未确认

c19をfailedと記録して直接再試行すると、ファイルを再び変更する可能性があります。succeededと記録すれば、別の障害のタイミングでは偽りになるかもしれません。正しい状態はunknownであり、確認が必要です。

復旧器はinspect_operationを呼ぶか、対象のバージョン/パッチの効果を読み取ります。外部システムが冪等キーに対応していれば、c19または独立した業務キーで照会できます。ローカルファイルシステムでは、対象の内容と期待した変更が適用済みかを検査します。起きていないことを証拠が示す場合にだけ、適切な条件で再試行を許します。

ここで「ローカルの表が一つあれば分散環境でexactly-onceを実現できる」とは約束できません。状態表と外部の副作用が一つの原子的なトランザクション内になければ、隙間は残ります。エンジニアリングの目標は、結果を明確にし、危険な重複を避け、判定できない場合に制御された復旧を用意することです。

c19の応答が失われたとき、三か所の状態は同じではない

p1、c19、r42→r43という今回の変更を引き継ぎ、「タイムアウト」を「変更していない」と解釈しません。

c19の応答が失われたとき、三か所の状態は同じではない
時刻/対象実際の変化導ける結論
t1：タスク台帳c19=pending操作を登録済み
t2：ディスクp1を適用済み；r42→r43外部の副作用はすでに発生している
t3：プロセス/ネットワーク成功の応答が失われたそれによってディスクの変化を否定することはできない
t4：復旧するハーネスc19をunknownと記録して確認するr43と一致すればテストへ進み、パッチを繰り返さない

失敗の応答と応答の欠落は、同じではありません。ここで最も重要な対象はディスク上の事実であり、要約がそれをどう表現したかではありません。

復旧後は、まずp1が有効になったか確認します。直接やり直しても、無条件に成功と推測してもいけません。確認自体が失敗した場合は、unknownを維持する必要があります。

B.8｜長いセッションのコンパクション：失ってはいけない情報は何か

ここまでの履歴には、複数の検索、全ファイルの読み取り、失敗した試行が含まれるかもしれません。その後のタスクに最も重要なのは、目標、制約、確認済みの根本原因、現在のファイルのバージョン、未確認の操作、テストの状態、証拠の位置です。

誤った要約：

excludeの問題は修正済みで、納品の準備中です。

これは同時に三つの誤りを犯しています。実行不明を完了と記し、元のテスト結果を新しいバージョンへ誤用し、「コミットしない、デプロイしない」を失っています。短く流暢でも、復旧状態には適しません。

より適切な教育用の要約：

{
 "task":"t7",
 "goal":"exclude按根目录相对路径匹配",
 "constraints":["保留包含规则","不提交、不部署"],
 "confirmed_cause":{"claim":"绝对路径进入相对模式匹配",
   "evidence":["e/read-c2@r42","e/test-c4@r42"]},
 "patch":{"id":"p1","call_id":"c19","status":"unknown"},
 "workspace":{"last_confirmed":"r42","observed_candidate":"r43"},
 "next":"先核验c19，再对确认后的当前版本运行测试",
 "verification":{"current_patch_tested":false}
}

要約は元の証拠の代わりにはなりません。e/read-c2@r42では出所を取り戻せる必要があります。ソースが変わっていれば、古い証拠は過去の判断しか支えられず、現在の事実を直接表せないと分かる必要があります。

c19を引き続き検証するため、コンパクション時に残すフィールドは？

同じc19の未確認の時間帯を引き継ぎます。新しい要約は新たな実行の証明ではなく、元の操作記録が引き続き復旧の根拠です。

c19を引き続き検証するため、コンパクション時に残すフィールドは？
フィールド保持すべき値/関係失った場合のリスク
操作の識別情報task=t7，call=c19，patch=p1どの変更かを関連付けられない
実行の前提expected_revision=r42古いパッチを新しいファイルに適用する
現在の知識応答がなく、実行結果はunknown誤ってfailedと書くと、重複変更を誘発する
確認の入口対象のpipeline/filter.pyとp1の記録要約だけから完了したか推測するしかない

ここで重要なのは要約を長くすることではなく、次の操作を決める事実と未決の状態を残すことです。背景の雑談は省略できますが、unknownを失敗に変えてはいけません。

元のログや外部状態の確認を終えて初めて、タスク状態を適用済みまたは未適用へ進める根拠が得られます。要約がこの結論を自ら生み出すことはできません。

B.9｜コンパクションは履歴のその場での削除ではなく、状態の切り替え

まずコンパクション対象の履歴のスナップショットバージョンH17を取得し、要約候補C18を生成します。重要な制約、ツール呼び出しの対応、unknown状態、証拠の参照を検証します。安定したシステム指示、必要なツール定義、新しい要約を再構成し、現在のコンテキストを条件付きで置き換えます。

要約の生成中にユーザーが新しい指示を挿入し、現在の履歴がH18へ変わったなら、H17に基づく要約で新しいメッセージを無条件に上書きしてはいけません。新しいコンテキストに新しいメッセージを追加するか、スナップショットを調整し直せます。具体的な方針はランナーが決めます。本質は並行する状態更新の問題であり、「モデルにもっと丁寧に要約させる」ことで解決するものではありません。

コンパクション後のモデルリクエストM5には、元の認可範囲、上記の復旧状態、確認ツール、最新の観察を含めるべきです。以前の長いソース全文をすべて常駐させる必要はありませんが、モデルが必要としたときに証拠IDで読み直せるようにします。キャッシュのヒットは変わるかもしれませんが、それはコストに影響することであり、誤ったコンテキストを残す理由にすべきではありません。

B.10｜モデル呼び出しM5：先に確認し、書き込みを繰り返さない

M5はc19 unknownを見て、次を選びます：

{"kind":"tool_call","call_id":"c20","name":"inspect_operation",
 "arguments":{"operation_id":"c19","target":"pipeline/filter.py","patch_ref":"patch/p1"}}

教育用の返却結果：

{"call_id":"c20","status":"succeeded",
 "finding":{"operation_applied":true,"workspace_revision":"r43",
 "expected_change_present":true}}

ハーネスはここでc19を確認済みの完了へ更新できますが、タスク全体を完了と記録することはまだできません。新しいコードが機能と回帰の要件を満たすかは、次段階の検証の問題です。

返却結果が「ファイルは存在する」と述べるだけでは、パッチの適用済みを証明できません。内容がp1と部分的に一致する場合は、部分的な変更、外部の並行処理、確認不足を見分け、成功へ強制的に分類してはいけません。結果のSchemaは不確実性を表せる必要があり、true/falseだけでモデルに一方を選ばせるべきではありません。

B.11｜モデル呼び出しM6：テストをr43に結び付ける必要がある

M6はテストc21を呼び出し、結果ではr43上で実際にどのテストを実行したかを示すべきです。合格したら、変更の範囲とユーザーの制約を確認し、最終的な納品を行います。テスト中にソースが再び変わったなら、結果が自動的に新バージョンの正しさを証明するわけではなく、影響範囲を再確認する必要があります。

最終回答は、根本原因、変更範囲、検証の証拠、残る制限という構成にできます。コミットやデプロイを済ませたとは主張してはいけません。ユーザーが明示的に禁じ、この例でも実行していないためです。適切な終了条件は、必要な修正が確認済み、関連する検証が完了、確認待ちの重要な副作用がなく、権限を越えていないことです。

独立したReviewを丸一ターン必ず追加するという固定の要件はありません。変更のリスクが低く証拠が十分なら終了できます。モジュールをまたぐ意味や並行処理のリスクが未確認なら、対象を絞った検証を続けます。Reviewの価値は特定のリスクを取り除くことにあり、手順の名前にあるのではありません。

テストの証拠が無効化

まず作業ツリーr7をテストし、その後整形してr8になった場合、どの確認を再実行すべきか判断し、差分を記録します。

重要な境界：同じcommitでも同じ作業ツリーとは限らないため、内容のバージョンに結び付ける必要があります。

ソースコードや工学的根拠をさらにたどる：ソースコード、診断、パッチ、テストは、同じ対象を指す必要があります。正常な経路だけでなく、キャンセル、バージョンの変化、結果不明の場合の振る舞いも照合します。

仕組み全体と一連の例は、コードの証拠に、commitだけでなく作業ツリーのバージョンが必要なのはなぜか？を参照してください。この節でも従来の導出と実験を残しています。両者は異なる水準の説明であり、互いを置き換えるものではありません。

証拠と理解の限界：読み取り、パッチ、テストは作業ツリーのバージョンに結び付ける必要があります。最終ファイルが再び変わった後、以前のテストが新しい結果まで自動的に保証することはありません。

検証の根拠：[A06] [A15] [D07] [C02]。ソースコードの確認範囲はコミット86e17e98c7f9と読んだパスに限ります。記事に記された経験、公開ドキュメント、独自の教育用実験は区別して示します。取得方法、読んだ範囲、制限を確認する。

B.12｜面接官の追加質問：各ターンで全履歴を送り直すのか

必ずしもそうではありません。インターフェースによって、クライアントが完全な論理履歴を渡す場合も、サーバーに保存された応答やセッションを参照する場合もあります。サービスは今回利用できるコンテキストを組み立てる必要があります。論理履歴の連続、ネットワーク上の増分だけの送信、計算キャッシュのヒットは、三つの独立した側面です。

不透明なコンパクション状態を使う場合、クライアントはモデル内部の保持内容をフィールドごとに検査できないかもしれません。そのため、外部の永続状態にタスクの制約、操作結果、証拠の参照を残すことがさらに重要になります。エンジニアリング上の信頼性のすべてを、検査できない要約ブロック一つに賭けてはいけません。

もう一つの追加質問は、サブエージェントがこれらのツールと状態を自動継承するか、というものです。仮定してはいけません。製品と設定に応じて確認し、引き継ぎ時にはタスクに必要な最小限の証拠と権限を明示的に渡します。メインエージェントがMCPを持っていても、各サブエージェントがアクセスできるとは限りません。サブエージェントが「完了」と返しても、最終ワークスペースで統合が済み、テストに合格したことにはなりません。

この例を読んだら、ある事実が最初に分かった段階、変更する権限を持つ人、記録の担当、コンパクション後の復旧方法、タスクを閉じるのに十分な証拠を答えられるべきです。これらに答えられて初めて、エージェントの実行を理解したといえ、「思考—行動—観察」を暗記できるだけではありません。
