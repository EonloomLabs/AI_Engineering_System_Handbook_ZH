Q077｜因果マスク、パディングマスク、ブロックデコードのマスクをどう構成するか？

この問いで先に知ること因果マスクは未来の位置を禁じ、パディングマスクはプレースホルダーを除外します。古いキャッシュがある場合、クエリーの行数と読める列数は異なるため、正方形の三角表をそのまま写してはいけません。

中心となる回答

因果maskは未来の位置の読み取りを禁じます；padding maskは、実際の内容がないパディング位置を除外します。ブロックデコードでは、新しいブロックの局所インデックスを、既存プレフィックスの後に続く大域位置へ対応させる必要もあります。あるKeyを読めるかは、論理位置と有効性で判断すべきであり、左上に三角形を描くだけでは足りません。[TR][CACHE]

まず全入力を見てから、キャッシュの場面を見る

4個のTokenからなる系列で、行はクエリー位置、列はKey位置で、1は読み取り許可を表します：

       k0 k1 k2 k3
q0     1  0  0  0
q1     1  1  0  0
q2     1  1  1  0
q3     1  1  1  1

ここが下三角なのは、クエリーとKeyが同じ大域位置0から始まるためです。今、3トークンのキャッシュがあり、新たに2トークンが来るとします。Qの長さは2、Kの長さは5です。新しいクエリーの大域位置は3と4で、正しいmaskは次のとおりです：

       old0 old1 old2 new3 new4
new3     1    1    1    1    0
new4     1    1    1    1    1

一般式は次のとおりです：key_position ≤ past_length + local_query_index。もし直接tril(ones(2,5))を作ると、最初の行はold0だけ、二行目はold0とold1だけを見て、履歴の大半が誤って隠されます。それでも妥当な2×5行列なので、shapeの確認だけでは問題は見つかりません。

さらに次を加えます：padding。二つの系列の長さは3と5で、バッチ化では短い系列をパディングします。パディングされたKey位置にはアテンションの重みを与えるべきではありません。paddingのクエリー位置は演算子で計算される場合がありますが、有効な回答や学習目標として使うべきではありません。左paddingでは、配列の添字と実際のトークン位置がさらに分かれやすくなります。位置IDはモデルと実装の取り決めに従うべきであり、配列の添字だけを使ってはいけません。

キャッシュを使うデコーディングのマスクは、絶対位置に沿って埋める必要があり、小さな三角形をそのまま写してはいけない

さらに考える：maskの誤りを検出できるテストをどう書きますか？

まず、ここで使う対象と記号を知る
Dropout：学習時にランダムにゼロにするルール
一般的な倒置型Dropoutは、学習時に、破棄確率pで要素をランダムにゼロとし、残した項を1-pで割って、期待値の大きさを保ちます。評価モードでは、通常、このランダムな操作を無効にします。低水準の関数では、呼び出し側がp=0を明示する必要がある場合もあります。独立した例：p=0.5で、ある値2が一回のマスクで残されたら出力は4、破棄されたら0です。学習で、対応するモデルのパラメーターを永久に削除することではありません。

重みを固定し、dropoutを無効にして、まずプレフィックスの出力を保存します。その後で未来のトークンだけを変えても、プレフィックスに対応するlogitsは変わらないはずです。さらに、全系列・トークンごと・複数のブロック分割による推論の出力を比べ、妥当な浮動小数点の許容誤差内で一致することを確認します。意図的にmaskを外したり位置をリセットしたりしたら、テストは失敗すべきです。そうでなければ、狙った誤りをテストできていない可能性が高いです。

真偽値maskの意味が逆で、キャッシュ追加後にはis_causalが誤った側に揃う可能性もある

前提知識：第46課 · 第47課 · 第58課。読み進める順序：まず実行契約を確認し、次に反例と修復を見て、最後に限界を検証します。

正しい二つのAPIでも、組み合わせると誤る場合がある

PyTorchのSDPAでは、ブール値Trueは、その位置の参加を許可することを表します。一方、MultiheadAttentionのattn_maskでは、Trueはその位置が禁止されることを表します。単なる命名の小さな違いではありません。同じブールデータを直接再利用すると、可視関係が逆転します。[SDPA] [MHA]

ローカルでは、単位投影を使ってMHAと下位のSDPAを対応させます。MHAには~allowedを渡し、SDPAにはallowedを渡すと出力が一致し、反転しないと一致しません。このテストは「マスクの意味」だけを切り分けます。前の節で投影の転置を確認するために使った、非対称行列のテストと混同すべきではありません。

二つ目の落とし穴：正方形でない三角形には絶対位置が必要

キャッシュにはすでに3位置があり、新たに2個のQueryが来ると、K/Vの総長は5です。新しいQueryの絶対位置は3と4であり、0と1ではありません。正しい許可表は次のとおりです：

            Key位置 0  1  2  3  4
新Query位置3       1  1  1  1  0
新Query位置4       1  1  1  1  1

一方、PyTorch2.10のSDPAのis_causal=Trueは、正方形でない場合に左上合わせを使うため、2×5の三角表は10000 / 11000となります。これでは、制限すべきでない履歴を制限します。これは明確なバージョンの根拠があるインターフェースの契約であり、「モデルがコンテキストを忘れた」のではありません。[SDPA]

数値の反例で、誤りを一目で分かるようにする

Q/Kをすべて0にし、許可された各位置のスコアを同じにします。Vの値は1・2・3・4・5とします。正しい二行の平均は2.5・3.0ですが、左上三角では1.0・1.5になります。本書では、実際のSDPAでこの二つの経路を実行しています。

q_positions = torch.arange(3, 5)   # 今回の絶対位置
k_positions = torch.arange(5)      # 履歴 + 現在
allowed = k_positions[None, :] <= q_positions[:, None]
out = F.scaled_dot_product_attention(q, k, v,
                                     attn_mask=allowed,
                                     dropout_p=0.0)

この部分は、絶対位置を明示したマスクの方法です。これと衝突する自動の因果オプションを同時に有効にしないでください。実際のモデルアダプターがオフセットを処理済みの場合もあるため、呼び出しの境界を調べ、二重の補正を避ける必要があります。[CACHE]

中心となる回答

RoPEはQ/Kの各成分対を、位置に応じた角度で回転させます。二位置の回転後の内積に、相対的な位置の差が含まれるようにします。位置の整数を単純にToken IDに加えるものではありません。キャッシュを使う推論では、新旧トークンの論理位置を連続させるか、指定された位置の方針に合わせる必要があります。そうしなければ相対関係が変わってしまいます。[ROPE]

二次元回転から相対位置を導く

二次元ベクトルx=[a,b]について、位置pと周波数θの対応は次のとおりです：

R(pθ) x = [a cos(pθ) − b sin(pθ), a sin(pθ) + b cos(pθ)]

Qが位置p、Kが位置tにあるとき、内積は(R(pθ)q)ᵀ(R(tθ)k)です。R(pθ)ᵀ=R(-pθ)と回転の合成の性質を使うと、次が得られます：qᵀR((t-p)θ)k。したがって、位置情報は差t-pを通じて関連性に入ります。高次元のベクトルでは、成分のペアごとに異なる周波数を使い、複数の尺度の位置変化を与えます。

アテンションが位置の差だけに依存するという意味ではありません。qとk自体は、テキストの内容と前の層の表現で決まります。RoPEは相対位置の構造を与え、内容の照合は引き続き学習した投影が担います。任意の長さに当然に汎化できるようにするとも言えません。学習分布を越える位相の組み合わせは、劣化をもたらす場合があります。

プレフィックスの長さをP=100とし、新しいトークンは本来位置100にあるとします。そのQ/Kを誤って位置0で回転させ、古いKは0から99のまま保存すると、モデルが読む「距離」は実際の距離ではなくなります。テンソルの長さ・dtype・キャッシュの連結軸がすべて正しくても、logitsは全系列の順伝播からずれている場合があります。

論理位置はモデルの系列内でのトークンの位置、物理キャッシュスロットはK/Vを置く配列のマス、有効長は非PAD内容の量を表します。単純なPADなし・スライディングウィンドウなしの例では、たまたま一致しますが、それを理由に開発でフィールドをまとめてはいけません。固定バージョンのTransformersのキャッシュ説明も、cache_positionとpaddingの内容を明確に区別しています。[CACHE]

キャッシュの再利用時に位置の回転を重複実行してはいけない

一般的なRoPEの実装は、Q/Kを先に回転させ、回転後のKをキャッシュします。次のターンで古いKを読むとき、その元の位置でさらに回転させると、角度を二度加えることになります。本書の二次元の反例です：[1,0]を90°回転させると[0,1]になり、さらに90°回転させると[-1,0]になります。形状はまったく同じでも、意味は完全に変わります。未回転の量をキャッシュする実装では、役割は逆になります。キャッシュの表現形式は契約の一部です。

スライディングウィンドウでも、絶対位置をゼロへ戻してはいけない

スライディングウィンドウで古いスロットを除いた後、保存長を一定に保っても、次のトークンの論理位置は通常増え続けます。スロットの添字を位置と見なし、毎回0からやり直すと、位置の位相と可視性が変わります。RoPEのスケーリング設定・位置オフセット・アダプターを変えても、元のキャッシュが使えなくなる場合があります。

中心となる回答

計算グラフに沿って順に微分する

まず、ここで使う対象と記号を知る
∂・∇：偏導関数と勾配
∂L/∂wは、他の独立変数を固定し、wをわずかに変えると、損失Lがどう変わるかを問います。複数のパラメーターについて、この変化率をまとめたものが勾配∇Lです。これらは導関数の記号であり、通常の二つの数を直接割ることではありません。独立した小さな例：L=w²なら、w=3での勾配は6です。最も単純な更新w←w−η×6のηは、学習率です。
まず、ここで使う対象と記号を知る
G・dQ・dW：逆伝播の中間勾配
G=∂L/∂Oは、通常、後続の演算から返された、現在の出力Oに対する損失の勾配です。逆伝播の疑似コードでは、∂L/∂QをdQ、∂L/∂WをdWと略記します。形状は微分する対象に対応し、特徴の次元dをQに掛けることではありません。先に順伝播のO=AVがあり、その後Gを受け取って初めて、dV=AᵀGとdA=GVᵀを計算できます。dAが変えるのは割合の経路、dVが変えるのは内容の経路です。

dV = AᵀG
dA = GVᵀ

まず、ここで使う対象と記号を知る
⊙：要素ごとの積であり、行列積ではない
要素ごとの積は、形状を合わせた後、同じ位置の数を掛け、さらにある次元に沿って足すことはしません。式で行列を並べた表記や@は、通常、行列積を表します。両者を置き換えることはできません。独立した小さな例：[1,2]⊙[3,4]=[3,8]で、内積なら11です。ゲーティング付きフィードフォワードの⊙は、特徴ごとに別の経路を調整します。
ds = a ⊙ (g − sum(a ⊙ g))

ここで引くのは行全体の重み付き和であり、省略できません。結果の各成分の和は0となり、「行全体のスコアに定数を加えてもsoftmaxは変わらない」という性質に一致します。最後に：

dQ = dS K / √d
dK = dSᵀ Q / √d

Q/K/Vを同じXから投影した場合、Xの勾配は、三つの分岐それぞれに投影の転置を掛けた和に、残差から直接戻る勾配を加えたものです。マルチヘッドの軸の並べ替えと連結は、逆伝播で対応する逆変換を行う必要があります。

有用な診断の一つとして、最初の位置の出力だけを損失に参加させます。因果maskの下では、未来のK/Vはこの損失から勾配を得ないはずです。未来の位置にゼロでない依存があれば、maskやインデックスが誤っている可能性があります。このテストが見るのはタスクの意味であり、数値的な微分だけではありません。
